# Röttger et al. Rendering

Also called: Pre-integration, Pre-integrated Volume Rendering, Texture-based VR, Texture-Based Volume Rendering with Pre/Post-Classification

## Overview
Röttger et al. Rendering is a technique that mitigates the high computational cost of volume integration by approximating the rendering integral and moving the computation to a pre-process [S1]. It computes a 3D lookup table of colors and opacities parameterized by front scalar value, back scalar value, and distance, which is stored in a 3D texture for hardware-accelerated lookups during rendering [S1, S2]. This method builds on [AR mapping to 3D texture](884-ar-mapping-to-3d-texture.md) by using the 3D texture not just for static data storage, but to evaluate the volume composition operator directly via texture interpolation [S4]. It is distinguished from standard ray casting by replacing per-voxel integration with texture lookups, and from pure pre-classification by supporting arbitrary transfer functions including isosurface effects through the parameterization of the lookup table [S2].

## How it works
The method consists of two phases: a pre-processing phase to generate the lookup table and a rendering phase to use it [G].

### Inputs and Outputs
*   **Inputs:** Volume scalar data, transfer function (mapping scalar to color and opacity), and camera/view parameters [S1].
*   **Outputs:** A 3D texture containing pre-integrated color and opacity values, and the final rendered image [S1].

### Data Structures
The core data structure is a 3D texture cube [S4].
*   **Dimensions:** The sources specify a tested limit of $512^3$ voxels [S4]. A specific implementation used a $256^3$ cube [S4].
*   **Format:** 4-component float texture (RGBA) [S4].
*   **Content:**
    *   **X-axis:** Discrete front scalar values [S1, S2].
    *   **Y-axis:** Discrete back scalar values [S1, S2].
    *   **Z-axis:** Distances (thickness) between front and back faces [S1, S2].
    *   **RGB Channels:** Store the pre-integrated color values [S1, S2].
    *   **Alpha Channel:** Stores the pre-integrated opacity values [S1, S2].

### Pre-processing: Lookup Table Generation
The lookup table is computed offline or at initialization [S1]. For a given transfer function, the integral of the volume rendering equation is computed for all combinations of front scalar $s_f$, back scalar $s_b$, and thickness $l$ [S2].

1.  Iterate over all discrete values of front scalar $s_f$ (x-axis) [S1].
2.  Iterate over all discrete values of back scalar $s_b$ (y-axis) [S1].
3.  Iterate over all discrete distances $l$ (z-axis) [S1].
4.  Compute the integrated color $C$ and opacity $\alpha$ for the triplet $(s_f, s_b, l)$ using the current transfer function [S1].
5.  Store $C$ in the RGB channels and $\alpha$ in the Alpha channel of the 3D texture at coordinates $(s_f, s_b, l)$ [S1].

*Partial Pre-integration:* To avoid recomputing the table when the transfer function changes, static components (exponentiation of distances) can be stored separately from dynamic components (color and opacity) [S1].

### Rendering Phase
During rendering, the pre-computed 3D table is used for lookups at each step in the volume [S1]. The method interpolates scalar values and ray segment lengths across the projected geometry to address the 3D texture [S3].

1.  **Projection:** Project the volume cells (e.g., tetrahedra or subdivision polygons) onto the image plane [S2, S3].
2.  **Interpolation:** For each fragment or pixel covered by a projected cell, interpolate three values across the polygon:
    *   $s_f$: The scalar function value on the front face [S3].
    *   $s_b$: The scalar function value on the back face [S3].
    *   $l$: The ray segment length (thickness) through the cell [S3].
3.  **Lookup:** Use the interpolated values $(s_f, s_b, l)$ as texture coordinates (addresses) into the 3D texture [S3].
4.  **Retrieval:** Sample the 3D texture to retrieve the pre-integrated color $C_{pre}$ and opacity $\alpha_{pre}$ [S3].
5.  **Compositing:** The retrieved color and opacity are blended into the framebuffer using standard alpha blending to simulate the volume composition operator [S4].

### Pseudocode
The following pseudocode illustrates the rendering lookup and blending process [G]. It assumes the 3D texture `LUT` is already populated [G].

```python
def render_fragment(s_f, s_b, l, LUT_dims, framebuffer_color, framebuffer_opacity):
    """
    s_f: interpolated scalar value at front face
    s_b: interpolated scalar value at back face
    l: interpolated ray segment length (thickness)
    LUT_dims: tuple (D_x, D_y, D_z) defining the 3D texture resolution
    framebuffer_color: current color in framebuffer
    framebuffer_opacity: current opacity in framebuffer
    """
    D_x, D_y, D_z = LUT_dims
    # 1. Normalize coordinates to [0, 1] range
    u = s_f / D_x
    v = s_b / D_y
    w = l / D_z

    # 2. Clamp to valid range to handle boundary conditions
    u = max(0.0, min(1.0, u))
    v = max(0.0, min(1.0, v))
    w = max(0.0, min(1.0, w))

    # 3. Lookup pre-integrated color and opacity
    # tex3D performs trilinear interpolation
    color, opacity = LUT.sample(u, v, w)

    # 4. Blend with existing framebuffer color
    # C_out = C_src * alpha_src + C_dst * (1 - alpha_src)
    final_color = color * opacity + framebuffer_color * (1.0 - opacity)
    final_opacity = opacity + framebuffer_opacity * (1.0 - opacity)

    return final_color, final_opacity
```

### Parameters
*   **Transfer Function:** Maps scalar values to color and opacity [S1].
*   **Texture Resolution:** Determined by the number of discrete steps for $s_f$, $s_b$, and $l$ [S1].
*   **Lighting Model Components (Variant):** In object-space implementations using gradients, parameters include Ambient ($K_a$), Diffuse ($K_d$), Specular ($K_s$), Shininess, Light Color, Light Position, and Eye Position [S4].

### Edge Cases and Pitfalls
*   **Transfer Function Changes:** Recomputing the lookup table is costly [S1].
*   **Gradient Sign Preservation (Variant):** If gradients are stored in the texture (as in the object-space variant), negative gradients must be normalized to $[-1, 1]$ and shifted to $[0, 1]$ for storage: $\text{stored} = (\nabla f + 1.0) / 2.0$ [S4].
*   **Texture Access Performance:** 3D texture access is slower than 2D due to irregular memory access patterns and the cost of trilinear interpolation (8 texture accesses vs 4 for bilinear) [S4].
*   **Fill Rate Limitation:** Performance is primarily limited by fill rate [S4].
*   **Alpha Test Effectiveness:** The benefit of alpha testing (skipping transparent fragments) is inversely proportional to data density [S4].

## Subtopics

### Object-Space Texture Rendering
*   **What it is:** A variant where volume data (gradient and opacity) is loaded into a 3D texture, and rendering is performed by rotating the camera and drawing texture slices (object-space) rather than ray casting.
*   **Difference:** Uses hardware interpolation of gradients for shading and blending, rather than pre-integrated color lookup for composition. It supports object-oriented geometry rendering.
*   **When to choose:** When shading quality is prioritized over the physical accuracy of volume composition, or when implementing specific lighting models on the GPU.
*   **Link:** [Object-Space Texture Rendering](885-object-space-texture-rendering.md)

### Partial Pre-integration
*   **What it is:** A technique that separates the static, computationally expensive components of the integration (exponentiation of distances) from the dynamic components (color and opacity).
*   **Difference:** Allows interactive changes to the transfer function with virtually no overhead, unlike full pre-integration which requires table regeneration.
*   **When to choose:** When the user needs to interactively adjust the transfer function during rendering.
*   **Link:** [Partial Pre-integration](886-partial-pre-integration.md)

### Pre-classification vs Post-classification
*   **What it is:** Pre-classification applies the transfer function to voxel samples before interpolation; post-classification interpolates samples first, then applies the transfer function [S4].
*   **Difference:** Pre-classification results in well-defined images; post-classification results in diffuse images because interpolation is not commutative with the transfer function [S4].
*   **When to choose:** Use pre-classification for sharp, well-defined boundaries [S4].
*   **Link:** [Classification Techniques](887-classification-techniques.md)

## Operating characteristics
*   **Time Complexity:** Rendering time is dominated by texture lookups and blending, which is $O(N)$ where $N$ is the number of fragments/pixels [G].
*   **Memory Complexity:** The 3D texture requires $D_x \cdot D_y \cdot D_z \cdot 4$ floats [S4].
*   **Measured Performance:** Performance is primarily limited by fill rate. On a GeForce FX chip (1.6 billion texels/sec), high zoom levels significantly decreased FPS due to increased fragment generation [S4].
*   **Scaling:** Performance degrades with higher zoom levels and higher data density (for alpha testing benefits) [S4].
*   **Strengths:** Substantial performance improvements over standard ray casting; supports arbitrary transfer functions including isosurface effects; leverages hardware interpolation [S1, S2].
*   **Limitations:** 3D texture access is slower than 2D; fill rate limited; pre-processing cost for transfer function changes; image quality can suffer from banding if 2D textures are used instead of 3D [S4].
*   **When to use:** When interactive performance is required and the transfer function is static or can be handled via partial pre-integration [S1].
*   **When not:** When the transfer function changes frequently without partial pre-integration, or when fill rate is the bottleneck and high zoom levels are expected [S4].

## Background
The method was introduced by Röttger et al. [S1, S2, S3]. It is part of the broader development of texture-based volume rendering techniques that utilize GPU hardware for acceleration [S4]. The approach builds on the idea of pre-integration to approximate the volume rendering integral, moving computation from the per-voxel ray casting step to a pre-process [S1]. It is often compared with other texture-based methods such as those by Engel, Kraus & Ertl [S4, S1] and Weiler et al. [S2, S3].
