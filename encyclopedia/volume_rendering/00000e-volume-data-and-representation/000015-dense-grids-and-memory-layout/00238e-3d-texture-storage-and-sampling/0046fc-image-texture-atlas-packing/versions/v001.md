# Image Texture Atlas Packing

Also called: 2D Texture Atlas Emulation, ImageTextureAtlas, WebGL 1.0 3D Texture Emulation, X3DTexture2DNode

## Overview
Image Texture Atlas Packing is a technique to represent 3D volumetric data (e.g., MRI/CT scans) as a set of 2D image slices arranged into a single 2D texture (atlas) to emulate 3D textures in WebGL 1.0, which lacks native 3D texture support [S1]. It sets itself apart from [3D Texture Storage and Sampling](3064-3d-texture-storage-and-sampling.md) by avoiding the need for hardware 3D textures, instead relying on fragment shader resampling to simulate 3D interpolation [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D volume dataset defined by dimensions $(D_x, D_y, D_z)$, where $D_z$ is the number of 2D slices. Optionally, surface normals (gradients) or transfer function data.
*   **Output:** A single 2D texture (atlas) containing all slices, and a sampling mechanism in the fragment shader that reconstructs 3D coordinates from 2D texture coordinates.

**Data Structures:**
The method uses the `ImageTextureAtlas` node definition (based on X3D `X3DTexture2DNode`) [S1]. Key fields include:
*   `numberOfSlices` (SFInt32): Total number of slices $D_z$.
*   `slicesOverX` (SFInt32): Number of slices tiled along the S (U) axis.
*   `slicesOverY` (SFInt32): Number of slices tiled along the T (V) axis.
*   `channels` (SFString): Specifies which color channels store data. Default is `"R"`. Can include `'G'`, `'B'`, `'A'` to store larger datasets or gradient vectors [S1].
*   `sortOrder` (SFString): Tiling order. `"ROW"` (default) tiles Z-axis slices contiguously in the row of the matrix. `"CHANNEL"` stores the next Z-axis slice in the contiguous color channel [S1].
*   `containerField` (SFString): Targets the input field of the parent node (e.g., `'voxels'` for `X3DVolumeDataNode` or `'surfaceNormals'` for `X3DVolumeStyleNode`) [S1].

**Packing Layout:**
1.  **ROW Order:** Slices are arranged in a 2D grid. If `slicesOverX` is $N_x$ and `slicesOverY` is $N_y$, the slice at index $k$ (where $0 \le k < D_z$) is located at grid position $(x, y)$ where $x = k \pmod{N_x}$ and $y = \lfloor k / N_x \rfloor$. Within the atlas, the slice occupies a rectangular region.
2.  **CHANNEL Order:** The first slice is stored in the Red channel of the first grid cell. The second slice is stored in the Green channel of the first grid cell, and so on. This allows packing more slices into a single grid cell if the texture supports multiple channels [S1].
3.  **Gradient Encoding:** For surface normals, the gradient vector $(\partial_x, \partial_y, \partial_z)$ for each voxel is encoded into the RGB channels of the atlas: R for X, G for Y, B for Z [S1].

**Sampling (Fragment Shader):**
To emulate 3D texture sampling, the fragment shader receives 3D texture coordinates $(u, v, w)$ corresponding to the volume space.
1.  Map $(u, v)$ to the atlas grid coordinates $(u_{grid}, v_{grid})$.
2.  Determine the slice index $k$ from $w$.
3.  Map $k$ to the atlas 2D coordinates $(u_{atlas}, v_{atlas})$ based on `sortOrder` and `channels`.
4.  Perform bilinear interpolation on the 2D texture at $(u_{atlas}, v_{atlas})$ to get the value for slice $k$.
5.  Perform trilinear interpolation by interpolating between the values of slices $k$ and $k+1$ (or using the $w$ coordinate to blend between the two nearest slices in the atlas if they are adjacent in memory) [S1].

*Note: The exact shader implementation details for trilinear interpolation from a 2D atlas are not provided in the sources, but the method states it is performed "at the pixel level" [S1].*

**4D Rendering Implementation:**
For time-evolving data:
1.  Create an atlas for each time step.
2.  Encode atlases into a video (e.g., mp4) [S1].
3.  Play video in a hidden HTML5 `<video>` element [S1].
4.  Link a dynamic `ImageTextureAtlas` to a canvas of the same size [S1].
5.  Update canvas content via JavaScript timer to match video frames [S1].
6.  X3DOM updates GPU texture data [S1].

**Dynamic Transfer Function Editing:**
Use the 2D canvas API to modify the TF texture directly, enabling native HTML5 transfer function editors [S1].

**Edge Cases and Pitfalls:**
*   **GPU Texture Size Limit:** The amount of volume data is restricted by the maximum 2D texture size of the GPU [S1].
*   **Precision Loss:** Video encoding for 4D rendering can cause potential loss of accuracy [S1].
*   **Refresh Time:** Texture data refresh time may impact real-time performance [S1].
*   **WebGL 1.0 Compatibility:** The method is designed for WebGL 1.0, which does not support 3D textures (Texturing3D component) [S1].

## Operating characteristics
*   **Time Complexity:** Sampling requires additional shader computations to map 2D atlas coordinates to 3D volume coordinates and perform interpolation, increasing fragment shader complexity compared to native 3D texture sampling [S1].
*   **Memory Complexity:** Memory usage is determined by the 2D texture size. Using multiple channels (`channels` field) allows packing more data into the same texture footprint, effectively increasing capacity up to the GPU's 2D texture limit [S1].
*   **Performance:** Less memory expensive than full volume rendering for techniques like MPR, as it only uses data in the neighborhood of the defined plane, making it suitable for less powerful GPUs like mobile devices [S1].
*   **Strengths:** Enables 3D volume rendering in WebGL 1.0 environments; supports dynamic updates via Canvas API; compatible with X3D standard.
*   **Limitations:** Limited by 2D texture size; potential precision loss in 4D video-based updates; requires custom shader logic for 3D interpolation.

## Background
The method was proposed to enable interactive visualization of volumetric data in Web-based GPU accelerated volume rendering algorithms, specifically addressing the lack of 3D texture support in WebGL 1.0 [S1]. It builds on the method proposed by Congote et al. (2011) [S1]. The `ImageTextureAtlas` node was introduced as part of community-driven extensions to the X3D volume rendering component [S1]. It is used in X3DOM for web-based volume rendering [S1].
