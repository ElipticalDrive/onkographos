# Hardware Volume Rendering Pipeline with Pixel Textures

Also called: Dependent Texture Classification, Dependent Texture Volume Rendering, Hardware Volume Rendering Pipeline (Pixel Texture Based), Pixel Texture Classification, Pixel Texture Shading on SGI V Series, SGI Octane2 Hardware Volume Rendering with Pixel Textures, VGH/QN Pipeline

## Overview
This method implements volume rendering on hardware supporting the OpenGL pixel texture (dependent texture) extension, specifically targeting architectures like the SGI Octane 2 with V-series graphics cards [S1, S2]. It solves the problem of applying multi-dimensional transfer functions (classification and shading) to volume data by using color fragments from a rendered slice to generate texture coordinates for a 3D lookup texture [S1, S2]. Unlike standard rasterization where shading is computed per-fragment during draw calls, this pipeline requires rendering the raw data slice to an auxiliary buffer first, then applying the pixel texture operation via a copy or draw operation to replace fragment colors with classified/shaded values [S1]. It distinguishes itself from sibling methods like [3D Texture Proxy Geometry](870-3d-texture-proxy-geometry.md) by avoiding geometry approximation and from [PixelFlow Volume Rendering](3443-pixelflow-volume-rendering.md) by relying on the specific hardware-dependent texture read mechanism rather than a custom streaming architecture.

## How it works
The pipeline separates the volume into a **Data Volume** (for classification) and a **Shading Volume** (for lighting). The core mechanism uses the pixel texture extension, which treats color fragment channels as texture coordinates to look up replacement values in a 3D texture [S1, S2].

### Inputs and Outputs
*   **Input:** A 3D volume dataset.
*   **Output:** A 2D image (frame buffer) representing the volume projection.
*   **Auxiliary Data:** A scratch/auxiliary buffer is required for hardware that does not support per-fragment dependent texture reads during rasterization (e.g., SGI V-series) [S1].

### Data Structures and Layout
The method relies on two primary 3D textures, spatially coincident with the volume geometry [S1, S2].

1.  **Data Volume (VGH):**
    *   **Purpose:** Encodes classification parameters.
    *   **Layout:** RGB 3D texture.
    *   **Components:**
        *   Red ($R$): Data Value ($V$), 8-bit unsigned integer (0–255) [S1, S2].
        *   Green ($G$): Gradient Magnitude ($G$), 8-bit unsigned integer (0–255) [S1, S2].
        *   Blue ($B$): Second Derivative ($H$, Hessian), 8-bit unsigned integer (0–255) [S1, S2].
    *   **Note:** Full 8-bit resolution is used for $V$ and $G$ [S2]. The $H$ axis uses limited resolution, represented as "sheets" for negative, zero, and positive values [S2].

2.  **Quantized Normal Volume (QN) or Normal Volume:**
    *   **Purpose:** Encodes surface normals for shading.
    *   **Layout A (Quantized):** RGB 3D texture.
        *   Red ($R$): First 8 bits of a 16-bit unsigned short normal index [S1, S2].
        *   Green ($G$): Second 8 bits of the 16-bit unsigned short normal index [S1, S2].
        *   Blue ($B$): Unused or padding [S1].
    *   **Layout B (Scaled/Biased):** RGB 3D texture.
        *   Red ($R$): Normal $x$ component, scaled and biased to [0, 1] [S1, S2].
        *   Green ($G$): Normal $y$ component, scaled and biased to [0, 1] [S1, S2].
        *   Blue ($B$): Normal $z$ component, scaled and biased to [0, 1] [S1, S2].

3.  **Transfer Function Textures:**
    *   **Classification Texture:** A 3D texture where the lookup coordinates are derived from the VGH data. The size along the $H$ axis is small (3 entries: negative, zero, positive) [S2].
    *   **Shading Texture:** A 2D or 3D texture (depending on hardware) that maps quantized normals to lighting results [S1].

### Parameters
*   **Interpolation:** Nearest-neighbor interpolation is used for pixel texture lookups to avoid blurring classification boundaries [S1].
*   **Quantization:** 16-bit quantization for normals [S1].
*   **Resolution:** 8 bits per channel for $V$ and $G$ [S2].

### Algorithm Steps
The rendering process is performed slice-by-slice along the view direction.

1.  **Render Data Slice:**
    Render a 2D slice of the **Data Volume (VGH)** to the **scratch buffer**. The fragment shader (or fixed-function pipeline) outputs the raw $V, G, H$ values as RGB color.
    *   *Hardware Note:* On SGI V-series, this must be done via `glDrawPixels` or `glCopyPixels` because pixel texture operations do not occur directly during rasterization [S1].

2.  **Apply Classification (Pixel Texture Lookup):**
    Perform a pixel texture operation on the scratch buffer using the **Classification Texture**.
    *   The RGB values from the scratch buffer (representing $V, G, H$) are scaled to $[0, 1]$.
    *   These scaled values serve as texture coordinates $(u, v, w)$ into the 3D Classification Texture.
    *   The color at these coordinates replaces the original fragment color.
    *   *Second Derivative Handling:* The $H$ coordinate maps to one of three "sheets" (negative, zero, positive). The opacity on the center sheet (zero) is controlled by classification widgets. The opacity on outer sheets is scaled by a "boundary emphasis" slider [S2].

3.  **Apply Shading (Optional):**
    If shading is enabled:
    *   Render a matching slice from the **Shading Volume** (either QN or Normal volume) to the scratch buffer (or a separate buffer).
    *   Apply a pixel texture lookup using the **Shading Texture**.
        *   If using QN: The 16-bit normal index is split into two 8-bit channels (R, G) to form 2D coordinates $(u, v)$ for a 2D shading texture [S1].
        *   If using Normal Volume: The RGB components form 3D coordinates for a 3D shading texture [S1].
    *   The resulting color is the shaded color.
    *   *Modulation:* The shaded color is multiplied (modulated) with the classified color from Step 2 [S1].

4.  **Composite:**
    Copy the processed slice from the scratch buffer to the frame buffer, blending it with previously rendered slices (typically using front-to-back or back-to-front alpha blending) [S1].

### Pseudocode
```python
# Initialization
scratch_buffer = allocate_2d_texture(width, height, format=RGBA)
frame_buffer = current_framebuffer

# Pre-computation (Software or Hardware)
# Generate Classification Texture based on V, G, H transfer functions
classification_tex = create_3d_texture(size_v=256, size_g=256, size_h=3)
# size_h=3 corresponds to negative, zero, positive second derivative sheets

# Generate Shading Texture (if shading enabled)
# For Quantized Normals: 2D texture mapping 8-bit R, 8-bit G to color
shading_tex = create_2d_texture(size_r=256, size_g=256) 
# For Normal Volumes: 3D texture mapping scaled RGB to color
# shading_tex = create_3d_texture(size_r=256, size_g=256, size_b=256)

# Rendering Loop (Back-to-Front or Front-to-Back)
for slice_index in range(num_slices):
    # 1. Render Data Slice to Scratch Buffer
    # Output raw V, G, H as RGB
    bind_texture(data_volume_vgh)
    render_slice(slice_index, target=scratch_buffer)
    
    # 2. Apply Classification via Pixel Texture
    # Hardware extension: use fragment color as texture coords
    bind_texture(classification_tex)
    enable_pixel_texture_extension()
    copy_pixels(scratch_buffer, target=scratch_buffer) # Replaces colors in scratch buffer
    
    # 3. Apply Shading (if enabled)
    if shading_enabled:
        # Render shading volume slice to a temporary buffer or reuse scratch if supported
        # Note: Some hardware requires separate buffers or specific copy operations
        bind_texture(shading_volume_qn_or_normal)
        render_slice(slice_index, target=scratch_buffer_shading)
        
        bind_texture(shading_tex)
        enable_pixel_texture_extension()
        copy_pixels(scratch_buffer_shading, target=scratch_buffer_shading)
        
        # Modulate classified color with shaded color
        # This step may require a multi-texture pass or fragment shader if available
        # On older hardware, this might be done via glTexEnv or separate blending
        modulate_colors(scratch_buffer, scratch_buffer_shading)

    # 4. Composite to Frame Buffer
    bind_texture(scratch_buffer)
    enable_blending()
    copy_pixels(scratch_buffer, target=frame_buffer)
```

### Edge Cases and Pitfalls
*   **Scratch Buffer Size:** When updating the shading volume in hardware, the quantized normal slices must be smaller than the scratch buffer's dimensions [S1].
*   **Hardware Flexibility:** Some hardware implementations do not support generating the shading pixel texture by rendering a point with its normal to the frame buffer and copying it [S1].
*   **Performance:** The need for scratch buffers and copy operations (on SGI V-series) is expensive. Newer hardware (e.g., GeForce 3) supports per-fragment dependent texture reads, eliminating the scratch buffer but constraining 3D transfer functions to be separable (2D for V/G, 1D for H) due to 2D dependent texture read limits [S1].
*   **Second Derivative Interpolation:** The second derivative axis must maintain the notion of sign via scale and bias to properly interpolate between the negative, zero, and positive sheets [S2].

## Subtopics

### [Multi-Pass/Multi-Texture Shading](5653-multi-pass-multi-texture-shading.md)
A technique for adding interactive shading to the hardware volume rendering pipeline by decoupling classification and lighting calculations into separate rendering passes. It distinguishes itself from single-pass methods by utilizing multiple textures and pipeline stages to handle complex lighting models, such as gradient-based enhancement, without significant performance penalties.

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels projected, but with high constant factors due to memory copies (scratch buffer) on older hardware [S1].
*   **Memory Complexity:** Requires storage for the Data Volume (VGH), Shading Volume (QN/Normal), and auxiliary scratch buffers [S1, S2].
*   **Performance:** On SGI V-series, performance is limited by the need to render slices to a scratch buffer and then copy/pixel-texture them [S1]. On GeForce 3, performance is improved by eliminating scratch buffers but limited by 2D dependent texture reads, requiring separable transfer functions [S1].
*   **Strengths:** Allows for complex multi-dimensional transfer functions (V, G, H) and interactive shading [S1, S2]. The pixel texture extension allows arbitrary function evaluation via lookup tables [S1].
*   **Limitations:** Hardware-dependent. Requires specific extensions (pixel textures). Older hardware requires expensive copy operations [S1].

## Background
This method was developed for the SGI Octane 2 with V-series graphics cards and later adapted for nVidia GeForce 3 series [S1]. It relies on the OpenGL pixel texture (dependent texture) extension, which was useful in computer graphics and visualization for its ability to use color fragments to generate texture coordinates [S1, S2]. The approach was described in papers by Mark Meyer et al. (2001) focusing on interactive volume rendering using multi-dimensional transfer functions [S1, S2].
