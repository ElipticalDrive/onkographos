# 3D Texture Storage

Also called: 3D Texture Voxel Storage, 3D texture voxel lookup, Texture-based Voxel Storage

## Overview
3D Texture Storage maps a 3D voxel grid into a hardware-accelerated 3D texture resource, leveraging native texture sampling units for coordinate indexing [S2, unofficial]. It solves the problem of inefficient memory access patterns in ray traversal by storing spatially adjacent voxels contiguously in memory, thereby improving cache locality compared to linear byte buffers [S1, unofficial]. It differs from raw buffer storage by delegating 3D coordinate indexing to the texture hardware, though it introduces specific pitfalls regarding coordinate rounding during sampling [S2, unofficial].

## How it works
**Inputs:** A 3D voxel grid of dimensions $W \times H \times D$ (width, height, depth) and a ray defined by origin $\mathbf{o}$ and direction $\mathbf{d}$ [G].
**Outputs:** Voxel value (e.g., density, color, or occupancy) at a specific 3D coordinate [S2, unofficial].

**Data Structures:**
The primary data structure is a 3D texture resource (e.g., `Texture3D<uint>` in HLSL) [S1, unofficial].
*   **Layout:** Voxels are stored in row-major order. The linear index $v$ for a voxel at integer coordinates $(x, y, z)$ is:
    $$ v = x + y \cdot W + z \cdot W^2 $$
    This layout ensures spatially adjacent voxels are contiguous in memory [G].
*   **Access:** Direct load operations (e.g., `voxels.Load(int4(p, 0)).r`) are used for point sampling to avoid hardware interpolation overhead when binary occupancy is required [S1, unofficial].

**Steps:**
1.  **Calculate Ray Position:** Determine the 3D coordinate $\mathbf{p} = (x, y, z)$ where the ray intersects the current voxel or sampling point [S2, unofficial].
2.  **Apply Offset:** Add a small offset to the ray direction or position to push the sampling point slightly forward into the voxel [S2, unofficial].
3.  **Sample Texture:** Sample the 3D texture at the adjusted position to resolve interpolation ambiguity [S2, unofficial].

**Pseudocode:**
```python
def sample_voxel_3d_texture(origin, direction, step_size, grid_width, texture_data):
    # 1. Calculate the 3D position along the ray
    p = origin + direction * step_size
    
    # 2. Apply offset to resolve rounding ambiguity
    epsilon = 1e-6
    p_adjusted = p + epsilon
    
    # 3. Sample the texture
    # For binary occupancy, use direct load at integer coordinates
    int_coords = (int(p_adjusted.x), int(p_adjusted.y), int(p_adjusted.z), 0)
    
    # Linear index calculation for row-major layout
    linear_index = int_coords[0] + int_coords[1] * grid_width + int_coords[2] * grid_width ** 2
    
    # Fetch value from flat texture data array
    voxel_value = texture_data[linear_index]
    return voxel_value
```

**Parameters:**
*   **Epsilon Offset:** A small value (e.g., $10^{-6}$) added to the sampling coordinate to prevent sampling on voxel boundaries [S2, unofficial].
*   **Grid Extent ($W$):** The width of the voxel grid, critical for the linear index calculation [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Rounding Noise:** GPU texture sampling interpolates coordinates between pixels, causing random rounding that produces noise when determining binary voxel occupancy [S2, unofficial].
*   **Boundary Conditions:** Accessing coordinates outside the texture bounds requires clamping or explicit boundary checks to avoid undefined behavior [G].
*   **Cache Locality:** While row-major layout improves locality for spatially adjacent accesses, ray tracing may still access voxels $W^2$ apart in memory if the ray traversal is not optimized [S1, unofficial].

## Subtopics

### Voxel Texture Encoding
Stores voxels in 2D textures using the `FP32RGBA` format. Each texel encodes a voxel as `<x, y, z, v>`, where $x, y, z$ are the 3D coordinates stored in the RGB channels (32-bit float each) and $v$ is the voxel value stored in the alpha channel [S3, unofficial]. This method is typically used in image-space splatting or recursive processing pipelines using Frame Buffer Objects (FBOs) rather than direct ray traversal [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per voxel access, as the hardware handles the linear indexing [S2, unofficial].
*   **Memory Complexity:** $O(W \cdot H \cdot D)$, where $W, H, D$ are the grid dimensions. The memory footprint is determined by the texture format (e.g., 32-bit uint per voxel) [S1, unofficial].
*   **Measured Performance:** On a MacBook Air M2, using 3D texture storage reduced GPU walltime by 14.2% and increased FPS by 10.3% compared to `ByteAddressBuffer` storage, due to better cache utilization for spatially adjacent data access [S1, unofficial].
*   **Strengths:** Hardware-accelerated 3D coordinate indexing; improved cache locality for spatially adjacent accesses [S1, S2, unofficial].
*   **Limitations:** Introduces noise in binary occupancy due to coordinate rounding; requires offset adjustments; may require full rewrite of caching and voxel streaming systems if migrating from buffer-based storage [S2, unofficial].
*   **When to Use:** When smooth interpolation is required or when hardware texture sampling units provide a significant performance advantage over manual buffer indexing [S1, S2, unofficial].
*   **When Not to Use:** When binary occupancy is critical and noise from rounding cannot be tolerated without significant offset tuning, or when memory bandwidth is severely constrained and manual control over memory layout is required [S2, unofficial].

## Background
The use of 3D textures for voxel storage emerged to leverage hardware-accelerated 3D coordinate indexing for efficient sampling during ray traversal [S2, unofficial]. Early implementations noted that while 3D textures provided efficient indexing, they introduced challenges with coordinate rounding and required significant architectural changes to caching and voxel streaming systems [S2, unofficial]. Recent developments in voxel raytracing have highlighted the performance benefits of 3D textures over linear byte buffers, particularly in reducing GPU walltime through improved cache locality [S1, unofficial]. The technique is used in real-time voxel raytracers [S1, unofficial] and image-space splatting pipelines [S3, unofficial].
