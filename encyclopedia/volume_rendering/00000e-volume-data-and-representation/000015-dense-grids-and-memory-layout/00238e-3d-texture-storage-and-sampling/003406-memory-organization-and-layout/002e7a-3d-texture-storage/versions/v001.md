# 3D Texture Storage

Also called: 3D Texture Voxel Storage

## Overview
3D Texture Storage maps a voxel grid directly into a GPU `Texture3D` resource, replacing linear byte buffers to improve cache locality for spatially adjacent accesses during ray traversal [S1, unofficial]. It differs from linear storage by leveraging hardware-accelerated coordinate-based sampling and caching, which reduces GPU walltime and increases FPS compared to manual indexing into `ByteAddressBuffer` resources [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A voxel grid of dimensions $W \times H \times D$.
- Output: A `Texture3D` resource bound to a shader register.

**Data Structures:**
The resource is declared as a 3D texture of unsigned integers.
```hlsl
Texture3D<uint> voxels : register(t0, space2);
```
The memory layout follows a row-major order where the linear index $v$ for a voxel at coordinates $(x, y, z)$ is:
$$ v = x + y \cdot W + z \cdot W^2 $$
where $W$ is the grid extent (width) [S1, unofficial].

**Steps:**
1.  **Resource Creation:** Allocate a `Texture3D` resource with dimensions matching the voxel grid.
2.  **Data Upload:** Upload the voxel data array, laid out in row-major order, to the texture.
3.  **Sampling:** In the shader, retrieve a voxel value using the `Load` method with integer coordinates.

**Pseudocode:**
```python
# Shader code example
uint voxel_at(int3 p) {
    // Load the uint at integer coordinates (p.x, p.y, p.z)
    // The fourth component (0) is required by the API signature but unused
    return voxels.Load(int4(p, 0)).r;
}
```

**Parameters and Edge Cases:**
-   **Precision:** The resource type `uint` typically implies 32-bit storage, but 16-bit formats may be used for bandwidth savings [S1, unofficial].
-   **Boundaries:** `Load` does not perform boundary clamping or wrapping automatically; out-of-bounds accesses are undefined or return 0 depending on the API implementation.
-   **Interpolation:** For tri-linear interpolation, the hardware fetches a $2 \times 2 \times 2$ cell. The layout ensures these 8 voxels are spatially adjacent in memory, minimizing cache misses [S1, unofficial].

## Subtopics

### Voxel Texture Encoding
Voxels are stored in 2D textures using the `FP32RGBA` format. Each texel encodes a voxel as `<x, y, z, v>`, where $x, y, z$ are the coordinates stored in the RGB channels (32-bit float each) and $v$ is the voxel value stored in the alpha channel [S2, unofficial]. This method prioritizes coordinate precision over storage density.

## Operating characteristics
-   **Performance:** Compared to `ByteAddressBuffer`, 3D texture storage reduces GPU walltime by 14.2% and increases FPS by 10.3% on a MacBook Air M2, attributed to better cache utilization for spatially adjacent data access [S1, unofficial].
-   **Memory:** Memory usage is determined by the texture format (e.g., 32-bit uint per voxel).
-   **Strengths:** Hardware-managed cache lines for 3D spatial locality; simpler shader code for access.
-   **Limitations:** Less flexible than linear buffers for non-uniform or sparse data structures without additional overhead (e.g., occupancy masks) [S1, unofficial].

## Background
The approach utilizes modern GPU `Texture3D` resources, which are standard in graphics APIs (DirectX, OpenGL, Vulkan). The specific comparison against linear buffers and the performance metrics on Apple Silicon were documented in a voxel raytracer development log [S1, unofficial]. The alternative encoding method using 2D textures for coordinate storage originates from research on image-space sheet-buffered splatting [S2, unofficial].
