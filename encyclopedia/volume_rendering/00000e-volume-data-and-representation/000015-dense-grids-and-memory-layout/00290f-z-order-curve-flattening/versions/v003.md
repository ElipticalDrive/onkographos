# Z-order Curve Flattening

Also called: Z-ordering, Z-order Curves, Morton ordering, Z-ordered memory, Morton-order curve, Z-order memory layout, Z-Ordered Memory Layout, Morton (z-) order data layout

## Overview
Z-order curve flattening is a locality-preserving memory layout technique that maps 3D voxel coordinates to a 1D linear index using a space-filling curve, placing spatially adjacent voxels in contiguous memory [S1][S2, unofficial]. It solves the index-space locality problem inherent in standard row-major (a-order) layouts, where coordinates adjacent in higher dimensions are separated by large memory strides [S3, unofficial]. By improving spatial locality, it increases cache hit rates during ray traversal and reduces memory bandwidth pressure when nearby rays access similar data [S1][S5, unofficial]. It is chosen over other space-filling curves like the Hilbert curve primarily because Z-order indices are computationally inexpensive to calculate [S3, unofficial].

## How it works
**Inputs:**
*   Grid dimensions $(M_x, M_y, M_z)$, ideally even powers of two [S3, unofficial].
*   Input data array $A$ in a-order (row-major) layout [S3, unofficial].
*   Element size in bytes (e.g., `sizeof(float)`) [S3, unofficial].

**Outputs:**
*   A new data array $Z$ containing the same values as $A$ but rearranged into Z-order layout [S3, unofficial].
*   A mapping structure containing precomputed tables for fast index calculation [S3, unofficial].

**Data Structures:**
*   `ZOrderStruct`: An opaque structure returned by initialization. It contains precomputed tables used to accelerate the computation of both a-order and z-order indices [S3, unofficial].
*   Linear Index $I$: A 64-bit integer offset (e.g., `off_t`) representing the position in the 1D array [S3, unofficial].

**Algorithm:**
The method follows three phases: Initialization, Conversion, and Access [S3, unofficial].

1.  **Initialization:**
    Initialize the indexing structure with dimensions $(i, j, k)$ and a layout enumerator (`ZORDER_LAYOUT` or `AORDER_LAYOUT`) [S3, unofficial]. This returns a structure pointer containing precomputed tables to accelerate index computation [S3, unofficial].

2.  **Data Conversion:**
    Convert the input array $A$ to Z-order layout by allocating a new array $Z$ and rearranging the data [S3, unofficial]. This step is not zero-copy; it always allocates new memory and copies data [S3, unofficial].

3.  **Index Calculation and Access:**
    To access a voxel at $(i, j, k)$, compute the linear index $I$ using the precomputed tables or bit-interleaving, then access the value directly at offset $I$ in array $Z$ [S3, unofficial].

**Pseudocode:**
The following Python-like pseudocode implements the core Z-order index calculation and data conversion logic directly, replacing library wrappers with standard operations [G].

```python
def compute_z_order_index(x, y, z):
    """Interleave bits of x, y, z to form the 1D Z-order index I [G]."""
    idx = 0
    max_bits = max(x.bit_length(), y.bit_length(), z.bit_length(), 1)
    for bit in range(max_bits):
        idx |= ((x >> bit) & 1) << (2 * bit)
        idx |= ((y >> bit) & 1) << (2 * bit + 1)
        idx |= ((z >> bit) & 1) << (2 * bit + 2)
    return idx

def convert_to_z_order(a_order_array, dims, element_size):
    """Rearranges row-major array A into Z-order layout Z [S3, unofficial]."""
    # Allocates a new array Z; no zero-copy in-place conversion is performed [S3, unofficial]
    z_order_array = allocate_new_array(dims, element_size)
    for k in range(dims[2]):
        for j in range(dims[1]):
            for i in range(dims[0]):
                # Row-major source index
                src_idx = i + j * dims[0] + k * dims[0] * dims[1]
                # Z-order destination index
                dst_idx = compute_z_order_index(i, j, k)
                z_order_array[dst_idx] = a_order_array[src_idx]
    return z_order_array

def access_voxel(z_order_array, i, j, k):
    """Retrieves a voxel value using the Z-order index [S3, unofficial]."""
    idx = compute_z_order_index(i, j, k)
    return z_order_array[idx]
```

**Formulas:**
The Z-order index $I$ for coordinates $(x, y, z)$ is computed by interleaving the bits of the coordinates [G]. For a 3D grid, if $x, y, z$ are represented in binary as $x = \sum x_m 2^m$, $y = \sum y_m 2^m$, $z = \sum z_m 2^m$, then:
$$ I = \sum_{m=0}^{M-1} (x_m 2^{2m} + y_m 2^{2m+1} + z_m 2^{2m+2}) $$
where $M$ is the number of bits required to represent the maximum dimension [G].

**Parameters:**
*   `ZORDER_LAYOUT` / `AORDER_LAYOUT`: Enumerators passed to initialization that determine which indexing logic the generic access routine uses [S3, unofficial].
*   `element_size`: Byte size of array elements, required for correct memory allocation and copying during conversion [S3, unofficial].

**Edge Cases and Pitfalls:**
*   **Non-Power-of-Two Dimensions:** The layout is optimized for dimensions that are even powers of two [S3, unofficial]. If dimensions are not powers of two, padding is applied, inflating the memory footprint by 1.5× to 4× depending on the deviation [S3, unofficial].
*   **Memory Allocation:** The conversion step always allocates a new array [S3, unofficial]. There is no zero-copy in-place conversion [S3, unofficial]. Data must be loaded in Z-order format initially if memory allocation is a constraint [S3, unofficial].
*   **Preprocessing Cost:** Many datasets are not stored in Z-order initially, incurring a re-ordering cost that is amortized if multiple visualizations are generated from the same dataset [S5, unofficial].
*   **Neighbor Proximity:** High-dimensional neighbors are not always close when mapped linearly, which can affect the efficiency of operations relying on true spatial proximity [S4].

## Subtopics

### Morton-order curve
The standard bit-interleaving implementation of Z-order [S3, unofficial]. It sets itself apart by providing the fastest index computation among space-filling curves [S3, unofficial]. It is chosen when computational speed outweighs marginal locality gains [S3, unofficial].

### Hilbert curve
A space-filling curve that preserves spatial locality better than Z-order but requires significantly more complex arithmetic to compute indices [S4]. It is chosen when strict neighborhood preservation is critical and index computation cost is acceptable [S4].

## Operating characteristics
*   **Time Complexity:** Index computation is $O(1)$ with precomputed tables or $O(\log N)$ bit operations [S3, G, unofficial]. Conversion is $O(N)$ where $N$ is the number of voxels [S3, unofficial].
*   **Memory Complexity:** $O(N)$ for the data array [S3, unofficial]. Additional overhead for precomputed tables is negligible [S3, unofficial]. Memory footprint can increase by 1.5×–4× if dimensions are not powers of two [S3, unofficial].
*   **Performance:**
    *   In a 2048³ grid raycasting scenario, Z-order flattening increased frame rates from 12 FPS to 102 FPS (over 8× speedup) compared to standard flattening [S2, unofficial].
    *   Performance gains vary by access pattern and hardware, ranging from negligible to 800% faster runtime on Intel Ivy Bridge and Knight's Corner architectures [S3, unofficial].
    *   CPU gains range from 3% to 29% on Intel/Nehalem and AMD/MagnyCours platforms; GPU gains reach 146% on NVIDIA/Fermi at 64-way concurrency [S5, unofficial].
*   **Strengths:**
    *   Improves GPU cache locality for ray traversal by keeping neighboring voxels in cache [S1].
    *   Improves locality for multiple rays accessing nearby memory [S1].
    *   Low computational cost for index generation compared to Hilbert curves [S3, unofficial].
*   **Limitations:**
    *   Requires data conversion (copying) if input is in row-major order [S3, unofficial].
    *   Memory inflation for non-power-of-two dimensions [S3, unofficial].
    *   Less locality preservation than Hilbert curves for certain access patterns, though the trade-off favors Z-order for its speed [S3, unofficial].

## Background
Z-order curve flattening, also known as Morton-order, was developed to address the index-space locality problem in multidimensional array storage [S3, unofficial]. Early research by Lam et al. (1991) focused on blocking and tiling to improve cache utilization, but these methods required intrusive code modifications [S3, unofficial]. Space-filling curves were proposed as a non-intrusive alternative that lays out data differently so that index-space neighbors become physical neighbors [S3, unofficial]. The Z-order curve was selected for widespread use in scientific computing and graphics due to its balance of locality and computational efficiency [S1][S3, unofficial]. It is commonly used in raycasting volume rendering, bilateral smoothing filters, and data-intensive codes with structured or unstructured memory access patterns [S3, unofficial].
