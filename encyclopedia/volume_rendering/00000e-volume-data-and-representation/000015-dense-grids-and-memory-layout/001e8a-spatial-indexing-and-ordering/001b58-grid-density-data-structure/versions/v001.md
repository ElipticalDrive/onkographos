# Grid Density Data Structure

Also called: 1D Array Density Layout, 3D Grid, 3D Voxel Grid Density Field, Dense Voxel Grid Storage, Dense structure, Linearized 3D Grid, Volume Grid Data Structure

## Overview
The Grid Density Data Structure is a dense, axis-aligned 3D grid used to store scalar density values for volume rendering [S1, unofficial]. It solves the problem of representing continuous volumetric media (such as smoke, clouds, or fluids) as a discrete, regularly sampled field that can be efficiently traversed by ray marchers [S1, unofficial][S4, unofficial]. Unlike sparse structures (e.g., trees or lists) which offer memory efficiency through bounding box culling but suffer from sampling latency due to indirection, the dense grid provides faster sampling speeds by eliminating pointer chasing, at the cost of higher memory usage and fixed resolution limits [S4, unofficial]. It builds on [Spatial Indexing and Ordering](1797-spatial-indexing-and-ordering.md) by providing the underlying memory layout for spatial queries.

## How it works
**Inputs:**
- Grid resolution $N$ (assumed equal in all dimensions, typically a power of 2: 8, 16, 32, 64, 128, etc.) [S1, unofficial].
- World-space bounds defined by minimum and maximum extents $\mathbf{b}_{min}$ and $\mathbf{b}_{max}$, forming an Axis-Aligned Bounding Box (AABB) [S1, unofficial]. The physical size must be identical in all three dimensions (e.g., a cube) [S1, unofficial].
- Optional: Additional scalar fields (e.g., temperature) [S2, unofficial].

**Outputs:**
- A contiguous 1D array of floating-point density values.
- Metadata enabling coordinate transformation between world space and grid indices.

**Data Structures:**
The core structure `Grid` contains:
1.  `float *density`: A contiguous memory block of size $N^3$ storing the density values [S1, unofficial].
2.  `size_t dimension`: The resolution $N$ [S1, unofficial].
3.  `Point bounds[2]`: An array of two 3D points representing $\mathbf{b}_{min}$ and $\mathbf{b}_{max}$ in world space [S1, unofficial].

For more complex implementations (e.g., path tracing), the structure may extend to `VolumeGrids`, holding handles for density, optional temperature, and a majorant field [S2, unofficial].

**Indexing Formula:**
The 3D coordinates $(x, y, z)$ map to a 1D linear index using row-major (Z-Y-X) ordering [S3, unofficial]:
$$ index(x, y, z) = (z \cdot N + y) \cdot N + x $$
where $0 \le x, y, z < N$ [S3, unofficial].

**Coordinate Transformation:**
To sample the grid, a world-space ray must be transformed into the grid's local coordinate system. This requires a transformation matrix $D$ that maps world coordinates to medium-local coordinates [S3, unofficial]:
$$ M = T(\mathbf{p}_0) \times S(\mathbf{p}_1 - \mathbf{p}_0) $$
$$ D = (W \times M)^{-1} $$
where:
- $\mathbf{p}_0, \mathbf{p}_1$ are two local-coordinate points defining the grid's orientation and scale.
- $T$ is a translation matrix.
- $S$ is a scaling matrix.
- $W$ is the world-to-local transformation matrix [S3, unofficial].

**Generation Example (Smoke Sphere):**
A common initialization pattern involves creating a spherical density falloff [S3, unofficial]:
1.  Initialize `density` array of size $N^3$ to 0.
2.  Iterate $z$ from $1$ to $N-2$, $y$ from $1$ to $N-2$, $x$ from $1$ to $N-2$ [S3, unofficial].
3.  Compute distance from center:
    $$ dist = \sqrt{\left(x - \frac{N-1}{2}\right)^2 + \left(y - \frac{N-1}{2}\right)^2 + \left(z - \frac{N-1}{2}\right)^2} $$
4.  Set density:
    $$ density[index] = \frac{1}{2^{dist+2}} $$
5.  Enforce boundary conditions (e.g., radius limit) to reduce harsh edges [S3, unofficial].

**Pseudocode:**
```python
import math

class Grid:
    def __init__(self, resolution, bounds_min, bounds_max):
        """
        Initialize a dense 3D grid.
        :param resolution: int, N (power of 2)
        :param bounds_min: tuple (x, y, z), world space min
        :param bounds_max: tuple (x, y, z), world space max
        """
        self.dimension = resolution
        self.bounds = [bounds_min, bounds_max]
        # Contiguous 1D array of floats
        self.density = [0.0] * (resolution ** 3)

    def set_density_sphere(self, center_x, center_y, center_z, radius_factor=1.0):
        """
        Generates a spherical density falloff.
        """
        n = self.dimension
        half_n = (n - 1) / 2.0
        
        # Iterate interior voxels to avoid boundary artifacts
        for z in range(1, n - 1):
            for y in range(1, n - 1):
                for x in range(1, n - 1):
                    # Calculate distance from center in grid units
                    dx = x - center_x
                    dy = y - center_y
                    dz = z - center_z
                    dist = math.sqrt(dx*dx + dy*dy + dz*dz)
                    
                    # Apply falloff formula
                    # Note: Source uses 1/(2**(dist+2))
                    val = 1.0 / (2.0 ** (dist + 2.0))
                    
                    # Linear index calculation (Z-Y-X order)
                    idx = (z * n + y) * n + x
                    self.density[idx] = val

    def get_density(self, x, y, z):
        """
        Retrieve density at integer grid coordinates.
        """
        if not (0 <= x < self.dimension and 
                0 <= y < self.dimension and 
                0 <= z < self.dimension):
            return 0.0 # Out of bounds
        
        idx = (z * self.dimension + y) * self.dimension + x
        return self.density[idx]

    def save_to_binary(self, filepath):
        """
        Saves the grid to a binary cache file.
        """
        import struct
        with open(filepath, 'wb') as f:
            n = self.dimension
            # Nested loops: z, y, x
            for z in range(n):
                for y in range(n):
                    for x in range(n):
                        density_val = self.get_density(x, y, z)
                        # Write float (4 bytes)
                        f.write(struct.pack('f', density_val))
```

**Edge Cases and Pitfalls:**
- **Boundary Artifacts:** Hard edges at the grid boundary can cause visual artifacts. Restricting the effective radius and enforcing zero density at the edges mitigates this [S3, unofficial].
- **Memory Usage:** Memory scales as $O(N^3)$. High resolutions (e.g., 256+) consume significant RAM, limiting the maximum feasible resolution compared to sparse structures [S4, unofficial].
- **Coordinate Mismatch:** The grid's world-space size must be uniform (cubic) if defined by symmetric bounds, or correctly mapped via the transformation matrix $D$ if non-uniform [S1, unofficial][S3, unofficial].

## Subtopics

### [Gradient Computation via Finite Differences](1077-gradient-computation-via-finite-differences.md)
Gradient Computation via Finite Differences estimates the spatial gradient vector of a scalar volume field at sample positions to enable local illumination (e.g., Phong shading) and multidimensional transfer functions. It sets itself apart from [Analytic Gradient Computation](2167-analytic-gradient-computation.md) by requiring no basis function derivatives and from [Sobel Operator](1416-sobel-operator.md) by using a minimal 6-neighbor stencil rather than a separable smoothing kernel, making it faster but less robust to noise.

### [EdgeMap Data Layout](1109-edgemap-data-layout.md)
The EdgeMap data layout is a memory structure within the Grid Density Data Structure that stores geometric intersection data for isosurface extraction. It organizes intersection points, surface normals, ray directions, and indexing offsets into contiguous arrays. It differs from sibling methods like Gradient Computation via Finite Differences by storing pre-computed geometric primitives rather than derivative values, and from Interpolated Discrete Values & Gradients by focusing on explicit intersection coordinates rather than field values [G].

### [Interpolated Discrete Values & Gradients](1268-interpolated-discrete-values-gradients.md)
This method computes the scalar field value at a 3D point using tri-cubic interpolation, requiring a 4×4×4 neighborhood of 64 voxels. It provides scalar value and gradient fields computed from discrete data at grid vertices using interpolation. It builds on [Grid Density Data Structure](998-grid-density-data-structure.md) and operates alongside siblings [Gradient Computation via Finite Differences](1077-gradient-computation-via-finite-differences.md) and [EdgeMap Data Layout](1109-edgemap-data-layout.md).

### [Euclidean Distance Field (EDF) Data Structure](3220-euclidean-distance-field-edf-data-structure.md)
The Euclidean Distance Field (EDF) is a spatial indexing structure used for space-skipping ray traversal in dense voxel volumes. It accelerates rendering by allowing rays to jump over empty space based on precomputed distance values, reducing the number of intersection tests. It differs from sibling structures like [EdgeMap Data Layout](1109-edgemap-data-layout.md) by storing scalar distance magnitudes rather than boundary flags, and from [Gradient Computation via Finite Differences](1077-gradient-computation-via-finite-differences.md) by providing traversal acceleration rather than surface normal estimation.

## Operating characteristics
- **Time Complexity:** Sampling is $O(1)$ per voxel access due to direct array indexing [S4, unofficial]. Construction is $O(N^3)$ to initialize and populate the grid [S3, unofficial].
- **Memory Complexity:** $O(N^3)$ floats. For $N=128$, this requires $128^3 \times 4$ bytes $\approx 8$ MB per density field [S1, unofficial].
- **Performance:** Dense grids are significantly faster to sample than sparse grids because they avoid the indirection overhead of tree traversal or hash lookups [S4, unofficial]. However, the fixed resolution limits detail compared to adaptive sparse structures [S4, unofficial].
- **Strengths:** Simple implementation, cache-friendly contiguous memory layout, supports precomputed data (e.g., lighting) easily [S4, unofficial].
- **Limitations:** High memory consumption restricts resolution; inefficient for sparse scenes with large empty volumes [S4, unofficial].
- **When to Use:** Suitable for dense media (clouds, smoke) where sampling speed is critical and memory allows for sufficient resolution [S4, unofficial].
- **When Not to Use:** Unsuitable for highly sparse scenes or when extreme resolution is required within limited memory budgets; use sparse structures (e.g., OpenVDB) instead [S4, unofficial].

## Background
The Grid Density Data Structure originates from early volume rendering techniques that quantized continuous density fields into discrete voxel grids [S1, unofficial]. It is analogous to how bitmaps represent 2D images, with 3D grids representing volumetric simulations (fluids, smoke) [S1, unofficial]. The approach is widely used in real-time and offline rendering for clouds and smoke, often leveraging 3D textures for hardware-accelerated sampling [S4, unofficial]. Data is frequently loaded from sparse formats like OpenVDB and converted to dense grids for rendering [S4, unofficial]. Heuristics for optimal grid resolution, such as the Surface Area Metric, have been developed to balance traversal and intersection costs, particularly in GPU ray tracing contexts [S6, unofficial].
