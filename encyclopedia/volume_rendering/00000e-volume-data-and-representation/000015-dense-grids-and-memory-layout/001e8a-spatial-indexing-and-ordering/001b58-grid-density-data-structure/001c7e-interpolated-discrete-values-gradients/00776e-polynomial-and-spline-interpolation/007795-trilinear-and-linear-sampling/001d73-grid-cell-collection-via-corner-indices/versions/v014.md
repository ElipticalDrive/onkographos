# Grid Cell Collection via Corner Indices

Also called: 8-Corner Grid Sampling, Trilinear Corner Indexing, GatherGeoParams, GatherFeatParams, Gather Tri-Interpolated Geometry Parameters, Gather Tri-Interpolated Feature Parameters

## Overview
Grid Cell Collection via Corner Indices is a data gathering method that retrieves the discrete values stored at the eight vertices of the grid cell enclosing a set of query points, preparing them for subsequent trilinear interpolation or surface extraction [S1, S3, unofficial]. It solves the problem of efficiently mapping arbitrary continuous coordinates to the discrete support points required by linear basis functions in dense voxel grids [S1, S3, unofficial]. It sets itself apart from higher-order methods like [Tricubic Interpolation](14963-tricubic-interpolation.md) by strictly limiting the support to the immediate 8 neighbors of the enclosing voxel, and from [VoxelGrid](2159-voxelgrid.md) by focusing on the low-level index computation and tensor gathering step rather than the high-level differentiable rendering pipeline [S2, S3, unofficial].

## How it works
**Inputs:**
1.  A dense grid tensor $\mathbf{G}$ of shape $(D_x, D_y, D_z, C)$, where $D$ are the grid dimensions and $C$ is the channel count (e.g., density, color, or geometry parameters) [S1, S2, S3, unofficial].
2.  A set of query points $\mathbf{P}$ with shape $(N, 3)$, representing coordinates in the grid's local space [S1, S2, unofficial].
3.  Boundary handling mode (e.g., periodic, clamping, or constant value filling) [S1, S4, unofficial].

**Outputs:**
1.  A gathered tensor $\mathbf{V}$ of shape $(N, 8, C)$, containing the values from the 8 corners for each query point [S1, S2, S3, unofficial].
2.  (Optional) A gathered position tensor $\mathbf{X}$ of shape $(N, 8, 3)$, containing the world or local coordinates of the 8 corners [S3, unofficial].

**Data Structures:**
*   **VoxSample (C-style):** A struct used in some implementations to hold the gathered data for a single cell. It contains two arrays of size 8: `values` (float array of size 8) and `positions` (vec3 array of size 8) [S3, unofficial].
    *   Index mapping for the 8 corners:
        *   Indices 0–3: Lowest Z-plane corners (sw, se, ne, nw).
        *   Indices 4–7: Highest Z-plane corners (sw, se, ne, nw) [S3, unofficial].
*   **VoxKey (PyTorch-style):** A 2D tensor of shape $(N, 8)$ storing the integer indices of the 8 corners for each query point [S2, unofficial].
*   **CareIdx:** A 1D tensor or array used to map or filter the gathered points [S2, unofficial].

**Algorithm Steps:**
1.  **Coordinate Normalization:** If the query points $\mathbf{P}$ are not already in the range $[0, 1]$ or $[0, D_d-1]$, normalize them to the grid's coordinate system [S1, S4, unofficial].
2.  **Index Computation:** For each query point $\mathbf{p}_i = (x, y, z)$:
    *   Compute the floor indices: $i_x = \lfloor x \rfloor, i_y = \lfloor y \rfloor, i_z = \lfloor z \rfloor$ [S1, S3, unofficial].
    *   Compute the ceil indices: $j_x = \lceil x \rceil, j_y = \lceil y \rceil, j_z = \lceil z \rceil$ [S1, S3, unofficial].
    *   Generate all 8 combinations of $(i_x/j_x, i_y/j_y, i_z/j_z)$ to form the corner indices [S1, S3, unofficial].
3.  **Boundary Handling:** Apply the specified boundary condition to the computed indices to ensure they fall within the valid grid domain $[0, D_d-1]$ [S1, S4, unofficial].
    *   *Periodic:* $idx = idx \mod D_d$ [S1, unofficial].
    *   *Clamping:* $idx = \max(0, \min(D_d-1, idx))$ [S1, S4, unofficial].
    *   *Constant Fill:* If out of bounds, the value is filled with a constant $cval$ during the final interpolation step, but indices must still be valid for gathering [S4, unofficial].
4.  **Gathering:** Index into the grid tensor $\mathbf{G}$ using the fixed corner indices to retrieve the values [S1, S3, unofficial].
    *   If positions are required, compute the world coordinates of the corners using the grid origin and voxel size [S3, unofficial].
5.  **Reshaping:** Reshape the gathered data into the output tensor $\mathbf{V}$ with shape $(N, 8, C)$ [S1, S3, unofficial].

**Pseudocode:**
```python
import torch
import math

def gather_corner_indices(grid_shape, query_points, boundary_mode='clamp'):
    """
    Gathers the 8 corner indices for a batch of query points.
    
    Args:
        grid_shape (tuple): (Dx, Dy, Dz) dimensions of the grid.
        query_points (torch.Tensor): Shape (N, 3), coordinates in grid space [0, D-1].
        boundary_mode (str): 'clamp', 'periodic', or 'constant'.
        
    Returns:
        torch.Tensor: Shape (N, 8, 3), integer indices of the 8 corners.
    """
    # 1. Compute floor and ceil indices
    # Ensure coordinates are within bounds for floor/ceil to work correctly
    # If using 'constant' boundary, we still need valid indices for gathering,
    # or we handle out-of-bounds values separately. Here we assume indices are valid.
    
    floor_indices = torch.floor(query_points).long()
    ceil_indices = torch.ceil(query_points).long()
    
    # 2. Generate 8 combinations
    # Combinations: (floor_x, floor_y, floor_z), (floor_x, floor_y, ceil_z), ...
    corners = []
    for dx in [0, 1]:
        for dy in [0, 1]:
            for dz in [0, 1]:
                ix = floor_indices[:, 0] if dx == 0 else ceil_indices[:, 0]
                iy = floor_indices[:, 1] if dy == 0 else ceil_indices[:, 1]
                iz = floor_indices[:, 2] if dz == 0 else ceil_indices[:, 2]
                corners.append(torch.stack([ix, iy, iz], dim=1))
    
    corner_indices = torch.stack(corners, dim=1) # Shape (N, 8, 3)
    
    # 3. Apply Boundary Handling
    if boundary_mode == 'clamp':
        corner_indices = corner_indices.clamp(min=0, max=torch.tensor(grid_shape) - 1)
    elif boundary_mode == 'periodic':
        corner_indices = corner_indices % torch.tensor(grid_shape)
    elif boundary_mode == 'constant':
        # For constant fill, we might clamp indices and handle the value later,
        # or use a specific padding strategy. Standard practice is to clamp
        # and then mask/replace values during interpolation.
        corner_indices = corner_indices.clamp(min=0, max=torch.tensor(grid_shape) - 1)
        
    return corner_indices

def gather_grid_values(grid_tensor, corner_indices):
    """
    Retrieves values from the grid tensor using the corner indices.
    
    Args:
        grid_tensor (torch.Tensor): Shape (Dx, Dy, Dz, C).
        corner_indices (torch.Tensor): Shape (N, 8, 3), integer indices.
        
    Returns:
        torch.Tensor: Shape (N, 8, C), gathered values.
    """
    # Grid tensor is 4D. We need to gather from it.
    # corner_indices has shape (N, 8, 3) -> (x, y, z)
    # We need to index grid_tensor[x, y, z, :]
    
    N = corner_indices.shape[0]
    C = grid_tensor.shape[3]
    
    # Extract x, y, z components
    x = corner_indices[:, :, 0] # (N, 8)
    y = corner_indices[:, :, 1] # (N, 8)
    z = corner_indices[:, :, 2] # (N, 8)
    
    # Gather values
    # grid_tensor[x, y, z, :]
    # We can use advanced indexing
    values = grid_tensor[x, y, z, :] # Shape (N, 8, C)
    
    return values
```

**Parameters:**
*   `grid_shape`: The dimensions of the voxel grid $(D_x, D_y, D_z)$ [S1, S3, unofficial].
*   `boundary_mode`: The strategy for handling indices outside the grid bounds ('clamp', 'periodic', 'constant') [S1, S4, unofficial].
*   `cval`: The constant value to use for out-of-bounds queries when `boundary_mode` is 'constant' [S4, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** Floating-point coordinates near integer boundaries may result in floor/ceil producing indices that are off by one due to precision errors. It is recommended to use a small epsilon or robust integer conversion [S1, S3, unofficial].
*   **Degenerate Input:** Query points exactly on the grid boundary may produce identical floor and ceil indices, resulting in duplicate corners. This is handled correctly by the algorithm but may be optimized [S1, S3, unofficial].
*   **Out-of-Bounds:** If the query point is outside the grid, the boundary mode determines the behavior. 'Constant' fill requires careful handling to ensure the interpolation weights do not produce invalid results [S4, unofficial].

## Subtopics

### Grid Interpolation with Boundary Handling
A linearly interpolated grid structure used for voxel interpolation (interp5) and image plane interpolation (interp4), handling boundary conditions via constant value filling [S4, unofficial]. It wraps a 2D/3D grid of values into a callable interpolation function, supporting 4th-order (bicubic) and 5th-order interpolation with a specified constant value for out-of-bounds queries [S4, unofficial].
*   **Step:** 
    1.  Initialize `Grid2` with `grid_vals` and `cval` [S4, unofficial].
    2.  For `interp4`: Map coordinates $x \in [0,1]$ to grid indices: $coords = (x \cdot grid\_res) - 0.5$. Flip coords along the last axis. Use `jax.scipy.ndimage.map_coordinates` with `order=1` and `cval` [S4, unofficial].
    3.  For `interp5`: Map coordinates $x$ to grid indices: $coords = (x \cdot (grid\_res+1)) - 1$. Permute x and y axes using matrix $\begin{bmatrix} 0 & 1 & 0 \\ 1 & 0 & 0 \\ 0 & 0 & 1 \end{bmatrix}$. Use `jax.scipy.ndimage.map_coordinates` with `order=1` and `cval` [S4, unofficial].
*   **Parameters:** `grid_vals`: `jnp.ndarray`, the voxel points to interpolate between. `cval`: `float`, constant value to fill past edges, default 0 [S4, unofficial].
*   **Code:** `grid_obj = Grid2(grid_vals = grid, cval=cval); predict_interp = lambda x: grid_obj.interp5(x)` [S4, unofficial].

### VIPER Cell Sampling with Extrapolation Flag Invalidation
A cell sampling technique that uses tri-linear interpolation at ray entry and exit points to check if target values lie within the cell range, combined with vertex flags to invalidate cells containing extrapolated data [S6, unofficial].
*   **Step:** 
    1.  Interpolate data values at the exact points where a ray enters and exits a grid cell [S6, unofficial].
    2.  Compare target values to the interpolated entry and exit values to determine if they lie within the cell [S6, unofficial].
    3.  Check the eight vertices of the cell for a flag value (positive or negative) [S6, unofficial].
    4.  If any vertex contains the flag value, ignore the cell and continue rendering [S6, unofficial].
    5.  During data placement, set a flag at each grid node that receives data [S6, unofficial].
    6.  After placement completes, assign a value equal to twice the largest data value found to all nodes with an unset flag [S6, unofficial].
    7.  Write the twice-maximum value to the data file so VIPER can read it during rendering [S6, unofficial].
*   **Pitfall:** Tri-linear interpolation across cells containing extrapolated data (unset flags) may produce a range that falsely contains a target value [S6, unofficial]. A-buffering delays knowledge of the largest data value until all points are processed, whereas Z-buffering finds it during placement [S6, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$, where $N$ is the number of query points, as each point requires a constant number of operations (8 index lookups and boundary checks) [S1, S3, unofficial].
*   **Memory Complexity:** $O(N \cdot C)$, where $C$ is the channel count, to store the gathered values for all query points [S1, S3, unofficial].
*   **Performance:** Highly efficient on modern GPUs due to the regular memory access pattern and lack of branching (if boundary conditions are handled via clamping or periodic arithmetic) [S1, S3, unofficial]. SIMD optimizations can further accelerate the gathering and subsequent interpolation steps [S3, unofficial].
*   **Strengths:** Simple to implement, differentiable (if using soft indexing or standard tensor operations), and provides $C^0$ continuity [S1, S3, S4, unofficial].
*   **Limitations:** Only provides linear interpolation, which may result in aliasing or blurring for high-frequency content compared to higher-order methods like [Tricubic Interpolation](14963-tricubic-interpolation.md) [S3, unofficial].
*   **When to Use:** When computational efficiency is critical, and the grid resolution is sufficient to avoid visible artifacts from linear interpolation [S1, S3, unofficial].
*   **When Not to Use:** When high-frequency details are present and higher-order interpolation is required, or when the grid is very sparse [S3, unofficial].

## Background
Grid Cell Collection via Corner Indices is a fundamental technique in volume rendering and voxel-based neural rendering, serving as the data gathering step for trilinear interpolation [S1, S2, S3, unofficial]. It is widely used in frameworks like Plenoxels and VoxelGrid for efficient feature queries [S1, S2, unofficial]. The method is also employed in scientific visualization tools like VIPER for handling extrapolated data [S6, unofficial].
