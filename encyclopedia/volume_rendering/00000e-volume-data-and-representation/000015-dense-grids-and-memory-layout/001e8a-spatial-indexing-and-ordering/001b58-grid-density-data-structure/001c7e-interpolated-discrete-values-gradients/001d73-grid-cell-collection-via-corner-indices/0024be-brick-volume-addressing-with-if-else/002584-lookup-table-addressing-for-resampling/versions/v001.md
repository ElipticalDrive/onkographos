# Lookup Table Addressing for Resampling

Also called: Brick Resampling Lookup Table

## Overview
Lookup Table Addressing for Resampling is a method to compute memory offsets for accessing neighboring samples in a brick-structured volume without using conditional branches or expensive runtime address calculations [S1, unofficial]. It solves the problem of efficiently determining whether adjacent samples lie within the current brick or in a neighboring brick by mapping the sample's local position to one of eight precomputed offset patterns [S1, unofficial]. Unlike its parent method, [Brick Volume Addressing with If-Else](3340-brick-volume-addressing-with-if-else.md), which uses explicit `if-else` checks and `ComputeOffset` calls, this method replaces branching with a direct table lookup, significantly improving performance on hardware where branch prediction is costly or memory bandwidth is limited [S1, unofficial].

## How it works

### Inputs and Outputs
- **Inputs**: The integer coordinates of the current sample $(i, j, k)$ relative to the global volume grid, and the brick dimensions $(BD_x, BD_y, BD_z)$.
- **Outputs**: An array of 7 integer offsets corresponding to the memory addresses of the 7 adjacent samples: right $(i+1, j, k)$, top $(i, j+1, k)$, back $(i, j, k+1)$, and their combinations (right-top, right-back, top-back, right-top-back) [S1, unofficial].

### Data Structures
The core data structure is a compressed lookup table (LUT) containing 56 offsets [S1, unofficial].
- **Layout**: The table is a 1D array of 56 32-bit integers (4 bytes each) [S1, unofficial].
- **Size**: $56 \times 4 = 224$ bytes [S1, unofficial].
- **Content**: The table is organized into 8 cases (indices 0–7). Each case contains 7 offsets for the neighbors relative to the current sample $(i, j, k)$ [S1, unofficial]. The order of neighbors is fixed as:
  1. $(i+1, j, k)$
  2. $(i, j+1, k)$
  3. $(i+1, j+1, k)$
  4. $(i, j, k+1)$
  5. $(i+1, j, k+1)$
  6. $(i, j+1, k+1)$
  7. $(i+1, j+1, k+1)$ [S1, unofficial]

### Algorithm Steps
The method assumes brick dimensions are powers of two. If they are not, a shift operation can be used to virtually satisfy the constraint, or the "power of two apart" constraint can be removed with a simple shift [S1, unofficial]. The following steps assume $BD_x, BD_y, BD_z$ are powers of two.

1. **Extract Brick Offset**: Compute the local coordinates within the brick by masking the global coordinates with the brick dimensions minus one:
   $$ i_{local} = i \ \& \ (BD_x - 1) $$
   $$ j_{local} = j \ \& \ (BD_y - 1) $$
   $$ k_{local} = k \ \& \ (BD_z - 1) $$
   [S1, unofficial]

2. **Increment**: Add 1 to each local coordinate:
   $$ i' = i_{local} + 1 $$
   $$ j' = j_{local} + 1 $$
   $$ k' = k_{local} + 1 $$
   [S1, unofficial]

3. **Mask with Complement**: Perform a bitwise AND with the bitwise NOT of the brick dimension minus one. This maps the values to either $0$ or the brick dimension itself ($BD_x, BD_y, BD_z$):
   $$ i_{mask} = i' \ \& \ \text{NOT}(BD_x - 1) $$
   $$ j_{mask} = j' \ \& \ \text{NOT}(BD_y - 1) $$
   $$ k_{mask} = k' \ \& \ \text{NOT}(BD_z - 1) $$
   [S1, unofficial]

4. **Sum Masked Values**: Sum the three masked values:
   $$ Sum = i_{mask} + j_{mask} + k_{mask} $$
   [S1, unofficial]

5. **Compute Index**: Divide the sum by the minimum brick dimension to get an index in the range $[0, 7]$. This division is implemented as a right bit shift:
   $$ Index = Sum \gg \log_2(\min(BD_x, BD_y, BD_z)) $$
   [S1, unofficial]

6. **Retrieve Offsets**: Use the computed index to retrieve the 7 offsets from the lookup table:
   $$ Offsets = LUT[Index] $$
   [S1, unofficial]

### Pseudocode
```python
def compute_resampling_offsets(i, j, k, BD_x, BD_y, BD_z, LUT):
    """
    Computes offsets for 7 neighbors using lookup table addressing.
    
    Args:
        i, j, k: Global integer coordinates of the current sample.
        BD_x, BD_y, BD_z: Brick dimensions (must be powers of two).
        LUT: Precomputed lookup table of size 56 integers.
        
    Returns:
        List of 7 offsets for neighbors:
        [right, top, right_top, back, right_back, top_back, right_top_back]
    """
    # Step 1: Extract brick offset part
    i_local = i & (BD_x - 1)
    j_local = j & (BD_y - 1)
    k_local = k & (BD_z - 1)
    
    # Step 2: Increment all by 1
    i_prime = i_local + 1
    j_prime = j_local + 1
    k_prime = k_local + 1
    
    # Step 3: Mask with complement of (BD-1)
    # NOT(BD-1) is equivalent to ~ (BD-1) in two's complement, 
    # but in Python integers are arbitrary precision, so we mask with a large enough value 
    # or assume fixed-width integers. For implementation, we use bitwise NOT on the relevant bits.
    # Assuming 32-bit integers for clarity, or using a mask that covers the dimension.
    # A robust way for arbitrary power-of-two BD:
    mask_x = ~ (BD_x - 1)
    mask_y = ~ (BD_y - 1)
    mask_z = ~ (BD_z - 1)
    
    # Note: In languages with fixed-width integers, ~ (BD-1) works directly.
    # In Python, we simulate this by masking with a sufficiently large power-of-two boundary.
    # However, the formula relies on the property that (val + 1) & ~ (BD-1) is either 0 or BD.
    i_mask = i_prime & mask_x
    j_mask = j_prime & mask_y
    k_mask = k_prime & mask_z
    
    # Step 4: Sum the three masked values
    total = i_mask + j_mask + k_mask
    
    # Step 5: Shift right by log2(min(BD)) to get index in [0, 7]
    min_bd = min(BD_x, BD_y, BD_z)
    shift_amount = min_bd.bit_length() - 1  # log2(min_bd)
    index = total >> shift_amount
    
    # Step 6: Retrieve offsets from LUT
    # LUT is a flat list of 56 integers, indexed by case (0-7) and neighbor (0-6)
    base_offset = index * 7
    offsets = [
        LUT[base_offset + 0], # Right (i+1, j, k)
        LUT[base_offset + 1], # Top (i, j+1, k)
        LUT[base_offset + 2], # Right-Top (i+1, j+1, k)
        LUT[base_offset + 3], # Back (i, j, k+1)
        LUT[base_offset + 4], # Right-Back (i+1, j, k+1)
        LUT[base_offset + 5], # Top-Back (i, j+1, k+1)
        LUT[base_offset + 6]  # Right-Top-Back (i+1, j+1, k+1)
    ]
    
    return offsets
```

### Parameters
- **Brick Dimensions**: Optimal brick size is $32^3$ [S1, unofficial]. The algorithm requires dimensions to be powers of two [S1, unofficial].
- **Lookup Table Size**: 224 bytes for the compressed table [S1, unofficial]. The naive approach would require $32^3 \times 7 \times 4$ bytes = 896 KB [S1, unofficial].

### Edge Cases and Pitfalls
- **Non-Power-of-Two Dimensions**: The index calculation relies on brick dimensions being powers of two. If dimensions are not powers of two, a shift operation can be introduced to virtually maintain the constraint, or the "power of two apart" constraint can be removed by introducing a simple shift [S1, unofficial].
- **Boundary Conditions**: The method handles brick boundaries implicitly by mapping out-of-bounds neighbors to offsets that point to neighboring bricks. The LUT must be precomputed correctly for all 8 cases [S1, unofficial].

## Operating characteristics

### Time and Memory Complexity
- **Time Complexity**: $O(1)$ for offset computation, as it involves a fixed number of bitwise operations and a single table lookup [S1, unofficial].
- **Memory Complexity**: The lookup table size is constant at 224 bytes for the compressed approach, regardless of brick size (assuming power-of-two dimensions) [S1, unofficial]. The naive approach scales with brick volume ($BD_x \times BD_y \times BD_z \times 7 \times 4$ bytes) [S1, unofficial].

### Measured Performance
- **Performance**: The compressed lookup table approach reduces table size by a factor of 4096 compared to the naive approach, allowing the table to fit in CPU cache [S1, unofficial]. This results in faster access times and reduced branch mispredictions compared to the if-else based method [S1, unofficial].
- **Hardware**: The method is designed for standard PC hardware and benefits from cache-friendly access patterns [S1, unofficial].

### Strengths and Limitations
- **Strengths**: Branchless execution, cache-friendly table size, efficient address computation [S1, unofficial].
- **Limitations**: Requires brick dimensions to be powers of two (or a workaround) [S1, unofficial]. Precomputation of the LUT is required [S1, unofficial].

### When to Use
- Use this method when resampling large brick-structured volumes on hardware where branch prediction is inefficient or cache misses are costly [S1, unofficial].
- Avoid if brick dimensions are not powers of two and the overhead of handling non-power-of-two dimensions outweighs the benefits [S1, unofficial].

## Background

### Origin
The method was introduced in the context of real-time mono- and multi-volume rendering of large medical datasets on standard PC hardware [S1, unofficial]. It was developed to optimize the addressing of neighboring samples in brick-structured volumes, which are commonly used in medical imaging for efficient storage and rendering [S1, unofficial].

### History and Development
The method builds upon the concept of brick volume addressing, where volumes are divided into smaller bricks to improve cache locality and manage memory efficiently [S1, unofficial]. The lookup table approach was proposed as an optimization to the if-else based addressing method, reducing the computational overhead of determining neighbor locations [S1, unofficial].

### Usage
The method is used in real-time volume rendering applications, particularly in medical imaging, where large datasets need to be rendered efficiently on standard hardware [S1, unofficial]. It is also applicable in other domains where brick-structured data is used, such as scientific visualization and game engines [S1, unofficial].
