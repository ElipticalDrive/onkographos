# iso_corners_list_f1v4

Also called: 64}

## Overview
`iso_corners_list_f1v4` is a GPU kernel variant that computes the values of one or more functions at the eight corners of the grid cells enclosing a list of input points, enabling trilinear interpolation or surface extraction [S1, unofficial]. It differs from its siblings by processing 256 consecutive lattice points per thread group across 2–4 neighboring bricks, sharing shell setup overhead among all points in the group rather than per-brick, which improves occupancy and reduces redundant memory accesses [S1, unofficial].

## How it works
**Inputs:**
- A list of input points (lattice coordinates or physical coordinates mapped to lattice indices).
- A set of functions (typically 1 for `f1v4`, or 8/16/32/64 for variants).
- Grid data structures: brick hierarchy, shell definitions, and function coefficients (e.g., $C$ matrix for Gaussian-type orbitals).

**Outputs:**
- For each input point, the values of the functions at the 8 corners of the enclosing voxel.
- In the case of `iso_dcorners`, the values in the $\phi^T D \phi$ form (density-like quantities) [S1, unofficial].

**Data Structures:**
- **Brick Hash:** Built on-device, mapping brick IDs to memory slots. Rejected siblings (mask 0) are kept in the octree structure to ensure consecutive bricks are neighbors in memory [S1, unofficial].
- **Shells:** Precomputed lists of lattice points or coefficients for each shell level, stored in group-shared memory for the group [S1, unofficial].
- **Function Coefficients ($C$):** Stored in global memory, accessed via tiled GEMM if enabled [S1, unofficial].

**Steps:**
1. **Thread Group Initialization:** Each thread group processes 256 consecutive points from the input list [S1, unofficial].
2. **Brick Identification:** Determine the bricks enclosing the 256 points. This may span 2–4 neighboring bricks [S1, unofficial].
3. **Shell Setup:** Compute the shells required for the bounding box of the group's points. This setup is shared among all 256 threads, reducing overhead compared to per-brick setup (which would handle 70–125 points) [S1, unofficial].
4. **Point Processing:** For each point in the group:
   - Identify which shells are within reach. Skip shells outside the point's bounding box [S1, unofficial].
   - Load the necessary shell data from group-shared memory.
   - Compute the function values at the 8 corners. For `iso_corners_list_f1v4`, this involves one function. For variants, it involves 8, 16, 32, or 64 functions [S1, unofficial].
   - If using tiled GEMM (`iso_gcorners`), perform matrix multiplication of AO values and coefficients [S1, unofficial].
5. **Output:** Store the computed corner values. Points that skip shells due to being out of reach simply do not access those shell data blocks [S1, unofficial].

**Parameters:**
- `GTO_ISO_GEMM`: Boolean flag enabling tiled GEMM for corner computation. Default value is 1 [S1, unofficial].
- `GTO_ISO_CORNERS_LIST`: Switch to enable/disable the list-based processing mode. Default is 1 (enabled) [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Precision:** Standard floating-point precision is used. No specific higher-precision requirements are noted [S1, unofficial].
- **Boundaries:** Points near the edge of the grid or brick boundaries must correctly identify neighboring bricks. The octree structure ensures that rejected siblings are kept to maintain neighbor connectivity [S1, unofficial].
- **Degenerate Input:** If a point is far from any brick, it may skip all shells. The kernel handles this by checking shell reachability [S1, unofficial].

**Pseudocode:**
```python
# Pseudocode for iso_corners_list_f1v4 kernel
# Each thread group handles 256 points

def iso_corners_list_f1v4_kernel(points, bricks, shells, coeffs):
    # Shared memory for shells
    shared_shells = group_shared_memory()
    
    # 1. Identify bricks for the 256 points
    # This may involve 2-4 neighboring bricks
    brick_ids = identify_bricks(points)
    
    # 2. Shared shell setup for the group
    # Compute shells for the bounding box of the group's points
    group_shells = compute_shells_for_box(points, bricks)
    
    # Load shells into shared memory
    load_shells_to_shared(group_shells, shared_shells)
    
    # 3. Process each point in the group
    for i in range(256):
        point = points[i]
        brick_id = brick_ids[i]
        
        # Determine which shells are within reach
        reachable_shells = get_reachable_shells(point, group_shells)
        
        # Skip shells out of reach
        corner_values = zeros(8)
        
        for shell in reachable_shells:
            shell_data = shared_shells[shell]
            
            # Compute contribution to corner values
            # For f1v4, this is one function
            # Formula: value = sum(shell_coeff * point_offset)
            # Specific formula depends on the function type (e.g., Gaussian)
            contribution = compute_shell_contribution(shell_data, point)
            corner_values += contribution
        
        # Store result
        output[i] = corner_values
```

## Subtopics

### [Cube Index Calculation](3717-cube-index-calculation.md)
Computes an 8-bit integer index representing the configuration of a voxel's eight corners relative to an isolevel, determining which edges are intersected by the surface. It serves as the lookup key for the Marching Cubes lookup table. Unlike sibling methods that handle sparse point clouds or pre-gathered data, this method operates directly on the scalar values at the voxel corners to produce the topology case.

### iso_gcorners and iso_geval kernels (Tiled GEMM implementation)
Implementation of `iso_gcorners` and `iso_geval` kernels as tiled GEMM operations [S1, unofficial]. Tiled GEMM kernel for computing corners for sets of 16, 32, or 64 functions [S1, unofficial]. Process 128 rows per group for corner points of the list [S1, unofficial]. Alternatively, process 32 vertices x value and gradient channels per group [S1, unofficial]. GTO_ISO_GEMM: Boolean flag enabling tiled GEMM; default value is 1 [S1, unofficial]. Used for canonical sets of more than 64 functions (wide GEMM w128/w192/y256) or specific sizes 16/32/64 [S1, unofficial].

### Vertex evaluation kernel
Kernel for computing value and gradient at 64 vertices per group of 256 threads, used for sets with densities [S1, unofficial]. Kernel step: One warp per channel (value, d/dx, d/dy, d/dz) accumulating F function columns in registers [S1, unofficial]. Kernel step: Shells are listed and rows of C are staged as for corners [S1, unofficial]. Kernel step: One thread per vertex applies its field's terms from the channels staged 16 vertices at a time [S1, unofficial].

## Operating characteristics
- **Time Complexity:** The kernel processes 256 points per group, with shared shell setup reducing overhead. On lavapipe, mol at h=0.2, corner kernel times reduced from 38ms to 34ms (HOMO), 168ms to 144ms (diff density), 197ms to 121ms (trans density), 315ms to 246ms (16 MOs) [S1, unofficial].
- **Memory Complexity:** Uses group-shared memory for shells, reducing global memory bandwidth. The octree structure keeps rejected siblings to maintain neighbor connectivity, increasing memory usage slightly [S1, unofficial].
- **Scaling:** Performance scales with the number of threads and groups. Tiled GEMM improves performance for larger function sets [S1, unofficial].
- **Strengths:** High occupancy due to shared shell setup. Efficient for dense point lists.
- **Limitations:** Requires careful management of shared memory for shells. May not be optimal for very sparse point lists [S1, unofficial].
- **When to use:** When processing large lists of points for isosurface extraction or interpolation.
- **When not to use:** For very small point lists or sparse data where per-brick processing might be more efficient [S1, unofficial].

## Background
Originated in the `md_gto_iso_gpu` optimization for GPU isosurface extraction, specifically for molecular orbitals and densities [S1, unofficial]. Developed by scanberg and co-authored with Claude Opus 5.5 [S1, unofficial]. Used in computational chemistry for visualizing electron densities and molecular orbitals [S1, unofficial].
