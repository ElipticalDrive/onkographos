# Grid Cell Collection via Corner Indices

Also called: 8-Corner Grid Sampling, Trilinear Corner Indexing

## Overview
This method collects the scalar values at the 8 vertices of the grid cell enclosing each input point, providing the necessary data for trilinear interpolation or similar operations [S1, unofficial]. It differs from [Nearest Voxel Lookup with Periodic Boundary](1573-nearest-voxel-lookup-with-periodic-boundary.md) by retrieving all 8 surrounding corners rather than a single nearest neighbor, enabling smooth continuous field evaluation [S1, unofficial].

## How it works
**Inputs:** A tensor of input points (coordinates) and a dense grid tensor storing values at lattice vertices.
**Outputs:** A tensor of corner values corresponding to the 8 neighbors for each input point.

**Data Structures:**
- `normalized_samples_for_indices`: Tensor of shape `[N, 3]` containing the continuous coordinates $(x, y, z)$ for $N$ points.
- `relevant_points`: Tensor of shape `[N, 8, 3]` containing the integer indices of the 8 corners for each point.
- `grid_tensor`: The source data array indexed by these corners.

**Steps:**
1.  **Compute Floor and Ceil Coordinates:** For each dimension $d \in \{x, y, z\}$, compute the floor and ceiling of the input coordinates.
    $$
    \text{floor}_d = \lfloor \text{coord}_d \rfloor, \quad \text{ceil}_d = \lceil \text{coord}_d \rceil
    $$
2.  **Generate Corner Indices:** Create all $2^3=8$ combinations of floor/ceil indices for the three dimensions. This forms the set of corner indices for each point.
3.  **Reshape and Flatten:** Reshape the corner indices tensor to a flat list of points to facilitate batched indexing.
4.  **Handle Boundaries:** Fix out-of-bounds indices. The standard implementation uses periodic boundary conditions [S1, unofficial].
5.  **Index Grid:** Use the fixed integer indices to gather values from the `grid_tensor`.

**Pseudocode:**
```python
import torch

def collect_corner_indices(normalized_samples_for_indices: torch.Tensor) -> torch.Tensor:
    """
    Computes the 8 corner indices for a batch of points.
    
    Args:
        normalized_samples_for_indices: Tensor of shape [N, 3] with continuous coordinates.
        
    Returns:
        Tensor of shape [N, 8, 3] with integer corner indices.
    """
    # 1. Compute floor and ceil for each dimension
    # Extract x, y, z components
    x = normalized_samples_for_indices[:, 0].unsqueeze(1)
    y = normalized_samples_for_indices[:, 1].unsqueeze(1)
    z = normalized_samples_for_indices[:, 2].unsqueeze(1)
    
    floor_x = torch.floor(x)
    ceil_x = torch.ceil(x)
    floor_y = torch.floor(y)
    ceil_y = torch.ceil(y)
    floor_z = torch.floor(z)
    ceil_z = torch.ceil(z)
    
    # 2. Generate all 8 combinations
    # Order: (floor/ceil, floor/ceil, floor/ceil)
    relevant_points = []
    for x_comp in [floor_x, ceil_x]:
        for y_comp in [floor_y, ceil_y]:
            for z_comp in [floor_z, ceil_z]:
                # Concatenate along the last dimension
                corner = torch.cat([x_comp, y_comp, z_comp], dim=1)
                relevant_points.append(corner)
                
    # 3. Stack into [N, 8, 3]
    # relevant_points is a list of 8 tensors of shape [N, 1] or [N, 3] depending on concat
    # The source code shows: torch.cat([x_component, y_component, z_component], 1)
    # So each element in relevant_points is [N, 3]
    corners_tensor = torch.stack(relevant_points, dim=1) # Shape [N, 8, 3]
    
    # 4. Convert to long integers
    corners_tensor = corners_tensor.type(torch.long)
    
    return corners_tensor

def gather_corner_values(corners_tensor: torch.Tensor, grid_tensor: torch.Tensor, grid_shape: tuple) -> torch.Tensor:
    """
    Gathers values from the grid using corner indices with periodic boundary handling.
    
    Args:
        corners_tensor: Tensor of shape [N, 8, 3] with integer indices.
        grid_tensor: The dense grid data.
        grid_shape: Tuple (Dx, Dy, Dz) defining the grid dimensions.
        
    Returns:
        Tensor of shape [N, 8] with the gathered values.
    """
    N = corners_tensor.shape[0]
    values = torch.zeros(N, 8, device=corners_tensor.device)
    
    # 5. Index into grid with periodic boundary conditions
    for i in range(8):
        # Extract indices for the i-th corner
        idx_x = corners_tensor[:, i, 0]
        idx_y = corners_tensor[:, i, 1]
        idx_z = corners_tensor[:, i, 2]
        
        # Apply periodic boundary conditions
        # Note: Modulo operator in PyTorch handles negative numbers differently than C++
        # Standard periodic wrap: (idx % size + size) % size
        idx_x = ((idx_x % grid_shape[0]) + grid_shape[0]) % grid_shape[0]
        idx_y = ((idx_y % grid_shape[1]) + grid_shape[1]) % grid_shape[1]
        idx_z = ((idx_z % grid_shape[2]) + grid_shape[2]) % grid_shape[2]
        
        # Gather values
        # Assuming grid_tensor is indexed as [z, y, x] or similar; 
        # standard PyTorch gather requires specific indexing. 
        # For a dense tensor, direct indexing is used.
        values[:, i] = grid_tensor[idx_z, idx_y, idx_x]
        
    return values
```

**Parameters:**
- `grid_shape`: The dimensions of the voxel grid. Typical values depend on the application (e.g., $128^3$, $256^3$).
- `boundary_condition`: Default is periodic. Other implementations may use clamping or reflection [G].

**Edge Cases and Pitfalls:**
- **Precision:** Floating-point coordinates near integer boundaries may result in floor/ceil returning the same value if the point lies exactly on a vertex, or adjacent values if slightly off. This is expected behavior for trilinear interpolation.
- **Out-of-Bounds:** Indices must be wrapped or clamped. Failure to handle negative indices or indices $\ge$ grid size results in undefined behavior or crashes [S1, unofficial].
- **Degenerate Input:** If input points are outside the grid bounds, periodic wrapping maps them inside. If periodic boundaries are not desired, clamping to the nearest valid index is required [G].

## Subtopics

### [VoxelGrid](2159-voxelgrid.md)
VoxelGrid is a dense, learnable 3D data structure that defines a parameterized function in 3D space by storing learnable values at the middle of voxels but effectively storing corner values for interpolation. It enables differentiable trilinear interpolation of density and color, replacing coordinate-based MLPs with a fixed, axis-aligned tensor layout for efficient neural rendering.

### [Curvilinear to Rectilinear Resampling](2248-curvilinear-to-rectilinear-resampling.md)
This method converts a curvilinear input grid into a rectilinear output grid by estimating function values at new sample points. It differs from sibling methods like [VoxelGrid](2159-voxelgrid.md) by explicitly handling the geometric distortion of the input domain, requiring a cell-localization step before interpolation, whereas rectilinear grids assume a fixed, orthogonal topology.

### [Voxel Trilinear Interpolation (SIMD)](2564-voxel-trilinear-interpolation-simd.md)
This method performs trilinear interpolation of scalar voxel values from a 3D brick using SIMD instructions (specifically AVX/AVX2 via 128-bit registers) to accelerate volume rendering. It differs from standard scalar trilinear interpolation by packing two voxel samples into 128-bit registers and computing their contributions in parallel, effectively doubling throughput for single-channel data. It builds on [Grid Cell Collection via Corner Indices](1518-grid-cell-collection-via-corner-indices.md) by providing the optimized sampling kernel that consumes the corner indices and values.

### iso_corners_list_f1v4
**Definition:** A kernel variant for computing corners from a list of points, handling 1, 8, 16, 32, or 64 functions [S2, unofficial].

**Steps:**
1.  Process 256 consecutive lattice points per group, covering 2-4 neighbouring bricks [S2, unofficial].
2.  Ensure every thread is busy; shell setup is shared by 256 points instead of one brick's 70-125 [S2, unofficial].
3.  List shells for the box of the group's points. A point skips a shell out of its reach [S2, unofficial].

**Performance:** On lavapipe, mol at h=0.2, corner kernel times reduced from 38ms to 34ms (HOMO), 168ms to 144ms (diff density), 197ms to 121ms (trans density), 315ms to 246ms (16 MOs) [S2, unofficial].

**Comparison:** Compared to group-per-brick mode, this mode requires the octree's brick level to keep slots of rejected siblings (mask 0, no corner slots) so consecutive bricks are neighbours [S2, unofficial].

## Operating characteristics
**Time Complexity:** $O(N)$ where $N$ is the number of input points, as each point requires constant-time index generation and gathering.
**Memory Complexity:** $O(N)$ to store the corner indices and gathered values.
**Measured Performance:** In the `iso_corners_list_f1v4` variant, processing 256 points per group reduced kernel times significantly (e.g., 34ms vs 38ms for HOMO on lavapipe) by sharing shell setup overhead [S2, unofficial].
**Strengths:** Enables smooth, differentiable interpolation essential for neural rendering and scientific visualization.
**Limitations:** Requires memory for 8 values per point. Out-of-bounds handling adds computational overhead if not optimized.

## Background
Originating from standard volume rendering techniques, this method is fundamental to trilinear interpolation. It is widely used in neural rendering frameworks like Plenoxels [S1, unofficial] and scientific computing tools for isosurface extraction [S2, unofficial].
