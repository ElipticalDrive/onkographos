# Brick Volume Addressing with If-Else

Also called: Brick Addressing Logic

## Overview
Brick Volume Addressing with If-Else is a method to compute memory offsets for accessing neighboring samples in a brick-structured volume, primarily for resampling or gradient computation [S1, unofficial]. It solves the problem of efficiently determining whether adjacent samples lie within the current brick or in a neighboring brick by using explicit conditional checks [S1, unofficial]. Unlike [VoxelGrid](2159-voxelgrid.md) which assumes a uniform linear layout, this method handles the discontinuity at brick boundaries by falling back to a more complex calculation only when necessary [S1, unofficial]. It differs from its sibling [Lookup Table Addressing for Resampling](3535-lookup-table-addressing-for-resampling.md) by using runtime `if-else` branches instead of precomputed lookup tables, which incurs pipeline flush penalties but avoids table memory overhead [S1, unofficial].

## How it works
**Inputs:**
- Volume dimensions: $D_x, D_y, D_z$ (integers) [S1, unofficial].
- Brick dimensions: $BD_x, BD_y, BD_z$ (integers) [S1, unofficial].
- Brick volume dimensions: $BVD_x, BVD_y, BVD_z$ where $BVD_x = D_x / BD_x$, etc. (integers) [S1, unofficial].
- Current resample position integer parts: $i, j, k$ [S1, unofficial].

**Outputs:**
- Base offset: $SampleOffset_{i,j,k}$ [S1, unofficial].
- Offsets for 7 neighbors relative to the base offset or via `ComputeOffset` [S1, unofficial].

**Data Structures:**
- No complex structures; relies on integer arithmetic and conditional logic [S1, unofficial].

**Steps:**
1. Compute local brick coordinates:
   $$i' = i \pmod{BD_x}$$
   $$j' = j \pmod{BD_y}$$
   $$k' = k \pmod{BD_z}$$
   [S1, unofficial]

2. Compute global brick indices:
   $$i'' = \lfloor i / BD_x \rfloor$$
   $$j'' = \lfloor j / BD_y \rfloor$$
   $$k'' = \lfloor k / BD_z \rfloor$$
   [S1, unofficial]

3. Check if all 8 samples (the $2 \times 2 \times 2$ neighborhood) fit within the current brick. The condition is true if the maximum local coordinate of the neighborhood is strictly less than the brick dimension minus one:
   $$i' < BD_x - 1 \quad \text{AND} \quad j' < BD_y - 1 \quad \text{AND} \quad k' < BD_z - 1$$
   [S1, unofficial]

4. If the condition is true (all samples in current brick):
   - Compute base offset using linear addressing within the brick:
     $$SampleOffset_{i,j,k} = i' + j' \cdot BD_x + k' \cdot BD_x \cdot BD_y$$
     [S1, unofficial]
   - Compute neighbor offsets by adding constants to the base offset:
     - $SampleOffset_{i+1,j,k} = SampleOffset_{i,j,k} + 1$
     - $SampleOffset_{i,j+1,k} = SampleOffset_{i,j,k} + BD_x$
     - $SampleOffset_{i+1,j+1,k} = SampleOffset_{i,j,k} + 1 + BD_x$
     - $SampleOffset_{i,j,k+1} = SampleOffset_{i,j,k} + BD_x \cdot BD_y$
     - $SampleOffset_{i+1,j,k+1} = SampleOffset_{i,j,k} + 1 + BD_x \cdot BD_y$
     - $SampleOffset_{i,j+1,k+1} = SampleOffset_{i,j,k} + BD_x + BD_x \cdot BD_y$
     - $SampleOffset_{i+1,j+1,k+1} = SampleOffset_{i,j,k} + 1 + BD_x + BD_x \cdot BD_y$
     [S1, unofficial]

5. If the condition is false (at least one neighbor is in a different brick):
   - Compute base offset:
     $$SampleOffset_{i,j,k} = ComputeOffset(i,j,k)$$
     [S1, unofficial]
   - Compute each neighbor's absolute offset using `ComputeOffset`:
     - $SampleOffset_{i+1,j,k} = ComputeOffset(i+1,j,k)$
     - $SampleOffset_{i,j+1,k} = ComputeOffset(i,j+1,k)$
     - $SampleOffset_{i+1,j+1,k} = ComputeOffset(i+1,j+1,k)$
     - $SampleOffset_{i,j,k+1} = ComputeOffset(i,j,k+1)$
     - $SampleOffset_{i+1,j,k+1} = ComputeOffset(i+1,j,k+1)$
     - $SampleOffset_{i,j+1,k+1} = ComputeOffset(i,j+1,k+1)$
     - $SampleOffset_{i+1,j+1,k+1} = ComputeOffset(i+1,j+1,k+1)$
     [S1, unofficial]

6. The `ComputeOffset(i,j,k)` function is defined as:
   $$ComputeOffset(i,j,k) = BlkOffset_{i,j,k} \cdot (BD_x \cdot BD_y \cdot BD_z) + OffsetWithinBlk_{i,j,k}$$
   [S1, unofficial]
   Where:
   $$BlkOffset_{i,j,k} = i'' + j'' \cdot BVD_x + k'' \cdot (BVD_x \cdot BVD_y)$$
   [S1, unofficial]
   And:
   $$OffsetWithinBlk_{i,j,k} = i' + j' \cdot BD_x + k' \cdot (BD_x \cdot BD_y)$$
   [S1, unofficial]

**Pseudocode:**
```python
def brick_addressing_if_else(i, j, k, Dx, Dy, Dz, BDx, BDy, BDz):
    # Step 1: Local coordinates
    ip = i % BDx
    jp = j % BDy
    kp = k % BDz
    
    # Step 2: Global brick indices
    im = i // BDx
    jm = j // BDy
    km = k // BDz
    
    # Step 3: Check boundary condition
    if (ip < BDx - 1) and (jp < BDy - 1) and (kp < BDz - 1):
        # Step 4: Linear addressing within brick
        base = ip + jp * BDx + kp * BDx * BDy
        offsets = [
            0,                  # i, j, k
            1,                  # i+1, j, k
            BDx,                # i, j+1, k
            1 + BDx,            # i+1, j+1, k
            BDx * BDy,          # i, j, k+1
            1 + BDx * BDy,      # i+1, j, k+1
            BDx + BDx * BDy,    # i, j+1, k+1
            1 + BDx + BDx * BDy # i+1, j+1, k+1
        ]
        return [base + off for off in offsets]
    else:
        # Step 5: ComputeOffset for each neighbor
        def compute_offset(ii, jj, kk):
            iip = ii % BDx
            jip = jj % BDy
            kip = kk % BDz
            iim = ii // BDx
            jmm = jj // BDy
            kmm = kk // BDz
            
            blk_offset = iim + jmm * (Dx // BDx) + kmm * ((Dx // BDx) * (Dy // BDy))
            within_blk = iip + jip * BDx + kip * (BDx * BDy)
            return blk_offset * (BDx * BDy * BDz) + within_blk
            
        neighbors = [
            (i, j, k),
            (i+1, j, k),
            (i, j+1, k),
            (i+1, j+1, k),
            (i, j, k+1),
            (i+1, j, k+1),
            (i, j+1, k+1),
            (i+1, j+1, k+1)
        ]
        return [compute_offset(ni, nj, nk) for ni, nj, nk in neighbors]
```

**Parameters:**
- Brick dimensions $BD_{x,y,z}$: Typical values mentioned are $32 \times 32 \times 32$ and $16 \times 16 \times 16$ [S1, unofficial].

**Edge Cases and Pitfalls:**
- Branch prediction uncertainty causes pipeline flushes, leading to performance penalties compared to pure linear addressing [S1, unofficial].
- The `else` branch executes in 10% of cases for $32 \times 32 \times 32$ bricks and 18% of cases for $16 \times 16 \times 16$ bricks [S1, unofficial].

## Subtopics

### [Lookup Table Addressing for Resampling](3535-lookup-table-addressing-for-resampling.md)
Replaces the `if-else` branching with a direct table lookup to avoid pipeline flushes, significantly improving performance on hardware where branch prediction is costly.

## Operating characteristics
- **Time Complexity:** The `if` branch is $O(1)$ with simple arithmetic. The `else` branch involves multiple `ComputeOffset` calls, each requiring modulo and division operations, making it more expensive [S1, unofficial].
- **Performance:** A speedup of ~30% is achieved compared to a solution that always uses the costly address calculations (implied comparison to a naive non-optimized approach) [S1, unofficial]. The method is faster than pure `ComputeOffset` for every call but slower than pure linear addressing due to branch penalties [S1, unofficial].
- **Scaling:** The frequency of the expensive `else` branch decreases with larger brick sizes (10% for 32^3 vs 18% for 16^3) [S1, unofficial].
- **Strengths:** Simplifies address calculation for the majority of cases (when inside a brick) [S1, unofficial].
- **Limitations:** Incurs pipeline flushes due to branch prediction uncertainty [S1, unofficial].

## Background
This method is described in the context of real-time mono- and multi-volume rendering of large medical datasets on standard PC hardware [S1, unofficial]. It addresses the performance impact of computing two offsets instead of one in algorithms like volume raycasting [S1, unofficial].
