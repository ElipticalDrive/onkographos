# Grid Cell Collection via Corner Indices

Also called: 8-Corner Grid Sampling, Trilinear Corner Indexing, Voxel Grid Sampling

## Overview
Grid Cell Collection via Corner Indices extracts the scalar or vector values stored at the eight vertices of the grid cell enclosing a set of input points [S1, S2, unofficial]. This method serves as the foundational data retrieval step for trilinear interpolation and other continuous sampling techniques on dense voxel grids [S1, S2, unofficial]. Unlike nearest-neighbor lookup, which selects a single voxel, or piecewise quadratic methods, which require gradient data, this method explicitly gathers the eight surrounding corner values required to compute weighted averages based on the point's fractional position within the cell [S1, S2, unofficial]. It differs from [Nearest Voxel Lookup with Periodic Boundary](1573-nearest-voxel-lookup-with-periodic-boundary.md) by providing all eight neighbors rather than just the closest one, and from [Piecewise Quadratic Hermite Interpolation](4001-piecewise-quadratic-hermite-interpolation.md) by not requiring derivative information [S1, S2, unofficial].

## How it works
**Inputs:**
- `points`: A tensor of shape $(N, 3)$ containing $N$ query points with coordinates $(x, y, z)$ in normalized space $[0, 1]$ [S1, unofficial].
- `grid`: A dense 3D tensor of shape $(D_x, D_y, D_z, C)$ containing the voxel values, where $C$ is the number of channels [S1, unofficial].
- `stride` (optional): An integer step size used to skip voxels, effectively subsampling the grid [S2, unofficial].

**Outputs:**
- `corner_values`: A tensor of shape $(N, 8, C)$ containing the sampled values for each point [S2, unofficial].
- `corner_positions` (optional): A tensor of shape $(N, 8, 3)$ containing the 3D coordinates of the 8 corners [S2, unofficial].

**Data Structures:**
The output is organized such that for each point $i$, the 8 corners are indexed $0$ to $7$ [S2, unofficial]. A common layout maps indices 0–3 to the lowest Z-plane corners (bottom face) and indices 4–7 to the highest Z-plane corners (top face) [S2, unofficial]. Within each plane, the order is:
- 0: $(x_{min}, y_{min}, z_{min})$
- 1: $(x_{max}, y_{min}, z_{min})$
- 2: $(x_{max}, y_{max}, z_{min})$
- 3: $(x_{min}, y_{max}, z_{min})$
- 4: $(x_{min}, y_{min}, z_{max})$
- 5: $(x_{max}, y_{min}, z_{max})$
- 6: $(x_{max}, y_{max}, z_{max})$
- 7: $(x_{min}, y_{max}, z_{max})$ [S2, unofficial].

**Steps:**
1. **Coordinate Discretization**: For each point $(x, y, z)$, compute the floor and ceiling indices along each axis [S1, unofficial]. Let $D_x, D_y, D_z$ be the grid dimensions [S1, unofficial].
   $$ i_x^{floor} = \lfloor x \cdot D_x \rfloor, \quad i_x^{ceil} = \lceil x \cdot D_x \rceil $$
   $$ i_y^{floor} = \lfloor y \cdot D_y \rfloor, \quad i_y^{ceil} = \lceil y \cdot D_y \rceil $$
   $$ i_z^{floor} = \lfloor z \cdot D_z \rfloor, \quad i_z^{ceil} = \lceil z \cdot D_z \rceil $$ [S1, unofficial].
2. **Corner Index Generation**: Generate all $2^3 = 8$ combinations of the floor and ceiling indices for the three axes [S1, unofficial].
3. **Index Flattening**: Reshape the corner indices tensor to a flat list of points [S1, unofficial].
4. **Boundary Handling**: Fix out-of-bounds indices using periodic boundary conditions [S1, unofficial].
5. **Value Retrieval**: Index into the grid tensor using the fixed indices [S1, unofficial].

**Pseudocode:**
```python
import torch

def collect_corner_indices(points, grid, stride=1, periodic=True):
    """
    Collects the 8 corner values for a batch of points from a 3D grid.
    Args:
        points: Tensor of shape (N, 3) with coordinates in [0, 1].
        grid: Tensor of shape (Dx, Dy, Dz, C) containing voxel values.
        stride: Integer step size to skip voxels [S2, unofficial].
        periodic: Boolean flag for periodic boundary conditions [S1, unofficial].
    Returns:
        corner_values: Tensor of shape (N, 8, C).
    """
    Dx, Dy, Dz, C = grid.shape
    N = points.shape[0]

    # 1. Coordinate Discretization: compute floor and ceil indices
    x_floor = torch.floor(points[:, 0] * Dx).long()
    x_ceil = torch.ceil(points[:, 0] * Dx).long()
    y_floor = torch.floor(points[:, 1] * Dy).long()
    y_ceil = torch.ceil(points[:, 1] * Dy).long()
    z_floor = torch.floor(points[:, 2] * Dz).long()
    z_ceil = torch.ceil(points[:, 2] * Dz).long()

    # 2. Generate all 8 combinations of (ceil/floor) x (ceil/floor) x (ceil/floor)
    # Order matches standard trilinear layout: 0:(0,0,0) to 7:(1,1,1)
    ix = torch.stack([x_floor, x_ceil, x_ceil, x_floor, x_floor, x_ceil, x_ceil, x_floor], dim=1)
    iy = torch.stack([y_floor, y_floor, y_ceil, y_ceil, y_floor, y_floor, y_ceil, y_ceil], dim=1)
    iz = torch.stack([z_floor, z_floor, z_floor, z_floor, z_ceil, z_ceil, z_ceil, z_ceil], dim=1)

    # Apply stride multiplier to indices [S2, unofficial]
    ix = ix * stride
    iy = iy * stride
    iz = iz * stride

    # 3. Reshape to flat list for gathering (N * 8)
    ix_flat = ix.reshape(-1)
    iy_flat = iy.reshape(-1)
    iz_flat = iz.reshape(-1)

    # 4. Fix out-of-bounds indices using periodic boundary conditions [S1, unofficial]
    if periodic:
        ix_flat = ix_flat % Dx
        iy_flat = iy_flat % Dy
        iz_flat = iz_flat % Dz
    else:
        ix_flat = torch.clamp(ix_flat, 0, Dx - 1)
        iy_flat = torch.clamp(iy_flat, 0, Dy - 1)
        iz_flat = torch.clamp(iz_flat, 0, Dz - 1)

    # 5. Index into the grid tensor using the fixed indices [S1, unofficial]
    # grid shape: (Dx, Dy, Dz, C)
    corner_values_flat = grid[ix_flat, iy_flat, iz_flat, :]  # (N * 8, C)

    # Reshape back to (N, 8, C)
    corner_values = corner_values_flat.reshape(N, 8, C)
    return corner_values
```

**Parameters:**
- `stride`: Default 1. Used to subsample the grid [S2, unofficial].
- `periodic`: Default True in neural rendering contexts to avoid boundary artifacts [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Precision**: Floating point coordinates near integer boundaries may result in `floor` and `ceil` being equal or off-by-one due to epsilon errors [G].
- **Out of Bounds**: If `periodic` is False, indices must be clamped to prevent out-of-bounds memory access [S1, unofficial].
- **Stride Alignment**: If `stride` > 1, the effective grid resolution is reduced, and query points must be scaled accordingly or the stride applied to indices [S2, unofficial].
- **Uninitialized Corners**: If boundary handling fails or is omitted, the corresponding corner in the output structure remains uninitialized (default value for the data type), which may lead to incorrect interpolation if not handled by the caller [S4, unofficial].

## Subtopics

### [VoxelGrid](2159-voxelgrid.md)
VoxelGrid is a dense, learnable 3D data structure that defines a parameterized function in 3D space by storing learnable values at the middle of voxels but effectively storing corner values for interpolation. It enables differentiable trilinear interpolation of density and color, replacing coordinate-based MLPs with a fixed, axis-aligned tensor layout for efficient neural rendering. It is chosen when a fixed, efficient tensor layout is preferred over MLPs for neural rendering.

### [Curvilinear to Rectilinear Resampling](2248-curvilinear-to-rectilinear-resampling.md)
This method converts a curvilinear input grid into a rectilinear output grid by estimating function values at new sample points. It differs from sibling methods like [VoxelGrid](2159-voxelgrid.md) by explicitly handling the geometric distortion of the input domain, requiring a cell-localization step before interpolation, whereas rectilinear grids assume a fixed, orthogonal topology. It is chosen when the source data is not axis-aligned.

### [Voxel Trilinear Interpolation (SIMD)](2564-voxel-trilinear-interpolation-simd.md)
Voxel Trilinear Interpolation (SIMD) retrieves scalar voxel values at arbitrary normalized coordinates within a 3D volume by interpolating between the 8 surrounding corner voxels, optimized for throughput using Single Instruction, Multiple Data (SIMD) instructions. It builds on [Grid Cell Collection via Corner Indices](1518-grid-cell-collection-via-corner-indices.md) by providing the specific arithmetic and memory access patterns required to evaluate the trilinear function efficiently on modern hardware. Unlike standard scalar implementations, this method processes multiple components (e.g., RGB or RGBA) in parallel using vector registers, significantly reducing instruction count for dense volume rendering. It is chosen for high-performance CPU/GPU rendering where throughput is critical.

### [3D Trilinear Interpolation](2613-3d-trilinear-interpolation.md)
3D Trilinear Interpolation estimates the value of a scalar or vector field at an arbitrary point $P=(x,y,z)$ within a regular 3D grid by combining the values at the eight corners of the enclosing voxel cell. It solves the problem of sampling dense grid data at sub-voxel resolution, providing smoother results than nearest-neighbor sampling. Unlike [VoxelGrid](2159-voxelgrid.md) which may imply discrete access, or [Curvilinear to Rectilinear Resampling](2248-curvilinear-to-rectilinear-resampling.md) which handles non-axis-aligned grids, this method assumes an axis-aligned, orthogonal rectangular parallelepiped cell. It is computationally cheaper than [Cubic Interpolation](link) but introduces visible artifacts (diamonds/crosses) at high magnification. It is chosen for general-purpose smooth interpolation on regular grids.

### [iso_corners_list_f1v4](2627-iso-corners-list-f1v4.md)
`iso_corners_list_f1v4` is a GPU kernel variant for computing grid cell corner indices from a list of input points, supporting 1, 8, 16, 32, or 64 functions. It builds on [Grid Cell Collection via Corner Indices](1518-grid-cell-collection-via-corner-indices.md) by processing 256 consecutive lattice points per group across 2–4 neighboring bricks, sharing shell setup overhead across the group rather than per-brick. It is chosen for high-throughput GPU-based isosurface extraction or rendering on brick-structured volumes.

### [UniformGrid Cell Vertex and Material Retrieval](2999-uniformgrid-cell-vertex-and-material-retrieval.md)
This method retrieves the linear indices and associated material data for the 8 vertices of a grid cell within a uniform 3D grid, given the linear index of the cell itself. It serves as the foundational indexing step for operations requiring corner values, such as trilinear interpolation or marching cubes, by mapping a single cell identifier to its constituent geometric corners. It differs from its parent [Grid Cell Collection via Corner Indices](1518-grid-cell-collection-via-corner-indices.md) by providing the explicit arithmetic formula for linear index calculation in a uniform grid, rather than a generic collection interface. It is chosen when the input is a cell ID rather than continuous coordinates.

### [Brick Volume Addressing with If-Else](3340-brick-volume-addressing-with-if-else.md)
Brick Volume Addressing with If-Else is a method to compute memory offsets for accessing neighboring samples in a brick-structured volume, primarily for resampling or gradient computation. It solves the problem of efficiently determining whether adjacent samples lie within the current brick or in a neighboring brick by using explicit conditional checks. Unlike [VoxelGrid](2159-voxelgrid.md) which assumes a uniform linear layout, this method handles the discontinuity at brick boundaries by falling back to a more complex calculation only when necessary. It differs from its sibling [Lookup Table Addressing for Resampling](3535-lookup-table-addressing-for-resampling.md) by using runtime `if-else` branches instead of precomputed lookup tables, which incurs pipeline flush penalties but avoids table memory overhead. It is chosen for brick-structured volumes where memory overhead of lookup tables is prohibitive.

### Grid Interpolation with Boundary Handling
A linearly interpolated grid structure used for voxel interpolation (interp5) and image plane interpolation (interp4), handling boundary conditions via constant value filling [S3, unofficial].
- **interp4**: Map coordinates $x$ in $[0,1]$ to grid indices: $coords = (x \cdot grid\_res) - 0.5$. Flip coords along last axis. Use `jax.scipy.ndimage.map_coordinates` with order=1 and `cval` [S3, unofficial].
- **interp5**: Map coordinates $x$ to grid indices: $coords = (x \cdot (grid\_res+1)) - 1$. Permute x and y axes using matrix $\begin{bmatrix} 0 & 1 & 0 \\ 1 & 0 & 0 \\ 0 & 0 & 1 \end{bmatrix}$ [S3, unofficial]. Use `jax.scipy.ndimage.map_coordinates` with order=1 and `cval` [S3, unofficial].
- **Parameters**: `grid_vals`: `jnp.ndarray`, the voxel points to interpolate between. `cval`: `float`, constant value to fill past edges, default 0 [S3, unofficial].
It is chosen when using JAX-based pipelines with specific coordinate transformations for image plane or voxel interpolation [S3, unofficial].

## Operating characteristics
- **Time Complexity**: $O(N)$ for $N$ points, as each point requires constant time (8 lookups) to collect corners [S1, S2, unofficial].
- **Memory Complexity**: $O(N \cdot 8 \cdot C)$ to store the corner values for $N$ points with $C$ channels [G].
- **Scaling**: Scales linearly with the number of points. Grid size does not affect lookup time, only memory bandwidth [S1, unofficial].
- **Strengths**: Simple, differentiable, and efficient for dense grids [S1, unofficial].
- **Limitations**: Does not handle non-axis-aligned grids (use [Curvilinear to Rectilinear Resampling](2248-curvilinear-to-rectilinear-resampling.md)) [S1, unofficial]. Requires boundary handling for points outside the grid [S1, unofficial].
- **When to Use**: When trilinear interpolation is required on a regular grid [S1, S2, unofficial].
- **When Not to Use**: When the grid is sparse (use [Sparse Voxel Octrees](link)) or non-axis-aligned (use [Curvilinear to Rectilinear Resampling](2248-curvilinear-to-rectilinear-resampling.md)) [S1, S2, unofficial].

## Background
The method originates from standard computer graphics techniques for sampling dense voxel data [S1, S2, unofficial]. Implementation details, such as the `VoxSample` struct layout and brick-based addressing logic, are documented in [S2, unofficial]. JAX-based variants with specific boundary handling are documented in [S3, unofficial].
