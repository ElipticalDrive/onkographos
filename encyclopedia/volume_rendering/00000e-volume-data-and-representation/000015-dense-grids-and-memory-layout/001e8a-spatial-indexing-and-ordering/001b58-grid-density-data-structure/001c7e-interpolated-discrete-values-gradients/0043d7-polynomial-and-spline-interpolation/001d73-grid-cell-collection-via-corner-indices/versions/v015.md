# Grid Cell Collection via Corner Indices

Also called: 8-Corner Grid Sampling, Trilinear Corner Indexing, GatherGeoParams, GatherFeatParams, Gather Tri-Interpolated Geometry Parameters, Gather Tri-Interpolated Feature Parameters

## Overview
Grid Cell Collection via Corner Indices is a data gathering method that retrieves the values stored at the eight vertices of the grid cell enclosing a set of query points, preparing them for trilinear interpolation or similar basis evaluations [S1, S2, S3, unofficial]. It solves the problem of efficiently mapping arbitrary continuous coordinates to the discrete support points required by the parent [Polynomial and Spline Interpolation](11104-polynomial-and-spline-interpolation.md) without computing the final weighted sum itself. It sets itself apart from higher-order methods like [B-spline Field Interpolation](11066-b-spline-field-interpolation.md) by strictly limiting the support to the immediate 8 neighbors of the enclosing voxel, and from [VoxelGrid](2159-voxelgrid.md) by focusing on the index computation and raw data retrieval step rather than the full differentiable rendering pipeline [S2, S3, unofficial].

## How it works
**Inputs:**
*   A dense grid tensor $\mathbf{G}$ of shape $(D_x, D_y, D_z, C)$, where $D$ are the spatial dimensions and $C$ is the channel count (e.g., density, color, or geometry parameters) [S1, S2, S3, unofficial].
*   A set of query points $\mathbf{P} \in \mathbb{R}^{N \times 3}$, where $N$ is the number of points and each row is $(x, y, z)$ [S1, S2, unofficial].
*   Optional: A stride parameter or grid resolution for coordinate normalization [S3, S4, unofficial].

**Outputs:**
*   A tensor of gathered values $\mathbf{V} \in \mathbb{R}^{N \times 8 \times C}$, where each point has 8 entries corresponding to the 8 corners of its enclosing cell [S1, S2, S3, unofficial].
*   In some implementations, a `VoxSample` structure containing arrays of values and positions [S3, unofficial].

**Data Structures:**
*   **Corner Indices:** A tensor of shape $(N \times 8, 3)$ containing integer coordinates for the 8 corners. The 8 combinations are generated from the floor and ceil of the query point's coordinates [S1, unofficial].
*   **VoxSample (Optional):** A struct used in some C++ implementations containing:
    *   `values`: `float[8]`
    *   `positions`: `vec3[8]`
    *   Index mapping: Indices 0-3 correspond to the lowest Z-plane corners (sw, se, ne, nw), and indices 4-7 correspond to the highest Z-plane corners (sw, se, ne, nw) [S3, unofficial].

**Steps:**
1.  **Coordinate Normalization (Optional):** If the grid is defined in physical space, normalize query points to the range $[0, 1]$ or $[0, D_d-1]$ depending on the implementation's indexing convention [S1, S4, unofficial].
2.  **Index Computation:** For each query point $\mathbf{p}_i = (x_i, y_i, z_i)$:
    *   Compute floor indices: $f_x = \lfloor x_i \rfloor, f_y = \lfloor y_i \rfloor, f_z = \lfloor z_i \rfloor$.
    *   Compute ceil indices: $c_x = \lceil x_i \rceil, c_y = \lceil y_i \rceil, c_z = \lceil z_i \rceil$.
    *   Generate the 8 corner index tuples by taking the Cartesian product of $\{f_x, c_x\} \times \{f_y, c_y\} \times \{f_z, c_z\}$ [S1, unofficial].
3.  **Boundary Handling:** Fix out-of-bounds indices. Common strategies include:
    *   Periodic boundary conditions (modulo grid dimensions) [S1, unofficial].
    *   Clamping to the nearest valid index $[0, D_d-1]$ [S2, S3, unofficial].
    *   Constant value filling for out-of-bounds queries, often handled by the interpolation wrapper rather than the gather step itself [S4, unofficial].
4.  **Gathering:** Index into the grid tensor $\mathbf{G}$ using the fixed corner indices.
    *   If using PyTorch-like indexing: `gathered = G[corner_indices]` [S1, unofficial].
    *   If using custom C++ kernels (e.g., `gather_triinterp_geo_params`): Pass voxel keys and care indices to a CUDA kernel that performs the gather [S2, unofficial].
5.  **Reshaping:** Reshape the flat list of gathered values back to shape $(N, 8, C)$ [S1, unofficial].

**Pseudocode:**
```python
import torch
import math

def grid_cell_collection_via_corner_indices(grid: torch.Tensor, points: torch.Tensor) -> torch.Tensor:
    """
    Collects voxel values at the 8 corners of the grid cell enclosing each input point.
    
    Args:
        grid: Tensor of shape (Dx, Dy, Dz, C)
        points: Tensor of shape (N, 3) with coordinates (x, y, z)
        
    Returns:
        Tensor of shape (N, 8, C) containing the values at the 8 corners
    """
    # 1. Compute floor and ceil indices
    # Clamp to valid range [0, D-1] to handle boundary conditions
    Dx, Dy, Dz, C = grid.shape
    
    floor_x = torch.clamp(torch.floor(points[:, 0]).long(), 0, Dx - 1)
    floor_y = torch.clamp(torch.floor(points[:, 1]).long(), 0, Dy - 1)
    floor_z = torch.clamp(torch.floor(points[:, 2]).long(), 0, Dz - 1)
    
    ceil_x = torch.clamp(torch.ceil(points[:, 0]).long(), 0, Dx - 1)
    ceil_y = torch.clamp(torch.ceil(points[:, 1]).long(), 0, Dy - 1)
    ceil_z = torch.clamp(torch.ceil(points[:, 2]).long(), 0, Dz - 1)
    
    # 2. Generate all 8 combinations
    # Order: (floor/floor/floor, floor/floor/ceil, ..., ceil/ceil/ceil)
    # Using itertools.product logic manually for clarity
    indices = []
    for x in [floor_x, ceil_x]:
        for y in [floor_y, ceil_y]:
            for z in [floor_z, ceil_z]:
                indices.append(torch.stack([x, y, z], dim=1))
                
    corner_indices = torch.cat(indices, dim=0) # Shape (N*8, 3)
    
    # 3. Gather values
    # Gather from grid using advanced indexing
    # Note: In practice, this might be done via a custom CUDA kernel for performance
    # Here we simulate the gather operation
    gathered_values = grid[corner_indices[:, 0], corner_indices[:, 1], corner_indices[:, 2]] # Shape (N*8, C)
    
    # 4. Reshape to (N, 8, C)
    gathered_values = gathered_values.view(-1, 8, C)
    
    return gathered_values
```

**Parameters:**
*   `grid`: The dense 3D tensor. Size: $(D_x, D_y, D_z, C)$.
*   `points`: Query coordinates. Size: $(N, 3)$.
*   `boundary_mode`: Strategy for out-of-bounds indices (clamp, periodic, constant). Default: Clamp [S1, S4, unofficial].

**Edge Cases and Pitfalls:**
*   **Precision:** Floating-point coordinates near integer boundaries may result in floor/ceil ambiguity. Ensure consistent handling (e.g., always clamp) to avoid index errors [S1, S2, unofficial].
*   **Degenerate Input:** Points exactly on grid boundaries may have ceil indices equal to $D_d$, which must be clamped to $D_d-1$ [S1, S2, unofficial].
*   **Memory:** Gathering $N \times 8$ values can be memory-intensive for large $N$. Use streaming or batched processing if necessary [S3, unofficial].

## Subtopics

### [VoxelGrid](2159-voxelgrid.md)
VoxelGrid is a dense, learnable 3D data structure that defines a parameterized function in 3D space by storing learnable values at the grid vertices to support efficient feature queries via trilinear interpolation. It enables differentiable trilinear interpolation of density and color, replacing coordinate-based MLPs with a fixed, axis-aligned tensor layout for efficient neural rendering. It builds on [Grid Cell Collection via Corner Indices](1518-grid-cell-collection-via-corner-indices.md) by explicitly storing values at the 8 corners of each voxel for interpolation.

### [Curvilinear to Rectilinear Resampling](2248-curvilinear-to-rectilinear-resampling.md)
This method converts a curvilinear input grid into a rectilinear output grid by estimating function values at new sample points.

### [Voxel Trilinear Interpolation (SIMD)](2564-voxel-trilinear-interpolation-simd.md)
Voxel Trilinear Interpolation (SIMD) retrieves scalar or vector values from a dense 3D volume grid at arbitrary floating-point coordinates by performing trilinear interpolation across the 8 surrounding voxel corners, optimized for Single Instruction, Multiple Data (SIMD) execution units. It solves the problem of extracting continuous fields from discrete voxel representations while maximizing throughput on modern CPUs. It sets itself apart from its sibling [3D Trilinear Interpolation](2613-3d-trilinear-interpolation.md) by explicitly structuring the computation to exploit SIMD registers (e.g., AVX/AVX2) for parallel evaluation of multiple components or channels, and from [VoxelGrid](2159-voxelgrid.md) by providing the specific low-level sampling kernel rather than the grid structure itself.

### [3D Trilinear Interpolation](2613-3d-trilinear-interpolation.md)
3D Trilinear Interpolation reconstructs the value of a scalar field at an arbitrary point within a voxel by linearly interpolating the values at the eight corners of the enclosing grid cell. It is the standard reconstruction filter for structured rectilinear volume data, providing $C^0$ continuity and smoother results than nearest-neighbor sampling at the cost of higher computational complexity. It differs from higher-order methods like [Cubic Volume Interpolation](4278-cubic-volume-interpolation.md) by using only the immediate 8 neighbors and linear weights, and from [VoxelGrid](2159-voxelgrid.md) by explicitly computing off-grid values rather than returning discrete cell contents.

### [iso_corners_list_f1v4](2627-iso-corners-list-f1v4.md)
`iso_corners_list_f1v4` is a GPU kernel variant that computes the values of one function at the eight corners of the grid cells enclosing a list of input points, enabling trilinear interpolation or surface extraction. It differs from its siblings by processing 256 consecutive lattice points per thread group across 2–4 neighboring bricks, sharing shell setup overhead among all points in the group rather than per-brick, which improves occupancy and reduces redundant memory accesses.

### [Brick Volume Addressing with If-Else](3340-brick-volume-addressing-with-if-else.md)
Brick Volume Addressing with If-Else is a method to compute memory offsets for accessing neighboring samples in a brick-structured volume, primarily for resampling or gradient computation. It solves the problem of efficiently determining whether adjacent samples lie within the current brick or in a neighboring brick by using explicit conditional checks. Unlike sibling methods that assume a uniform linear layout, this method uses an `if-else` statement to test if needed data elements are within one brick; if true, it uses fast linear addressing, otherwise it falls back to costly address calculations. It differs from its sibling [Lookup Table Addressing for Resampling](3535-lookup-table-addressing-for-resampling.md) by using runtime `if-else` branches instead of precomputed lookup tables, which incurs pipeline flush penalties but avoids table memory overhead.

### Grid Interpolation with Boundary Handling
A linearly interpolated grid structure used for voxel interpolation (interp5) and image plane interpolation (interp4), handling boundary conditions via constant value filling [S4, unofficial]. It wraps a 2D/3D grid of values into a callable interpolation function, supporting 4th-order (bicubic) and 5th-order interpolation with a specified constant value for out-of-bounds queries [S4, unofficial].
*   **Steps:**
    1.  Initialize `Grid2` with `grid_vals` and `cval` (constant value for out-of-bounds, default 0) [S4, unofficial].
    2.  For `interp4`: Map coordinates $x \in [0,1]$ to grid indices: $\text{coords} = (x \cdot \text{grid\_res}) - 0.5$. Flip coords along the last axis. Use `jax.scipy.ndimage.map_coordinates` with `order=1` and `cval` [S4, unofficial].
    3.  For `interp5`: Map coordinates $x$ to grid indices: $\text{coords} = (x \cdot (\text{grid\_res}+1)) - 1$. Permute x and y axes using matrix $\begin{bmatrix} 0 & 1 & 0 \\ 1 & 0 & 0 \\ 0 & 0 & 1 \end{bmatrix}$. Use `jax.scipy.ndimage.map_coordinates` with `order=1` and `cval` [S4, unofficial].
    4.  Return a lambda function that calls the appropriate interpolation method [S4, unofficial].
*   **Parameters:** `grid_vals`: `jnp.ndarray`, the voxel points to interpolate between. `cval`: `float`, constant value to fill past edges, default 0 [S4, unofficial].

### VIPER Cell Sampling with Extrapolation Flag Invalidation
A cell sampling technique that uses tri-linear interpolation at ray entry and exit points to check if target values lie within the cell range, combined with vertex flags to invalidate cells containing extrapolated data [S6, unofficial].
*   **Steps:**
    1.  Interpolate data values at the exact points where a ray enters and exits a grid cell [S6, unofficial].
    2.  Compare target values to the interpolated entry and exit values to determine if they lie within the cell [S6, unofficial].
    3.  Check the eight vertices of the cell for a flag value (positive or negative) [S6, unofficial].
    4.  If any vertex contains the flag value, ignore the cell and continue rendering [S6, unofficial].
    5.  During data placement, set a flag at each grid node that receives data [S6, unofficial].
    6.  After placement completes, assign a value equal to twice the largest data value found to all nodes with an unset flag [S6, unofficial].
    7.  Write the twice-maximum value to the data file so VIPER can read it during rendering [S6, unofficial].
*   **Pitfalls:** Tri-linear interpolation across cells containing extrapolated data (unset flags) may produce a range that falsely contains a target value [S6, unofficial]. A-buffering delays knowledge of the largest data value until all points are processed, whereas Z-buffering finds it during placement [S6, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ for $N$ query points, as each point requires constant-time index computation and 8 memory accesses [S1, S2, unofficial].
*   **Memory Complexity:** $O(N \cdot C)$ for the output tensor, where $C$ is the channel count [S1, S2, unofficial].
*   **Performance:** Highly efficient on GPUs when implemented as a custom kernel (e.g., `gather_triinterp_geo_params`) due to coalesced memory access patterns [S2, unofficial]. Performance on CPUs can be improved using SIMD optimizations [S5, unofficial].
*   **Strengths:** Simple, differentiable, and efficient for dense grids [S1, S2, unofficial].
*   **Limitations:** Limited to linear interpolation; not suitable for high-frequency details without higher-order methods [S3, unofficial]. Boundary handling can introduce artifacts if not carefully managed [S4, S6, unofficial].
*   **When to use:** When trilinear interpolation is sufficient and performance is critical [S1, S2, S5, unofficial].
*   **When not to use:** When higher-order continuity or accuracy is required [S3, unofficial].

## Background
The method originates from the need for efficient sampling in neural radiance fields and voxel-based rendering, particularly in implementations like Plenoxels and Sparse Voxel Rasterization [S1, S2, unofficial]. It is a fundamental building block for differentiable volume rendering, allowing gradients to flow back to the grid values [S2, unofficial]. The specific kernel names (`gather_triinterp_geo_params`, `gather_triinterp_feat_params`) are associated with custom CUDA extensions in these frameworks [S2, unofficial].
