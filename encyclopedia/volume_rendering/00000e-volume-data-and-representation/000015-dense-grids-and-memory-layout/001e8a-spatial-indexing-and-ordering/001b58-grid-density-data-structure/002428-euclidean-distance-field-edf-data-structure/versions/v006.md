# Euclidean Distance Field (EDF) Data Structure

Also called: EuclideanDF, Tiled Euclidean Distance Fields

## Overview
The Euclidean Distance Field (EDF) is a dense grid data structure used in volume rendering to accelerate ray traversal by storing the distance to the nearest occupied voxel [S1, unofficial]. It solves the problem of slow, voxel-by-ray stepping in dense or complex geometries by allowing rays to skip empty space in large increments proportional to the stored distance [S1, unofficial]. It is distinguished from its siblings, such as the [VoxelGrid Data Structure](1216-voxelgrid-data-structure.md) which steps one voxel at a time, and the [EdgeMap Data Layout](1109-edgemap-data-layout.md) which uses boundary representations, by providing a continuous metric of proximity that trades higher memory bandwidth and pre-processing costs for only modest traversal length reductions (~8% shorter than space-partitioning methods) [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A binary occupancy grid where voxels are marked as empty or occupied [S1, unofficial].
*   **Output:** A tiled EDF grid containing downsampled distance values and a corresponding occupancy bitmask grid [S1, unofficial].

**Data Structures:**
The implementation uses a tiled layout to balance memory cost and traversal efficiency [S1, unofficial].
1.  **Distance Field Grid:** Stores distance values at a reduced resolution [S1, unofficial]. One distance value represents a $4^3 = 64$ voxel block [S1, unofficial].
    *   **Layout:** 2 bytes per $4^3$ voxel block [S1, unofficial].
2.  **Occupancy Bitmask Grid:** Stores a single bit per $1^3$ voxel to indicate exact occupancy within the coarse blocks [S1, unofficial].
    *   **Layout:** 1 bit per $1^3$ voxel [S1, unofficial].

**Algorithm Steps:**
1.  **Compute Distance Field:** Calculate the Euclidean distance from every voxel to the nearest occupied voxel [G].
2.  **Downsample:** Store the computed distances in the coarse grid at a 1:4 resolution [S1, unofficial].
3.  **Generate Bitmasks:** Create a bitmask for every $4^3$ block, where the $i$-th bit is set if the $i$-th voxel in that block is occupied [S1, unofficial].
4.  **Ray Traversal:**
    *   Query the EDF grid to get the distance $d$ to the nearest occupied voxel [S1, unofficial].
    *   If $d > 0$, advance the ray position by $d$ [S1, unofficial].
    *   If $d = 0$, the ray is at or near an occupied voxel [S1, unofficial]. Query the occupancy bitmask for the current $4^3$ block to determine exact occupancy or refine the traversal step [S1, unofficial].

**Pseudocode:**
```python
def step_ray(ray_pos, edf_grid, bitmask_grid):
    # Map ray position to tile and block indices [G]
    tile_idx, block_idx = get_grid_indices(ray_pos)
    
    # Query distance field
    d = edf_grid[tile_idx][block_idx]
    
    if d > 0:
        return d  # Advance ray by distance
    else:
        # d == 0: query occupancy bitmask for exact voxel check [S1, unofficial]
        if bitmask_grid[tile_idx][block_idx].test_bit(ray_pos.local_index()):
            return 0.0  # Hit occupied voxel
        else:
            return 1.0  # Advance by 1 voxel to avoid stall
```

**Parameters:**
*   **Scale Factor:** 4 (1:4 resolution) [S1, unofficial]. This was chosen to reduce memory costs without significantly harming traversal efficiency [S1, unofficial].
*   **Tile Size:** $256^3$ voxels [S1, unofficial]. The EDF is tiled at this resolution for memory management [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Grazing Rays:** Dense areas with fine geometry (like foliage) are worst cases for ray traversal because they cause grazing rays to advance slowly, as distance values remain small [S1, unofficial].
*   **Pre-processing Cost:** Computing the EDF has a significant cost, reported as 10x more GPU time than XBrickMap [S1, unofficial].
*   **Memory Bandwidth:** The method incurs high memory bandwidth costs, which becomes problematic for incoherent rays that lose coherence as they move away from the origin [S1, unofficial].
*   **Traversal Length:** The traversal is not considerably shorter than methods relying on space partitioning (~8% reduction), limiting the overall performance gain [S1, unofficial].

## Subtopics

### [Felzenswalb Distance Transform](4676-felzenswalb-distance-transform.md)
The Felzenswalb distance transform is an algorithm for computing the exact Euclidean distance field (EDF) from a binary volume in three passes, eliminating the propagation and numerical errors inherent in approximate methods. It is distinguished from its nearest alternative, the Satherley and Jones method, by its exactness, parallelizability, and significantly higher computational efficiency, though it requires greater memory consumption.

### Manhattan Distance Field (ManhattanDF)
Space skipping traversal using tiled $256^3$ Manhattan distance fields at 1:4 resolution, combined with $4^3$ occupancy bitmasks [S1, unofficial]. Memory cost is 1 byte per $4^3$ voxel plus 1 bit per $1^3$ voxel [S1, unofficial].

### Weighted Euclidean Distance Field
A geometric measure of spatial location used as a diversifying information attribute in Multi-Dimensional Transfer Function (MDTF) design, allowing users to set seed points or define body parts [S2, unofficial].
$$ \rho(\mathbf{x}) = \left( \sum_{i=1}^3 k_i (x_i - c_i)^2 \right)^{1/2} $$
where $\mathbf{x} = (x_1, x_2, x_3)$ is the voxel position, $(c_1, c_2, c_3)$ is the reference point, and $(k_1, k_2, k_3)$ are optional dimension-specific weighting factors [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Pre-processing is expensive, taking approximately 10x more GPU time than XBrickMap [S1, unofficial]. Traversal speedup is modest, reducing traversal length by only ~8% compared to space-partitioning methods [S1, unofficial].
*   **Memory Complexity:** 2 bytes per $4^3$ voxel for the distance field plus 1 bit per $1^3$ voxel for occupancy masks [S1, unofficial].
*   **Measured Performance:** In dense geometries (foliage), EDFs perform worse than space-partitioning methods [S1, unofficial]. Directional variants (OctantDF) can lower iterations by ~20-25% and increase throughput for incoherent rays by ~30-50%, but remain worse than space-partitioning methods overall [S1, unofficial].
*   **Strengths:** Reduces the number of ray steps in empty space; exact distance transforms avoid numerical errors [S1, unofficial].
*   **Limitations:** High memory bandwidth usage; significant pre-processing cost; limited traversal length reduction compared to spatial partitioning; poor performance on grazing rays in dense volumes [S1, unofficial].
*   **When to use:** When memory bandwidth is not the primary bottleneck and pre-processing time is acceptable; for volumes with large empty regions [S1, unofficial].
*   **When not to use:** For incoherent rays in dense, fine-geometry volumes where space-partitioning methods offer better performance; when memory bandwidth is severely constrained [S1, unofficial].

## Background
The tiled implementation with 1:4 resolution and occupancy masks was chosen to balance memory costs and traversal efficiency [S1, unofficial]. The concept of using spatial location as a diversifying attribute in transfer functions, including weighted Euclidean distances, was introduced in the context of Multi-Dimensional Transfer Function (MDTF) design for medical imaging [S2, unofficial].
