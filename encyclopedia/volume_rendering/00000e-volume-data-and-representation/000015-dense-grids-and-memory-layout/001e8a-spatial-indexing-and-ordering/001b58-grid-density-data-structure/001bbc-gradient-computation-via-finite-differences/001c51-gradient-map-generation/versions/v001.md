# Gradient Map Generation

Also called: Gradient Map Compute Shader

## Overview
Gradient Map Generation is a GPU compute shader pass that calculates the spatial gradient vector for every voxel in a 3D scalar volume and stores the result in a dedicated image buffer. It solves the problem of efficiently pre-computing surface normals and density changes required for lighting calculations, such as diffuse shading or light propagation, by offloading the finite difference operations from the CPU to the GPU. It differs from its siblings by focusing on the storage and formatting of the gradient data (direction and magnitude) in a texture format suitable for subsequent rendering passes, rather than just computing the values for immediate use or averaging them over regions.

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar volume texture (e.g., `GL_R8` or `GL_R16`) containing voxel intensities.
*   **Output:** A 3D image buffer (`gradient_map`) with layout `GL_RGBA8_SNORM`. This buffer stores the normalized gradient direction in the RGB channels and the gradient magnitude in the Alpha channel.

**Data Structures:**
The output `gradient_map` is a 3D image texture. Each voxel $(x, y, z)$ in the output corresponds to a voxel in the input volume.
*   `gradient_map[x, y, z].rgb`: Normalized gradient direction vector $\mathbf{n}$.
*   `gradient_map[x, y, z].a`: Gradient magnitude $|\nabla f|$, clamped to $[0, 1]$.

**Algorithm Steps:**
1.  **Dispatch:** The compute shader is dispatched with work groups covering the dimensions of the volume. Each invocation handles one voxel.
2.  **Gradient Computation:** For the current voxel at global invocation ID $(x, y, z)$, compute the gradient vector $\nabla f = (\frac{\partial f}{\partial x}, \frac{\partial f}{\partial y}, \frac{\partial f}{\partial z})$ using finite differences. The specific stencil (central, forward, backward) depends on boundary conditions and the implementation of `get_gradient`.
3.  **Magnitude Calculation:** Calculate the Euclidean norm of the gradient vector:
    $$ m = \|\nabla f\| = \sqrt{\left(\frac{\partial f}{\partial x}\right)^2 + \left(\frac{\partial f}{\partial y}\right)^2 + \left(\frac{\partial f}{\partial z}\right)^2} $$
    Apply a magnitude modifier $k$ (denoted as `grad_magnitude_modifier` in sources) and clamp the result to the range $[0, 1]$:
    $$ m_{final} = \text{clamp}(m \cdot k, 0.0, 1.0) $$
4.  **Normalization:** Normalize the gradient vector to obtain the direction:
    $$ \mathbf{n} = \frac{\nabla f}{\|\nabla f\|} $$
    *Edge Case:* If $\|\nabla f\| \approx 0$ (flat region), the direction is undefined. The implementation must handle this, typically by storing $(0,0,0)$ or a default normal.
5.  **Storage:** Write the results to the `gradient_map` image at $(x, y, z)$:
    *   `rgb` channel: $\mathbf{n}$ (converted to `snorm`8 format).
    *   `a` channel: $m_{final}$ (converted to `unorm`8 format).

**Pseudocode:**
```python
# Pseudocode for a single compute shader invocation
# Inputs: volume_texture (3D), gradient_map (3D image, RGBA8_SNORM)
# Uniforms: grad_magnitude_modifier (float), volume_dimensions (vec3)

def compute_gradient_map(x, y, z):
    # 1. Get gradient vector using finite differences
    # Note: Boundary conditions (Neumann/Dirichlet) must be handled in get_gradient
    grad_vec = get_gradient(volume_texture, x, y, z, volume_dimensions)
    
    # 2. Calculate magnitude
    magnitude = length(grad_vec)
    
    # Handle zero gradient to avoid division by zero
    if magnitude < 1e-6:
        normalized_dir = vec3(0.0, 0.0, 0.0)
        clamped_mag = 0.0
    else:
        # 3. Normalize direction
        normalized_dir = normalize(grad_vec)
        
        # 4. Apply modifier and clamp magnitude
        modified_mag = magnitude * grad_magnitude_modifier
        clamped_mag = clamp(modified_mag, 0.0, 1.0)
        
    # 5. Store in gradient map
    # RGB stores direction (snorm8), A stores magnitude (unorm8)
    gradient_map[x, y, z] = vec4(normalized_dir, clamped_mag)

# Main dispatch loop
# For each voxel (x, y, z) in volume_dimensions:
#     compute_gradient_map(x, y, z)
```

**Parameters:**
*   `grad_magnitude_modifier`: A scalar multiplier for the gradient magnitude. Typical values depend on the volume's dynamic range and the lighting model's sensitivity. Not given in the sources.
*   `volume_dimensions`: The width, height, and depth of the volume.

**Edge Cases and Pitfalls:**
*   **Boundaries:** Finite differences at the volume boundaries require special handling (e.g., clamping indices, using one-sided differences, or assuming zero gradient). The source `get_gradient` function must define this behavior [S1, unofficial].
*   **Zero Gradient:** Voxels with constant intensity have a zero gradient. Normalization fails. The implementation must check for this [G].
*   **Precision:** Using `RGBA8_SNORM` for direction limits normal precision. For higher precision, `RGBA16F` or `RGBA32F` can be used, but this increases memory bandwidth [S1, unofficial].

## Subtopics

### [Volume Gradient Computation and Light Propagation Compute Shader](3869-volume-gradient-computation-and-light-propagation-compute-sh.md)
This variant extends Gradient Map Generation by integrating light propagation logic directly into the gradient computation shader. It samples the 3D volume, computes spatial gradients using central differences, transforms these gradients between world and view spaces, and initiates a per-pixel light propagation pass across volume layers. It is chosen when view-space gradient transformation and layer-wise accumulation are required in a single pass to reduce memory traffic. It builds on [Gradient Map Generation](1204-gradient-map-generation.md) by combining gradient calculation with light propagation.

### Gradient Computation & Smoothing
This variant adds a post-processing step to the gradient map. After the initial gradient computation, a second compute shader applies a 3x3x3 box filter (averaging) to the computed gradient field. This is used to reduce noise in the gradient field, which is beneficial for lighting and shading stability. It is chosen when the input volume is noisy or low-resolution [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$, where $N$ is the number of voxels in the volume. Each voxel is processed once.
*   **Memory Complexity:** $O(N)$ for the output gradient map. The input volume is read-only.
*   **Performance:** Performance is limited by memory bandwidth, as each voxel requires reading from the volume texture and writing to the gradient map. Using `GL_R8` or `GL_R16` for input and `GL_RGBA8_SNORM` for output is efficient.
*   **Strengths:** Offloads gradient computation from CPU; enables parallel processing; produces a reusable texture for multiple lighting passes.
*   **Limitations:** Requires additional memory for the gradient map; boundary handling can introduce artifacts; magnitude scaling is arbitrary and may require tuning.
*   **When to use:** When gradients are needed for multiple rendering passes (e.g., diffuse lighting, light propagation) or when the volume is large and CPU computation is a bottleneck.
*   **When not to use:** When gradients are only needed for a single, simple lighting calculation and memory is constrained.

## Background
Gradient Map Generation is a standard technique in GPU-based volume rendering, often implemented as a compute shader pass. It is commonly used in conjunction with techniques like Partitioned Volume Raycasting (PVR) or Light Propagation Volumes (LPV) to provide surface normals for lighting. The method relies on finite difference approximations of the gradient, a fundamental concept in numerical analysis.
