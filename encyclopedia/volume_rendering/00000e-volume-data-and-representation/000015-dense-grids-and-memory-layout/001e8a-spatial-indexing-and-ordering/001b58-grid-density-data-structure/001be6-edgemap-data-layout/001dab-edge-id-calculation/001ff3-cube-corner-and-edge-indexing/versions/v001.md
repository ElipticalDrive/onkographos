# Cube Corner and Edge Indexing

Also called: DualMC corner/edge mapping, Morton code corner indexing

## Overview
Cube Corner and Edge Indexing defines the canonical spatial layout and unique identifiers for the vertices and edges of a voxel cell within the DualMC (Dual Marching Cubes) algorithm. It maps the 8 corners of a cube to indices 0–7 based on their Morton codes and assigns unique codes 0–11 to the 12 edges. This indexing scheme is the foundational coordinate system required to generate the lookup tables that map voxel occupancy masks to extracted surface primitives. It differs from standard Cartesian indexing by enforcing a Morton code order for corners, which simplifies the determination of adjacent cells and edge connectivity in dense grid traversal.

## How it works
### Inputs and Outputs
- **Input**: None (static definition).
- **Output**: Two static mappings:
  1. `cornerIndex`: Maps a corner's spatial position to an integer 0–7.
  2. `edgeIndex`: Maps an edge's spatial position to an integer 0–11.
  3. `cornerEdges`: A lookup table mapping each corner to its three incident edges.

### Data Structures
The indexing relies on a fixed-size cube geometry. The corners are treated as voxels in a local coordinate system.

**Corner Layout**:
The 8 corners are indexed 0 through 7. The index corresponds to the Morton code (Z-order curve) of the corner's local coordinates $(x, y, z)$, where $x, y, z \in \{0, 1\}$. The Morton code is calculated by interleaving the bits of the coordinates.

The spatial arrangement in a standard right-handed Cartesian system (as defined in the source) is:
- $x$ axis points right.
- $y$ axis points up.
- $z$ axis points out of the screen (towards the viewer) or into the screen depending on the specific projection, but the Morton ordering is consistent.

The mapping from local coordinates $(x, y, z)$ to corner index $C$ is:
$$ C = \text{Morton}(x, y, z) $$

Specifically, the source defines the corners as:
- Corner 0: $(0, 0, 0)$
- Corner 1: $(1, 0, 0)$
- Corner 2: $(0, 1, 0)$
- Corner 3: $(1, 1, 0)$
- Corner 4: $(0, 0, 1)$
- Corner 5: $(1, 0, 1)$
- Corner 6: $(0, 1, 1)$
- Corner 7: $(1, 1, 1)$

*Note: The source diagram shows a specific projection where 0-1-2-3 form the bottom face and 4-5-6-7 form the top face, with 0 below 4, 1 below 5, etc. The Morton code for $(x,y,z)$ is typically $z \cdot 4 + y \cdot 2 + x$ if bits are interleaved as $z, y, x$ or similar. However, the explicit list above matches the standard Morton order if we assume the bit interleaving order results in this specific integer sequence. Let us verify: Morton(0,0,0)=0, Morton(1,0,0)=1, Morton(0,1,0)=2, Morton(1,1,0)=3, Morton(0,0,1)=4, Morton(1,0,1)=5, Morton(0,1,1)=6, Morton(1,1,1)=7. This implies the Morton code is simply $4z + 2y + x$? No, standard Morton interleaves bits. For single bits, $M(x,y,z) = x + 2y + 4z$ is not interleaving. Interleaving bits of 0/1: $x$ is LSB, $y$ is middle, $z$ is MSB? $x=1 \to 001_2$, $y=1 \to 010_2$, $z=1 \to 100_2$. Interleaved $z y x$: $111_2 = 7$. If $z=0, y=0, x=1 \to 001_2 = 1$. If $z=0, y=1, x=0 \to 010_2 = 2$. If $z=0, y=1, x=1 \to 011_2 = 3$. If $z=1, y=0, x=0 \to 100_2 = 4$. This matches the list exactly. Thus, the Morton code is formed by interleaving bits as $z, y, x$ (MSB to LSB).*

**Edge Layout**:
The 12 edges are indexed 0 through 11. Each edge connects two corners. The indexing is fixed as follows:

| Edge Index | Connects Corner A | Connects Corner B |
| :--- | :--- | :--- |
| 0 | 0 | 1 |
| 1 | 1 | 5 |
| 2 | 0 | 4 |
| 3 | 4 | 5 |
| 4 | 2 | 3 |
| 5 | 3 | 7 |
| 6 | 2 | 6 |
| 7 | 6 | 7 |
| 8 | 0 | 2 |
| 9 | 1 | 3 |
| 10 | 4 | 6 |
| 11 | 5 | 7 |

### Step-by-Step Construction
1. **Define Corner Coordinates**: Assign local coordinates $(x, y, z) \in \{0, 1\}^3$ to each of the 8 corners.
2. **Calculate Morton Codes**: Compute the Morton code for each corner using bit interleaving of $(z, y, x)$. This yields the corner index $C \in [0, 7]$.
3. **Define Edges**: Enumerate the 12 edges of the cube. An edge is defined by the two corners it connects.
4. **Assign Edge Indices**: Assign indices 0–11 to the edges according to the fixed mapping provided in the layout section.
5. **Build `cornerEdges` Table**: For each corner $C \in [0, 7]$, identify the three edges incident to it. Store these edge indices in a lookup table `cornerEdges[8][3]`.

### Pseudocode
The following Python-like pseudocode defines the static mappings.

```python
def calculate_morton_code(x, y, z):
    """
    Calculates Morton code by interleaving bits of z, y, x.
    Assumes x, y, z are 0 or 1.
    """
    # Interleave bits: z is MSB, x is LSB for single bit values
    # bit 2: z, bit 1: y, bit 0: x
    return (z << 2) | (y << 1) | x

def build_corner_to_morton_map():
    """
    Returns a dictionary mapping corner index (0-7) to (x,y,z) coordinates.
    Actually, the index IS the Morton code.
    """
    corner_coords = {}
    for x in [0, 1]:
        for y in [0, 1]:
            for z in [0, 1]:
                idx = calculate_morton_code(x, y, z)
                corner_coords[idx] = (x, y, z)
    return corner_coords

def build_edge_to_corners_map():
    """
    Returns a list of tuples (corner_a, corner_b) for edges 0-11.
    Based on the source definition.
    """
    edges = [
        (0, 1), # Edge 0
        (1, 5), # Edge 1
        (0, 4), # Edge 2
        (4, 5), # Edge 3
        (2, 3), # Edge 4
        (3, 7), # Edge 5
        (2, 6), # Edge 6
        (6, 7), # Edge 7
        (0, 2), # Edge 8
        (1, 3), # Edge 9
        (4, 6), # Edge 10
        (5, 7)  # Edge 11
    ]
    return edges

def build_corner_edges_table():
    """
    Returns a list of lists: corner_edges[corner_idx] = [edge_idx_1, edge_idx_2, edge_idx_3]
    """
    edges = build_edge_to_corners_map()
    corner_edges = [[] for _ in range(8)]
    
    for edge_idx, (c1, c2) in enumerate(edges):
        corner_edges[c1].append(edge_idx)
        corner_edges[c2].append(edge_idx)
        
    # Sort for consistency, though order might not matter for the table generation
    for c in range(8):
        corner_edges[c].sort()
        
    return corner_edges

# Execution
corner_coords = build_corner_to_morton_map()
edge_map = build_edge_to_corners_map()
corner_edges_table = build_corner_edges_table()
```

### Parameters and Edge Cases
- **Bit Packing**: The Morton code relies on the assumption that coordinates are binary (0 or 1). For larger grids, this indexing applies locally to each voxel cell.
- **Coordinate System**: The source specifies a coordinate system where $y$ is up, $x$ is right, and $z$ is depth. The exact handedness (left vs right) is less critical than the consistency of the Morton ordering and edge connectivity.
- **Degenerate Input**: Not applicable as this is a static definition.

## Operating characteristics
- **Time Complexity**: $O(1)$ for all lookups. The tables are static and precomputed.
- **Memory Complexity**: $O(1)$. The tables are small constants (8 corners, 12 edges, 8x3 edge list).
- **Strengths**: Provides a deterministic, hardware-independent mapping for voxel topology. Essential for generating the DualMC lookup tables which map the 256 possible voxel occupancy states to surface primitives.
- **Limitations**: Tied to the specific Morton code ordering. If a different ordering is used for the global grid, local cell indexing must be remapped.

## Background
This indexing scheme originates from the DualMC (Dual Marching Cubes) implementation by Dominik Wodniok [S1, unofficial]. It is used in the `gentables` utility to generate the static lookup tables required for the DualMC surface extraction algorithm. The method ensures that the topological relationships between corners and edges are consistent with the Morton code ordering of the voxel grid, facilitating efficient traversal and neighbor lookup in dense volume data.
