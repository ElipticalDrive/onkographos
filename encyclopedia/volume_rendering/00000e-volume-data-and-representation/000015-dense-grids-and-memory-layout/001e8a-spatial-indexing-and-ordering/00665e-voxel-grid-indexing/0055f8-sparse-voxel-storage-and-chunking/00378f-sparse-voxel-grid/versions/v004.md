# Sparse Voxel Grid

Also called: Sparse Voxel List, Coordinate List Storage

## Overview
A sparse voxel grid is a volume representation that stores only non-zero or active voxel data as a list of coordinates and their corresponding values, discarding empty space to reduce memory usage [S1, unofficial]. It solves the problem of inefficient memory allocation in dense grids where large portions of the volume are empty or uniform [S1, unofficial]. Unlike its siblings, it relies on a flat list structure requiring explicit search mechanisms (iteration, trees, or hash tables) for data retrieval, rather than hierarchical spatial indexing or chunked memory layouts [S1, unofficial].

## How it works
**Inputs:** A set of active voxel coordinates $(x, y, z)$ and their associated data values (e.g., density, color, SDF).
**Outputs:** A data structure containing the list of active voxels and a query mechanism to retrieve values for arbitrary 3D points.

**Data Structures:**
The core structure is a list (or array) of entries. Each entry contains:
1.  **Coordinate:** A 3D integer tuple $(x, y, z)$.
2.  **Data:** The voxel's attribute value(s).

**Querying Mechanism:**
To retrieve the value at a target coordinate, the system must search the list. Two primary methods are cited:
1.  **Linear Search:** Iterating through all elements in the list to find a matching coordinate [S1, unofficial].
2.  **Accelerated Search:** Using an auxiliary data structure such as a tree (e.g., KD-tree variant) or a hash table to accelerate lookup [S1, unofficial].

**Pitfalls:**
*   **Query Performance:** Without acceleration, querying requires iterating all elements, which is $O(N)$ where $N$ is the number of active voxels [S1, unofficial].
*   **Sparsity vs. Overhead:** While it saves memory compared to dense grids, the overhead of maintaining search structures (trees/hash tables) must be weighed against the savings [S1, unofficial].

## Subtopics

### Sparse Volume Data Storage
A storage strategy for volumetric terrain rendering that keeps sampled volume data in separate cells, discarding Signed Distance Fields (SDFs) after Hermite data construction to allow parallel modifications and extractions [S2]. It is chosen when dynamic terrain modification and surface extraction performance are critical [S2].
*   **Layout:** Material indices are stored in a 1D typed array of `uint8` [S2]. Edge data (edges, zero crossings, normals) is stored in typed arrays simulating a hash map, split into three groups (edges, zero crossings, normals), each further split into X, Y, Z axis arrays [S2]. Edges are stored as starting grid point indices in ascending order [S2].
*   **Formulas:**
    *   Flattened index for grid point $(x, y, z)$ with resolution $n$: $index = z \times (n+1)^2 + y \times (n+1) + x$ [S2].
    *   Ending point index $b$ for starting point $a$:
        *   X-axis: $b = a + 1$ [S2].
        *   Y-axis: $b = a + (n+1)$ [S2].
        *   Z-axis: $b = a + (n+1)^2$ [S2].
*   **Parameters:** Grid resolution $n$ is an integer from 1 to 256 [S2].

### Weight-sharing Voxel Representation
A voxel representation where weights are shared across different spatial scales to reduce memory usage and enhance performance [S3]. It is chosen when multi-scale representation is needed but memory is constrained, as it reduces model size compared to maintaining independent voxels for each scale [S3].

## Operating characteristics
*   **Time Complexity:** Querying is $O(N)$ for linear search, where $N$ is the number of active voxels [S1, unofficial]. With hash tables or trees, it can be improved to $O(\log N)$ or $O(1)$ on average, though specific constants are not given [S1, unofficial].
*   **Memory Complexity:** Proportional to the number of active voxels, significantly less than dense grids for sparse volumes [S1, unofficial].
*   **Strengths:** Simple data structure; efficient memory usage for highly sparse data [S1, unofficial].
*   **Limitations:** Slow querying without auxiliary structures; no inherent spatial locality optimization in the base list form [S1, unofficial].
*   **When to use:** When sparsity is high and query patterns are not the primary bottleneck, or when combined with efficient search structures [S1, unofficial].
*   **When not to use:** When frequent random access is required without the overhead of maintaining search structures [S1, unofficial].

## Background
The concept of sparse voxel grids as a list of coordinates and data is discussed in the context of accelerating Neural Radiance Fields (NeRF) inference by harnessing spatial sparsity [S1, unofficial]. The term "Sparse Voxel Grid" is used to distinguish this list-based approach from hierarchical structures like Octrees, which are also mentioned as variants for accelerating search [S1, unofficial]. The specific formulas and detailed layout for "Sparse Volume Data Storage" originate from work on volumetric terrain rendering with WebGL [S2]. The "Weight-sharing Voxel Representation" is introduced in the context of FrugalNeRF for few-shot novel view synthesis [S3].
