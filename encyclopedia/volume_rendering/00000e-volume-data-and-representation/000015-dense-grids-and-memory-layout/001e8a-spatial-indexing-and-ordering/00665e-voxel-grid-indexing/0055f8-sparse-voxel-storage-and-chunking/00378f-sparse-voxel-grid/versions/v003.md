# Sparse Voxel Grid

Also called: Sparse Voxel List, Coordinate List (COO) for Volumes

## Overview
A sparse voxel grid is a volume representation that stores only non-zero or active voxels as a list of coordinates and their corresponding attribute data, discarding empty space to reduce memory footprint [S1, unofficial]. It differs from its siblings by using a flat list structure rather than hierarchical trees or fixed-size chunks; while [S1, unofficial] notes this requires accelerated search structures (trees or hash tables) for efficient querying, it serves as the foundational sparse representation upon which more complex indexing schemes are built.

## How it works
**Inputs and Outputs:**
- Input: A set of active voxel attributes (e.g., color, density, SDF value) and their 3D integer coordinates $(x, y, z)$.
- Output: A sparse data structure containing the list of active voxels.

**Data Structures:**
The core data structure is a list of tuples:
$$ [(x_1, y_1, z_1, d_1), (x_2, y_2, z_2, d_2), \dots, (x_N, y_N, z_N, d_N)] $$
where $N$ is the number of active voxels, $(x_i, y_i, z_i)$ are the integer grid coordinates, and $d_i$ is the attribute data [S1, unofficial].

**Querying and Acceleration:**
Direct iteration over the list is inefficient for large $N$. To support efficient lookups, the list is indexed by accelerated data structures [S1, unofficial]:
1.  **Hash Tables:** Map coordinates to data indices for $O(1)$ average-case access.
2.  **Trees:**
    *   **KD-Tree:** A binary tree variant for spatial search [S1, unofficial].
    *   **Octree:** A tree where each node divides space into 8 octants (leaves), recursively subdividing 3D space [S1, unofficial].

**Algorithm for List-Based Query (Naive):**
1.  Iterate through each tuple $(x_i, y_i, z_i, d_i)$ in the list.
2.  Check if $(x_i, y_i, z_i)$ matches the query coordinate $(x_q, y_q, z_q)$.
3.  If a match is found, return $d_i$.
4.  If the end of the list is reached without a match, return null/empty [S1, unofficial].

**Pitfalls:**
- Querying without acceleration requires $O(N)$ time complexity, which is prohibitive for high-resolution scenes [S1, unofficial].
- The representation inherently handles empty space by omission, but queries must correctly identify the absence of data (i.e., no hit in the accelerated structure) [S1, unofficial].

## Subtopics

### Sparse Volume Data Storage
A storage strategy that keeps sampled volume data in separate cells, discarding Signed Distance Fields (SDFs) after Hermite data construction to allow parallel modifications, extractions, and culling of distant portions [S2]. It uses typed arrays to simulate hash maps for edge data, enabling zero-copy communication with Web Workers [S2].
- **Layout:** Material indices are stored in a 1D `uint8` array. Edge data (edges, zero crossings, normals) is stored in typed arrays split into three groups (X, Y, Z axes). Edges are stored as starting grid point indices in ascending order [S2].
- **Formulas:** For grid resolution $n$ and coordinates $(x, y, z)$, the flattened index is:
  $$ \text{index} = z \times (n+1)^2 + y \times (n+1) + x $$
  The ending point index $b$ for a starting point $a$ is:
  - X-axis: $b = a + 1$
  - Y-axis: $b = a + (n+1)$
  - Z-axis: $b = a + (n+1)^2$ [S2]
- **Parameters:** Grid resolution $n$ is an integer from 1 to 256 [S2].

### Weight-sharing Voxel Representation
A voxel representation where weights are shared across different spatial scales to reduce memory usage and enhance performance, compared to maintaining independent voxels for each scale [S3]. It enables multi-scale representation (e.g., $L=2$ scales in FrugalNeRF) to balance quality and training time [S3].

## Operating characteristics
- **Time Complexity:** Naive list search is $O(N)$ [S1, unofficial]. With acceleration (hash table or octree), lookup approaches $O(1)$ or $O(\log N)$ depending on the structure [S1, unofficial].
- **Memory Complexity:** Proportional to the number of active voxels $N$, not the bounding box volume. Significantly more memory-efficient than dense grids for sparse scenes [S1, unofficial].
- **Strengths:** Efficient storage for sparse data; supports high resolution without proportional memory cost [S1, unofficial].
- **Limitations:** Requires additional data structures for acceleration; random access is slower than dense arrays without indexing [S1, unofficial].

## Background
The concept of sparse voxel grids emerged as a solution to the memory constraints of dense voxel grids in 3D rendering and neural radiance fields (NeRF). Chris Choy popularized the term in the context of accelerating NeRF inference by storing only non-zero elements [S1, unofficial]. The approach is fundamental to methods like Neural Sparse Voxel Fields, which use progressive octree refinement to learn sparse voxel grids [S1, unofficial].
