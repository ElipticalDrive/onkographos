# Sparse Voxel Grid

Also called: Sparse Voxel List, Coordinate List Grid

## Overview
A sparse voxel grid is a volume representation that stores only non-zero (active) elements as a list of coordinates and their corresponding data, discarding empty space [S1, unofficial]. It solves the memory inefficiency of dense grids by leveraging spatial sparsity, allowing for higher resolution sampling without proportional memory costs [S1, unofficial]. Unlike its sibling [Sparse Voxel Chunk Indexing](8606-sparse-voxel-chunk-indexing.md) which uses hierarchical chunking, the basic sparse voxel grid typically relies on flat lists or hash-based acceleration structures for storage [S1, unofficial].

## How it works
**Inputs:** A set of active voxel coordinates $\mathbf{i} = (x, y, z)$ and their associated data values $\mathbf{d}$.
**Outputs:** A data structure enabling lookup of $\mathbf{d}$ given $\mathbf{i}$, or iteration over all active voxels.

**Data Structures:**
The core storage is a list of tuples $(x, y, z, \text{data})$ [S1, unofficial]. To accelerate queries, this list is indexed by an accelerated data structure, specifically a tree (such as a KD-tree variant) or a hash table [S1, unofficial].

**Steps:**
1.  **Storage:** Store only active voxels. For each active voxel at integer coordinates $(x, y, z)$, store the coordinate triplet and the associated data value (e.g., density, color, SDF) [S1, unofficial].
2.  **Indexing (Query Acceleration):**
    *   **Hash Table:** Map the coordinate triplet $(x, y, z)$ to a hash value to retrieve the data in $O(1)$ average time [S1, unofficial].
    *   **Tree (KD-tree/Octree):** Organize the coordinates into a spatial tree structure. If dividing all 3 dimensions into 8 leaves per node, the structure becomes an octree [S1, unofficial].
3.  **Lookup:** To find the data for a target coordinate:
    *   If using a list without acceleration, iterate through all elements to check for a coordinate match [S1, unofficial].
    *   If using a hash table, compute the hash of the target coordinate and retrieve the value [S1, unofficial].
    *   If using a tree, traverse the tree to locate the leaf node containing the coordinate [S1, unofficial].

**Parameters:**
*   **Resolution:** Not explicitly bounded in the general definition, but determined by the range of integer coordinates stored [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Query Performance:** Naive iteration over the list of coordinates is slow ($O(N)$) and should be avoided for large datasets [S1, unofficial].
*   **Sparsity Assumption:** The method assumes significant empty space; if the volume is dense, the overhead of the acceleration structure may outweigh the memory savings [S1, unofficial].

## Subtopics

### Sparse Volume Data Storage
A storage strategy for volumetric terrain rendering that keeps sampled volume data in separate cells, discarding Signed Distance Fields (SDFs) after Hermite data construction to allow parallel modifications and extractions [S2]. It distinguishes itself by storing edge data sparsely using typed arrays that simulate hash maps, rather than standard JavaScript hash maps which are inefficient for Web Workers [S2].
*   **Layout:** Material indices are stored in a one-dimensional typed array of 8-bit unsigned integers (`uint8`) [S2]. Edge data (edges, Zero Crossings, normals) is stored in typed arrays split into three groups, each further split into three arrays for X, Y, and Z axes [S2]. Edges are stored as starting grid point indices in ascending order [S2].
*   **Formulas:**
    *   Flattened index for grid point $(x, y, z)$ with resolution $n$:
        $$ \text{index} = z \times (n+1)^2 + y \times (n+1) + x $$
    *   Ending point index $b$ for starting point index $a$:
        *   X-axis: $b = a + 1$
        *   Y-axis: $b = a + (n+1)$
        *   Z-axis: $b = a + (n+1)^2$
*   **Parameters:** Grid resolution $n$ is an integer from 1 to 256 [S2].

### Weight-sharing Voxel Representation
A voxel representation used in multi-scale NeRF variants (e.g., FrugalNeRF) where weights are shared across different spatial scales to reduce memory usage and enhance performance [S3]. It is chosen when balancing quality and training time in few-shot novel view synthesis, as it reduces model size compared to maintaining independent voxels for each scale [S3].

## Operating characteristics
*   **Time Complexity:** Lookup is $O(1)$ with a hash table or $O(\log N)$ with a tree structure, compared to $O(N)$ for a naive list search [S1, unofficial].
*   **Memory Complexity:** Proportional to the number of active voxels, not the bounding box volume [S1, unofficial].
*   **Strengths:** Efficiently handles large volumes with significant empty space; supports high resolution without excessive memory consumption [S1, unofficial].
*   **Limitations:** Querying requires an acceleration structure; naive iteration is prohibitively slow for large datasets [S1, unofficial].
*   **When to use:** When the volume is sparse and random access to voxel data is required [S1, unofficial].
*   **When not to use:** When the volume is dense, or when hierarchical adjacency information is required (in which case an octree or chunked grid is preferred) [S1, unofficial].

## Background
The concept of sparse voxel grids is fundamental to efficient 3D representation, particularly in the context of Neural Radiance Fields (NeRF) and terrain rendering. Chris Choy's work on Faster Neural Radiance Fields Inference highlights the use of sparse voxel grids and octrees to increase resolution by harnessing spatial sparsity [S1, unofficial]. In terrain rendering, Sparse Volume Data Storage was developed to handle dynamic modifications and parallel surface extractions efficiently using WebGL and typed arrays [S2]. Weight-sharing voxel representations were introduced in FrugalNeRF to enable fast convergence in few-shot novel view synthesis by sharing weights across scales [S3].
