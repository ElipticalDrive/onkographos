# Sparse Voxel Chunk Indexing

Also called: Bitmask Chunk Indexing, Chunk-based Voxel Indexing

## Overview
Sparse Voxel Chunk Indexing is a memory-efficient storage scheme for sparse 3D voxel grids that organizes active voxels into fixed-size $8 \times 8 \times 8$ chunks, each accompanied by a 512-bit bitmask indicating occupancy [S1, unofficial]. It solves the problem of excessive memory overhead in dense grids and the pointer-chasing latency of deep trees by providing $O(1)$ access to chunk topology and linear storage for values [S1, unofficial]. Unlike [Sparse Voxel Grid](8021-sparse-voxel-grid.md) which may use hash maps or larger tree nodes, and [OpenVDB Volume Grid Storage](14574-openvdb-volume-grid-storage.md) which uses a multi-resolution octree, this method relies on shallow, fixed-depth chunking with bit-level precision [S1, unofficial].

## How it works
**Inputs:** A set of active voxel coordinates $(x, y, z)$ and their associated scalar/vector values.
**Outputs:** A linear buffer of voxel values and a list of Chunk structures containing bitmasks and metadata.

**Data Structures:**
1.  **Chunk:** A struct representing an $8 \times 8 \times 8$ block of voxels.
    *   `bitMask[16]`: An array of 16 unsigned integers (64-bit or 32-bit depending on implementation, but logically 512 bits total). Each bit corresponds to a voxel in the chunk. The mapping from 3D coordinate $(x, y, z)$ within the chunk to a bit index is typically $x + 8y + 64z$ or a similar linearization [S1, unofficial].
    *   `partialCounts[3]`: An array of 3 cumulative voxel counts. These store the number of active voxels at the 1/4, 1/2, and 3/4 points of the chunk's linearized bit order to accelerate rank queries (finding the $k$-th active voxel) [S1, unofficial].
    *   `voxelIndex`: An integer offset pointing to the start of this chunk's active values in the global linear voxel buffer [S1, unofficial].
2.  **IndexGrid / Chunk List:** A contiguous array of `Chunk` handles or structures, ordered spatially or by creation time [S1, unofficial].
3.  **Voxel Buffer:** A linear array storing only the values of active voxels, ordered by their appearance in the chunk bitmasks [S1, unofficial].

**Algorithm: Mapping Map Index to Voxel Index**
To find the global linear index of the $k$-th active voxel in the entire grid (where $k$ is the "map index"):
1.  Determine which chunk contains the $k$-th voxel. This is often done via a binary search or direct lookup if chunks are uniform, but the source describes a specific traversal using `partialCounts` [S1, unofficial].
2.  Let `mapIndex` be the index of the chunk in the chunk list.
3.  Calculate the local rank `localIndex` of the voxel within that chunk: `localIndex = k - map[mapIndex].voxelIndex` [S1, unofficial].
4.  Determine the `bitMaskIndex` by shifting `localIndex` right by 5 (dividing by 32): `bitMaskIndex = localIndex >> 5` [S1, unofficial].
5.  Initialize `voxNum` (the count of active voxels in previous masks) using `partialCounts` if `bitMaskIndex > 3`. Specifically, `voxNum` is initialized to the cumulative count stored at the highest relevant partial count entry [S1, unofficial].
6.  Loop from `startMask = bitMaskIndex & ~3` to `bitMaskIndex`. For each mask index `i` in this range:
    *   If `i` is the final index (`i == bitMaskIndex`), mask out bits at and after the target voxel using `(1 << (localIndex & 31)) - 1`.
    *   Add the population count (bit count) of the masked value to `voxNum` [S1, unofficial].
7.  Return `map[mapIndex].voxelIndex + voxNum` as the global linear index in the voxel buffer [S1, unofficial].

**Algorithm: Mapping Chunk Index and Voxel Number to 3D Position**
To find the 3D coordinate $(x, y, z)$ of the $n$-th active voxel in a specific chunk:
1.  Initialize `count = 0`, `pos = 0`, `startIndex = 0` [S1, unofficial].
2.  Loop `i` from 0 to 2:
    *   If `chunks[chunk].partialCounts[i] < voxNum`:
        *   Set `count` to `chunks[chunk].partialCounts[i]`.
        *   Add 128 to `pos`.
        *   Add 4 to `startIndex`.
    *   Else: break [S1, unofficial].
3.  Increment `voxNum` by `count` (effectively adjusting `voxNum` to be relative to the start of the current 1/4 segment) [S1, unofficial].
4.  Loop `i` from `startIndex` to 15:
    *   If `count == voxNum`, break [S1, unofficial].
    *   Get `bitCount` of `bitMask[i]` [S1, unofficial].
    *   If `count + bitCount >= voxNum`:
        *   Step bit-by-bit:
        *   Loop `bitNum` from 0:
            *   Add `(bitMask[i] >> bitNum) & 1` to `count`.
            *   Increment `bitNum` and `pos` until `count == voxNum` [S1, unofficial].
    *   Else:
        *   Add `bitCount` to `count`.
        *   Add 32 to `pos` [S1, unofficial].
5.  Decrement `pos` by 1 [S1, unofficial].
6.  If `count < voxNum`, return `(-1, -1, -1)` (error) [S1, unofficial].
7.  Else, return `ivec3(pos % 8, (pos / 8) % 8, pos / 64)` [S1, unofficial].

**Pitfalls:**
*   **Total Internal Reflection (TIR):** In ray marching through refractive media, TIR can cause `rayDir` to become zero or invalid, leading to infinite loops. The implementation must check if `rayDir == vec3(0.0)` after refraction calculation and revert to `oldRayDir` if so [S1, unofficial].
*   **Precision:** Bitwise operations on large indices may overflow if not using 64-bit integers for `voxNum` or `pos` in very large grids [G].
*   **Boundary Conditions:** The `partialCounts` array only covers 3 points for 16 masks. The logic assumes a specific distribution of bits. If the bitmask distribution is highly irregular, the optimization may fail or require fallback [S1, unofficial].

## Subtopics

### [GPU Accelerated Sparse Grid Construction](9812-gpu-accelerated-sparse-grid-construction.md)
This method constructs the **IndexGrid** acceleration structure on the GPU from a set of signed voxel coordinates, enabling the handling of large-scale inputs with a competitive memory footprint. Unlike standard NanoVDB which assumes a fixed topology, this algorithm supports dynamic sparsity patterns, such as those required for Level-of-Detail (LOD) hierarchies. It builds on [Sparse Voxel Chunk Indexing](8606-sparse-voxel-chunk-indexing.md) and implements the core construction logic for the [IndexGrid](9819-indexgrid.md) data structure.

### [IndexGrid](9819-indexgrid.md)
IndexGrid is a sparse data structure derived from NanoVDB, designed to aggressively accelerate stencil-centric operations (e.g., convolution) while serving as an effective acceleration structure for ray marching and other spatial operations. It solves the problem of memory inefficiency and code complexity in standard VDB implementations by separating topology (sparsity pattern) from values (features). Unlike hash tables, which lack spatial coherence, or octrees, which suffer from $O(\log n)$ access times, IndexGrid uses a fixed-depth shallow tree to maintain $O(1)$ amortized access while preserving spatial coherence.

### Slice-Based Binary Shell (SBS) Conversion
**Definition:** Converts a dense 3D volume into a sparse Slice-Based Binary Shell structure containing only non-empty voxels, organized by slice with cumulative offsets for fast GPU traversal [S2, unofficial].

**Steps:**
1.  Initialize `current_offset = 0` and iterate over each z-slice [S2, unofficial].
2.  For each slice, find non-empty voxel coordinates where `slice_data > 0` [S2, unofficial].
3.  Stack 2D indices into `[y, x]` format and append to `index_array` [S2, unofficial].
4.  Extract corresponding voxel values and append to `attribute_list` [S2, unofficial].
5.  Update `slice_offsets[z] = current_offset` and increment `current_offset += len(indices)` [S2, unofficial].
6.  Convert lists to numpy arrays: `index_array` to int32, `attribute_list` to uint8 [S2, unofficial].

**Layout:**
Dictionary `sbs_data` with three fields: `index_array` (N×2 int32, stores [y, x] coordinates), `attribute_list` (N uint8, stores voxel values), `slice_offsets` (Z int32, stores cumulative start index per z-slice) [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Access to a voxel's value is $O(1)$ amortized if the chunk is known. Finding the chunk from a global rank or coordinate requires $O(\log C)$ or $O(1)$ depending on the index structure (e.g., binary search over chunks or direct mapping) [S1, unofficial]. Rank queries (finding the $k$-th active voxel) are accelerated by `partialCounts` to near $O(1)$ for the chunk level, with bit-counting being $O(1)$ on modern hardware [S1, unofficial].
*   **Memory Complexity:** Storage is proportional to the number of active voxels plus the overhead of the bitmasks (1 bit per potential voxel in the chunk, so 1/8 byte per voxel) and chunk metadata [S1, unofficial]. This is significantly more compact than hash-based sparse grids for moderately dense regions.
*   **Performance:** Measured performance depends heavily on the sparsity pattern. For highly sparse data, it outperforms dense grids. For very sparse data with large holes, it may still allocate full chunks if the chunking granularity is coarse [S1, unofficial].
*   **Strengths:** Cache-friendly linear storage of values; simple bitwise operations for topology; no pointer chasing [S1, unofficial].
*   **Limitations:** Fixed chunk size ($8^3$) may lead to fragmentation if active voxels are clustered in smaller regions; bit-counting can be slower than direct indexing if not optimized [S1, unofficial].

## Background
Sparse Voxel Chunk Indexing is a core component of the NanoVDB and OpenVDB libraries, developed by DreamWorks Animation and later open-sourced [S1, unofficial]. It was designed to handle the massive datasets generated in visual effects (VFX) and scientific visualization, where memory efficiency and fast access are critical [S1, unofficial]. The method evolved from earlier sparse voxel octree representations to provide a more regular and GPU-friendly memory layout [S1, unofficial].
