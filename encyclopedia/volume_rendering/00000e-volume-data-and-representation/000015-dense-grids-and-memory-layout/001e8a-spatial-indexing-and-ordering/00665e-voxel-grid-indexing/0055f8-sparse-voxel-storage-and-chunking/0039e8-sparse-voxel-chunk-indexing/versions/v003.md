# Sparse Voxel Chunk Indexing

Also called: Bitmask Chunk Indexing, Chunk-based Voxel Indexing

## Overview
Sparse Voxel Chunk Indexing maps logical 3D voxel coordinates $(x, y, z)$ to a linear buffer of attribute data by organizing active voxels into fixed-size $8 \times 8 \times 8$ chunks, each represented by a 512-bit bitmask. It solves the lookup latency of flat sparse lists by using bit-counting over chunk masks to compute offsets in $O(1)$ amortized time, avoiding the traversal overhead of tree-based structures like [Octrees](link) or the hash collisions of [Hash Tables](link). It is distinct from [Sparse Voxel Grid](8021-sparse-voxel-grid.md) which may use larger or variable blocks, and [OpenVDB Volume Grid Storage](14574-openvdb-volume-grid-storage.md) which uses a multi-resolution tree structure; this method relies on a flat array of chunk descriptors with embedded bitmasks [S1, unofficial].

## How it works
**Inputs:** A set of active voxel coordinates $\{(x_i, y_i, z_i)\}$ and their associated attribute data $d_i$.
**Outputs:** A linear `voxel_buffer` containing attributes $d_i$, and an `IndexGrid` (or chunk array) mapping chunk indices to voxel offsets.

**Data Structures:**
1.  **Chunk Struct:**
    *   `bitMask[16]`: Array of 16 `uint32_t` values (64 bytes total). Represents the occupancy of an $8 \times 8 \times 8$ chunk (512 bits). Bit $k$ is 1 if the voxel at local index $k$ is active, 0 otherwise.
    *   `partialCounts[3]`: Array of 3 `uint32_t` values. Stores cumulative voxel counts within the chunk at specific bit positions to accelerate bit counting. Specifically, these correspond to cumulative counts at the 1/4, 1/2, and 3/4 points of the chunk's bit range [S1, unofficial].
    *   `voxelIndex`: A `uint32_t` offset pointing to the start of this chunk's voxels in the global `voxel_buffer`.
2.  **Chunk Handle/Map:** A list or hash map of `Chunk` structs, indexed by a global chunk ID.
3.  **Voxel Buffer:** A contiguous array of attribute data.

**Coordinate Mapping:**
Voxels are linearized within a chunk using local index $k = x + 8y + 64z$, where $0 \le k < 512$. The global voxel index is derived from the chunk's `voxelIndex` plus the bit count of active voxels preceding $k$ in `bitMask`.

**Algorithm: Lookup Voxel Index from Chunk and Local Index**
Given a `mapIndex` (index into the chunk array), a `chunk` descriptor, and a `localIndex` ($0 \le localIndex < 512$):

1.  Calculate `bitMaskIndex` = `localIndex` >> 5 (integer division by 32). This identifies which of the 16 `uint32_t` words in `bitMask` contains the target bit.
2.  Initialize `voxNum` = 0.
3.  If `bitMaskIndex` > 3, add `chunk.partialCounts[bitMaskIndex - 4]` to `voxNum` [S1, unofficial]. *Note: The source logic implies `partialCounts` are used for offsets greater than the first 4 words, likely mapping indices 4-7, 8-11, 12-15 to the 3 partial counts.*
4.  Loop `i` from `bitMaskIndex & ~3` (start of the 4-word block containing `bitMaskIndex`) to `bitMaskIndex - 1`:
    *   Add `popcount(chunk.bitMask[i])` to `voxNum`.
5.  Handle the final word `chunk.bitMask[bitMaskIndex]`:
    *   Create a mask `m = (1 << (localIndex & 31)) - 1`. This mask has 1s for all bit positions strictly less than `localIndex` within the 32-bit word.
    *   Add `popcount(chunk.bitMask[bitMaskIndex] & m)` to `voxNum`.
6.  Return `map[mapIndex].voxelIndex + voxNum`.

**Algorithm: Lookup Chunk Position from Chunk Index and Voxel Number**
Given a `chunk` descriptor and a target `voxNum` (0-based index of the voxel within the chunk's active voxels):

1.  Initialize `count = 0`, `pos = 0`, `startIndex = 0`.
2.  Loop `i` from 0 to 2:
    *   If `chunk.partialCounts[i] < voxNum`:
        *   `count = chunk.partialCounts[i]`
        *   `pos += 128` (Skip 4 words * 32 bits)
        *   `startIndex += 4`
        *   Continue to next iteration.
    *   Else:
        *   Break loop.
3.  Increment `voxNum` by 1 (adjusting for 0-based vs 1-based counting logic in source) [S1, unofficial].
4.  Loop `i` from `startIndex` to 15:
    *   If `count == voxNum`, break.
    *   Get `bitCount = popcount(chunk.bitMask[i])`.
    *   If `count + bitCount >= voxNum`:
        *   Iterate bit-by-bit within `chunk.bitMask[i]`:
            *   Initialize `bitNum = 0`.
            *   While `count < voxNum`:
                *   If `(chunk.bitMask[i] >> bitNum) & 1`:
                    *   `count += 1`
                *   `bitNum += 1`
                *   `pos += 1`
            *   Break inner loop.
    *   Else:
        *   `count += bitCount`
        *   `pos += 32`
5.  Decrement `pos` by 1 [S1, unofficial].
6.  If `count < voxNum`, return `(-1, -1, -1)` (error/not found).
7.  Else, return `ivec3(pos % 8, (pos / 8) % 8, pos / 64)` [S1, unofficial].

**Pitfalls:**
*   **Total Internal Reflection (TIR):** In refraction-based rendering using this structure, TIR can cause infinite loops if the ray direction becomes zero or invalid. Check if `rayDir == vec3(0.0)` after refraction calculation; if so, revert to `oldRayDir` [S1, unofficial].
*   **Bitmask Precision:** Ensure `uint32_t` operations are used for bitmasks to avoid overflow in `popcount` or shift operations.
*   **Boundary Conditions:** The `partialCounts` logic assumes a specific mapping of indices to counts. If the chunk has fewer than 512 voxels, the bitmask correctly reflects 0s, but `partialCounts` must be precomputed accurately during chunk construction.

## Subtopics

### [GPU Accelerated Sparse Grid Construction](9812-gpu-accelerated-sparse-grid-construction.md)
This method constructs the **IndexGrid** acceleration structure on the GPU from a set of signed voxel coordinates, enabling the handling of large-scale inputs with a competitive memory footprint. Unlike standard NanoVDB which assumes a fixed topology, this algorithm supports dynamic sparsity patterns, such as those required for Level-of-Detail (LOD) hierarchies. It builds on [Sparse Voxel Chunk Indexing](8606-sparse-voxel-chunk-indexing.md) and implements the core construction logic for the [IndexGrid](9819-indexgrid.md) data structure.

### [IndexGrid](9819-indexgrid.md)
IndexGrid is a sparse data structure derived from NanoVDB, designed to aggressively accelerate stencil-centric operations (e.g., convolution) while serving as an effective acceleration structure for ray marching and other spatial operations. It solves the problem of memory inefficiency and code complexity in standard VDB implementations by separating topology (sparsity pattern) from values (features). Unlike hash tables, which lack spatial coherence, or octrees, which suffer from $O(\log n)$ access times, IndexGrid uses a fixed-depth shallow tree to maintain $O(1)$ amortized access while preserving spatial coherence.

#### Slice-Based Binary Shell (SBS) Conversion
**Definition:** Converts a dense 3D volume into a sparse Slice-Based Binary Shell structure containing only non-empty voxels, organized by slice with cumulative offsets for fast GPU traversal [S2, unofficial].
**Steps:**
1.  Initialize `current_offset = 0` and iterate over each z-slice [S2, unofficial].
2.  For each slice, find non-empty voxel coordinates where `slice_data > 0` [S2, unofficial].
3.  Stack 2D indices into `[y, x]` format and append to `index_array` [S2, unofficial].
4.  Extract corresponding voxel values and append to `attribute_list` [S2, unofficial].
5.  Update `slice_offsets[z] = current_offset` and increment `current_offset += len(indices)` [S2, unofficial].
6.  Convert lists to numpy arrays: `index_array` to int32, `attribute_list` to uint8 [S2, unofficial].
**Layout:** Dictionary `sbs_data` with three fields: `index_array` (N×2 int32, stores [y, x] coordinates), `attribute_list` (N uint8, stores voxel values), `slice_offsets` (Z int32, stores cumulative start index per z-slice) [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Lookup is $O(1)$ amortized for both coordinate-to-index and index-to-coordinate mappings, dominated by bit counting operations (`popcount`) which are typically hardware-accelerated. Construction is $O(N)$ where $N$ is the number of active voxels.
*   **Memory Complexity:** Each chunk consumes 64 bytes (bitmask) + 12 bytes (partial counts) + 4 bytes (voxel index) = 80 bytes, plus the attribute data. This is more memory-efficient than octrees for moderately dense chunks but less efficient than hash tables for extremely sparse data.
*   **Performance:** Competitive memory footprint on GPU [S1, unofficial]. Suitable for large-scale inputs with dynamic sparsity [S1, unofficial].
*   **Strengths:** Fast stencil operations, spatial coherence, no tree traversal overhead.
*   **Limitations:** Fixed chunk size ($8^3$) may lead to fragmentation if sparsity is highly irregular. Bitmask operations can be costly on older hardware without `popcount` instructions.
*   **When to Use:** When spatial coherence is important and chunk density is relatively uniform. Ideal for GPU-based rendering and convolution operations.
*   **When Not to Use:** For extremely sparse data where most chunks are empty (use hash tables or sparse voxel grids). For data with highly variable resolution (use multi-resolution structures like OpenVDB).

## Background
Originating from implementations like DoonEngine, this method leverages the efficiency of bitmasks for sparse voxel storage [S1, unofficial]. It is closely related to the IndexGrid structure derived from NanoVDB, aiming to optimize stencil-centric operations [S1, unofficial]. The approach addresses the limitations of traditional VDB structures by separating topology from values and using fixed-depth structures for faster access [S1, unofficial].
