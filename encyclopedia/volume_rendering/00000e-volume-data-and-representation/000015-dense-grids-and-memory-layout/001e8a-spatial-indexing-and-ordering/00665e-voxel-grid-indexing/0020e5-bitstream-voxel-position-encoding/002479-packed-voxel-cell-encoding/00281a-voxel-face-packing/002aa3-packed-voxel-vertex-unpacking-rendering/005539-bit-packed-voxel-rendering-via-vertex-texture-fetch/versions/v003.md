# Bit-packed Voxel Rendering via Vertex Texture Fetch

Also called: Bit-packed Voxel Rendering

## Overview
Bit-packed Voxel Rendering via Vertex Texture Fetch is a technique to render a $128 \times 128 \times 128$ voxel grid by packing voxel existence data into 4 separate $128 \times 128$ RGBA images, where each pixel's 32 bits represent 32 voxels along the Z-axis [S1, unofficial]. The vertex shader samples these textures to determine voxel presence and projects vertices accordingly, using vertex texture fetch [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D voxel grid of resolution $128 \times 128 \times 128$ [S1, unofficial].
*   **Input:** 4 2D textures, each of size $128 \times 128$ pixels, formatted as RGBA8 [S1, unofficial].
*   **Input:** A vertex buffer containing vertex attributes [S1, unofficial].
*   **Output:** Rendered voxel geometry on the screen [S1, unofficial].

**Data Structures:**
The 3D grid is flattened into 4 separate 2D textures [S1, unofficial]. Each texture stores a slice of the Z-axis data [S1, unofficial].
*   **Texture Dimensions:** $128 \times 128$ pixels [S1, unofficial].
*   **Pixel Format:** RGBA, 8 bits per channel [S1, unofficial].
*   **Bit Packing:** Each pixel contains 32 bits ($4 \times 8$) [S1, unofficial].
*   **Mapping:**
    *   Texture $T_0$ stores Z indices $0$ to $31$ [S1, unofficial].
    *   Texture $T_1$ stores Z indices $32$ to $63$ [S1, unofficial].
    *   Texture $T_2$ stores Z indices $64$ to $95$ [S1, unofficial].
    *   Texture $T_3$ stores Z indices $96$ to $127$ [S1, unofficial].
    *   Total voxels: $128 \times 128 \times 32 \times 4 = 2,097,152$ [S1, unofficial].

**Vertex Attributes:**
Two approaches are described for vertex generation [S1, unofficial].
1.  **Explicit Geometry:** Vertex attributes for position and normal, plus a parallel attribute containing UV coordinates and bit information (effectively a 3D UV coordinate to sample the correct bit) [S1, unofficial].
2.  **Procedural Geometry:** A single 3D UV-coordinate attribute and a vertex index stored in the `.w` component of a `vec4` attribute [S1, unofficial].

**Algorithm Steps:**
1.  **Texture Upload:** Load the 4 RGBA textures into GPU memory [S1, unofficial].
2.  **Vertex Setup:** Create a vertex buffer [S1, unofficial].
3.  **Rendering Loop:** For each of the 4 textures ($T_i$ where $i \in [0, 3]$):
    a.  Set a Z-offset of $i \times 32$ units to shift vertices to the correct depth slice [S1, unofficial].
    b.  Bind texture $T_i$ [S1, unofficial].
    c.  Execute vertex shader for all vertices in the buffer [S1, unofficial].
4.  **Shader Execution (per vertex):**
    a.  Sample the bound texture at the vertex's $(X, Y)$ UV coordinates [S1, unofficial].
    b.  Extract the bit corresponding to the vertex's local Z-index (0–31) from the sampled pixel using floating-point manipulation [S1, unofficial].
    c.  If the bit is set, project the vertex normally [S1, unofficial].
    d.  If the bit is not set, move the vertex behind the near clipping plane so the WebGL pipeline culls it [S1, unofficial].
5.  **Draw:** Issue a draw call for the current texture [S1, unofficial].

**Pseudocode (Vertex Shader & Draw Loop Logic):**
```python
def extract_bit_from_float(pixel_value, bit_index):
    """Extract a specific bit from a float representation using math, avoiding integer ops."""
    # Shift the target bit to the ones place and take modulo 2
    shifted = pixel_value * (2.0 ** (31.0 - bit_index))
    return 1.0 if (int(shifted) % 2) == 1 else 0.0

def render_voxel_grid(vertices, textures):
    """
    Simulates the draw loop and vertex shader logic for bit-packed voxel rendering.
    vertices: list of dicts with 'uv' (x, y), 'local_z' (0-31), and 'base_z'
    textures: list of 4 2D arrays (128x128) containing float values 0.0-1.0
    """
    for i, texture in enumerate(textures):
        z_offset = i * 32.0
        for v in vertices:
            x, y = v['uv']
            local_z = v['local_z']
            
            # Sample texture at (x, y)
            pixel_value = texture[y][x]
            
            # Extract bit for local_z using floating-point manipulation
            bit = extract_bit_from_float(pixel_value, local_z)
            
            if bit > 0.5:
                # Voxel exists: project normally
                clip_z = (v['base_z'] + z_offset) * 2.0 - 1.0
            else:
                # Voxel empty: push behind near clipping plane
                clip_z = -2.0
            
            # gl_Position would be set here using clip_z
```

**Parameters:**
*   **Grid Resolution:** $128 \times 128 \times 128$ voxels [S1, unofficial].
*   **Texture Size:** $128 \times 128$ pixels per texture [S1, unofficial].
*   **Number of Textures:** 4 [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **WebGL Bit Operations:** WebGL lacks native bit operations (shift, and, or) and integer support on some Mac drivers [S1, unofficial].
*   **Vertex Texture Fetch Support:** Vertex texture fetch is required [S1, unofficial].
*   **Library Choice:** Three.js may not support `drawArrays` cleanly for this approach; GLOW library is suggested as a cleaner alternative [S1, unofficial].

## Operating characteristics
*   **Performance:** The explicit geometry method is memory-heavy but probably quite fast [S1, unofficial].
*   **Strengths:** Efficient culling of empty space; low memory footprint for the data structure; simple shader logic [S1, unofficial].
*   **Limitations:** Requires vertex texture fetch support; limited by WebGL integer/bit operation support; not suitable for dynamic voxel changes without texture updates; fixed grid resolution [S1, unofficial].
*   **When to Use:** When rendering large, static or semi-static voxel grids where most voxels are empty, and vertex texture fetch is available [S1, unofficial].
*   **When Not to Use:** When dynamic voxel updates are frequent (texture updates are costly); when running on hardware without vertex texture fetch support; when using libraries that do not support the required draw calls [S1, unofficial].

## Background
The technique was proposed in a 2012 Stack Overflow answer by Mikael Emtinger for rendering animated voxel scenes in WebGL using Three.js or GLOW [S1, unofficial]. It was suggested as an alternative to loading large static files and incrementally adding/deleting voxels, leveraging the GPU's ability to sample textures in the vertex shader for culling [S1, unofficial].
