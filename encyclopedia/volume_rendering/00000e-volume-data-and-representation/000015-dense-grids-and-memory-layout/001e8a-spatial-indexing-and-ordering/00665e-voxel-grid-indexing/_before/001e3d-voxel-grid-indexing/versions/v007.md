# Voxel Grid Indexing

Also called: Dense Voxel Grid, Voxel Grids, Voxel Indexing, VoxelGridDesc

## Overview
Voxel Grid Indexing maps 3D spatial coordinates $(i, j, k)$ to a 1D linear array index to enable $O(1)$ random access to dense volumetric data [S1, S4, S8, unofficial]. It solves the problem of efficiently locating and storing metadata (such as occupancy, density, or color) for points within a discretized 3D space [S7, S8, unofficial]. Unlike sparse representations that require tree traversal or hashing, this method relies on arithmetic strides (row-major ordering) to provide the fastest possible query performance, at the cost of cubic memory complexity with respect to resolution [S8, unofficial].

## How it works
**Inputs:**
- 3D integer coordinates $(i, j, k)$ or continuous world coordinates $(x, y, z)$.
- Grid dimensions: $size_x, size_y, size_z$ (number of voxels along each axis) [S2, unofficial].
- Optional padding: $sectionSide$ (base dimension) and $sideSize = sectionSide + 1$ for boundary handling [S1, unofficial].
- Optional physical parameters: $voxel\_size\_m$, $half\_patch$, $extent$ [S5, unofficial].

**Outputs:**
- A 1D linear index $I$ into a contiguous 1D array (e.g., `TArray`, `std::vector`) [S1, unofficial].
- Or, the inverse: 3D coordinates from a linear index [S1, unofficial].

**Data Structures:**
- **Dense Array:** A 1D array of size $size_x \times size_y \times size_z$ (or padded size) storing voxel data [S1, S4, unofficial].
- **VoxelGridDesc (Metadata):** A struct containing grid dimensions ($extent$, $height\_cells$), physical scale ($voxel\_size\_m$, $height\_step\_m$), and bounds ($base\_depth\_m$, $half\_patch$) [S5, unofficial].

**Formulas:**

1. **Standard Row-Major Indexing (Unpadded):**
   The linear index $I$ from coordinates $(i, j, k)$ where $i$ is the fastest-varying dimension (X), $j$ is Y, and $k$ is Z:
   $$ I = i + j \cdot size_x + k \cdot (size_x \cdot size_y) $$
   Alternatively defined as:
   $$ I = i \cdot 1 + j \cdot size\_yz + k \cdot size\_yz\_y $$
   Where $size\_yz = size_x$ and $size\_yz\_y = size_x \cdot size_y$ [S2, S4, S5, unofficial].
   *Note: Source [S4, unofficial] uses $offset = (k \cdot (dims[1] - 1) + j) \cdot (dims[0] - 1) + i$, implying dimensions might be reduced by 1 in specific implementations, but standard dense grids use full dimensions.*

2. **Padded Indexing (Boundary Safe):**
   To prevent out-of-bounds access when querying neighbors at grid edges, a padding of +1 is added to each dimension [S1, S3, unofficial].
   Let $sideSize = sectionSide + 1$ (or $kPaddedSize$) [S1, S3, unofficial].
   $$ I = (x + 1) \cdot kPaddedArea + (y + 1) \cdot kPaddedSize + (z + 1) $$
   Where $kPaddedArea = kPaddedSize \cdot kPaddedSize$ [S3, unofficial].
   *Note: The $+1$ offset accounts for a 1-voxel border around the valid data [S3, unofficial].*

3. **Inverse Mapping (Linear to 3D):**
   Given index $I$ and padded size $sideSize$:
   $$ z = I \pmod{sideSize} $$
   $$ I' = \lfloor I / sideSize \rfloor $$
   $$ y = I' \pmod{sideSize} $$
   $$ x = \lfloor I' / sideSize \rfloor $$
   [S1, unofficial].

4. **World to Voxel Index (Continuous to Discrete):**
   For continuous world coordinates $(x, y, z)$ and grid origin/size parameters [S5, S6, unofficial]:
   $$ ix = \text{clamp}\left( \left\lfloor \frac{x + half\_ext}{voxel\_size\_m} \right\rfloor, 0, extent - 1 \right) $$
   $$ iz = \text{clamp}\left( \left\lfloor \frac{z + half\_ext}{voxel\_size\_m} \right\rfloor, 0, extent - 1 \right) $$
   Where $half\_ext$ is half the patch size [S5, unofficial].
   For point clouds, indices are computed relative to the minimum point:
   $$ points\_index = \lfloor (points - min\_points) / grid\_cell\_size \rfloor $$
   [S6, unofficial].

**Pseudocode:**

```python
def compute_linear_index(i, j, k, size_x, size_y, size_z):
    """
    Computes the 1D index for a 3D voxel grid in row-major order.
    X varies fastest, then Y, then Z.
    """
    # Strides
    stride_y = size_x
    stride_z = size_x * size_y
    
    # Linear index
    index = i + j * stride_y + k * stride_z
    return index

def compute_linear_index_padded(x, y, z, section_side):
    """
    Computes index with 1-voxel padding on all sides.
    section_side: The logical width/height/depth of the voxel chunk.
    """
    side_size = section_side + 1
    padded_area = side_size * side_size
    
    # Offset by 1 to account for the border
    index = (x + 1) * padded_area + (y + 1) * side_size + (z + 1)
    return index

def decode_linear_index(index, section_side):
    """
    Decodes a padded linear index back to 3D coordinates.
    """
    side_size = section_side + 1
    
    # Reverse the padding offset
    # Note: This assumes the index was generated with the +1 offset logic
    # If using standard unpadded, logic differs slightly.
    
    # Using the padded formula from [S1, unofficial] inverse:
    # i = pos / (sideSize * sideSize)
    # j = (pos % (sideSize * sideSize)) / sideSize
    # k = (pos % (sideSize * sideSize)) % sideSize
    
    # However, [S3, unofficial] uses (x+1), so we must subtract 1 after decoding if we want logical coords
    # Let's stick to the direct inverse of the padded formula:
    
    k = index % side_size
    temp = index // side_size
    j = temp % side_size
    i = temp // side_size
    
    # Adjust for the +1 border if returning logical coordinates
    # If the input index included the border, i,j,k might be 0..side_size-1
    # Logical coords are usually 0..section_side-1
    # This depends on whether the border is stored or just for safety.
    # Assuming the index maps to the padded array directly:
    return i, j, k

def world_to_voxel_index(x, z, voxel_size_m, extent, half_patch):
    """
    Maps continuous world X,Z to clamped voxel indices.
    """
    half_ext = half_patch
    
    # Compute raw index
    ix_raw = (x + half_ext) / voxel_size_m
    iz_raw = (z + half_ext) / voxel_size_m
    
    # Floor and clamp
    ix = max(0, min(int(ix_raw), extent - 1))
    iz = max(0, min(int(iz_raw), extent - 1))
    
    return ix, iz
```

**Parameters:**
- `sectionSide`: Base voxel dimension per chunk section (e.g., 16) [S1, unofficial].
- `size_x_, size_y_, size_z_`: Grid dimensions in voxels [S2, unofficial].
- `grid_cell_size`: Size of grid cells in x, y, z dimensions (float) [S6, unofficial].
- `voxel_size_m`: Physical size of a voxel in meters [S5, unofficial].

**Edge Cases and Pitfalls:**
- **Boundary Access:** Without padding, accessing neighbors of edge voxels (e.g., $i-1$ when $i=0$) results in invalid memory access or wrapping to the previous slice in 1D arrays. Padding solves this by allocating extra space [S1, unofficial].
- **Precision:** Floating-point to integer conversion for world-to-voxel mapping must use `floor` or explicit casting to avoid off-by-one errors at boundaries [S5, S6, unofficial].
- **Memory Explosion:** Memory usage scales as $O(N^3)$ where $N$ is the resolution per axis. High resolutions become prohibitive [S7, S8, unofficial].

## Subtopics

### [Coordinate Space Conversion](1785-coordinate-space-conversion.md)
Coordinate Space Conversion defines the deterministic arithmetic for mapping between continuous world coordinates, continuous voxel coordinates, discrete integer voxel indices, and block indices in a sparse voxel grid. It solves the problem of accurately locating which voxel contains a given point and converting that voxel back to world space, ensuring consistency across host (CPU), device (GPU), and shader (GLSL) execution paths. It differs from Voxel Grid Initialization by performing the per-point arithmetic rather than static bounding box setup, and from World to UVW Normalization by operating in physical units and integer indices rather than normalized $[0, 1]$ texture coordinates [1785-coordinate-space-conversion.md].

### [Voxel Grid Initialization](2168-voxel-grid-initialization.md)
Voxel Grid Initialization establishes the foundational data structures and memory layouts required for volume rendering, specifically configuring scene boundaries, grid resolutions, and active voxel states. It solves the problem of transitioning from abstract scene parameters (bounding boxes, camera frustums) to a concrete, addressable 3D grid representation. It differs from Coordinate Space Conversion by focusing on memory allocation and state activation rather than coordinate transformation, and from Sparse Voxel Storage and Chunking by often dealing with the initial population of dense or semi-dense grids before sparsification or chunking strategies are applied [2168-voxel-grid-initialization.md].

### [World to UVW Normalization](2229-world-to-uvw-normalization.md)
World to UVW Normalization maps arbitrary 3D world coordinates into the normalized $[0, 1]$ range of a voxel grid, enabling consistent indexing and texture sampling regardless of the scene's physical scale or origin. It differs from Coordinate Space Conversion by explicitly handling discrete voxel grid boundaries and dimensionality, and from Texture Coordinate Conversion by operating at the grid indexing level rather than applying shader-specific offsets like Y-flips or centering adjustments [G].

### [Bitstream Voxel Position Encoding](2371-bitstream-voxel-position-encoding.md)
Bitstream Voxel Position Encoding is a method to encode the 3D position of a voxel into a linear bitstream for tree traversal, where each child index is determined by 3 bits. It solves the problem of mapping spatial coordinates to a hierarchical structure (such as an Octree) by creating a deterministic bit sequence that guides navigation from the root to the leaf node representing the voxel.

### [Grid Embedding](4454-grid-embedding.md)
Grid Embedding is a method for storing shape-specific latent codes in a dense, learnable 4D tensor lookup table indexed by model ID. It solves the problem of efficiently retrieving and optimizing per-model geometric or feature representations by structuring them as a dense grid rather than a sparse or unstructured collection. It differs from sibling methods like Spatial Hashing or Sparse Voxel Grid by enforcing a fixed, dense memory layout for model-level indexing, whereas siblings typically focus on spatial coordinate hashing or sparse occupancy.

### [Spatial Hashing](5002-spatial-hashing.md)
Spatial Hashing maps 3D world positions to hierarchical string-based spatial hashes (keys) and vice versa, enabling efficient traversal of a voxel hierarchy without storing explicit grid structures. It differs from flat spatial hashing by using a fixed-depth 12-level octal encoding where each character represents a 2x2x2 voxel block, allowing direct conversion between coordinates and region boundaries. Unlike Bitstream Voxel Position Encoding which stores raw bits, this method compresses position into a human-readable string for hierarchical queries.

### [Memory Layout and Data Mapping](8133-memory-layout-and-data-mapping.md)
Memory Layout and Data Mapping defines the mechanism for storing 3D voxel grids in contiguous 1D memory buffers and computing the bidirectional mapping between logical voxel coordinates (IJK) and linear array indices. It solves the problem of efficient random access and traversal of dense volumetric data by establishing a consistent row-major ordering where the X-dimension varies fastest, followed by Y, then Z.

### [Sparse Voxel Storage and Chunking](15595-sparse-voxel-storage-and-chunking.md)
Sparse Voxel Storage and Chunking represents volumetric data by storing only non-zero elements, significantly reducing memory usage compared to dense grids. It differs from its siblings Uniform Grid Indexing by avoiding the storage of empty space, but requires accelerated data structures for efficient querying, unlike the direct indexing of uniform grids.

### [Index Computation and Mapping](15596-index-computation-and-mapping.md)
Index Computation and Mapping defines the algorithms for translating continuous 3D spatial coordinates into discrete linear indices within a voxel grid data structure. It solves the problem of spatial localization, enabling efficient ray marching, point cloud queries, and isosurface extraction by mapping world positions to specific memory locations. This family distinguishes itself from Spatial Hashing by guaranteeing deterministic, collision-free indexing for all points within the grid bounds, and from Sparse Voxel Storage and Chunking by relying on fixed memory layouts rather than dynamic allocation [G].

### Data Collection from Indices
Data Collection from Indices extracts data from a tensor given a list of indices, handling both 2D and 3D data tensors. It reshapes data to 2D (flattening the first two dimensions) if it is 3D, calculates a combined point index, and performs the gather operation [S9, unofficial].

### Coarse Geometry Searching
Coarse Geometry Searching is a two-stage optimization process where the first stage efficiently finds the coarse 3D areas of interest (geometry) using a low-resolution voxel grid with view-invariant color, reducing queried points for the fine stage. It initializes density grids to 0 with a specific bias to ensure high transmittance at the start of training, and scales learning rates based on the number of training views visible to each voxel [S10].

## Operating characteristics
- **Time Complexity:** Index computation is $O(1)$ arithmetic operations (multiplications, additions, modulo) [S1, S4, S8, unofficial].
- **Memory Complexity:** Cubic with respect to resolution, $O(N^3)$, where $N$ is the number of voxels per axis [S7, S8, unofficial].
- **Performance:** Provides the fastest possible query speed for dense data due to direct memory access without branching or tree traversal [S8, unofficial].
- **Strengths:** Simple implementation, cache-friendly for contiguous access patterns (if spatial locality is preserved via SFC, though standard row-major has poor locality for non-adjacent slices [G]), deterministic indexing.
- **Limitations:** Prohibitive memory usage for high-resolution grids or large bounding boxes; inefficient for sparse scenes where most voxels are empty [S7, S8, unofficial].
- **When to Use:** Small to medium-sized scenes, dense volumes (e.g., fluid simulation, medical imaging with full resolution), or as a coarse approximation in multi-stage rendering (e.g., Direct Voxel Grid Optimization) [S10].
- **When Not to Use:** Large open-world scenes with significant empty space, or when memory is constrained [S8, unofficial].

## Background
Voxel grids are a fundamental representation in computer graphics and scientific visualization, dating back to the early days of 3D rendering. They provide an explicit discretization of 3D space into cubes, storing metadata in an array [S7, unofficial]. While simple, their $O(N^3)$ storage requirements have led to the development of sparse variants and neural representations like NeRF, which exploit symmetries that voxel grids do not [S7, unofficial]. Recent work, such as Direct Voxel Grid Optimization, has revisited dense voxel grids for neural rendering by optimizing the grid values directly, leveraging their fast query capabilities [S10].
