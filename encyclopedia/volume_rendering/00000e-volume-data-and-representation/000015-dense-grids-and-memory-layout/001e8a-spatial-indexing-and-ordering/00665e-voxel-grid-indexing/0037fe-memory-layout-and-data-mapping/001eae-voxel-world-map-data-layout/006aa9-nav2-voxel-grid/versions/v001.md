# Nav2 Voxel Grid

Also called: VoxelGrid

## Overview
The Nav2 Voxel Grid is an efficient 3D spatial indexing structure designed for robotics navigation, specifically serving as the backend for the Voxel Layer in `nav2_costmap_2d` [S1, S2]. It solves the problem of representing 3D occupancy data with minimal memory overhead by mapping a 3D world onto a 2D array of pointers, where each pointer manages a vertical column of voxels [S1, S2]. It distinguishes itself from general-purpose 3D grids by relying on bitwise integer operations to achieve raytracing and cell marking performance comparable to standard 2D structures, making it significantly faster than most 3D structures [S1, S2].

## How it works
The method implements a dense voxel grid where the horizontal dimensions ($X, Y$) are managed via a 2D array, and the vertical dimension ($Z$) is managed via bitmasks within integer types.

**Inputs and Outputs:**
*   **Input:** Map dimensions (width, height), voxel resolution, and vertical limits.
*   **Output:** A data structure supporting 3D raycasting and cell marking (marked, free, unknown).

**Data Structures:**
The core structure is a 2D array of character pointers (`char**` or similar), sized according to the map's horizontal dimensions ($W \times H$) [S1, S2].
*   **Pointer Array:** Each element `grid[x][y]` points to a memory block representing the vertical column at $(x, y)$ [S1, S2].
*   **Voxel State Encoding:** The state of each voxel in the column is encoded using bit locations within integer types [S1, S2].
*   **Cell States:** The grid supports three distinct representations for the state of a cell:
    1.  Marked (Occupied)
    2.  Free
    3.  Unknown [S1, S2]

**Parameters:**
*   **Levels per Column:** The grid supports up to 16 different levels per voxel column [S1, S2]. This limit is a direct consequence of the underlying implementation relying on bitwise AND and OR integer operations, which typically operate on standard integer widths (e.g., 16 bits or fewer for specific flags) [S1, S2].
*   **Typical Values:** Not given in the sources.

**Algorithm Steps:**
1.  **Initialization:** Allocate a 2D array of pointers with size equal to the map width $\times$ height [S1, S2]. Initialize each pointer to `nullptr` or an empty block [G].
2.  **Column Access:** To access voxel at $(x, y, z)$:
    *   Retrieve the pointer `ptr = grid[x][y]` [S1, S2].
    *   If `ptr` is null, the column is empty/unknown [G].
    *   Calculate the bit index corresponding to $z$. Since the grid supports 16 levels, $z$ is typically mapped to a 4-bit or 8-bit field within an integer [S1, S2].
3.  **Cell Marking:** To mark a voxel as occupied, free, or unknown:
    *   Use bitwise OR (`|`) to set the corresponding bit in the integer representation of the column [S1, S2].
    *   Use bitwise AND (`&`) with a complement mask to clear bits if marking as free or resetting state [S1, S2].
4.  **Raycasting:** Perform 3D raycasting by iterating through the voxel column indices along the ray path:
    *   For each $(x, y)$ intersected by the ray, access the column pointer [S1, S2].
    *   Check the bitmasks for the specific $z$ levels intersected by the ray segment [S1, S2].
    *   Return occupancy status based on the bitwise state [S1, S2].

**Edge Cases and Pitfalls:**
*   **Level Limit:** The implementation is strictly limited to 16 levels per voxel column due to the reliance on bitwise integer operations [S1, S2]. Exceeding this limit is not supported [S1, S2].
*   **Precision:** The use of bitwise operations requires careful handling of integer widths to avoid overflow or incorrect state interpretation [S1, S2].
*   **Boundaries:** Accessing coordinates outside the $W \times H$ map bounds or $Z$ levels outside $[0, 15]$ must be guarded [G].

## Operating characteristics
*   **Time Complexity:** Raytracing and cell marking performance are comparable to standard 2D structures [S1, S2]. This is significantly faster than most general 3D structures [S1, S2].
*   **Memory Complexity:** Memory usage is proportional to the map area ($W \times H$) plus the number of non-empty columns. Each column uses a small integer (or char array) to store up to 16 levels [S1, S2].
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Performance scales linearly with the number of voxels traversed during raycasting, but the 2D pointer array overhead is minimal compared to full 3D array allocations [S1, S2].
*   **Strengths:** High speed for raycasting and marking; low memory overhead for sparse or partially filled 3D maps; simple implementation using bitwise operations [S1, S2].
*   **Limitations:** Hard limit of 16 vertical levels per column; limited to 3 cell states (marked, free, unknown) [S1, S2].
*   **When to use:** When high-performance 3D occupancy grid operations (raycasting, marking) are required in robotics navigation, particularly within the ROS 2 Nav2 ecosystem [S1, S2].
*   **When not to use:** When more than 16 vertical levels are needed, or when more than 3 distinct cell states are required [S1, S2].

## Background
The Nav2 Voxel Grid package originated as a direct port to ROS 2 for use in the voxel layer of `nav2_costmap_2d` [S1, S2]. It was branched out as a separate package to allow reuse in other applications where a dense voxel grid representation may be useful [S1, S2]. It is used by the Voxel Layer inside `nav2_costmap_2d` [S1, S2]. The package also contains implementations of 3D raycasting [S1, S2].
