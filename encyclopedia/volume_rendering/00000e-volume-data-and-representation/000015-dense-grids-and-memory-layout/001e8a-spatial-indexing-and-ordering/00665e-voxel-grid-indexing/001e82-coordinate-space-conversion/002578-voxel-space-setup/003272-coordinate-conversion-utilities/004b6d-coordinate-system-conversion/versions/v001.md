# Coordinate System Conversion
Also called: Swept-Volume Coordinate Transformation, Cartesian-to-Cylindrical-to-System Conversion

## Overview
This method converts normalized Cartesian voxel data into system-specific coordinates required for swept-volume displays, mapping 3D spatial positions to 2D panel coordinates and an angular sweep parameter. It differs from [Metric Coordinate Conversion](12960-metric-coordinate-conversion.md) by targeting the specific geometric requirements of cylindrical projection displays rather than general metric scaling, and from [Sliced Volume Coordinate Mapping](8287-sliced-volume-coordinate-mapping.md) by handling the full volumetric data transformation prior to slicing or rendering, rather than mapping pre-existing slices.

## How it works
**Inputs:** Normalized Cartesian data points in Descartes coordinates $(x, y, z)$ with associated color attributes $(r, g, b)$.
**Outputs:** System coordinates $(h, w, \theta)$ with associated color attributes $(r, g, b)$, where $h$ is height, $w$ is width, and $\theta$ is the sweep angle.

**Data Structures:**
The input is a list or grid of tuples: $(x, y, z, r, g, b)$.
The output is a list or grid of tuples: $(h, w, \theta, r, g, b)$.

**Parameters:**
- $x_{center}, y_{center}$: The center of the display screen or coordinate system origin. [S1]
- Screen resolution scaling factors: Applied to adjust object data scaling to the actual display screen resolution. [S1]

**Steps:**
1.  **Centering:** Subtract the center coordinates from the input Cartesian coordinates to normalize the position relative to the display center.
    $$x' = x - x_{center}$$
    $$y' = y - y_{center}$$
    $$z' = z - z_{center}$$
    [S1]

2.  **Cartesian to Cylindrical:** Convert the centered Cartesian coordinates $(x', y', z')$ to cylindrical coordinates $(\theta, \rho, z')$.
    $$\theta = \arctan2(y', x')$$
    $$\rho = \sqrt{x'^2 + y'^2}$$
    The color attributes $(r, g, b)$ are preserved.
    [S1]

3.  **Cylindrical to System:** Map the cylindrical coordinates to the swept-volume system coordinates $(h, w, \theta)$.
    - $h$ (Height): Corresponds to the vertical position, typically derived from $z'$ or $y'$ depending on the specific display axis alignment. [S1]
    - $w$ (Width): Corresponds to the radial distance $\rho$, mapped to the horizontal panel coordinate. [S1]
    - $\theta$ (Angle): The angular component from the cylindrical conversion. [S1]
    The color attributes $(r, g, b)$ are preserved.
    [S1]

4.  **Data Reduction (Optional but implied):** After transformation, reduce stored data by saving only voxels that will be activated on the display panel. If a memory query for a panel coordinate $(h, w)$ finds no matching condition, the color data is set to 0. [S1]

**Pseudocode:**
```python
import math

def convert_coordinate_system(points, x_center, y_center, z_center, 
                              screen_width, screen_height):
    """
    Convert normalized Cartesian data to swept-volume system coordinates.
    
    Args:
        points: List of tuples (x, y, z, r, g, b)
        x_center, y_center, z_center: Center of the display coordinate system
        screen_width, screen_height: Resolution of the display panel
        
    Returns:
        List of tuples (h, w, theta, r, g, b)
    """
    output = []
    
    for x, y, z, r, g, b in points:
        # Step 1: Centering
        x_prime = x - x_center
        y_prime = y - y_center
        z_prime = z - z_center
        
        # Step 2: Cartesian to Cylindrical
        # theta is the angle in the xy-plane
        theta = math.atan2(y_prime, x_prime)
        # rho is the radial distance in the xy-plane
        rho = math.sqrt(x_prime**2 + y_prime**2)
        
        # Step 3: Cylindrical to System Coordinates
        # h corresponds to the vertical axis (z in this context, or y depending on setup)
        # w corresponds to the horizontal axis (rho mapped to screen width)
        # Note: Exact mapping of h/w to z'/rho depends on specific hardware layout.
        # Assuming standard swept-volume where z is height and rho maps to width.
        
        h = z_prime 
        # Map rho to screen width coordinate [0, screen_width]
        # This requires scaling based on the physical radius of the display
        # Not explicitly defined in [S1], so we assume a linear mapping placeholder
        # [G] Implementation note: rho must be scaled by (screen_width / max_rho)
        w = rho 
        
        output.append((h, w, theta, r, g, b))
        
    return output
```
[G] The source [S1] mentions "adjust the object data scaling to the actual display screen resolution" but does not provide the exact scaling formula for $w$. The implementer must determine the maximum physical radius of the swept volume and scale $\rho$ accordingly to fit $[0, \text{screen\_width}]$.

## Subtopics

### Coordinate System and Axis Swapping
This variant handles the conversion for mesh voxelization tools that assume a specific input coordinate system (x=right, y=up, z=forward) and swap axes during voxelization to match the output volume's memory layout. Specifically, the x and y axes are swapped so that the output volume's first dimension corresponds to height (Y-axis). This is distinct from the swept-volume method as it prepares data for storage in a 3D grid rather than a 2D panel projection. Parameters include `--height` (Y-axis, default 32), `--width` (X-axis, default 32), and `--depth` (Z-axis, default 32) [S2, unofficial].

## Operating characteristics
**Time Complexity:** Linear with respect to the number of input voxels $N$, $O(N)$, as each point undergoes a constant number of arithmetic operations.
**Memory Complexity:** $O(N)$ to store the transformed coordinates and color attributes.
**Strengths:** Directly maps 3D data to the geometric requirements of swept-volume displays, enabling efficient rendering on cylindrical screens.
**Limitations:** Requires precise knowledge of the display center and resolution. The data reduction step is hardware-dependent and not fully specified in the general method.
**When to use:** When rendering volumetric data on swept-volume displays or cylindrical projection systems.
**When not to use:** For standard orthogonal or perspective volume rendering on flat screens, or when metric spatial relationships are required without angular projection.

## Background
The method originates from the design of 3D swept-volume volumetric displays, where data must be transformed from standard Cartesian coordinates to a cylindrical coordinate system that matches the physical layout of the display panel and the sweep mechanism. It was described in the context of improving the design of such displays, focusing on efficient data storage and retrieval based on panel coordinates. [S1]
