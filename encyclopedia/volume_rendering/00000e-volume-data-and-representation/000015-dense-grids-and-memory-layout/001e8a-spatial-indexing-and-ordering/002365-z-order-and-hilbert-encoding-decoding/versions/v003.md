# Z-Order and Hilbert Encoding/Decoding


## Overview
Z-Order and Hilbert encoding map $N$-dimensional voxel coordinates to 1D linear indices to optimize spatial locality in contiguous memory layouts [S1, unofficial]. Unlike Morton codes which use simple bit-interleaving, Hilbert encoding uses a recursive curve traversal to minimize the distance between adjacent linear indices, offering superior cache coherence for streaming workloads [G]. These methods solve the problem of scattered memory access during volume rendering by ensuring that spatially adjacent voxels are stored near each other in the buffer [G].

## How it works
**Inputs:**
*   `coords`: An array of $N$-dimensional integer coordinates $(x_0, x_1, \dots, x_{N-1})$.
*   `bits`: The number of bits per dimension (typically 10–16 for GPU textures).
*   `mode`: 'z_order' or 'hilbert'.

**Outputs:**
*   `index`: A single 64-bit integer representing the linear position.

**Data Structures:**
*   `index`: 64-bit unsigned integer.
*   `coords`: Array of integers, each fitting within `bits`.

**Steps:**

### Z-Order (Morton Code)
1.  **Bit Interleaving:** For each dimension $d$, extract the $b$-th bit of $x_d$.
2.  **Pack:** Place the $b$-th bit of $x_0$ at bit position $b \cdot N$, $x_1$ at $(b \cdot N) + 1$, etc.
3.  **Result:** The resulting integer is the Z-order code.

Formula for 3D ($N=3$):
$$ I = \sum_{b=0}^{bits-1} \left( (x_0 \gg b \& 1) \ll (3b) + (x_1 \gg b \& 1) \ll (3b+1) + (x_2 \gg b \& 1) \ll (3b+2) \right) $$

### Hilbert Encoding
1.  **Gray Code Conversion:** Convert coordinates to Gray code to ensure adjacent integers differ by one bit.
2.  **Recursive Reflection:** Apply a transformation matrix based on the quadrant of the current sub-cube. The direction of traversal depends on the parity of the bits processed so far.
3.  **Bit Packing:** Interleave the transformed bits similarly to Z-order.

Pseudocode for Hilbert Encode (3D, 16-bit total, 5 bits per dim):

```python
def hilbert_encode_3d(x, y, z, bits_per_dim=5):
    """
    Encodes 3D coordinates into a Hilbert index.
    Assumes x, y, z are non-negative integers < 2^bits_per_dim.
    """
    n = 1 << (bits_per_dim - 1)
    rx, ry, rz = 0, 0, 0
    r = x | (y << 1) | (z << 2)
    
    for s in range(bits_per_dim - 1):
        d = n >> s
        rx = 1 if (x & d) else 0
        ry = 1 if (y & d) else 0
        rz = 1 if (z & d) else 0
        
        # If the right bit of x is 1, invert the order of the sub-cube
        if rx == 1:
            # Swap x and y
            x, y = y, x
            # Invert y
            y = d - 1 - y
        # If the right bit of y is 1, invert x and z
        if ry == 1:
            # Swap x and z
            x, z = z, x
            # Invert z
            z = d - 1 - z
        # If the right bit of z is 1, invert y and z
        if rz == 1:
            # Swap y and z
            y, z = z, y
            # Invert z
            z = d - 1 - z
            
    # Final interleaving
    index = 0
    for i in range(bits_per_dim):
        index |= ((x >> i) & 1) << (3 * i)
        index |= ((y >> i) & 1) << (3 * i + 1)
        index |= ((z >> i) & 1) << (3 * i + 2)
        
    return index
```

**Parameters:**
*   `bits_per_dim`: Typically 10 for 1024^3 volumes. Total index size is $3 \times bits\_per\_dim$.
*   **Edge Cases:** Coordinates must be within bounds $[0, 2^{bits}-1]$. Negative coordinates require offsetting or two's complement handling [G].

## Subtopics

### [Morton Code Sorting for Brick Layout](9894-morton-code-sorting-for-brick-layout.md)
Morton Code Sorting for Brick Layout organizes sub-bricks into a global buffer to maximize spatial coherence. It sets itself apart by operating iteratively at each level of the brick hierarchy, using enumeration sort to guarantee compactness. Choose this when rendering hierarchical volumes with fixed-size bricks to minimize cache misses during ray marching.

### Serialized-Morton/ASTC
Serialized-Morton/ASTC rearranges voxel attributes into correlations to enable ASTC codec reuse [S2, unofficial]. It differs from standard Morton layouts by prioritizing compression efficiency over pure spatial locality, requiring a mapping from voxel locations to serialized attributes for random access [S2, unofficial]. Choose this when bandwidth is the bottleneck and ASTC hardware decompression is available. Note that rearranging attributes can weaken spatial correlations available to UV mapping alone [S2, unofficial].

## Operating characteristics
**Time Complexity:**
*   Encoding/Decoding: $O(N \cdot B)$ where $N$ is dimensions and $B$ is bits per dimension.
*   Sorting: $O(K \log K)$ or $O(K)$ with radix sort, where $K$ is the number of voxels/bricks.

**Memory Complexity:**
*   Index storage: $O(K)$ integers.
*   Serialized-Morton/ASTC variants require more memory than 3DNTC at matched quality due to addressing overhead [S2, unofficial].

**Performance:**
*   Hilbert encoding provides better cache locality than Z-order for continuous paths, reducing cache misses in streaming renderers [G].
*   Z-order is faster to compute due to simpler bit manipulation [G].
*   Serialized-Morton/ASTC averages 10.8 ms per frame on MPEG and 23.1 ms on AOM for specific hardware/resolutions, with addressing accounting for a significant portion of latency [S2, unofficial].

**Strengths:**
*   Excellent spatial locality for both methods.
*   Hilbert minimizes jumps between distant memory locations.

**Limitations:**
*   Hilbert encoding is computationally more expensive than Z-order.
*   Serialized variants introduce addressing overhead and memory costs [S2, unofficial].

## Background
Z-order (Morton code) was introduced by G. M. Morton in 1966 [G]. Hilbert curves were used in spatial indexing by R. R. Peano and later David Hilbert [G]. Modern GPU implementations (e.g., `o-voxel-gpu`) provide optimized CUDA kernels for these encodings to support real-time volume rendering [S1, unofficial]. Serialized-Morton/ASTC was proposed in recent research to leverage texture compression hardware for mesh and volume data [S2, unofficial].
