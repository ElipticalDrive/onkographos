# Global Static Indexing for Regular Grids

Also called: 2^n tree decomposition indexing, 3-bit hierarchical Z order, Hierarchical Z-order Indexing (3-bit), Lebesgue curve indexing

## Overview
Global Static Indexing is a storage layout and indexing scheme for rectilinear grids that minimizes disk I/O during progressive traversal by reordering data based on a $2^n$ tree decomposition (Lebesgue curve) instead of a binary tree [S1]. It enables out-of-core visualization of very large grids (e.g., $8192^3$) with modest memory (60MB) by combining interleaved storage of hierarchy levels while maintaining geometric proximity within each resolution level [S1]. Unlike standard row-major or brick decomposition schemes, it is twice as fast as 1-bit hierarchical Z-ordering and orders of magnitude faster than standard arrays, with no data replication [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A $d$-dimensional rectilinear grid of size $N^d$ (typically $N=2^L$), where each element $s$ has spatial coordinates $(i_1, \dots, i_d)$.
*   **Output:** A 1D linear index $I'(s)$ mapping each element to a position in a flat array optimized for progressive coarse-to-fine traversal.

**Data Structures:**
*   **Hierarchy Levels:** A hierarchy $H = \{S_0, S_1, \dots, S_{k-1}\}$ where $S_0 \subset S_1 \subset \dots \subset S_{k-1} = S$. $S_i$ represents the set of elements at resolution level $i$.
*   **Derived Sets:** The grid is partitioned into derived sets $S'_i = S_i \setminus S_{i-1}$ (with $S_{-1} = \emptyset$). $S'_i$ contains only the *new* elements introduced at level $i$.
*   **Constants:** Precomputed constants $C_i$ for each level $i$, representing the cumulative count of elements in all coarser levels ($0 \dots i-1$).
*   **Block Size:** Data is typically read in blocks of 64KB [S1].

**Formulas:**
1.  **Z-Order Index ($I(s)$):** For an element $s$ with coordinates $(i_1, \dots, i_d)$, let each coordinate $i_j$ have $h$ bits $b^j_1 \dots b^j_h$. The standard Z-order index $I(s)$ is formed by interleaving these bits:
    $$ I(s) = b^1_1 b^2_1 \dots b^d_1 b^1_2 b^2_2 \dots b^d_2 \dots b^1_h b^2_h \dots b^d_h $$
2.  **Level Constant ($C_i$):** For level $i > 0$, the starting index is:
    $$ C_i = 2^{l(i-1)} $$
    where $l$ is the number of bits per dimension per block (e.g., $l=3$ for 3-bit hierarchical indexing). $C_0 = 0$.
3.  **Local Index ($I''_i(s)$):** For an element $s$ with standard Z-order index $j$ belonging to derived set $S'_i$:
    $$ I''_i(j) = \lfloor j / 2^{li} \rfloor - \lfloor j / 2^{l(i+1)} \rfloor - 1 $$
    *Note: The source uses integer division notation $j/2^{li}$ [S1].*
4.  **Global Index ($I'(s)$):**
    $$ I'(s) = C_i + I''_i(s) $$

**Parameters:**
*   **$l$ (bits per level):** Typically 3 for the "3-bit hierarchical Z-order" variant [S1].
*   **$k$ (levels):** Determined by the grid depth. For a grid of size $2^L$, $k \approx L/l$.
*   **Compression:** Data is compressed using zlib before storage [S1].

**Numbered Steps:**

1.  **Preprocessing (Offline):**
    1.  Determine the hierarchy levels $S_i$ for the grid.
    2.  Compute the derived sets $S'_i = S_i \setminus S_{i-1}$.
    3.  Calculate the number of elements $c_i = |S'_i|$ for each level.
    4.  Compute the constants $C_i = \sum_{j=0}^{i-1} c_j$. For the specific $2^n$ tree decomposition with block size $2^l$, $C_i = 2^{l(i-1)}$ for $i>0$ and $C_0=0$ [S1].

2.  **Runtime Indexing (Per Element):**
    1.  **Determine Level:** Given spatial coordinate $s$, determine its resolution level $i$ such that $s \in S'_i$. This is typically done by finding the highest resolution level that contains $s$ or by checking the coordinate bits against the block size $2^l$.
    2.  **Compute Standard Z-Index:** Calculate the standard Z-order index $j = I(s)$ by interleaving the bits of the coordinates of $s$.
    3.  **Compute Local Index:** Calculate $I''_i(j) = \lfloor j / 2^{li} \rfloor - \lfloor j / 2^{l(i+1)} \rfloor - 1$.
    4.  **Compute Global Index:** Return $I'(s) = C_i + I''_i(j)$.

**Optimization (Bit Manipulation):**
The final index $I'(s)$ can be computed directly from $j$ using bit shifts and additions to avoid explicit division:
$$ I'(s) = \text{shift\_right}(j, l \cdot i) + \text{complement\_bits}(\text{shift\_right}(j, l \cdot (i+1)), l \cdot (k - i - 1)) $$
This leverages the fact that $C_i - \lfloor j / 2^{l(i+1)} \rfloor - 1$ corresponds to complementing the rightmost $l(k - i - 1)$ bits of $\lfloor j / 2^{l(i+1)} \rfloor$ [S1].

**Pseudocode:**

```python
def compute_global_index(coordinates, level_bits=3, total_levels=None):
    """
    Computes the global static index for a grid element.
    
    Args:
        coordinates: Tuple of integers (i1, i2, ..., id) representing the element's position.
        level_bits: Number of bits per dimension per hierarchy level (l). Default 3.
        total_levels: Total number of hierarchy levels (k). Required for bit complementation optimization.
                      If None, uses the fallback formula.
    
    Returns:
        The global linear index I'(s).
    """
    d = len(coordinates)
    
    # Step 1: Determine the level i for the element s.
    # In a 2^n tree decomposition, the level is determined by the coarsest block 
    # that contains the element. For a grid of size 2^L, level i covers blocks 
    # of size 2^(l*i). The element belongs to the highest level i such that 
    # the element is inside a block defined by that level's grid.
    # A simple way to find i is to find the most significant bit position 
    # that differs from the origin or use the coordinate magnitude.
    # However, the source implies i is known or determined by the traversal context.
    # For a single element lookup, we assume i is provided or derived from 
    # the max coordinate bits. Here we assume i is passed or derived from 
    # the context of the progressive traversal. 
    # [G] If i is not provided, it must be derived from the coordinates. 
    # In a full grid, level i contains elements where the coordinates' 
    # most significant bits (above l*i) are constant within a block.
    # For this implementation, we assume 'i' is determined by the caller 
    # based on the progressive traversal step (coarse to fine).
    # If we must derive i from coordinates alone for a static lookup:
    # i is the level of the coarsest block containing s.
    # This is complex without knowing the grid size L. 
    # The source algorithm assumes i is known: "Given s, determine its level of resolution i".
    # We will assume i is an input for the sake of a complete function, 
    # or derived from the max bit depth of the coordinates if L is known.
    # Let's assume L is known and i is derived.
    # [G] Deriving i: Find the largest i such that the element is in S_i \ S_{i-1}.
    # This is equivalent to finding the highest resolution level that "owns" the element.
    # In a quadtree/octree, this is the leaf node. In this hierarchical indexing,
    # it's the finest level where the element is distinct from its parent.
    # Actually, the source defines S'_i as the NEW elements. 
    # So i is the finest level at which the element is present.
    # For a regular grid, every element is present at the finest level.
    # The hierarchy is usually defined by sub-sampling. 
    # S_0 is the coarsest grid (1 element per block of size 2^L).
    # S_1 is finer, etc.
    # The element s is in S'_i if it is in S_i but not in S_{i-1}.
    # This implies s is a "new" detail at level i.
    # In practice, for progressive slicing, the renderer requests elements 
    # at specific levels. The index function maps (s, i) to I'(s).
    # So i is an input parameter from the traversal logic.
    
    # Step 2: Compute standard Z-order index j
    j = z_order_index(coordinates)
    
    # Step 3: Compute Global Index
    if total_levels is not None:
        # Optimization using bit manipulation
        # C_i = 2^(l*(i-1)) for i > 0
        # I''_i(j) = (j >> (l*i)) - (j >> (l*(i+1))) - 1
        # I'(s) = C_i + I''_i(j)
        
        if i == 0:
            C_i = 0
        else:
            C_i = 1 << (level_bits * (i - 1))
            
        term1 = j >> (level_bits * i)
        term2 = j >> (level_bits * (i + 1))
        I_double_prime = term1 - term2 - 1
        
        return C_i + I_double_prime
    else:
        # Fallback: Compute C_i explicitly
        # C_i = sum of c_j for j < i
        # For 2^n tree, c_j = 2^(l*j) * (2^d - 1) ? 
        # Source says C_i = 2^(l*(i-1)). This seems to be for the specific 
        # case where the number of elements follows a geometric progression 
        # related to the tree structure.
        # We stick to the source formula: C_i = 2^(l*(i-1))
        if i == 0:
            C_i = 0
        else:
            C_i = 1 << (level_bits * (i - 1))
            
        term1 = j >> (level_bits * i)
        term2 = j >> (level_bits * (i + 1))
        I_double_prime = term1 - term2 - 1
        
        return C_i + I_double_prime

def z_order_index(coordinates):
    """
    Computes the standard Z-order (Morton) index by interleaving bits.
    """
    d = len(coordinates)
    # Find max bits needed
    max_val = max(coordinates)
    if max_val == 0:
        h = 1
    else:
        h = max_val.bit_length()
        
    index = 0
    for bit_pos in range(h):
        for dim in range(d):
            bit = (coordinates[dim] >> bit_pos) & 1
            index |= (bit << (bit_pos * d))
    return index
```

**Edge Cases and Pitfalls:**
*   **Level Determination:** The algorithm requires knowing the resolution level $i$ for each element $s$. In progressive traversal, this is provided by the traversal logic. If computed statically, it requires knowing the grid's total depth and the sub-sampling scheme [S1].
*   **Precision:** The bit manipulation optimization relies on correct bit widths. Ensure integer types are large enough to hold the index (e.g., 64-bit integers for $8192^3$ grids).
*   **Boundary Conditions:** $C_0 = 0$. The formula for $C_i$ applies for $i > 0$ [S1].
*   **Scaling with Output Texture:** Performance declines as output resolution increases (e.g., $512^2$ to $2048^2$) due to cache trashing. This requires a larger memory cache or parallelization strategies like tiling [S1].

## Operating characteristics
*   **Time Complexity:** Index computation is $O(1)$ per element after preprocessing, dominated by bit operations. Preprocessing is $O(N)$ to compute constants.
*   **Memory Complexity:** Minimal overhead. Only constants $C_i$ are stored. No data replication [S1].
*   **Performance:**
    *   On a Linux laptop (500Mhz Pentium III, 20MB cache), progressive slicing of a $2048 \times 2048 \times 1920$ grid achieved real-time interaction rates using only 20MB of cache memory [S1].
    *   On an SGI Onyx2 (300Mhz R12000, 60MB RAM, 4 threads), progressive slicing of an $8192^3$ grid (0.5 tera-nodes) maintained real-time interaction rates [S1].
    *   The 3-bit hierarchical Z-order scheme is twice as fast as the 1-bit hierarchical Z-order scheme and orders of magnitude faster than standard row-major array storage or brick decomposition schemes [S1].
*   **Strengths:**
    *   Minimizes disk I/O during progressive traversal [S1].
    *   Independent of the out-of-core blocking factor (e.g., 64KB blocks) [S1].
    *   Simple bit-string manipulation for index conversion, suitable for hardware implementation [S1].
    *   No data replication, avoiding performance degradation with dynamic modifications [S1].
*   **Limitations:**
    *   Performance degrades with high-resolution output textures due to cache trashing [S1].
    *   Requires preprocessing to compute constants [S1].

## Background
*   **Origin:** Introduced by Valerio Pascucci and Randall J. Frank at Lawrence Livermore National Laboratory [S1].
*   **Paper:** "Global Static Indexing for Real-Time Exploration of Very Large Regular Grids" [S1].
*   **History:** Improves upon the approach in [25] (1-bit hierarchical Z-order) by using a conceptual $2^n$ tree decomposition instead of a binary tree, allowing for better geometric locality and simpler bit-string manipulation [S1].
*   **Usage:** Used for progressive visualization algorithms, specifically progressive computation of planar slices with general orientation, supporting both parallel and rotated slice sequences [S1].
