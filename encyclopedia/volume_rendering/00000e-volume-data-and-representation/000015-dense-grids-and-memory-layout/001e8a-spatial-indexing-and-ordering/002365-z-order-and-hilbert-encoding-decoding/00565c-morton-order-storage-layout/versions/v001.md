# Morton Order Storage Layout

Also called: 3D Z-curve layout, Performance and Storage Scaling, Z-order storage

## Overview
Morton order storage layout arranges volumetric data in memory according to the 3D Z-order (Lebesgue) curve to maximize spatial locality and cache efficiency during traversal [S1]. It differs from standard row-major layouts by ensuring that voxels with adjacent spatial coordinates are stored adjacently in linear memory, which is critical for minimizing cache misses in encrypted or large-scale volume rendering pipelines [S1].

## How it works
**Inputs and Outputs:**
- Input: A 3D volume grid of dimensions $W \times H \times D$ and voxel data type (e.g., 16-bit integer, 2048-bit BigInteger).
- Output: A linear memory buffer (array) where elements are ordered by their Morton codes.

**Data Structures:**
- **Morton Code:** A 64-bit (or larger) integer where the bits of the $x, y, z$ coordinates are interleaved. For a coordinate $(x, y, z)$, the Morton code $M$ is constructed by placing the $i$-th bit of $x$ at position $3i$, $y$ at $3i+1$, and $z$ at $3i+2$ in the resulting integer [S1].
- **Storage Array:** A contiguous array of voxels. In naive implementations, this may be a 3D BigInteger array flattened or accessed via Morton indices [S1].

**Steps:**
1. **Coordinate to Morton Code Conversion:** For each voxel at $(x, y, z)$, compute its Morton code $M$.
   - Let $x_i, y_i, z_i$ be the $i$-th bit of the coordinates.
   - $M = \sum_{i=0}^{n-1} (x_i \cdot 4^i + y_i \cdot 2 \cdot 4^i + z_i \cdot 4^i \cdot 2)$? No, standard interleaving:
   - $M = \sum_{i=0}^{n-1} (x_i \ll 2i) | (y_i \ll (2i+1)) | (z_i \ll (2i+2))$?
   - Correct standard 3D Morton interleaving:
     $$ M = \sum_{i=0}^{n-1} \left( x_i \cdot 2^{3i} + y_i \cdot 2^{3i+1} + z_i \cdot 2^{3i+2} \right) $$
     where $x_i, y_i, z_i \in \{0, 1\}$ are the bits of the coordinates.
2. **Sorting:** Sort all voxels based on their computed Morton codes. This can be done using a radix sort or by directly mapping the sorted indices to the linear buffer if the grid is regular and the mapping is bijective.
3. **Storage:** Place the voxel data at the index corresponding to its rank in the sorted Morton order.

**Parameters:**
- **Bit Width:** The number of bits per coordinate dimension. For a $512^3$ grid, 9 bits per dimension are required (since $2^9 = 512$), resulting in a 27-bit Morton code. For larger grids or encrypted data with larger keys, the storage size scales accordingly [S1].
- **Voxel Size:** The size of the data stored per voxel. In the cited example, plaintext is 16-bit, while encrypted data uses 2048-bit keys [S1].

**Edge Cases and Pitfalls:**
- **Precision:** For very large grids, Morton codes may exceed standard integer widths (e.g., 64-bit), requiring arbitrary-precision arithmetic (BigInteger) [S1].
- **Boundary Conditions:** The Morton order assumes a regular, axis-aligned grid. Irregular or sparse grids require additional handling (e.g., brick decomposition) which is outside the scope of the basic Morton layout [S1].

**Pseudocode:**
```python
def compute_morton_code(x, y, z, bits_per_dim):
    """
    Computes the 3D Morton code for coordinates (x, y, z).
    bits_per_dim: number of bits required to represent the max coordinate.
    """
    code = 0
    for i in range(bits_per_dim):
        # Extract i-th bit of x, y, z
        x_bit = (x >> i) & 1
        y_bit = (y >> i) & 1
        z_bit = (z >> i) & 1
        
        # Interleave bits: x at 3i, y at 3i+1, z at 3i+2
        code |= (x_bit << (3 * i))
        code |= (y_bit << (3 * i + 1))
        code |= (z_bit << (3 * i + 2))
    return code

def morton_sort_volume(volume_grid, width, height, depth):
    """
    Reorders a 3D volume grid into Morton order.
    volume_grid: 3D array [x][y][z]
    Returns: 1D array of voxels in Morton order.
    """
    bits_per_dim = width.bit_length() # Assuming power of 2 for simplicity
    
    # Create list of (morton_code, voxel_data)
    voxels = []
    for x in range(width):
        for y in range(height):
            for z in range(depth):
                m_code = compute_morton_code(x, y, z, bits_per_dim)
                voxels.append((m_code, volume_grid[x][y][z]))
    
    # Sort by Morton code
    voxels.sort(key=lambda item: item[0])
    
    # Extract sorted data
    sorted_volume = [voxel for _, voxel in voxels]
    return sorted_volume
```

## Operating characteristics
- **Time Complexity:** Sorting $N$ voxels takes $O(N \log N)$ with comparison-based sorts, or $O(N)$ with radix sort if Morton codes are used as keys. The Morton code computation is $O(\log (\max(W, H, D)))$ per voxel.
- **Memory Complexity:** $O(N)$ for storing the volume data. The Morton codes themselves require additional storage if not computed on the fly, but can be computed during traversal.
- **Performance:** Morton order significantly improves cache hit rates compared to row-major layouts for spatially coherent access patterns [S1]. In the cited encrypted volume rendering context, a $512^3$ grid with 2048-bit keys requires 64GB of storage, fitting into two 48GB GPUs [S1].
- **Scalability:** The approach is highly parallelizable; encryption and decryption can process voxels/pixels independently, scaling linearly with processing power [S1].
- **Limitations:** The naive implementation using BigInteger arrays may incur overhead for large keys. Storage size amplification is significant for encrypted data (e.g., 256x larger than plaintext) [S1].

## Background
The concept of Morton order (Z-order curve) was introduced by Guy M. Morton in 1966 [S1]. It has been widely used in spatial indexing and data compression. In the context of volume rendering, it has been proposed to improve cache usage for encrypted volumes [S1]. The specific application to homomorphic-encrypted volume rendering was detailed by Stuart et al. [S1], who also proposed its use in MapReduce implementations for distributed rendering.
