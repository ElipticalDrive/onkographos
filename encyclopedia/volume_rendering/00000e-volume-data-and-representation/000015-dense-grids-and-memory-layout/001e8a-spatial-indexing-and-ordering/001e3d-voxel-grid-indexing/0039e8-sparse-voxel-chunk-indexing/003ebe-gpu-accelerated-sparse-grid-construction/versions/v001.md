# GPU Accelerated Sparse Grid Construction

Also called: GPU Accelerated IndexGrid Construction, IndexGrid Construction on GPU

## Overview
This method constructs the **IndexGrid** acceleration structure on the GPU from a set of signed voxel coordinates, enabling the handling of large-scale inputs with a competitive memory footprint [S1]. Unlike standard NanoVDB which assumes a fixed topology, this algorithm supports dynamic sparsity patterns, such as those required for Level-of-Detail (LOD) hierarchies [S1]. It serves as the foundational construction step for the IndexGrid data structure used in the fVDB framework [S1].

## How it works
The algorithm builds the hierarchical IndexGrid topology in a top-down manner using parallel sorting and run-length encoding to determine node counts and offsets.

### Inputs and Outputs
*   **Input**: A set of signed voxel coordinates $(i, j, k)$.
*   **Output**: An allocated IndexGrid structure on the GPU device memory, containing upper, lower, and leaf nodes, with active voxels registered in leaf bitmasks.

### Data Structures
The IndexGrid is composed of three node types: Upper, Lower, and Leaf. The construction relies on two primary 64-bit integer keys for sorting and registration.

1.  **Sort Key `a`**: Used to group coordinates by their 12-bit coarse grid position.
    $$ a = (k \gg 12) \mid ((j \gg 12) \ll 21) \mid ((i \gg 12) \ll 42) $$
    *   `i, j, k`: Signed voxel coordinates.
    *   `>> 12`: Right shift by 12 bits extracts the coarse 12-bit index.
    *   `|`: Bitwise OR combines the shifted components.
    *   Layout: Bits [0-20] are zero; Bits [21-41] store $j$'s coarse index; Bits [42-63] store $k$'s coarse index; Bits [0-20] effectively store $i$'s coarse index in the upper bits (specifically bits 42-63). *Note: The formula places $i$ in the highest bits (42-63), $j$ in the middle (21-41), and $k$ in the lowest relevant bits (0-20) of the 64-bit integer.*

2.  **Registration Key `b`**: Used to register nodes and voxels into their parent structures.
    $$ b = (M \ll 36) \mid (\text{upper::off}(i,j,k) \ll 21) \mid (\text{lower::off}(i,j,k) \ll 9) \mid \text{leaf::off}(i,j,k) $$
    *   `M`: A multiplier or mask value (context implies it identifies the run or group, typically derived from the run index).
    *   `upper::off(i,j,k)`: The offset of the upper node.
    *   `lower::off(i,j,k)`: The offset of the lower node.
    *   `leaf::off(i,j,k)`: The offset of the leaf node.
    *   `b & 511`: Extracts the leaf offset (bits 0-8) for bitmask registration.

### Algorithm Steps
1.  **Input**: Receive signed voxel coordinates $(i, j, k)$.
2.  **Key Generation**: For each coordinate, compute the 64-bit sort key $a$ using the formula above.
3.  **Full Radix Sort**: Perform a full radix sort on the array of keys $a$. This groups coordinates that share the same coarse 12-bit grid position.
4.  **Run-Length Encoding (RLE)**: Run-length encode the sorted keys $a$ to identify distinct runs. Each run corresponds to a unique coarse grid cell.
5.  **Registration Key Generation**: For each run $r$ (where $r = 0, 1, \dots$), and for each coordinate $(i, j, k)$ within that run, compute the registration key $b$.
    *   $M$ is typically the run index $r$.
    *   The offsets (`upper::off`, `lower::off`, `leaf::off`) are determined by the hierarchical structure being built. In the context of this algorithm, these offsets are often implicit or calculated based on the position within the run and the global allocation strategy. *Note: The source defines the key structure but implies the offsets are derived from the hierarchical registration process.*
6.  **Partial Radix Sort**: Perform a partial radix sort on the keys $b$ associated with each run. This sorts nodes within each coarse cell.
7.  **Node Counting**:
    *   **Upper Node Count**: Equal to the number of runs identified in Step 4.
    *   **Lower Node Count**: Equal to the number of unique values of $b \gg 21$ (extracting the upper offset).
    *   **Leaf Node Count**: Equal to the number of unique values of $b \gg 9$ (extracting the lower offset).
8.  **Memory Allocation**: Allocate device memory for the IndexGrid arrays (upper, lower, leaf nodes, and leaf bitmasks) using the counts derived in Step 7.
9.  **Top-Down Build**:
    *   **9.1 Register Upper Nodes**: Use the keys $a$ to register upper nodes into the root table.
    *   **9.2 Register Lower Nodes**: Use $b \gg 21$ to register lower nodes into their parent upper nodes.
    *   **9.3 Register Leaf Nodes**: Use $b \gg 9$ to register leaf nodes into their parent lower nodes.
    *   **9.4 Register Active Voxels**: Use $b \& 511$ (the lower 9 bits of $b$) to register active voxels into the `mBitMask` of the corresponding leaf node.
10. **Optional**: Add machine learning features as blind data if required by the application [S1].

### Parameters and Edge Cases
*   **Shift Amounts**: The shift amounts (12, 21, 9) are fixed constants derived from the 12-bit coarse grid resolution and the 9-bit leaf bitmask resolution ($2^9 = 512$).
*   **Precision**: The use of 64-bit integers for keys `a` and `b` ensures that all necessary information (coordinates, offsets, masks) fits without overflow, provided the number of nodes does not exceed $2^{36}$ for the `M` field.
*   **Boundaries**: The algorithm assumes valid signed voxel coordinates. Negative coordinates must be handled correctly by the shift operations (arithmetic vs. logical shift). The source uses `>>`, which is arithmetic in many languages but logical in others; for unsigned 64-bit keys, logical shift is implied to preserve the bit pattern.
*   **Degenerate Input**: If the input is empty, the algorithm should return empty structures. If all coordinates are identical, there will be one run, one upper node, etc.

## Operating characteristics
*   **Time Complexity**: Dominated by the sorting steps. Full radix sort is $O(N \log N)$ or $O(N)$ depending on the radix sort implementation (typically $O(N)$ for fixed-width keys). Partial sorts are proportional to the size of each run.
*   **Memory Complexity**: Proportional to the number of nodes (upper, lower, leaf) and active voxels. The IndexGrid structure is designed for a competitive memory footprint [S1].
*   **Performance**: The method is optimized for GPU execution, leveraging parallel sorting and registration. It enables rapid construction of grids with different topologies, which is crucial for dynamic sparsity patterns [S1].
*   **Strengths**: Supports dynamic sparsity, integrates with deep learning frameworks (PyTorch), and provides fast ray tracing kernels via HDDA [S1].
*   **Limitations**: Requires GPU memory for intermediate sorted arrays. The complexity of the registration step (Step 11) can be non-trivial to implement efficiently without atomic operations or parallel prefix sums.

## Background
The method was introduced as part of the **fVDB** framework, a deep-learning framework for sparse, large-scale, and high-performance spatial intelligence [S1]. It is based on the **IndexGrid** data structure, which is derived from **NanoVDB** [Museth 2021] [S1]. The key innovation is the ability to build IndexGrids on the GPU with dynamic topology, addressing the limitations of fixed-topology structures like standard NanoVDB [S1]. The framework is fully integrated with PyTorch and is used for tasks such as large-scale point-cloud segmentation, 3D generative modeling, and Neural Radiance Fields [S1].
