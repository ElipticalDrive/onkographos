# Coordinate Conversion Utilities

Also called: FVoxelCoordinates, LocalToVoxel, Voxel Chunk Coordinate Conversion, Voxel Coordinate Conversion, VoxelToLocal, voxelVector

## Overview
Coordinate Conversion Utilities provide the mathematical primitives for mapping between world-space positions, global voxel indices, and local chunk-relative coordinates in a voxel grid [S1, S2, unofficial]. They solve the problem of addressing data stored in spatially partitioned chunks by translating continuous world coordinates into discrete integer grid indices [S1, S2, unofficial]. Unlike [Spherical Voxel Grid Setup](3883-spherical-voxel-grid-setup.md) which handles angular domains, or [Incremental Back-Rotation for Voxel Mapping](6759-incremental-back-rotation-for-voxel-mapping.md) which handles orientation, these utilities assume an axis-aligned Cartesian grid [S1, S2, unofficial]. They differ from [Voxel Center Precomputation](10731-voxel-center-precomputation.md) by operating on indices rather than pre-calculated floating-point centers, and from [PixelGrid2D Construction](9430-pixelgrid2d-construction.md) by maintaining 3D spatial hierarchy rather than flattening to 2D [S1, S2, unofficial].

## How it works
The method consists of two primary conversion paths: World-to-Voxel (including chunking) and Local-to-Global. The inputs are a world-space position vector $\mathbf{P}_{world} = (x, y, z)$, a chunk size $C$, and a voxel size $V$. The outputs are global voxel coordinates $\mathbf{I}_{global} = (i, j, k)$, chunk coordinates $\mathbf{C}_{idx} = (c_x, c_y, c_z)$, and local voxel coordinates $\mathbf{L} = (l_x, l_y, l_z)$.

### Data Structures
*   **World Position**: Floating-point vector $(x, y, z)$.
*   **Chunk Size**: Integer $C$ (typically a power of 2, e.g., 16 or 32) [S2, unofficial].
*   **Voxel Size**: Floating-point $V$ (world units per voxel) [S2, unofficial].
*   **Global Voxel Coordinate**: Integer vector $(i, j, k)$ [S2, unofficial].
*   **Local Voxel Coordinate**: Integer vector $(l_x, l_y, l_z)$ within $[0, C-1]$ [S2, unofficial].

### Step 1: World to Global Voxel Coordinates
Convert world position to global voxel index using floor division.
$$ i = \lfloor x / V \rfloor $$
$$ j = \lfloor y / V \rfloor $$
$$ k = \lfloor z / V \rfloor $$
[G] If the world origin is not at $(0,0,0)$, subtract the world origin offset from $x, y, z$ before division.

### Step 2: Global Voxel to Chunk and Local Coordinates
Determine which chunk contains the voxel and the position within that chunk.
$$ c_x = \lfloor i / C \rfloor $$
$$ c_y = \lfloor j / C \rfloor $$
$$ c_z = \lfloor k / C \rfloor $$
$$ l_x = i \pmod C $$
$$ l_y = j \pmod C $$
$$ l_z = k \pmod C $$

**Handling Negative Coordinates**:
In many implementations, the modulo operator returns negative values for negative operands. To ensure local coordinates are always positive (within $[0, C-1]$), apply the following correction [S2, unofficial]:
If $l_x < 0$, then $l_x = l_x + C$.
If $l_y < 0$, then $l_y = l_y + C$.
If $l_z < 0$, then $l_z = l_z + C$.

### Step 3: Local to Global Voxel Coordinates
Reconstruct global coordinates from chunk and local indices.
$$ i = c_x \times C + l_x $$
$$ j = c_y \times C + l_y $$
$$ k = c_z \times C + l_z $$

### Pseudocode
```python
def world_to_global_voxel(world_pos, voxel_size):
    """
    Converts world-space position to global voxel coordinates.
    :param world_pos: tuple (x, y, z)
    :param voxel_size: float
    :return: tuple (i, j, k)
    """
    x, y, z = world_pos
    i = int(x // voxel_size)
    j = int(y // voxel_size)
    k = int(z // voxel_size)
    return (i, j, k)

def global_voxel_to_chunk_and_local(global_voxel, chunk_size):
    """
    Converts global voxel coordinates to chunk index and local voxel coordinates.
    :param global_voxel: tuple (i, j, k)
    :param chunk_size: int
    :return: tuple (chunk_idx, local_voxel)
    """
    i, j, k = global_voxel
    
    # Calculate chunk indices
    cx = i // chunk_size
    cy = j // chunk_size
    cz = k // chunk_size
    
    # Calculate local indices with modulo
    lx = i % chunk_size
    ly = j % chunk_size
    lz = k % chunk_size
    
    # Handle negative modulo results
    if lx < 0:
        lx += chunk_size
    if ly < 0:
        ly += chunk_size
    if lz < 0:
        lz += chunk_size
        
    chunk_idx = (cx, cy, cz)
    local_voxel = (lx, ly, lz)
    
    return chunk_idx, local_voxel

def local_to_global_voxel(chunk_idx, local_voxel, chunk_size):
    """
    Converts chunk index and local voxel coordinates to global voxel coordinates.
    :param chunk_idx: tuple (cx, cy, cz)
    :param local_voxel: tuple (lx, ly, lz)
    :param chunk_size: int
    :return: tuple (i, j, k)
    """
    cx, cy, cz = chunk_idx
    lx, ly, lz = local_voxel
    
    i = cx * chunk_size + lx
    j = cy * chunk_size + ly
    k = cz * chunk_size + lz
    
    return (i, j, k)

def world_to_local_voxel(world_pos, voxel_size, chunk_size):
    """
    Convenience function: World -> Global -> Chunk + Local.
    :param world_pos: tuple (x, y, z)
    :param voxel_size: float
    :param chunk_size: int
    :return: tuple (chunk_idx, local_voxel)
    """
    global_v = world_to_global_voxel(world_pos, voxel_size)
    return global_voxel_to_chunk_and_local(global_v, chunk_size)
```

### Edge Cases and Pitfalls
*   **Negative Coordinates**: Standard integer division and modulo behavior varies by language. In Python, `-5 % 16` is `11`, but in C++/Java, `-5 % 16` is `-5`. The correction step (adding chunk size) is mandatory for C-style languages [S2, unofficial].
*   **Boundary Precision**: Floating-point division can suffer from precision errors near chunk boundaries. Using `floor` or integer division on scaled coordinates is preferred over `round` to avoid jitter [S2, unofficial].
*   **Chunk Size Alignment**: Chunk size $C$ is typically a power of 2 to allow bitwise optimization ($i \& (C-1)$ for modulo, $i >> \log_2 C$ for division) [S2, unofficial].

## Subtopics

### [Sliced Volume Coordinate Mapping](8287-sliced-volume-coordinate-mapping.md)
Sliced Volume Coordinate Mapping converts 3D voxel coordinates into 2D texture coordinates for volumetric data stored as a tiled grid of 2D slices within a single 2D image. It solves the problem of accessing 3D volumetric data in raster-based renderers that lack native 3D texture sampling support by flattening the volume into a 2D layout. It differs from standard 3D texture sampling by requiring explicit coordinate transformation logic to resolve 3D positions to 2D image pixels, and it uses linear interpolation between adjacent slices to reduce banding artifacts compared to nearest-neighbor sampling.

### [Voxel Index Computation](11238-voxel-index-computation.md)
Voxel Index Computation computes discrete voxel indices for a batch of 3D points by mapping their continuous coordinates into a structured grid defined by bounding boxes and voxel dimensions. It differs from [Sliced Volume Coordinate Mapping](8287-sliced-volume-coordinate-mapping.md) by operating on a unified 3D grid structure rather than slicing the volume into 2D planes, making it suitable for dense volumetric queries and ray marching initialization.

### Adaptive Coordinate Conversion
Adaptive Coordinate Conversion is a technique used by Lim et al. to visualize 3D ultrasound datasets, where points within the native pyramidal ultrasound coordinate system were adaptively converted on the fly to a Cartesian grid [S3]. This allows GPU-based raycasting to process non-Cartesian data formats without pre-resampling the entire dataset, adapting the conversion dynamically during rendering [S3].

### Coordinate System Bit Encoding
Coordinate System Bit Encoding defines a `uint32_t` enum with 16 valid values (1-16) representing axis directions for coordinate system alignment [S4, unofficial]. The encoding uses 3 bits for axis direction: Bit 0: Left(0)/Right(1); Bit 1: Down(0)/Up(1); Bit 2: Back(0)/Front(1). Value 0 is UNSPECIFIED. Examples: LDB=1, RDB=2, LUB=3, RUB=4, LDF=5, RDF=6, LUF=7, RUF=8, LFD=9, RFD=10, LFU=11, RFU=12, LBD=13, RBD=14, LBU=15, RBU=16 [S4, unofficial].
*   `axesMatch(a, b)`: Determines if axes align by converting enums to 0-based indices ($aNum = a-1, bNum = b-1$). If either is UNSPECIFIED (<0), returns `{true, true, true}`. Otherwise, compares bit $i$ of $aNum$ and $bNum$ for $i=0,1,2$. Returns a 3-element bool array indicating match per axis [S4, unofficial].
*   `needRotation(a, b)`: Checks if a $\pm \pi/2$ rotation is required by comparing bit 3 of the 0-based indices. If either is UNSPECIFIED, returns false. Otherwise, returns true if bit 3 differs [S4, unofficial].

## Operating characteristics
*   **Time Complexity**: $O(1)$ for single coordinate conversion. The operations involve basic arithmetic (division, modulo, multiplication, addition) [S2, unofficial].
*   **Memory Complexity**: $O(1)$ auxiliary space. No additional data structures are required for the conversion itself [S2, unofficial].
*   **Performance**: Highly efficient on modern CPUs and GPUs. Bitwise operations can replace division/modulo if chunk size is a power of 2 [S2, unofficial].
*   **Strengths**: Simple, deterministic, and fast. Essential for sparse voxel octrees and chunk-based world generation [S1, S2, unofficial].
*   **Limitations**: Assumes axis-aligned grids. Does not handle rotation or non-Cartesian coordinate systems without additional transformation matrices [S3][S4, unofficial].
*   **When to use**: When accessing voxel data in chunked grids, determining chunk ownership, or mapping world positions to grid indices [S1, S2, unofficial].
*   **When not to use**: For spherical voxel grids, rotated coordinate systems, or non-uniform voxel sizes [S3883, S6759, unofficial].

## Background
Coordinate conversion utilities are fundamental to voxel-based game engines and volumetric rendering systems. Early implementations in voxel engines like `voxel-engine-stackgl` used simple modulo arithmetic for chunking [S1, unofficial]. In larger-scale procedural generation systems like `VoxelWorlds`, these utilities are extended to handle biome caching and GPU data preparation, ensuring that world-to-voxel mappings are consistent across CPU and GPU paths [S2, unofficial]. In medical visualization, adaptive coordinate conversion was introduced by Lim et al. to handle pyramidal ultrasound data, demonstrating the need for flexible coordinate transformations beyond simple Cartesian grids [S3]. The bit-encoding scheme for coordinate systems, as seen in `nianticlabs/spz`, provides a compact way to handle axis alignment in file formats and rendering pipelines [S4, unofficial].
