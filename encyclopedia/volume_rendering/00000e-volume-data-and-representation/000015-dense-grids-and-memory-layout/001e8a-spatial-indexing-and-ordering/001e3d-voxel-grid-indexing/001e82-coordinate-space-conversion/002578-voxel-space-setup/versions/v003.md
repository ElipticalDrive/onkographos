# Voxel Space Setup

Also called: AABB to Voxel Grid Mapping, SetupVoxelization

## Overview
Voxel Space Setup computes the bounding box and transformation matrices required to map world-space coordinates to voxel grid indices, handling padding and cube voxel normalization [S1, unofficial]. It solves the problem of establishing a consistent coordinate system for rasterization-based voxelization, ensuring that geometry is correctly mapped into a discrete grid structure [S1, unofficial]. It differs from [Spherical Voxel Grid Setup](3883-spherical-voxel-grid-setup.md) by operating in a Cartesian coordinate system tailored for axis-aligned bounding boxes, and from [Coordinate Conversion Utilities](6766-coordinate-conversion-utilities.md) by generating the initial global transformation matrices rather than performing per-voxel arithmetic lookups.

## How it works
**Inputs:**
- Axis-Aligned Bounding Box (AABB) of the model: `g_aabbModel[0]` (min) and `g_aabbModel[1]` (max), stored as 3D vectors.
- Grid dimensions: `g_gridSizeX`, `g_gridSizeY`, `g_gridSizeZ` (integers).
- Boolean flag: `g_useCubeVoxels` (enforces uniform voxel dimensions).

**Outputs:**
- `g_voxelSpace[0]` and `g_voxelSpace[1]`: The minimum and maximum coordinates of the voxel space in world units.
- `g_matWorldToVoxel`: A 4x4 matrix transforming world coordinates to voxel indices.
- `g_matWorldToVoxelProj`: A 4x4 matrix transforming world coordinates to Normalized Device Coordinates (NDC) for rasterization.
- `g_strideX`, `g_strideY`, `g_dataSize`: Memory layout strides for the voxel buffer.

**Data Structures:**
The voxel data is stored in a linear buffer. The layout is defined by strides calculated to pad the Z-dimension to 32-bit word boundaries for memory alignment.
- `g_strideX`: Number of 32-bit words per voxel in the X dimension. Calculated as `(g_gridSizeZ + 31) / 32`.
- `g_strideY`: Number of 32-bit words per voxel in the Y dimension. Calculated as `g_strideX * g_gridSizeX`.
- `g_dataSize`: Total size in words. Calculated as `g_strideY * g_gridSizeY`.

**Steps:**
1.  **Calculate Strides:** Compute `g_strideX` by dividing `g_gridSizeZ` by 32 and rounding up. Compute `g_strideY` by multiplying `g_strideX` by `g_gridSizeX`. Compute `g_dataSize` by multiplying `g_strideY` by `g_gridSizeY` [S1, unofficial].
2.  **Compute Model Extent:** Calculate the extent vector by subtracting the AABB min from the AABB max: `extent = g_aabbModel[1] - g_aabbModel[0]` [S1, unofficial].
3.  **Apply Padding:** Scale the extent by a factor that adds 2 units of padding to the grid. The scaling factor is `(gridSize + 2) / gridSize` for each axis, where `gridSize` is a vector of the grid dimensions [S1, unofficial].
    $$ \text{extent} = \text{extent} \times \frac{\text{gridSize} + 2}{\text{gridSize}} $$
4.  **Enforce Cube Voxels (Optional):** If `g_useCubeVoxels` is true, replace the extent components with the maximum of the X, Y, and Z components, making the voxel dimensions uniform across all axes [S1, unofficial].
5.  **Compute Center:** Calculate the center of the original AABB: `center = 0.5 * (g_aabbModel[0] + g_aabbModel[1])` [S1, unofficial].
6.  **Compute Voxel Space Min:** Calculate the minimum coordinate of the voxel space in world units:
    $$ \text{voxelSpaceMin} = \text{center} - 0.5 \times \text{extent} $$
7.  **Store Bounds:** Store `voxelSpaceMin` as `g_voxelSpace[0]` and `voxelSpaceMin + extent` as `g_voxelSpace[1]` [S1, unofficial].
8.  **Compute World-to-Voxel Matrix:** Construct `g_matWorldToVoxel` by translating by `-voxelSpaceMin` and scaling by `gridSize / extent`. The matrix is transposed for column-major storage [S1, unofficial].
    $$ \text{g\_matWorldToVoxel} = \text{Translate}(-\text{voxelSpaceMin}) \times \text{Scale}\left(\frac{\text{gridSize}}{\text{extent}}\right) $$
9.  **Compute World-to-Projection Matrix:** Construct `g_matWorldToVoxelProj` for rasterization. Translate by `(-center.x, -center.y, -voxelSpaceMin.z)` and scale by `(2.0/extent.x, 2.0/extent.y, 1.0/extent.z, 0.0)`. The matrix is transposed [S1, unofficial].
    $$ \text{g\_matWorldToVoxelProj} = \text{Translate}(-\text{center}.x, -\text{center}.y, -\text{voxelSpaceMin}.z) \times \text{Scale}\left(\frac{2.0}{\text{extent}.x}, \frac{2.0}{\text{extent}.y}, \frac{1.0}{\text{extent}.z}, 0.0\right) $$

**Pseudocode:**
```python
def setup_voxelization(aabb_min, aabb_max, grid_size_x, grid_size_y, grid_size_z, use_cube_voxels):
    # 1. Calculate Strides
    # Pad Z stride to 32-bit words
    stride_x = (grid_size_z + 31) // 32
    stride_y = stride_x * grid_size_x
    data_size = stride_y * grid_size_y

    # 2. Compute Model Extent
    extent_x = aabb_max[0] - aabb_min[0]
    extent_y = aabb_max[1] - aabb_min[1]
    extent_z = aabb_max[2] - aabb_min[2]

    # 3. Apply Padding
    # Scale extent by (gridSize + 2) / gridSize
    scale_x = (grid_size_x + 2.0) / grid_size_x
    scale_y = (grid_size_y + 2.0) / grid_size_y
    scale_z = (grid_size_z + 2.0) / grid_size_z
    
    extent_x *= scale_x
    extent_y *= scale_y
    extent_z *= scale_z

    # 4. Enforce Cube Voxels
    if use_cube_voxels:
        max_extent = max(extent_x, max(extent_y, extent_z))
        extent_x = max_extent
        extent_y = max_extent
        extent_z = max_extent

    # 5. Compute Center
    center_x = 0.5 * (aabb_min[0] + aabb_max[0])
    center_y = 0.5 * (aabb_min[1] + aabb_max[1])
    center_z = 0.5 * (aabb_min[2] + aabb_max[2])

    # 6. Compute Voxel Space Min
    voxel_space_min_x = center_x - 0.5 * extent_x
    voxel_space_min_y = center_y - 0.5 * extent_y
    voxel_space_min_z = center_z - 0.5 * extent_z

    # 7. Store Bounds
    voxel_space_min = [voxel_space_min_x, voxel_space_min_y, voxel_space_min_z]
    voxel_space_max = [
        voxel_space_min_x + extent_x,
        voxel_space_min_y + extent_y,
        voxel_space_min_z + extent_z
    ]

    # 8. Compute World-to-Voxel Matrix
    # Translate by -voxelSpaceMin
    # Scale by gridSize / extent
    # Note: Matrix multiplication order in source is Translate * Scale, then transposed.
    # We construct the 4x4 matrix explicitly.
    mat_world_to_voxel = identity_matrix()
    
    # Translation part
    mat_world_to_voxel[3][0] = -voxel_space_min_x
    mat_world_to_voxel[3][1] = -voxel_space_min_y
    mat_world_to_voxel[3][2] = -voxel_space_min_z
    
    # Scale part (applied before translation in the source's vector math, 
    # but source says Translate * Scale. In column-major, M*v = T*(S*v).
    # So Scale is applied first, then Translation.
    # The source code: XMMatrixMultiplyTranspose(Translate, Scale)
    # This results in a matrix where the upper 3x3 is Scale, and the translation column is -Scale * voxelSpaceMin?
    # Let's look at the source: XMMatrixTranslationFromVector(-voxelSpaceMin) * XMMatrixScalingFromVector(gridSize / extent)
    # Matrix multiplication A * B applies B first, then A.
    # So Scale is applied first, then Translation.
    # Translation vector in the resulting matrix is -voxelSpaceMin.
    # Wait, standard affine matrix: [S 0; T 1].
    # T * S = [I 0; T 1] * [S 0; 0 1] = [S 0; T 1].
    # So the translation component is just -voxelSpaceMin.
    # However, the source stores it as g_matWorldToVoxel.
    
    # Let's re-read carefully: XMMatrixMultiplyTranspose(Translate(-voxelSpaceMin), Scale(gridSize/extent))
    # This computes (Translate * Scale)^T.
    # Translate * Scale = [ S  0 ]
    #                     [ T  1 ] where T = -voxelSpaceMin.
    # Transpose = [ S^T T^T ]
    #             [ 0   1   ]
    # Since S is diagonal, S^T = S.
    # So the matrix is:
    # [ sx  0   0  tx ]
    # [ 0   sy  0  ty ]
    # [ 0   0   sz  tz ]
    # [ 0   0   0   1  ]
    # where tx = -voxelSpaceMin.x, etc.
    
    mat_world_to_voxel[0][0] = grid_size_x / extent_x
    mat_world_to_voxel[1][1] = grid_size_y / extent_y
    mat_world_to_voxel[2][2] = grid_size_z / extent_z
    mat_world_to_voxel[3][0] = -voxel_space_min_x
    mat_world_to_voxel[3][1] = -voxel_space_min_y
    mat_world_to_voxel[3][2] = -voxel_space_min_z

    # 9. Compute World-to-Projection Matrix
    # Translate by (-center.x, -center.y, -voxelSpaceMin.z)
    # Scale by (2.0/extent.x, 2.0/extent.y, 1.0/extent.z, 0.0)
    # Note: The 4th component of scale is 0.0, which implies the W component is not scaled, 
    # but the translation in Z uses voxelSpaceMin.z, not center.z.
    
    proj_scale_x = 2.0 / extent_x
    proj_scale_y = 2.0 / extent_y
    proj_scale_z = 1.0 / extent_z
    
    mat_world_to_voxel_proj = identity_matrix()
    
    mat_world_to_voxel_proj[0][0] = proj_scale_x
    mat_world_to_voxel_proj[1][1] = proj_scale_y
    mat_world_to_voxel_proj[2][2] = proj_scale_z
    mat_world_to_voxel_proj[3][0] = -center_x
    mat_world_to_voxel_proj[3][1] = -center_y
    mat_world_to_voxel_proj[3][2] = -voxel_space_min_z

    return {
        "stride_x": stride_x,
        "stride_y": stride_y,
        "data_size": data_size,
        "voxel_space_min": voxel_space_min,
        "voxel_space_max": voxel_space_max,
        "mat_world_to_voxel": mat_world_to_voxel,
        "mat_world_to_voxel_proj": mat_world_to_voxel_proj
    }
```

**Parameters:**
- `g_useCubeVoxels`: Boolean flag. When true, ensures voxels are cubic by using the maximum dimension of the padded AABB for all axes [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Boundary Misses:** A grid padding of 2 units is added to the extent to prevent edge cases where triangles exactly on the boundary are missed [S1, unofficial].
- **Precision:** The calculation relies on floating-point arithmetic for the transformation matrices. Ensure that the grid size and extent are compatible to avoid overflow or underflow in the scaling factors.

## Subtopics

### [Spherical Voxel Grid Setup](3883-spherical-voxel-grid-setup.md)
Spherical Voxel Grid Setup initializes the data structures required for efficient ray casting traversal within a spherical coordinate volume. It computes discretization steps, precomputes trigonometric values, and constructs geometric primitives (line segments) that define voxel boundaries, enabling the `walkSphericalVolume` algorithm to determine ray-voxel intersections. It differs from Cartesian voxel grid setups by operating in an $(r, \theta, \phi)$ coordinate system tailored for egocentric view synthesis, where resolution requirements are anisotropic and radial distances vary significantly. Choose this when rendering spherical volumes or egocentric views. Link: [Spherical Voxel Grid Setup](3883-spherical-voxel-grid-setup.md).

### [Coordinate Conversion Utilities](6766-coordinate-conversion-utilities.md)
Coordinate Conversion Utilities provide the arithmetic mapping between world-space positions, global voxel indices, chunk indices, and local voxel positions within a chunk. They solve the problem of addressing data in a sparse or dense voxel grid that is partitioned into fixed-size chunks, ensuring that coordinates wrap correctly across chunk boundaries and negative indices are handled consistently. Unlike [Spherical Voxel Grid Setup](3883-spherical-voxel-grid-setup.md), which handles angular discretization, these utilities operate on Cartesian grid topology. Choose this for chunked voxel grid implementations. Link: [Coordinate Conversion Utilities](6766-coordinate-conversion-utilities.md).

### OpenVDB Density Grid Loading
Loads a heterogeneous density field from an OpenVDB file to provide spatial density queries for participating media [S2, unofficial]. It computes the AABB from the active voxel bounding box using `gridPtr->evalActiveVoxelBoundingBox()` and converts indices to world coordinates. Density at a position is interpolated using `openvdb::tools::GridSampler` with `openvdb::tools::BoxSampler`. The maximum density is retrieved via `gridPtr->evalMinMax(minValue, maxValue)` [S2, unofficial]. Choose this when integrating OpenVDB-based density fields into a path tracer.

### Ray Tracing Volume Data Setup
Typical simplifications include an integral mapping of voxel address space to pixel address space (1-1 is easiest; usually projection of a voxel map to $k \times k$ pixels), where arbitrary mapping requires interpolation [S3, unofficial]. The sampling lattice is rectilinear and uniformly spaced [S3, unofficial]. Pixel spacing must be less than voxel spacing [S3, unofficial]. The setup assumes one ray per pixel (no supersampling) and parallel projection [S3, unofficial]. Choose this for simple direct volume rendering with parallel projection.

### Incremental Back-Rotation for Voxel Mapping
An algorithm to determine the source voxel position for a destination voxel during room rotation, used to eradicate holes produced by forward rotation [S4]. It rotates the eight corners of the source room to locate the destination room, calculates the minimum coordinates of the destination room, and back-rotates them using the rotation equation by replacing $\theta$ with $-\theta$. An incremental procedure back-scans the entire room using constant increments of $\sin(\theta)$ and $\cos(\theta)$ for all voxels/beams [S4].
Formulas:
$$ X_{src} = (X_{dest} + 1) \cos(\theta) + Y_{dest} \sin(\theta) $$
$$ Y_{src} = -(X_{dest} + 1) \sin(\theta) + Y_{dest} \cos(\theta) $$
$$ X_{src} = X_{dest} \cos(\theta) + (Y_{dest} + 1) \sin(\theta) $$
$$ Y_{src} = -X_{dest} \sin(\theta) + (Y_{dest} + 1) \cos(\theta) $$
Pitfalls: Holes can be produced from forward rotation; back-rotation solves this by mapping destination voxels to source voxels [S4]. The overlap problem is overcome by starting the scan at the source vertex which is also located within the destination room [S4]. Complexity: The coordinate calculation employs only two fixed-point additions that can be performed in parallel [S4]. Choose this for rotating voxel rooms without holes.

## Operating characteristics
**Time Complexity:** The setup process is $O(1)$ with respect to the number of voxels, as it involves a fixed number of arithmetic operations on the bounding box and grid dimensions. The stride calculation is also $O(1)$.

**Memory Complexity:** The memory required for the voxel grid is proportional to the product of the grid dimensions: $O(\text{gridSizeX} \times \text{gridSizeY} \times \text{gridSizeZ})$. The strides ensure memory alignment, which may increase the memory footprint slightly due to padding.

**Measured Performance:** Not given in the sources.

**Scaling:** The method scales linearly with the grid dimensions. The padding and cube voxel enforcement add constant overhead.

**Strengths:**
- Ensures correct mapping of world geometry to voxel indices.
- Handles padding to prevent boundary artifacts.
- Supports uniform voxel sizes for consistent sampling.

**Limitations:**
- Limited to Cartesian coordinate systems.
- Does not handle sparse data structures natively (requires chunking utilities).
- Rasterization-based voxelization may suffer from aliasing if not supersampled.

**When to use:** Use this method when setting up a dense voxel grid for rasterization-based voxelization in a Cartesian coordinate system.

**When not to use:** Do not use this for spherical volumes, sparse voxel octrees, or OpenVDB-based density fields. Use [Spherical Voxel Grid Setup](3883-spherical-voxel-grid-setup.md) or [OpenVDB Density Grid Loading](#openvdb-density-grid-loading) instead.

## Background
The method originates from GPU Pro 3, specifically the chapter on voxelization [S1, unofficial]. It is used in real-time rendering pipelines to convert 3D geometry into a voxel representation for subsequent processing, such as global illumination or shadow mapping. The approach emphasizes memory alignment and boundary handling to ensure robustness in hardware rasterization.
