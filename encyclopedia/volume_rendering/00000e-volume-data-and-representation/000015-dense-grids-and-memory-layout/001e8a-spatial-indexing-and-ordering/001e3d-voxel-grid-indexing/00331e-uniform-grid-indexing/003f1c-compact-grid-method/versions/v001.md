# Compact Grid Method
Also called: Static Grid Acceleration Structure

## Overview
The Compact Grid Method is a static data structure for representing a uniform grid acceleration structure with minimal memory requirements: exactly one index per grid cell and exactly one index per object reference, built in linear time [S1]. It solves the problem of efficiently mapping objects to grid cells for ray tracing without the memory overhead of linked lists or dynamic arrays [S1]. It sets itself apart from its siblings by using a two-pass counting-sort-like algorithm to pack object indices into a single contiguous array, managed by a cell offset array that defines list boundaries implicitly, avoiding null pointers or extra tracking arrays [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of $N$ objects (e.g., triangles), each with a bounding box.
*   **Output:** Two static arrays:
    1.  $L$: A 1D array of object indices, containing the concatenated object lists for all non-empty cells.
    2.  $C$: A 1D array of size $M+1$ (where $M$ is the total number of cells), storing the offsets into $L$.

**Data Structures:**
*   **Array $L$:** Stores object indices. Uses 32-bit unsigned integers. Size equals the total number of object-cell overlaps.
*   **Array $C$:** Stores cell offsets. Uses 32-bit unsigned integers. Size is $M+1$. Linearized from a 3D grid of resolution $M_x \times M_y \times M_z$.
*   **Memory Layout:** The 3D cell $(z, y, x)$ maps to 1D index $i$ in $C$ via:
    $$C[z][y][x] = C[((M_y z) + y)M_x] + x$$
    [S1]

**Algorithm Steps:**

1.  **Compute Bounding Box and Resolution:**
    Compute the bounding box of all objects. Determine the grid resolution $M_i$ for each dimension $i \in \{x, y, z\}$ using:
    $$M_i = S_i \sqrt{\frac{\rho N}{V}}$$
    where $S_i$ is the size of the bounding box in dimension $i$, $V$ is the volume of the bounding box, and $\rho$ is the grid density [S1].
    *   **Parameter $\rho$:** Grid density, ratio of cells to objects ($M = \rho N$). Typical value: 4 [S1]. (Note: Literature varies from 2 to 10; 4 is used in the primary source based on minimizing time to image [S1]).

2.  **Initialize and Count:**
    Allocate array $C$ of size $M+1$ and initialize all entries to zero.
    Iterate over all objects $i$ from $0$ to $N-1$. For each object, determine all cells $j$ it overlaps. For each such cell, increment $C[j]$.
    After this pass, $C[j]$ holds the number of objects overlapping cell $j$ [S1].

3.  **Compute Offsets (Cumulative Sum):**
    Compute cumulative sums in $C$ to determine list boundaries. Iterate $i$ from $1$ to $M$:
    $$C[i] += C[i-1]$$
    After this pass, $C[i]$ records the offset of the object list for cell with 1D index $i+1$ (i.e., one past the end of cell $i$'s list). The joint size of all object lists is $C[M-1]$ (which is now stored in $C[M-1]$ before the final increment logic, but effectively the total count is $C[M-1]$ if we consider the pre-increment state, or more precisely, the total number of entries is $C[M-1]$ after step 2, and $C[M]$ after step 3 holds the total count plus the padding [S1]).
    *   *Correction based on source:* The source states "Joint size of object lists is $C[M-1]$" after the cumulative sum if we consider the standard prefix sum behavior where $C[i]$ becomes the start of the *next* block. Let's follow the source's specific indexing: "C[i] records the offset of the object list of the cell with 1D index i+1". So $C[0]$ is start of cell 1, $C[1]$ is start of cell 2... $C[M-1]$ is start of cell $M$. $C[M]$ is one past the end of cell $M$. The total size is $C[M]$ [S1].

4.  **Allocate and Insert:**
    Allocate array $L$ of size $C[M]$ (the total number of object references).
    Iterate over objects in **reverse order** ($i$ from $N-1$ down to $0$).
    For each object $i$, iterate over all cells $j$ it overlaps.
    Decrement $C[j]$ and store object index $i$ at $L[C[j]]$.
    $$L[--C[j]] = i$$
    [S1]

    *   **Result:** The indices in each object list are sorted by object index due to the reverse iteration order [S1].

**Pseudocode:**

```python
def build_compact_grid(objects, grid_density=4):
    N = len(objects)
    
    # Step 1: Compute bounding box and resolution
    bbox_min, bbox_max = compute_global_bounding_box(objects)
    S_x = bbox_max.x - bbox_min.x
    S_y = bbox_max.y - bbox_min.y
    S_z = bbox_max.z - bbox_min.z
    V = S_x * S_y * S_z
    
    # Calculate resolutions
    # M_i = S_i * sqrt((rho * N) / V)
    M_x = int(round(S_x * ((grid_density * N) / V) ** 0.5))
    M_y = int(round(S_y * ((grid_density * N) / V) ** 0.5))
    M_z = int(round(S_z * ((grid_density * N) / V) ** 0.5))
    
    M = M_x * M_y * M_z
    
    # Step 2: Initialize C and count overlaps
    # C has size M + 1
    C = [0] * (M + 1)
    
    for obj_idx, obj in enumerate(objects):
        cells = get_overlapping_cells(obj, bbox_min, bbox_max, M_x, M_y, M_z)
        for cell_idx in cells:
            C[cell_idx] += 1
            
    # Step 3: Cumulative sum
    # C[i] becomes the start offset for cell i+1
    # C[0] is start for cell 1
    # C[M-1] is start for cell M
    # C[M] is one past end of cell M
    for i in range(1, M + 1):
        C[i] += C[i-1]
        
    total_objects = C[M]
    
    # Step 4: Allocate L and insert in reverse
    L = [0] * total_objects
    
    for obj_idx in range(N - 1, -1, -1):
        obj = objects[obj_idx]
        cells = get_overlapping_cells(obj, bbox_min, bbox_max, M_x, M_y, M_z)
        for cell_idx in cells:
            C[cell_idx] -= 1
            L[C[cell_idx]] = obj_idx
            
    return L, C, M_x, M_y, M_z

    max_y = min(M_y - 1, int((obj.bbox_max.y - bbox_min.y) / (bbox_max.y - bbox_min.y) * M_y))
    min_z = max(0, int((obj.bbox_min.z - bbox_min.z) / (bbox_max.z - bbox_min.z) * M_z))
    max_z = min(M_z - 1, int((obj.bbox_max.z - bbox_min.z) / (bbox_max.z - bbox_min.z) * M_z))
    
    cells = []
```

**Edge Cases and Pitfalls:**
*   **Last Cell Offset:** The size of the object list for cell with 1D index $i$ is $C[i+1] - C[i]$. This expression is invalid for the last cell ($i=M-1$) because $C[M]$ would be out of bounds if $C$ were size $M$. The array $C$ is explicitly extended to size $M+1$ to handle this [S1].
*   **Precision:** Grid resolution calculation involves floating-point square roots and rounding. [G] Ensure integer conversion handles rounding consistently (e.g., `round` vs `floor`) to avoid off-by-one errors in cell mapping.
*   **Object Count:** Array $L$ uses 32-bit unsigned integers, sufficient for over 4 billion objects [S1].

## Operating characteristics
*   **Time Complexity:** Linear in the number of objects $N$ and total cell overlaps [S1]. Build time is very fast (e.g., 0.00 s for 'Ulm' scene, 0.08 s for 'Atrium' scene [S1]).
*   **Memory Complexity:** Linear in the number of objects. Exactly one machine word per cell and one machine word per object reference [S1].
*   **Measured Performance:**
    *   'Ulm' scene: Cell memory 8.58 Kb, triangle list memory 14.30 Kb, total memory 22.88 Kb [S1].
    *   'Atrium' scene: Cell memory 8.51 MB, triangle list memory 6.64 MB, total memory 15.14 MB [S1].
    *   Memory footprint is roughly three quarters of the scene memory size [S1].
*   **Strengths:** Minimal memory overhead compared to linked lists (2-3 words per object reference) and dynamic arrays (3 words per cell + unused entries) [S1]. No null pointers or extra tracking arrays [S1].
*   **Limitations:** Static structure; objects cannot be inserted or removed after build [S1]. Requires rebuilding from scratch for dynamic scenes, which may be costly if done every frame [S1]. Larger memory footprint than the Hashed Grid Method [S1].
*   **When to Use:** Applications where time to image or memory usage is critical, and the scene is static or rebuilt infrequently [S1].
*   **When Not to Use:** Highly dynamic scenes requiring frequent updates, or when memory is extremely constrained and the Hashed Grid Method is viable [S1].

## Background
The Compact Grid Method was presented in the paper "Compact, Fast and Robust Grids for Ray Tracing" [S1]. The idea of two passes over triangles is traced to Eric Haines [Hai99]. The specific compact implementation is attributed to the authors of [S1], though similar concepts exist in [WIK*06] and [ISP07] tracing back to Steven Parker [S1]. It is algorithmically similar to counting sort [S1].
