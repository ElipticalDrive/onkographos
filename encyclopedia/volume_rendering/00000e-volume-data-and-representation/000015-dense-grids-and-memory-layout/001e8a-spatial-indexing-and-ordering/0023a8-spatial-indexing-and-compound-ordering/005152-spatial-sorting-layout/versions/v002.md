# Spatial Sorting Layout

Also called: Directional sort, Spatial layout

## Overview
Spatial sorting is a memory layout technique for tetrahedral meshes that orders vertices along a dominant spatial direction to maximize cache coherence during streaming rendering [S1]. It solves the problem of poor spatial locality in unstructured grids by ensuring that cells sharing vertices are stored contiguously in memory [S1]. Unlike general spatial indexing, it relies on a single global sorting direction, making it highly efficient for meshes with anisotropic geometry but ineffective for isotropic shapes like spheres [S1].

## How it works
**Inputs:** A tetrahedral mesh defined by a vertex list and a cell list (tetrahedra defined by 4 vertex indices).
**Outputs:** A new interleaved file/stream containing vertices and their associated cells in spatial order.

**Data Structures:**
1.  **Vertex List:** Array of vertex positions.
2.  **Mapping File:** A lookup table mapping old vertex indices to new vertex indices.
3.  **Cell List:** Array of tetrahedra, each storing 4 vertex indices.

**Steps:**
1.  **Select Direction:** Identify a spatial direction vector that intersects the maximum number of tetrahedra in the mesh [S1].
2.  **Sort Vertices:** Perform an out-of-core sort of the vertices based on their projection onto the selected direction [S1].
3.  **Create Mapping:** Generate a mapping file that records the permutation from the original vertex indices to the new sorted indices [S1].
4.  **Reindex Cells:** Write the tetrahedral cells to a new file, updating all vertex indices according to the mapping file [S1].
5.  **Sort Cells:** Sort the reindexed cell file based on the largest vertex index contained within each tetrahedron [S1].
6.  **Interleave:** Read the sorted vertex file and sorted cell file simultaneously. Write each cell to the output file immediately after the vertex corresponding to the cell’s largest index has been written [S1].

**Pseudocode:**
```python
# Step 1: Select direction (implementation detail omitted, assumed known)
direction = find_dominant_direction(mesh.vertices)

# Step 2: Sort vertices
# Project vertices onto direction and sort
vertex_projections = [dot(v.position, direction) for v in mesh.vertices]
sorted_indices = argsort(vertex_projections)

# Step 3: Create mapping
mapping = [0] * len(mesh.vertices)
for new_idx, old_idx in enumerate(sorted_indices):
    mapping[old_idx] = new_idx
    # Store mapping to file
    write_mapping_file(new_idx, old_idx)

# Step 4: Reindex cells
new_cells = []
for cell in mesh.cells:
    # cell is a tuple/list of 4 old indices
    new_cell_indices = [mapping[old_idx] for old_idx in cell]
    new_cells.append(new_cell_indices)

# Step 5: Sort cells by max index
# Sort the new_cells list based on the maximum value in each cell
sorted_cells = sorted(new_cells, key=lambda cell: max(cell))

# Step 6: Interleave
output_file = open("interleaved.dat", "wb")
# We need to access vertices in the new sorted order
sorted_vertices = [mesh.vertices[i] for i in sorted_indices]

# Map max_cell_index to the position in the sorted_vertices list
# Since sorted_cells contains indices into the NEW vertex list,
# and sorted_vertices is ordered by the NEW indices,
# we can iterate through sorted_vertices and append cells.

# However, the source says: "writing each cell immediately after the vertex 
# corresponding to the cell’s largest index has been written."
# This implies we iterate through the sorted vertices, and for each vertex,
# we check if it is the max index of any cell.

# To do this efficiently, we can group cells by their max index.
cells_by_max_index = {}
for cell in sorted_cells:
    max_idx = max(cell)
    if max_idx not in cells_by_max_index:
        cells_by_max_index[max_idx] = []
    cells_by_max_index[max_idx].append(cell)

for new_vertex_idx, vertex in enumerate(sorted_vertices):
    write_vertex(output_file, vertex)
    if new_vertex_idx in cells_by_max_index:
        for cell in cells_by_max_index[new_vertex_idx]:
            write_cell(output_file, cell)
```

**Parameters:**
*   **Sorting Direction:** Not given in the sources.
*   **Out-of-core Sort:** Required for large meshes [S1].

**Edge Cases and Pitfalls:**
*   **Isotropic Meshes:** The method works especially well only for meshes with a dominant principal direction [S1]. It performs poorly on meshes without such a direction, such as spheres [S1].

## Subtopics

### Density-sorted point storage
Storing points sorted by density results in the least spatial coherence among point-based layouts [S2, book]. Points are sorted by their density value, allowing irrelevant points (assigned transparent values in transfer functions) to be quickly culled from the rendering pipeline [S2, book]. This approach requires storing $(x,y,z)$ coordinates and possibly gradient vectors alongside the points because neighborhood relations are completely lost [S2, book]. All points must be transformed to view space before culling for occlusion or viewing pyramid exclusion [S2, book]. During rendering, points must be depth-sorted or tossed into depth bins [S2, book]. A compromise involves sorting points by density within volume slices only, providing implicit depth-ordering when used with an axis-aligned sheet-buffer method [S2, book].

## Operating characteristics
**Time Complexity:** Dominated by the out-of-core sorting of vertices and cells [S1].
**Memory Complexity:** Requires storage for the vertex list, cell list, and a mapping file [S1].
**Strengths:** Maximizes spatial coherence for streaming rendering on meshes with a dominant direction [S1].
**Limitations:** Ineffective for isotropic meshes (e.g., spheres) [S1]. Loses neighborhood information if applied to points rather than meshes [S2, book].
**When to use:** When rendering large tetrahedral meshes with a clear principal direction and limited memory bandwidth.
**When not to use:** For isotropic meshes or when neighborhood relations are critical for other algorithms [S1][S2, book].

## Background
The technique was proposed for streaming simplification of tetrahedral meshes, building on work by Wu and Kobbelt for triangle mesh simplification [S1]. It addresses the need for efficient memory access patterns in large-scale volume rendering.
