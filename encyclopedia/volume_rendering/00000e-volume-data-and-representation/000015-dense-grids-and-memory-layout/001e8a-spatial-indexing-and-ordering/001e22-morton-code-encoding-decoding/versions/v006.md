# Morton Code Encoding/Decoding

Also called: MSFC, Morton Coordinate Construction, Morton Order, Morton Order Indexing, Z-order, Z-order curve, Z-order curve encoding, Z-order encoding

## Overview
Morton Code Encoding/Decoding is a method to rearrange pixels or voxels from an $N$-dimensional regular grid into a linear 1D form using the Morton Space Filling Curve (MSFC), also known as the Z-order curve [S1][S3, unofficial][S8]. It maps $N$-dimensional coordinates $(x, y, z)$ into a single integer index such that points close in Euclidean distance have close indices, thereby preserving spatial locality in linear memory [S1][S5, S9, unofficial]. This method sets itself apart from simple row-major linearization by using bit-interleaving rather than arithmetic strides, which minimizes the distance between indices of spatially neighboring voxels more effectively [S1, S8]. It builds on [Spatial Indexing and Ordering](1797-spatial-indexing-and-ordering.md).

## How it works
**Inputs and Outputs:**
*   **Encoding:** Input is a set of $N$-dimensional integer coordinates (typically 3D: $x, y, z$). Output is a 1D Morton code (integer index).
*   **Decoding:** Input is a 1D Morton code. Output is the corresponding $N$-dimensional integer coordinates.

**Data Structures:**
*   **Coordinates:** Integer arrays/tensors. For 3D, typically `int32` with values in $[0, 128)$ or similar bounds depending on grid size [S2, S7, unofficial].
*   **Morton Code:** Unsigned integer. For 3D coordinates with up to 21 bits each, a 64-bit unsigned integer (`uint64_t`) is used [S9, unofficial]. The range is $[0, 2^{3m}-1]$ for an $N \times N \times N$ grid where $N=2^m$ [S1].
*   **Lookup Table (Optional):** A flat array of size `dimensions * tableSize` storing precomputed interleaved bits for each coordinate value [S5, unofficial].
*   **Magic Bits (Optional):** An array of `uint64` values used for fast decoding via bitwise operations [S5, unofficial].

**Numbered Steps:**

1.  **Initialization (Optional for Lookup/Magic Methods):**
    *   If using lookup tables, allocate `Table` of size `dimensions * tableSize`.
    *   If using magic bits, generate `Magic` array based on dimension count [S5, unofficial].

2.  **Encoding (Bit Interleaving):**
    *   For each bit position $i$ from 0 to $m-1$ (where $m$ is the number of bits per coordinate):
        *   Extract the $i$-th bit of $x$, $y$, and $z$.
        *   Place the $i$-th bit of $x$ at position $3i$ in the result.
        *   Place the $i$-th bit of $y$ at position $3i+1$ in the result.
        *   Place the $i$-th bit of $z$ at position $3i+2$ in the result.
    *   Alternatively, use precomputed lookup tables or magic bit shifts for performance [S4, S5, S9, unofficial].

3.  **Decoding (Bit Extraction):**
    *   Initialize $x, y, z$ to 0.
    *   For each bit position $i$ from 0 to $m-1$:
        *   Extract the bit at position $3i$ from the Morton code and place it at bit $i$ of $x$.
        *   Extract the bit at position $3i+1$ from the Morton code and place it at bit $i$ of $y$.
        *   Extract the bit at position $3i+2$ from the Morton code and place it at bit $i$ of $z$.
    *   Alternatively, use magic bit shifts to parallelize extraction [S4, S5, S9, unofficial].

**Formulas:**

*   **Naive Encoding (Bitwise):**
    For each bit index $i$ from 0 to 31 (for 32-bit coords):
    $$ \text{answer} \ |= \ ((x \ \& \ ((\text{uint64\_t})1 \ll i)) \ll 2i) \ | \ ((y \ \& \ ((\text{uint64\_t})1 \ll i)) \ll (2i + 1)) \ | \ ((z \ \& \ ((\text{uint64\_t})1 \ll i)) \ll (2i + 2)) $$
    [S9, unofficial]

*   **Naive Decoding (Bitwise):**
    For each bit index $i$ from 0 to 20 (for 64-bit code, 3D):
    $$ x \ |= \ ((\text{morton} \ \& \ (\text{uint64\_t}(1\text{ull}) \ll (3i + 0))) \gg ((3i + 0) - i)) $$
    $$ y \ |= \ ((\text{morton} \ \& \ (\text{uint64\_t}(1\text{ull}) \ll (3i + 1))) \gg ((3i + 1) - i)) $$
    $$ z \ |= \ ((\text{morton} \ \& \ (\text{uint64\_t}(1\text{ull}) \ll (3i + 2))) \gg ((3i + 2) - i)) $$
    [S9, unofficial]

*   **Lookup Table Encoding:**
    $$ \text{result} \ |= \ \text{Table}[k \cdot \text{tableSize} + v] $$
    Where $k$ is the dimension index and $v$ is the coordinate value [S5, unofficial].

*   **Magic Bit Decoding:**
    For dimension $i$:
    $$ r = (\text{code} \gg i) \ \& \ \text{Magic}[0] $$
    For $j$ from 0 to $\text{len}(\text{Magic})-2$:
    $$ r = (r \ \oplus \ (r \gg ((\text{dimensions}-1) \cdot (1 \ll j)))) \ \& \ \text{Magic}[j+1] $$
    $$ \text{result}[i] = \text{uint32}(r) $$
    [S5, unofficial]

**Parameters:**
*   **Dimensions:** Number of coordinate components (2, 3, or 4 supported in common implementations) [S5, unofficial].
*   **Table Size:** Maximum value for any single coordinate component. For 3D with `uint64`, max coordinate is $2^{20}-1$ if table size is $2^{20}$ [S5, unofficial].
*   **Grid Size:** $N \times N \times N$ where $N=2^m$ [S1].

**Edge Cases and Pitfalls:**
*   **Overflow:** The Morton code must fit in the output integer type. For 3D, `uint64_t` supports up to 21 bits per coordinate ($2^{21}-1$) [S9, unofficial].
*   **Input Validation:** Encoding fails if lookup table is not generated, input vector length exceeds dimensions, or coordinate values exceed table size [S5, unofficial].
*   **Decoding Edge Case:** Decoding returns nil/error if dimensions is 0 or magic array is empty [S5, unofficial].
*   **Precision:** Bitwise operations assume integer coordinates. Floating-point coordinates must be quantized to grid indices first [G].

**Pseudocode:**

```python
def morton_encode_naive(x: int, y: int, z: int) -> int:
    """
    Encodes 3D integer coordinates into a Morton code using naive bit interleaving.
    Assumes coordinates fit within 21 bits for 64-bit output.
    """
    answer = 0
    # Iterate through each bit position of the coordinates
    for i in range(21):  # 21 bits per coordinate for 64-bit total
        # Extract i-th bit of x, y, z
        bit_x = (x >> i) & 1
        bit_y = (y >> i) & 1
        bit_z = (z >> i) & 1
        
        # Place bits at positions 3i, 3i+1, 3i+2
        answer |= (bit_x << (3 * i))
        answer |= (bit_y << (3 * i + 1))
        answer |= (bit_z << (3 * i + 2))
        
    return answer

def morton_decode_naive(morton: int) -> tuple:
    """
    Decodes a Morton code back into 3D integer coordinates.
    """
    x = 0
    y = 0
    z = 0
    
    # Iterate through each bit position of the Morton code
    for i in range(21):  # 21 bits per coordinate
        # Extract bits at positions 3i, 3i+1, 3i+2
        bit_x = (morton >> (3 * i)) & 1
        bit_y = (morton >> (3 * i + 1)) & 1
        bit_z = (morton >> (3 * i + 2)) & 1
        
        # Place bits at position i in x, y, z
        x |= (bit_x << i)
        y |= (bit_y << i)
        z |= (bit_z << i)
        
    return (x, y, z)

def morton_encode_lookup(x: int, y: int, z: int, table: list) -> int:
    """
    Encodes 3D integer coordinates using a precomputed lookup table.
    table: list of size 3 * table_size, where table[dim * table_size + val] 
           contains the interleaved bits for that dimension and value.
    """
    result = 0
    # Assuming table is structured as [x_bits..., y_bits..., z_bits...]
    # Each component contributes to the final interleaved result
    result |= table[x]
    result |= table[1 * len(table)//3 + y] # Assuming equal table sizes per dim
    result |= table[2 * len(table)//3 + z]
    return result

def morton_decode_magic(morton: int, magic: list, dimensions: int) -> list:
    """
    Decodes a Morton code using magic bits for parallel extraction.
    magic: list of uint64 magic constants.
    dimensions: number of dimensions (e.g., 3).
    """
    result = [0] * dimensions
    for i in range(dimensions):
        r = (morton >> i) & magic[0]
        for j in range(len(magic) - 1):
            r = (r ^ (r >> ((dimensions - 1) * (1 << j)))) & magic[j + 1]
        result[i] = r
    return result
```

## Subtopics

### [Morton Index Calculation via Byte-Lookup Table](2384-morton-index-calculation-via-byte-lookup-table.md)
Uses precomputed lookup tables for each byte of coordinates to avoid bitwise interleaving, optimizing for chunked voxel data up to $256^3$ voxels.

### [Morton Code Generation for Octrees](4673-morton-code-generation-for-octrees.md)
Generates unique integer keys for octree cells by recursively concatenating octant indices, differing from coordinate-based bit-interleaving.

### [2D Morton Code](4680-2d-morton-code.md)
Maps 2D coordinates $(x, y)$ into a 1D index by interleaving bits, computationally cheaper than 3D but with slightly lower locality preservation than Hilbert curves.

### [Morton Code Spatial Sorting](4818-morton-code-spatial-sorting.md)
Reorders a flat list of 3D points (e.g., Gaussian splats) by Morton codes to improve spatial locality and compression, rather than constructing a tree or lookup tables.

### [Morton Order Indexing for Out-of-Core Rendering](6826-morton-order-indexing-for-out-of-core-rendering.md)
Integrates spatial indexing with a histogram-based lookup table to manage variable-sized voxel sets on disk, reducing seek operations.

### [Morton Packing for Texture Atlases](6996-morton-packing-for-texture-atlases.md)
Packs block-level texture charts into a 2D atlas using Morton ordering to maximize spatio-temporal coherence for sparse volume data.

## Operating characteristics
*   **Time Complexity:** Naive encoding/decoding is $O(m)$ where $m$ is the number of bits per coordinate. Lookup table encoding is $O(1)$ per coordinate component (assuming table access is $O(1)$). Magic bit decoding is $O(1)$ with a small constant factor depending on word size [S5, S9, unofficial].
*   **Memory Complexity:** Naive method uses $O(1)$ extra memory. Lookup table method uses $O(D \cdot S)$ memory where $D$ is dimensions and $S$ is table size [S5, unofficial].
*   **Measured Performance:** Lookup tables and magic bits are significantly faster than naive bit-shifting loops, especially on GPUs where bitwise operations can be parallelized [S5, S2, unofficial].
*   **Strengths:** Preserves spatial locality better than row-major ordering; hierarchical nature allows efficient octree construction; simple bitwise operations are hardware-friendly [S1, S8][S9, unofficial].
*   **Limitations:** Locality preservation is not as strong as Hilbert curves; limited by integer width (e.g., 64-bit limits 3D coords to 21 bits) [S5, S9, unofficial].
*   **When to Use:** When spatial locality is important for cache coherence or out-of-core rendering, and performance of encoding/decoding is critical [S1][S3, S9, unofficial].
*   **When Not to Use:** When maximum locality preservation is required (consider Hilbert curves) or when coordinates exceed the bit-width limit of the chosen integer type [S5, S9, unofficial].

## Background
Morton order was initially proposed by G. M. Morton in 1966 [S1, S8]. It is a linearization of an $N$-dimensional grid corresponding to the order of leaf nodes encountered during a post-order depth-first traversal of the corresponding $2^n$-tree (quadtree in 2D, octree in 3D) [S8]. The Morton code of a cell is its index in this order, obtained by hierarchically subdividing a Z-shaped space-filling curve [S1, S8]. It is widely used in sparse voxel octree construction, out-of-core rendering, and spatial indexing for dense grids to optimize disk seeks and cache performance [S1][S3, unofficial][S8][S9, unofficial].
