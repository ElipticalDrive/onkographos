# Morton Code Encoding/Decoding

Also called: Z-order, Z-order curve, Morton Order, Z-order encoding, Z-order curve encoding

## Overview
Morton Code Encoding/Decoding converts N-dimensional integer coordinates into a single 1D integer index (the Morton code) by interleaving the bits of each coordinate component, and reverses this process to recover the original coordinates [S1, S3, S7, unofficial]. This linearization preserves spatial locality, mapping nearby points in N-dimensional space to nearby indices in a 1D array, which accelerates cache-coherent access in volume rendering and sparse voxel octree construction [S5, unofficial][S6][S7, unofficial]. It differs from hierarchical indexing methods like [Morton Code Generation for Octrees](4673-morton-code-generation-for-octrees.md) by operating directly on flat Cartesian coordinates rather than tree paths [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Encode:** Input is an N-dimensional vector of non-negative integers $(x_0, x_1, \dots, x_{N-1})$. Output is a single unsigned integer (Morton code) [S7, S3, unofficial].
*   **Decode:** Input is a Morton code (unsigned integer). Output is the N-dimensional vector of integers [S1, S4, S5, unofficial].

**Data Structures:**
*   **Coordinates:** Array of integers. Standard 3D implementations use values in $[0, 128)$ or bounds fitting within the bit width [S1, S5, unofficial].
*   **Morton Code:** Typically `uint64_t` for 3D coordinates up to 21 bits each (since $3 \times 21 = 63 < 64$) [S7, unofficial].

**Algorithm (Naive Bit Interleaving):**
This method directly interleaves bits from each coordinate component [S7, unofficial]. It iterates over each bit position $i$ from 0 to $B-1$ (where $B$ is the number of bits per coordinate, e.g., 21 for 64-bit codes in 3D) [S7, unofficial].

1. Initialize `result = 0`.
2. For each bit position $i$ from 0 to $B-1$:
   a. Extract the $i$-th bit of each coordinate $x_k$: $b_k = (x_k \gg i) \& 1$ [G].
   b. Place $b_k$ into the $k \cdot N + i$-th position of the result, where $N$ is the number of dimensions [G]. The standard Z-order interleaves bits at position $i$ of each coordinate into positions $i, i+N, i+2N, \dots$ of the code [G].
   
   **General Formula for N dimensions:**
   $$ \text{Morton} = \sum_{i=0}^{B-1} \sum_{k=0}^{N-1} \left( (x_k \gg i) \& 1 \right) \ll (N \cdot i + k) $$
   
   **Specific 3D Formula (from [S7, unofficial]):**
   $$ \text{answer} = \sum_{i=0}^{31} \left( (x \& (1 \ll i)) \ll 2i \right) \mid \left( (y \& (1 \ll i)) \ll (2i + 1) \right) \mid \left( (z \& (1 \ll i)) \ll (2i + 2) \right) $$
   *(Note: [S7, unofficial] uses a loop up to 31 bits for `int`, but for `uint64_t` codes, the loop limit is determined by the available bits per coordinate, typically 21 for 3D 64-bit codes [S7, unofficial]).*

**Algorithm (Fast Bit Interleaving / Parallel Bits):**
To avoid loops, bits are spread and combined using bitwise operations and masks [S2, unofficial].
**Encoding Steps (3D, 64-bit):**
1. **Spread X:** Spread the bits of $x$ into even positions [G].
   Standard 32-bit spread (from [S2, unofficial], adapted for 64-bit context):
   $$ x = (x \mid (x \ll 16)) \& 0x00FF00FF00FF00FF $$
   $$ x = (x \mid (x \ll 8)) \& 0x0F0F0F0F0F0F0F0F $$
   $$ x = (x \mid (x \ll 4)) \& 0x3333333333333333 $$
   $$ x = (x \mid (x \ll 2)) \& 0x5555555555555555 $$
2. **Spread Y:** Same as X.
3. **Spread Z:** Same as X.
4. **Combine:**
   $$ \text{Morton} = x \mid (y \ll 1) \mid (z \ll 2) $$
   *(Note: For 3D, the shift amounts are 0, 1, 2 relative to the spread bits) [G].*

**Decoding Steps (3D, 64-bit):**
1. **Extract X:** Reverse the spread.
   $$ x = \text{morton} \& 0x5555555555555555 $$
   $$ x = (x \oplus (x \gg 1)) \& 0x3333333333333333 $$
   $$ x = (x \oplus (x \gg 2)) \& 0x0F0F0F0F0F0F0F0F $$
   $$ x = (x \oplus (x \gg 4)) \& 0x00FF00FF00FF00FF $$
   $$ x = (x \oplus (x \gg 8)) \& 0x0000FFFF0000FFFF $$
   $$ x = (x \oplus (x \gg 16)) \& 0x00000000FFFFFFFF $$
2. **Extract Y:**
   $$ y = (\text{morton} \gg 1) \& 0x5555555555555555 $$
   Apply same reverse spread as X.
3. **Extract Z:**
   $$ z = (\text{morton} \gg 2) \& 0x5555555555555555 $$
   Apply same reverse spread as X.

**Alternative Decoding (Magic Bits):**
Uses precomputed "magic" masks to extract bits in parallel [S3, unofficial].
1. Generate `Magic` array based on dimensions [S3, unofficial].
2. For each dimension $i$:
   $$ r = (\text{code} \gg i) \& \text{Magic}[0] $$
   For $j$ from 0 to len(Magic)-2:
   $$ r = (r \oplus (r \gg ((N-1) \cdot 2^j))) \& \text{Magic}[j+1] $$
   $$ \text{coord}_i = r $$

**Parameters:**
*   **Bit Width:** 64-bit unsigned integer is standard for 3D [S7, unofficial]. Max coordinate value is $2^{21}-1$ [S7, unofficial].
*   **Dimensions:** 2, 3, or 4 supported in dynamic implementations [S3, unofficial].

**Edge Cases and Pitfalls:**
*   **Overflow:** If coordinates exceed the bit width allocated per dimension (e.g., $> 2^{21}-1$ for 3D in 64-bit), the Morton code will collide or overflow [S3, S7, unofficial].
*   **Input Validation:** Encode must check if input coordinates exceed the table size (if using lookup tables) or bit limits [S3, unofficial].
*   **Decoding Edge Case:** If dimensions are 0 or magic array is empty, decode returns nil/error [S3, unofficial].

**Pseudocode (Naive 3D Encode/Decode):**

```python
def morton_encode_naive(x: int, y: int, z: int) -> int:
    """
    Encodes 3D integer coordinates into a 64-bit Morton code using naive bit interleaving.
    Assumes x, y, z are non-negative and fit within 21 bits.
    """
    morton = 0
    # Loop up to 21 bits for 64-bit code (3 * 21 = 63)
    for i in range(21):
        # Extract i-th bit of each coordinate
        bit_x = (x >> i) & 1
        bit_y = (y >> i) & 1
        bit_z = (z >> i) & 1
        
        # Place bits in Morton code
        # Bit i of x goes to position 3*i
        # Bit i of y goes to position 3*i + 1
        # Bit i of z goes to position 3*i + 2
        morton |= (bit_x << (3 * i))
        morton |= (bit_y << (3 * i + 1))
        morton |= (bit_z << (3 * i + 2))
        
    return morton

def morton_decode_naive(morton: int) -> tuple:
    """
    Decodes a 64-bit Morton code back into 3D integer coordinates.
    """
    x = 0
    y = 0
    z = 0
    
    # Loop up to 21 bits
    for i in range(21):
        # Extract bits from Morton code
        # Bit at position 3*i is x
        # Bit at position 3*i + 1 is y
        # Bit at position 3*i + 2 is z
        
        bit_x = (morton >> (3 * i)) & 1
        bit_y = (morton >> (3 * i + 1)) & 1
        bit_z = (morton >> (3 * i + 2)) & 1
        
        x |= (bit_x << i)
        y |= (bit_y << i)
        z |= (bit_z << i)
        
    return (x, y, z)
```

## Subtopics

### [Morton Index Calculation via Byte-Lookup Table](2384-morton-index-calculation-via-byte-lookup-table.md)
A method to compute the Morton (Z-order) curve index for a 3D voxel position $(x, y, z)$ by using precomputed lookup tables for each byte of the coordinates, avoiding expensive bitwise interleaving operations. It sets itself apart from naive bitwise interleaving by trading memory access for computational simplicity, and from general Morton encoding by optimizing specifically for chunked voxel data with a hard limit of $256^3$ voxels per chunk. It builds on [Morton Code Encoding/Decoding](1700-morton-code-encoding-decoding.md).

### [Morton Code Generation for Octrees](4673-morton-code-generation-for-octrees.md)
This method generates unique integer keys for octree cells by recursively concatenating octant indices to a parent key, enabling efficient hierarchical spatial indexing and neighbor lookups. It differs from its parent, [Morton Code Encoding/Decoding](1700-morton-code-encoding-decoding.md), which uses bit-interleaving of Cartesian coordinates, by constructing keys via path-based concatenation during tree traversal.

### [Morton Code Spatial Sorting](4818-morton-code-spatial-sorting.md)
Morton Code Spatial Sorting reorders a set of 3D points (typically Gaussian splats) by their Morton codes to improve spatial locality. This ordering enhances compression ratios when quantizing and saving data as images, such as PNGs. It differs from sibling methods by focusing on the global reordering of a flat list of parameters rather than constructing a hierarchical tree structure or optimizing lookup tables for index generation [G].

### [2D Morton Code](4680-2d-morton-code.md)
The 2D Morton Code maps two-dimensional grid coordinates $(x, y)$ into a one-dimensional integer index by interleaving their binary representations. This method preserves spatial locality, meaning that points close in 2D space typically have similar Morton indices, which optimizes cache performance and enables efficient spatial indexing for dense grids. It differs from 3D Morton codes by operating on only two dimensions and from Hilbert curves by using simple bit interleaving rather than recursive space-filling curve traversal, making it computationally cheaper but with slightly lower locality preservation.

## Operating characteristics
*   **Time Complexity:** Naive encoding/decoding is $O(B)$ where $B$ is the number of bits per coordinate [G]. Fast bit-interleaving (parallel bits) is $O(1)$ with a constant number of bitwise operations (typically 5-10 shifts/masks per dimension) [S2, unofficial]. Lookup table methods are $O(1)$ but require memory allocation for tables [S3, unofficial].
*   **Memory Complexity:** $O(1)$ for naive/fast methods [G]. Lookup table methods require $O(D \cdot \text{tableSize})$ memory where $D$ is dimensions and `tableSize` is the maximum coordinate value + 1 [S3, unofficial].
*   **Performance:** Fast bit-interleaving is significantly faster than naive looping [S2, S3, unofficial]. Lookup tables can be faster on CPUs with high cache hit rates for small tables, but may suffer from cache misses for large tables [S3, unofficial].
*   **Strengths:** Preserves spatial locality, enabling efficient spatial hashing, grid traversal, and neighbor lookups [S5, unofficial][S6][S7, unofficial]. Simple to implement [S7, unofficial].
*   **Limitations:** Limited by integer bit width (64-bit limits 3D coordinates to ~21 bits) [S3, S7, unofficial]. Not suitable for very large coordinate spaces without multi-word codes [G].
*   **When to use:** When spatial locality is critical for cache performance (e.g., sparse voxel octrees, density grid access) [S5, unofficial][S6][S7, unofficial]. When coordinates are small integers.
*   **When not to use:** When coordinates exceed bit limits [G]. When hierarchical structure is needed (use Octree methods instead) [S1, unofficial].

## Background
Morton order was introduced by G. M. Morton in 1966 [S6]. It is also known as the Z-order curve because the 2D projection of the curve resembles the letter 'Z' [S6]. It is a space-filling curve that linearizes multi-dimensional data [S6][S7, unofficial]. It is widely used in computer graphics for spatial indexing, particularly in sparse voxel octrees (SVOs) for out-of-core construction and rendering [S6][S7, unofficial].
