# Morton Code Encoding/Decoding

Also called: Morton Order, Morton Order Indexing, Z-order, Z-order curve, Z-order curve encoding, Z-order encoding

## Overview
Morton Code Encoding/Decoding maps $N$-dimensional integer coordinates (typically 3D voxel positions $(x, y, z)$) into a single 1D integer index by interleaving the bits of each coordinate component [S1, S2, S4, S8, unofficial]. This linearization preserves spatial locality, ensuring that points close in Euclidean distance have close Morton indices, which optimizes cache performance and reduces disk seek operations for out-of-core rendering [S2, S6, unofficial][S7][S8, unofficial]. It differs from sibling methods like [Grid Density Data Structure](998-grid-density-data-structure.md) and [Voxel Grid Indexing](1719-voxel-grid-indexing.md) by using non-linear bit-interleaving rather than simple row-major strides or hierarchical tree pointers for the base linearization step [S2, unofficial][S7].

## How it works
**Inputs and Outputs:**
*   **Encode:** Input is an array of $N$ integer coordinates, typically shape $[N, 3]$ for 3D voxels, with values in $[0, 2^{20})$ for 64-bit codes [S1, S4, S6, S8, unofficial]. Output is an array of 1D Morton indices, shape $[N]$, stored as `uint64_t` [S1, S4, S6, S8, unofficial].
*   **Decode:** Input is an array of Morton indices, shape $[N]$ [S1, S6, unofficial]. Output is an array of coordinates, shape $[N, 3]$ [S1, S6, unofficial].

**Data Structures:**
*   **Naive Implementation:** No auxiliary structures required.
*   **Lookup Table Implementation (Go `morton` library):** A `Morton` struct containing:
    *   `Dimensions` (uint8): Number of coordinate components (2, 3, or 4) [S4, unofficial].
    *   `Table` ([]uint64): Flat lookup array of size `dimensions * tableSize` [S4, unofficial].
    *   `Magic` ([]uint64): Array of 6 precomputed magic bitmasks [S4, unofficial].
    *   `tableSize` (uint32): Maximum value for any single coordinate component [S4, unofficial].

**Algorithm: Encoding (Naive Bitwise Interleaving)**
This method directly interleaves bits from $x, y, z$ into a 64-bit integer. It is computationally expensive due to per-bit loops but requires no memory [S8, unofficial].

1.  Initialize `answer = 0`.
2.  For each bit index $i$ from 0 to 20 (since $3 \times 21 = 63 < 64$):
    a. Extract the $i$-th bit of $x$: `bit_x = (x >> i) & 1`.
    b. Extract the $i$-th bit of $y$: `bit_y = (y >> i) & 1`.
    c. Extract the $i$-th bit of $z$: `bit_z = (z >> i) & 1`.
    d. Place `bit_x` at position $2i$ in `answer`.
    e. Place `bit_y` at position $2i+1$ in `answer`.
    f. Place `bit_z` at position $2i+2$ in `answer`.
3.  Return `answer`.

*Formula:*
$$ \text{answer} = \bigvee_{i=0}^{20} \left( (x \& (1 \ll i)) \ll 2i \right) \lor \left( (y \& (1 \ll i)) \ll (2i+1) \right) \lor \left( (z \& (1 \ll i)) \ll (2i+2) \right) $$
where $\lor$ is bitwise OR and $\ll$ is bitwise left shift [S8, unofficial].

*Pseudocode (Naive):*
```python
def morton_encode_naive(x: int, y: int, z: int) -> int:
    answer = 0
    for i in range(21):  # 21 bits per axis fits in 64-bit integer (3*21=63)
        answer |= ((x & (1 << i)) << (2 * i))
        answer |= ((y & (1 << i)) << (2 * i + 1))
        answer |= ((z & (1 << i)) << (2 * i + 2))
    return answer
```

**Algorithm: Decoding (Naive Bit Extraction)**
This method extracts bits from the Morton code back into coordinates.

1.  Initialize $x=0, y=0, z=0$.
2.  For each bit index $i$ from 0 to 20:
    a. Extract bit at position $3i$ from `morton` and place it at bit $i$ of $x$.
    b. Extract bit at position $3i+1$ from `morton` and place it at bit $i$ of $y$.
    c. Extract bit at position $3i+2$ from `morton` and place it at bit $i$ of $z$.
3.  Return $(x, y, z)$.

*Formula:*
$$ x = \bigvee_{i=0}^{20} \left( (morton \& (1 \ll (3i))) \gg i \right) $$
$$ y = \bigvee_{i=0}^{20} \left( (morton \& (1 \ll (3i+1))) \gg i \right) $$
$$ z = \bigvee_{i=0}^{20} \left( (morton \& (1 \ll (3i+2))) \gg i \right) $$
[ S8 ]

*Pseudocode (Naive):*
```python
def morton_decode_naive(morton: int) -> tuple:
    x = 0
    y = 0
    z = 0
    for i in range(21):
        x |= ((morton & (1 << (3 * i))) >> i)
        y |= ((morton & (1 << (3 * i + 1))) >> i)
        z |= ((morton & (1 << (3 * i + 2))) >> i)
    return (x, y, z)
```

**Algorithm: Encoding (Lookup Table / Magic Bits)**
This method uses precomputed tables to avoid per-bit loops, trading memory for speed [S4, unofficial].

1.  **Initialization:**
    a. Set `tableSize` to the maximum coordinate value + 1 (e.g., $2^{20}$ for 21-bit coords).
    b. Allocate `Table` of size `dimensions * tableSize`.
    c. For each dimension $d$ from 0 to `dimensions-1`:
        i. For each value $v$ from 0 to `tableSize-1`:
            1. Compute `Table[d * tableSize + v]` by interleaving bits of $v$ with offset $d$ and spread `dimensions`.
    d. Generate `Magic` array of 6 `uint64` values using `MakeMagic(dimensions)` [S4, unofficial].

2.  **Encode:**
    a. Initialize `result = 0`.
    b. For each coordinate component $v_k$ at index $k$:
        i. Check if $v_k < tableSize$. If not, return error [S4, unofficial].
        ii. `result |= Table[k * tableSize + v_k]`.
    c. Return `result`.

*Pseudocode (Lookup Table Encode):*
```python
def morton_encode_lookup(vector: list, table: list, table_size: int, dimensions: int) -> int:
    if len(vector) > dimensions:
        raise ValueError("Input vector length exceeds dimensions")
    result = 0
    for k, v in enumerate(vector):
        if v >= table_size:
            raise ValueError(f"Coordinate {k} exceeds table size")
        result |= table[k * table_size + v]
    return result
```

**Algorithm: Decoding (Magic Bits)**
This method uses bitwise operations with precomputed magic masks to extract coordinates in parallel [S4, unofficial].

1.  **Decode:**
    a. For each dimension $i$ from 0 to `dimensions-1`:
        i. Initialize `r = (code >> i) & Magic[0]`.
        ii. For $j$ from 0 to `len(Magic)-2`:
            1. `r = (r ^ (r >> ((dimensions - 1) * (1 << j)))) & Magic[j+1]`.
        iii. `result[i] = r`.
    b. Return `result`.

*Pseudocode (Magic Bits Decode):*
```python
def morton_decode_magic(code: int, magic: list, dimensions: int) -> list:
    result = [0] * dimensions
    for i in range(dimensions):
        r = (code >> i) & magic[0]
        for j in range(len(magic) - 1):
            shift = (dimensions - 1) * (1 << j)
            r = (r ^ (r >> shift)) & magic[j + 1]
        result[i] = r
    return result
```

**Parameters:**
*   **Bit Width:** 64-bit unsigned integer (`uint64_t`) is standard, supporting up to 21 bits per coordinate in 3D ($3 \times 21 = 63$) [S4, S8, unofficial].
*   **Coordinate Range:** Typically $[0, 128)$ for small grids or $[0, 2^{20})$ for large out-of-core structures [S1, S4, S6, unofficial].
*   **Dimensions:** Supports 2, 3, and 4 dimensions [S4, unofficial].

**Edge Cases and Pitfalls:**
*   **Overflow:** Encoding coordinates larger than $2^{20}-1$ in 3D will overflow a 64-bit integer [S4, unofficial].
*   **Table Size:** Lookup table encoding fails if `tableSize` is 0 or if input coordinates exceed `tableSize` [S4, unofficial].
*   **Magic Array:** Decoding fails if `Magic` array is empty or `Dimensions` is 0 [S4, unofficial].
*   **Precision:** Naive bitwise operations are exact for integers but slow for large arrays [S8, unofficial].

## Operating characteristics
*   **Time Complexity:**
    *   Naive Encoding/Decoding: $O(\log C)$ where $C$ is the coordinate magnitude (number of bits) [S8, unofficial].
    *   Lookup Table/Magic Bits: $O(1)$ per coordinate component after $O(C \cdot D)$ precomputation, where $D$ is dimensions [S4, unofficial].
*   **Memory Complexity:**
    *   Naive: $O(1)$ auxiliary space [S8, unofficial].
    *   Lookup Table: $O(D \cdot S)$ where $S$ is `tableSize` (e.g., $3 \times 2^{20}$ `uint64`s $\approx 24$ MB for 3D, 21-bit coords) [S4, unofficial].
*   **Performance:**
    *   Naive method is slow for large datasets due to per-bit loops [S8, unofficial].
    *   Lookup table/magic bits method is significantly faster, avoiding loops [S4, unofficial].
    *   Morton ordering reduces disk seek operations to at most 8 for rectangular subsets in 3D octrees, usually fewer [S2, unofficial].
*   **Strengths:** Preserves spatial locality better than row-major ordering; enables efficient out-of-core rendering and compression [S2, unofficial][S7][S8, unofficial].
*   **Limitations:** Limited by integer width (64-bit restricts 3D coords to 21 bits); lookup tables consume significant memory for large coordinate ranges [S4, S8, unofficial].
*   **When to Use:** When spatial locality is critical for cache/disk performance, and coordinate ranges fit within 64-bit integers.
*   **When Not to Use:** When coordinates exceed 21 bits per axis in 3D, or when memory is extremely constrained and naive bit operations are too slow (consider [Morton Index Calculation via Byte-Lookup Table](2384-morton-index-calculation-via-byte-lookup-table.md) if memory allows, or hierarchical methods if locality requirements are less strict).

## Background
Morton order was introduced by G. M. Morton in 1966 [S7]. It is a linearization of an $n$-dimensional grid corresponding to the post-order depth-first traversal of a $2^n$-tree (octree in 3D) [S7]. The order is hierarchical, meaning the Morton order for a higher tree level corresponds to the coarser version of the grid [S7]. It is also known as the Z-order curve because the traversal follows a Z-shaped pattern recursively [S2, unofficial][S7]. It is widely used in out-of-core construction of Sparse Voxel Octrees (SVOs) to store voxel data in a sequential structure that preserves cache coherence [S7][S8, unofficial].
