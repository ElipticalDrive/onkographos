# Morton Code Encoding/Decoding

Also called: Z-order, Z-order curve, Morton Order, Z-order encoding, Z-order curve encoding

## Overview
Morton Code Encoding/Decoding converts $N$-dimensional integer coordinates (typically 3D voxel positions $(x, y, z)$) into a single 1D integer index by interleaving the bits of each coordinate component [S3, S7, unofficial]. This linearization preserves spatial locality, ensuring that points close in Euclidean distance have close Morton indices, which optimizes cache performance and enables efficient spatial indexing for dense grids [S2, S7, unofficial]. It differs from simple row-major strides by providing better locality for multi-dimensional data and serves as the foundational indexing mechanism for its children, such as octree generation and byte-lookup optimizations [S3, S1, unofficial].

## How it works
### Inputs and Outputs
*   **Encoding Input:** An array of $N$ coordinates, typically `coords` of shape $[N, 3]$ containing 32-bit signed integers. Values are usually constrained to a range such as $[0, 128)$ or within the limits of the output integer width [S1, S5, unofficial].
*   **Encoding Output:** An array `indices` of shape $[N]$ containing 64-bit unsigned integers (uint64_t) representing the Morton codes [S7, S1, unofficial].
*   **Decoding Input:** An array `indices` of shape $[N]$ containing Morton codes [S1, S5, unofficial].
*   **Decoding Output:** An array `coords` of shape $[N, 3]$ containing the original integer coordinates [S1, S5, unofficial].

### Data Structures
For implementations using lookup tables (e.g., [S3, unofficial]), the `Morton` struct contains:
*   `Dimensions` (uint8): The number of coordinate components (2, 3, or 4) [S3, unofficial].
*   `Table` ([]uint64): A flat lookup array of size `dimensions * tableSize`. `Table[dim * tableSize + val]` stores the precomputed interleaved bits for a specific value in a specific dimension [S3, unofficial].
*   `Magic` ([]uint64): An array of 6 precomputed "magic" bitmasks used for fast decoding [S3, unofficial].
*   `tableSize` (uint32): The maximum value for any single coordinate component that can be encoded [S3, unofficial].

### Numbered Steps

#### Encoding (Bit Interleaving)
The core operation is interleaving the bits of the coordinate components. For 3D coordinates $(x, y, z)$, the $i$-th bit of $x$ becomes the $3i$-th bit of the result, the $i$-th bit of $y$ becomes the $(3i+1)$-th bit, and the $i$-th bit of $z$ becomes the $(3i+2)$-th bit [S7, unofficial].

1.  Initialize `answer` to 0.
2.  For each bit index $i$ from 0 to 31 (for 32-bit coordinates):
    *   Extract the $i$-th bit of $x$: `bit_x = x & (1 << i)`
    *   Extract the $i$-th bit of $y$: `bit_y = y & (1 << i)`
    *   Extract the $i$-th bit of $z$: `bit_z = z & (1 << i)`
    *   Shift `bit_x` to position $2i$ (relative to the start of the interleaved block for x, but effectively $3i$ in the final 64-bit word if we consider the pattern $zyxzyx...$). *Correction based on [S7, unofficial] formula:* The formula in [S7, unofficial] shifts $x$ by $2i$, $y$ by $2i+1$, $z$ by $2i+2$. This implies the output pattern is $z_{bit} y_{bit} x_{bit}$ for each $i$.
    *   Update `answer`:
        $$ answer \ |= \ (bit\_x \ll 2i) \ | \ (bit\_y \ll (2i + 1)) \ | \ (bit\_z \ll (2i + 2)) $$
3.  Return `answer` as a uint64_t [S7, unofficial].

*Alternative Fast Encoding (Bit Parallel):*
For higher performance, bits can be interleaved using bitwise operations without a loop [S2, unofficial]:
1.  Define `part1by1(n)`:
    *   `n = n & 0x0000ffff`
    *   `n = (n ^ (n << 8)) & 0x00ff00ff`
    *   `n = (n ^ (n << 4)) & 0x0f0f0f0f`
    *   `n = (n ^ (n << 2)) & 0x33333333`
    *   `n = (n ^ (n << 1)) & 0x55555555`
    *   Return `n`
2.  Compute `encoded = (part1by1(y) << 1) | part1by1(x)` [S2, unofficial]. *Note: This specific sequence interleaves 2D. For 3D, a similar 5-step parallel shift sequence is required, or the loop method is used.*

*Lookup Table Encoding:*
1.  Initialize `result` to 0.
2.  For each dimension $k$ and coordinate value $v$:
    *   Retrieve `table_val = Table[k * tableSize + v]`.
    *   `result |= table_val` [S3, unofficial].

#### Decoding (Bit Un-interleaving)
The inverse operation extracts bits from the Morton code back into coordinates.

1.  Initialize $x, y, z$ to 0.
2.  For each bit index $i$ from 0 to 20 (since $64/3 \approx 21$):
    *   Extract the bit at position $3i$ from `morton`: `bit_x = morton & (1 << (3*i))`
    *   Extract the bit at position $3i+1$ from `morton`: `bit_y = morton & (1 << (3*i+1))`
    *   Extract the bit at position $3i+2$ from `morton`: `bit_z = morton & (1 << (3*i+2))`
    *   Shift bits back to position $i$:
        $$ x \ |= \ (bit\_x \gg ((3i + 0) - i)) $$
        $$ y \ |= \ (bit\_y \gg ((3i + 1) - i)) $$
        $$ z \ |= \ (bit\_z \gg ((3i + 2) - i)) $$
3.  Return $(x, y, z)$ [S7, unofficial].

*Alternative Fast Decoding (Bit Parallel):*
Using the inverse of the parallel encoding steps [S2, unofficial]:
1.  Define `compact1by1(x)`:
    *   `x = x & 0x55555555`
    *   `x = (x ^ (x >> 1)) & 0x33333333`
    *   `x = (x ^ (x >> 2)) & 0x0f0f0f0f`
    *   `x = (x ^ (x >> 4)) & 0x00ff00ff`
    *   `x = (x ^ (x >> 8)) & 0x0000ffff`
    *   Return `x`
2.  Compute `x = compact1by1(morton)`, `y = compact1by1(morton >> 1)` [S2, unofficial].

*Magic Bit Decoding (N-Dimensional):*
1.  For each dimension $i$ from 0 to $D-1$:
    *   `r = (code >> i) & Magic[0]`
    *   For $j$ from 0 to `len(Magic)-2`:
        *   `r = (r ^ (r >> ((D-1) * (1 << j)))) & Magic[j+1]`
    *   `result[i] = uint32(r)` [S3, unofficial].

### Parameters and Typical Values
*   **Coordinate Width:** 32-bit integers are common, allowing Morton codes up to 64 bits (supporting coordinates up to $2^{20}-1$ in 3D) [S7, S3, unofficial].
*   **Grid Size:** In some implementations, coordinates are constrained to $[0, 128)$, fitting within 7 bits per dimension, resulting in a 21-bit Morton code [S1, S5, unofficial].
*   **Dimensions:** Typically 2 or 3. 4D is supported by some libraries but limited by uint64 width [S3, unofficial].

### Edge Cases and Pitfalls
*   **Overflow:** The Morton code must fit in the output integer type. For 3D coordinates, a 64-bit integer supports coordinates up to $2^{20}-1$. Larger coordinates require 128-bit integers or multi-word representations [S3, S7, unofficial].
*   **Input Validation:** Encoding must check if the input vector length exceeds dimensions or if coordinate values exceed the lookup table size (if using tables) [S3, unofficial].
*   **Decoding Edge Case:** Decoding returns nil/error if dimensions are 0 or magic bits are not initialized [S3, unofficial].
*   **Precision:** Bitwise operations assume integer coordinates. Floating-point coordinates must be discretized to grid indices first [S6].

### Pseudocode

```python
def morton_encode_3d(x: int, y: int, z: int) -> int:
    """
    Encodes 3D integer coordinates into a 64-bit Morton code using bit interleaving.
    Based on [S7, unofficial].
    """
    answer = 0
    # Iterate over 21 bits to fit within 64-bit integer (3 * 21 = 63)
    for i in range(21):
        # Extract i-th bit of each coordinate
        bit_x = (x >> i) & 1
        bit_y = (y >> i) & 1
        bit_z = (z >> i) & 1
        
        # Place bits into the answer at positions 3i, 3i+1, 3i+2
        # Note: The formula in [S7, unofficial] uses shifts 2*i, 2*i+1, 2*i+2 relative to 
        # the bit extraction, which effectively maps x->3i, y->3i+1, z->3i+2 
        # if we consider the bit extraction already isolated the bit.
        # However, [S7, unofficial] code: ((x & (1<<i)) << 2*i)
        # If x has bit i set, (x & (1<<i)) is 2^i.
        # (2^i) << 2i = 2^(3i). Correct.
        
        answer |= (bit_x << (3 * i))
        answer |= (bit_y << (3 * i + 1))
        answer |= (bit_z << (3 * i + 2))
        
    return answer

def morton_decode_3d(morton: int) -> tuple:
    """
    Decodes a 64-bit Morton code back into 3D integer coordinates.
    Based on [S7, unofficial].
    """
    x = 0
    y = 0
    z = 0
    
    # 64 bits / 3 dimensions = 21 bits per coordinate
    for i in range(21):
        # Extract bits at positions 3i, 3i+1, 3i+2
        bit_x = (morton >> (3 * i)) & 1
        bit_y = (morton >> (3 * i + 1)) & 1
        bit_z = (morton >> (3 * i + 2)) & 1
        
        # Place bits back into coordinates at position i
        x |= (bit_x << i)
        y |= (bit_y << i)
        z |= (bit_z << i)
        
    return (x, y, z)
```

## Operating characteristics
*   **Time Complexity:** Naive bit-interleaving is $O(\log C)$ where $C$ is the coordinate range (number of bits). Parallel bitwise methods are $O(1)$ (constant number of operations, typically 5-7 shifts/XORs) [S2, S7, unofficial]. Lookup table methods are $O(1)$ per coordinate component [S3, unofficial].
*   **Memory Complexity:** $O(1)$ for the encoding/decoding logic. Lookup table methods require $O(D \cdot V)$ memory where $D$ is dimensions and $V$ is the value range (table size) [S3, unofficial].
*   **Performance:** Parallel bitwise methods are significantly faster than loop-based methods [S3, unofficial]. Lookup tables trade memory bandwidth for computational simplicity [S2, unofficial].
*   **Strengths:** Excellent spatial locality preservation; simple integer arithmetic; hierarchical structure [S6].
*   **Limitations:** Locality is not as strong as Hilbert curves; limited by integer width (64-bit limits 3D coordinates to $2^{20}$) [S3, S7, unofficial].

## Background
Morton order was introduced by G. M. Morton in 1966 [S6]. It is a linearization of an $N$-dimensional grid corresponding to the order of leaf nodes in a post-order depth-first traversal of a $2^N$-tree (octree in 3D) [S6]. It is also known as the Z-order curve because the traversal pattern resembles the letter 'Z' in 2D [S6][S7, unofficial]. It is widely used in sparse voxel octrees, database indexing, and graphics for cache-coherent data access [S6][S7, unofficial].
