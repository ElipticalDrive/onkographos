# HashNeRF Parameters

Also called: HashNeRF Hyperparameters

## Overview
This article details the specific hyperparameters, training configurations, and architectural choices required to implement the HashNeRF method, which utilizes a multi-resolution hash grid encoding for neural radiance fields. It distinguishes itself from standard NeRF by replacing positional encoding with a learnable sparse hash table, and from ZipNeRF by its specific initialization and optimizer settings for the embedding table. The configuration is designed for efficient training on synthetic and real-world datasets, balancing memory usage with rendering quality through a pyramid of hash grids.

## How it works
The method optimizes a neural network that maps 3D coordinates to color and density using a multi-resolution hash encoding. The implementation relies on specific data structures, optimizer settings, and training loops defined below.

### Inputs and Outputs
*   **Inputs:** 3D point coordinates $(x, y, z)$, camera pose parameters, and ground truth RGB images.
*   **Outputs:** Predicted RGB color and volume density ($\sigma$) for each ray sample.

### Data Structures
The core data structure is the **Hash Grid Pyramid**.
*   **Structure:** A list of $L$ hash tables (grids).
*   **Number of Levels ($L$):** 10 grids [S2].
*   **Resolutions:** Geometric progression with growth factor $b=2$. Resolutions range from $16$ to $8192$ [S2]. The finest resolution is typically $512$ in the base implementation [S1, unofficial].
*   **Hash Map Size:** Each level uses a hash map of size $2^{19}$ entries by default [S1, unofficial]. However, specific variants (e.g., RING-NeRF adaptations) may use $2^{21}$ ($128^3$) entries per level [S2].
*   **Embedding Dimensions:**
    *   Standard HashNeRF: Hidden dimension $64$, geometric feature dimension $15$ [S1, unofficial].
    *   RING-NeRF Variant: Uses $8$ features per level [S2].
*   **Bounding Box:** Defines the spatial extent of the scene, used to normalize coordinates before hashing.

### Initialization
*   **Embedding Table:** When `args.i_embed==1`, the model uses a hashed embedding table stored in `embedding_params` [S1, unofficial].
*   **Optimizer Specifics:** The optimizer uses RAdam with a specific epsilon for embedding parameters: $\epsilon = 1e-15$ [S1, unofficial].
*   **Model Architecture:** If `args.i_embed==1`, the model uses `NeRFSmall` with fixed dimensions; otherwise, it uses the standard `NeRF` model with configurable depth/width [S1, unofficial].

### Training Configuration
*   **Iterations:** 25,000 iterations [S2].
*   **Batch Size:** $2^{16}$ rays [S2].
*   **Optimizer:** RAdam [S1, unofficial][S2].
*   **Learning Rate Schedule:** Cosine decay from initial $1e-2$ to final $1e-3$ [S2].
*   **Loss Functions:**
    *   Sparse Loss Weight: $1e-10$ [S1, unofficial].
    *   TV Loss Weight: $1e-6$ [S1, unofficial].
    *   Distortion Loss: Implemented as in NerfStudio [S2].
*   **Regularization:**
    *   `raw_noise_std`: Standard deviation of noise added to the output $\sigma_a$ (alpha/density). Recommended value: $1.0$ [S1, unofficial].

### Rendering Parameters
*   **Render Factor:** Downsampling factor for fast preview. Set to $4$ or $8$ [S1, unofficial].
*   **Resolution:**
    *   Blender Synthetic: Default $800 \times 800$. Can be set to $400 \times 400$ via `half_res` [S1, unofficial].
    *   LLFF: Images downsampled by `factor` (default $8$) [S1, unofficial].
*   **Coordinate System:**
    *   NDC: Disabled (`no_ndc`) for non-forward-facing scenes [S1, unofficial].
    *   Disparity: Sampling linearly in disparity (`lindisp`) rather than depth [S1, unofficial].
    *   Spherical: Enabled (`spherify`) for 360-degree scenes [S1, unofficial].

### Proposal Sampling (Multi-Scale/Advanced)
*   **Samplers:** 2 rounds of sampling via 2 different grid-based proposal samplers, followed by one final forward pass [S2].
*   **Architecture:** Uses the I-NGP-based concatenation model [S2].
*   **Resolutions:** Max resolutions of $512$ and $2048$ for the samplers [S2].
*   **Features:** Samplers use features of size $1$ (density only) [S2].

### Edge Cases and Pitfalls
*   **Hash Collisions:** With a finite hash map size, collisions can occur. The `log2_hashmap_size` parameter controls this trade-off between memory and accuracy [S1, unofficial][S2].
*   **Bounding Box:** Incorrect bounding box settings can lead to out-of-bounds errors or poor reconstruction of scene geometry. The `bounding_box_min` and `bounding_box_max` must encompass the entire scene [S1, unofficial].
*   **Optimizer Epsilon:** Using the default RAdam epsilon may lead to instability in the embedding table updates. The specific value of $1e-15$ is recommended for embedding parameters [S1, unofficial].
*   **Dataset Mismatch:** Ensure `dataset_type` matches the data format. LLFF data requires specific handling of `factor` and `llffhold` [S1, unofficial].

## Subtopics

### Hashed Embedding Table Initialization
When `args.i_embed==1`, the model uses a hashed embedding table. The initialization uses RAdam with a specific epsilon of $1e-15$ for these parameters [S1, unofficial]. If `args.i_embed==1`, the model uses `NeRFSmall` with fixed dimensions (hidden_dim=64, geo_feat_dim=15); otherwise, it uses the standard `NeRF` model with configurable depth/width [S1, unofficial].

## Operating characteristics
*   **Memory Complexity:** Depends on the number of levels, hashmap size, and feature dimensions. With 10 levels and $2^{19}$ entries per level, memory usage is significant but sparse. The RING-NeRF variant uses $2^{21}$ entries per level, increasing memory usage [S2].
*   **Time Complexity:** Linear with respect to the number of levels and features per level. The multi-resolution approach allows for efficient encoding at different scales.
*   **Performance:** Trained for 25k iterations with a batch size of $2^{16}$ rays [S2]. The use of proposal samplers (2 rounds) improves sampling efficiency [S2].
*   **Strengths:** Efficient memory usage due to sparsity, fast training convergence, and high-quality rendering.
*   **Limitations:** Sensitive to hash map size and bounding box definition. May require careful tuning of learning rate and loss weights.
*   **When to Use:** Suitable for real-time or near-real-time neural rendering applications where memory and speed are critical.
*   **When Not to Use:** For scenes with very large bounding boxes or high-frequency details that require extremely fine resolutions, the hash collisions may degrade quality.

## Background
HashNeRF was introduced as an efficient alternative to traditional positional encoding in NeRF. It leverages multi-resolution hash grids to encode spatial information, allowing for faster training and rendering. The method has been adapted and extended in various works, including RING-NeRF, which explores different inductive biases and encoding strategies [S2]. The implementation details provided here are based on the HashNeRF-pytorch repository and the RING-NeRF paper [S1, unofficial][S2].
