# Active Cut Management

Also called: Active Cut Management with Merge/Split Queues, Adaptive voxelization via cut adaptation, View-dependent hierarchical LOD for volume rendering

## Overview
Active Cut Management is a view-dependent level-of-detail technique for volume rendering that maintains an "active cut"—a set of octree nodes that partition the model space exactly once—by dynamically merging and splitting nodes to balance visual quality against frame time budgets [S1]. It distinguishes itself from static multiresolution methods by continuously adapting the representation hierarchy every frame based on screen-space error metrics and hardware bandwidth constraints, ensuring texel sizes remain close to one pixel while respecting fill-rate and memory limits [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** The current octree structure of the volume data, the current camera/view parameters, the target frame rate, and the available texture memory size.
*   **Output:** A set of active nodes (the active cut) ready for rendering, and updated texture memory residency status.

**Data Structures:**
The method relies on an octree where each node tracks its resolution level and screen-space error. Two priority queues are constructed each frame:
1.  **Merge Queue:** Contains the parents of all nodes currently on the active cut. Sorted by priority (error metric).
2.  **Split Queue:** Contains nodes on the active cut that are candidates for refinement. Sorted by priority (error metric).

**Error Metric:**
The priority for both queues is determined by the maximum screen-space size of a node’s texels in pixel units [S1].
$$ E_{node} = \max(\text{screen space size of texels}) $$
Ideally, $E_{node} \approx 1$ pixel. Nodes with $E_{node} > 1$ (yellow in source visuals) are candidates for splitting, while nodes with $E_{node} < 1$ (green in source visuals) are candidates for merging if they are non-leaf nodes [S1]. Leaf nodes (red in source visuals) are at sufficient resolution [S1].

**Parameters:**
*   **Frame Time Budget:** The total time allowed for rendering and cut adaptation. This limits the number of nodes rendered (fill rate) and the number of merges/splits (texture loads) [S1].
*   **Texture Memory Limit:** The maximum size of texture memory available [S1].
*   **Target Frame Rate:** The desired minimum frame rate [S1].

**Algorithm Steps:**
1.  **Initialize Queues:** Construct the merge queue (parents of active cut nodes) and split queue (active cut nodes) [S1].
2.  **Bound Operations:** Determine the maximum number of splits and merges allowed in the current frame based on machine bandwidths (disk to RAM, RAM to texture memory) and texture cache status (LRU policy) [S1]. Cache misses increase the cost of operations [S1].
3.  **Process Splits:**
    *   Select the highest-priority node from the split queue.
    *   If texture memory limits or frame rate targets are reached, a split may only proceed if it is paired with a merge that reduces overall error. Specifically, a merge followed by a split is allowed only if:
        $$ E_{merge\_node} < E_{split\_node} $$
        This ensures the combined operation reduces the total error [S1].
    *   If the node is not resident in texture memory, load it from RAM or disk. This may span multiple frames [S1].
    *   If another node in the queue has a higher error than the currently splitting node, stall the current split and begin splitting the higher-error node immediately [S1].
4.  **Process Merges:**
    *   Select the highest-priority node from the merge queue.
    *   Perform the merge if it fits within the frame time and memory budgets.
5.  **Render:** Traverse the resulting active cut hierarchically. Cull nodes outside the viewing frustum or with zero opacity in the transfer function [S1].

**Pseudocode:**
```python
def active_cut_management(octree, camera, frame_budget, texture_memory_limit, target_fps):
    # 1. Identify current active cut and build queues
    active_cut = get_active_cut(octree)
    merge_queue = PriorityQueue()
    split_queue = PriorityQueue()
    
    for node in active_cut:
        # Calculate screen-space error (max texel size in pixels)
        error = calculate_screen_space_error(node, camera)
        
        # Add to split queue if it's a candidate for refinement
        if not node.is_leaf and error > 1.0:
            split_queue.push(node, priority=error)
            
        # Add parent to merge queue if it exists
        if node.parent:
            parent_error = calculate_screen_space_error(node.parent, camera)
            merge_queue.push(node.parent, priority=parent_error)
            
    # 2. Determine operation limits based on bandwidth and cache
    max_splits = estimate_max_operations(frame_budget, texture_memory_limit, merge_queue, split_queue)
    max_merges = estimate_max_operations(frame_budget, texture_memory_limit, merge_queue, split_queue)
    
    splits_performed = 0
    merges_performed = 0
    
    # 3. Process splits
    while split_queue and splits_performed < max_splits:
        candidate = split_queue.peek()
        
        # Check if we need to force a merge to stay within memory/frame limits
        if texture_memory_full() or frame_rate_dropped():
            # Only allow split if paired with a beneficial merge
            if merge_queue:
                merge_candidate = merge_queue.peek()
                if merge_candidate.error < candidate.error:
                    # Perform merge
                    perform_merge(merge_candidate)
                    merges_performed += 1
                    # Remove merged node from active cut and update queues
                    update_queues_after_merge(merge_candidate)
                else:
                    break # Cannot split without beneficial merge
            else:
                break # No merges available to offset split cost
                
        # Check if a higher priority split exists
        # Note: In a real implementation, the queue is dynamic. 
        # If the top of the queue changes, we re-evaluate.
        if not is_top_priority(candidate):
            break # Stall current split for higher priority node
            
        # Perform split (may span multiple frames)
        if not is_resident_in_texture_memory(candidate):
            load_from_ram_or_disk(candidate)
            
        perform_split(candidate)
        splits_performed += 1
        update_queues_after_split(candidate)
        
    # 4. Process merges
    while merge_queue and merges_performed < max_merges:
        candidate = merge_queue.peek()
        
        # Check frame budget
        if time_remaining() < cost_of_merge(candidate):
            break
            
        # Check if beneficial (optional optimization, core logic relies on split pairing)
        perform_merge(candidate)
        merges_performed += 1
        update_queues_after_merge(candidate)
        
    return get_active_cut(octree)
```

**Edge Cases and Pitfalls:**
*   **Cache Misses:** Texture caches in main memory and texture memory use an LRU policy. Splits/merges causing cache misses are more expensive and should be accounted for in the frame budget [S1].
*   **Preemption:** If a node is mid-split and another node has a higher error, the current split is stalled, and the new node begins splitting immediately [S1].
*   **Multi-frame Splits:** A single split operation may require loading multiple texture nodes and thus span multiple frames. The system must track the state of in-progress splits [S1].

## Operating characteristics
*   **Time Complexity:** The adaptation phase is bounded by the frame time budget. The number of merges and splits is limited by bandwidth (disk/RAM/texture) and cache hit rates [S1].
*   **Memory Complexity:** Dependent on the number of active nodes and their texture residency. Texture memory usage increases with splits and decreases with merges [S1].
*   **Performance:** Maintains texel sizes close to one pixel, optimizing fill rate and visual quality. Tested on an Oxygen Post model with 513,375 tetrahedra [S1].
*   **Strengths:** View-dependent refinement ensures higher detail near the viewpoint. Dynamic adaptation handles varying scene complexity and camera motion.
*   **Limitations:** Requires careful management of texture memory and bandwidth. Split operations may not complete in a single frame, requiring state persistence.

## Background
Active Cut Management was introduced in the context of interactive visualization of unstructured grids using hierarchical 3D representations [S1]. It draws conceptual parallels to view-dependent continuous level of detail techniques used for polygonal models, such as those by Xia and Varshney, Duchandeau et al., Hoppe, and Luebke and Erikson [S1]. The method was demonstrated on datasets like the Oxygen Post model (513,375 tetrahedra) and Cylinder data set (615,000 tetrahedra) [S1].
