# VoxelLodTerrain


## Overview
VoxelLodTerrain is a specialized terrain node for smooth, decimable terrain designed for large-scale worlds (e.g., *No Man's Sky*, *Space Engineers*), replacing the single-level-of-detail sparse grid of VoxelTerrain with a multi-LOD system [S1, unofficial]. It solves the problem of limited view distance and performance bottlenecks in single-LOD sparse grids by using an octree to manage multiple levels of detail, allowing for much larger render distances without requiring preprocessing [S1, unofficial]. It sets itself apart from siblings like Geometry Clipmap by using a multi-grid sparse storage approach for LODs rather than a single geometric mesh structure, making LODs independent for parallel updates [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Player position, world edit history, voxel data generation functions.
*   **Output:** Visible meshes for the current frame, updated octree structure.

**Data Structures:**
1.  **Octree:** Determines which blocks need to be visible. The root size matches the rendering engine's maximum view distance. To support infinite worlds, a sparse grid of octrees is used [S1, unofficial].
2.  **VoxelMap (Sparse Grids):** Multiple sparse grids, one for each level of detail (LOD). This allows horizontal access to any block at any LOD and makes LODs independent [S1, unofficial].
    *   **Block Size:** 1 block equals $16 \times 16 \times 16$ voxels [S1, unofficial].
    *   **Memory:** Approximately 128 MB for 8 LODs in the worst case without compression, assuming 16 MB per $256 \times 256 \times 256$ voxel volume [S1, unofficial].
    *   **Compression:** Run-Length Encoding (RLE) is a candidate for completely uniform blocks (like air) [S1, unofficial].

**Numbered Steps:**
1.  **Octree Traversal:** Regularly traverse the octree to determine which blocks need to be visible based on the player's position and the maximum view distance [S1, unofficial].
2.  **Asynchronous Data Loading:** Load voxel data for required blocks asynchronously. Data does not need to match visuals immediately; a block can be loaded but not yet meshed [S1, unofficial].
3.  **Asynchronous Meshing:** Generate meshes for loaded blocks asynchronously. Meshes are generated for every LOD [S1, unofficial].
4.  **LOD Management:** Store data in multiple VoxelMaps (one per LOD). Access blocks horizontally across LODs [S1, unofficial].
5.  **Hole Prevention (Mesh Readiness):** Prevent loading holes by restricting octree subdivision/unsubdivision based on mesh readiness:
    *   A node can subdivide only if all replacing meshes are ready.
    *   A node can unsubdivide only if the replacing mesh is ready [S1, unofficial].
    *   *Alternative:* Build all meshes in advance for every LOD and toggle visibility based on the octree. If a mesh is not available when toggling is needed, pass without blocking the octree, and inspect the octree/cache when the mesh becomes available [S1, unofficial].
6.  **Frame Spreading:** If data maintenance is too expensive for the main thread, spread it across frames (e.g., processing 8 grids over 8 frames) [S1, unofficial].
7.  **Seam Handling:** Use a cheaper technique than Transvoxel's 3D T-junction polygonization, specifically 'Marching Squares Skirts' [S1, unofficial].

    # 1. Determine required blocks using Octree
    required_blocks = octree_traverse(player_pos, max_view_dist)
    
    # 2. Asynchronously load voxel data for required blocks
    # Data is stored in VoxelMap grids, one per LOD
    for lod_index, lod_grid in enumerate(lod_grids):
        for block in required_blocks:
            if not lod_grid.has_block(block):
                # Asynchronous load
                voxel_data_source.load_async(block, lod_index, on_data_loaded)
    
    # 3. Asynchronously generate meshes
    # Meshes are generated for every LOD
    for lod_index, lod_grid in enumerate(lod_grids):
        for block in lod_grid.active_blocks:
            if not lod_grid.has_mesh(block):
                # Asynchronous meshing
                mesh_generator.generate_async(block, lod_index, on_mesh_ready)
    
    # 4. Handle visibility and hole prevention
    for lod_index, lod_grid in enumerate(lod_grids):

**Parameters:**
*   **Block Size:** $16 \times 16 \times 16$ voxels [S1, unofficial].
*   **LODs:** 8 LODs (typical worst-case memory usage) [S1, unofficial].
*   **Compression:** RLE for uniform blocks [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Loading Holes:** Asynchronous data and mesh generation causes the octree and visuals to be out of sync, creating temporary block holes if the octree subdivides/unsubdivides immediately [S1, unofficial].
*   **Memory Usage:** High memory usage if all meshes are built in advance for every LOD [S1, unofficial].
*   **Editing:** Editing the world requires replaying edits at all LODs or computing lower LODs from higher ones (like texture mipmaps), which can complicate distance fields [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Approximately 128 MB for 8 LODs in the worst case without compression, assuming 16 MB per $256 \times 256 \times 256$ voxel volume [S1, unofficial].
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Not given in the sources.
*   **Strengths:** Smooth, decimable terrain; large-scale worlds; asynchronous loading and meshing; independent LODs for parallel updates [S1, unofficial].
*   **Limitations:** High memory usage if all meshes are built in advance; complex hole prevention; editing world is challenging [S1, unofficial].
*   **When to Use:** Large-scale worlds with smooth terrain (e.g., *No Man's Sky*, *Space Engineers*) [S1, unofficial].
*   **When Not to Use:** Single-level-of-detail sparse grids with limited view distance [S1, unofficial].

## Background
VoxelLodTerrain was submitted as a working LOD terrain by Zylann on May 29, 2019, using an octree with on-demand block loading [S1, unofficial]. The world was fixed size at that time, requiring a small grid of octrees for infinite streaming [S1, unofficial]. It was developed to address the limitations of VoxelTerrain, which only works with a sparse grid and renders a single level of detail, limiting its view distance and suitability for Minecraft-like games [S1, unofficial].
