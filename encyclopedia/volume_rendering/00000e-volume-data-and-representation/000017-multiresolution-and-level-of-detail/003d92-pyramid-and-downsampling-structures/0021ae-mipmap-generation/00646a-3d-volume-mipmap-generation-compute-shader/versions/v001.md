# 3D Volume Mipmap Generation (Compute Shader)

Also called: 3D Box Filter Mipmap

## Overview
This method generates a mipmap chain for a 3D voxel texture by applying a 2x2x2 box filter (averaging 8 adjacent texels) via a GPU compute shader [S3, S5, unofficial]. It solves the problem of high-frequency aliasing and performance bottlenecks in ray-marching or cone-tracing algorithms by providing pre-integrated lighting and density data at multiple resolutions [S1, S5, S6, unofficial]. Unlike sibling methods like [Atlas Mipmapping](2639-atlas-mipmapping.md) which pack data into 2D atlases, or [GPU 3D Mip Chain Generation](5067-gpu-3d-mip-chain-generation.md) which may use built-in hardware blits, this approach is specifically designed for sparse 3D textures where hardware mipmap generation is unsupported or insufficient [S5, unofficial]. It differs from [Voxel Mipmap Generation](12422-voxel-mipmap-generation.md) in its explicit reliance on a compute shader dispatch for the downsampling pass rather than a fixed-function pipeline [S3, S5, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A base-resolution 3D texture (`source_image`) containing voxel data (e.g., density, color, radiance).
*   **Output:** A lower-resolution 3D texture (`mipmap_image`) representing the next level of the mipmap chain.
*   **Parameters:** `tex_size` (dimensions of the base texture), `scene_size` (bounding box of the scene, used for coordinate normalization), `voxelizationSparsity` (controls update frequency, default 1) [S1, S3, S4, unofficial].

**Data Structures:**
*   `source_image`: `image3D` buffer, `readonly`, binding 0. Supported formats: `rgba8`, `rgba32f`, `r32f` [S3, unofficial].
*   `mipmap_image`: `image3D` buffer, `writeonly`, binding 1. Same formats as source [S3, unofficial].
*   Both buffers use `restrict` layout qualifiers to prevent aliasing issues [S3, unofficial].

**Algorithm Steps:**
1.  **Dispatch:** Launch a compute shader with a workgroup size of $4 \times 4 \times 4$ (i.e., `local_size_x = 4`, `local_size_y = 4`, `local_size_z = 4`) [S3, unofficial].
2.  **Coordinate Mapping:** Each invocation identifies its output position $(x, y, z)$ using `gl_GlobalInvocationID.xyz` [S3, unofficial].
3.  **Source Lookup:** Calculate the coordinates of the 8 neighboring texels in the source texture. For an output voxel at $(x, y, z)$, the source coordinates are $(2x+i, 2y+j, 2z+k)$ for $i, j, k \in \{0, 1\}$ [S3, unofficial].
4.  **Filtering:** Load the 8 source texels, sum their values, and divide by 8 to compute the average [S3, S5, unofficial].
5.  **Storage:** Store the averaged result into `mipmap_image` at `gl_GlobalInvocationID.xyz` [S3, unofficial].

**Formulas:**
The output color/density $C_{out}$ at coordinates $(x, y, z)$ is defined as [S3, unofficial]:

$$
C_{out}(x,y,z) = \frac{1}{8} \sum_{i=0}^{1} \sum_{j=0}^{1} \sum_{k=0}^{1} C_{in}(2x+i, 2y+j, 2z+k)
$$

Where $C_{in}$ is the source texture value.

To determine which mipmap level to sample during ray traversal (e.g., for cone tracing), the Level of Detail (LOD) $v_{level}$ is calculated based on the cone diameter $d$ and the base texture size $tex_{size}$ [S1, unofficial]:

$$
v_{level} = \log_2 \left( \frac{diameter}{tex_{size}} \right)
$$

The world position $p$ is converted to texture space coordinates $pos_{texspace}$ using the scene bounding box size $scene_{size}$ [S1, unofficial]:

$$
pos_{texspace} = \frac{position}{scene_{size}} \times tex_{size}
$$

**Pseudocode:**
The following Python-like pseudocode implements the compute shader kernel for a single mipmap level generation [S3, unofficial]:

```python
# Compute Shader Kernel
# Inputs: source_image (image3D, readonly), mipmap_image (image3D, writeonly)
# Globals: gl_GlobalInvocationID (ivec3)

def generate_mipmap_level(source_image, mipmap_image):
    # Output coordinates for this workgroup invocation
    out_pos = ivec3(gl_GlobalInvocationID.xyz)
    
    # Base coordinate in the source texture (every 2nd voxel)
    base_pos = out_pos * 2
    
    # Load the 8 neighboring voxels from the source texture
    # Offsets correspond to the 8 corners of the 2x2x2 block
    c000 = imageLoad(source_image, base_pos + ivec3(0, 0, 0))
    c100 = imageLoad(source_image, base_pos + ivec3(1, 0, 0))
    c010 = imageLoad(source_image, base_pos + ivec3(0, 1, 0))
    c110 = imageLoad(source_image, base_pos + ivec3(1, 1, 0))
    c001 = imageLoad(source_image, base_pos + ivec3(0, 0, 1))
    c101 = imageLoad(source_image, base_pos + ivec3(1, 0, 1))
    c011 = imageLoad(source_image, base_pos + ivec3(0, 1, 1))
    c111 = imageLoad(source_image, base_pos + ivec3(1, 1, 1))
    
    # Average the 8 texels
    # Note: Division by 8.0 ensures floating point precision is maintained
    averaged_color = (c000 + c100 + c010 + c110 + c001 + c101 + c011 + c111) / 8.0
    
    # Store the result in the lower-resolution mipmap image
    imageStore(mipmap_image, out_pos, averaged_color)

# Sampling function used during ray traversal (e.g., in a fragment shader)
# Inputs: position (vec3), diameter (float), voxelMap (sampler3D), tex_size (vec3), scene_size (vec3)
def sample_voxel_cone(position, diameter, voxelMap, tex_size, scene_size):
    # Calculate LOD level based on cone aperture relative to texture size
    # [S1, unofficial]
    v_level = log2(diameter / tex_size)
    
    # Convert world position to texture space coordinates
    # [S1, unofficial]
    pos_texspace = (position / scene_size) * tex_size
    
    # Sample the mipmap at the calculated LOD
    # [S1, unofficial]
    color = textureLod(voxelMap, pos_texspace, v_level)
    
    return color
```

**Edge Cases and Pitfalls:**
*   **Boundary Conditions:** The compute shader must handle boundary checks if the texture dimensions are not powers of two or if the dispatch size exceeds the texture bounds. Standard implementations assume power-of-two dimensions for simplicity [S3, unofficial].
*   **Opaque Voxels:** Linear pre-filtering (box filter) does not preserve accurate transparency for highly opaque voxels. It tends to reduce density in low-resolution levels, which decreases the probability of local self-shadowing, leading to overly bright Level of Details (LoDs) [S2].
*   **Sparse Textures:** Modern GPUs often do not support hardware mipmap generation for 3D textures. Therefore, a compute shader is required for sparse 3D textures [S5, unofficial].
*   **Performance:** Voxelization sparsity and frequent mipmap regeneration can cause unstable framerates, making it potentially unsuitable for interactive applications without optimization (e.g., lazy updates) [S4, unofficial].

## Subtopics

### [Cone Stepping and Mip Level Selection](3515-cone-stepping-and-mip-level-selection.md)
Cone Stepping and Mip Level Selection is the sampling strategy used in Voxel Pre-integration to determine which resolution level of a 3D mipmap to sample at each step along a ray. It solves the problem of aliasing and performance by ensuring that the spatial extent of the sample (the cone diameter) matches the resolution of the texture data, effectively averaging light over the area covered by the cone. It differs from sibling methods like Brick LOD Selection by calculating resolution bounds for individual sample positions based on cone geometry rather than determining LOD for entire brick volumes based on distance.

### Depth-of-field via Mipmap Level Selection
A cheap depth-of-field effect achieved by using blurred data during ray casting, where the mipmap level is determined by the projection size (circle of confusion) of points off the focal plane [S7]. During eye-ray traversal, the projection size is computed for each sample lookup, and the corresponding mipmap level is selected. This results in a plausible soft blur effect while accelerating rendering by sampling lower-resolution data [S7].

### Voxel Mipmap Pyramid
A storage structure where multiple 3D arrays (boxes) of decreasing sizes form a mipmap pyramid within a chunk. A typical layout includes a base level of $32^3$, followed by $16^3$, $8^3$, and $4^3$ mip levels [S8, unofficial]. The downsampling algorithm guarantees that if a voxel at a certain mip level is "Air" (empty), all corresponding voxels in upper mip levels are also "Air" [S8, unofficial]. This structure is used for Level Of Detail (LOD) to render fewer triangles in the distance and for other optimizations, with negligible extra storage cost [S8, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of voxels in the output level. Each output voxel requires 8 reads and 1 write. The total work for a full mipmap chain is proportional to the volume of the base texture.
*   **Memory Complexity:** Storing the full mipmap chain results in roughly 33% extra memory consumption compared to the base texture alone [S5, unofficial].
*   **Performance:** Generation is highly parallelizable on GPUs via compute shaders. However, for sparse textures, the overhead of dispatching and handling empty regions can impact performance [S5, unofficial].
*   **Strengths:** Reduces high-frequency aliasing in ray marching; enables efficient cone tracing for indirect lighting; supports depth-of-field effects.
*   **Limitations:** Linear filtering loses microscopic self-shadowing and transparency accuracy for dense volumes [S2]; hardware support for 3D mipmaps is limited, necessitating compute shaders [S5, unofficial]; potential framerate instability if regeneration is not optimized [S4, unofficial].
*   **When to use:** Real-time global illumination via voxel cone tracing, depth-of-field effects, and LOD rendering for voxel terrains.
*   **When not to use:** When accurate transparency and self-shadowing at all scales are critical without additional microflake models [S2]; on hardware with efficient 3D mipmap blit support if compute shader overhead is prohibitive.

## Background
The method originates from the field of voxel cone tracing for real-time global illumination. It was popularized by researchers such as Izeemann, Lefebvre, and Neyret in the context of GigaVoxels and voxel cone tracing techniques [S1, unofficial][S7]. The specific use of a 2x2x2 box filter in a compute shader for sparse 3D textures addresses the lack of hardware support for 3D mipmap generation in many GPU architectures [S5, unofficial]. Variations and improvements, such as microflake models for accurate downsampling, have been proposed to address the inaccuracies of naive linear filtering in dense volumes [S2].
