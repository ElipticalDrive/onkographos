# Mipmap Generation
Also called: 3D Texture Mipmap Generation, Compute Shader Mipmap Generation, Volume Mipmapping
## Overview
Mipmap generation creates a hierarchy of downscaled volume data representations to enable multi-resolution rendering and faster traversal [S2, unofficial]. It solves the problem of aliasing and performance degradation when viewing high-resolution volumes from a distance or at varying scales [S4, unofficial]. It sets itself apart from siblings like [VoxelGrid Down Sample](1014-voxelgrid-down-sample.md) by explicitly managing the creation of a full mip-chain via compute shaders or specific filtering modes rather than simple grid reduction, and differs from [Streaming MIP Implementation (Basic)](1803-streaming-mip-implementation-basic.md) by focusing on the static generation of the hierarchy rather than the streaming of levels [G].
## How it works
**Inputs and Outputs:**
- Input: A base 3D texture (Level 0) containing the original volume data [S2, unofficial].
- Output: A mip-chain of 3D textures where each subsequent level has reduced spatial dimensions [S2, unofficial].

**Data Structures:**
The mipmap levels are managed via a `MipmapLevel` structure [S2, unofficial]:
- `sizeX_`, `sizeY_`, `sizeZ_`: Integer dimensions of the current level [S2, unofficial].
- `dataCpu_`: Pointer to CPU-side memory [S2, unofficial].
- `dataGpu_`: Pointer to CUDA/GPU array memory [S2, unofficial].
- `dataTex_`: CUDA texture object handle [S2, unofficial].
- `cpuDataCounter_`, `gpuDataCounter_`: Usage counters for synchronization [S2, unofficial].
- `parent_`: Reference to the parent Volume object [S2, unofficial].

**Parameters:**
- `MipmapFilterMode::AVERAGE`: Applies average filtering when generating the mipmap level [S2, unofficial].
- `MipmapFilterMode::HALTON`: Uses Halton sampling to select voxels when generating the mipmap level [S2, unofficial].
- Level scaling: Level 0 is the original data [S2, unofficial]. Level 1 is 2x downsampling, level 2 is 3x downsampling, and level $n$ is $(n+1)$x downsampling [S2, unofficial].

**Algorithm Steps:**
1. Initialize `current_dimension` to the grid resolution and `mip_level` to 0 [S1, unofficial].
2. Loop while `current_dimension` is greater than or equal to 1 [S1, unofficial].
3. Check if the next mipmap level already exists using `mipmapCheckOrCreate` before creating it [S2, unofficial].
4. Bind each 3D texture face as a write-only image texture at the next mip level using RGBA8 format [S1, unofficial].
5. Dispatch compute work groups sized to $\lceil \text{current\_dimension} / 8 \rceil$ in all three dimensions [S1, unofficial].
6. Inside the compute shader, calculate the global thread ID, determine source coordinates in the parent level based on the filter mode, and write the computed value to the target image at the current mip level [G].
7. Insert memory barriers for texture fetch and shader image access [S1, unofficial].
8. Increment `mip_level` and halve the `current_dimension` for the next iteration [S1, unofficial].

**Pseudocode:**
```python
def generate_mip_chain(base_volume, filter_mode="AVERAGE"):
    current_dim = base_volume.size  # Assumes cubic volume for simplicity
    mip_level = 0
    
    while current_dim >= 1:
        # Check if next level exists, create if not [S2, unofficial]
        # Implementation detail not given in sources [G]
        if not level_exists(mip_level + 1):
            create_mipmap_level(mip_level + 1)
            
        # Bind each 3D texture face as a write-only image texture at the next mip level using RGBA8 format [S1, unofficial]
        target_image = get_level_image(mip_level + 1)
        
        # Dispatch compute work groups sized to ceil(current_dim / 8) in all three dimensions [S1, unofficial]
        group_size = 8
        num_groups = (current_dim + group_size - 1) // group_size
        # Launch compute shader [G]
        launch_compute_shader(num_groups, num_groups, num_groups, group_size, group_size, group_size)
        
        # Insert memory barriers for texture fetch and shader image access [S1, unofficial]
        insert_memory_barrier()
        
        # Increment mip level and halve the current dimension for the next iteration [S1, unofficial]
        mip_level += 1
        current_dim = current_dim // 2

def compute_shader_downsample(global_id, parent_level, target_image, filter_mode):
    x, y, z = global_id
    parent_x = x * 2
    parent_y = y * 2
    parent_z = z * 2
    
    if filter_mode == "AVERAGE":
        sum_val = 0.0
        count = 0
        for dx in range(2):
            for dy in range(2):
                for dz in range(2):
                    val = parent_level.sample(parent_x + dx, parent_y + dy, parent_z + dz)
                    sum_val += val
                    count += 1
        result = sum_val / count
    elif filter_mode == "HALTON":
        # Halton sequence sampling to select voxels [S2, unofficial]
        # Standard Halton sequence generation [G]
        h = (global_id.x + global_id.y + global_id.z) % 8
        sample_offset = (h % 2, (h // 2) % 2, (h // 4) % 2)
        result = parent_level.sample(parent_x + sample_offset[0], 
                                     parent_y + sample_offset[1], 
                                     parent_z + sample_offset[2])
    else:
        result = parent_level.sample(parent_x, parent_y, parent_z)
        
    target_image.write(x, y, z, result)
```

**Edge Cases and Pitfalls:**
- **Precision:** When using `AVERAGE` filtering, accumulation of floating-point values in large neighborhoods can lead to precision loss. Use higher precision accumulators if necessary [G].
- **Boundaries:** Ensure that sampling neighborhoods do not exceed the bounds of the parent texture. Clamp coordinates or handle edge cases explicitly [G].
- **Degenerate Input:** If the base volume has dimensions that are not powers of two, standard halving may result in non-integer dimensions. The implementation must handle the final levels carefully, possibly using nearest-neighbor or adaptive box sizes [G].

## Subtopics

### [Atlas Mipmapping](2639-atlas-mipmapping.md)
Atlas Mipmapping addresses the undersampling artifacts that occur when a distant surfel covers few pixels but retains its full-resolution texture tile, causing a single pixel to span multiple texels during a bilinear fetch. It focuses on storage layout optimization for atlases rather than the general generation algorithm.

### [Voxel Pre-integration](2956-voxel-pre-integration.md)
Voxel Pre-integration is a method to generate mipmaps for a voxelized 3D texture using bilinear filtering to create a volumetric sampling function that yields average color and occlusion for cone tracing. It solves the problem of approximating light from areas of various sizes by sampling a 4D texture (3D space + mip levels) using linear interpolation. It differs from sibling methods like Atlas Mipmapping and GPU 3D Mip Chain Generation by specifically targeting the creation of a "volumetric sampling function" for indirect lighting approximation via cone tracing, rather than general texture compression or shadow volume optimization. Trade-offs include potential inaccuracies in appearance when input voxels are very opaque due to the loss of masking and shadowing effects [G].

### [Mipmap Filtering](4541-mipmap-filtering.md)
Mipmap Filtering is a pre-filtering technique that avoids aliasing artifacts when a projected texture's resolution exceeds the sample resolution, and mitigates block-like discontinuities when the projected resolution is lower than the target resolution. It sets itself apart from its siblings by explicitly managing the transition between different levels of detail in the mip-chain during the sampling phase, whereas [Atlas Mipmapping](2639-atlas-mipmapping.md) focuses on storage layout, [Voxel Pre-integration](2956-voxel-pre-integration.md) on radiative transfer approximation, and [GPU 3D Mip Chain Generation](5067-gpu-3d-mip-chain-generation.md) on the creation process itself [G].

### [GPU 3D Mip Chain Generation](5067-gpu-3d-mip-chain-generation.md)
`generateMipChain3d` is a GPU primitive that fills a 3D texture's mip chain by executing per-(level, z-slice) render passes, targeting specific Z-slices via `GPURenderPassColorAttachment.depthSlice`. It mirrors the 2D `generateMipChain` approach but extends it to 3D volumes, enabling efficient downsampling for both display (box filter) and acceleration (max-value pyramid) purposes. Unlike standard mipmaps which store averaged or filtered values for display, this method supports building a per-field max pyramid in deviation space to enable transfer-function-adaptive skipping during volume ray marching, allowing dynamic region skipping based on live contrast settings without rebuilding the structure.

### [Shadow Volume Mipmap Generation](5724-shadow-volume-mipmap-generation.md)
Shadow Volume Mipmap Generation constructs a 3-level mipmap chain for a shadow volume texture using bitwise OR accumulation to preserve shadow presence across downsampled resolutions. It sets itself apart from standard 3D mipmap generation by using logical OR instead of averaging or min/max filtering.

### [Voxel Mipmap Generation](12422-voxel-mipmap-generation.md)
Voxel Mipmap Generation creates a hierarchy of downsampled voxel representations from a primary volume buffer to enable rendering at varying scales or distances. It differs from [Atlas Mipmapping](2639-atlas-mipmapping.md) by operating on a contiguous 3D voxel grid rather than 2D texture atlases, and from [GPU 3D Mip Chain Generation](5067-gpu-3d-mip-chain-generation.md) by often employing specific compute shader passes or CPU-side accumulation loops for the downsampling step.

### [Clipmap Voxel Storage with Mipmap Generation](13504-clipmap-voxel-storage-with-mipmap-generation.md)
This method implements a voxel storage structure using clipmaps that generates mipmaps for inner clipmaps and the largest clipmap via compute shaders, copying regions between textures to handle axis-aligned downsampling. It differs from standard 3D mipmap chains by organizing data into a clipmap layout (concentric rings or layers) and using explicit region copies for downsampling rather than recursive texture sampling, which optimizes memory locality for view-dependent rendering.

### Multi-Frequency Texture Sampling with LOD
A technique to simulate high-frequency noise details using a small 3D texture by sampling it at different frequencies (Fractal Brownian Motion levels), reducing the number of texture lookups for distant objects [S3, unofficial]. It limits the number of frequency levels (LODs) sampled for far-away primary samples to minimize texture lookups, which are a bottleneck, and blends between different LODs to ensure smooth transitions in visual quality [S3, unofficial]. A typical texture resolution is $128 \times 128 \times 128$, which is small enough for fast web loading but large enough for 2-3 FBM levels [S3, unofficial].

### Volume Rendering with Mipmapping
Applies mipmapping to the retained texture to improve rendering performance in a hybrid CPU-GPU pipeline [S4, unofficial]. The process involves uploading the final 3D texture atlas and lookup tables to the GPU, then rendering the volume slice-by-slice by drawing a proxy polygon for each slice [S4, unofficial]. A fragment shader samples the correct texels from the packed texture using the lookup tables, selecting the appropriate mipmap level based on distance to reduce aliasing and improve speed [S4, unofficial].

### WebGPU Volume Mipmap Generation
Automatic generation of mipmap chains for volume textures in WebGPU, performed after data upload and after rendering to slices [S5, unofficial]. The shader is created lazily on first use [S5, unofficial]. For unfilterable formats (e.g., 32-bit float formats on devices without the `float32-filterable` capability), it generates mips using a samplerless fallback that reads texels with `textureLoad` and computes the average of the previous mip level's texels [S5, unofficial]. The unfilterable path uses `textureLoad` (no sampler) while the filterable path uses standard `textureSample` [S5, unofficial]. They share a shader per dimension, selected by the `UNFILTERABLE` define [S5, unofficial]. A known pitfall is that if a source dimension is odd, the 2x2x2 load block shifts, causing spatial bias that affects float textures specifically [S5, unofficial].

## Operating characteristics
- **Time Complexity:** Generation is $O(N)$ relative to the total number of voxels in the mip-chain, where $N$ is the volume of the base level. Each level is processed in parallel via compute shaders [G].
- **Memory Complexity:** Not given in the sources.
- **Strengths:** Reduces aliasing artifacts, improves rendering performance for distant views, and enables efficient traversal in acceleration structures [S4, unofficial].
- **Limitations:** Requires additional memory for the mip-chain. The choice of filter (Average vs. Halton) affects visual quality and computational cost [S2, unofficial].
- **When to Use:** When rendering large volumes at varying distances or scales, or when using acceleration structures that benefit from multi-resolution data [S2, S4, unofficial].
- **When Not to Use:** When memory is extremely constrained and the volume is only viewed at a single resolution, or when the volume is very small and the overhead of managing the mip-chain outweighs the benefits [G].

## Background
Mipmap generation is applied in hybrid CPU-GPU pipelines to improve rendering performance [S4, unofficial]. WebGPU implementations automatically generate mipmap chains for volume textures after data upload and slice rendering [S5, unofficial]. Specific implementation details, such as the use of Halton sampling and non-standard level scaling conventions, appear in specialized libraries and research projects [S1, S2, unofficial].
