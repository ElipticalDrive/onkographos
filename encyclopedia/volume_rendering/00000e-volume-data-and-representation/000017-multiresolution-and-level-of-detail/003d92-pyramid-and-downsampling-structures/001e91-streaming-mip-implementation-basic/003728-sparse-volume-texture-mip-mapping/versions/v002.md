# Sparse Volume Texture Mip Mapping

Also called: SVT Mip Mapping

## Overview
Sparse Volume Texture (SVT) Mip Mapping provides level-of-detail management for sparse volume data by exposing a `MipLevel` input pin on the sample node, allowing requests for specific resolution tiers [S1]. Unlike its parent [Streaming MIP Implementation (Basic)](1803-streaming-mip-implementation-basic.md) which handles streaming mechanics, or siblings like [Conical MImP](7656-conical-mimp.md) and [Spread-space MIP chain with luminance weighting](9093-spread-space-mip-chain-with-luminance-weighting.md) that compute LOD dynamically, SVT Mip Mapping relies on the engine's streaming system to preload tiles, with sampling failing or falling back if the requested level is not yet loaded [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A Sparse Volume Texture asset containing pre-computed mip levels [S2, unofficial].
*   **Input:** `MipLevel` integer pin on the `Sparse Volume Texture Sample` node [S1].
*   **Output:** Voxel value sampled at the specified LOD [S1].

**Data Structures:**
The SVT asset stores compressed tiles for each mip level [S2, unofficial]. The engine's streaming system loads these tiles into VRAM based on internal logic, not the `MipLevel` pin value [S1].

**Steps:**
1. The material or shader sets the `MipLevel` input pin on the `Sparse Volume Texture Sample` node to an integer $L \ge 0$ [S1].
2. The rendering engine checks if the tile data for mip level $L$ at the current sampling location has been streamed into VRAM [S1].
3. If the data is present, the hardware texture sampler performs interpolation using the texels from mip level $L$ [G].
4. If the data for level $L$ is not streamed in, sampling may fail or fall back to a lower-resolution available level [S1].

**Parameters:**
*   `MipLevel`: The target LOD index [S1].
*   `r.SparseVolumeTexture.Streaming.NumPrefetchFrames`: Number of frames to prefetch when a frame is requested. Default is 3 [S1].
*   `r.SparseVolumeTexture.Streaming.PrefetchMipLevelBias`: Bias applied to the mip level of prefetched frames. Prefetching occurs at increasingly higher mip levels (lower resolution) to anticipate movement [S1].

**Pitfalls:**
*   **Streaming Disconnect:** Setting the `MipLevel` pin does not trigger streaming. If the requested level is not already loaded, the sample will not automatically fetch it [S1].
*   **Precision:** When handling very large datasets (e.g., $32k \times 32k \times 16k$), standard 32-bit signed integers (`int32`) for linear indexing can overflow. This requires modifying engine source code to use `uint32` or `int64` for indexing operations [S2, unofficial].

**Pseudocode:**
```python
def sample_svt_mip(streamed_mips, global_coord, mip_level):
    """
    Samples a sparse volume texture at a specific mip level.
    Args:
        streamed_mips: dict mapping mip level index to available tile data.
        global_coord: float3 sampling coordinate.
        mip_level: int, the desired LOD.
    Returns:
        float4: Sampled voxel value.
    """
    if mip_level < 0:
        mip_level = 0
    # Check if the requested mip level tile is available in VRAM
    if mip_level in streamed_mips:
        # Engine handles coordinate scaling and interpolation for the specific mip level [G]
        return streamed_mips[mip_level][global_coord]
    else:
        # Fallback to base level or return zero if not streamed in [S1]
        return streamed_mips[0][global_coord]
```

## Subtopics

### Sparse Volume Texture with Heterogeneous Volumes
This variant integrates SVT Mip Mapping with Heterogeneous Volume actors to render complex, multi-material datasets [S2, unofficial]. It supports sparse datasets up to $32k \times 32k \times 16k$ voxels, provided the compressed tile data (including MIP data and padding for correct interpolation) does not exceed 4 GiB [S2, unofficial]. To handle the large address space, the engine source code must be patched to replace `int32` linear indexing with `uint32` or `int64` to prevent overflow [S2, unofficial]. The sampling logic uses modified coordinates:
$$ \text{LinearIndex} = X + Y \cdot \text{Dimensions}.X + Z \cdot \text{Dimensions}.X \cdot \text{Dimensions}.Y $$
where `LinearIndex` is `uint32` [S2, unofficial]. This method is chosen when visual quality and large dataset support are prioritized over raw performance, as it achieves excellent visual quality but lower frame rates compared to simpler methods [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Not given in the sources.
*   **Measured Performance:** On an RTX 3050, SVT with Heterogeneous Volumes achieves 18–22 FPS on $4096^3+$ data. On an RTX 5000, it achieves 10–12 FPS for the same data size [S2, unofficial].
*   **Strengths:** High visual quality; supports extremely large datasets via sparsity; native LOD support via mip levels [S1][S2, unofficial].
*   **Limitations:** Streaming is not driven by the sample node, leading to potential missing data if not prefetched correctly; integer overflow issues in default engine builds for large textures; lower FPS on high-resolution heterogeneous volumes compared to tiled ray marchers [S1][S2, unofficial].
*   **When to use:** Real-time visualization of large, complex scientific datasets where visual fidelity is critical and hardware supports large VRAM allocations [S2, unofficial].
*   **When not to use:** When strict performance is required on low-end hardware, or when the dataset is too large to fit the compressed tile limit [S2, unofficial].

## Background
Research by GEOMAR (Helmholtz-Zentrum Hereon) demonstrated the viability of SVTs for scientific visualization in immersive environments like the ARENA2 dome, highlighting the need for source code modifications to handle large indexing spaces [S2, unofficial]. The mip mapping capability allows for level-of-detail management similar to standard 2D textures [S1].
