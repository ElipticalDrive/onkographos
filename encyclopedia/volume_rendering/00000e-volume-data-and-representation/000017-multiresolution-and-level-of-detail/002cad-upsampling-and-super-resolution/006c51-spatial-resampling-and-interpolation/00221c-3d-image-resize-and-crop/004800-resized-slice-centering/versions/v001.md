# Resized Slice Centering
Also called: Centered Resizing with Air Padding

## Overview
Resized Slice Centering is a data preparation technique for volume rendering that places a resized 2D content matrix (such as a CT slice) into the center of a larger container matrix, padding the unused regions with the Hounsfield unit value for air (-1024) [S1, unofficial]. It solves the problem of aligning variable-sized or resized anatomical data into a fixed-size voxel grid required by rendering engines, ensuring that the object remains spatially centered relative to the coordinate system [S1, unofficial]. It differs from [Zero Padding for Aliasing Reduction](6382-zero-padding-for-aliasing-reduction.md) by using a specific physical constant (air HU) rather than zero, and from [Cosine Projection via Upsampling](13919-cosine-projection-via-upsampling.md) by operating in Cartesian image space rather than frequency or projection space.

## How it works
**Inputs:**
- `content`: A 2D matrix of size `contentWidth x contentHeight` (or square `length x length` as per source logic).
- `containerWidth`: The target width of the output matrix.
- `containerHeight`: The target height of the output matrix.
- `airValue`: The padding value, typically -1024 (Hounsfield Unit for air) [S1, unofficial].

**Outputs:**
- `output`: A 2D matrix of size `containerWidth x containerHeight`.

**Data Structures:**
- The `output` matrix is initialized entirely to `airValue`.
- Indices `xCentre` and `yCentre` track the position within the `content` matrix.

**Steps:**
1. Initialize `output` as a matrix of dimensions `containerWidth x containerHeight`, filling all elements with `airValue` (-1024) [S1, unofficial].
2. Calculate the starting index for centering:
   $$ centreBegins = \frac{containerWidth - content.length}{2} $$
   *Note: The source uses `CT_x_axis` for container width and `content.length` for the content dimension, assuming square content or specific axis alignment [S1, unofficial].*
3. Initialize `xCentre = 0` and `yCentre = 0` [S1, unofficial].
4. Iterate through each pixel `(x, y)` of the `output` matrix:
   - If `y > centreBegins` and `y < centreBegins + content.length`:
     - Copy `content[xCentre][yCentre]` to `output[x][y]` [S1, unofficial].
     - Increment `yCentre` [S1, unofficial].
   - If `x > centreBegins` and `x < centreBegins + content.length`:
     - Increment `xCentre` [S1, unofficial].

**Pseudocode:**
```python
def resized_slice_centering(content, container_width, container_height, air_value=-1024):
    """
    Centers a resized 2D matrix within a larger container matrix, padding unused regions with air value.
    
    Args:
        content: 2D list or array of shape (content_len, content_len) or (width, height).
                 Source assumes square content or specific axis logic.
        container_width: int, width of the output container.
        container_height: int, height of the output container.
        air_value: float, padding value (default -1024 for air HU).
        
    Returns:
        2D list or array of shape (container_height, container_width).
    """
    # Determine content dimensions. Source uses 'content.length' for both axes in centering calc.
    # Assuming square content for the specific logic in [S1, unofficial], or taking max dimension.
    # For general implementation, we assume content is square or we use the relevant axis.
    # The source logic implies square content: content.length.
    content_len = len(content)
    
    # 1. Create output matrix initialized to air value
    output = [[air_value for _ in range(container_width)] for _ in range(container_height)]
    
    # 2. Calculate center begins
    # Source: centreBegins = (CT_x_axis - content.length) / 2
    centre_begins = (container_width - content_len) / 2
    
    # 3. Initialize content indices
    x_centre = 0
    y_centre = 0
    
    # 4. Iterate through output matrix
    for y in range(container_height):
        for x in range(container_width):
            # Check if current output position falls within the vertical range of the content
            if y > centre_begins and y < centre_begins + content_len:
                # Check if current output position falls within the horizontal range
                # Note: The source logic increments x_centre based on x range, 
                # but copies content[x_centre][y_centre]. 
                # This implies a row-major copy where x_centre tracks columns and y_centre tracks rows.
                if x > centre_begins and x < centre_begins + content_len:
                    output[y][x] = content[x_centre][y_centre]
                    y_centre += 1
                # Increment x_centre if we are in the horizontal span of the content
                # The source says: "If x > centreBegins && x < centreBegins + length, increment xCentre"
                # This must happen regardless of the y-check to advance the column index?
                # Actually, looking at the source:
                # "If y > ... copy ... and increment yCentre"
                # "If x > ... increment xCentre"
                # This logic is slightly ambiguous in the source. 
                # Standard centering: x_centre corresponds to x, y_centre to y.
                # Let's follow the source literally:
                if x > centre_begins and x < centre_begins + content_len:
                    x_centre += 1
                    
    return output
```
*Correction on Pseudocode Logic based on Source [S1, unofficial]:*
The source steps are:
4. If `y > centreBegins && y < centreBegins + length`, copy `content[xCentre][yCentre]` to `output[x][y]` and increment `yCentre`.
5. If `x > centreBegins && x < centreBegins + length`, increment `xCentre`.

This implies `xCentre` is incremented for every `x` in the range, and `yCentre` is incremented only when a copy happens. This effectively maps the 2D content to the 2D output. However, standard 2D array indexing requires both indices to advance for a raster scan. The source logic might be describing a specific traversal or contains a simplification. A robust implementation for square content `N x N` into `W x W` centered:
```python
def resized_slice_centering_robust(content, container_width, container_height, air_value=-1024):
    content_len = len(content)
    output = [[air_value for _ in range(container_width)] for _ in range(container_height)]
    
    # Calculate start index
    start = (container_width - content_len) // 2
    
    # Copy content into the center
    for i in range(content_len):
        for j in range(content_len):
            out_x = start + i
            out_y = start + j
            if 0 <= out_x < container_width and 0 <= out_y < container_height:
                output[out_y][out_x] = content[i][j]
                
    return output
```
*Note: The source's specific step-by-step logic [S1, unofficial] is unusual for standard 2D copying. The robust version above achieves the same "centered" result. The source's pitfall warns about negative `centreBegins`.*

**Parameters:**
- `airValue`: Default is -1024, representing the Hounsfield unit of air [S1, unofficial].

**Edge Cases and Pitfalls:**
- If `content.length` is greater than `containerWidth`, `centreBegins` becomes negative. The source code does not explicitly clamp indices, leading to invalid memory access or incorrect placement [S1, unofficial].
- The method assumes `content.length` is less than `containerWidth` [S1, unofficial].

## Subtopics

### Sinogram Padding for Inscribed Circle Geometry
Pads the sinogram to a square shape to accommodate inscribed circle geometry, ensuring the detector width matches the image diagonal [S2, unofficial]. It calculates the diagonal size as `diagonal = ceil(sqrt(2) * sinogram.shape[2])`, determines the padding amount `pad = diagonal - sinogram.shape[2]`, and calculates center offsets `old_center = sinogram.shape[2] // 2`, `new_center = diagonal // 2`, `pad_before = new_center - old_center` [S2, unofficial]. The sinogram is then padded along the width dimension with zeros using `torch.nn.functional.pad` [S2, unofficial]. This variant is used in Radon transform contexts where square symmetry is required for reconstruction algorithms [S2, unofficial].

## Operating characteristics
- **Time Complexity:** $O(W \times H)$ for initializing the output matrix and copying the content, where $W$ and $H$ are container dimensions.
- **Memory Complexity:** $O(W \times H)$ for the output matrix.
- **Strengths:** Simple to implement; preserves the physical meaning of background (air) in CT data; ensures spatial centering.
- **Limitations:** Does not handle resizing interpolation (assumes content is already resized); sensitive to input size relative to container size (pitfall with negative indices); does not handle non-square content gracefully without modification [S1, unofficial].
- **When to use:** When preparing CT slices for volume rendering where background must be explicitly air (HU -1024) rather than zero, and the content is already the correct resolution.
- **When not to use:** When the content is larger than the container (requires cropping or scaling first); when zero-padding is acceptable for non-CT data.

## Background
This method originates from practical implementations in volume rendering pipelines, specifically noted in the `joshcodd/volume-rendering` repository [S1, unofficial]. It addresses the need to align 2D projections or slices into a fixed 3D volume grid. The use of -1024 (air HU) is specific to Computed Tomography (CT) data, distinguishing it from generic image padding.
