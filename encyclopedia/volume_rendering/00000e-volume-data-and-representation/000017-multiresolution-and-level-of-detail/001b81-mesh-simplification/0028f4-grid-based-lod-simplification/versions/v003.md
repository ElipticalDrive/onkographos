# Grid-based LOD Simplification

Also called: Coordinate Rounding LOD, Geometry Quantization LOD, LOD Simplification, POP Buffer LOD, Progressively Ordered Primitive Buffer, Snapping LOD

## Overview
Grid-based LOD Simplification renders large-scale voxel or blocky meshes at multiple levels of detail by quantizing vertex coordinates to a coarse grid and implicitly managing primitive visibility [S1, unofficial]. It solves the problem of rendering distant geometry efficiently without storing multiple explicit mesh copies on the GPU by sorting primitives into a Progressively Ordered Primitive (POP) buffer [S1, unofficial]. Unlike [Mesh simplification via valence pattern removal](1931-mesh-simplification-via-valence-pattern-removal.md) which modifies topology, or [GPU-based Mesh Decimation via Edge Collapse](3505-gpu-based-mesh-decimation-via-edge-collapse.md) which requires complex graph operations, this method relies on simple coordinate rounding and sorting [S1, unofficial]. It is distinct from [Linear Spline Simplification](3483-linear-spline-simplification.md) as it operates on discrete integer grids rather than continuous spline approximations [S2, unofficial].

## How it works
### Inputs and Outputs
- **Input**: A mesh composed of axis-aligned quads (or triangles) with integer vertex coordinates [S1, unofficial].
- **Output**: A sorted array of primitives (POP buffer) and an offset table mapping each LOD level to the start index of primitives at that level [S1, unofficial].

### Data Structures
1. **Primitive Array**: An array of quad definitions, where each quad contains four vertex coordinates [S1, unofficial].
2. **LOD Bucket Array**: An array of size $L_{max}$ (total number of LOD levels), initialized to zero [S1, unofficial]. This serves as both the counter and the prefix-sum offset table [S1, unofficial].

### LOD Computation
The core of the method is determining the coarsest LOD level at which a primitive remains non-degenerate [S1, unofficial].

1. **Vertex LOD**: For a vertex $v$ with integer coordinate $x$, the LOD is defined as the number of trailing zeros in its binary representation:
   $$ lod(v) = \text{count\_trailing\_zeros}(x) $$
   [S1, unofficial]

2. **Primitive LOD**:
   - For a triangle with vertices $v_1, v_2, v_3$:
     $$ lod(t) = \max(lod(v_1), lod(v_2), lod(v_3)) $$
     [S1, unofficial]
   - For a general axis-aligned quad, the LOD is the minimum LOD along each axis [S1, unofficial]. For a single axis interval $[lo, hi]$, the LOD is the smallest integer $i$ such that $(lo \gg i) == (hi \gg i)$ [S1, unofficial]. This can be computed efficiently using the XOR of the endpoints:
     $$ LOD = \text{count\_leading\_zeros}(lo \oplus hi) $$
     [S1, unofficial]

3. **Degeneracy Check**: If rounding causes two vertices of a cell to map to the same point (edge collapse), the primitive is considered degenerate at that LOD and is removed from that level's bucket [S1, unofficial].

### Algorithm Steps
1. **Initialize Buckets**: Create an array `buckets` of size $L_{max}$, initialized to 0 [S1, unofficial].
2. **Count LODs**: Iterate through all primitives [S1, unofficial]. For each primitive, compute its LOD using the formulas above [S1, unofficial]. Increment `buckets[lod]` [S1, unofficial].
3. **Compute Prefix Sums**: Transform the counts into starting offsets [S1, unofficial].
4. **Sort Primitives**: Place each primitive into its correct position in the sorted array using the computed offsets [S1, unofficial]. This is typically done in-place using a stable partitioning or counting sort variant [S1, unofficial].
5. **Handle Squashed Faces (Optional)**: After sorting, multiple primitives may map to the same screen space (over-drawing) [S1, unofficial]. A final pass can move "squashed" faces to the next higher LOD level to improve fragment processing performance [S1, unofficial].
6. **Render**: To render at a specific LOD $L$, draw primitives from the sorted array starting at `offset[L]` up to `offset[L+1]` [S1, unofficial]. In the vertex shader, round the vertex coordinates to the grid size $2^L$ to visualize the simplification [S1, unofficial].

### Pseudocode
```python
def build_pop_buffer(quads, max_lod):
    # Step 1: Count primitives per LOD
    buckets = [0] * max_lod
    for q in quads:
        buckets[compute_quad_lod(q)] += 1
            
    # Step 2: Compute prefix sums (offsets)
    t = 0
    for i in range(max_lod):
        b = buckets[i]
        buckets[i] = t
        t += b
            
    # Step 3: Partition quads into sorted array in-place
    for i in range(len(quads) - 1, -1, -1):
        while True:
            q = quads[i]
            lod = compute_quad_lod(q)
            ptr = buckets[lod]
            if i < ptr:
                break
            quads[i] = quads[ptr]
            quads[ptr] = q
            buckets[lod] += 1
                
    # Step 4 (Optional): Handle squashed faces by moving over-drawn primitives to the next LOD level
    # This step is not required but improves performance if rendering is fragment-processing limited [S1, unofficial].
                
    return buckets

def compute_quad_lod(quad):
    # quad is a list of 4 vertices, each with .x and .y attributes
    min_x = min(v.x for v in quad)
    max_x = max(v.x for v in quad)
    min_y = min(v.y for v in quad)
    max_y = max(v.y for v in quad)
    lod_x = interval_lod(min_x, max_x)
    lod_y = interval_lod(min_y, max_y)
    return min(lod_x, lod_y)

def interval_lod(lo, hi):
    # Returns the smallest i where (lo >> i) == (hi >> i)
    for i in range(33):
        if (lo >> i) == (hi >> i):
            return i
    return 32
```

### Parameters
- **Distance Constants**: In some implementations, distance constants for LOD selection are 4 and 8 [S2, unofficial]. The specific logic for selecting LOD based on camera distance is handled by the renderer [S2, unofficial].
- **Bias**: A bias parameter in the geomorphing LOD function, based on display resolution, FOV, and hardware requirements [S1, unofficial].

### Edge Cases and Pitfalls
- **Cracks at LOD Transitions**: Abrupt switching between LOD levels in adjacent chunks causes geometric discontinuities (cracks) [S1, unofficial].
  - *Solution 1*: Use skirts or transition seams, which increases implementation complexity and draw overhead [S1, unofficial].
  - *Solution 2 (Geomorphing)*: Interpolate between LOD levels using vertex morphing [S1, unofficial]. The LOD parameter $l$ is computed as a function of vertex coordinate $v$ and distance to camera $d$:
    $$ l = \text{bias} + \text{viewDist}(v) $$
    [S1, unofficial]
  - *Stable Rounding*: To avoid discontinuities from the logarithmic LOD function, compute a fixed point for the LOD value [S1, unofficial]. Let $L_{max}$ be the maximum LOD for the chunk and neighbors [S1, unofficial]. Iterate 2-3 times in the vertex shader to stabilize the LOD value [S1, unofficial].
- **Squashed Faces**: Rounding multiple faces to the same level can cause over-drawing [S1, unofficial]. A final pass can move these faces to the next LOD level [S1, unofficial].
- **Greedy Meshing Trade-off**: LOD reduction is less effective on greedy-meshed meshes than on naive meshes because snapped quads may not have matching counterparts to merge with (absorption) [S2, unofficial].

## Subtopics

### [Mesh simplification via valence pattern removal](1931-mesh-simplification-via-valence-pattern-removal.md)
A topology-based approach that removes vertices based on valence patterns. Choose when preserving exact geometric boundaries is less important than reducing vertex count via topological simplification.

### [Linear Spline Simplification](3483-linear-spline-simplification.md)
Uses linear splines to approximate geometry. Choose when smooth interpolation is required over discrete grid snapping.

### [GPU-based Mesh Decimation via Edge Collapse](3505-gpu-based-mesh-decimation-via-edge-collapse.md)
Performs edge collapse operations on the GPU. Choose when dynamic, real-time decimation of arbitrary meshes is needed, rather than pre-computed grid-based LOD.

### [Octree Simplification](4641-octree-simplification.md)
Hierarchically divides space into octants to manage detail. Choose when spatial partitioning naturally matches the scene structure and dynamic updates are frequent.

### [Sample-based Simplification](7814-sample-based-simplification.md)
Reduces detail by sampling or downsampling the underlying data. Choose when the source data is inherently discrete or rasterized.

### [Isosurface Simplification via Persistence](8470-isosurface-simplification-via-persistence.md)
Removes geometric features based on topological persistence metrics. Choose when preserving significant shape features is critical over uniform grid quantization.

### [Triangular Mesh Simplification](9103-triangular-mesh-simplification.md)
General-purpose decimation for arbitrary triangle meshes. Choose when working with non-axis-aligned or organic geometry that cannot be quantized to a grid.

## Operating characteristics
- **Time Complexity**: Building the POP buffer takes $O(n)$ time using counting sort, where $n$ is the number of primitives [S1, unofficial].
- **Memory Complexity**: $O(n)$ for the sorted primitive array and $O(L_{max})$ for the offset table [S1, unofficial]. No multiple mesh copies are stored [S1, unofficial].
- **Performance**: The method is described as faster and simpler to implement than alternatives like Sea of Memes' approach [S1, unofficial]. With `renderDistance = 4` and LOD 1, approximately 1.2% of quads are removed, at the cost of ~11px horizontal displacement [S2, unofficial].
- **Scaling**: Scales well with large numbers of primitives due to the linear sorting step.
- **Strengths**: Implicit LOD (no multiple meshes), fast construction, smooth transitions with geomorphing.
- **Limitations**: Discontinuities (cracks) if not handled with geomorphing or seams; less effective on greedy-meshed data; requires integer coordinates or quantization [S1, unofficial].
- **When to Use**: Blocky voxel games or scenes with axis-aligned primitives where pre-computation is acceptable [S1, unofficial].
- **When Not to Use**: Scenes with arbitrary curved geometry or dynamic meshes that cannot be pre-sorted [S1, unofficial].

## Background
The method originates from the "POP Buffer" (Progressively Ordered Primitive Buffer) concept introduced by M. Limper, Y. Jung, J. Behr, and M. Alexa in their paper "The POP Buffer: Rapid Progressive Clustering by Geometry Quantization" (Pacific Graphics 2013) [S1, unofficial]. It was adapted for voxel engines to handle level of detail transitions smoothly [S1, unofficial]. The specific implementation details regarding interval LOD and stable rounding were popularized in blog posts discussing voxel engine optimization, such as those by 0fps.net [S1, unofficial]. It is used in games like box3.dao3.fun [S1, unofficial].
