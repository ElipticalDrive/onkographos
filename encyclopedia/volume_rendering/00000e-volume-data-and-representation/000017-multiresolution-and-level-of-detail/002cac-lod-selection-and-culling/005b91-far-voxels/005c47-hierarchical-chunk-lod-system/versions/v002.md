# Hierarchical Chunk LOD System

Also called: Octree-based Chunk LOD, Recursive Chunk LOD

## Overview
A recursive Level of Detail (LOD) system using octree-like chunk subdivision to maintain a consistent surface approximation across different distances [S1, unofficial]. It splits chunks into 8 children when close to the viewer and merges them when far away, yielding interactive rates by handling levels of detail and culling [S1, unofficial]. It differs from [Flat blocking multi-resolution volume rendering](6428-flat-blocking-multi-resolution-volume-rendering.md) by using a dynamic, recursive tree structure rather than static pre-computed blocks.

## How it works
**Inputs and Outputs:**
*   **Input:** Viewer position ($P_{view}$), maximum LOD depth ($L_{max}$), view distance radius ($R_{view}$), base chunk size ($S_{base}$), and density data.
*   **Output:** A set of active `Chunk` objects, each containing a generated mesh and collider, forming the visible terrain.

**Data Structures:**
The core structure is the `Chunk` object.
*   `position`: `Vector3Int` representing the chunk's grid coordinates.
*   `mesh`: Reference to the generated `Mesh` object.
*   `dirty`: `bool`. Flag indicating if the mesh needs regeneration.
*   `densities`: `float[]`. Array of density values for the chunk's voxel grid.
*   `lod`: `int`. Current Level of Detail index (0 is finest, $L_{max}$ is coarsest).
*   `size`: `int`. The side length of the chunk in voxels.
*   `children`: `Chunk[8]`. Array of 8 child chunks (null if leaf).
*   `transform`: Unity `Transform` component for spatial hierarchy.

**Parameters:**
*   `levelsOfDetail` ($L_{max}$): Maximum depth of the LOD hierarchy. Range: $[0, 9]$. Typical value: 4 [S1, unofficial].
*   `viewDistance` ($R_{view}$): Radius within which chunks are considered for splitting. Typical value: 500 [S1, unofficial].
*   `chunkSize` ($S_{base}$): Size of the finest detail chunk. Range: $[2, 64]$. Typical value: 2 [S1, unofficial].

**Algorithm Steps:**

1.  **Initialization:**
    Create root chunks at positions $(x, y, z) \times (S_{base} \ll L_{max})$.
    Set each root chunk's `lod` = $L_{max}$ and `size` = $S_{base} \ll L_{max}$.
    Set `dirty` = true for all new chunks [S1, unofficial].

2.  **Update Loop (per frame or per viewer movement):**
    For each active chunk $C$:
    a.  **Culling Check:** If $C$ is outside the view distance $R_{view}$ from $P_{view}$, mark it for potential removal or ignore.
    b.  **Split Condition:** If $C$ is inside $R_{view}$ AND $C.lod > 0$:
        i.  Call `Split(C)`.
    c.  **Merge Condition:** If $C$ is outside $R_{view}$ AND $C.lod < L_{max}$ AND $C$ has children:
        i.  Call `Merge(C)`.
    d.  **Dirty Check:** If $C.dirty$ is true:
        i.  Generate mesh from `densities` using Marching Cubes or similar algorithm.
        ii. Set $C.dirty$ = false.

3.  **Split Operation:**
    a.  If $C.children$ is null, allocate `Chunk[8]`.
    b.  Calculate `childSize` = $C.size / 2$.
    c.  For each of the 8 octants $i \in [0, 7]$:
        i.  Create new `Chunk` child $C_i$.
        ii. Set $C_i.size$ = `childSize`.
        iii. Set $C_i.lod$ = $C.lod - 1$.
        iv. Set $C_i.position$ = $C.position + \text{offset}_i$, where $\text{offset}_i$ is $(\pm \text{childSize}/2, \pm \text{childSize}/2, \pm \text{childSize}/2)$ based on octant index.
        v.  Initialize $C_i$ with same material and collider settings as $C$.
        vi. Set $C_i.dirty$ = true.
    d.  Set $C.dirty$ = false (since children will handle their own generation).
    e.  Recursively call `RequestUpdateChunk` on all children to ensure they are processed [S1, unofficial].

4.  **Merge Operation:**
    a.  Recursively merge all children of $C$.
    b.  Destroy child objects.
    c.  Set $C.children$ = null.
    d.  Set $C.dirty$ = true (to regenerate mesh at current LOD).

**Edge Cases and Pitfalls:**
*   **Dirty Flag:** A chunk is only processed for mesh generation if `chunk.dirty` is true. Splitting or merging sets `dirty` to true. Initial creation sets `dirty` to true [S1, unofficial].
*   **Recursion Depth:** The system is described as "very recursive-based," which may lead to inefficiency or complexity compared to iterative approaches [S1, unofficial].
*   **Precision:** Floating-point precision issues may arise with large world coordinates. Using integer grid positions (`Vector3Int`) helps mitigate this.
*   **Boundary Conditions:** Ensure density data is available for all chunks, including those at the edge of the world.

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of active chunks. Splitting and merging are $O(1)$ per chunk, but recursive updates can propagate.
*   **Memory Complexity:** $O(N)$ for active chunks. Hidden chunks consume minimal memory.
*   **Performance:** Interactive rates are achieved by only rendering visible chunks at appropriate LODs [S1, unofficial]. However, CPU-based job approach is not implemented correctly in the source, leading to high CPU usage [S1, unofficial].
*   **Strengths:** Dynamic LOD, consistent surface approximation, efficient culling.
*   **Limitations:** High CPU usage due to recursion and lack of optimized job system. Lack of textures (requires triplanar shader or similar) [S1, unofficial].

## Background
Originated in the `tcgj/terrain-generator` project, written in Unity 2019.2.15f1 [S1, unofficial]. It builds on Marching Cubes algorithms [S1, unofficial]. The author notes potential inefficiencies in the recursive logic [S1, unofficial].
