# Hierarchical Chunk LOD System

Also called: Octree-based Chunk LOD, Recursive Chunk LOD

## Overview
A recursive Level of Detail (LOD) system that partitions a volume domain into octree-like chunks, splitting them into eight children when close to the viewer and merging them when far away to maintain a consistent surface approximation across varying distances [S1, unofficial]. It differs from frequency-domain methods by using spatial subdivision and from flat blocking by dynamically adjusting the hierarchy depth based on viewer proximity rather than a fixed grid structure [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Viewer position ($P_{viewer}$), maximum LOD depth ($L_{max}$), base chunk size ($S_{base}$), view distance radius ($R_{view}$), and volume density data.
*   **Outputs:** A set of active chunks, each containing a generated mesh and associated metadata (position, size, LOD level).

**Data Structures:**
The core structure is the `Chunk` object.
*   `position`: `Vector3Int` representing the chunk's origin in world space.
*   `size`: `int` representing the side length of the chunk.
*   `lod`: `int` representing the current level of detail (0 is finest, $L_{max}$ is coarsest).
*   `children`: Array of 8 `Chunk` references (or null if leaf).
*   `dirty`: `bool` flag indicating if the mesh needs regeneration.
*   `densities`: `float[]` array storing the volume data for this chunk.
*   `mesh`: `Mesh` object for rendering.

**Numbered Steps:**

1.  **Initialization:**
    Create root chunks at positions determined by $(x, y, z) \times (S_{base} \ll L_{max})$. Set each root chunk's `lod` to $L_{max}$ and `size` to $S_{base} \ll L_{max}$. Set `dirty` to `true` [S1, unofficial].

2.  **Update Loop (Recursive):**
    For each active chunk, determine if it requires splitting or merging based on the viewer's distance.
    *   **Split Condition:** If the chunk is within the view distance $R_{view}$ and `lod` > 0, and `dirty` is true:
        1.  Create 8 children.
        2.  For each child $i$ (0 to 7):
            *   Set `child.size` = `parent.size` / 2.
            *   Set `child.lod` = `parent.lod` - 1.
            *   Set `child.position` = `parent.position` + offset. The offset is calculated by adding `child.size / 2` to the parent's position components based on the octant index $i$ (e.g., bit 0 for X, bit 1 for Y, bit 2 for Z) [S1, unofficial].
            *   Initialize child mesh settings (material, collider) from parent.
            *   Set `child.dirty` = `true`.
        3.  Set `parent.children` to the array of new children.
        4.  Set `parent.dirty` = `false`.
        5.  Recursively call `RequestUpdateChunk` on all 8 children [S1, unofficial].
    *   **Merge Condition:** If the chunk is outside the view distance $R_{view}$ and has children:
        1.  Recursively merge all children (destroy them).
        2.  Set `parent.children` = `null`.
        3.  Set `parent.dirty` = `true`.
        4.  Regenerate the parent's mesh at the current `lod` level [S1, unofficial].

3.  **Mesh Generation:**
    If `dirty` is true and the chunk is a leaf (no children), generate the mesh using the density data and current resolution. The resolution is derived from the `lod` level [S1, unofficial].

**Parameters:**
*   `levelsOfDetail` ($L_{max}$): Maximum depth of the hierarchy. Range: $[0, 9]$. Typical value: 4 [S1, unofficial].
*   `viewDistance` ($R_{view}$): Radius within which chunks are considered for splitting. Typical value: 500 units [S1, unofficial].
*   `chunkSize` ($S_{base}$): Base resolution at highest detail. Range: $[2, 64]$. Typical value: 2 [S1, unofficial].

**Pitfalls:**
*   **Dirty Flag:** A chunk is only processed for mesh generation if `chunk.dirty` is true. Splitting or merging sets this flag. Failure to reset it causes redundant computation [S1, unofficial].
*   **Recursion Depth:** The system is highly recursive. Deep hierarchies or frequent splits/merges can lead to stack overflow or performance bottlenecks on the CPU [S1, unofficial].
*   **Boundary Checks:** Ensure viewer position checks account for the full extent of the chunk (radius + half-length) to avoid premature culling or splitting [S1, unofficial].

**Pseudocode:**

```python
class Chunk:
    def __init__(self, position, size, lod, parent_material):
        self.position = position
        self.size = size
        self.lod = lod
        self.children = None
        self.dirty = True
        self.material = parent_material
        self.mesh = None

    def update(self, viewer_pos, view_distance, max_lod):
        # Check if chunk is within view distance
        half_size = self.size / 2.0
        dist_x = abs(viewer_pos.x - self.position.x)
        dist_y = abs(viewer_pos.y - self.position.y)
        dist_z = abs(viewer_pos.z - self.position.z)
        
        # Simple AABB check against view radius
        if (dist_x > view_distance + half_size or dist_x < -view_distance - half_size or
            dist_y > view_distance + half_size or dist_y < -view_distance - half_size or
            dist_z > view_distance + half_size or dist_z < -view_distance - half_size):
            # Outside view distance: Merge if possible
            if self.children is not None:
                self.merge()
            return

        # Inside view distance: Split if possible and needed
        if self.lod > 0 and self.dirty:
            self.split()
            # Recursively update children
            for child in self.children:
                child.update(viewer_pos, view_distance, max_lod)
        elif self.children is None and self.dirty:
            # Leaf node, generate mesh
            self.generate_mesh()
            self.dirty = False

    def split(self):
        if self.children is None:
            self.children = [None] * 8
            child_size = self.size // 2
            for i in range(8):
                # Calculate offset based on octant index
                offset_x = (i & 1) * child_size
                offset_y = (i & 2) * child_size
                offset_z = (i & 4) * child_size
                
                new_pos = Vector3Int(
                    self.position.x + offset_x,
                    self.position.y + offset_y,
                    self.position.z + offset_z
                )
                self.children[i] = Chunk(new_pos, child_size, self.lod - 1, self.material)
        self.dirty = False

    def merge(self):
        if self.children is not None:
            for child in self.children:
                if child is not None:
                    child.destroy()
            self.children = None
            self.dirty = True
```

## Subtopics

### Hierarchical Culling & Multi-resolution Approximation
Uses spatial hierarchies for culling but may employ different approximation techniques for the volume data itself. Choose when memory bandwidth is the primary constraint. [Link](2010-hierarchical-culling-multi-resolution-approximation.md)

### Streaming and Level-of-Detail (LOD) selection
Focuses on data streaming from disk/memory rather than in-memory hierarchy management. Choose for extremely large datasets that do not fit in RAM. [Link](3087-streaming-and-level-of-detail-lod-selection.md)

### Focus Point Based Brick LOD Selection
Uses a specific focus point (e.g., camera or object) to determine LOD, potentially allowing for non-spherical view distances. Choose when the viewer's attention is concentrated in a specific area. [Link](5282-focus-point-based-brick-lod-selection.md)

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of active chunks. Splitting and merging are recursive operations, potentially leading to $O(2^L)$ overhead in the worst case if the entire volume is within view distance and needs updating.
*   **Memory Complexity:** $O(2^L)$ for the hierarchy structure, where $L$ is the max LOD depth. The actual volume data storage depends on whether data is duplicated at each level or shared.
*   **Measured Performance:** The implementation described is CPU-based and noted to take "too much CPU" for rendering, indicating poor performance for real-time applications without optimization [S1, unofficial].
*   **Strengths:** Simple to implement recursively; provides smooth transitions between detail levels based on distance.
*   **Limitations:** High CPU overhead due to recursion and object creation/destruction; lacks texture support in the described implementation; potential for "popping" artifacts if LOD transitions are not smoothed [S1, unofficial].
*   **When to use:** Small to medium-sized volumes where CPU budget allows for recursive updates and dynamic mesh generation.
*   **When not to use:** Large-scale scenes requiring GPU-based acceleration or streaming; real-time applications with strict CPU constraints.

## Background
The method originates from a terrain generator project written in Unity 2019.2.15f1, utilizing concepts from marching cubes and noise shaders [S1, unofficial]. It builds upon the work of Seb Lague (Marching Cubes), Keijiro (Noise Shader), Paul Bourke (Polygonize), and NVIDIA (GPUGems3) [S1, unofficial]. The author notes the system is "very recursive-based" and suggests there may be more elegant solutions, highlighting its experimental nature [S1, unofficial].
