# Level of Detail Calculation

Also called: ComputeVoxelSize, LoD Level Calculation, Voxel Pre-integration, Cone Stepping and Mip Level Selection, Brick LOD Selection

## Overview
Level of Detail Calculation determines the specific resolution level (mip level) of a voxelized or hierarchical volume representation required to render a primitive or region at a given screen position. It solves the problem of mapping continuous screen-space metrics (such as projected width) to discrete data hierarchy indices, ensuring that rendering resources are allocated proportional to visual importance. It sets itself apart from sibling methods by providing the fundamental arithmetic mapping from geometric extent to LOD index, which other methods like [Focus Point Based Brick LOD Selection](5282-focus-point-based-brick-lod-selection.md) or [LoD Selection via Projected Width](7837-lod-selection-via-projected-width.md) use as a core component of their broader selection strategies.

## How it works
**Inputs and Outputs:**
*   **Input:** `MaxLevels` (integer, total number of resolution levels in the hierarchy, typically $\ge 1$), `width` (float, the projected width of the target primitive or voxel in screen-space units, or a normalized metric derived from it).
*   **Output:** `level0` (integer, the lower LOD index), `plevel0` (float, the fractional part for interpolation), `level1` (integer, the upper LOD index), `plevel1` (float, the fractional part for interpolation).

**Data Structures:**
No complex data structures are required. The method operates on scalar values. If used within a shader, these are typically uniform variables or computed per-vertex/per-pixel attributes.

**Steps:**
1.  Compute the continuous LOD level using the logarithmic relationship between the maximum hierarchy depth and the projected width.
2.  Determine the lower integer LOD index (`level0`) and its fractional remainder (`plevel0`).
3.  Determine the upper integer LOD index (`level1`) and its fractional remainder (`plevel1`).

**Formulas:**
The continuous level is calculated as [S1]:
$$ \text{level} = \text{MaxLevels} - 1 + \log_2(\text{width}) $$

The lower LOD index and its weight are [S1]:
$$ \text{level0} = \lceil \text{level} \rceil $$
$$ \text{plevel0} = \text{level} - \text{level0} $$

The upper LOD index and its weight are [S1]:
$$ \text{level1} = \lfloor \text{level} \rfloor $$
$$ \text{plevel1} = \text{level1} - \text{level} $$

*Note on Weights:* In standard linear interpolation, the weight for `level0` would typically be `1 - plevel0` and for `level1` would be `plevel1`. However, the source defines `plevel0` and `plevel1` directly as the differences. **Parameters:**
*   `MaxLevels`: The depth of the mip-chain. Typical values depend on the volume resolution (e.g., 10 for 1024^3).
*   `width`: The projected width. If `width` is 0, $\log_2(0)$ is undefined. Edge case: Clamp `width` to a minimum epsilon (e.g., $10^{-6}$) to prevent NaNs.

**Pseudocode:**
```python
import math

def calculate_lod_level(max_levels: int, width: float) -> tuple:
    """
    Calculates LOD indices and fractional parts based on projected width.
    
    Args:
        max_levels: Total number of levels in the hierarchy (integer).
        width: Projected width of the primitive (float).
        
    Returns:
        A tuple (level0, plevel0, level1, plevel1) as defined in [S1].
    """
    # Guard against zero or negative width which causes log domain error
    if width <= 0.0:
        width = 1e-9
        
    # Step 1: Calculate continuous level
    # Formula: level = MaxLevels - 1 + log2(width)
    level = (max_levels - 1) + math.log2(width)
    
    # Step 2: Calculate lower LOD index and plevel0
    # Formula: level0 = ceil(level), plevel0 = level - level0
    level0 = math.ceil(level)
    plevel0 = level - level0
    
    # Step 3: Calculate upper LOD index and plevel1
    # Formula: level1 = floor(level), plevel1 = level1 - level
    level1 = math.floor(level)
    plevel1 = level1 - level
    
    return level0, plevel0, level1, plevel1
```

### [LOD Level Tree Traversal](16320-lod-level-tree-traversal.md)
LOD Level Tree Traversal is a raycasting method for 4D sparse voxel octrees that determines the visual output of a pixel by terminating the tree traversal based on specific criteria (data presence, maximum depth, or projected size) and then mapping the traversal state to a color value. It differs from standard volume rendering by decoupling the traversal termination logic from the final color computation, allowing the same traversal engine to render density, normals, or traversal complexity (stack depth) by swapping only the final color calculation step. It builds on [Level of Detail Calculation](7836-level-of-detail-calculation.md) by using the calculated LOD limits to prune the search space.

## Operating characteristics
**Time and Memory Complexity:**
The calculation itself is $O(1)$ time complexity, involving a logarithm, ceiling, and floor operations. Memory complexity is $O(1)$ as it requires only scalar storage.

**Measured Performance:**
The source [S1] notes that raster-based approaches for LOD generation are faster in specific contexts but have hardware limitations due to OpenGL architecture. The arithmetic calculation is negligible compared to the cost of data fetching or traversal.

**Strengths and Limitations:**
*   **Strengths:** Provides a deterministic, continuous mapping from screen space to data resolution. Simple to implement.
*   **Limitations:** Sensitive to the definition of `width`. If `width` is not properly normalized or clamped, it leads to invalid LOD indices. The source formulas result in negative fractional parts (`plevel0`, `plevel1`), which may require specific interpretation or post-processing by the caller to be used as interpolation weights in the range [0, 1].

**When to Use:**
Use when a direct logarithmic mapping from projected size to mip level is required, particularly in microgeometry rendering or voxel-based systems where the hierarchy is power-of-two based.

## Background
The method originates from research into fast voxelization and level of detail for microgeometry rendering [S1]. It is specifically cited in the context of SGGX-H models and raster-based LOD generation, aiming to balance accuracy and sampling control for large models [S1].
