# LOD Tree Search


## Overview
LOD Tree Search is a traversal algorithm for multidimensional (multikey) data structures, specifically 3D binary trees used in sparse voxel octrees, to efficiently locate leaf nodes containing an isosurface at a specific Level of Detail (LOD). It solves the problem of finding all cells where the scalar field value crosses a threshold without examining every node in the hierarchy. It is distinguished from sibling methods like [Work-based LOD Rendering](16373-work-based-lod-rendering.md) by its deterministic, key-based pruning strategy rather than workload balancing.

## How it works
The algorithm operates on a 3D binary tree where each node stores three keys: the minimum data value, the maximum data value, and the Level of Detail (LOD) of the virtual voxel. The goal is to find all cells $c$ such that $LOD(c) = LOD_{desired}$ and the isosurface intersects the cell.

**Inputs:**
- `branch`: The current node or subtree root in the 3D binary tree.
- `desired_LOD`: The target level of detail integer.
- `isovalue`: The scalar threshold for isosurface extraction.

**Outputs:**
- A list of cells (or their identifiers) that satisfy the intersection condition.

**Data Structures:**
The tree is a 3D binary tree. Each node contains:
- `min_val`: Minimum scalar value in the subtree.
- `max_val`: Maximum scalar value in the subtree.
- `lod`: The level-of-detail index for this node.
- `left`: Pointer to the left child (representing smaller keys in the partitioning dimension).
- `right`: Pointer to the right child.

**Algorithm Steps:**
1.  **Check LOD Condition:** Compare `branch.lod` with `desired_LOD`.
    -   If `branch.lod > desired_LOD`: The current node is too detailed. Recursively call `search_minimum` on the `left` branch. This is based on the property that the left branch contains nodes with smaller keys (including potentially lower LODs or values that might satisfy the LOD constraint in a different partitioning dimension, though the source implies a specific traversal order for LOD keys). [S1, unofficial]
    -   If `branch.lod < desired_LOD`: The current node is too coarse. Recursively call `search_minimum` on the `right` branch. [S1, unofficial]
    -   If `branch.lod == desired_LOD`: Proceed to check for isosurface intersection.
2.  **Check Isosurface Intersection:** If `branch.lod == desired_LOD`, verify if the isosurface intersects the cell bounds:
    -   Condition: `branch.min_val < isovalue` AND `branch.max_val > isovalue`.
    -   If true, add `branch` to the output list. [S1, unofficial]
3.  **Recurse:** After processing the current node (if LOD matches), recursively search both children to find other intersecting cells at the same LOD level:
    -   Call `search_minimum(branch.right)`.
    -   Call `search_minimum(branch.left)`. [S1, unofficial]

**Pseudocode:**

    """
    Recursively searches the 3D binary tree for cells with specific LOD
    that contain the isosurface.
    """

        return

        search_minimum(branch.right, desired_lod, isovalue)

**Optimizations and Pitfalls:**
-   **Min/Max Key Pruning:** If `branch.min_val < isovalue`, all cells in the left branch (which have smaller keys) will also have `min_val < isovalue`. The algorithm can skip testing the minimum key condition for these nodes, though the intersection check `min < iso AND max > iso` still requires the max check. [S1, unofficial]
-   **Max Key Pruning:** Similarly, if the maximum key condition is met (e.g., `branch.max_val <= isovalue`), testing can stop for the right branch if the partitioning guarantees larger values. [S1, unofficial]
-   **LOD Key Optimization:** If the `desired_LOD` is the global minimum or maximum possible LOD, and the search moves to a smaller (left) subtree of an already minimum LOD node, LOD key testing can stop. This is valuable because the search is most time-consuming at the lowest LOD levels. [S1, unofficial]
-   **Precision:** Floating-point comparisons for `min_val < isovalue` and `max_val > isovalue` must handle edge cases where values are exactly equal to the isovalue. The source uses strict inequalities. [S1, unofficial]

## Operating characteristics
-   **Time Complexity:** Depends on the distribution of data and the sparsity of the isosurface. In the worst case, it may visit many nodes, but pruning based on min/max bounds and LOD keys significantly reduces the search space compared to a full traversal.
-   **Memory Complexity:** $O(N)$ where $N$ is the number of nodes in the 3D binary tree, as the tree structure must be stored.
-   **Strengths:** Efficiently isolates cells at a specific resolution, reducing the number of triangles generated and processed. Leverages multikey indexing for fast pruning.
-   **Limitations:** Requires the data to be pre-processed into a 3D binary tree with min/max/LOD keys. Performance degrades if the isosurface is extremely complex or if the LOD distribution is uneven.
-   **When to use:** When rendering isosurfaces at a specific level of detail is required, and the data is stored in a multidimensional tree structure.
-   **When not to use:** When the entire volume needs to be rendered at all LODs simultaneously without culling, or if the tree construction cost outweighs the search savings for small datasets.

## Background
The method originates from the DYNAISOLOD algorithm, which combines dynamic isosurface extraction with level-of-detail techniques in voxel space. It was developed to improve the performance of isosurface rendering by avoiding the generation of triangles for cells that do not intersect the isosurface or are at an inappropriate resolution. The approach builds on the Marching Cubes algorithm, applying it on a cell-by-cell basis only to the relevant cells found via the tree search. [S1, unofficial]
