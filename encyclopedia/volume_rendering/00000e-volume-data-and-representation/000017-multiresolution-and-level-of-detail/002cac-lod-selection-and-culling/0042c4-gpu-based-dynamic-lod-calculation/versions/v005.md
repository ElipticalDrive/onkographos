# GPU-Based Dynamic LOD Calculation

Also called: Compute shader LOD, Ruggedness-aware LOD

## Overview
This method calculates Level of Detail (LOD) for visible tiles entirely on the GPU using a compute shader, replacing traditional CPU-side calculations based on viewpoint distance and screen-space error [S1]. It distinguishes itself by incorporating terrain ruggedness into the LOD decision, ensuring higher resolution for complex terrain features even at similar distances [S1]. It addresses the computational bottleneck of CPU-side LOD determination when thousands of tiles are visible [S1].

## How it works
**Inputs:**
*   Viewpoint position and field of view ($\theta$) [S1].
*   Tile geometry: center position, ground resolution ($r$), and elevation data for ruggedness calculation [S1].
*   Parameters: allowable screen-space error threshold ($\epsilon$), ruggedness weight coefficient ($\alpha$) [S1].

**Outputs:**
*   LOD level for each visible tile [S1].
*   Vertex buffer offset corresponding to the selected LOD level [S1].

**Data Structures:**
*   Tile metadata buffer containing: tile center coordinates, ground resolution $r$, and precomputed or dynamically computed normalized standard deviation of elevation $\sigma$ [S1].
*   Output buffer for LOD levels and vertex offsets [S1].

**Parameters:**
*   $\theta$: Field of view [S1].
*   $r$: Ground resolution of the tile in meters per pixel [S1].
*   $\epsilon$: Allowable screen-space error threshold. Typical value: 1–2 pixels [S1].
*   $\sigma$: Normalized standard deviation of elevation values within the tile, reflecting terrain ruggedness [S1].
*   $\alpha$: Coefficient adjusting the influence weight of terrain relief. Value: $\alpha=0.5$ [S1].

**Steps:**
1.  **Frustum and Occlusion Culling:** Determine visible tiles using parallel compute shader strategies, potentially drawing on WebGPU compute pipeline techniques [S1].
2.  **Ruggedness Calculation:** For each visible tile, compute $\sigma$, the normalized standard deviation of elevation values within the tile [S1].
3.  **LOD Calculation:** Compute the LOD level using the following formula [S1]:
    $$ \text{LOD} = \max\left(0, \left\lfloor \log_2\left( \frac{d \cdot \tan(\theta/2)}{r \cdot \epsilon \cdot (1 + \alpha \cdot \sigma)} \right) \right\rfloor \right) $$
    Where:
    *   $d$ is the distance from the tile center to the viewpoint [S1].
    *   $\theta$ is the field of view [S1].
    *   $r$ is the ground resolution of the tile (meters per pixel) [S1].
    *   $\epsilon$ is the allowable screen-space error threshold [S1].
    *   $\alpha$ is the ruggedness weight coefficient [S1].
    *   $\sigma$ is the normalized standard deviation of elevation values within the tile [S1].
4.  **Output Generation:** Output the calculated LOD level and the corresponding vertex buffer offset for each tile [S1].
5.  **Dynamic Assembly:** Extract the vertex grid at the corresponding resolution from the raw elevation data based on the calculated LOD level [S1].
6.  **LOD Blending (Mitigation):** To prevent visual "popping" artifacts during LOD transitions, perform linear interpolation of LOD levels in the vertex shader [S1]. For each vertex, calculate $t$ as the ratio of the minimum distance from the vertex to the tile boundary to the tile's inscribed circle radius ($t \in [0,1]$) [S1]. Compute the interpolated LOD level as:
    $$ \text{LOD}_{\text{interpolated}} = (1 - t) \cdot \text{LOD}_{\text{current}} + t \cdot \text{LOD}_{\text{neighbor}} $$
    Use this interpolated level for vertex position sampling [S1].

**Pseudocode:**
```python
import math

def compute_lod(tile_center, viewpoint, fov, ground_resolution, elevation_data, epsilon=1.5, alpha=0.5):
    # 1. Frustum/Occlusion Culling (Parallelized on GPU)
    if not is_visible(tile_center, viewpoint, fov):
        return None

    # 2. Calculate Ruggedness (Sigma)
    sigma = calculate_normalized_std_dev(elevation_data)

    # 3. Calculate LOD
    d = distance(tile_center, viewpoint)
    numerator = d * math.tan(fov / 2.0)
    denominator = ground_resolution * epsilon * (1.0 + alpha * sigma)
    lod_value = math.log2(numerator / denominator)
    lod_level = max(0, math.floor(lod_value))

    # 4. Output LOD and Vertex Offset
    vertex_offset = get_vertex_offset_for_lod(tile_center.base_offset, lod_level)
    return lod_level, vertex_offset

def calculate_normalized_std_dev(elevation_data):
    n = len(elevation_data)
    if n == 0:
        return 0.0
    mean = sum(elevation_data) / n
    variance = sum((e - mean) ** 2 for e in elevation_data) / n
    std_dev = math.sqrt(variance)
    # Normalization method not specified in sources [G]
    elevation_range = max(elevation_data) - min(elevation_data)
    if elevation_range == 0:
        return 0.0
    return std_dev / elevation_range

def vertex_shader_interpolation(vertex_pos, tile_current_lod, tile_neighbor_lod, boundary, inscribed_radius):
    # Calculate t

    if inscribed_radius == 0:
        t = 0.0
    else:
        t = dist_to_boundary / inscribed_radius
    t = max(0.0, min(1.0, t))

    # Interpolate LOD
    interpolated_lod = (1.0 - t) * tile_current_lod + t * tile_neighbor_lod
    return interpolated_lod
```

**Edge Cases and Pitfalls:**
*   **LOD Popping:** Discrete jumps in LOD levels cause visual artifacts. Mitigated by linear interpolation in the vertex shader [S1].
*   **Division by Zero:** Ensure $r$, $\epsilon$, and inscribed circle radius are non-zero [G].
*   **Ruggedness Calculation:** The normalization method for $\sigma$ is not explicitly defined in the sources, only that it is a "normalized standard deviation" [S1]. [G] A common approach is normalization by the data range.

## Operating characteristics
*   **Time Complexity:** Parallel computation per tile in the compute shader reduces CPU overhead, scaling with the number of visible tiles [S1].
*   **Memory Complexity:** Requires storage for tile metadata, elevation data, and output buffers for LOD levels and offsets [S1].
*   **Performance:** Offloads LOD calculation from CPU to GPU, beneficial when thousands of tiles are visible [S1].
*   **Strengths:** Reduces CPU bottleneck, incorporates terrain ruggedness for better visual quality, parallelizable [S1].
*   **Limitations:** Requires GPU compute shader support, potential for visual popping if blending is not implemented [S1].
*   **When to Use:** Large-scale terrain rendering with many visible tiles, where CPU LOD calculation is a bottleneck [S1].

## Background
This method was introduced in the paper "Efficient Parsing and Rendering of Large-Scale Terrain Data Based on WebGPU" [S1]. It addresses the limitations of CPU-side LOD calculation by migrating the process to the GPU compute shader, leveraging parallelization strategies from WebGPU and big data processing techniques for large-scale terrain mapping [S1]. The parameter $\alpha=0.5$ was determined through testing on 30 terrain samples to minimize root-mean-square pixel error [S1].
