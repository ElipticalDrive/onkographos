# Hierarchical Culling & Multi-resolution Approximation

Also called: Multi-resolution volume hierarchy, Visibility hierarchy

## Overview
Hierarchical Culling & Multi-resolution Approximation accelerates volume rendering by organizing data into a spatial hierarchy to discard invisible regions and approximate visible regions at lower resolutions [S1]. It distinguishes itself from sibling methods by combining explicit frustum culling of subregions with hardware-assisted cell projection for exploration, rather than relying solely on error metrics or temporal coherence [S1, S3].

## How it works
**Inputs and Outputs:**
* **Input:** A precomputed spatial hierarchy of the volume data, a camera position and orientation defining the view frustum, a scale factor $s$ controlling the zoom level, and a target frame time $t_{\text{target}}$ [S1, S3].
* **Output:** A rendered image using full resolution for final output or hardware-assisted cell projection for exploration [S1].

**Data Structures:**
The method relies on a hierarchy of the volume data, typically an octree or similar space-partitioning structure where nodes represent subregions [S1][S2, unofficial]. The hierarchy allows for efficient pruning of cells outside the view frustum [S3].

**Steps:**
1. **Build Hierarchy:** Construct a hierarchy of the volume data [S1].
2. **Frustum Culling:** Test the bounding volumes of subregions against the view frustum [S1].
    * If a subregion is fully invisible, discard it entirely [S1].
    * If visible, proceed to resolution selection [S1].
3. **Resolution Selection & Rendering:**
    * For final image quality, render using the full resolution of the visible cells [S1].
    * For exploration, render using an approximated version via hardware-assisted cell projection [S1].
    * Alternatively, for surface-based hierarchical rendering, compute an estimated projected size for each cell [S3].
        * If the projected size is smaller than a pixel, avoid visiting children and draw the surface element of the current cell instead [S3].
        * Stop hierarchy exploration when the projection of the current cell becomes too small [S3].

**Parameters:**
* **Scale Factor ($s$):** Controls the zoom level. Tested range is 1.0 to 5.16. Scales of 256 and larger are required to view these volumes effectively [S1].
* **Minimum Projected Size:** A global minimum projected size that can be edited by the user to control the number of displayed cells at each frame [S3].

**Edge Cases and Pitfalls:**
* At low scales (e.g., scale 1), the hierarchy overhead may make rendering slightly slower than non-hierarchical rendering [S1].
* Significant speedups are only achieved when zoomed in considerably (e.g., scale 256), where it can be about twice as fast [S1].
* For large volumes, gains may be more significant even at lower scales, but the hierarchy must be robust enough to handle the data size [S1].

**Pseudocode:**
```python
def render_hierarchical_volume(hierarchy, camera, scale_factor, t_target):
    # Precomputed hierarchy is passed in as per [S1]
    min_proj = 1.0  # Global minimum projected size in screen pixels [S3]
    render_list = []

    def traverse_node(node):
        # Step 2: Frustum Culling
        if not is_aabb_frustum_test(node.bounding_box, camera.frustum_planes):
            return  # Discard invisible subregion [S1]

        # Step 3: Resolution Selection
        # Projected size estimation from cell size and distance to screen plane [S3]
        cell_size = node.bounding_box.diagonal_length()
        dist_to_screen = camera.distance_to_projection_plane(node.center)
        projected_size = (cell_size * dist_to_screen) / camera.focal_length

        # LOD selection: stop exploration when projection is too small [S3]
        if projected_size < min_proj:
            # Use hardware-assisted cell projection for exploration [S1]
            # or draw surface element if using surface-based hierarchy [S3]
            render_list.append((node, 'approximated'))
            return

        # If leaf node or full resolution required [S1]
        if node.is_leaf():
            render_list.append((node, 'full'))
        else:
            # Recurse into children
            for child in node.children:
                traverse_node(child)

    traverse_node(hierarchy.root)

    # Render the collected list
    for node, resolution in render_list:
        if resolution == 'full':
            # Standard volume raycasting or scanline on full resolution data [S1]
            render_full_resolution(node)
        else:
            # Hardware-assisted cell projection for exploration [S1]
            render_projected_approximation(node)

    # Dynamic adjustment of minimum projected size to maintain framerate [S3]
    t_frame = get_current_frame_time()
    delta_t = t_frame - t_target
    # Use third power of difference to minimize influence near goal, emphasize when far, keeping sign [S3]
    growth_factor = 1.0 + (delta_t ** 3) * 0.01
    min_proj *= growth_factor
    # When idle, reduce limit projected size close to zero [S3]
    if abs(delta_t) < 0.001:
        min_proj *= 0.9

def is_aabb_frustum_test(aabb, frustum_planes):
```

## Subtopics

### [Coarse Floor Rendering](5760-coarse-floor-rendering.md)
Coarse Floor Rendering prevents scene flicker during chunk plan swaps in hierarchical volume rendering by rendering the coarsest pyramid level as a continuous whole-volume floor behind the active octree. Unlike previous implementations where unmatched bricks were synchronously destroyed and revealed the scene background, this method ensures no brick draws nothing while waiting for re-stream, providing continuous coverage.

### Frustum Culling for Volumetric Data
Frustum culling eliminates elements outside the view frustum to save memory transfer and generation, performed hierarchically on the data structure before data generation and transfer [S2, unofficial]. Unlike surface rendering where culling is for rendering economy, here it is crucial for memory transfer and space savings because volumetric data sizes are very large (e.g., 256^3 voxels at 32-bit is 65MB, 512^3 is 500MB) [S2, unofficial].

### Projected Size LOD with Frustum Culling
Projected Size LOD with Frustum Culling dynamically adjusts level-of-detail based on screen-space footprint rather than fixed distance thresholds [S3]. It is chosen when interactive frame rates must be maintained during user interaction, as it automatically scales displayed complexity to match available rendering time [S3].

## Operating characteristics
* **Time Complexity:** The hierarchy provides significant speedups only when zoomed in considerably [S1]. At scale 1, the hierarchy is slightly slower than non-hierarchical rendering; at scale 256, it is about twice as fast [S1].
* **Memory Complexity:** The hierarchy itself adds overhead, but culling reduces the amount of data transferred and processed [S2, unofficial].
* **Measured Performance:** On the Lockheed fighter dataset, rendering every cell with the scanline algorithm took over 3 minutes. Using the hierarchy to draw an approximated version took less than 3 seconds [S1].
* **Strengths:** Significant performance gains for large volumes when zoomed in; effective for exploration via approximation [S1].
* **Limitations:** Overhead at low zoom levels; approximation quality may be lower than full resolution [S1].
* **When to Use:** Large-scale volume exploration where interactive frame rates are needed for approximation, or final rendering at high zoom levels [S1].
* **When Not to Use:** Low zoom levels where the hierarchy overhead outweighs culling benefits [S1].

## Background
The method was introduced in the context of hierarchical and parallelizable direct volume rendering for irregular and multiple grids [S1]. It builds on the principles of spatial hierarchies and frustum culling, adapting them for the large data sizes typical of volumetric datasets [S2, unofficial]. The approach was further refined with resolution adaptive techniques for volume sculpting, incorporating dynamic LOD selection based on projected size [S3].
