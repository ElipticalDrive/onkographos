# Mesh Level of Detail

Also called: Mesh LOD

## Overview
Mesh Level of Detail is a secondary optimization system applied to individual mesh instances within a voxel-based instancing framework to reduce vertex count based on distance [S1]. It operates on top of the primary spatial LOD system (such as terrain or brick LOD), allowing distinct geometric resolutions for the same logical object type as the viewer approaches [S1]. Unlike primary volume LOD which changes the data representation (e.g., voxel resolution), this method swaps the entire mesh asset used for rendering [S1]. It is specifically designed for `VoxelInstanceLibraryMultiMeshItem` to avoid the overhead of duplicating scene objects or managing separate visibility ranges for each resolution variant [S1].

## How it works
The system maintains a hierarchy of mesh assets associated with a single logical instance type. The renderer selects the appropriate mesh based on the instance's distance from the camera relative to the primary terrain LOD's view distance.

**Inputs and Outputs:**
*   **Input:** A list of visible voxel instances, each associated with a `VoxelInstanceLibraryMultiMeshItem`.
*   **Output:** A set of draw calls using the selected mesh resolution for each instance.

**Data Structures:**
The core data structure is `VoxelInstanceLibraryMultiMeshItem`. It contains specific properties for mesh LODs:
*   `mesh`: The base mesh (LOD0).
*   `mesh_lod_1`: The mesh for the first LOD transition (LOD1).
*   `mesh_lod_2`: The mesh for the second LOD transition (LOD2).
*   `mesh_lod_3`: The mesh for the third LOD transition (LOD3).
*   *Note:* If only `mesh` is set, no LOD is used. Fewer than 4 LODs can be simulated by assigning the same mesh to multiple slots [S1].

**Parameters:**
*   **LOD Switch Distances:** Defined as ratios $r_i$ (typically $0 \le r_i \le 1$) relative to the view distance $D_{terrain}$ of the corresponding terrain LOD level [S1].
    *   Let $D_{terrain}$ be the maximum render distance for the current terrain LOD index.
    *   The switch distance for LOD $i$ is $D_{switch, i} = r_i \times D_{terrain}$.
*   **Maximum LOD Distance:** The distance corresponding to the last defined LOD mesh. Instances beyond this distance can be hidden from rendering [S1].

**Algorithm:**
1.  **Retrieve Distance:** For each visible instance, calculate its Euclidean distance $d$ from the camera.
2.  **Determine Terrain LOD:** Identify the current terrain LOD index and its associated view distance $D_{terrain}$ [S1].
3.  **Calculate Thresholds:** Compute the switch distances $D_{switch, 1}, D_{switch, 2}, D_{switch, 3}$ using the configured ratios [S1].
4.  **Select Mesh:**
    *   If $d > D_{switch, 3}$, select `mesh_lod_3`.
    *   Else if $d > D_{switch, 2}$, select `mesh_lod_2`.
    *   Else if $d > D_{switch, 1}$, select `mesh_lod_1`.
    *   Else, select `mesh` (LOD0).
5.  **Cull Distant Instances:** If $d$ exceeds the maximum distance of the last defined LOD mesh (or a configured global maximum), mark the instance as hidden. The instance is still generated in memory but not rendered [S1].
6.  **Render:** Issue draw calls using the selected mesh for all visible instances.

**Edge Cases and Pitfalls:**
*   **Performance Issue:** Changing `MultiMesh.mesh` to a different LOD dynamically may cause performance issues or glitches in the underlying engine implementation [S1].
*   **Generation vs. Rendering:** Hiding instances beyond the max LOD distance does not stop their generation, only their rendering [S1]. This is useful if the terrain itself has no LOD, but adds CPU overhead for culling [S1].
*   **Editor Limitations:** Manual editing of instances in the editor is not supported; instances must be defined via procedural generation [S1].

## Subtopics

## Operating characteristics
*   **Complexity:** The selection logic is $O(1)$ per instance, involving simple distance comparisons. The primary cost is the memory overhead of storing multiple mesh variants per instance type and the CPU cost of generating instances that are subsequently culled [S1].
*   **Strengths:** Reduces vertex count for distant objects without requiring complex geometry simplification algorithms at runtime. Allows for "impostor" techniques (e.g., using simple quads for distant trees) [S1]. Avoids the scene graph overhead of managing separate objects for each LOD level [S1].
*   **Limitations:** Limited to 4 LOD levels (LOD0-LOD3) per instance type [S1]. Switching meshes dynamically may incur performance penalties [S1]. Does not reduce the cost of instance generation, only rendering [S1].
*   **When to use:** When rendering large numbers of identical objects (e.g., forests) where distant objects can be represented by lower-poly meshes or impostors [S1]. When the primary volume LOD is insufficient for mesh-level detail control [S1].

## Background
This system was introduced in the Voxel Tools addon for Godot 4 to address the lack of automatic mesh LOD in Godot 3 [S1]. It serves as an alternative to using Visibility Ranges with MultiMesh, which requires duplicating data and increasing the number of scene objects to process [S1]. Godot 4 later added automatic mesh LOD, but this system remains for users requiring fine-grained control over mesh and material assignment per LOD level [S1].
