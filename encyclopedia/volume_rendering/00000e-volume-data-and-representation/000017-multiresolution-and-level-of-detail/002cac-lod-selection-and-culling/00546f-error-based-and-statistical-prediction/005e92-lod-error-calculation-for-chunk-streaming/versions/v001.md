# LOD Error Calculation for Chunk Streaming

Also called: Chunk Streaming LOD Error

## Overview
This method determines the appropriate Level of Detail (LOD) for volumetric chunks in a streaming pipeline by comparing a geometric error metric against a distance-based threshold. It solves the problem of balancing visual fidelity with VRAM constraints in large-scale voxel scenes by deciding when to subdivide a chunk or load it at its current resolution. It differs from statistical methods like [Histogram Spectra for LOD Selection](11687-histogram-spectra-for-lod-selection.md) by using a simple geometric distance formula rather than precomputed data histograms to estimate error.

## How it works
**Inputs and Outputs:**
*   **Inputs:** `ChunkSize` (scalar, e.g., side length in world units), `StreamingFactor` (scalar multiplier), `ChunkCenterPos` (3D vector), `CameraPos` (3D vector).
*   **Output:** `LODError` (scalar). The sign of this value dictates the streaming action.

**Data Structures:**
No complex data structures are required for the calculation itself. The calculation is performed per chunk.

**Steps:**
1.  Calculate the Euclidean distance between the camera and the chunk center:
    $$ d = ||\text{ChunkCenterPos} - \text{CameraPos}|| $$
2.  Calculate the LOD Error using the formula:
    $$ \text{LODError} = (\text{ChunkSize} \times \text{StreamingFactor}) - d $$
3.  Evaluate `LODError`:
    *   If `LODError > 0`: The chunk is too large for the current distance. Further subdivision of the chunk is necessary to reduce the effective `ChunkSize` for the next level.
    *   If `LODError < 0`: The chunk is sufficiently small. The chunk is marked as needing to be loaded at its current LOD.

**Parameters:**
*   **StreamingFactor:** A scalar multiplier for chunk size. It controls the granularity of detail at distance. A larger value results in finer details at greater distances but requires more VRAM. Typical value: $2.0$ [S1].

**Edge Cases and Pitfalls:**
*   **VRAM Management:** When VRAM space is sufficient, chunks closer to the player should be prioritized for loading to ensure high fidelity near the camera [S1].
*   **Subdivision Priority:** When determining loading order, prioritize loading chunks with higher LOD levels (coarser granularity) first. This allows the system to directly remove all associated child blocks (finer LODs) from memory, freeing up VRAM for other chunks [S1].
*   **Zero Distance:** If the camera is inside a chunk, $d=0$, resulting in a positive error, triggering subdivision. This is expected behavior for hierarchical structures.

**Pseudocode:**
```python
def calculate_lod_error(chunk_size: float, streaming_factor: float, chunk_center_pos: Vector3, camera_pos: Vector3) -> float:
    """
    Calculates the LOD error for a volumetric chunk.
    
    Args:
        chunk_size: The side length of the chunk in world units.
        streaming_factor: Scalar multiplier for chunk size (typically 2.0).
        chunk_center_pos: 3D position of the chunk center.
        camera_pos: 3D position of the camera.
        
    Returns:
        LODError: Positive value indicates need for subdivision; negative indicates ready for loading.
    """
    # Calculate Euclidean distance
    distance = vector_length(chunk_center_pos - camera_pos)
    
    # Calculate error
    lod_error = (chunk_size * streaming_factor) - distance
    
    return lod_error

def process_chunk_streaming(chunk: Chunk, camera_pos: Vector3, streaming_factor: float, vram_available: bool) -> Action:
    """
    Determines the action to take for a chunk based on LOD error.
    """
    lod_error = calculate_lod_error(chunk.size, streaming_factor, chunk.center, camera_pos)
    
    if lod_error > 0:
        # Chunk needs further subdivision
        return Action.SUBDIVIDE
    else:
        # Chunk is ready to be loaded
        # Note: Actual loading order depends on VRAM and distance priority
        return Action.LOAD
```

## Subtopics

### Root Geometric Error Resolution
This variant calculates the geometric error for the root node of a tile hierarchy, often used in 3D Gaussian Splatting or tile-based streaming contexts. It determines the base error before refinement.
*   **Step 1:** If `params.minGeometricError` is finite and $> 0.0$, return `rootGeometricErrorFromMinLevel(params.minGeometricError, lodMaxDepth, params.samplingRatePerLevel)` with source 'configured_min_geometric_error' [S2, unofficial].
*   **Step 2:** If `rootNode.ownError` is finite and $> 0.0$, calculate diagonal `diag = sqrt(ex[0]^2 + ex[1]^2 + ex[2]^2)`, return `Math.max(rootNode.ownError, diag * 1e-6, 1e-6)` with source 'estimated_root_simplify' [S2, unofficial].
*   **Step 3 (Fallback):** If `splatCount <= 1`, return `Math.max(diag * 1e-6, 1e-6)`. Else, return `Math.max(diag * 0.125, diag * 1e-6, 1e-6)` with source 'estimated_root_fallback' [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per chunk. The calculation involves basic arithmetic and a vector norm.
*   **Memory Complexity:** $O(1)$ auxiliary space.
*   **Performance:** The method is extremely lightweight, suitable for GPU-driven pipelines where many chunks are evaluated per frame. In tests on large-scale voxel scenes (up to 10 billion voxels at 64^3 resolution), this approach contributed to real-time rendering times of approximately 6 milliseconds per frame [S1].
*   **Strengths:** Simple to implement; low computational overhead; effective for uniform voxel grids where chunk size is constant.
*   **Limitations:** Does not account for data complexity or content variation within the chunk (unlike [Histogram Spectra](11687-histogram-spectra-for-lod-selection.md)). It assumes uniform importance across the chunk. The `StreamingFactor` must be tuned manually for different scenes.
*   **When to use:** Uniform voxel datasets (e.g., Minecraft-like worlds) where geometric distance is the primary driver of visual quality.
*   **When not to use:** Heterogeneous data where some regions contain high-frequency detail regardless of distance, or when VRAM constraints require content-aware LOD selection.

## Background
This method originates from the **Aokana** framework, a GPU-driven voxel rendering system for open-world games [S1]. It was designed to handle massive voxel scales (e.g., 8K resolution per chunk) by leveraging a shallow SVDAG (Sparse Voxel Data Access Graph) structure. The approach references the GPU-Driven rendering pipelines shared by Ubisoft [Haar and Aaltonen 2015] but adapts them for voxel data. The specific formula and streaming logic were validated on scenes like "Greenfield," where one cube corresponds to one voxel [S1]. The method allows for efficient VRAM management by prioritizing the loading of coarser LODs to free up memory from child blocks [S1].
