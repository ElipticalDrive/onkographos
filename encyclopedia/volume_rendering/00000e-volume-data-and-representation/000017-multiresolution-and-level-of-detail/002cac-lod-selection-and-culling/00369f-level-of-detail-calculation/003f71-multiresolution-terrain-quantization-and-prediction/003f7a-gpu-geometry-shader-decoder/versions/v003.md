# GPU Geometry Shader Decoder

Also called: Geometry program terrain decoder, On-the-fly GPU decompression

## Overview
The GPU Geometry Shader Decoder is a method for decompressing multiresolution terrain height data directly on the graphics hardware, bypassing the rasterizer to avoid hardware attribute limits [S1]. It solves the problem of rendering massive terrain datasets by performing variable-length decompression in parallel on the GPU, emitting only height values to a buffer to avoid the 1,024 scalar attribute limit [S1]. Unlike methods that cache decompressed geometry or emit full vertex attributes, this approach decodes patches on-the-fly and renders them immediately, optimizing for throughput by maximizing shared memory utilization and minimizing vertex program threads [S1].

## How it works
The decoder operates as a geometry program (geometry shader) that reads a compressed bitstream and outputs height values [S1]. It relies on the parent method's quantization scheme, specifically the shift values assigned to vertex types (Corner, Leg, Hypotenuse, Interior) [S1].

### Inputs and Outputs
*   **Inputs**:
    *   Pointer to a texture buffer in GPU memory containing the compressed bitstream [S1].
    *   Offset into the texture buffer indicating the start of the current patch's bitstream [S1].
    *   Three quantization shift values corresponding to the vertex types defined in the parent method [S1].
*   **Outputs**:
    *   A buffer containing only the reconstructed height values ($z$) for the terrain patch [S1]. These values are later accessed in a second rendering pass to generate full geometry (position, normals, etc.) [S1].

### Data Structures
*   **Bitstream State**: A 32-bit register (`s.word`) acts as a buffer for bits read from the texture [S1]. A pointer (`s.ptr`) tracks the current position in the texture buffer [S1]. A counter (`s.bits`) tracks the number of valid bits currently buffered in `s.word` [S1].
*   **Register Storage**: A small set of registers holds the height values of the current and previous rows to facilitate prediction [S1]. Specifically, values $z[i-2]$, $z[i-1]$, and $z[i]$ are maintained to predict row $i+1$ [S1].

### Algorithm Steps
1.  **Initialization**: Read the first three height values verbatim from the bitstream and emit them to the output buffer [S1]. These serve as the base for subsequent predictions [S1].
2.  **Row-by-Row Decoding**: Iterate through the terrain patch row by row [S1]. For each row $i$:
    *   Maintain only one row of height values in registers, as only the previous row is needed to generate the next [S1].
    *   For each vertex in the row:
        1.  **Prediction**: Calculate the predicted height using parallelogram prediction based on previously decoded vertices [S1]. The source pseudocode uses a specific accumulator logic for this prediction [S1].
        2.  **Residual Read**: Read the next residual value from the variable-length bitstream [S1].
        3.  **Quantization**: Left-shift the residual according to the vertex's quantization level (determined by its type: Corner, Leg, Hypotenuse, Interior) [S1].
        4.  **Reconstruction**: Add the shifted residual to the predicted height to obtain the final height value [S1].
        5.  **Emission**: Emit the reconstructed height value to the output buffer [S1].
3.  **Variable-Length Bitstream Reading**: Implement efficient, conditional-free reads from the bitstream [S1]. Bits enter a 32-bit register from the right 16 bits at a time [S1]. At most 16 bits are read from the left side of the buffer [S1]. An underflow signal triggers a fetch of another 16 bits from the texture buffer, advancing the pointer [S1].

### Pseudocode
The following pseudocode represents the decoder logic [S1]. The loops are manually unrolled in the actual implementation to avoid conditionals and maximize SIMD parallel execution [S1].

```python
# Stream state: s['word'] (32-bit buffer), s['ptr'] (texture buffer pointer), s['bits'] (valid bits count)
def read_bits(n):
    s['bits'] -= n
    m = s['bits'] & 16  # Extracts 16 if underflow, 0 otherwise [G]
    s['bits'] += m
    s['word'] <<= m
    s['ptr'] += m
    value = s['word'] >> s['bits']
    s['word'] -= value << s['bits']
    return value

def read_residual():
    # Bit length determined by RBUC entropy coding; not specified in sources [G]
    n = get_bit_length_from_header() # [G]
    return read_bits(n)

def read_verbatim():
    return read_bits(32)

# Decoder logic
z = [read_verbatim(), read_verbatim(), read_verbatim()]
emit(z[0])
emit(z[1])
emit(z[2])

for i in range(2, n + 1):
    # Initialize accumulator with parallelogram prediction base and first residual
    s = z[i-2] + z[i] + read_residual()
    z[i+1] = z[i-1]
    z[i-1] += s
    # Reconstruct first vertex of row i with quantization shift
    z[i] = z[i-1] + z[i+1] - z[i-2] + (read_residual() << shift)
    emit(z[i])
    emit(z[i-1])
    for j in range(i - 2, -1, -1):
        s += read_residual()
        z[j] += s
        emit(z[j])
```

### Parameters
*   **Quantization Shifts**: Three integer values passed to the shader, corresponding to the shift amounts for Corner, Leg, Hypotenuse, and Interior vertices as defined in the parent method [S1].
*   **Buffer Size**: The output buffer must be large enough to hold the $z$ values of the displayed geometry after frustum culling, typically on the order of a few megabytes [S1].
*   **Instruction Count Limit**: The unrolled program instruction count currently limits the output to 35 rows, although the buffer size allows up to 62 rows [S1].

### Edge Cases and Pitfalls
*   **Hardware Attribute Limits**: OpenGL/hardware limits geometry programs to 1,024 scalar attributes (e.g., on NVIDIA GeForce GTX 280) [S1]. Emitting all attributes (xy, z, texcoords, normals) would limit patch size due to vertex replication on boundaries [S1]. The decoder bypasses this by emitting only $z$ values [S1].
*   **Instruction Count**: The unrolled program instruction count limits the number of rows that can be decoded in a single pass [S1]. The current implementation supports 35 rows, while the buffer supports 62 [S1].
*   **Precision**: The residual values are left-shifted according to the quantization level [S1]. Incorrect shift values will result in incorrect height reconstruction [S1].
*   **Output Capacity**: The 4,096 bytes of output available to a geometry program is significantly more than the 128 bytes available to a fragment program, but still restricts attribute emission [S1].

## Subtopics

### [Adapt-Decompress-Draw Rendering Pipeline](10013-adapt-decompress-draw-rendering-pipeline.md)
The Adapt-Decompress-Draw pipeline is a three-stage rendering system for multiresolution terrain that decodes compressed height data on the GPU and renders it as triangles without maintaining a persistent cache of decompressed geometry. It solves the problem of rendering massive terrain datasets by performing variable-length decompression directly into a transform feedback buffer, bypassing the rasterizer during the decode phase to avoid attribute limits. Unlike sibling methods that cache geometry, this pipeline adapts the visible patch cut on the CPU, decodes it in parallel on the GPU, and immediately draws it, optimizing for throughput by minimizing vertex program threads and maximizing shared memory utilization.

## Operating characteristics
*   **Time Complexity**: The decoder is free of conditionals and loops (loops are unrolled), executing a fixed number of instructions per patch [S1]. It requires 11 assembly instructions per bitstream read [S1]. The average instruction count is 22.2 per vertex without quantization and 23.5 with quantization [S1].
*   **Memory Complexity**: The decoder uses a small buffer for the output height values, on the order of a few megabytes, depending on the visible geometry after frustum culling [S1]. No caching of decompressed geometry is used, simplifying implementation [S1].
*   **Performance**: The method exploits parallelism by decoding rows in parallel on the GPU [S1]. The use of geometry shaders allows for the generation of geometry on-the-fly, reducing memory bandwidth usage compared to CPU-based decoding [S1].
*   **Strengths**: High throughput due to parallel execution; bypasses rasterizer attribute limits; no need for persistent cache; efficient variable-length bitstream reading [S1].
*   **Limitations**: Instruction count limits the number of rows per patch (35 rows currently); hardware-specific attribute limits (1,024 scalar attributes) necessitate the output-only-height approach; requires manual unrolling of loops [S1].
*   **When to Use**: Suitable for rendering massive terrain datasets where memory bandwidth is a bottleneck and the GPU has sufficient instruction count capacity for the desired patch size [S1].
*   **When Not to Use**: When the terrain patch size exceeds the instruction count limit (35 rows) and cannot be subdivided further; when full vertex attributes (normals, texcoords) are needed in the same pass and cannot be generated in a subsequent pass [S1].

## Background
The GPU Geometry Shader Decoder was introduced in the paper "On-the-fly decompression and rendering of multiresolution terrain" [S1]. It was developed to address the limitations of CPU-based decoding and the attribute limits of early geometry shaders (e.g., NVIDIA GeForce GTX 280) [S1]. The method builds on the multiresolution terrain quantization and prediction scheme described in the parent article [S1].
