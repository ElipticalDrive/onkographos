# Level-of-Detail Grammar

Also called: LOD grammar, additive ladders

## Overview
Level-of-Detail (LOD) Grammar is a system for managing scenes that exceed rendering budgets by using additive ladders, substitutive levels, and spatial tiles to adjust detail based on data arrival, distance, and screen position [S1, unofficial]. It enables scalable interactive web visualization of multidimensional scientific data by allowing scenes to outgrow a single rendering budget [S1, unofficial]. Unlike [Additive levels of detail for Gaussian splats](3114-additive-levels-of-detail-for-gaussian-splats.md) which focuses on specific splat optimization, or [CP-LOD](9646-cp-lod-coverage-preserving-prefix-lod.md) which preserves coverage via prefix ordering, LOD Grammar provides a general structural grammar for the archive layout and streaming strategy [S1, unofficial].

## How it works
The method operates on a compiled archive (e.g., `.luxar.zarr`) containing spatial tiles and hierarchical LOD groups.

**Inputs and Outputs:**
*   **Input:** A scene description including Gaussian splats, points, lines, meshes, and annotations, along with their spatial coordinates and attributes.
*   **Output:** A hierarchical archive structure (e.g., Zarr format) containing LOD groups and spatial chunks, served via static HTTP.

**Data Structures:**
The archive structure includes specific directories for LOD groups. For a Gaussian splat layer named `nuclei`, the layout is:
```text
nuclei/
├─ centers
├─ cholesky
├─ amplitudes
├─ chunk_bounds
└─ additive_0 … additive_3 (LOD)
```
*   `centers`, `cholesky`, `amplitudes`: Standard Gaussian splat attributes.
*   `chunk_bounds`: Spatial boundaries for tiling.
*   `additive_0 … additive_3`: Hierarchical LOD levels, where `additive_0` is the coarsest base.

**Steps:**
1.  **Compile Scene:** The scene is compiled into the archive structure. Gaussian splats are fitted to the data, with a cross-validated choice of splat count [S1, unofficial].
2.  **Create Additive Ladders:** For each layer, multiple LOD levels are generated (`additive_0` to `additive_3`). These form an additive ladder where `additive_0` provides a coarse representation [S1, unofficial].
3.  **Spatial Tiling:** Data is divided into spatial tiles using `chunk_bounds`. This allows distant or off-screen objects to be represented by fewer tiles or lower LOD levels [S1, unofficial].
4.  **Streaming and Selection:**
    *   **Data Arrival:** The coarse scene is painted from the first chunk (`additive_0`). As more data arrives, higher additive levels are streamed and added to sharpen the image [S1, unofficial].
    *   **Distance/Screen Position:** Substitutive levels and spatial tiles are selected based on the projected splat footprint. Distant or off-screen objects use coarser substitutive levels or are culled entirely [S1, unofficial].
5.  **Rendering:** A client-side viewer (WebGL/WebGPU) renders the selected tiles and LOD levels. A client-side cache with prefetching hides network latency during orbit or dimension scrubbing [S1, unofficial].

**Parameters:**
*   **LOD Levels:** The number of additive levels (e.g., 4 levels: `additive_0` to `additive_3`) is determined by the scene complexity and budget [S1, unofficial].
*   **Splat Count:** Cross-validated to fit GPU memory and rendering budget [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Network Latency:** Without prefetching, LOD selection may cause visible stuttering during camera movement [S1, unofficial].
*   **Budget Exceedance:** If the scene exceeds the rendering budget even with LOD, the system may fail to maintain interactivity [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Rendering time depends on the number of visible tiles and LOD levels selected. Streaming time depends on network latency and chunk size.
*   **Memory Complexity:** GPU memory usage is proportional to the number of visible splats/points at the selected LOD levels.
*   **Measured Performance:** Scales from a handful of primitives to millions of points and splats while remaining interactive [S1, unofficial].
*   **Strengths:** Enables interactive visualization of large multidimensional datasets in the browser. Handles scenes that outgrow a single rendering budget.
*   **Limitations:** Requires a compiled archive structure. Performance depends on network conditions for streaming.
*   **When to Use:** For web-based visualization of large scientific datasets (e.g., microscopy) where interactivity is required.
*   **When Not to Use:** For offline rendering or when network access is unavailable.

## Background
LOD Grammar was introduced in the Luxar system for Gaussian splatting for microscopy and scalable interactive web visualization of multidimensional scientific data [S1, unofficial]. It addresses the challenge of visualizing large nD datasets in browsers by combining additive ladders for progressive detail and spatial tiling for culling [S1, unofficial].
