# View-dependent data loading

Also called: Frustum-based scene culling, Level-of-detail based geometry and texture loading, View-Dependent Rendering, frustum-based multiresolution loading

## Overview
View-dependent data loading is a strategy for interactive exploration of massive volumetric datasets on limited hardware by loading only the spatial extent and resolution necessary for the current camera view [S1]. It combines frustum-based scene culling with level-of-detail (LOD) selection to reduce data requests and facilitate navigation [S1]. Unlike static LOD systems that precompute full-resolution pyramids for the entire dataset, this method dynamically determines the minimum resolution required per frame based on the projected size of volume units relative to screen pixels, avoiding the storage and computational overhead of precomputed hierarchies for extremely large 3D volumes [S1].

## How it works
The method determines which subset of a multiresolution dataset (e.g., IDX format) to load by analyzing the camera's relationship to the data volume [S1]. It ensures that the loaded data provides approximately one voxel per screen pixel, balancing visual fidelity with memory and bandwidth constraints [S1].

### Inputs and Outputs
*   **Inputs:**
    *   Camera parameters: Model-view-projection (MVP) matrix or equivalent frustum definition (near/far planes, aspect ratio, field of view) [S1].
    *   Data volume bounds: The 3D bounding box of the dataset [S1].
    *   Multiresolution hierarchy metadata: The reduction factor per level (e.g., HZ levels where each level halves the resolution in one direction) [S1].
    *   Screen resolution: Width and height in pixels [S1].
*   **Outputs:**
    *   Spatial extent: The sub-volume of the dataset to load (clipped by the frustum) [S1].
    *   Resolution level: The specific LOD index to load for that sub-volume [S1].

### Data Structures
The implementation relies on the multiresolution format's metadata [S1]. For IDX formats, this includes the root resolution and the reduction factor per level [S1]. No additional precomputed pyramid structures are stored in memory for the culling logic itself; the hierarchy is accessed on-demand [S1].

### Steps
1.  **Frustum Clipping (Spatial Culling):** Apply the camera's viewing frustum clip planes (derived from model, viewing, and projection transformations) to the 3D bounding box of the data volume [S1]. Determine the intersection of the frustum and the data volume [S1]. This defines the spatial extent of the data to be loaded; data outside this intersection is discarded [S1].
2.  **Projection and Sampling Ratio Calculation:** Project a unit of the data volume (e.g., a single voxel or a grid cell at the current LOD) onto the 2D camera viewing plane [S1]. Calculate the projected area of this unit on the screen [S1]. Compare this to the area of a single screen pixel (in screen space units) [S1].
3.  **Resolution Level Determination:** Calculate the ratio $N$ of the projected area of the volume unit to the area of one screen pixel [S1]. If $N$ volume units project to cover one pixel, then $1/N$ resolution data is sufficient [S1]. Let $A_{\text{pixel}}$ be the area of one screen pixel and $A_{\text{unit}}$ be the projected area of a volume unit at the base resolution [S1]. The ratio is $R = A_{\text{unit}} / A_{\text{pixel}}$ [S1]. The minimum resolution level $L$ is chosen such that the effective sampling density matches the screen resolution [S1]. Specifically, the level is determined such that a unit of the data volume covers approximately one pixel on the screen [S1].
4.  **LOD Selection:** Using the hierarchy's reduction factor, select the coarsest level $L$ that satisfies the condition derived in Step 3 [S1]. For HZ formats, each level reduces resolution by half in one direction [S1]. The selected level $L$ and the clipped spatial extent from Step 1 define the data request [S1].

### Formulas
Let $P$ be the projection of a volume unit onto the screen [S1].
Let $S$ be the area of one screen pixel [S1].
The number of volume units covering one pixel is:
$$ N = \frac{\text{Area}(P)}{S} $$
The condition for sufficient resolution is that the loaded data unit projects to approximately one pixel [S1]. If the current level $L$ has a resolution reduction factor of $2^L$ (assuming binary halving per level in the relevant dimension), the projected area scales by $1/4^L$ (for area) or $1/2^L$ (for linear dimension) [S1]. The source states: "if 4 volume units project to one pixel, 1/4 resolution data is sufficient" [S1]. This implies a linear scaling relationship where the required level $L$ satisfies:
$$ \text{Projected Size at Level } L \approx \text{Pixel Size} $$
The exact level index is the smallest integer $L$ such that the projected area of a unit at level $L$ is less than or equal to the area of one pixel, or equivalently, the linear dimension of the projected unit is less than or equal to the pixel dimension [S1].

### Parameters
*   **HZ level reduction factor:** Each HZ level reduces the resolution by half in one direction [S1].
*   **Target coverage:** One pixel per volume unit (approximately) [S1].

### Edge Cases and Pitfalls
*   **Over-sampling:** Loading higher resolution than necessary wastes time and memory because multiple data units are averaged over the same pixel [S1].
*   **Under-sampling:** Loading lower resolution results in an overly coarse or "jaggy" image [S1].
*   **Extreme Distances:** When the camera is very far, the projected area becomes very small, potentially requiring the coarsest level [G]. The system must handle the case where the required level exceeds the available hierarchy depth [G].
*   **Extreme Proximity:** When the camera is very close, the projected area exceeds the pixel area significantly [G]. The system must load the finest available level and may need to handle sub-voxel sampling or tiling if the volume unit spans multiple pixels [G].

### Pseudocode
```python
import math

def view_dependent_loading(camera, volume_bounds, hierarchy):
    """
    Determine the spatial extent and resolution level to load.
    
    Args:
        camera: dict with 'mvp' (4x4 matrix), 'screen_width', 'screen_height'.
        volume_bounds: tuple (min_x, min_y, min_z, max_x, max_y, max_z).
        hierarchy: dict with 'max_level' and 'reduction_factor' (default 2).
        
    Returns:
        sub_volume: The clipped bounding box to load, or None if outside frustum.
        lod_level: The integer index of the resolution level to load.
    """
    def transform_point(p, mvp):
        w = mvp[3][0]*p[0] + mvp[3][1]*p[1] + mvp[3][2]*p[2] + mvp[3][3]
        return (
            (mvp[0][0]*p[0] + mvp[0][1]*p[1] + mvp[0][2]*p[2] + mvp[0][3]) / w,
            (mvp[1][0]*p[0] + mvp[1][1]*p[1] + mvp[1][2]*p[2] + mvp[1][3]) / w,
            (mvp[2][0]*p[0] + mvp[2][1]*p[1] + mvp[2][2]*p[2] + mvp[2][3]) / w
        )

    def clip_bounds_to_frustum(bounds, mvp):
        corners = [
            (bounds[0], bounds[1], bounds[2]), (bounds[3], bounds[1], bounds[2]),
            (bounds[0], bounds[3], bounds[2]), (bounds[3], bounds[3], bounds[2]),
            (bounds[0], bounds[1], bounds[4]), (bounds[3], bounds[1], bounds[4]),
            (bounds[0], bounds[3], bounds[4]), (bounds[3], bounds[3], bounds[4])
        ]
        clip_corners = [transform_point(c, mvp) for c in corners]
        min_clip = [min(c[i] for c in clip_corners) for i in range(3)]
        max_clip = [max(c[i] for c in clip_corners) for i in range(3)]
        if min_clip[0] > 1 or max_clip[0] < -1 or \
           min_clip[1] > 1 or max_clip[1] < -1 or \
           min_clip[2] > 1 or max_clip[2] < -1:
            return None
        return (min_clip, max_clip)

    def project_unit_size(mvp, screen_w, screen_h):
        p0 = transform_point((0, 0, 0), mvp)
        p1 = transform_point((1, 0, 0), mvp)
        p2 = transform_point((0, 1, 0), mvp)
        def to_screen(p):
            return ((p[0] + 1) * 0.5 * screen_w, (p[1] + 1) * 0.5 * screen_h)
        s0, s1, s2 = to_screen(p0), to_screen(p1), to_screen(p2)
        width = abs(s1[0] - s0[0])
        height = abs(s2[1] - s0[1])
        return width, height

    # Step 1: Frustum Clipping
    clip_result = clip_bounds_to_frustum(volume_bounds, camera['mvp'])
    if clip_result is None:
        return None, 0

    # Step 2: Projection and Sampling Ratio
    unit_w, unit_h = project_unit_size(camera['mvp'], camera['screen_width'], camera['screen_height'])
    max_dim = max(unit_w, unit_h)

    # Step 3 & 4: Resolution Level Determination
    # If N units project to one pixel, 1/N resolution is sufficient.
    # HZ levels reduce resolution by half in one direction per level.
    # We need level L such that projected size / 2^L <= 1 pixel.
    if max_dim <= 0:
        lod_level = 0
    else:
        lod_level = math.ceil(math.log2(1.0 / max_dim))

    # Clamp to available hierarchy levels
    lod_level = max(0, min(lod_level, hierarchy['max_level']))

    return clip_result, lod_level
```

## Subtopics

### On-Demand Processing
On-demand strategies determine at run time which parts of the data need to be processed, thereby eliminating pre-processing times and limiting the amount of data that needs to be handled [S2]. For example, ray-guided and visualization-driven volume rendering systems only request volume bricks to be loaded that are necessary for rendering the current view [S2]. Data that is not visible is never rendered, processed, or even loaded from disk [S2]. Other examples target interactive filtering and segmentation: on-the-fly noise removal and edge enhancement during volume rendering only for the currently visible part of the volume, interactive active-ribbon segmentation on a dynamically selected subset of the data, and visibility-driven on-the-fly filtering (noise removal and feature detection) of 4D ultrasound data [S2].

## Operating characteristics
*   **Time Complexity:** The culling and projection calculations are $O(1)$ per frame relative to the dataset size [G]. The data loading time depends on the volume of the clipped sub-volume and the selected resolution level [S1].
*   **Memory Complexity:** Memory usage is proportional to the size of the loaded sub-volume at the selected LOD, rather than the full dataset [S1].
*   **Measured Performance:** In the VisIt visualization application, this technique enables interactive navigation of arbitrarily large datasets on modest hardware by loading only the necessary sub-volume and resolution [S1].
*   **Strengths:** Reduces data transfer and memory footprint; enables interactive frame rates for massive datasets; avoids precomputation overhead of full pyramids [S1].
*   **Limitations:** Requires a multiresolution data format (like IDX) that supports efficient random access to coarse levels [S1]. Performance may degrade if the camera moves rapidly, causing frequent LOD changes and data reloads [G].
*   **When to use:** Interactive visualization of massive simulation datasets on low-cost hardware; remote visualization where bandwidth is limited [S1].
*   **When not to use:** Static rendering where the full dataset fits in memory; scenarios requiring consistent high-resolution detail regardless of camera distance [G].

## Background
View-dependent rendering was introduced as a combination of frustum-based scene culling and level-of-detail based geometry and texture loading to facilitate interactive graphical applications [S1]. The concept of frustum clipping is integral to OpenGL and DirectX rasterization pipelines [S1]. The specific application to massive volumetric datasets, particularly using the IDX format, was implemented in the VisIt visualization application to enable interactive exploration of simulation data on modest hardware [S1]. The technique is similar to MIP mapping, which was introduced by [27] (Lance Williams, "Pyramidal Parametrics," 1983), but adapted for 3D volumes where precomputing pyramids is cumbersome [S1].
