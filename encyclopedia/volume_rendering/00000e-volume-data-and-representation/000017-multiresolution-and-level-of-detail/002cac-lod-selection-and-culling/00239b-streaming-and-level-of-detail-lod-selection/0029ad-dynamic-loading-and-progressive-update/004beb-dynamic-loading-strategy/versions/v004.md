# Dynamic Loading Strategy


## Overview
A strategy to determine the level-of-detail (LOD) and specific data blocks to be loaded, thereby reducing VRAM usage by projecting block regions onto the camera plane to determine visibility [S1]. It sets itself apart from static LOD systems by dynamically computing visibility and resolution requirements per frame based on the current viewpoint, avoiding the storage overhead of precomputed full-resolution hierarchies for extremely large 3D volumes [S1].

## How it works
**Inputs:** Camera position and orientation; a set of 3D blocks, each defined by its spatial extent and associated LOD levels [G].
**Outputs:** A subset of blocks and their corresponding LOD levels to be loaded and rendered for the current frame [G].

**Data Structures:**
*   **Block:** A 3D volume partition.
    *   `xy_center`: 2D coordinate of the block's center on the $xy$ plane [S1].
    *   `xy_corners`: Array of 4 2D coordinates defining the base rectangle of the block [S1].
    *   `z_max`: Scalar, the height of the highest part within the block [S1].
    *   `lod_levels`: List of available resolution levels (coarsest to finest) [G].
*   **Camera:**
    *   `position`: 3D vector $(x_c, y_c, z_c)$ [G].
    *   `view_projection_matrix`: 4x4 matrix for projecting 3D points to clip space [G].
*   **Threshold:** Scalar $T$, the maximum distance from the camera to a block for which a finer LOD is required [S1].

**Steps:**
1.  **Define 3D Center Point:** For each block, compute the 3D center point. The $x$ and $y$ components are the center points of the block on the $xy$ plane. The $z$ component is assigned the height of the highest part within the block ($z_{\text{max}}$) [S1].
2.  **Define Block Region:** Construct a rectangular region for the block. This region is formed by the block’s four $xy$ corner points and the previously determined $z$ value ($z_{\text{max}}$) [S1].
3.  **Visibility Check:** Project the block region onto the camera plane. Determine whether the block is visible to the camera. Blocks that are not visible are eliminated from the rendering phase [S1].
4.  **LOD Selection:** Starting with the coarsest LOD, check if the distance from the camera to all visible blocks within the finer LOD exceeds a certain threshold [S1]. If the distance exceeds the threshold, rendering is performed using the resources loaded at the current LOD [S1]. Otherwise, the evaluation progresses to the subsequent, finer LOD [S1].

**Formulas:**
*   Distance to block center: $d = \sqrt{(x_c - x_b)^2 + (y_c - y_b)^2 + (z_c - z_b)^2}$, where $(x_b, y_b, z_b)$ is the 3D center point from Step 1 [S1].
*   Perspective projection: For a point $\mathbf{p} = (x, y, z)$, clip coordinates are $\mathbf{c} = \mathbf{M}_{\text{vp}} \cdot [x, y, z, 1]^\top$. Normalized device coordinates (NDC) are $(c_x/c_w, c_y/c_w, c_z/c_w)$ [G].

**Parameters:**
*   $T$: Distance threshold for LOD switching. Typical values depend on scene scale and required visual fidelity. Not given in the sources [S1].

**Edge Cases and Pitfalls:** Not given in the sources [S1].

**Pseudocode:**
```python
def dynamic_loading_strategy(blocks, camera, distance_threshold):
    loaded_blocks = []
    for block in blocks:
        # Step 1: Define 3D center point
        center_3d = (block.xy_center[0], block.xy_center[1], block.z_max)

        # Step 2: Define block region
        region_corners = [(c[0], c[1], block.z_max) for c in block.xy_corners]

        # Step 3: Visibility check (inline)
        # Project all 4 corners to NDC
        ndc_points = []
        for c in region_corners:
            # Matrix-vector multiplication for perspective projection
            clip_w = (camera.view_projection_matrix[3][0]*c[0] + 
                      camera.view_projection_matrix[3][1]*c[1] + 
                      camera.view_projection_matrix[3][2]*c[2] + 
                      camera.view_projection_matrix[3][3])
            if clip_w <= 0.0:
                continue # Behind camera
            clip_x = (camera.view_projection_matrix[0][0]*c[0] + 
                      camera.view_projection_matrix[0][1]*c[1] + 
                      camera.view_projection_matrix[0][2]*c[2] + 
                      camera.view_projection_matrix[0][3])
            clip_y = (camera.view_projection_matrix[1][0]*c[0] + 
                      camera.view_projection_matrix[1][1]*c[1] + 
                      camera.view_projection_matrix[1][2]*c[2] + 
                      camera.view_projection_matrix[1][3])
            clip_z = (camera.view_projection_matrix[2][0]*c[0] + 
                      camera.view_projection_matrix[2][1]*c[1] + 
                      camera.view_projection_matrix[2][2]*c[2] + 
                      camera.view_projection_matrix[2][3])
            ndc_points.append((clip_x / clip_w, clip_y / clip_w, clip_z / clip_w))

        if not ndc_points:
            continue # Not visible

        # Check if projected rectangle overlaps canonical view frustum [-1, 1]
        min_x = min(p[0] for p in ndc_points)
        max_x = max(p[0] for p in ndc_points)
        min_y = min(p[1] for p in ndc_points)
        max_y = max(p[1] for p in ndc_points)
        if not (min_x <= 1.0 and max_x >= -1.0 and min_y <= 1.0 and max_y >= -1.0):
            continue # Not visible

        # Step 4: LOD Selection
        current_lod = block.lod_levels[0]
        for lod in block.lod_levels[1:]:
            dist = ((camera.position[0] - center_3d[0])**2 +
                    (camera.position[1] - center_3d[1])**2 +
                    (camera.position[2] - center_3d[2])**2)**0.5
            if dist > distance_threshold:
                break
            current_lod = lod
        loaded_blocks.append((block, current_lod))
    return loaded_blocks
```

## Subtopics

### [Progressive Multiscale Loading](13806-progressive-multiscale-loading.md)
Progressive Multiscale Loading is a rendering strategy where each frame selects the appropriate resolution level per volume region, aiming for approximately one voxel per screen pixel. Coarse data fills the view first, and finer data replaces it region-by-region as it arrives, producing a complete coarse view within seconds that sharpens in place. It sets itself apart from static LOD systems by dynamically determining the minimum resolution required per frame based on projected size, avoiding the storage overhead of precomputed full-resolution hierarchies for extremely large 3D volumes.

## Operating characteristics
VRAM usage is reduced by only loading visible blocks and appropriate LODs [S1]. Not given in the sources [S1].

## Background
Originated in the context of real-time neural rendering of large-scale scenes on the web, specifically in the "City-on-Web" project [S1]. The method addresses the challenge of rendering massive urban environments with limited client-side resources by dynamically managing data loading based on visibility and distance [S1].
