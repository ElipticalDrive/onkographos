# View-dependent data loading

Also called: Frustum-based scene culling, Level-of-detail based geometry and texture loading, View-Dependent Rendering, frustum-based multiresolution loading

## Overview
View-dependent data loading is a strategy for interactive exploration of massive volumetric datasets on limited hardware by loading only the spatial extent and resolution necessary for the current camera view [S1]. It combines frustum-based scene culling with level-of-detail (LOD) selection to reduce data requests and facilitate navigation [S1]. Unlike static LOD systems that precompute full-resolution pyramids for the entire dataset, this method dynamically determines the minimum resolution required per frame based on the projected size of volume units relative to screen pixels, avoiding the storage and computational overhead of precomputed hierarchies for extremely large 3D volumes [S1].

## How it works
The method determines which subset of a multiresolution dataset (e.g., IDX format) to load by analyzing the camera's relationship to the data volume. It ensures that the loaded data provides approximately one voxel per screen pixel, balancing visual fidelity with memory and bandwidth constraints [S1].

### Inputs and Outputs
*   **Inputs:**
    *   Camera parameters: Model-view-projection (MVP) matrix or equivalent frustum definition (near/far planes, aspect ratio, field of view).
    *   Data volume bounds: The 3D bounding box of the dataset.
    *   Multiresolution hierarchy metadata: The reduction factor per level (e.g., HZ levels where each level halves the resolution in one direction) [S1].
    *   Screen resolution: Width and height in pixels.
*   **Outputs:**
    *   Spatial extent: The sub-volume of the dataset to load (clipped by the frustum).
    *   Resolution level: The specific LOD index to load for that sub-volume.

### Data Structures
The implementation relies on the multiresolution format's metadata. For IDX formats, this includes the root resolution and the reduction factor per level [S1]. No additional precomputed pyramid structures are stored in memory for the culling logic itself; the hierarchy is accessed on-demand [S1].

### Steps
1.  **Frustum Clipping (Spatial Culling):**
    Apply the camera's viewing frustum clip planes (derived from model, viewing, and projection transformations) to the 3D bounding box of the data volume [S1]. Determine the intersection of the frustum and the data volume. This defines the spatial extent of the data to be loaded; data outside this intersection is discarded [S1].

2.  **Projection and Sampling Ratio Calculation:**
    Project a unit of the data volume (e.g., a single voxel or a grid cell at the current LOD) onto the 2D camera viewing plane [S1]. Calculate the projected area of this unit on the screen. Compare this to the area of a single screen pixel (in screen space units) [S1].

3.  **Resolution Level Determination:**
    Calculate the ratio $N$ of the projected area of the volume unit to the area of one screen pixel. If $N$ volume units project to cover one pixel, then $1/N$ resolution data is sufficient [S1].
    *   Let $A_{pixel}$ be the area of one screen pixel.
    *   Let $A_{unit}$ be the projected area of a volume unit at the base resolution.
    *   The ratio is $R = A_{unit} / A_{pixel}$.
    *   The minimum resolution level $L$ is chosen such that the effective sampling density matches the screen resolution. Specifically, the level is determined such that a unit of the data volume covers approximately one pixel on the screen [S1].

4.  **LOD Selection:**
    Using the hierarchy's reduction factor, select the coarsest level $L$ that satisfies the condition derived in Step 3. For HZ formats, each level reduces resolution by half in one direction [S1]. The selected level $L$ and the clipped spatial extent from Step 1 define the data request [S1].

### Formulas
Let $P$ be the projection of a volume unit onto the screen.
Let $S$ be the area of one screen pixel.
The number of volume units covering one pixel is:
$$ N = \frac{\text{Area}(P)}{S} $$
The condition for sufficient resolution is that the loaded data unit projects to approximately one pixel. If the current level $L$ has a resolution reduction factor of $2^L$ (assuming binary halving per level in the relevant dimension), the projected area scales by $1/4^L$ (for area) or $1/2^L$ (for linear dimension). The source states: "if 4 volume units project to one pixel, 1/4 resolution data is sufficient" [S1]. This implies a linear scaling relationship where the required level $L$ satisfies:
$$ \text{Projected Size at Level } L \approx \text{Pixel Size} $$
The exact level index is the smallest integer $L$ such that the projected area of a unit at level $L$ is less than or equal to the area of one pixel, or equivalently, the linear dimension of the projected unit is less than or equal to the pixel dimension [S1].

### Parameters
*   **HZ level reduction factor:** Each HZ level reduces the resolution by half in one direction [S1].
*   **Target coverage:** One pixel per volume unit (approximately) [S1].

### Edge Cases and Pitfalls
*   **Over-sampling:** Loading higher resolution than necessary wastes time and memory because multiple data units are averaged over the same pixel [S1].
*   **Under-sampling:** Loading lower resolution results in an overly coarse or "jaggy" image [S1].
*   **Extreme Distances:** When the camera is very far, the projected area becomes very small, potentially requiring the coarsest level. The system must handle the case where the required level exceeds the available hierarchy depth [G].
*   **Extreme Proximity:** When the camera is very close, the projected area exceeds the pixel area significantly. The system must load the finest available level and may need to handle sub-voxel sampling or tiling if the volume unit spans multiple pixels [G].

### Pseudocode
```python
def view_dependent_loading(camera, volume_bounds, hierarchy):
    """
    Determine the spatial extent and resolution level to load.
    
    Args:
        camera: Object containing MVP matrix, screen width, screen height.
        volume_bounds: Bounding box of the dataset (min_x, min_y, min_z, max_x, max_y, max_z).
        hierarchy: Object containing base resolution and reduction factor per level.
        
    Returns:
        sub_volume: The clipped bounding box to load.
        lod_level: The integer index of the resolution level to load.
    """
    # Step 1: Frustum Clipping
    # Transform volume bounds to clip space using the camera's MVP matrix
    # Determine the intersection of the transformed bounds with the canonical view volume
    # [-1, 1] for x, y, z (or similar depending on API)
    # This defines the spatial extent of data to be loaded
    sub_volume = clip_volume_with_frustum(volume_bounds, camera.mvp_matrix)
    
    if sub_volume is empty:
        return None, 0

    # Step 2: Projection and Sampling Ratio
    # Project a unit volume (e.g., 1x1x1 voxel at base resolution) onto the screen
    # Calculate the projected area in screen pixels
    # Note: This requires projecting the corners of the unit volume and computing the 
    # convex hull area or using the Jacobian of the projection transform for affine approximations
    
    # For simplicity, assume we project the center of the sub-volume or the average 
    # projected size of a unit. The source describes projecting a "3D volume unit".
    
    # Get the projected size of a base-resolution unit in screen space
    # This is often approximated by the derivative of the projection matrix
    projected_unit_size = project_unit_to_screen(camera.mvp_matrix, camera.screen_width, camera.screen_height)
    
    # Calculate the ratio N: how many volume units cover one pixel?
    # If projected_unit_size is a linear dimension (e.g., width in pixels),
    # then N_linear = projected_unit_size
    # The source says "if 4 volume units project to one pixel", implying linear coverage.
    # So if a unit is 0.25 pixels wide, 4 units fit in 1 pixel.
    
    # Determine the required linear scale factor
    # We want the loaded unit to be approx 1 pixel wide.
    # If current unit is P pixels wide, we need to reduce resolution by factor P.
    
    # Step 3: LOD Selection
    # HZ levels reduce resolution by half in one direction per level.
    # Let reduction_factor = 2 per level.
    # We need to find L such that: projected_unit_size / (2^L) <= 1.0
    
    projected_width = projected_unit_size.width
    projected_height = projected_unit_size.height
    
    # Use the maximum dimension to ensure coverage in both directions
    max_projected_dim = max(projected_width, projected_height)
    
    # Calculate required level
    # L = ceil(log2(max_projected_dim))
    # If max_projected_dim is 0.5, L=0 (1 unit = 0.5 pixels, so 2 units per pixel? 
    # Wait, source: "if 4 volume units project to one pixel, 1/4 resolution data is sufficient"
    # This means if a unit is 0.25 pixels wide, we need 1/4 resolution (Level 2 if binary halving).
    # So if projected_width = 0.25, we need Level 2.
    # Formula: Level = ceil(log2(1 / projected_width))? 
    # If projected_width = 0.25, 1/0.25 = 4, log2(4) = 2. Correct.
    # If projected_width = 0.5, 1/0.5 = 2, log2(2) = 1. Correct.
    # If projected_width = 1.0, 1/1.0 = 1, log2(1) = 0. Correct.
    
    if max_projected_dim <= 0:
        lod_level = 0 # Fallback
    else:
        lod_level = ceil(log2(1.0 / max_projected_dim))
        
    # Clamp to available hierarchy levels
    lod_level = clamp(lod_level, 0, hierarchy.max_level)
    
    return sub_volume, lod_level
```

## Subtopics

### Frustum Culling
A geometric technique to discard objects outside the camera's view. It is a prerequisite for view-dependent loading to determine the spatial extent. [Link](52-frustum-culling.md)

### MIP Mapping
A texture filtering technique that precomputes image pyramids to select the appropriate resolution based on screen-space projection. It is conceptually similar to the LOD selection in view-dependent loading but differs in that it precomputes all levels, which is cumbersome for massive 3D volumes. [Link](53-mip-mapping.md)

### IDX Format
A multiresolution data format that allows access to different resolution levels without storing full pyramids. It is the typical data structure used in conjunction with view-dependent loading in systems like VisIt. [Link](54-idx-format.md)

## Operating characteristics
*   **Time Complexity:** The culling and projection calculations are $O(1)$ per frame relative to the dataset size, depending only on the number of primitives or the bounding box complexity. The data loading time depends on the volume of the clipped sub-volume and the selected resolution level.
*   **Memory Complexity:** Memory usage is proportional to the size of the loaded sub-volume at the selected LOD, rather than the full dataset. This allows interactive exploration of datasets that exceed available RAM.
*   **Measured Performance:** In the VisIt visualization application, this technique enables interactive navigation of arbitrarily large datasets on modest hardware by loading only the necessary sub-volume and resolution [S1].
*   **Strengths:** Reduces data transfer and memory footprint; enables interactive frame rates for massive datasets; avoids precomputation overhead of full pyramids.
*   **Limitations:** Requires a multiresolution data format (like IDX) that supports efficient random access to coarse levels; performance may degrade if the camera moves rapidly, causing frequent LOD changes and data reloads.
*   **When to use:** Interactive visualization of massive simulation datasets on low-cost hardware; remote visualization where bandwidth is limited.
*   **When not to use:** Static rendering where the full dataset fits in memory; scenarios requiring consistent high-resolution detail regardless of camera distance (e.g., architectural fly-throughs with strict quality requirements).

## Background
View-dependent rendering was introduced as a combination of frustum-based scene culling and level-of-detail based geometry and texture loading to facilitate interactive graphical applications [S1]. The concept of frustum clipping is integral to OpenGL and DirectX rasterization pipelines [S1]. The specific application to massive volumetric datasets, particularly using the IDX format, was implemented in the VisIt visualization application to enable interactive exploration of simulation data on modest hardware [S1]. The technique is similar to MIP mapping, which was introduced by [27] (Lance Williams, "Pyramidal Parametrics," 1983), but adapted for 3D volumes where precomputing pyramids is cumbersome [S1].
