# Dynamic Loading and Progressive Update

Also called: Chargement dynamique et mise à jour progressive, City-on-Web LOD & Dynamic Loading

## Overview
Dynamic Loading and Progressive Update is a strategy for visualizing massive volumetric scenes by adaptively loading data based on the viewpoint position, bounding memory usage to only the visible data and the required resolution ("useful resolution") [S1, unofficial][S2]. It sets itself apart from static LOD selection by dynamically culling invisible blocks and adapting resolution based on the camera's distance and the block's projected size, ensuring that only necessary data resides in memory [S1, unofficial]. Unlike [CP-LOD](9646-cp-lod-coverage-preserving-prefix-lod.md), which focuses on coverage-preserving prefix structures, this method emphasizes the temporal management of data transfer and memory reuse to maintain navigation fluidity during viewpoint changes [S1, unofficial].

## How it works
The method manages the lifecycle of volumetric data blocks (bricks) and their hierarchical structure (e.g., N3-tree) to balance visual quality with memory constraints.

**Inputs and Outputs:**
*   **Input:** Camera position, camera field of view (FOV), scene bounds, data variation frequency, and the current state of the loaded data structure.
*   **Output:** A set of loaded data blocks at appropriate LODs, updated tree structure, and rendered image.

**Data Structures:**
1.  **Brick:** A multi-resolution volume block. Size varies from $16\text{ KB}$ to $1\text{ MB}$ depending on resolution and compression [S1, unofficial].
2.  **N3-tree:** A hierarchical structure where leaves point to bricks. Nodes support subdivision and merging [S1, unofficial].
3.  **LOD Bounds:** For each brick, a lower bound ($LOD_{min}$) and an upper bound ($LOD_{max}$) are defined [S1, unofficial]. These are determined by global scene bounds and data variation frequency [S1, unofficial].
4.  **Camera Parameter Request (Bitmask):** Used in point cloud variants to track reload state. Bit 0 indicates quarter-resolution request pending; Bit 1 indicates full-resolution request pending [S4, unofficial].

**Steps:**

1.  **Determine Useful Resolution:** Calculate the required resolution for visible data based on the viewpoint position and the data's variation frequency [S1, unofficial]. High-variation data requires higher resolution than constant data [S1, unofficial].
2.  **Select LOD for Bricks:** For each visible brick, determine its LOD level. If the useful resolution exceeds the brick's current LOD, select a higher LOD (finer resolution). If the useful resolution is coarser than the brick's $LOD_{min}$, select a lower LOD [S1, unofficial].
3.  **Update Tree Structure:**
    *   If the useful LOD is coarser than the $LOD_{max}$ of all bricks under a tree node, merge the bricks (or remove the node) to move up the hierarchy [S1, unofficial].
    *   If the useful LOD is finer than the $LOD_{min}$ of a brick, subdivide the brick into $N$ children and update the tree leaf [S1, unofficial].
4.  **Load Data Incrementally:** Load the required bricks at the selected LODs. Do not reload all data at once to maintain navigation fluidity [S1, unofficial].
    *   *Note:* Loading large bricks takes $60\text{ }\mu\text{s}$ to $4\text{ ms}$ [S1, unofficial]. Updating sparse tree nodes individually incurs high transfer latency costs [S1, unofficial].
5.  **Manage Update Frequency:** Control the frequency of brick and tree updates by respecting the defined $LOD_{min}$ and $LOD_{max}$ bounds [S1, unofficial]. This prevents excessive reloading during minor camera movements [S1, unofficial].

**Pseudocode:**

```python
def update_scene(camera, scene_bounds, data_variation, current_tree):
    """
    Updates the volumetric scene based on camera position and LOD bounds.
    """
    # 1. Determine useful resolution based on viewpoint and data variation
    useful_resolution = calculate_useful_resolution(camera, data_variation)
    
    # 2. Iterate through visible bricks in the tree
    visible_bricks = get_visible_bricks(current_tree, camera)
    
    for brick in visible_bricks:
        # 3. Determine target LOD for the brick
        # LOD levels are integers, e.g., 0 (coarsest) to N (finest)
        current_lod = brick.get_current_lod()
        lod_min = brick.lod_min
        lod_max = brick.lod_max
        
        # Calculate required LOD based on useful resolution
        required_lod = resolution_to_lod(useful_resolution, brick)
        
        # Clamp required LOD to the brick's allowed bounds
        target_lod = clamp(required_lod, lod_min, lod_max)
        
        # 4. Check if LOD change is needed
        if target_lod != current_lod:
            # 5. Load new data at target LOD
            # This involves fetching the brick data from storage/memory
            load_brick_data(brick, target_lod)
            
            # 6. Update tree structure if necessary
            # If the brick's LOD is at its min, consider merging with siblings
            if target_lod == lod_min:
                try_merge_with_siblings(brick, current_tree)
            # If the brick's LOD is at its max, consider subdividing
            elif target_lod == lod_max:
                try_subdivide_brick(brick, current_tree)
                
    return current_tree

def calculate_useful_resolution(camera, data_variation):
    """
    Calculates the resolution needed based on camera distance and data complexity.
    """
    # Simplified logic: resolution increases with proximity and data variation
    distance = camera.distance_to_scene_center()
    # Higher variation requires higher resolution
    variation_factor = data_variation.get_complexity_factor()
    # Inverse relationship with distance
    base_resolution = camera.focal_length / distance
    return base_resolution * variation_factor

def clamp(value, min_val, max_val):
    return max(min_val, min(value, max_val))
```

**Parameters:**
*   **LOD Bounds ($LOD_{min}, LOD_{max}$):** Defined per brick. Determined by global scene bounds and data variation frequency [S1, unofficial].
*   **Peak VRAM Target:** ~1100 MB for web-based rendering of large scenes [S2].
*   **Minimum Frame Rate:** 10 Hz, required to maintain refresh frequency during heavy loads [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Loading Latency:** Loading large bricks ($16\text{ KB}$ to $1\text{ MB}$) takes $60\text{ }\mu\text{s}$ to $4\text{ ms}$ [S1, unofficial].
*   **Tree Update Cost:** Updating sparse tree nodes individually incurs high transfer latency costs [S1, unofficial].
*   **Sudden Visibility:** Sudden camera movements or entering unvisited zones can cause too much data to become visible simultaneously, exceeding the time available per image for real-time refresh [S1, unofficial].
*   **Redundant Reloads:** Rapid camera movement could cause repeated full-resolution requests. Bitmask flags combined with timestamp checks ensure each resolution tier is requested only once per movement phase [S4, unofficial].

## Subtopics

### [Dynamic Loading Strategy](13106-dynamic-loading-strategy.md)
A strategy to determine the level-of-detail (LOD) and specific data blocks to load, reducing VRAM usage by projecting block regions onto the camera plane to determine visibility. It sets itself apart from static LOD selection by dynamically culling invisible blocks and adapting resolution based on the camera's distance and the block's projected size, ensuring that only necessary data resides in memory.

### Time-Sliced Loading
A strategy to maintain real-time frame rates (minimum 10Hz) during heavy data loads by spreading necessary loading operations across multiple frames, limiting the time available for loading in each frame [S1, unofficial]. A pitfall is that sudden camera movements or entering unvisited zones can cause too much data to become visible simultaneously, exceeding the time available per image for real-time refresh [S1, unofficial].

### Progressive Wavelet Refinement
A rendering technique where data is loaded and displayed incrementally by wavelet detail levels to provide immediate visual feedback while refining resolution over time [S3]. It loads the lowest detail level first, then switches to lower levels (higher resolution) triggered by a timer [S3]. Unlike LaMar et al., this method keeps the wavelet level constant within each tile [S3].

### Adaptive View-Dependent Point Cloud Reload
A method that tracks camera parameter changes via a timestamp. If the elapsed time exceeds `WVS_RELOAD_DELAY[0]` and bit 0 of `currentCameraParameterRequest` is unset, it requests a 1/4 resolution point cloud update and sets bit 0. If the elapsed time exceeds `WVS_RELOAD_DELAY[1]` and bit 1 is unset, it requests a full-resolution update and sets bits 0 and 1 [S4, unofficial]. Pitfalls include rapid camera movement causing repeated full-resolution requests, mitigated by bitmask flags and timestamp checks [S4, unofficial].

## Operating characteristics
*   **Memory Usage:** Peak VRAM usage is kept around 1100 MB for web-based rendering of large scenes [S2].
*   **Performance:**
    *   LOD3: PSNR 23.72, SSIM 0.660, LPIPS 0.306, VRAM 132.1 MB, DISK 40.2 MB [S2].
    *   LOD2: PSNR 24.23, SSIM 0.682, LPIPS 0.297, VRAM 841.6 MB, DISK 201.7 MB [S2].
    *   LOD1: PSNR 24.73, SSIM 0.736, LPIPS 0.192, VRAM 3970.2 MB, DISK 1259.6 MB [S2].
*   **Loading Time:** Loading large bricks takes $60\text{ }\mu\text{s}$ to $4\text{ ms}$ [S1, unofficial].
*   **Strengths:** Reduces VRAM usage for distant blocks; enables real-time neural rendering of large-scale scenes on web platforms [S2].
*   **Limitations:** High transfer latency for sparse tree node updates; potential for frame rate drops during sudden camera movements or entry into unvisited zones [S1, unofficial].
*   **When to Use:** When rendering massive scenes with limited memory resources (e.g., web-based rendering) and when viewpoint-dependent resolution is critical [S1, unofficial][S2].
*   **When Not to Use:** When real-time performance cannot tolerate the latency of incremental loading or when the scene is small enough to fit entirely in memory [S1, unofficial].

## Background
The concept of dynamic loading and progressive update originates from the need to visualize massive volumetric scenes interactively. The specific strategy described in [S1, unofficial] was developed to allow visualization of massive scenes by dynamically and adaptively loading data based on viewpoint position, bounding memory usage to visible data and required resolution [S1, unofficial]. The "City-on-Web" approach [S2] further refined this for web-based neural rendering, balancing training time and quality. Progressive wavelet refinement was introduced in [S3] for giga-scale multiresolution volume rendering on distributed clusters. The adaptive point cloud reload mechanism is documented in [S4, unofficial].
