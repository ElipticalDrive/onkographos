# Time-Sliced Loading

Also called: Frame-time limited loading, Spread loading, Time-Sliced Loading for Real-Time Stability

## Overview
Time-Sliced Loading is a strategy to maintain real-time frame rates (minimum 10Hz) during heavy data loads by spreading necessary loading operations across multiple frames, limiting the time available for loading in each frame [S1, unofficial]. It solves the problem of sudden camera movements or entering unvisited zones causing too much data to become visible simultaneously, which would otherwise exceed the time available per image for real-time refresh [S1, unofficial]. It sets itself apart from [Dynamic Loading Strategy](13106-dynamic-loading-strategy.md) by explicitly capping the computational budget per frame for data transfer and processing, rather than relying solely on visibility culling.

## How it works
**Inputs and Outputs:**
*   Input: A stream of data requests (textures, slices, or volume chunks) generated by the rendering pipeline.
*   Output: Partially loaded data structures updated incrementally, maintaining a stable frame rate.

**Data Structures:**
*   **Load Queue:** A list of pending data items to be loaded. The sources do not specify the exact internal layout (e.g., linked list vs. array) or bit-packing details [G].
*   **Frame Timer:** A mechanism to track elapsed time within a single frame.

**Parameters:**
*   **Minimum Frame Rate:** 10Hz. This defines the maximum allowable time per frame for all operations, including loading [S1, unofficial].
*   **Time Budget per Load Operation:** The remaining time in the frame after rendering and other tasks. The sources do not specify a fixed constant for this, but imply it is dynamic based on the frame rate target [S1, unofficial].

**Steps:**
1.  **Request Generation:** The rendering system identifies necessary data based on the current viewpoint and level of detail.
2.  **Queueing:** Data requests are added to the load queue.
3.  **Frame Start:** At the beginning of each frame, the system initializes a timer.
4.  **Processing Loop:**
    a.  While the timer is within the frame budget and the load queue is not empty:
        i.  Pop the next data item from the queue.
        ii. Perform the loading operation (e.g., memory allocation, data transfer from CPU to GPU, decompression).
        iii. Update the internal data structure to reflect the partially or fully loaded state.
    b.  If the frame budget is exceeded, stop processing and yield to the renderer.
5.  **Rendering:** Render the scene using the currently available data. Missing data may be represented by placeholders (e.g., gray slices) until loaded [S2, unofficial].
6.  **Frame End:** Submit the frame to the display. Repeat from Step 3.

**Pseudocode:**
```python
import time

class TimeSlicedLoader:
    def __init__(self, min_frame_rate_hz=10):
        self.min_frame_rate_hz = min_frame_rate_hz
        self.max_frame_time = 1.0 / min_frame_rate_hz
        self.load_queue = []
        self.loaded_data = {}

    def add_request(self, data_id, data_source):
        self.load_queue.append({'id': data_id, 'source': data_source})

    def process_frame(self):
        frame_start_time = time.perf_counter()
        frame_budget = self.max_frame_time

        # Process as many loads as possible within the frame budget
        while self.load_queue:
            current_time = time.perf_counter()
            elapsed = current_time - frame_start_time

            if elapsed >= frame_budget:
                break

            item = self.load_queue.pop(0)
            self._load_data(item)

    def _load_data(self, item):
        # Simulate loading operation
        # In reality, this involves memory allocation, I/O, or GPU transfer
        data = item['source'].fetch()
        self.loaded_data[item['id']] = data

    def render(self):
        # Render using self.loaded_data
        pass
```

**Edge Cases and Pitfalls:**
*   **Sudden Camera Movements:** Rapid changes in viewpoint can generate a burst of requests that exceed the frame budget, leading to visible lag or gray placeholders [S1, unofficial].
*   **Unvisited Zones:** Entering a previously unvisited area can trigger a large load burst [S1, unofficial].
*   **Precision:** The sources do not specify precision issues related to the loading process itself [G].

## Subtopics

### Cache Pre-delivery for Progressive Loads
A mechanism to inform a volume about images already cached before its own loading stages begin, preventing empty or gray slices during progressive loads [S2, unofficial]. When `load()` starts, the volume delivers each fully loaded cached image to itself. Deliveries run in batches of at most 8 ms. A cancelled or restarted load stops the batches. A delivery only marks the texture slices; each render fills them under the budget of `rendering.reducedTextureFill` [S2, unofficial]. It differs from previous behavior where the volume did not know cached images until its own stage requested them, causing nearby fills to skip frames and show gray [S2, unofficial].

### Incremental reduced texture fill
A rendering strategy that limits texture reduction work per frame to maintain interactivity during progressive loading and large volume rendering [S2, unofficial]. One render fills at most 16 reduced slices that hold data. The render stops after 8 ms, but only after it fills one slice. The texture requests another render, and the next fill starts where the last fill stopped [S2, unofficial]. The parameter `rendering.reducedTextureFill` defines the maximum number of reduced slices (16) and the time budget per render (8 ms) [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** The time spent on loading per frame is bounded by the frame budget (e.g., 100ms for 10Hz). The total time to load all data is proportional to the total data size divided by the average frame budget allocated to loading [S1, unofficial].
*   **Memory Complexity:** Depends on the size of the load queue and the amount of data currently in memory. The sources do not specify a fixed memory limit [G].
*   **Measured Performance:** Maintains a minimum frame rate of 10Hz during heavy loads [S1, unofficial].
*   **Scaling:** Performance scales with the available frame budget. Higher frame rate targets reduce the time available for loading, potentially increasing the time to fully load data.
*   **Strengths:** Prevents frame freezes and maintains interactivity during large data loads.
*   **Limitations:** Can result in visible placeholders (gray slices) if data is not loaded quickly enough. Sudden large loads can still cause temporary stuttering if the burst exceeds the frame budget significantly.
*   **When to Use:** Real-time volume rendering of large datasets where interactivity is critical.
*   **When Not to Use:** Offline rendering where frame rate is not a concern, or when immediate full data availability is required.

## Background
Time-Sliced Loading was developed as part of a broader strategy for interactive exploration of procedural volumes. It addresses the limitations of static loading strategies in the face of dynamic camera movements and large data sets. The approach is rooted in the producer/consumer model for data management [S1, unofficial].
