# Pseudo Volume Textures with Per-Voxel Lighting

Also called: Custom Implementation (Pseudo Volume Textures with Per-Voxel Lighting), Direct Volume Rendering with Pseudo Volume Textures, Pseudo Volume Textures, YouTube tutorial series based on ShaderBits Blog

## Overview
This method implements direct volume rendering using 2D textures containing tiles that represent low-resolution 2D slices of the volume, referred to as 'pseudo volume textures' [S1, S2, unofficial]. It solves the problem of rendering dynamic volumetric data by allowing the volume to be "painted" at runtime [S1, S2, unofficial]. It differs from true 3D volume textures by restricting effective maximum volume resolution further, but distinguishes itself from its parent [Ray-marched Volumetric Lighting with Density Thresholding](2456-ray-marched-volumetric-lighting-with-density-thresholding.md) by recomputing lighting for each frame via secondary ray marches for every voxel sample [S1, S2, unofficial].

## How it works
**Inputs and Outputs:**
- Input: A 2D texture atlas (pseudo volume texture) containing tiled 2D slices of the volume data [S1, S2, unofficial].
- Input: Primary ray direction and origin for the viewer [G].
- Input: Light source position and direction [G].
- Output: Final color buffer with per-voxel lighting [G].

**Data Structures:**
- **Pseudo Volume Texture:** A 2D texture where each tile represents a 2D slice of the volume [S1, S2, unofficial].
- **Voxel Sample:** A point along the primary ray intersecting the volume [G].

**Steps:**
1. For each pixel in the screen space, cast a primary ray into the volume [G].
2. Sample the pseudo volume texture along the primary ray to obtain voxel density and color data [S1, S2, unofficial].
3. For each voxel sample taken along the primary ray, perform a secondary ray march towards the light source [S1, S2, unofficial].
4. Accumulate lighting along the secondary ray to determine the illumination for the current voxel sample [G].
5. Composite the lit voxel color into the final pixel color [G].

**Edge Cases and Pitfalls:**
- Recomputing lighting per frame causes prohibitive performance impact for larger volumes [S1, S2, unofficial].
- Effective maximum volume resolution is restricted compared to true volume textures [S1, S2, unofficial].
- Adding a precomputed lighting cache that is only updated on voxel content or light source change would require an additional render pass and custom C++ and shader code, which is not straightforward anymore [S1, S2, unofficial].

    final_color = [0.0, 0.0, 0.0]
    accumulated_opacity = 0.0
    t = 0.0
    step_size = 0.1  # Not given in the sources.

    while t < 1.0:
        sample_pos = ray_origin + ray_direction * t
        # Sample pseudo volume texture: map 3D position to 2D tile coordinates and UV, then fetch density and color.
        # Tile mapping logic not given in the sources.
        density, color = sample_pseudo_volume(pseudo_volume_texture, sample_pos)

        if density > 0.0:
            # Secondary ray march towards light source for per-voxel lighting
            light_transmittance = 1.0
            light_t = 0.0
            light_dir = normalize(light_position - sample_pos)
            light_dist = length(light_position - sample_pos)

            while light_t < light_dist:
                light_sample_pos = sample_pos + light_dir * light_t
                light_density, _ = sample_pseudo_volume(pseudo_volume_texture, light_sample_pos)
                # Standard Beer-Lambert attenuation for participating media [G]
                light_transmittance *= exp(-light_density * step_size)
                light_t += step_size

            illumination = light_transmittance
            # Standard front-to-back volume compositing [G]
            alpha = 1.0 - exp(-density * step_size)
            final_color = final_color * (1.0 - alpha) + color * illumination * alpha * (1.0 - accumulated_opacity)
            accumulated_opacity += alpha * (1.0 - accumulated_opacity)

        t += step_size
    return final_color

## Operating characteristics
- **Time Complexity:** Prohibitive for larger volumes due to the per-voxel secondary ray march for lighting [S1, S2, unofficial].
- **Memory Complexity:** Restricted by the 2D texture atlas structure, limiting effective maximum volume resolution compared to true volume textures [S1, S2, unofficial].
- **Strengths:** Allows runtime "painting" of the volume, making it fully dynamic [S1, S2, unofficial].
- **Limitations:** Performance impact is prohibitive for larger volumes; effective maximum volume resolution is restricted [S1, S2, unofficial].
- **When to use:** When dynamic volume painting is required and volume size is small enough to tolerate the performance cost of per-frame lighting recomputation [S1, S2, unofficial].
- **When not to use:** For large volumes where performance is critical [S1, S2, unofficial].

## Background
This approach was used in the ARENA2 visualization dome [S1, S2, unofficial]. It is based on an implementation by Sundén and Ropinski [S1, unofficial]. The technique is part of a survey on rendering large volume datasets in Unreal Engine 5 [S1, S2, unofficial].
