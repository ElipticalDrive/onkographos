# GPU-accelerated UPBP with RTX BVH

Also called: Robust Volumetric Light Transport Simulation GPU, UPBP GPU implementation

## Overview
This method is a full GPU implementation of the Unified Points, Beams, and Paths (UPBP) algorithm that leverages NVIDIA RTX hardware for light and camera path generation, combined with new accelerated data structures and a constant-time Multiple Importance Sampling (MIS) weight algorithm [S1]. It solves the performance bottleneck of CPU-based UPBP implementations by offloading path tracing and density estimation queries to the GPU, achieving significant speedups over single-threaded and multi-threaded CPU baselines [S1]. Unlike its CPU sibling [Unified Points, Beams, and Paths (UPBP)](1402-unified-points-beams-and-paths-upbp.md), this implementation specifically adapts the Point-Point and Beam-Beam estimators to work with ray-tracing acceleration structures rather than traditional hash grids or grids, using small-extent rays for point queries and AABBs for sphere containment checks [S1].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Scene geometry, participating media properties (phase function, extinction coefficient), light source definitions, camera parameters, and UPBP configuration parameters (kernel widths, subpath lengths) [S1].
*   **Outputs:** Rendered image with unbiased volumetric lighting estimates [S1].

**Data Structures:**
The implementation utilizes specific data structures for different estimators, stored on the GPU:
1.  **Point-Point 3D (P-P3D):** Stores an Axis-Aligned Bounding Box (AABB) representing a sphere centered on each photon point, with a radius equal to the kernel width [S1]. If a camera point lies inside this sphere, the distance between the points is less than or equal to the radius [S1].
2.  **Beam-Beam (B-B) and Point-Beam (P-B):** Uses a custom GPU data structure that spends more time building than an LBVH but less time querying, resulting in better overall performance for these estimators [S1].
3.  **Hash Grids:** A GPU implementation of hash grids is provided for comparison, particularly for P-P3D, but exhibits poor performance in specific scenarios [S1].

**Algorithm Steps:**
1.  **Light Subpath Generation:** Generate light subpaths on the GPU using RTX hardware acceleration [S1]. Cache data at light vertices required for Photon Density Estimation (PDE) or Beam-Photon Transport (BTP) [S1].
2.  **Camera Subpath Generation:** Generate camera subpaths on the GPU [S1]. This kernel accounts for most of the GPU running time, as it generates subpaths, queries the data structures, and evaluates the estimators [S1].
3.  **Point Query Adaptation:** For Point-Point estimators, adapt the point query to the ray-tracing framework by creating a ray with a very small extent where the origin is the point and an arbitrary direction is chosen [S1].
4.  **Density Estimation Query:** For P-P3D, check if the camera point is inside the AABB of the photon's sphere [S1]. For B-B and P-B, query the custom data structure to find relevant beams or points [S1].
5.  **MIS Weight Evaluation:** Compute the MIS weight in constant time by splitting the path weight into three independent parts: one for the light subpath, one for the camera subpath, and a quantity depending on both subpath ends [S1]. The subpath weight is formulated as a recursive quantity evaluated as the subpath is traced [S1].
6.  **Path Weight Computation:** Upon forming a full path by combining two subpaths, compute the weight only from data cached at the light and camera vertices that are merged with PDE or connected with BTP [S1].

*   **Subpath Lengths:** Equal number of light and camera subpaths in experiments [S1].

**Edge Cases and Pitfalls:**
*   **Small Light Sources:** Hash grids perform notoriously poorly on scenes with small light sources concentrated in a small part of the scene, causing non-uniform distribution of light samples [S1]. This significantly affects P-P3D estimators in scenes like San Miguel and Sun Temple [S1].
*   **Point Query in Ray Tracing:** Point queries must be adapted to ray queries using small-extent rays, which may introduce precision issues if not handled carefully [S1].
*   **Data Structure Construction:** The new data structures spend more time building than LBVH, which may impact performance in dynamic scenes or if frequent rebuilds are required [S1].

## Operating characteristics
**Time and Memory Complexity:**
*   **Speedup:** The GPU implementation achieves a speedup of 21 to 69 times over the single-threaded SmallUPBP and 4 to 15 times over the multi-threaded version [S1].
*   **Data Structure Performance:**
    *   **Beam-Beam (B-B1D):** The new GPU data structure spends more time building than LBVH but less time querying, resulting in better overall performance [S1].
    *   **Point-Point 3D (P-P3D):** Hash grids perform best on most scenes, but fail on scenes with small, concentrated light sources (San Miguel, Sun Temple) [S1].
    *   **Point-Point 2D (P-P2D):** The new data structure has the lowest query time but highest construction time, with no clear winner among data structures [S1].

**Measured Performance:**
*   **Baseline CPU Times (SmallUPBP):**
    *   Bathroom: ST 134.01s, MT 28.46s
    *   Bistro: ST 127.22s, MT 18.28s
    *   Mirror Balls: ST 58.33s, MT 9.97s
    *   San Miguel: ST 115.06s, MT 26.84s
    *   Still Life: ST 50.72s, MT 7.86s
    *   Sun Temple: ST 419.78s, MT 89.00s [S1]
*   **GPU Data Structure Times (ms, 20 iterations):**
    *   **B-B1D (San Miguel):** Grid (CPU) Build 36, Query 491; Ours (GPU) Build 20, Query 2; Hash Grid (GPU) Build 8, Query 625; LBVH (GPU) Build 10, Query 52 [S1].
    *   **P-P2D (Bathroom):** Hash Grid (CPU) Build 424, Query 28646; Ours (GPU) Build 415, Query 171; Hash Grid (GPU) Build 52, Query 1946; LBVH (GPU) Build 88, Query 833 [S1].

**Strengths and Limitations:**
*   **Strengths:** Significant performance improvement over CPU implementations; efficient constant-time MIS weight evaluation; effective use of RTX hardware for path generation; robust data structures for beam-based estimators [S1].
*   **Limitations:** Poor performance of hash grids for P-P3D in scenes with small light sources; higher construction time for the new data structures compared to LBVH; most GPU time spent in the camera kernel [S1].

**When to Use:**
*   Use when high-performance volumetric rendering is required and NVIDIA RTX hardware is available [S1].
*   Use for scenes with sparse and dense media where beam-based estimators are beneficial [S1].
*   Avoid hash grids for P-P3D in scenes with small, concentrated light sources [S1].

**When Not to Use:**
*   Avoid if the scene has small, concentrated light sources and P-P3D is the primary estimator, as hash grids will perform poorly [S1].
*   Avoid if frequent data structure rebuilds are required, due to higher construction times [S1].

## Background
The method originates from the paper "Efficient Hardware Acceleration of Robust Volumetric Light Transport Simulation" [S1]. It builds on the UPBP algorithm [Unified Points, Beams, and Paths (UPBP)](1402-unified-points-beams-and-paths-upbp.md) and the CPU-based SmallUPBP implementation [S1]. The work adapts UPBP for GPU execution, leveraging NVIDIA RTX hardware for path generation and introducing new data structures and MIS weight algorithms to optimize performance [S1]. The implementation is publicly available [S1].
