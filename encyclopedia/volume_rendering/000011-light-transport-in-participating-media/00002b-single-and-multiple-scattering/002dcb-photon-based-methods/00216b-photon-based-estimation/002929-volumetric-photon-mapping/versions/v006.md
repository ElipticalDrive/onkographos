# Volumetric Photon Mapping

Also called: Photon Mapping in Participating Media, Real-time volume rendering for three-dimensional fetal ultrasound using volumetric photon mapping, Screen-space volumetric photon mapping, Volume Photon Map Creation, Volumetric Photon Mapping (VPM) for Fetal Ultrasound, Volumetric Photon Mapping (VPM) for Real-Time Fetal Ultrasound, Volumetric photon mapping with screen-space destiny estimation

## Overview
Volumetric Photon Mapping (VPM) is a global illumination technique for participating media that simulates light transport by decoupling the simulation of indirect illumination from the final rendering pass [S1, S2]. It solves the problem of efficiently computing multiple scattering effects in dense media by storing photon interactions in a spatial data structure and estimating in-scattered radiance during a subsequent gathering step [S1, S2]. Unlike direct integration methods that require expensive recursive ray tracing for every pixel, VPM pre-computes photon paths, allowing for real-time or near-real-time rendering of complex lighting effects such as caustics and subsurface scattering [S1, S2]. It is distinguished from its sibling [Beam Radiance Estimate](1283-beam-radiance-estimate.md) by storing discrete photon packets rather than continuous beam radiance estimates, and from [Point-Based Light Transport in Participating Media](3763-point-based-light-transport-in-participating-media.md) by its specific use of volumetric interaction storage for density estimation [S1, S2].

## How it works
Volumetric Photon Mapping operates in two distinct phases: a preprocessing phase where photons are emitted and stored, and a rendering phase where radiance is estimated and integrated [S1, S2].

### Inputs and Outputs
*   **Inputs:** Scene geometry, participating media properties (extinction $\sigma_t$, scattering $\sigma_s$, absorption $\sigma_a$, phase function $p$), light source positions and intensities, camera parameters, and photon count $N_{photons}$ [S1, S2].
*   **Outputs:** A rendered image containing direct and indirect illumination, or intermediate illumination volumes [S1].

### Data Structures
The method stores photon interactions in a spatial data structure. Two primary storage strategies are documented:
1.  **KD-Tree:** The traditional approach stores photon position, incidence direction, and power in a k-dimensional tree for efficient nearest-neighbor queries [S1][S4, unofficial].
2.  **Volume Texture (GPU):** To accelerate computation and avoid the overhead of KD-tree gathering, photons can be stored in a 3D volume texture. This structure stores the flux of each photon, trading spatial precision for memory locality and GPU-friendly access patterns [S1].

### Preprocessing Phase: Photon Emission and Storage
This phase generates the photon map by tracing light from sources through the medium [S1, S2].

1.  **Photon Emission:** Photons are emitted from light sources. In GPU implementations, threads co-complete emission tasks using a shared counter to minimize idle time [S1]. Photons are cast with random propagation directions to simulate scattering across voxels, rather than strictly front-to-back [S1].
2.  **Ray Marching and Interaction:** A ray is cast from the light source. If it intersects the volume, the path is divided into steps. At each step, the interaction probability is determined by the extinction coefficient $\sigma_t$ [S6, unofficial].
    *   **Null Collisions:** In heterogeneous media, a majorant $\sigma_{max}$ is used to sample step sizes. A null collision occurs with probability $P_{null} = (\sigma_{max} - \sigma_t)/\sigma_{max}$ [S3].
    *   **Scattering/Absorption:** If a real interaction occurs, the photon's fate is determined by the scattering albedo $\omega = \sigma_s / \sigma_t$. If scattered, the direction is updated using the phase function (e.g., Henyey-Greenstein) [S1][S6, unofficial].
    *   **Russian Roulette:** To terminate paths with low energy, Russian roulette is applied. A common implementation terminates the ray with 50% probability after three interactions [S6, unofficial].
3.  **Storage:** Upon interaction, a volume photon is added to the map at the current position, storing position, direction, and power [S6, unofficial]. If the photon hits a surface, standard surface photon mapping rules apply [S6, unofficial].

### Rendering Phase: Density Estimation and Integration
This phase computes the final radiance by gathering contributions from the stored photons [S1, S2].

1.  **Direct Illumination:** Calculated separately via single scattering (SS) using standard ray marching or ray casting, without relying on the photon map [S1].
2.  **Indirect Illumination (Gathering):** For each sample point $\mathbf{x}$ along the camera ray, the in-scattered radiance $L_{ms}(\mathbf{x})$ is estimated by gathering nearby photons [S1, S2].
    *   **Search:** The algorithm searches for photons within a radius $r$ (or $K$-nearest neighbors) [S1][S4, unofficial].
    *   **Density Estimation:** The radiance is estimated using a point-to-point estimator with a 3D kernel $K$ [S2]. The general form is:
        $$ L_{ms}(\mathbf{x}) \approx \frac{1}{N} \sum_{i=1}^{N} \frac{P_i}{V_i} K\left(\frac{\|\mathbf{x} - \mathbf{p}_i\|}{r}\right) p(\omega_i, \omega_o) $$
        where $P_i$ is photon power, $V_i$ is the volume of influence, and $p(\omega_i, \omega_o)$ is the phase function evaluating the likelihood of scattering from the photon's incoming direction $\omega_i$ to the camera direction $\omega_o$ [S1][S4, unofficial].
    *   **Screen-Space Destiny Estimation:** A specific variant for real-time rendering (e.g., in fetal ultrasound) uses a screen-space method to estimate photon brightness, avoiding complex KD-tree queries by leveraging texture filtering or screen-space projections [S1].
3.  **Integration:** The total radiance is integrated along the camera ray using transmittance $T$ [S1, S2]:
    $$ L(\mathbf{x}_0, \omega_0) = L_0 T(\mathbf{x}_0, \mathbf{x}_n) + \sum_{j=1}^{n} T(\mathbf{x}_0, \mathbf{x}_{j-1}) \sigma_s(\mathbf{x}_j) L_s(\mathbf{x}_j) \Delta s_j $$
    where $L_s = L_{ss} + L_{ms}$ [S1].

### Pseudocode
The following pseudocode illustrates the core logic, combining the general VPM approach with the specific GPU texture-based implementation details found in the sources [S1][S4, unofficial].

```python
# Constants
SQ_RADIUS = 0.7  # Search radius squared [S4, unofficial]
EXPOSURE = 0.4   # Luminance scaling factor [S1]

def preprocess_photons(media, lights, num_photons):
    """
    Emits photons and stores them in a volume texture.
    """
    photon_map = create_volume_texture(media.dimensions)
    shared_counter = 0
    
    # GPU Thread Co-completion for emission efficiency [S1]
    while shared_counter < num_photons:
        photon = emit_photon_from_random_light(lights)
        current_pos = photon.origin
        current_dir = photon.direction
        current_power = photon.power
        
        # Ray march through volume [S6, unofficial]
        while current_pos is inside(media):
            # Sample step size based on extinction [S3]
            step = sample_step(current_pos, media.sigma_t)
            next_pos = current_pos + current_dir * step
            
            # Check for interaction [S6, unofficial]
            if interact_with_medium(current_pos, next_pos, media):
                # Update direction using phase function (e.g., Henyey-Greenstein) [S1]
                current_dir = sample_phase_function(current_dir, media.g)
                
                # Store photon interaction in volume texture [S1]
                # Storing position, direction, and power/flux
                photon_map.set(current_pos, {
                    'pos': current_pos,
                    'dir': current_dir,
                    'power': current_power
                })
                
                # Russian Roulette termination [S6, unofficial]
                if russian_roulette(media.sigma_a, media.sigma_s):
                    break
                else:
                    current_power *= (1.0 - media.sigma_a / media.sigma_t)
            
            current_pos = next_pos
            
        shared_counter += 1
        
    return photon_map

def render_volumetric_photon_mapping(camera, media, photon_map):
    """
    Renders the scene by integrating direct and indirect illumination.
    """
    image = create_image(camera.resolution)
    
    for pixel in camera.rays():
        ray = pixel.ray
        total_radiance = 0.0
        
        # 1. Direct Illumination (Single Scattering) [S1]
        direct_light = compute_direct_illumination(ray, media, lights)
        
        # 2. Indirect Illumination (Multiple Scattering via Photon Map) [S1]
        # Ray march through the volume to find sample points [S3]
        samples = march_ray(ray, media)
        
        for sample_point in samples:
            # Gather photons within search radius [S4, unofficial]
            gathered_energy = 0.0
            num_nearby = 0
            
            # Iterate through relevant photons (optimized via texture lookup or grid) [S4, unofficial]
            nearby_photons = get_nearby_photons(photon_map, sample_point, SQ_RADIUS)
            
            for photon in nearby_photons:
                dist_sq = distance_sq(sample_point, photon.pos)
                if dist_sq < SQ_RADIUS:
                    # Calculate weight [S4, unofficial]
                    # Note: Source [S4, unofficial] initializes N to zero, 
                    # making the dot product term 0. Weight is overwritten by power/num_vol.
                    # We follow the source's explicit calculation flow.
                    weight = max(0.0, -dot(normal(sample_point), photon.dir))
                    weight *= (1.0 - sqrt(dist_sq)) / EXPOSURE
                    
                    # Overwrite weight if normal-based weighting is ineffective [S4, unofficial]
                    weight = photon.power / len(nearby_photons)
                    
                    gathered_energy += photon.power * weight
                    num_nearby += 1
            
            # Estimate in-scattered radiance [S1]
            if num_nearby > 0:
                l_ms = gathered_energy / num_nearby
            else:
                l_ms = 0.0
                
            # Integrate along ray [S1]
            transmittance = compute_transmittance(ray, sample_point)
            total_radiance += transmittance * media.sigma_s * l_ms
            
        # Combine Direct and Indirect [S1]
        final_radiance = direct_light + total_radiance
        
        # Apply HDR tone mapping [S1]
        image[pixel] = tone_map(final_radiance)
        
    return image
```

### Parameters
*   **Anisotropy Coefficient ($g$):** Controls scattering direction in the Henyey-Greenstein phase function. $g \in [-1, 1]$. Negative values produce back scattering, 0 is isotropic, and positive values produce forward scattering [S1].
*   **Exposure:** Luminance value assigned to each photon, influencing output brightness. Typical tested values: 0.3 to 0.4 [S1].
*   **Number of Photons:** Controls scattering realism. Higher counts improve quality but reduce FPS. Large datasets require higher counts [S1].
*   **Samples:** Number of samples per ray during rendering. Fixed at 800 in tested fetal ultrasound datasets [S1].
*   **Search Radius ($r$ or $sqRadius$):** The radius for gathering nearby photons. Set to 0.7 in some implementations [S4, unofficial].

### Edge Cases and Pitfalls
*   **Speckle Noise:** In ultrasound data, speckle noise degrades signal-to-noise ratio and makes gradient-based normal calculation unreliable. VPM is less sensitive to this than local illumination methods [S1].
*   **Storage Overhead:** Traditional KD-tree storage is memory-intensive and slow for gathering. Using volume textures mitigates this but requires careful management of texture size [S1].
*   **GPU Thread Scheduling:** Emitting photons one-per-thread can lead to resource wastage due to batch scheduling. Co-completing emission tasks using shared counters improves efficiency [S1].
*   **Ineffective Normal Weighting:** In some implementations, if the surface normal $N$ is not properly initialized or is zero, the cosine weighting term becomes zero, and the weight defaults to a uniform distribution based on power and count [S4, unofficial].

## Subtopics

### [Beam Radiance Estimate](1283-beam-radiance-estimate.md)
Estimates in-scattered radiance along an entire camera ray using a 2D smoothing kernel perpendicular to the ray, eliminating redundant gathering.

### [Photon Emission and Storage](3880-photon-emission-and-storage.md)
The preprocessing phase generating photon paths and recording interactions in spatial structures.

### [Photon Beam Tracing](5401-photon-beam-tracing.md)
Stores photon paths as beam segments rather than points, allowing for density estimation via beam intersection.

### [Progressive Photon Mapping](6672-progressive-photon-mapping.md)
Uses a multipass rendering technique to gradually reduce inaccuracy by iteratively emitting and accumulating photons.

### Surface Photon Mapping
A method for estimating surface illumination by accumulating energy from photons stored on the same object surface, weighted by distance and surface normal alignment [S4, unofficial]. It initializes an energy accumulator and searches for photons within a squared radius of 0.7 [S4, unofficial]. The weight is calculated as $\max(0.0, -\text{dot}(N, \text{photon.dir})) \times (1.0 - \text{cur\_dist}) / \text{exposure}$, where $N$ is the surface normal [S4, unofficial].

### Proposed Fetal Ultrasound Rendering Method
A rendering process for ultrasound data that renders direct and indirect lighting separately using a raycaster, with indirect illumination computed via VPM [S1]. It splits the rendering equation into direct ($L_{ss}$) and indirect ($L_{ms}$) components, ignoring emission terms for ultrasound data [S1]. It employs a high dynamic range (HDR) technique to handle intensity ranges exceeding display capabilities [S1].

### GPU Texture Photon Mapping
A method proposed by Czuczor et al. that stores photon collision information in GPU texture memory and uses texture filtering instead of KD-tree nearby-seeking [S1]. This method is effective for surface rendering but noted as not directly applicable to volume rendering without modification [S1].

### Homogeneous RTE Approximation
An approximation for the Radiative Transfer Equation in homogeneous media where in-scattered radiance is computed by summing contributions over discrete segments along the camera ray [S3]. Sample points $x_0, \dots, x_{s-1}$ define the segments within the medium [S3].

### Reverse Photon Mapping
A modification introduced by Havran et al. to speed up calculations at the last collection stage of photon mapping [S1].

### Hierarchical Photon Mapping
A method proposed by Spencer and Jones that increases illumination accuracy by passing photon energy layer-by-layer through a binary tree system [S1].

### Interactive Photon Map Update
A modification by Daniel et al. to produce interactive character for real-time realistic volume rendering, creating a data format for assessing scene areas affected by altering the transfer function to allow effective updates to the photon map [S1].

### Volumetric Photon Mapping with Radiance Transfer
A study by Zhang et al. that incorporated the volumetric photon mapping algorithm into the customary predesigned radiance transfer procedure [S1].

## Operating characteristics
*   **Time Complexity:** The preprocessing phase is $O(N_{photons} \times \text{steps})$, where steps depend on media density. The rendering phase is $O(N_{samples} \times N_{gather})$, where $N_{gather}$ is the number of photons in the search radius. Using KD-trees, gathering is $O(\log N)$, while volume textures offer $O(1)$ access but potentially larger search areas [S1][S4, unofficial].
*   **Memory Complexity:** Memory costly due to the requirement of a huge volumetric photon map, especially for large volumes and high photon counts [S2]. Storing photons in volume textures reduces overhead compared to KD-trees but still requires significant GPU memory [S1].
*   **Measured Performance:** On an Intel E5 CPU with 8GB RAM and a GPU, real-time performance (200+ FPS) was achieved for fetal ultrasound datasets (e.g., $289 \times 212 \times 266$ resolution) with 800 samples and exposure 0.4, using relatively low photon counts (17-26) [S1]. The method claims real-time performance even with up to ten million photons [S1].
*   **Strengths:** Simulates realistic global illumination effects (scattering, shadows) in real-time; robust against speckle noise in ultrasound data; separates direct and indirect lighting for flexibility [S1].
*   **Limitations:** Requires GPU acceleration for real-time performance; high photon counts can be memory-intensive; traditional KD-tree gathering is slow [S1, S2].
*   **When to Use:** Real-time visualization of participating media where global illumination effects are critical, such as medical ultrasound or foggy scenes.
*   **When Not to Use:** When memory is severely constrained and photon counts must be very low, leading to noisy results; or when only single scattering is required.

## Background
Volumetric Photon Mapping was developed as an extension of the surface photon mapping algorithm introduced by Jensen [S1, S2]. Jensen and Christensen generalized photon mapping from surface light travel to volume light transport by storing volumetric interactions as photons and estimating density using a 3D kernel [S2]. The method has been adapted for various applications, including real-time fetal ultrasound visualization, where it addresses the limitations of local illumination methods in handling speckle noise and providing depth information [S1]. Variants such as Beam Radiance Estimate and Progressive Photon Mapping have been developed to improve convergence and reduce memory usage [S2].
