# Froxel-diagonal inverse-square bias

Also called: bounded point-light falloff in fog, inverse squared light distance bias

## Overview
This method bounds the near-field singularity of a point or spot light's inverse-square attenuation in volumetric fog by adding a bias term to the denominator, preventing extreme aliasing and jitter artifacts when samples land very close to the light source [S1, unofficial]. Unlike Godot's fixed floor or Unity's normalized range clamping, this technique uses a bias scaled to the froxel's physical size, ensuring the bound adapts to the resolution and depth of the volume cell [S1, unofficial].

## How it works
**Inputs:**
- Sample position in view space ($\mathbf{p}$).
- Light position in view space ($\mathbf{l}$).
- Froxel geometry: the view-space bounding box of the froxel containing $\mathbf{p}$.

**Outputs:**
- Attenuation factor ($A$).

**Data Structures:**
The froxel is defined by its view-space bounding box. This box is determined by the froxel's slice thickness (depth along the view axis) and the extent of its corners on the horizontal and vertical axes across the frame [S1, unofficial]. The bounding box is constant in size regardless of the froxel's position on screen [S1, unofficial].

**Steps:**
1. Identify the froxel containing the current sample position $\mathbf{p}$ in the volumetric fog grid [S1, unofficial].
2. Calculate the view-space bounding box of this froxel. Determine its depth (slice thickness) and its width/height extents based on the corner positions [S1, unofficial].
3. Compute the squared diagonal length $b^2$ of this bounding box. Let $w$, $h$, and $d_{slice}$ be the width, height, and depth of the froxel's bounding box in view space. Then:
   $$ b^2 = w^2 + h^2 + d_{slice}^2 $$
4. Calculate the Euclidean distance $d$ from the sample position $\mathbf{p}$ to the light position $\mathbf{l}$:
   $$ d = \| \mathbf{p} - \mathbf{l} \| $$
5. Compute the attenuation factor $A$ using the biased inverse-square formula:
   $$ A = \frac{1}{d^2 + b^2} $$
6. Apply $A$ to the light's contribution during the fog integration step [S1, unofficial].

**Parameters:**
- Bias ($b^2$): The squared diagonal of the froxel's view-space bounding box. It is composed of the slice's depth and the extent of the froxel's corners on each axis across the frame [S1, unofficial].

**Pitfalls:**
- Within approximately one froxel diagonal of a light, the fog intensity falls short of the true inverse-square falloff [S1, unofficial].
- This dimming is more pronounced when the fog slice depth (often denoted as `Fog::length`) is large [S1, unofficial].
- The bias must be passed as a parameter to the lighting shader; surface shading callers should pass 0 to remain unchanged [S1, unofficial].

**Pseudocode:**
```python
def froxel_diagonal_inverse_square_bias(sample_pos, light_pos, froxel_bbox):
    """
    Calculate light attenuation for a sample in volumetric fog.
    
    Args:
        sample_pos: vec3, position of the sample in view space.
        light_pos: vec3, position of the light in view space.
        froxel_bbox: dict or struct containing width, height, and depth of the 
                     froxel's view-space bounding box.
                     
    Returns:
        float, attenuation factor.
    """
    # 1. Calculate distance squared
    delta = sample_pos - light_pos
    d_sq = dot(delta, delta)
    
    # 2. Get froxel dimensions
    w = froxel_bbox.width
    h = froxel_bbox.height
    d_slice = froxel_bbox.depth
    
    # 3. Compute squared diagonal bias
    b_sq = w*w + h*h + d_slice*d_slice
    
    # 4. Apply bias to denominator
    # Note: If d_sq is 0 (sample at light center), result is 1/b^2
    attenuation = 1.0 / (d_sq + b_sq)
    
    return attenuation
```

## Operating characteristics
**Time and Memory Complexity:**
The computation is $O(1)$ per sample, requiring only basic arithmetic operations (subtraction, dot product, addition, division) [S1, unofficial]. Memory overhead is negligible, requiring only the storage of the froxel's bounding box dimensions, which are typically available from the grid structure [S1, unofficial].

**Measured Performance:**
In a test with a still point light at the center of a 0.6 m-deep near froxel, the bias ensures the fog intensity stays within 25% over a 16-frame jitter cycle [S1, unofficial]. Specifically, every sample lies within half the diagonal $b$, so $1/(d^2+b^2)$ stays within $[1/(1.25 b^2), 1/b^2]$ [S1, unofficial]. Without the bias, the intensity ranged from 6.03 to 12.47 (a 2.07× variation) [S1, unofficial].

**Strengths and Limitations:**
- **Strengths:** Eliminates extreme aliasing and jitter artifacts caused by near-field spikes. Adapts to resolution and volume cell depth, unlike fixed-floor methods [S1, unofficial].
- **Limitations:** Introduces a systematic dimming error within one froxel diagonal of the light, which worsens with deeper fog slices [S1, unofficial].

**When to Use:**
Use this method for real-time volumetric fog rendering with point or spot lights, particularly when using froxel-based integration with jittered sampling [S1, unofficial]. It is suitable when visual stability across jitter cycles is prioritized over absolute physical accuracy in the immediate vicinity of the light [S1, unofficial].

**When Not to Use:**
Avoid if absolute physical accuracy of light falloff is required at very close range, or if the froxel depth is extremely large relative to the light distance, as the dimming error becomes significant [S1, unofficial].

## Background
This method is used in SGL3D (Steve's Game Library) for volumetric fog rendering [S1, unofficial]. It is based on Unreal Engine's `r.VolumetricFog.InverseSquaredLightDistanceBiasScale` practice, which scales the amount added to the inverse squared falloff denominator to effectively remove the spike that causes extreme aliasing [S1, unofficial]. The implementation was introduced in SGL3D PR #265 to address issues where a point light near the camera left soft, discrete puffs in the volumetric fog due to unbounded inverse-square attenuation [S1, unofficial]. Prior approaches in other engines included Godot's fixed floor (`max(dist, 0.0001)`) and Unity's normalized range clamping (`1/(1 + 25 d^2/range^2)`), both of which do not adapt to the froxel size [S1, unofficial].
