# Precomputed Lighting (Baking)

Also called: Baking Lighting, Baking the lighting, Direct Lighting Caching, Precomputed Light Transmissivity, Precomputed Transfer Function

## Overview
Precomputed Lighting (Baking) is a real-time volume rendering optimization that accelerates light transport by pre-calculating the direct lighting term ($L_i$) for each voxel in a grid and storing it as texture data [S1, S2, S3, unofficial]. It solves the performance bottleneck of evaluating illumination integrals per raymarching step by replacing runtime light sampling with trilinear interpolation of baked values [S1, S2, unofficial]. Unlike [Voxel Cone Tracing](1454-voxel-cone-tracing.md) which approximates multiple scattering via cone tracing at runtime, or [Spherical Harmonic Volumetric Visibility](1225-spherical-harmonic-volumetric-visibility.md) which compresses directional data into basis functions, this method stores raw or simplified lighting intensity directly, making it view-independent but strictly dependent on the static scene and light configuration [S2, unofficial].

## How it works
**Inputs:**
*   3D voxel grid representing the participating medium (density field).
*   Scene geometry (for shadow casting).
*   Light source definitions (position, intensity, direction).

**Outputs:**
*   A 3D texture (or volume buffer) containing precomputed lighting values ($L_{baked}$) for each voxel.

**Data Structures:**
*   **Baking Texture:** A 3D texture array or volume texture. The resolution can be lower than the simulation voxel grid because lighting is spatially smooth [S3, unofficial].
*   **Storage Layout:** Typically stored in memory order optimized for cache coherency (e.g., iterating x, then y, then z) to minimize cache misses during the baking pass [S1, unofficial].

**Steps:**

1.  **Baking Pass (Offline/Pre-frame):**
    For each voxel center $(x, y, z)$ in the grid:
    a. Cast a ray from the voxel center towards each light source in the scene.
    b. Perform a secondary raymarch or shadow map lookup to determine the transmissivity (visibility) along the path to the light [S2, S3, unofficial].
    c. Calculate the direct illumination $L_i$ received by the voxel, accounting for attenuation through the medium [S1, S2, unofficial].
    d. Store the resulting $L_i$ value in the corresponding voxel of the baking texture [S1, S3, unofficial].

2.  **Rendering Pass (Real-time):**
    a. Perform standard volumetric raymarching from the camera.
    b. For each sample point along the camera ray, perform a few real-time light samples (e.g., ~2 steps) to capture high-frequency details or dynamic effects [S3, unofficial].
    c. Sample the precomputed lighting texture at the sample point's coordinates using trilinear interpolation [S2, unofficial].
    d. Combine the interpolated baked lighting with the real-time samples to compute the final radiance [S3, unofficial].

**Formulas:**
The baked lighting value $L_{baked}(v)$ for a voxel $v$ is approximated as:
$$ L_{baked}(v) = \int_{\Omega} L_e(\omega) T(v, \omega) d\omega $$
Where:
*   $L_e(\omega)$ is the emitted radiance from light sources in direction $\omega$.
*   $T(v, \omega)$ is the transmissivity (visibility) from voxel $v$ to the light in direction $\omega$, computed via raymarching or shadow maps [S2, unofficial].

**Parameters:**
*   **Cache Resolution:** Can be significantly lower than the actual voxel resolution (e.g., 1/2 or 1/4 scale) because light attenuation is inherently blurry [S3, unofficial].
*   **Light Samples:** The number of real-time light samples taken during the main pass is small (typically ~2) to blend with the baked data [S3, unofficial].

**Edge Cases and Pitfalls:**
*   **Dynamic Changes:** The baking must be restarted whenever the lighting configuration or the volume simulation changes [S1, unofficial].
*   **Performance:** The baking pass itself is computationally expensive and can take significant time, negating some real-time benefits if not cached effectively [S1, unofficial].
*   **Memory:** Storing full lighting data per voxel increases memory bandwidth requirements during the render pass [S1, unofficial].

**Pseudocode:**

```python
# Baking Pass
def bake_lighting(volume_grid, lights, resolution):
    """
    Pre-computes direct lighting for each voxel.
    """
    baking_texture = create_3d_texture(resolution)
    
    # Iterate in memory-friendly order (x, y, z) to optimize cache usage [S1, unofficial]
    for z in range(resolution.z):
        for y in range(resolution.y):
            for x in range(resolution.x):
                voxel_center = get_voxel_center(x, y, z, resolution)
                total_light = vec3(0.0)
                
                for light in lights:
                    # Cast ray from voxel to light to compute visibility/transmissivity [S2, unofficial]
                    visibility = compute_visibility(voxel_center, light.position, volume_grid)
                    
                    # Calculate direct illumination contribution [S1, unofficial]
                    light_contribution = light.intensity * visibility
                    
                    total_light += light_contribution
                
                baking_texture.set(x, y, z, total_light)
    
    return baking_texture

# Rendering Pass
def render_volume(camera_ray, volume_grid, baking_texture, step_size):
    """
    Renders volume using baked lighting with minimal real-time sampling [S3, unofficial].
    """
    accumulated_color = vec3(0.0)
    accumulated_alpha = 0.0
    sample_pos = camera_ray.origin
    
    while sample_pos is inside volume and accumulated_alpha < 1.0:
        density = volume_grid.sample(sample_pos)
        
        # Perform a few real-time light samples for high-frequency detail [S3, unofficial]
        # Typically ~2 steps are sufficient to blend with baked data
        realtime_light = vec3(0.0)
        for i in range(2):
            visibility = compute_visibility(sample_pos, light.position, volume_grid)
            realtime_light += light.intensity * visibility
        
        # Sample precomputed lighting via trilinear interpolation [S2, unofficial]
        baked_light = baking_texture.sample_trilinear(sample_pos)
        
        # Combine baked and real-time lighting [S3, unofficial]
        # Note: Exact blending weights depend on implementation specifics [G]
        final_light = realtime_light + baked_light
        
        # Standard volume rendering integration
        color = density * final_light
        alpha = density * step_size
        
        accumulated_color += color * (1.0 - accumulated_alpha)
        accumulated_alpha += alpha * (1.0 - accumulated_alpha)
        
        sample_pos += camera_ray.direction * step_size
        
    return accumulated_color
```

## Operating characteristics
*   **Time Complexity:** Baking pass is $O(V \cdot L)$ where $V$ is the number of voxels and $L$ is the number of lights, involving secondary raymarching [S1, S2, unofficial]. Render pass is $O(R)$ where $R$ is the number of raymarch steps, with constant-time texture lookups [S1, unofficial].
*   **Memory Complexity:** $O(V)$ for storing the baking texture. Resolution can be reduced to save memory [S3, unofficial].
*   **Strengths:** Significantly reduces per-frame lighting calculation cost; view-independent [S2, unofficial].
*   **Limitations:** Requires re-baking for any change in lighting or geometry; baking pass can be slow; static lighting assumption [S1, unofficial].
*   **When to use:** Static scenes with static lighting where real-time performance is critical and baking time is acceptable [S1, unofficial].
*   **When not to use:** Dynamic lighting, dynamic geometry, or highly transient scenes [S1, unofficial].

## Background
Precomputed Lighting (Baking) is a historical technique mentioned for reference and educational purposes in modern volume rendering literature [S1, unofficial]. It draws inspiration from traditional shadow mapping and precomputed radiance transfer concepts, adapted for volumetric data [S1, S2, unofficial]. While largely superseded by more flexible real-time approximations like voxel cone tracing or spherical harmonics, it remains a fundamental concept in understanding the trade-offs between precomputation and runtime calculation [S1, unofficial].
