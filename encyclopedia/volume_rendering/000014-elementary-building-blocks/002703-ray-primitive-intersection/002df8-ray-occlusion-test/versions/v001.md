# Ray Occlusion Test

Also called: hitSomething, hitSomething8, rtcOccluded1, rtcOccluded8

## Overview
The Ray Occlusion Test determines whether a ray intersects any geometry within a specified distance range, returning only a binary result (hit or miss) rather than detailed intersection data [S1, unofficial]. It is optimized for simple occlusion checks where hit position, normal, or texture coordinates are unnecessary. It differs from [Ray-primitive intersection](769-ray-primitive-intersection.md) by skipping the computation of hit attributes and from [Ray-Triangle Intersection](11312-ray-triangle-intersection.md) by focusing on early-out efficiency for binary visibility rather than precise geometric contact.

## How it works
**Inputs and Outputs**
- **Input**: Ray origin $\mathbf{o}$, ray direction $\mathbf{d}$ (normalized), minimum distance $t_{near}$, maximum distance $t_{far}$ (often infinity), and a scene acceleration structure context.
- **Output**: Boolean indicating if any geometry was hit within $[t_{near}, t_{far}]$.

**Data Structures**
The method typically utilizes a ray structure containing:
- `origin`: 3D vector $(x, y, z)$
- `direction`: 3D vector $(x, y, z)$
- `tnear`: float, minimum intersection distance
- `tfar`: float, maximum intersection distance (initially set to $t_{far}$)
- `hit`: boolean or hit distance (used internally to signal success)

**Steps**
1. Initialize the ray structure with $\mathbf{o}$, $\mathbf{d}$, $t_{near}$, and $t_{far}$.
2. Initialize the scene context (e.g., BVH traversal state).
3. Invoke the occlusion query function (e.g., `rtcOccluded1` for single ray or `rtcOccluded8` for 8 rays).
4. The function traverses the acceleration structure. If an intersection is found at $t \in [t_{near}, t_{far}]$, it sets `ray.tfar` to a negative value or sets a hit flag.
5. Return `ray.tfar < 0.0f` (or equivalent hit flag) [S1, unofficial].

**Parameters**
- `min_dist`: Minimum ray distance for intersection. Default is often $0.0$ or a small epsilon to avoid self-intersection [S1, unofficial].
- `max_dist`: Maximum ray distance. Default is often infinity [S1, unofficial].

**Edge Cases and Pitfalls**
- **Precision**: Near-miss cases may suffer from floating-point inaccuracies; ensure `min_dist` is handled consistently with the scene's scale.
- **Boundaries**: If `min_dist` > `max_dist`, the test should immediately return false.
- **Degenerate Input**: Zero-length direction vectors should be normalized or rejected before the test.

## Subtopics

## Operating characteristics
- **Time Complexity**: $O(\log N)$ for BVH-based structures on average, where $N$ is the number of primitives. Significantly faster than full intersection tests when occlusion is likely, as it can terminate early.
- **Memory Complexity**: Depends on the acceleration structure (e.g., BVH memory footprint).
- **Performance**: Optimized for throughput in scenarios requiring many visibility checks (e.g., shadow rays, depth of field).
- **Strengths**: Low overhead, no attribute computation, suitable for SIMD/vectorized execution (e.g., `rtcOccluded8`).
- **Limitations**: No hit details provided; not suitable for shading or texturing.
- **When to use**: Shadow testing, visibility culling, depth of field blur checks.
- **When not to use**: When hit position, normal, or material ID is required.

## Background
The method is commonly associated with Intel's Embree library, which provides `rtcOccluded1` and `rtcOccluded8` functions for efficient ray occlusion testing [S1, unofficial]. It is a fundamental building block in modern real-time and offline renderers for handling visibility queries efficiently.
