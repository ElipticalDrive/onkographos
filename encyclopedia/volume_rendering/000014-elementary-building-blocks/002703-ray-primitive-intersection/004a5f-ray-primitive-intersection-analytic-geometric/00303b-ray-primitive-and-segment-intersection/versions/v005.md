# Ray-Primitive and Segment Intersection

Also called: Intersection Ordering Optimization, Ray-Primitive and Segment Intersection Ordering

## Overview
This method optimizes the evaluation of volumetric ray-object intersections by determining the correct processing order of intersection points and segments, and by providing the geometric primitives to compute exact intersection locations. It solves the problem of redundant or incorrect shading calculations when multiple objects or intersection types (points vs. segments) lie along a single ray. It sets itself apart from sibling methods like [Sphere Intersection](1620-sphere-intersection.md) and [Ray-Triangle Intersection](11312-ray-triangle-intersection.md) by focusing on the *ordering* and *dependency* of these geometric tests rather than the analytic solution of a single primitive, ensuring that faster point calculations are performed before slower segment calculations to enable early termination [S1, unofficial].

## How it works
The method consists of two parts: the geometric computation of ray-segment intersections and the algorithmic ordering of intersection events (points and segments) along the ray.

### Inputs and Outputs
**Inputs:**
- Ray: Origin $\mathbf{o} = (o_x, o_y)$, Direction $\mathbf{d} = (d_x, d_y)$ (typically normalized).
- Segments: List of line segments defined by endpoints $\mathbf{A} = (a_x, a_y)$ and $\mathbf{B} = (b_x, b_y)$.
- Objects: List of objects, each with a bounding box and an intersection class (1, 2, 3, or 4).

**Outputs:**
- Sorted list of intersection events (points and segments) ordered by their relevance to the closest intersection.
- Intersection parameters $t$ (ray distance) and $s$ (segment parameter) for valid intersections.

### Data Structures
1.  **Intersection Point Event:**
    -   `object_id`: Identifier of the object.
    -   `distance`: The $t$ value where the ray enters (Class 1) or exits (Class 2, 3) the bounding box.
    -   `type`: Enum `POINT`.
2.  **Intersection Segment Event:**
    -   `object_id`: Identifier of the object.
    -   `t_start`: The $t$ value where the ray enters the bounding box.
    -   `t_end`: The $t$ value where the ray exits the bounding box.
    -   `type`: Enum `SEGMENT`.
3.  **Ray-Segment Intersection Result:**
    -   `t`: Distance along the ray.
    -   `s`: Parameter along the segment ($0 \le s \le 1$).
    -   `valid`: Boolean indicating if the intersection is within the segment bounds and ray direction.

### Numbered Steps

#### 1. Bounding Box and Initial Intersection
For each object, compute the entry and exit points of the ray with its bounding box [S1, unofficial].
-   Calculate the distance $t_{enter}$ and $t_{exit}$ where the ray intersects the bounding box.
-   If the ray does not intersect the bounding box, discard the object.

#### 2. Classification and Distance Assignment
Assign a distance value to each object based on its intersection class to determine processing priority [S1, unofficial]:
-   **Class 1 (Point Intersection):** Distance is $t_{enter}$ (where the ray enters the box). Point calculations are fast and should be done first.
-   **Class 2 (Average/Min Projection):** Distance is $t_{exit}$ (where the ray exits the box).
-   **Class 3 (Max Projection):** Distance is $t_{exit}$ (where the ray exits the box).
-   **Class 4 (Segment):** These are processed after points.

#### 3. Sorting
Sort all objects (and their associated points/segments) by their assigned distance in ascending order [S1, unofficial]. This ensures that Class 1 intersections are processed before Class 2/3 intersections, even if the Class 2/3 object's bounding box is entered first.

#### 4. Ray-Segment Intersection Computation
For each segment associated with an object, compute the exact intersection with the ray using the analytic formula [S2, unofficial].

**Formula:**
Given ray $\mathbf{o}, \mathbf{d}$ and segment $\mathbf{A}, \mathbf{B}$:
$$ s_x = b_x - a_x, \quad s_y = b_y - a_y $$
$$ \text{denom} = d_x s_y - d_y s_x $$
$$ t = \frac{(a_x - o_x) s_y - (a_y - o_y) s_x}{\text{denom}} $$
$$ s = \frac{(a_x - o_x) d_y - (a_y - o_y) d_x}{\text{denom}} $$

**Validity Check:**
$$ \text{valid} = (t \ge 0) \land (0 \le s \le 1) $$

**Intersection Point:**
$$ \mathbf{p} = \mathbf{o} + t \mathbf{d} $$

#### 5. Processing Order and Early Termination
Process the sorted events using a variable $D_{min}$ initialized to infinity [S1, unofficial].

1.  **Process Points First:** Iterate through the sorted list. If an event is a **Point** (Class 1):
    -   If $t < D_{min}$, update $D_{min} = t$.
    -   This establishes the closest intersection point.

2.  **Process Segments:** Iterate through the sorted list. If an event is a **Segment**:
    -   Use $D_{min}$ to optimize the segment calculation [S1, unofficial]:
        -   If the segment's $t_{start} \ge D_{min}$, skip the segment (it is behind the closest point).
        -   If the segment contains $D_{min}$ (i.e., $t_{start} < D_{min} < t_{end}$), only compute the intersection for the sub-segment *outside* the point (typically the part after $D_{min}$ for Class 1, or adjust based on projection type).
        -   For **Class 3 (Max Projection)**: If a value $v_2$ is encountered such that $v_2 > v_t$ (where $v_t$ is the max value up to point $P_t$), terminate the segment calculation early [S1, unofficial]. This requires the Class 1 calculation to have established $P_t$ first.

### Pseudocode

```python
def ray_segment_intersect(ox, oy, dx, dy, ax, ay, bx, by):
    """
    Computes intersection between ray (O, D) and segment (A, B).
    Returns intersection data or None if parallel/invalid.
    """
    sx = bx - ax
    sy = by - ay
    denom = dx * sy - dy * sx
    
    # Check for parallel rays/segments
    if abs(denom) < 1e-9:
        return None
        
    t = ((ax - ox) * sy - (ay - oy) * sx) / denom
    s = ((ax - ox) * dy - (ay - oy) * dx) / denom
    
    valid = (t >= 0) and (0 <= s <= 1)
    
    if valid:
        hit_x = ox + dx * t
        hit_y = oy + dy * t
        return {
            't': t,
            's': s,
            'x': hit_x,
            'y': hit_y,
            'valid': True
        }
    else:
        return None

def process_ray_intersections(ray_origin, ray_dir, objects):

    """

        else:
            dist = t_exit

            'obj_id': obj['id'],

            't_end': t_exit,
            'class': obj['class']
        })
        
    # Step 3: Sort events by distance
    events.sort(key=lambda e: e['dist'])
    
    # Step 5: Process with Dmin

    results = []
    
    for event in events:
        if event['type'] == 'POINT':

                d_min = event['dist']
                # Perform Class 1 intersection calculation
                # (e.g., compute exact point intersection)
                results.append(('POINT', event['obj_id'], d_min))
                
        elif event['type'] == 'SEGMENT':
            # Process Segment (Class 2, 3, 4)
            # Optimization: Skip if segment starts after closest point
            if event['t_start'] >= d_min:
                continue
                
            # Optimization: If segment contains d_min, adjust range
            # For Class 1 point inside Class 4 segment, compute only outside part
            # For Class 3, check for early termination based on values
```

### Parameters and Edge Cases
-   **Threshold:** A threshold of $10^{-9}$ is used for the denominator check to handle parallel rays/segments [S2, unofficial].
-   **Inside Solid:** If a ray starts inside a solid, it must report the exit point to prevent holes or inside-out meshes from passing as outside intersections [S3, unofficial].
-   **Precision:** Floating-point precision issues may arise when $t$ is very close to $D_{min}$. Guard clauses should be used to avoid double-processing or gaps.

## Subtopics

### [Linear Edge Intersection](868-linear-edge-intersection.md)
Linear Edge Intersection determines the precise position where an isosurface intersects a grid edge by linearly interpolating between the scalar field values at the two vertices defining that edge. It solves the problem of locating surface geometry within a discrete voxel grid, serving as the fundamental geometric primitive for contouring algorithms like Marching Cubes and ray-marching isosurface extraction. It sets itself apart from its siblings by assuming a strictly linear variation of the scalar field along the edge, providing an exact algebraic solution for the intersection point under that assumption, whereas [Iterative Bisection Intersection Refinement](880-iterative-bisection-intersection-refinement.md) uses numerical approximation and [Hermite Interpolation for Isosurface Extraction](13666-hermite-interpolation-for-isosurface-extraction.md) uses gradient data for higher-order accuracy.

### [Voxel selection via pick ray intersection](893-voxel-selection-via-pick-ray-intersection.md)
This method extracts spatial information from a simulation by mapping 2D screen coordinates to 3D voxel indices, serving as a direct manipulation interface for tasks such as segmentation seed selection. It differs from [Reverse Index Map for Voxel Location](1097-reverse-index-map-for-voxel-location.md) by computing the intersection dynamically rather than relying on a pre-computed index texture, and from [Ray-Box Intersection for Interaction](2638-ray-box-intersection-for-interaction.md) by focusing on identifying the specific seed voxel for segmentation rather than just the entry point for fluid injection.

### [Boundary Segment Validity Conditions](7652-boundary-segment-validity-conditions.md)
Boundary Segment Validity Conditions define the geometric and topological constraints required for a line segment connecting two points on a polygonal mesh to be classified as a valid spatial boundary segment. These conditions ensure that the segment represents a true visibility boundary (e.g., a silhouette or occlusion edge) rather than a segment penetrating the geometry. This method is distinct from sibling methods like [Linear Edge Intersection](868-linear-edge-intersection.md) and [Voxel selection via pick ray intersection](893-voxel-selection-via-pick-ray-intersection.md) by explicitly validating the segment against the mesh normals and intersection geometry to prevent self-intersection or penetration artifacts in volume rendering integrals.

## Operating characteristics
-   **Time Complexity:** Sorting objects takes $O(N \log N)$ where $N$ is the number of objects. Intersection calculations are $O(1)$ per object/segment. Early termination reduces the average number of segment calculations.
-   **Memory Complexity:** $O(N)$ to store the events list.
-   **Strengths:** Significantly reduces shading computation time by avoiding unnecessary segment evaluations. Ensures correct handling of overlapping objects and different projection types (max, min, average).
-   **Limitations:** Requires pre-computation of bounding boxes and classification of objects. Sorting adds overhead for very small numbers of objects.
-   **When to Use:** When rendering scenes with multiple volumetric objects or complex intersection types where some intersections are faster to compute than others.
-   **When Not to Use:** For simple scenes with a single object or where all intersections are of the same type and cost.

## Background
The method originates from volumetric ray tracing optimization techniques, specifically described in "Volumetric Ray Tracing" by Sobierajski et al. [S1, unofficial]. It addresses the computational bottleneck of evaluating multiple intersection types along a ray. The geometric ray-segment intersection formula is a standard technique in computer graphics, often implemented in interactive raycasting tutorials [S2, unofficial]. The concept of device-callable ray queries for any shape type, including handling rays starting inside solids, is discussed in the context of EBGeometry [S3, unofficial].
