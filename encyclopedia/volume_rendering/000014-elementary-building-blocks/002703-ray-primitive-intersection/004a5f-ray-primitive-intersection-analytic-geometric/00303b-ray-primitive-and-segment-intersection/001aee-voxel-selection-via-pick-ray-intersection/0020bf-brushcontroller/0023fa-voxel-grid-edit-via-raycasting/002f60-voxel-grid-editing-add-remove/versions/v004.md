# Voxel Grid Editing (Add/Remove)
Also called: Interactive voxel manipulation, Raycast-based Voxel Interaction, Screen-to-Voxel Mapping, Voxel Click Handling, Voxel Interaction and Grid Snapping

## Overview
This method enables dynamic modification of a voxel grid by adding or removing individual voxels at specific positions determined by raycasting from screen-space mouse input [S1, S2, S3, unofficial]. It solves the problem of translating 2D user interaction into 3D volumetric changes, allowing for real-time sculpting or construction in voxel-based environments [S1, S3, unofficial]. Unlike static voxelization tools, this approach focuses on interactive feedback loops where mesh regeneration or spatial index updates occur immediately after a click [S1, S2, unofficial]. It differs from [Raycast-based Voxel Editing](5211-raycast-based-voxel-editing.md) by emphasizing the specific logic of grid snapping and face-normal determination for single-voxel operations rather than bulk brush strokes [S2, unofficial].

## How it works
### Inputs and Outputs
**Inputs:**
*   Screen-space mouse coordinates (pixel position) [S1, S3, unofficial].
*   Camera projection matrix and view direction [S1, S3, unofficial].
*   Current voxel grid data structure (Octree or Voxel Array) [S2, S3, unofficial].
*   Material/type identifier for new voxels [S1, unofficial].

**Outputs:**
*   Modified voxel grid (added/removed voxel) [S1, S2, unofficial].
*   Updated visual representation (regenerated mesh or updated node visibility) [S1, S2, unofficial].

### Data Structures
The implementation relies on specific structures to track interaction state and grid topology.

**1. Hover Info / Hit State (C++/General)**
Used to store the result of the raycast before modification [S3, unofficial].
*   `hasHit` (bool): True if the ray intersected a valid voxel face.
*   `node` (Pointer/Reference): Reference to the octree node or voxel object hit.
*   `position` (vec3): The 3D world coordinate of the intersection point.
*   `normal` (vec3): The surface normal of the hit face, indicating the direction of the click relative to the voxel.
*   `depth` (int): The octree depth of the hit node.
*   *Default Constructor:* `hasHit = false`, `node = nullptr`, `depth = 0` [S3, unofficial].

**2. Player Interaction Component State (Unity/C#)**
Holds persistent state for the interaction system [S2, unofficial].
*   `tree` (Octree): The underlying spatial data structure.
*   `targetVoxelCursor` (GameObject): Visual indicator for the selected voxel.
*   `normalCursor` (GameObject): Visual indicator for the face normal.
*   `hitMask` (LayerMask): Physics layer mask to restrict raycasting to voxel objects.
*   `blockBreak` (ParticleSystem): Visual effect for removal.
*   `hitVoxelPosition` (Vector3): The grid position of the voxel currently under the cursor.
*   `neighborVoxelPosition` (Vector3): The grid position of the adjacent voxel in the direction of the normal.

### Numbered Steps

1.  **Ray Generation**: Convert the screen-space mouse position $(u, v)$ into a 3D ray originating from the camera. This is typically done using the camera's `ScreenPointToRay` function, which computes the ray origin and direction based on the viewport and projection matrix [S1, S3, unofficial].
    *   Input: Mouse pixel coordinates $(u, v)$.
    *   Output: Ray $\mathbf{r}(t) = \mathbf{o} + t\mathbf{d}$, where $\mathbf{o}$ is the camera position and $\mathbf{d}$ is the normalized direction vector [S1, unofficial].

2.  **Physics Raycast**: Cast the generated ray into the scene against the voxel geometry.
    *   Perform a raycast with a maximum distance (e.g., 3 units in Unity examples, or infinite in custom engines) [S1, S2, unofficial].
    *   Filter results using a layer mask to ignore non-voxel objects [S2, unofficial].
    *   If no hit occurs, terminate the operation [S3, unofficial].
    *   If a hit occurs, retrieve the hit point $\mathbf{p}_{hit}$ and the face normal $\mathbf{n}$ from the collision data [S1, S2, unofficial].

3.  **Grid Snapping (Hit Voxel Determination)**: Determine the integer grid coordinates of the voxel that was physically hit.
    *   The hit point $\mathbf{p}_{hit}$ is in world space.
    *   Snap to the grid center of the hit voxel. The formula depends on the coordinate system convention (centered vs. corner-aligned).
    *   *Centered Convention (Unity/ForlornU):*
        $$ \mathbf{p}_{snap} = \mathbf{p}_{hit} - \mathbf{n} \times 0.5 $$
        $$ \mathbf{v}_{hit} = \lfloor \mathbf{p}_{snap} \rfloor + 0.5 $$
        Where $\lfloor \cdot \rfloor$ is the component-wise floor function [S2, unofficial].
    *   *Alternative Integer Convention:*
        $$ \mathbf{v}_{hit} = \lfloor \mathbf{p}_{hit} \rfloor $$
        [S1, S3, unofficial].

4.  **Target Voxel Calculation (Neighbor Determination)**: Determine the position of the voxel to be added or removed based on the face normal.
    *   The normal $\mathbf{n}$ points *out* of the hit voxel face.
    *   The adjacent voxel position $\mathbf{v}_{adj}$ is calculated by adding the normal vector to the hit voxel's position.
    *   Formula:
        $$ \mathbf{v}_{adj} = \mathbf{v}_{hit} + \mathbf{n} $$
        [S1, S2, unofficial].
    *   This $\mathbf{v}_{adj}$ represents the empty space adjacent to the hit face, which is the target for addition, or the hit voxel itself for removal, depending on the mode [S1, S2, unofficial].

5.  **Operation Execution**: Perform the add or remove action based on user input (e.g., Left Click vs. Right Click, or Mode flags).
    *   **Removal Mode**:
        *   Target: The hit voxel $\mathbf{v}_{hit}$.
        *   Action: Remove the voxel from the octree/grid at $\mathbf{v}_{hit}$ [S2, unofficial].
        *   Trigger: `tree.RemoveVoxel(v_hit)` [S2, unofficial].
    *   **Addition Mode**:
        *   Target: The adjacent voxel $\mathbf{v}_{adj}$.
        *   Action: Insert a new voxel into the octree/grid at $\mathbf{v}_{adj}$ with the current material/type [S1, S2, unofficial].
        *   Trigger: `tree.InsertVoxel(v_adj, material)` [S2, unofficial].
    *   *Note on Inverted Worlds:* Some implementations swap the target logic if the world coordinate system is inverted, calling `Click(neighbor, hit, 0, 1)` for removal and `Click(hit, neighbor, 1, 0)` for addition [S2, unofficial].

6.  **Feedback and Regeneration**:
    *   Update visual cursors to reflect the new hit state [S2, unofficial].
    *   Play particle effects (e.g., block break) if a voxel was removed [S2, unofficial].
    *   Trigger mesh regeneration or spatial index update.
        *   In mesh-based renderers: Call the mesh builder function to reconstruct the geometry from the modified grid [S1, unofficial].
        *   In octree-based renderers: Call `CubicQuery` or similar neighbor update functions to ensure connectivity and visibility are correct [S2, unofficial].

### Pseudocode

```python
def handle_voxel_edit(mouse_pos, camera, voxel_tree, edit_mode):
    """
    Handles voxel addition or removal based on mouse click.
    
    Args:
        mouse_pos: (x, y) screen coordinates.
        camera: Camera object with ScreenPointToRay method.
        voxel_tree: Octree or VoxelGrid instance.
        edit_mode: Boolean, True for Edit/Add-Remove mode, False for Navigation.
        
    Returns:
        None
    """
    if not edit_mode:
        return

    # Step 1: Ray Generation
    ray = camera.screen_point_to_ray(mouse_pos)
    
    # Step 2: Physics Raycast
    hit = physics.raycast(ray, distance=100.0, layer_mask=VOXEL_LAYER)
    
    if not hit.has_hit:
        return

    hit_point = hit.point
    hit_normal = hit.normal
    
    # Step 3: Grid Snapping
    # Determine the voxel that was physically hit
    # Using centered grid convention: snap to center of hit voxel
    snapped_point = hit_point - (hit_normal * 0.5)
    hit_voxel_coords = floor_vector(snapped_point) + 0.5
    
    # Step 4: Target Voxel Calculation
    # The adjacent voxel is in the direction of the normal
    target_voxel_coords = hit_voxel_coords + hit_normal
    
    # Step 5: Operation Execution
    # Assume Left Click = Remove, Right Click = Add
    # This logic can be inverted based on specific UI requirements [S2, unofficial]
    if is_left_click():
        # Remove the hit voxel
        voxel_tree.remove_voxel(hit_voxel_coords)
        play_particle_effect(hit_voxel_coords, type="BREAK")
    elif is_right_click():
        # Add voxel to the adjacent position
        voxel_tree.insert_voxel(target_voxel_coords, current_material)
        play_particle_effect(target_voxel_coords, type="PLACE")
        
    # Step 6: Feedback and Regeneration
    update_cursors(hit_voxel_coords, target_voxel_coords)
    voxel_tree.rebuild_mesh_or_update_neighbors()

def floor_vector(v):
    """Component-wise floor function for vector."""
    return Vector3(floor(v.x), floor(v.y), floor(v.z))
```

### Parameters and Edge Cases
*   **Ray Distance**: The maximum distance for the raycast must be sufficient to reach distant voxels but not so large as to cause performance issues or hit unintended geometry. A fixed value (e.g., 3.0 in Unity) or infinite is used [S1, S2, unofficial].
*   **Grid Alignment**: The offset of 0.5 in the snapping formula assumes voxel centers are at integer + 0.5 coordinates. If voxels are corner-aligned (0 to 1), the formula simplifies to `floor(hit_point)` [S1, S2, unofficial].
*   **Precision**: Floating-point errors in raycast hit points can cause jitter when snapping. Using `floor` with a small epsilon or snapping to the nearest integer center is recommended [S2, unofficial].
*   **Degenerate Input**: If the ray hits an edge or vertex shared by multiple voxels, the normal may be ambiguous. Most physics engines return a consistent normal, but edge cases may require fallback logic or ignoring the hit [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: The raycast operation is $O(\log N)$ for octree-based structures or $O(1)$ for uniform voxel grids with spatial hashing, where $N$ is the number of voxels. Mesh regeneration is $O(V)$ where $V$ is the number of visible voxels, which can be expensive if done every frame [S1, S2, unofficial].
*   **Memory Complexity**: $O(N)$ for storing the voxel grid. The interaction component adds negligible overhead [S2, unofficial].
*   **Performance**: Real-time interaction is feasible if mesh regeneration is optimized (e.g., incremental updates, chunk-based rebuilding) [S1, unofficial]. Full mesh rebuilds on every click can cause frame drops in large scenes [S1, unofficial].
*   **Strengths**: Intuitive user interface; precise control over individual voxels; works with complex octree structures [S2, S3, unofficial].
*   **Limitations**: Single-voxel granularity can be slow for large-scale edits; requires efficient raycasting against the voxel geometry [S1, S2, unofficial].

## Background
This method originated from the need for interactive voxel editors in game development and 3D modeling tools. Early implementations in Unity-based voxel games (e.g., *VoxelCaverns*) popularized the "screen-to-raycast-to-grid" pattern for player interaction [S2, unofficial]. It is widely used in voxel-based sandbox games (e.g., *Minecraft* clones), 3D model voxelization tools, and procedural generation editors [S1, S3, unofficial]. The technique bridges the gap between 2D screen input and 3D volumetric data, enabling real-time sculpting and construction [S1, S3, unofficial].
