# Pulsar Forward Pass (Sphere Intersection and Draw)


## Overview
The Pulsar Forward Pass is a GPU-accelerated ray-sphere intersection and rendering method designed for differentiable sphere-based neural rendering [S1]. It solves the problem of efficiently determining which spheres contribute to each pixel and computing their color contributions while simultaneously preparing data for a backward pass [S1]. It sets itself apart from sibling methods by explicitly managing a shared memory buffer for sphere draw information and using a fixed-size priority queue to track the closest five spheres per pixel, enabling a highly optimized backward pass that avoids redundant intersection searches [S1].

## How it works

### Inputs and Outputs
**Inputs:**
- A list of $N$ spheres, each defined by center $\mathbf{c}_i$, radius $r_i$, and color/opacity parameters [S1].
- Camera parameters (origin $\mathbf{o}$, direction vectors for each pixel) [S1].
- Rendering resolution (width $W$, height $H$) [S1].
- Early termination threshold $n$ (default 1%) [S1].

**Outputs:**
- Rendered image (color and optionally depth/normal) [S1].
- Gradients for sphere parameters and camera parameters (if backward pass is enabled) [S1].

### Data Structures

1.  **Sphere List:** Array of sphere parameters [S1].
2.  **Block-wide Shared Memory Buffer:** Stores sphere draw information (intersection depth, sphere ID, normal, etc.) for spheres intersecting the current pixel block. Size is a multiple of the block size to always accommodate all sphere hits [S1].
3.  **Backward Pass Buffer:** Per-pixel storage containing the normalization factor, and the intersection depths and IDs of the closest 5 spheres [S1].
4.  **Priority Queue:** Per-pixel, fixed-size (5 elements) optimized priority queue tracking the IDs and intersection depths of the closest spheres for the backward pass [S1].
5.  **Gradient Buffers:** Sphere-specific gradients buffer and camera gradient buffer per sphere [S1].

### Parameters
- **Block Size:** $16 \times 16 = 256$ threads (8 warps per block) [S1].
- **Early Termination Threshold ($n$):** Default 1% [S1].
- **Max Tracked Spheres:** 5 (fixed at compile time) [S1].
- **Camera Gradient Normalization Constant:** $1 \times 10^{-3}$ [S1].

### Steps

1.  **Sorting and Bounding:** Sort spheres to find an arbitrary number of closest spheres to the camera. Manual sorting is used instead of OPTIX to avoid the runtime hit of manual sorting and because OPTIX does not provide access to the acceleration structure [S1]. During sorting, find the enclosing rectangle for all visible spheres and use this information for tighter bounds of the region to draw [S1].
2.  **Block-wise Intersection Search:** Launch GPU blocks of $16 \times 16$ threads [S1]. Implement intersection search through coalesced loading of the intersection information structures and testing of the limits of the current pixel block [S1]. Write access to the shared memory buffer needs to be properly synchronized [S1]. If the buffer becomes too full or the spheres are exhausted, Step 3 execution is invoked to clear it [S1].
3.  **Draw Operation (Step 2):** Each pixel thread works autonomously [S1]. The draw operation is executed for each pixel separately and for each sphere draw information that has been loaded into the shared memory buffer [S1]. Because every pixel is processed by its own thread, write conflicts for the channel information are avoided and each pixel thread can work through the list of loaded draw information at full speed [S1]. Track intersection depths for each sphere using a small optimized priority queue to track the IDs and intersection depths of the closest five spheres for the backward pass [S1]. Update the denominator of the rendering equation to continuously track the minimum required depth that a sphere must have for an $n$ percent contribution to the color channels [S1]. Each pixel thread can vote whether it is 'done' with processing spheres and future spheres would have not enough impact; if all pixels in a block vote 'done', execution is terminated [S1]. The vote is implemented through a thread-warp-block stage-wise reduction operation [S1]. If a backward pass is intended, write information from the forward pass into a buffer [S1].
4.  **Backward Pass (Optional):** Parallelize the backward pass over the pixels. Each thread only processes the spheres that have been detected at the pixel position, but requires synchronization for gradient accumulation for each sphere [S1]. Reserve memory to store all sphere specific gradients [S1]. Accumulate sphere gradients through synchronized access from each pixel thread [S1]. Allocate a buffer for the camera gradient information per sphere [S1]. Accumulate camera gradients sphere-wise and run a device-wide reduction as a post-processing step, because synchronizing the accumulation of camera gradients causes too much memory pressure [S1]. Normalize sphere gradients by averaging over the number of pixels from which they are computed [S1]. Normalize camera gradients by taking the area that each sphere covers in the image as a normalization factor, together with a constant $1 \times 10^{-3}$ [S1]. Gradient computation for each gradient is only performed if the gradients are required by the PyTorch autodiff framework [S1].

### Edge Cases and Pitfalls
- **Buffer Overflow:** The shared memory buffer must be synchronized and cleared if it becomes full or spheres are exhausted [S1].
- **Memory Pressure:** Synchronizing camera gradient accumulation per pixel causes too much memory pressure; use sphere-wise accumulation and device-wide reduction [S1].
- **Precision:** Use double precision for intersection calculations if necessary to avoid artifacts, though not explicitly stated, standard practice in ray tracing [G].
- **Degenerate Input:** Empty sphere list or zero-radius spheres should be handled gracefully [G].

## Operating characteristics

- **Time Complexity:** Depends on the number of spheres $N$ and image resolution $W \times H$. The sorting step is $O(N \log N)$ or $O(N)$ with specialized sorts. The intersection search is $O(N \cdot W \cdot H)$ in the worst case, but early termination and block-wise processing reduce this significantly. The backward pass is $O(N \cdot W \cdot H)$ but optimized by skipping intersection search [S1].
- **Memory Complexity:** $O(N)$ for sphere storage, $O(W \cdot H)$ for image and backward buffers. Shared memory buffer size is a multiple of the block size to always accommodate all sphere hits [S1].
- **Measured Performance:** Camera gradient accumulation reduction takes 0.6 ms for 1,000,000 spheres [S1].
- **Scaling:** Scales favorably with future GPU generations due to block size optimization. Scales well with image resolution and the number of spheres [S1].
- **Strengths:** Fast execution, robust to large spheres, efficient backward pass by avoiding redundant intersection searches [S1].
- **Limitations:** Requires manual sorting, which may be slower than OPTIX for very large datasets if OPTIX access were available. Memory pressure can be an issue if not managed correctly [S1].
- **When to Use:** When differentiable sphere-based rendering is required and performance is critical. When the number of spheres is large and early termination can be effective [S1].
- **When Not to Use:** Not given in the sources.

## Background

The Pulsar Forward Pass was introduced in the paper "Pulsar: Efficient Sphere-based Neural Rendering" [S1]. It was developed to address the limitations of existing methods like OPTIX, which do not provide access to the acceleration structure for manual sorting and arbitrary closest sphere queries [S1]. The method was designed to be efficient and differentiable, enabling optimization of sphere parameters and camera parameters using gradient descent [S1]. It has been used in neural rendering applications where sphere-based representations are advantageous [S1].
