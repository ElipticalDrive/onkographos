# Ray-Sphere Intersection

Also called: Analytical ray-sphere intersection, Ball Ray Intersection, Quadratic Ray-Sphere Intersection, Ray-Ball Intersection, Sphere Ray Intersection, Sphere-Ray Intersection Check, SphereCollider.forward, Spherical Volume Intersection

## Overview

Ray-sphere intersection computes the entry and exit distances ($t$) where a ray intersects a sphere, defining the valid sampling interval for volume rendering within that spherical volume [S1, S5, S9, S10, unofficial]. It solves the problem of efficiently determining the geometric bounds of a spherical primitive to limit raymarching steps or to evaluate density integrals [S8, S10, unofficial]. Unlike [Ray-Plane/Rectangle Intersection](6498-ray-plane-rectangle-intersection.md), which handles flat boundaries, this method solves a quadratic equation to account for the sphere's curvature [S1, S10, unofficial].

## How it works

**Inputs and Outputs:**
*   **Inputs:** Ray origin $\mathbf{o}$ (vec3), ray direction $\mathbf{d}$ (vec3, typically normalized but not required), sphere center $\mathbf{c}$ (vec3), sphere radius $r$ (float). Optional: transformation matrices to convert world-space ray to local space [S1, unofficial].
*   **Outputs:** Boolean hit status, intersection distances $t_{near}$ and $t_{far}$ (floats), and optionally the hit point and surface normal [S1, S10, S11, unofficial].

**Data Structures:**
*   **Sphere:** Defined by center $\mathbf{c}$ and radius $r$. In some implementations, the sphere is defined by quaternion coefficients $\alpha_w, \beta_w, \gamma_w$ for use in kernel space or Möbius transformations [S4].
*   **Ray:** Defined by origin $\mathbf{o}$ and direction $\mathbf{d}$.

**Steps:**

1.  **Transform to Local Space (Optional):** If the sphere is defined in a local coordinate system (e.g., via a transformation matrix), transform the ray origin and direction into that space. Let the transformed ray be $\mathbf{r}_o, \mathbf{r}_d$ [S1, unofficial]. If the sphere is centered at the origin, $\mathbf{c} = \mathbf{0}$ [S5, unofficial]. Otherwise, compute the vector from the ray origin to the sphere center: $\mathbf{oc} = \mathbf{o} - \mathbf{c}$ [S1, S2, unofficial].

2.  **Compute Quadratic Coefficients:** Substitute the ray equation $\mathbf{q}(t) = \mathbf{o} + \mathbf{d}t$ into the sphere equation $|\mathbf{x} - \mathbf{c}|^2 = r^2$. This yields the quadratic equation $At^2 + Bt + C = 0$ [S1, unofficial][S4][S10, unofficial]. The coefficients are:
    $$
    \begin{aligned}
    A &= \mathbf{d} \cdot \mathbf{d} \\
    B &= 2 (\mathbf{oc} \cdot \mathbf{d}) \\
    C &= (\mathbf{oc} \cdot \mathbf{oc}) - r^2
    \end{aligned}
    $$
    Note: Some implementations use a half-coefficient form to avoid the factor of 2 in $B$, defining $b = \mathbf{oc} \cdot \mathbf{d}$ and solving $At^2 + 2bt + C = 0$ [S2, unofficial].

3.  **Compute Discriminant:** Calculate the discriminant $\Delta$:
    $$
    \Delta = B^2 - 4AC
    $$
    Alternatively, using the half-coefficient form: $\Delta = 4(b^2 - AC)$ [S2, unofficial]. If $\Delta < 0$, the ray does not intersect the sphere (miss) [S1, S10, unofficial].

4.  **Solve for $t$:** If $\Delta \ge 0$, compute the roots:
    $$
    t_{1,2} = \frac{-B \pm \sqrt{\Delta}}{2A}
    $$
    Using the half-coefficient form: $t_{1,2} = -b \pm \sqrt{b^2 - AC}$ [S2, unofficial].
    Ensure $t_1 \le t_2$ by swapping if necessary [S10, unofficial].

5.  **Filter Roots:**
    *   If both $t_1$ and $t_2$ are negative, the sphere is behind the ray origin (miss) [S10, S11, unofficial].
    *   If $t_1 < 0$ and $t_2 \ge 0$, the ray origin is inside the sphere. The entry distance is $0$ (or $t_1$ if negative values are allowed for internal sampling) and the exit distance is $t_2$ [S10, S11, unofficial].
    *   If $t_1 \ge 0$, both intersections are in front of the ray. The entry distance is $t_1$ and the exit distance is $t_2$ [S10, unofficial].
    *   Clamp distances to the ray segment bounds $[t_{min}, t_{max}]$ if applicable [S1, S2, unofficial].

6.  **Compute Hit Point and Normal (Optional):**
    *   Hit point: $\mathbf{p} = \mathbf{o} + \mathbf{d} \cdot t$ [S10, S13, unofficial].
    *   Surface normal: $\mathbf{n} = \text{normalize}(\mathbf{p} - \mathbf{c})$ [S1, S11, S13, unofficial]. Note: Some implementations compute the normal as $\text{normalize}(\mathbf{c} - \mathbf{p})$ depending on the desired orientation (inward vs outward) [S11, unofficial].

**Pseudocode:**

```python
def ray_sphere_intersection(ray_origin, ray_direction, sphere_center, sphere_radius):
    """
    Computes the intersection of a ray with a sphere.
    
    Args:
        ray_origin: vec3, origin of the ray.
        ray_direction: vec3, direction of the ray (does not need to be normalized).
        sphere_center: vec3, center of the sphere.
        sphere_radius: float, radius of the sphere.
        
    Returns:
        tuple: (hit: bool, t_near: float, t_far: float, hit_point: vec3, normal: vec3)
               hit_point and normal are None if no hit.
    """
    # Vector from ray origin to sphere center
    oc = ray_origin - sphere_center
    
    # Quadratic coefficients
    a = dot(ray_direction, ray_direction)
    b = 2.0 * dot(oc, ray_direction)
    c = dot(oc, oc) - sphere_radius * sphere_radius
    
    # Discriminant
    discriminant = b * b - 4.0 * a * c
    
    if discriminant < 0:
        return (False, 0.0, 0.0, None, None)
    
    sqrt_disc = sqrt(discriminant)
    
    # Calculate the two t values
    t1 = (-b - sqrt_disc) / (2.0 * a)
    t2 = (-b + sqrt_disc) / (2.0 * a)
    
    # Ensure t1 is the smaller value
    if t1 > t2:
        t1, t2 = t2, t1
        
    # Determine the valid intersection interval
    # If both t are negative, the sphere is behind the ray
    if t1 < 0 and t2 < 0:
        return (False, 0.0, 0.0, None, None)
        
    # If t1 is negative, the ray origin is inside the sphere
    if t1 < 0:
        t_near = 0.0
        t_far = t2
    else:
        t_near = t1
        t_far = t2
        
    # Compute hit point and normal at t_near
    hit_point = ray_origin + ray_direction * t_near
    normal = normalize(hit_point - sphere_center)
    
    return (True, t_near, t_far, hit_point, normal)
```

**Parameters:**
*   `radius`: Float, default 1.0 [S5, S9, unofficial].
*   `near_plane`: Float, default 0.0, used to clamp the minimum near distance to avoid self-intersection or z-fighting [S9, S11, unofficial].
*   `soft_intersection`: Boolean, default False. If True, the distance between near and far is always $2 \times radius$ [S5, unofficial].

**Edge Cases and Pitfalls:**
*   **Ray Origin Inside Sphere:** If the ray origin is inside the sphere, $t_1$ will be negative. The entry distance should be clamped to 0.0 or handled specifically for volume rendering to allow sampling from the inside [S10, S11, unofficial].
*   **Tangent Ray:** If $\Delta = 0$, the ray is tangent to the sphere. $t_1 = t_2$. This is a valid hit but may cause numerical instability if not handled [S10, unofficial].
*   **Numerical Precision:** Negative discriminants due to floating-point errors for tangent rays should be clamped to 0.0 [S5, unofficial].
*   **Uninitialized Variables:** In some implementations, the normal calculation references an uninitialized `t` variable, leading to garbage values [S11, unofficial].
*   **Self-Intersection:** A threshold (e.g., 0.0001) is often used to prevent self-intersection artifacts [S11, unofficial].

## Subtopics

### [3-Sphere Intersection (Trilateration)](5144-3-sphere-intersection-trilateration.md)
The 3-Sphere Intersection method computes the geometric intersection points of the surfaces of three spheres, generating new sample points on the boundary of a carved volume. It solves the system of equations defined by the sphere boundaries to find positions that lie on all three surfaces simultaneously. Unlike [Ray-Sphere Intersection](3539-ray-sphere-intersection.md), which finds where a ray enters or exits a single sphere, this method determines the specific vertices formed by the mutual overlap of three distinct spheres, a process essential for advancing the surface boundary in sphere carving algorithms.

### [Ray-Splat Intersection (Sphere Approximation)](7123-ray-splat-intersection-sphere-approximation.md)
This method performs a ray-splat intersection test by approximating the true Gaussian splat ellipsoid with a sphere. It solves the problem of efficiently determining visibility for splat-based rendering without the computational cost of exact ellipsoid-ray intersection. It is distinguished from its parent [Ray-Sphere Intersection](3539-ray-sphere-intersection.md) by its specific application to Gaussian splatting parameters, and from its sibling [Fast Sphere Rendering via Ray-Sphere Test](9512-fast-sphere-rendering-via-ray-sphere-test.md) by its integration into the broader splat rendering pipeline context where it serves as a fallback or optimization when true ellipsoid testing is disabled.

### [Spherical Medium Density Integration](9077-spherical-medium-density-integration.md)
Spherical Medium Density Integration computes the optical depth along a ray segment passing through a sphere where density decreases quadratically from the center to the edge. It solves the problem of analytically integrating a spatially varying density function within a spherical volume, avoiding numerical sampling [G]. It differs from its parent [Ray-Sphere Intersection](3539-ray-sphere-intersection.md) by providing the accumulated density value rather than just geometric hit points, and from siblings like [Ray-Splat Intersection](7123-ray-splat-intersection-sphere-approximation.md) by using an exact quadratic falloff rather than a Gaussian or constant approximation [G].

### [Pulsar Forward Pass (Sphere Intersection and Draw)](9396-pulsar-forward-pass-sphere-intersection-and-draw.md)
The Pulsar Forward Pass is a GPU-accelerated ray-sphere intersection and rendering method designed for differentiable sphere-based neural rendering. It solves the problem of efficiently determining which spheres contribute to each pixel and computing their color contributions while simultaneously preparing data for a backward pass. It sets itself apart from sibling methods by explicitly managing a shared memory buffer for sphere draw information and using a fixed-size priority queue to track the closest five spheres per pixel, enabling a highly optimized backward pass that avoids redundant intersection searches.

### [Inverse Transforming Spheres](10196-inverse-transforming-spheres.md)
Inverse Transforming Spheres computes the coefficients $(\alpha', \beta', \gamma')$ of a sphere in kernel space given the coefficients $(\alpha, \beta, \gamma)$ of that sphere in world space after a quaternionic Möbius transformation. This allows a ray tracer to test if a world-space sphere intersects a kernel distance function by transforming the sphere into kernel space and performing a standard ray-sphere intersection. It differs from forward transformation by solving for the pre-image coefficients directly via algebraic expansion of the quaternionic Möbius map, avoiding iterative root-finding.

## Operating characteristics

*   **Time Complexity:** $O(1)$ per sphere. The method involves a constant number of arithmetic operations (dot products, square root, division) [S1, S10, unofficial].
*   **Memory Complexity:** $O(1)$ auxiliary space. Only a few scalar variables are needed to store the coefficients and roots [S1, S10, unofficial].
*   **Measured Performance:** The analytical solution is significantly faster than discrete raymarching approaches, which require multiple iterations and distance queries [S14, unofficial]. For example, in sparse voxel representations, ray-sphere intersection is used to quickly determine entry and exit depths for points treated as spheres [S8, unofficial].
*   **Scaling:** Performance scales linearly with the number of spheres if tested against a list, but each individual test is constant time. GPU implementations can batch these tests for many rays and spheres simultaneously [S8, S9, unofficial].
*   **Strengths:** Exact solution, no iteration required, robust for most cases, efficient for bounding volume hierarchies (BVH) or scene bounding spheres [S1, S9, unofficial].
*   **Limitations:** Does not handle non-spherical primitives. Numerical instability can occur for rays tangent to the sphere or rays originating very close to the surface [S5, S11, unofficial].
*   **When to Use:** When the scene contains spherical primitives or when a spherical bounding volume is used to cull rays [S1, S9, unofficial].
*   **When Not to Use:** When higher precision is required for non-spherical shapes, or when the sphere is part of a complex mesh that requires triangle intersection [S14, unofficial].

## Background

The analytical ray-sphere intersection is a fundamental technique in computer graphics, originating from the need to efficiently test for collisions between rays and simple geometric primitives [S1, S10, unofficial]. It is widely used in ray tracing, volume rendering, and collision detection [S1, S8, S10, unofficial]. The method is based on solving the quadratic equation derived from the intersection of a line (ray) and a sphere [S1, unofficial][S4]. Variations of this method have been adapted for different rendering pipelines, including neural rendering and Gaussian splatting [S9, S11, unofficial]. The use of quaternions and Möbius transformations extends the method to kernel space for signed distance field rendering [S4][S11, unofficial].
