# IRIS Ray-Geometry Intersection

Also called: OptiX-based Gaussian Intersection, Proxy Geometry Intersection

## Overview
IRIS Ray-Geometry Intersection is an intersection-aware ray-based sampling method for implicit editable scenes that determines samples as the maximum response points of Gaussians intersected by each ray [S1]. It solves the problem of efficiently sampling 3D Gaussian primitives in a ray-tracing pipeline by replacing expensive analytic Gaussian intersection tests with hardware-accelerated ray-triangle intersection tests using proxy geometry [S1]. Unlike standard ray-triangle intersection methods that return the closest hit, this method computes a specific sampling parameter $t_{\text{sample}}$ for each intersected Gaussian to identify the point of maximum response along the ray [S1]. It sets itself apart from sibling methods like [Ray-box intersection](776-ray-box-intersection.md) or [Ray-Sphere Intersection](3539-ray-sphere-intersection.md) by using affine-transformed icosahedra as proxies for Gaussians and leveraging OptiX Any-hit shaders to aggregate samples in a bounded hit buffer, reducing the number of heavy `optixTrace` calls [S1].

## How it works
**Inputs:**
*   Ray origin $O$ and direction $V$ in world coordinates.
*   A set of 3D Gaussians, each defined by a mean position, covariance matrix (or scale/rotation), and opacity.
*   Hyperparameters:
    *   Target sample quota (IPR): 128 for bounded scenes (NeRF Synthetic), 256 for unbounded scenes (Mip-NeRF 360) [S1].
    *   Hit buffer size: 16 entries [S1].
    *   Squared Mahalanobis distance threshold $\lambda$: 6.25 for bounded scenes (90% mass coverage), 11.3449 for unbounded scenes (99% mass coverage) [S1].

**Outputs:**
*   A list of samples, where each sample is a 2-tuple $(t_{\text{sample}}, \text{Gaussian index})$ [S1].

**Data Structures:**
1.  **Canonical Proxy Geometry:** A single regular icosahedron defined by a set of triangle vertices and indices. This geometry is stored once to minimize memory footprint [S1].
2.  **Instance Buffer:** An array of affine transformation matrices. Each entry maps the canonical icosahedron to the bounding proxy of a specific Gaussian [S1].
3.  **Hit Buffer:** A fixed-size buffer of 16 entries. Each entry stores a 2-tuple:
    *   `t_sample`: The intersection parameter computed in object space.
    *   `gaussian_index`: The index of the Gaussian primitive [S1].
4.  **Output Buffer:** Accumulates samples transferred from the hit buffer.

**Algorithm Steps:**

1.  **Proxy Generation (Pre-computation):**
    For each Gaussian $i$ with mean $\mu_i$ and covariance $\Sigma_i$:
    a. Compute the confidence ellipsoid corresponding to the $\chi^2$ distribution with 3 degrees of freedom at quantile $\lambda$ [S1].
    b. Conservatively bound this ellipsoid with a regular icosahedron.
    c. Compute the affine transformation matrix $M_i$ that maps the canonical icosahedron vertices to the vertices of this bounding icosahedron [S1].
    d. Populate the Instance Buffer with $M_i$ for all Gaussians [S1].

2.  **Ray Tracing Setup:**
    Initialize the OptiX pipeline with Ray Generation and Any-hit shaders [S1]. The geometry is registered as instanced triangles using the canonical icosahedron vertices and the Instance Buffer [S1].

3.  **Ray Generation Shader:**
    a. Initialize an empty Output Buffer for the current ray [S1].
    b. Initialize a local Hit Buffer of size 16 [S1].
    c. Call `optixTrace` with the ray $(O, V)$ [S1].

4.  **Any-hit Shader (Intersection Logic):**
    For each triangle hit by the ray:
    a. Identify the instance ID to retrieve the affine transformation matrix $M$ [S1].
    b. Transform the ray origin $O$ and direction $V$ into the object coordinate frame of the Gaussian:
       $$O_{\text{obj}} = M^{-1} (O - \mu)$$
       $$V_{\text{obj}} = M^{-1} V$$
       [Note: The source defines $O_{\text{obj}}$ and $V_{\text{obj}}$ as the ray origin and direction in the object coordinate frame. The exact transformation depends on whether $M$ includes translation. Assuming $M$ maps canonical proxy to Gaussian space, the inverse maps world to object. If $M$ is purely linear (rotation/scale), translation is handled separately. The source states "affine transformation matrices that map the reference proxy to the resulting Gaussian primitive". Thus, $M$ transforms canonical points to Gaussian points. To get object-space ray, we need the inverse transform. Let $T$ be the translation to the Gaussian center. The full transform is $X_{\text{world}} = M_{\text{linear}} X_{\text{obj}} + T$. Then $X_{\text{obj}} = M_{\text{linear}}^{-1} (X_{\text{world}} - T)$. The source formula uses $O_{\text{obj}}$ and $V_{\text{obj}}$. We assume the implementation correctly computes these.]
    c. Compute the sampling parameter $t_{\text{sample}}$ using the formula [S1]:
       $$t_{\text{sample}} = -\frac{\langle O_{\text{obj}}, V_{\text{obj}} \rangle}{\langle V_{\text{obj}}, V_{\text{obj}} \rangle}$$
       where $\langle \cdot, \cdot \rangle$ denotes the dot product [S1].
    d. Add the tuple $(t_{\text{sample}}, \text{Gaussian index})$ to the local Hit Buffer [S1].
    e. If the Hit Buffer is full (16 entries):
       i. Sort the entries in the Hit Buffer by $t_{\text{sample}}$ (ascending or descending, typically ascending for front-to-back, but the source says "maximum response points", implying the specific $t$ is the key metric. The source says "accumulated and sorted... to reduce... optixTrace calls". It does not specify sort order, but standard accumulation usually keeps the best candidates. Given $t_{\text{sample}}$ is the parameter for max response, we likely want the smallest positive $t$ or the one closest to the ray origin. However, the formula $t = -\langle O, V \rangle / \langle V, V \rangle$ is the projection of $-O$ onto $V$. If $O$ is origin, this is the parameter along the ray where the perpendicular from the origin hits the line. For a Gaussian centered at origin in object space, this is the closest approach. We store this $t$. The sorting is likely to keep the most relevant samples. We will assume sorting by $t_{\text{sample}}$ ascending [G]).
       ii. Transfer the sorted samples from the Hit Buffer to the Output Buffer [S1].
       iii. Clear the Hit Buffer [S1].

5.  **Iteration:**
    Repeat steps 3-4 until the total number of gathered samples in the Output Buffer reaches the predefined target sample quota (IPR) [S1].

**Edge Cases and Pitfalls:**
*   **Precision:** The formula for $t_{\text{sample}}$ involves division by $\langle V_{\text{obj}}, V_{\text{obj}} \rangle$. If the ray direction is zero or nearly zero in object space, this causes division by zero or numerical instability [S1].
*   **Boundary Conditions:** The proxy geometry is a conservative bound. If the threshold $\lambda$ is too small, Gaussians may be clipped, leading to missed samples. If too large, performance degrades due to more triangle intersections [S1].
*   **Buffer Management:** The hit buffer size (16) is small. If the scene has many overlapping Gaussians, the buffer fills quickly, requiring frequent transfers to the output buffer. This increases the overhead of the Ray Generation shader [S1].
*   **Quota Tuning:** The target sample quota (IPR) significantly impacts performance and quality. Too low leads to under-sampling; too high leads to unnecessary computation [S1].

## Operating characteristics
*   **Time Complexity:** Dominated by the number of ray-triangle intersection tests performed by the hardware RT cores. The number of tests is proportional to the number of Gaussians and the scene complexity. The buffer management adds a small constant overhead per 16 hits [S1].
*   **Memory Complexity:** Proportional to the number of Gaussians (for the instance buffer) and the hit buffer size (constant 16 entries per ray) [S1].
*   **Measured Performance:** On an NVIDIA RTX 5090 GPU, using the full model with 128 IPR on the NeRF Synthetic dataset achieves an average PSNR of 32.65. Reducing IPR to 64 drops PSNR to 32.47, and to 16 drops it to 29.87 [S1].
*   **Strengths:** Leverages hardware-accelerated ray-triangle intersection, reducing the computational burden of analytic Gaussian intersection. The hit buffer reduces the number of `optixTrace` calls [S1].
*   **Limitations:** The proxy geometry is an approximation. The method requires a custom OptiX pipeline and CUDA kernels for instance buffer population [S1].
*   **When to Use:** When rendering 3D Gaussian splats in a ray-tracing environment where hardware acceleration is available and analytic intersection is too slow [S1].
*   **When Not to Use:** In non-OptiX environments or when exact Gaussian intersection is required without approximation [S1].

## Background
The IRIS method was introduced in the paper "IRIS: Intersection-aware Ray-based Implicit Editable Scenes" in 2026 [S1]. It builds on the 3DGRT OptiX API-based approach [S1]. The method is designed for implicit editable scenes and uses a slightly modified version of the 3DGRT pipeline [S1]. It is implemented in PyTorch within the Nerfstudio ecosystem [S1].
