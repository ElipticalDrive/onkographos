# Exact Rational Ray-Surfel Evaluation

Also called: Homography-based Ray-Surfel Intersection, Screen-space Homography Surfel Intersection

## Overview
Exact Rational Ray-Surfel Evaluation computes the intersection of a viewing ray with a flat surfel rectangle in its local $(u, v)$ coordinates using a homography approximation around the center of the screen-space bounding box [S1, unofficial]. It sets itself apart from the reference 2DGS formulation by replacing the per-pixel cross-product-based inversion with a precomputed affine approximation, reducing computational cost while maintaining visual fidelity [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** The surfel's screen-space bounding box center $(u_0, v_0)$, the Jacobian matrix $\mathbf{J}$ of the homography, the ray direction vector $\mathbf{d}$, and the pixel offset $\Delta$ from the center $(u_0, v_0)$.
*   **Output:** The local coordinates $(u, v)$ of the intersection point on the surfel.

**Data Structures:**
*   $\mathbf{J}$: A $2 \times 2$ matrix representing the linear part of the homography.
*   $\Delta$: A 2D vector $(\Delta_u, \Delta_v)$ representing the pixel's offset from the bounding box center.
*   $\mathbf{d}$: A 3D vector representing the ray direction.

**Steps:**
1.  Compute the dot product $d^{\top}\Delta$. Note that $\mathbf{d}$ is typically treated as a 2D vector in the context of the homography derivation or projected appropriately; however, the source formula uses $d^{\top}\Delta$ directly [S1, unofficial].
2.  Compute the numerator vector $\mathbf{J}\Delta$.
3.  Compute the denominator $1 + d^{\top}\Delta$.
4.  Calculate $u$ and $v$ using the rational functions below.

**Formulas:**
The local coordinates are approximated as [S1, unofficial]:

$$
u = u_0 + \frac{(\mathbf{J}\Delta)_u}{1 + d^{\top}\Delta}
$$

$$
v = v_0 + \frac{(\mathbf{J}\Delta)_v}{1 + d^{\top}\Delta}
$$

Where:
*   $(u_0, v_0)$ is the center of the surfel's screen-space bounding box.
*   $\mathbf{J}$ is the Jacobian matrix of the homography.
*   $\Delta$ is the offset from the center $(u_0, v_0)$ to the current pixel.
*   $d$ is the ray direction.

**Pseudocode:**
```python
def exact_rational_ray_surfel_evaluation(u0, v0, J, d, pixel_u, pixel_v):
    # Calculate offset from center
    delta_u = pixel_u - u0
    delta_v = pixel_v - v0
    delta = (delta_u, delta_v)
    
    # Calculate dot product d^T * delta
    # Note: d is a 3D vector, delta is 2D. 
    # The source formula implies a specific projection or 2D reduction of d.
    # Assuming d is projected or reduced to 2D components (dx, dy) compatible with delta.
    # If d is strictly 3D, this step requires clarification on projection.
    # Based on standard homography, d is often the ray direction in camera space.
    # We assume d here refers to the relevant 2D components or the formula 
    # implies a specific 2D dot product context.
    # For implementation, if d is 3D (dx, dy, dz), and delta is 2D, 
    # the term d^T * delta is ambiguous without further context on d's dimensionality 
    # in the homography derivation. 
    # However, following the source strictly:
    d_dot_delta = d[0] * delta_u + d[1] * delta_v # Assuming d is treated as 2D or projected
    
    denominator = 1.0 + d_dot_delta
    
    # Calculate J * delta
    # J is 2x2 matrix [[J00, J01], [J10, J11]]
    j_delta_u = J[0][0] * delta_u + J[0][1] * delta_v
    j_delta_v = J[1][0] * delta_u + J[1][1] * delta_v
    
    # Calculate u and v
    u = u0 + j_delta_u / denominator
    v = v0 + j_delta_v / denominator
    
    return u, v
```

**Parameters:**
*   Typical values are not specified in the sources. The method relies on the geometric properties of the surfel and the camera.

**Edge Cases and Pitfalls:**
*   **Division by Zero:** If $1 + d^{\top}\Delta = 0$, the denominator becomes zero. This corresponds to a singularity in the homography mapping.
*   **Precision:** The method avoids per-pixel cross products and divisions inherent in the 2DGS formulation, improving performance [S1, unofficial].
*   **Approximation:** The method is an approximation around the center of the bounding box. For large bounding boxes, the error may increase.

## Operating characteristics
**Time and Memory Complexity:**
*   The method reduces computational cost by avoiding per-pixel cross products and divisions [S1, unofficial].
*   It allows most of the intersection cost to leave the pixel loop [S1, unofficial].

**Measured Performance:**
*   On Mip-NeRF 360, Tanks & Temples, and Deep Blending, mean frame rates rise to 2698, 3016, and 4413 FPS, respectively, 1.8× over the CUDA implementation [S1, unofficial].
*   Fragment-bound scenes gain most (+47% on stump and flowers) and scenes bound by sorting and binning gain least (+20% on train) [S1, unofficial].

**Strengths and Limitations:**
*   **Strengths:** High performance on fragment-bound scenes; matches hardware rasterizer quality with at most 0.05 dB and 0.0007 LPIPS deviation [S1, unofficial].
*   **Limitations:** The hardware rasterizer has no ray–surfel variant, so the 2DGS intersection comparison was timed only on the CUDA renderer [S1, unofficial].

**When to Use:**
*   Use when performance is critical and the scene is fragment-bound.
*   Avoid when the surfel bounding boxes are very large, as the approximation error may increase.

## Background
The method was introduced in "Bake It Till You Make It: Ultrafast Spatial Texture-Atlas Splatting" [S1, unofficial]. It addresses the per-pixel cost of surfel intersection in 2DGS, which 3DGS avoids by working directly in image space [S1, unofficial].
