# Closed-form perspective-correct surfel rasterization

Also called: homography-based surfel projection, rational interpolation for surfels

## Overview
A rasterization technique for planar surfels that computes screen-space texture coordinates $(u, v)$ using an algebraically exact rational function of pixel position, avoiding per-pixel cross products and vector constructions [S1, unofficial]. It sets itself apart from the reference 2DGS formulation by replacing the per-pixel cross-product-based inversion with a precomputed affine approximation, reducing computational cost while maintaining visual fidelity [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A surfel defined in camera space, the current camera projection matrix, and the screen-space bounding box of the surfel [S1, unofficial].
*   **Output:** For each pixel $(x, y)$ within the bounding box, the interpolated texture coordinates $(u, v)$ and a validity flag [S1, unofficial].

**Data Structures:**
The method precomputes eight coefficients per surfel per frame [S1, unofficial]. These are stored in a structure with the following layout:
*   `u0`, `v0`: `float16` (FP16). The intersection coordinates at the center of the screen-space bounding box [S1, unofficial].
*   `J_uu`, `J_uv`, `J_vu`, `J_vv`: `float16` (FP16). Elements of the Jacobian matrix $\mathbf{J}$, representing the rate of change of $u$ and $v$ per pixel offset [S1, unofficial].
*   `opacity`, `shape`: `float16` (FP16). Surfels' opacity and shape parameters (contextual, not part of the coordinate formula but stored alongside) [S1, unofficial].
*   `d_x`, `d_y`: `float32` (FP32). Components of the perspective denominator gradient vector $\mathbf{d}$ [S1, unofficial]. Stored in FP32 because they span several orders of magnitude; errors here scale across the entire surfel [S1, unofficial].

**Numbered Steps:**
1. Determine the screen-space bounding box of the surfel [S1, unofficial].
2. Compute the center of this bounding box, $(x_c, y_c)$ [S1, unofficial].
3. Evaluate the surfel intersection at the center to obtain $(u_0, v_0)$ [S1, unofficial].
4. Compute the Jacobian $\mathbf{J}$ and the denominator gradient $\mathbf{d}$ at the center [S1, unofficial].
5. Store the eight coefficients: $(u_0, v_0)$, $\mathbf{J}$, and $\mathbf{d}$ [S1, unofficial].
6. For each pixel $(x, y)$ in the bounding box, calculate the pixel offset from the center: $\Delta = (x - x_c, y - y_c)$ [S1, unofficial].
7. Compute the perspective denominator: $denom = 1 + \mathbf{d}^{\top}\Delta$ [S1, unofficial].
8. **Edge Case/Pitfall:** If $denom \le 0$, the plane is parallel to or behind the camera for this pixel. Skip the fragment [S1, unofficial].
9. Compute the numerator corrections: $num_u = (\mathbf{J}\Delta)_u$ and $num_v = (\mathbf{J}\Delta)_v$ [S1, unofficial].
10. Evaluate the final coordinates: $u = u_0 + \frac{num_u}{denom}$ and $v = v_0 + \frac{num_v}{denom}$ [S1, unofficial].

**Formula:**
The core interpolation formula is:
$$ u = u_0 + \frac{(\mathbf{J}\Delta)_u}{1 + \mathbf{d}^{\top}\Delta}, \quad v = v_0 + \frac{(\mathbf{J}\Delta)_v}{1 + \mathbf{d}^{\top}\Delta} $$
Where:
*   $\Delta$ is the pixel offset from the bounding box center [S1, unofficial].
*   $(u_0, v_0)$ is the intersection at the center [S1, unofficial].
*   $\mathbf{J}$ is the Jacobian (rate of change per pixel) [S1, unofficial].
*   $\mathbf{d}$ is the gradient of the perspective denominator [S1, unofficial].

**Pseudocode:**
```python
def cross(a, b):
    return [a[1]*b[2] - a[2]*b[1], a[2]*b[0] - a[0]*b[2], a[0]*b[1] - a[1]*b[0]]

def precompute_surfel_coefficients(T_u, T_v, T_w, x_c, y_c):
    # p = T_u x T_v - y(T_u x T_w) - x(T_w x T_v)
    # p_x = -(T_w x T_v) = T_v x T_w
    # p_y = -(T_u x T_w) = T_w x T_u
    p0 = cross(T_u, T_v)
    px = cross(T_v, T_w)
    py = cross(T_w, T_u)
    
    # Evaluate vector p at center
    p_c = [p0[i] + x_c * px[i] + y_c * py[i] for i in range(3)]
    p_c_z = p_c[2]
    
    # u0, v0
    u0 = p_c[0] / p_c_z
    v0 = p_c[1] / p_c_z
    
    # Jacobian J and gradient d
    J_uu = px[0] / p_c_z
    J_uv = py[0] / p_c_z
    J_vu = px[1] / p_c_z
    J_vv = py[1] / p_c_z
    d_x = px[2] / p_c_z
    d_y = py[2] / p_c_z
    
    return u0, v0, J_uu, J_uv, J_vu, J_vv, d_x, d_y

def rasterize_surfel_pixel(u0, v0, J_uu, J_uv, J_vu, J_vv, d_x, d_y, delta_x, delta_y):
    denom = 1.0 + (d_x * delta_x + d_y * delta_y)
    if denom <= 0.0:
        return None, None, False
    num_u = J_uu * delta_x + J_uv * delta_y
    num_v = J_vu * delta_x + J_vv * delta_y
    u = u0 + num_u / denom
    v = v0 + num_v / denom
    return u, v, True
```

**Parameters:**
*   **Precision Split:** $(u_0, v_0)$, $\mathbf{J}$, opacity, and shape are stored as FP16. The denominator gradient $\mathbf{d}$ is stored as FP32 [S1, unofficial].
*   **Typical Values:** Not given in the sources [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Denominator $\le 0$:** Pixels with a non-positive denominator look at the plane from behind the camera and must be skipped [S1, unofficial].
*   **Floating-Point Reassociation:** Near the alpha cutoff, floating-point reassociation can flip whether a fragment is drawn, causing non-byte-identical renders between the closed-form and reference methods (59–66 dB PSNR difference), though visual quality remains high [S1, unofficial].
*   **Precision Sensitivity:** Errors in $\mathbf{d}$ scale across the whole surfel, necessitating FP32 storage [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Per pixel, the method requires about 10 fused multiply-adds and one division, compared to roughly 15 fused multiply-adds and two divisions in the reference method [S1, unofficial].
*   **Memory Complexity:** The precomputation stores 8 coefficients per surfel [S1, unofficial]. The staging changes no arithmetic, only the shared-memory layout [S1, unofficial].
*   **Measured Performance:** 32% higher mean frame rate than 2DGS on tested scenes [S1, unofficial].
*   **Quality:** The renders match the 2DGS formulation to within 0.03 dB PSNR and 0.0002 LPIPS on 13 scenes [S1, unofficial].
*   **Strengths:** No per-pixel cross product, making it computationally cheaper and numerically safer than packing plane rows at reduced precision (which costs 0.05–0.7 dB due to error amplification) [S1, unofficial].
*   **Limitations:** Not byte-identical to the reference method due to floating-point differences near alpha cutoffs [S1, unofficial].

## Background
This method is described in "Bake It Till You Make It: Ultrafast Spatial Texture-Atlas Splatting" [S1, unofficial]. It builds on the homography projection properties of planar surfels, exploiting the fact that $(u, v)$ is a ratio of two linear functions of the pixel position, similar to perspective-correct texturing in rasterizers [S1, unofficial].
