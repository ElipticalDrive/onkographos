# Splat Raycasting Dispatch


## Overview
Splat Raycasting Dispatch is the core computational kernel that performs ray-splat intersection tests for Gaussian primitives, returning hit distances and primitive indices. It solves the problem of efficiently determining which splats intersect a given ray within a specified depth range, serving as the bridge between high-level scene management and low-level geometric intersection logic. It is distinguished from its siblings by its specific implementation as a batched, buffer-oriented dispatch function (often compiled to WebAssembly) that operates on pre-extracted subbuffers, whereas [Ray-Splat Intersection](6816-ray-splat-intersection.md) describes the general geometric algorithm and [Spherical Panoramic Gaussian Splatting (SPaGS)](3042-spherical-panoramic-gaussian-splatting-spags.md) adapts the coordinate space for spherical projections.

## How it works
The method takes a batch of splat records and a single ray, computing intersections for all splats in the batch against the ray. It outputs two arrays: one for the squared distances (or depths) of hits, and one for the corresponding splat indices.

### Inputs and Outputs
*   **Inputs**:
    *   `subbuffer`: Array of `u32` containing splat data (positions, covariances, etc.), size $4 \times \text{count}$.
    *   `subbuffer2`: Array of `u32` containing auxiliary splat data, size $4 \times \text{count}$.
    *   `origin`: Ray origin $(O_x, O_y, O_z)$ as `f32`.
    *   `dir`: Ray direction $(D_x, D_y, D_z)$ as `f32`.
    *   `min_opacity`: `f32` threshold for inclusion.
    *   `tables`: Precomputed lookup tables (e.g., for opacity or color) of type `RaycastTables`.
    *   `near`, `far`: `f32` clipping plane distances.
*   **Outputs**:
    *   `distances`: `Vec<f32>` of size `RAYCAST_BUFFER_COUNT`, populated with hit distances.
    *   `indices`: `Vec<u32>` of capacity `RAYCAST_BUFFER_COUNT`, populated with splat indices.

### Data Structures
The implementation relies on a fixed-capacity buffer structure to manage memory efficiently, particularly in constrained environments like WebAssembly.

*   **`RAYCAST_BUFFER_COUNT`**: Constant `usize` set to $65536$ [S1, unofficial].
*   **`RaycastBuffers` struct**:
    *   `splats`: `Vec<u32>`, size $65536 \times 4$.
    *   `splats2`: `Vec<u32>`, size $65536 \times 4$.
    *   `distances`: `Vec<f32>`, size $65536$.
    *   `indices`: `Vec<u32>`, capacity $65536$.
    *   `tables`: `RaycastTables` object.

### Steps
1.  **Validation**: Ensure the number of splats `count` (as `usize`) does not exceed `RAYCAST_BUFFER_COUNT` ($65536$). If it does, throw an error [S1, unofficial].
2.  **Buffer Extraction**: Extract the relevant subbuffers from the main splat arrays. Specifically, take `splats[0..(4 * count)]` and `splats2[0..(4 * count)]` [S1, unofficial].
3.  **Buffer Clearing**: Clear the `distances` and `indices` buffers to ensure no stale data from previous frames or batches remains [S1, unofficial].
4.  **Dispatch**: Call the core intersection function `raycast_splat_ellipsoids` with the extracted subbuffers, ray parameters, and clipping bounds [S1, unofficial].
    *   Function signature: `raycast_splat_ellipsoids(subbuffer, subbuffer2, distances, indices, origin, dir, min_opacity, tables, near, far)`
5.  **Return**: Return the `distances` array as a `Float32Array` view [S1, unofficial].

### Edge Cases and Pitfalls
*   **Buffer Overflow**: The `count` parameter must not exceed `RAYCAST_BUFFER_COUNT` ($65536$). Exceeding this limit throws an error [S1, unofficial].
*   **Precision**: The source uses `f32` for coordinates and distances. Implementers should be aware of potential precision issues with very large scene coordinates or very small splats, though no specific mitigation is mentioned in the source [S1, unofficial].
*   **Empty Batches**: If `count` is 0, the function should return empty buffers without error.

## Subtopics

### Splat Raycasting Implementation
This variant describes the higher-level JavaScript/TypeScript wrapper that manages the data flow between the scene graph and the WASM dispatch kernel. It handles coordinate transformation, buffer management, and result post-processing.
*   **Coordinate Transformation**: Transforms the ray origin and direction from world space to mesh space using the inverse of `matrixWorld` [S1, unofficial].
*   **Buffer Management**: Iterates over splat ranges using `splats.forEachRaycastRange`. For each range, it copies splat records into temporary buffers (`buffer` and `buffer2`) using `splats.copySplatRecords`, mapping original indices to `raycastVisibleIndices` [S1, unofficial].
*   **Flushing**: When the buffer capacity is reached, it flushes the data by calling `raycast_splat_buffers` (the dispatch kernel) with the current batch [S1, unofficial].
*   **Result Processing**: After the WASM call returns, it retrieves `distances` and `hitIndices`. For each hit, it computes the world point using `ray.at(distance)` and stores the distance, point, object, and original splat index in the `intersects` array [S1, unofficial].
*   **Parameters**: Uses `minRaycastOpacity` (default $0.1$), which must be strictly less than $1.0$ [S1, unofficial].
*   **Data Structures**: Uses `raycastVisibleIndices` (`Uint32Array`) to map buffer slot indices to original splat indices, sized to `buffer.length / 4`. This array is reallocated if capacity changes [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: Linear with respect to the number of splats in the batch, $O(N)$, where $N$ is the number of splats processed per dispatch call. The constant factor is low due to SIMD optimizations in the WASM backend.
*   **Memory Complexity**: Fixed buffer size of $65536$ splats. Memory usage is constant regardless of scene size, limited by the buffer capacity.
*   **Performance**: The method is designed for high-performance real-time rendering, leveraging WebAssembly for near-native speed. Performance is measured on web platforms with WASM support.
*   **Strengths**: Efficient batch processing, fixed memory footprint, easy integration with JavaScript/TypeScript ecosystems.
*   **Limitations**: Limited by the fixed buffer size ($65536$), requiring batching for larger scenes. Precision is limited to `f32`.
*   **When to Use**: Real-time web-based 3D Gaussian Splatting rendering.
*   **When Not to Use**: Scenes with more than $65536$ splats in a single raycast pass without batching, or applications requiring `f64` precision.

## Background
The method originates from the Gaussian-Splat-Lite project, an unofficial implementation of 3D Gaussian Splatting optimized for web browsers using WebAssembly [S1, unofficial]. It was developed by William Liu (WilliamLiu-1997) and published on GitHub [S1, unofficial]. The project aims to provide a lightweight, efficient renderer for 3D Gaussian Splatting in the browser, leveraging Rust for the core computation and WebAssembly for execution.
