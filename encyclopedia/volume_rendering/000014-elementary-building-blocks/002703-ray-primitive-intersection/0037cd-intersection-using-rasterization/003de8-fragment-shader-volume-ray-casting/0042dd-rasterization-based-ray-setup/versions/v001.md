# Rasterization-based Ray Setup

Also called: Raycast Shader Setup, RenderVolume, bounding box rasterization

## Overview
Rasterization-based ray setup is a method for generating ray origins and directions for volume ray casting by rasterizing the volume's bounding box geometry [S2, unofficial]. It solves the problem of mapping screen-space fragments to 3D ray parameters efficiently on the GPU [S2, unofficial]. Unlike procedural intersection methods which may require different logic for orthogonal versus perspective projections, this approach yields identical ray setup logic for both projection types [S2, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Volume 3D texture, transfer function texture, camera position, model-view-projection matrices (or inverted model matrix), and a full-screen quad vertex buffer.
*   **Output:** Fragment shader outputs containing ray start position and direction vector (or start/exit positions) for subsequent ray marching.

**Data Structures:**
*   **Vertex Buffer:** Contains a quad (4 vertices) with two attributes per vertex:
    *   Position: 2 floats (offset 0 bytes).
    *   UV coordinates: 2 floats (offset 8 bytes).
*   **Textures:**
    *   Unit 0: Volume 3D texture.
    *   Unit 1: Front face depth texture (from bounding box rasterization).
    *   Unit 2: Back face depth texture (from bounding box rasterization).
    *   Unit 3: Transfer function texture.

**Parameters:**
*   `camerapos`: World space camera position [S1, unofficial].
*   `invertedmodel`: Inverted model matrix for transforming camera space to world space [S1, unofficial].
*   `transferindex`: Uniform index for transfer function lookup [S1, unofficial].

**Steps:**
1.  Bind the raycast program.
2.  Bind the volume 3D texture to texture unit 0.
3.  Bind the front face depth texture to texture unit 1.
4.  Bind the back face depth texture to texture unit 2.
5.  Bind the transfer function texture to texture unit 3.
6.  Set the uniform `transferindex`.
7.  Set the uniform `camerapos` (world space).
8.  Set the uniform `invertedmodel`.
9.  Bind the quad vertex buffer with vertex attribute at offset 0 (2 floats) and UV attribute at offset 8 bytes (2 floats).
10. Draw `GL_TRIANGLE_STRIP` with 4 vertices [S1, unofficial].

**Fragment Shader Logic:**
For each fragment generated by rasterizing the bounding box:
1.  Compute the ray start position and direction vector based on the fragment's screen coordinates and the bounding box intersection [S2, unofficial].
2.  The ray start position is typically determined by the intersection of the view ray with the front face of the bounding box.
3.  The ray direction is computed from the camera position to the fragment's world position.

**Pseudocode:**
```python
# Vertex Shader (simplified)
# Input: Quad vertices with position (x, y) and UV (u, v)
# Output: gl_Position, varying_uv

vec4 clip_space_pos = vec4(position.xy, 0.0, 1.0);
gl_Position = clip_space_pos;
varying_uv = uv;

# Fragment Shader
uniform sampler3D volume_texture;
uniform sampler2D front_depth_texture;
uniform sampler2D back_depth_texture;
uniform sampler3D transfer_function;
uniform vec3 camerapos;
uniform mat4 invertedmodel;

void main() {
    // 1. Get depth values from front and back faces of the bounding box
    // Note: These textures are generated by rasterizing the bounding box
    // from front and back views respectively.
    float front_depth = texture(front_depth_texture, varying_uv).r;
    float back_depth = texture(back_depth_texture, varying_uv).r;

    // 2. Compute ray start and end positions in world space
    // This requires reconstructing world coordinates from depth and UV
    // The exact reconstruction depends on the projection matrix used
    // during the depth texture generation pass.
    
    // Reconstruct world position from depth and UV
    // This step assumes standard OpenGL depth range [0, 1] and linear depth
    // or appropriate inverse projection matrix usage.
    vec4 clip_pos = vec4(varying_uv * 2.0 - 1.0, front_depth, 1.0);
    vec4 view_pos = inverse_projection_matrix * clip_pos;
    vec3 world_pos = (invertedmodel * view_pos).xyz;

    // Ray direction is from camera to world position
    vec3 ray_direction = normalize(world_pos - camerapos);
    
    // Ray start position is the world position on the front face
    vec3 ray_start = world_pos;

    // 3. Output ray parameters for volume ray casting
    // The actual ray marching loop is performed in a subsequent pass
    // or within this shader if single-pass is desired.
    // For this setup, we typically output ray_start and ray_direction
    // to be used in the next stage.
    
    // [G] In a full implementation, the ray marching loop would follow
    // here, using ray_start, ray_direction, and the volume texture.
    // However, the "Rasterization-based Ray Setup" specifically refers
    // to the generation of these parameters.
}
```

**Edge Cases and Pitfalls:**
*   **Precision:** Depth precision in the front/back face depth textures can affect ray start accuracy, especially for large volumes or distant cameras.
*   **Boundaries:** The bounding box must tightly enclose the volume data to avoid unnecessary ray casting through empty space.
*   **Degenerate Input:** If the volume is empty or the bounding box is invalid, the depth textures may not be populated correctly, leading to undefined ray parameters.

## Subtopics

### Procedural Ray/Box Intersection
Computes ray-box intersection analytically in the shader. Chosen when avoiding the extra pass for depth textures is preferred, but may require different logic for perspective vs. orthogonal projections [S2, unofficial].

### Early Ray Termination
Optimization technique to stop ray casting when a surface is hit or opacity threshold is reached. Can be implemented using early-z-test or loop breaks [S2, unofficial].

### Empty Space Skipping
Optimization to skip transparent regions, often using hierarchical structures or tighter bounding geometry [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** O(1) for ray setup per fragment, plus O(N) for ray marching where N is the number of samples along the ray.
*   **Memory Complexity:** Requires storage for front and back face depth textures (2 * width * height * 4 bytes each) plus the volume texture.
*   **Performance:** Efficient on modern GPUs due to parallel fragment processing. The extra pass for depth textures adds overhead but simplifies the ray setup logic.
*   **Strengths:** Identical logic for orthogonal and perspective projections; easy to implement with standard rasterization pipelines.
*   **Limitations:** Requires an additional render pass to generate depth textures; depth precision issues can affect accuracy.
*   **When to Use:** Suitable for real-time volume rendering where simplicity and compatibility with standard rasterization pipelines are prioritized.
*   **When Not to Use:** When memory bandwidth is a critical bottleneck due to the extra depth textures, or when extremely high precision is required for ray origins.

## Background
The rasterization-based ray setup approach was introduced by Krüger and Westermann in 2003 [S2, unofficial]. It emerged as an alternative to procedural ray/box intersection methods proposed by Röttger et al. (2003) and Green (2004) [S2, unofficial]. This method leverages the GPU's rasterization capabilities to generate ray parameters, simplifying the shader logic and ensuring consistency across different projection types.
