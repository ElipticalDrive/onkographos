# Ray-Box Intersection via OpenGL Geometry Shaders

Also called: CubeIntersection, Front/Back Hit Textures

## Overview
This method computes the 3D entry and exit points of view rays intersecting a volume's bounding box by rasterizing the box geometry to textures, thereby avoiding procedural intersection calculations in the fragment shader [S1, unofficial]. It leverages the GPU's parallel rasterization pipeline to generate ray setup data as a byproduct of rendering a simple color cube [S1, unofficial]. Unlike analytical ray-box intersection tests, it relies on face culling and depth testing to separate front and back intersections across two rendering passes [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A camera projection matrix (Model-View-Projection, MVP), a boolean flag `m_bFront` indicating whether to compute the front (entry) or back (exit) intersection, and the geometry of a unit cube centered at the origin [S1, unofficial].
*   **Output:** Two 2D textures (`TEXTURE_FRONT_HIT` and `TEXTURE_BACK_HIT`) storing the 3D world-space intersection coordinates for each pixel [S1, unofficial].

**Data Structures:**
*   **Hit Textures:** Two 2D textures of size $W \times H$ (matching the viewport resolution) [S1, unofficial].
    *   Format: `GL_RGBA16F`
    *   Internal Format: `GL_RGBA16F`
    *   Type: `GL_FLOAT`
    *   Layout: Each texel stores a 4-component vector $(x, y, z, w)$. The $x, y, z$ components store the world-space intersection point. The $w$ component is typically unused or set to 1.0 [G].
*   **Framebuffer Object (FBO):** Contains the color attachment (the hit texture) and a depth renderbuffer [S1, unofficial].
    *   **Depth Buffer:** Format `GL_DEPTH_COMPONENT16` [S1, unofficial].

**Numbered Steps:**
1.  **Initialize FBO:** Create a Framebuffer Object (FBO). Attach a `GL_RGBA16F` texture as the color attachment (either `TEXTURE_FRONT_HIT` or `TEXTURE_BACK_HIT`). Attach a `GL_DEPTH_COMPONENT16` renderbuffer as the depth attachment. Clear both the color buffer and the depth buffer [S1, unofficial].
2.  **Configure Rasterization State:** Enable `GL_CULL_FACE` and `GL_DEPTH_TEST` [S1, unofficial]. Set the culling mode based on the `m_bFront` flag: if `m_bFront` is true, cull `GL_BACK` faces to capture only the front-facing intersections (entry points); if `m_bFront` is false, cull `GL_FRONT` faces to capture only the back-facing intersections (exit points) [S1, unofficial].
3.  **Render Geometry:** Bind the "hit shader" program. Pass the MVP matrix as a uniform variable to the shader program [S1, unofficial]. Draw the cube geometry using the hit shader program [S1, unofficial].
4.  **Shader Execution:** The shader consists of a Vertex Shader, a Geometry Shader, and a Fragment Shader [G]. The Vertex Shader passes vertex positions to the geometry shader [G]. The Geometry Shader receives the triangle vertices, computes the intersection of the view ray with the triangle plane, and outputs the intersection point as a single point primitive [G]. The position is transformed into clip space and written to `gl_Position` to ensure correct depth testing [G]. The world-space intersection coordinates are passed to the fragment shader as varying/interpolated values [G]. The Fragment Shader receives the interpolated world-space intersection coordinates and writes them to the output color buffer (the hit texture) [G]. Since the depth test is enabled and the geometry shader outputs points at the correct depth, only the closest intersection (front or back) is written per pixel [G].
5.  **Repeat:** Repeat steps 1-4 for the back hit texture by toggling the `m_bFront` flag to false [S1, unofficial].

**Formulas:**
*   **Ray Definition:** For a pixel at screen coordinates $(u, v)$, the view ray origin $\mathbf{o}$ and direction $\mathbf{d}$ in world space are derived from the inverse projection and view matrices [G]. The geometry shader typically computes the intersection of this ray with the triangle plane defined by vertices $\mathbf{v}_0, \mathbf{v}_1, \mathbf{v}_2$ [G].
*   **Plane Intersection:** Given a triangle plane with normal $\mathbf{n}$ and a point $\mathbf{p}_0$ on the plane, the intersection distance $t$ along the ray $\mathbf{o} + t\mathbf{d}$ is:
    $$ t = \frac{(\mathbf{p}_0 - \mathbf{o}) \cdot \mathbf{n}}{\mathbf{d} \cdot \mathbf{n}} $$
    The intersection point is $\mathbf{p}_{hit} = \mathbf{o} + t\mathbf{d}$ [G].
*   **Depth Writing:** The geometry shader must transform $\mathbf{p}_{hit}$ into clip space to set `gl_Position`, ensuring the depth buffer correctly resolves occlusions between front and back faces if they were rendered simultaneously (though they are rendered separately here) or between multiple triangles [G].

**Parameters:**
*   `m_bFront`: Boolean flag. `true` for entry points, `false` for exit points [S1, unofficial].
*   `MVP`: Model-View-Projection matrix uniform [S1, unofficial].
*   `Width`, `Height`: Resolution of the hit textures [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Depth Buffer Precision:** The depth buffer is cleared along with the color buffer, but the depth test is enabled, requiring correct depth writing from the geometry shader [S1, unofficial]. Using `GL_DEPTH_COMPONENT16` may lead to precision issues for large bounding boxes or small depth differences [G].
*   **Degenerate Triangles:** Ensure the cube geometry does not produce degenerate triangles that could cause undefined behavior in the geometry shader [G].
*   **Ray-Box Tangency:** Rays that are tangent to the box edges or corners may produce unstable intersection results. The rasterization approach handles this via depth testing, but precision limits may cause flickering or missed hits [G].
*   **Face Culling:** Incorrect culling configuration (e.g., culling both front and back) will result in empty hit textures. The culling mode must be explicitly set based on the desired hit type [S1, unofficial].
*   **Shader Compilation:** Ensure the hit shader program is correctly compiled and linked. Shader compilation errors should be checked and reported [G].

**Pseudocode:**
```python
def render_hit_textures(cube_geometry, mvp_matrix, width, height, front_flag):
    """
    Renders the front or back hit textures for ray-box intersection.
    
    Args:
        cube_geometry: List of triangle indices or vertex data for a unit cube.
        mvp_matrix: 4x4 Model-View-Projection matrix.
        width: Width of the output texture.
        height: Height of the output texture.
        front_flag: Boolean, True for front (entry) hits, False for back (exit) hits.
    
    Returns:
        hit_texture: 2D texture containing the intersection points.
    """
    # 1. Create and configure FBO
    fbo = glGenFramebuffers(1)
    hit_texture = glGenTextures(1)
    glBindTexture(GL_TEXTURE_2D, hit_texture)
    glTexImage2D(GL_TEXTURE_2D, 0, GL_RGBA16F, width, height, 0, GL_RGBA, GL_FLOAT, None)
    depth_buffer = glGenRenderbuffers(1)
    glBindRenderbuffer(GL_RENDERBUFFER, depth_buffer)
    glRenderbufferStorage(GL_RENDERBUFFER, GL_DEPTH_COMPONENT16, width, height)
    
    glBindFramebuffer(GL_FRAMEBUFFER, fbo)
    glFramebufferTexture2D(GL_FRAMEBUFFER, GL_COLOR_ATTACHMENT0, GL_TEXTURE_2D, hit_texture, 0)
    glFramebufferRenderbuffer(GL_FRAMEBUFFER, GL_DEPTH_ATTACHMENT, GL_RENDERBUFFER, depth_buffer)
    
    if glCheckFramebufferStatus(GL_FRAMEBUFFER) != GL_FRAMEBUFFER_COMPLETE:
        raise RuntimeError("FBO is incomplete")
    
    # 2. Configure rasterization state
    glEnable(GL_CULL_FACE)
    glEnable(GL_DEPTH_TEST)
    
    if front_flag:
        glCullFace(GL_BACK) # Cull back faces to get front hits
    else:
        glCullFace(GL_FRONT) # Cull front faces to get back hits
    
    glDepthFunc(GL_LEQUAL)
    
    # 3. Clear buffers
    glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT)
    
    # 4. Bind and use hit shader program
    hit_shader = load_hit_shader_program() # Contains Vertex, Geometry, Fragment shaders
    glUseProgram(hit_shader)
    
    # 5. Set uniforms
    glUniformMatrix4fv(glGetUniformLocation(hit_shader, "mvp_matrix"), 1, GL_FALSE, mvp_matrix)
    
    # 6. Draw cube geometry
    glDrawElements(GL_TRIANGLES, len(cube_geometry), GL_UNSIGNED_INT, cube_geometry)
    
    # 7. Unbind FBO
    glBindFramebuffer(GL_FRAMEBUFFER, 0)
    
    return hit_texture
```

## Subtopics

### [Two-Pass Ray Entry/Exit Determination](2669-two-pass-ray-entry-exit-determination.md)
This method determines the 3D entry and exit points of view rays intersecting a volume’s bounding box by rasterizing the box geometry to textures, thereby avoiding procedural intersection calculations in the fragment shader. It sets apart from analytical ray-box intersection tests by leveraging the GPU's parallel rasterization pipeline to generate ray setup data as a byproduct of rendering a simple color cube [G]. Unlike the parent method which uses geometry shaders to output hit positions, this approach relies on standard vertex/fragment pipelines with face culling to separate front and back intersections [G].

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the number of pixels in the viewport. The cost is dominated by the rasterization of the cube geometry, which is constant per frame regardless of scene complexity [G].
*   **Memory Complexity:** $O(W \times H)$ for the hit textures and depth buffer, where $W$ and $H$ are the viewport dimensions [G].
*   **Measured Performance:** Performance depends on the GPU's rasterization speed and the resolution of the hit textures. For high-resolution viewports, the cost can be significant. However, it is generally faster than per-ray analytical intersection tests for large numbers of rays [G].
*   **Scaling:** Scales linearly with viewport resolution. Does not scale with scene complexity (number of volumes) as it only renders the bounding box [G].
*   **Strengths:**
    *   Avoids complex ray-box intersection math in shaders [G].
    *   Leverages GPU parallelism for ray setup [G].
    *   Simple to implement using standard OpenGL features [G].
*   **Limitations:**
    *   Requires two passes (front and back) or a more complex single-pass approach [G].
    *   Precision issues with depth buffer can affect accuracy [G].
    *   Only works for axis-aligned boxes (or requires transformation to align with axes) [G].
    *   Dependent on OpenGL geometry shaders, which may not be available or performant on all hardware (e.g., mobile GPUs) [G].
*   **When to Use:** Suitable for volume rendering applications where ray-box intersection is a bottleneck and the bounding boxes are axis-aligned. Best for desktop GPUs with robust geometry shader support [G].
*   **When Not to Use:** Not suitable for mobile GPUs without geometry shader support. Not ideal for non-axis-aligned boxes without additional transformation overhead [G].

## Background
This method is implemented in the VRCUDA project, an unofficial implementation of volume rendering using CUDA and OpenGL interoperability [S1, unofficial]. It was developed to optimize the ray-box intersection step in volume rendering pipelines by offloading the computation to the GPU's rasterization hardware. The technique is particularly useful in real-time volume rendering applications where performance is critical [S1, unofficial].
