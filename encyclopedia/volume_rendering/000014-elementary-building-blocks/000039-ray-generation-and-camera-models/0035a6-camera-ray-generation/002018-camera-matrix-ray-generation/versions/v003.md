# Camera Matrix Ray Generation

Also called: Camera Ray Generation, Raster-to-World Ray Construction, Ray Generation from Camera Matrix, Ray Initialization & AABB Intersection, getBound, initialRays

## Overview
Camera Matrix Ray Generation computes the origin and direction of a primary ray for each pixel in an image based on camera intrinsic parameters (focal length, principal point) and extrinsic parameters (camera-to-world pose) [S10, S13, S16, unofficial]. It solves the problem of mapping 2D raster coordinates to 3D world-space rays, enabling subsequent volume rendering or ray tracing operations [S1, S4, S5, unofficial]. Unlike orthographic generation which uses parallel rays, this method constructs perspective rays that diverge from a single viewpoint [S10, S16, unofficial].

## How it works
**Inputs:**
*   Image dimensions: $H$ (height), $W$ (width) [S10, S16, unofficial].
*   Camera intrinsic matrix $K$ (3x3) or parameters: focal lengths $f_x, f_y$, principal point $(c_x, c_y)$ [S10, S13, S27, unofficial].
*   Camera-to-world transformation matrix $T_{c2w}$ (4x4), where the upper-left 3x3 block is rotation $\mathbf{R}_{c2w}$ and the translation vector is $\mathbf{t}_{c2w}$ (camera origin) [S10, S16, S27, unofficial].
*   Optional: Axis-aligned bounding box (AABB) of the scene for early ray termination [S13, unofficial].

**Outputs:**
*   Ray origins $\mathbf{o}$: Tensor of shape $(H, W, 3)$ in world space [S10, S16, unofficial].
*   Ray directions $\mathbf{d}$: Tensor of shape $(H, W, 3)$ in world space (often normalized) [S10, S16, unofficial].
*   Optional: Near and far t-values ($t_{min}, t_{max}$) for AABB intersection [S13, unofficial].

**Data Structures:**
*   Pixel coordinate grids: 2D arrays of shape $(H, W)$ containing integer or float pixel indices $i$ (column, width) and $j$ (row, height) [S10, S16, S20, unofficial].
*   Intrinsic parameters: Extracted from $K$ as scalars or vectors [S10, S27, unofficial].
*   Transformation matrices: Stored as 4x4 matrices or separate rotation/translation components [S10, S16, unofficial].

**Steps:**

1.  **Generate Pixel Coordinates:** Create 2D meshgrids for pixel indices $i \in [0, W)$ and $j \in [0, H)$ [S10, S16, S20, unofficial].
2.  **Center Pixel Coordinates (Optional):** Add 0.5 to $i$ and $j$ to target pixel centers instead of corners [S7, S13, S20, unofficial]. Note: Some implementations omit this if calibration accuracy is insufficient [S8, unofficial].
3.  **Compute Camera-Space Directions:** Calculate unnormalized direction vectors in the camera coordinate system [S10, S26, unofficial]. The camera typically looks along the negative Z-axis (OpenGL convention) or positive Z-axis (OpenCV convention) [S10, S25, S26, S9, unofficial]. For the standard OpenGL convention (looking down -Z):
    $$
    \mathbf{d}_{cam} = \begin{bmatrix} \frac{i - c_x}{f_x} \\ -\frac{j - c_y}{f_y} \\ -1 \end{bmatrix}
    $$
    where the negative sign on the Y-component accounts for the image Y-axis being opposite to the camera V-axis (down vs up) [S10, S20, S25, S26, unofficial]. For OpenCV convention (looking down +Z), the Z component is $1$ and Y sign may vary depending on image orientation [S9, S27, unofficial].
4.  **Transform Directions to World Space:** Rotate the camera-space directions into world space using the rotation part of the camera-to-world matrix:
    $$
    \mathbf{d}_{world} = \mathbf{R}_{c2w} \mathbf{d}_{cam}
    $$
    [S10, S16, S26, S27, unofficial].
5.  **Set Ray Origins:** The ray origin is the camera position in world space, extracted from the translation component of $T_{c2w}$:
    $$
    \mathbf{o}_{world} = \mathbf{t}_{c2w}
    $$
    This origin is broadcast to match the shape of the directions $(H, W, 3)$ [S10, S16, S20, unofficial].
6.  **Normalize Directions (Optional):** Normalize $\mathbf{d}_{world}$ to unit length if required by the renderer [S10, S15, unofficial].
7.  **Compute AABB Intersection (Optional):** If an AABB is provided, compute $t_{min}$ and $t_{max}$ for each ray to determine the valid marching range [S13, unofficial].

**Pseudocode:**

```python
def generate_rays(H, W, K, c2w, use_pixel_centers=True, compute_aabb=False, aabb_min=None, aabb_max=None):
    # 1. Extract intrinsics
    fx = K[0][0]
    fy = K[1][1]
    cx = K[0][2]
    cy = K[1][2]
    
    # 2. Extract extrinsics
    R_c2w = [[c2w[r][c] for c in range(3)] for r in range(3)]
    t_c2w = [c2w[0][3], c2w[1][3], c2w[2][3]]
    
    rays_o = []
    rays_d = []
    t_min_list = []
    t_max_list = []
    
    for j in range(H):
        row_o = []
        row_d = []
        row_tmin = []
        row_tmax = []
        for i in range(W):
            px = float(i)
            py = float(j)
            if use_pixel_centers:
                px += 0.5
                py += 0.5
                
            # 3. Camera-space direction (OpenGL: look down -Z)
            dx = (px - cx) / fx
            dy = -(py - cy) / fy
            dz = -1.0
            
            # 4. Transform to world space
            wx = R_c2w[0][0]*dx + R_c2w[0][1]*dy + R_c2w[0][2]*dz
            wy = R_c2w[1][0]*dx + R_c2w[1][1]*dy + R_c2w[1][2]*dz
            wz = R_c2w[2][0]*dx + R_c2w[2][1]*dy + R_c2w[2][2]*dz
            
            # 5. Normalize
            len_d = (wx*wx + wy*wy + wz*wz)**0.5
            if len_d > 0:
                wx, wy, wz = wx/len_d, wy/len_d, wz/len_d
                
            # 6. Origin
            ox, oy, oz = t_c2w[0], t_c2w[1], t_c2w[2]
            
            row_o.append((ox, oy, oz))
            row_d.append((wx, wy, wz))
            
            if compute_aabb and aabb_min is not None and aabb_max is not None:
                # 7. Ray-AABB intersection (slab method)
                def safe_div(num, den):
                    return num / den if den != 0 else float('inf')
                    
                t_x0 = safe_div(aabb_min[0] - ox, wx)
                t_x1 = safe_div(aabb_max[0] - ox, wx)
                t_y0 = safe_div(aabb_min[1] - oy, wy)
                t_y1 = safe_div(aabb_max[1] - oy, wy)
                t_z0 = safe_div(aabb_min[2] - oz, wz)
                t_z1 = safe_div(aabb_max[2] - oz, wz)
                
                # Ensure t0 < t1
                if t_x0 > t_x1: t_x0, t_x1 = t_x1, t_x0
                if t_y0 > t_y1: t_y0, t_y1 = t_y1, t_y0
                if t_z0 > t_z1: t_z0, t_z1 = t_z1, t_z0
                
                t_min = max(t_x0, t_y0, t_z0)
                t_max = min(t_x1, t_y1, t_z1)
                
                row_tmin.append(t_min)
                row_tmax.append(t_max)
            else:
                row_tmin.append(0.0)
                row_tmax.append(0.0)
                
        rays_o.append(row_o)
        rays_d.append(row_d)
        t_min_list.append(row_tmin)
        t_max_list.append(row_tmax)
        
    return rays_o, rays_d, t_min_list, t_max_list
```

**Parameters:**
*   $f_x, f_y$: Focal lengths in pixels [S10, S18, unofficial].
*   $c_x, c_y$: Principal point coordinates in pixels [S10, S18, unofficial].
*   $H, W$: Image height and width in pixels [S10, S16, unofficial].
*   $T_{c2w}$: 4x4 camera-to-world matrix [S10, S16, unofficial].
*   `use_pixel_centers`: Boolean, default True [S20, unofficial].

**Edge Cases and Pitfalls:**
*   **Division by Zero:** If $f_x$ or $f_y$ is zero, or if ray direction components are zero during AABB intersection, division by zero occurs [S13, unofficial]. IEEE 754 infinities may result, requiring explicit checks or clamping [S13, unofficial].
*   **Coordinate System Conventions:** OpenGL cameras look down -Z, OpenCV down +Z [S10, S9, unofficial]. Image Y-axis is typically down, while camera V-axis is up [S26, unofficial]. Signs in direction calculation must match these conventions [S10, S25, S26, unofficial].
*   **Pixel Centering:** Omitting +0.5 offset can cause slight misalignment, but may be acceptable if calibration is inaccurate [S8, unofficial].
*   **AABB Intersection:** If $t_{min} > t_{max}$, the ray does not intersect the AABB [S13, unofficial]. This case must be handled to avoid invalid marching ranges [S13, unofficial].

## Subtopics

### [Pinhole Camera Ray Generation](5058-pinhole-camera-ray-generation.md)
Pinhole Camera Ray Generation computes the origin and direction vectors for rays corresponding to each pixel in an image plane, assuming an ideal pinhole camera model with no lens distortion or depth of field. It differs from its parent, Camera Matrix Ray Generation, by explicitly constructing the view frustum geometry (basis vectors and view plane bounds) from high-level camera parameters (eye, look-at, up, FOV) rather than relying on a pre-computed 4x4 projection/view matrix. It serves as the foundational ray setup for basic ray tracing and volume rendering pipelines where explicit control over the view plane sampling is required.

### Camera Intrinsics Simplification
Assumes a simplified intrinsic matrix $\mathbf{K}$ with zero skew and unit aspect ratio, where $f_x = f_y = f_{\text{camera}}$ and the principal point is centered at $(W/2, H/2)$ [S26, unofficial]. This reduces the number of parameters to a single focal length and image dimensions, streamlining ray generation when precise calibration is unnecessary [S26, unofficial].

### Camera Intrinsic Matrix Construction
Builds a 3x3 camera intrinsic matrix $K$ from focal length and image dimensions [S10, unofficial]. The matrix is constructed as a 3x3 array with $K[0,0] = f$, $K[1,1] = f$, $K[0,2] = 0.5 \times W$, $K[1,2] = 0.5 \times H$, $K[2,2] = 1$, and all other elements zero [S10, unofficial]. This standardizes input for ray generation pipelines that expect a full intrinsic matrix [S10, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(H \times W)$ for generating rays for all pixels, as each pixel's ray is computed independently [S10, S16, unofficial].
*   **Memory Complexity:** $O(H \times W)$ to store ray origins and directions [S10, S16, unofficial].
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Performance scales linearly with pixel count; batched tensor operations on GPUs reduce overhead compared to scalar loops [S10, S16, unofficial].
*   **Strengths:** Accurate perspective projection; supports arbitrary camera poses and intrinsics; efficient batch computation [S10, S16, unofficial].
*   **Limitations:** Requires accurate calibration data; sensitive to coordinate system mismatches; division-by-zero risks if intrinsics or directions are degenerate [S13, S26, unofficial].
*   **When to Use:** Standard perspective rendering, NeRF, volume rendering with known camera poses [S10, S16, unofficial].
*   **When Not to Use:** Orthographic scenes, object-space ray tracing, or when only FOV and aspect ratio are available [S10, S16, unofficial].

## Background
Originating from standard computer graphics and photogrammetry, the method maps pixel coordinates to world rays using camera matrices [S10, S24, unofficial]. It is fundamental to NeRF (Neural Radiance Fields) implementations, where accurate ray generation is critical for training and rendering [S10, S20, unofficial]. The approach is widely used in volume rendering, ray tracing, and 3D reconstruction pipelines [S1, S5, S16, unofficial].
