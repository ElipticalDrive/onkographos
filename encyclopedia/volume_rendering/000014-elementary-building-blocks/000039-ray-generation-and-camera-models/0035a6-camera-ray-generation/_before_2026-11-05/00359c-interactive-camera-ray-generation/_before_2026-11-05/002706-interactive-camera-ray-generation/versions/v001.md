# Interactive Camera Ray Generation

Also called: Camera Control and Ray Generation, Camera and Light Animation, sunVec

## Overview
Generates camera position, forward vector, and sun direction based on time and touch input for a moving camera system [S1, unofficial]. It differs from static or matrix-based setups by computing the view ray basis and light vectors procedurally in the shader using trigonometric functions and normalized touch coordinates, enabling interactive control without CPU-side matrix updates [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** `currentTime` (float), `start` (float, initialization time), `resolution` (vec2), `touch` (vec2, normalized screen coordinates), `dt` (float, delta time, used in variants).
*   **Outputs:** `cameraPosition` (vec3), `cameraForward` (vec3), `sunDirection` (vec3).

**Data Structures:**
*   `vec2 touch`: Normalized touch coordinates in range $[0, 1]$.
*   `vec2 resolution`: Screen width and height.

**Parameters:**
*   `CAMERA_HEIGHT`: Constant Y coordinate for the camera rail [S1, unofficial].
*   `CAMERA_SENSIVITY`: Base sensitivity for touch input [S1, unofficial].
*   `CAMERA_FOV`: Field of view in degrees [S1, unofficial].
*   `SUN_PATH_ROTATION`: Azimuth offset for sun direction in degrees [S1, unofficial].
*   `speed`: 3.0 [S1, unofficial].
*   `startZ`: 48.0 [S1, unofficial].
*   `maxYaw`: 1.2 [S1, unofficial].
*   `maxPitch`: 0.8 [S1, unofficial].
*   `deadzone`: 0.02 [S1, unofficial].
*   `power`: 1.15 [S1, unofficial].

**Steps:**

1.  **Calculate Elapsed Time:**
    Compute elapsed time normalized by a factor.
    $$ t_{elapsed} = \frac{currentTime - start}{1024.0} $$
    [S2, unofficial]

2.  **Process Touch Input:**
    Normalize touch to $[0, 1]$, center to $[-1, 1]$, apply aspect ratio correction, flip Y, apply deadzone, apply non-linear power, and scale by sensitivity [S1, unofficial].
    ```python
    touch_uv = touch / max(resolution, vec2(1.0))
    touch_n = (touch_uv - vec2(0.5)) * 2.0
    aspect = resolution.x / max(1.0, resolution.y)
    touch_n.x *= aspect
    touch_n.y = -touch_n.y
    # Deadzone and power application implied by source logic
    # touch_n = apply_deadzone_and_power(touch_n, deadzone, power)
    # touch_n *= CAMERA_SENSIVITY
    ```
    [S1, unofficial]

3.  **Compute Camera Position:**
    The camera moves along a Z-rail with sinusoidal sway [S1, unofficial].
    ```python
    t = elapsedTime # or t from input
    speed = 3.0
    start_z = 48.0
    sway_amp = 1.2
    sway = sin(t * 0.8) * 0.5 + 0.2 * sin(t * 0.7)
    camera_position = vec3(sway * sway_amp, float(CAMERA_HEIGHT), start_z + t * speed)
    ```
    [S1, unofficial]

4.  **Compute Camera Orientation (Yaw/Pitch):**
    Map processed touch to yaw and pitch angles, adding small procedural oscillations [S1, unofficial].
    ```python
    max_yaw = 1.2
    max_pitch = 0.8
    yaw = touch_n.x * max_yaw + sin(t * 0.9) * 0.08 + sin(t * 0.28) * 0.12
    pitch = -0.45 + touch_n.y * max_pitch + sin(t * 1.1) * 0.05
    ```
    [S1, unofficial]

5.  **Compute Forward Vector:**
    Construct the forward vector from yaw and pitch, then normalize and negate [S1, unofficial].
    ```python
    cx = cos(pitch)
    fwd_x = sin(yaw) * cx
    fwd_y = sin(pitch)
    fwd_z = -cos(yaw) * cx
    camera_forward = normalize(vec3(fwd_x, fwd_y, fwd_z))
    camera_forward = -camera_forward # Negate as per source
    ```
    [S1, unofficial]

6.  **Compute Sun Direction:**
    The sun direction is driven by time $t$, with an azimuth offset [S1, unofficial].
    ```python
    sun_direction = normalize(vec3(radians(SUN_PATH_ROTATION), sin(t), cos(t)))
    ```
    [S1, unofficial]

7.  **Generate Ray Direction (for rendering):**
    Convert fragment coordinates to NDC, correct for aspect ratio, compute ray direction in camera space, and transform to world space [S1, unofficial].
    ```python
    ndc = (gl_FragCoord / resolution) * 2.0 - 1.0
    ndc.x *= aspect # Correct NDC.x by aspect ratio
    fov_rad = CAMERA_FOV * PI / 180.0
    px = ndc.x * tan(fov_rad / 2.0)
    py = ndc.y * tan(fov_rad / 2.0)
    
    # Assuming camera_right and camera_up are derived from camera_forward
    # and world up vector (0,1,0)
    ray_dir = normalize(camera_forward + camera_right * px + camera_up * py)
    ```
    [S1, unofficial]

**Edge Cases and Pitfalls:**
*   Division by zero in aspect ratio calculation if resolution Y is 0. Use `max(1.0, resolution.y)` [S1, unofficial].
*   Touch input normalization must handle resolution changes dynamically [S1, unofficial].
*   Deadzone prevents jitter when touch is near center [S1, unofficial].

## Subtopics

### PathCamera
A camera that glides forward along a procedural road centerline, yawing to follow bends and banking gently, producing an orthonormal ray basis for the shader [S3, unofficial]. It differs from the interactive touch-based camera by using a fixed procedural path defined by a road function `roadX(z)` [S3, unofficial]. Choose this for automated fly-throughs or driving simulations [S3, unofficial].
*   **Position:** $z += speed \cdot dt$; $position = [roadX(z), height, z]$ [S3, unofficial].
*   **Target:** $target = [roadX(z + lookAhead), lookHeight, z + lookAhead]$ [S3, unofficial].
*   **Basis:** $forward = normalize(target - position)$; $right = normalize(cross(forward, WORLD\_UP))$; $up = normalize(cross(right, forward))$ [S3, unofficial].
*   **Parameters:** Eye height: 3.5 world units; Look-ahead distance: 15 world units; Look height: 1.5 world units; World up vector: $[0, 1, 0]$ [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per frame per pixel for ray generation.
*   **Memory Complexity:** $O(1)$, no additional buffers required.
*   **Performance:** Very fast, suitable for real-time interactive applications [S1, unofficial].
*   **Strengths:** No CPU-GPU synchronization for camera updates; fully procedural and deterministic based on time [S1, unofficial].
*   **Limitations:** Limited to predefined motion patterns; complex camera paths require complex trigonometric functions [S1, unofficial].
*   **When to use:** Interactive demos, simple fly-throughs, or when CPU-side camera updates are undesirable [S1, unofficial].
*   **When not to use:** Complex cinematic camera paths requiring keyframe interpolation or external animation data [S1, unofficial].

## Background
Originated in GLSL voxel-world shaders for real-time rendering, specifically in the Voxel-World-Shader project [S1, unofficial]. It is used in interactive volume rendering demos where camera control is handled entirely on the GPU [S1, S2, unofficial]. The method is also referenced in neon-raymarcher projects for procedural camera movement [S3, unofficial].
