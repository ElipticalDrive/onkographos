# First-Person Camera Control

Also called: Camera Control, Camera Controller, Camera State & GPU Data Packing, Input Handler, Mouse and Keyboard Input Controller

## Overview
First-Person Camera Control manages the position, orientation (yaw and pitch), and projection parameters of a virtual camera, translating discrete user input (mouse movement, keyboard presses) into continuous 3D transformations [S2, S3, unofficial]. It differs from orbital or arcball models by decoupling rotation from the camera's position, allowing the viewer to look around freely while moving independently, which is essential for navigation in volumetric scenes [S3, unofficial]. It packs these state variables into a GPU-friendly structure to minimize bandwidth overhead during rendering passes [S1, unofficial].

## How it works
The method consists of three phases: input handling, state update, and GPU data packing.

### Inputs and Outputs
**Inputs:**
- Mouse movement deltas ($\Delta x, \Delta y$) and active button state [S2, unofficial].
- Keyboard key states (WASD or arrow keys for movement) [S3, unofficial].
- Time delta ($\Delta t$) for frame-rate independent movement [S3, unofficial].
- Projection parameters: vertical field of view ($\text{vfov}$), aspect ratio, near/far planes [S3, unofficial].

**Outputs:**
- A packed camera state structure sent to the GPU for ray generation [S1, unofficial].

### Data Structures
The GPU-friendly structure `CameraGpuData` contains the following fields [S1, unofficial]:
- `position`: `float[4]` (x, y, z, unused/padding) [S1, unofficial].
- `rot`: `float[3][4]` (3 rows, 4 columns; represents the rotation basis) [S1, unofficial].
- `sin_half_vfov`: `float` [S1, unofficial].
- `frame_count`: `uint` [S1, unofficial].
- `width`: `float` [S1, unofficial].
- `height`: `float` [S1, unofficial].
- `prev_position`: `float[4]` (used for temporal accumulation or motion vectors) [S1, unofficial].

The internal CPU-side state (based on [S3, unofficial]) includes:
- `_position`: `vec3` [S3, unofficial].
- `_yaw`: `float` (horizontal rotation, default 0.0) [S3, unofficial].
- `_pitch`: `float` (vertical rotation, default 0.0) [S3, unofficial].
- `_front`: `vec3` (normalized forward vector) [S3, unofficial].
- `_right`: `vec3` (normalized right vector) [S3, unofficial].
- `_up`: `vec3` (normalized up vector) [S3, unofficial].
- `_speed`: `float` (movement speed) [S3, unofficial].
- `_sensitivity`: `float` (mouse sensitivity) [S3, unofficial].

### Parameters
Typical default values [S1, S2, S3, unofficial]:
- `vfov`: $\pi \times 0.5$ radians (90 degrees) [S1, unofficial].
- `moving_speed`: $1.0$ units/second [S1, unofficial].
- `mouse_speed` / `_sensitivity`: $0.01$ radians/pixel [S1, S3, unofficial].
- `ROTATION_FACTOR`: $0.0025$ [S2, unofficial].
- `PAN_FACTOR`: $1.0$ [S2, unofficial].
- `LIGHT_FACTOR`: $0.0025$ [S2, unofficial].
- `ZOOM_FACTOR`: $0.0025$ [S2, unofficial].

### Steps

1. **Initialize State**: Set `_position` to the starting eye coordinates. Set `_yaw` to $0.0$ and `_pitch` to $0.0$. Set `_front` to $(0, 0, -1)$ or similar default forward direction [S3, unofficial].

2. **Process Input**:
   - **Mouse**: Read $\Delta x$ and $\Delta y$.
     - If left button is active and Control key is held: Update lighting parameters using $\Delta x \times \text{LIGHT\_FACTOR}$ and $\Delta y \times \text{LIGHT\_FACTOR}$ [S2, unofficial].
     - If left button is active and Control key is not held: Update rotation angles:
       $$ \text{yaw} \leftarrow \text{yaw} + \Delta x \times \text{ROTATION\_FACTOR} $$
       $$ \text{pitch} \leftarrow \text{pitch} + \Delta y \times \text{ROTATION\_FACTOR} $$
       Clamp `_pitch` to $[-\pi/2, \pi/2]$ to prevent gimbal lock or inversion [S3, G, unofficial].
     - If right button is active: Update camera pan (position offset) using $\Delta x \times \text{PAN\_FACTOR}$ and $\Delta y \times \text{PAN\_FACTOR}$ [S2, unofficial].
   - **Keyboard**: Check active keys (W, A, S, D, Q, E) to determine movement direction [S3, unofficial].

3. **Update Camera Vectors**: Recalculate the basis vectors based on current `_yaw` and `_pitch` [S3, unofficial]:
   $$ \text{front}_x = \cos(\text{pitch}) \sin(\text{yaw}) $$
   $$ \text{front}_y = -\sin(\text{pitch}) $$
   $$ \text{front}_z = \cos(\text{pitch}) \cos(\text{yaw}) $$
   $$ \text{front} = \text{normalize}(\text{front}) $$
   $$ \text{right} = \text{normalize}(\text{cross}(\text{front}, \text{world\_up})) $$
   $$ \text{up} = \text{cross}(\text{right}, \text{front}) $$
   Where `world_up` is typically $(0, 1, 0)$ [S3, unofficial].

4. **Update Position**: If movement keys are active, modify `_position` along the basis vectors [S3, unofficial]:
   $$ \text{velocity} = \text{speed} \times \Delta t $$
   $$ \text{position} \leftarrow \text{position} + \text{velocity} \times (\text{front} \times \text{forward\_key} + \text{right} \times \text{right\_key} + \text{up} \times \text{up\_key}) $$
   Note: "Forward" key moves along `-front` if front points into the scene, or `front` depending on coordinate system convention. The source [S3, unofficial] implies `moveForward` modifies position by `_speed * deltaTime` along the respective camera axes.

5. **Pack GPU Data**: Construct `CameraGpuData` [S1, unofficial]:
   - `position`: Set to `_position`.
   - `rot`: Construct the $3 \times 3$ rotation matrix from `_right`, `_up`, and `_front` (or `_front`, `_right`, `_up` depending on row/column major order). The source [S1, unofficial] specifies `vec_z` (front), `vec_x` (right), `vec_y` (up) construction:
     $$ \text{vec\_z} = (\cos(\text{pitch})\sin(\text{yaw}), -\sin(\text{pitch}), \cos(\text{pitch})\cos(\text{yaw})) $$
     $$ \text{vec\_x} = \text{normalize}(\text{cross}(\text{vec\_y}, \text{vec\_z})) $$
     $$ \text{vec\_y} = \text{cross}(\text{vec\_z}, \text{vec\_x}) $$
     Pack these into the `rot` array.
   - `sin_half_vfov`: $\sin(\text{vfov} / 2)$ [S1, unofficial].
   - `width`, `height`: Current viewport dimensions [S1, unofficial].
   - `prev_position`: Set to the previous frame's position for temporal coherence [S1, unofficial].

### Pseudocode

```python
import math

class FirstPersonCamera:
    def __init__(self, position=(0.0, 0.0, 0.0), vfov=math.pi * 0.5):
        self.position = list(position)
        self.yaw = 0.0
        self.pitch = 0.0
        self.speed = 1.0
        self.sensitivity = 0.01
        self.vfov = vfov
        self.world_up = [0.0, 1.0, 0.0]
        self._update_vectors()

    def _update_vectors(self):
        # Calculate front vector from yaw and pitch
        front_x = math.cos(math.radians(self.pitch)) * math.sin(math.radians(self.yaw))
        front_y = -math.sin(math.radians(self.pitch))
        front_z = math.cos(math.radians(self.pitch)) * math.cos(math.radians(self.yaw))
        self.front = _normalize([front_x, front_y, front_z])
        
        # Calculate right and up vectors
        self.right = _normalize(_cross(self.front, self.world_up))
        self.up = _cross(self.right, self.front)

    def process_mouse(self, dx, dy, button=0, keys=None):
        if keys is None:
            keys = {}
        
        if button == 0: # Left click
            if keys.get('Control'):
                # Update lighting or other params
                pass
            else:
                self.yaw += dx * self.sensitivity
                self.pitch += dy * self.sensitivity
                # Clamp pitch to avoid flipping
                if self.pitch > 89.0:
                    self.pitch = 89.0
                if self.pitch < -89.0:
                    self.pitch = -89.0
                self._update_vectors()
        elif button == 2: # Right click
            # Pan camera
            self.position[0] += dx * 1.0 # PAN_FACTOR
            self.position[1] += dy * 1.0 # PAN_FACTOR

    def process_keyboard(self, dt, keys):
        velocity = self.speed * dt
        direction = [0.0, 0.0, 0.0]
        
        if keys.get('W'):
            direction[0] -= self.front[0]
            direction[1] -= self.front[1]
            direction[2] -= self.front[2]
        if keys.get('S'):
            direction[0] += self.front[0]
            direction[1] += self.front[1]
            direction[2] += self.front[2]
        if keys.get('A'):
            direction[0] -= self.right[0]
            direction[1] -= self.right[1]
            direction[2] -= self.right[2]
        if keys.get('D'):
            direction[0] += self.right[0]
            direction[1] += self.right[1]
            direction[2] += self.right[2]
        if keys.get('Q'): # Down
            direction[1] -= 1.0
        if keys.get('E'): # Up
            direction[1] += 1.0
            
        if any(d != 0 for d in direction):
            direction = _normalize(direction)
            self.position[0] += direction[0] * velocity
            self.position[1] += direction[1] * velocity
            self.position[2] += direction[2] * velocity

    def get_gpu_data(self, frame_count, width, height, prev_position):
        # Construct rotation matrix rows
        # Source [S1, unofficial] uses vec_z (front), vec_x (right), vec_y (up)
        # Note: Source [S1, unofficial] pseudocode implies specific vector construction
        vec_z = [
            math.cos(math.radians(self.pitch)) * math.sin(math.radians(self.yaw)),
            -math.sin(math.radians(self.pitch)),
            math.cos(math.radians(self.pitch)) * math.cos(math.radians(self.yaw))
        ]
        # vec_y is not explicitly calculated in S1 snippet but implied by cross products
        # Using standard basis from _update_vectors for consistency
        vec_x = self.right
        vec_y = self.up
        
        rot = [vec_x, vec_y, vec_z]
        
        return {
            "position": self.position + [0.0],
            "rot": rot,
            "sin_half_vfov": math.sin(self.vfov / 2.0),
            "frame_count": frame_count,
            "width": float(width),
            "height": float(height),
            "prev_position": prev_position + [0.0]
        }

def _normalize(v):
    length = math.sqrt(sum(x*x for x in v))
    if length == 0:
        return [0.0, 0.0, 0.0]
    return [x / length for x in v]

def _cross(a, b):
    return [
        a[1]*b[2] - a[2]*b[1],
        a[2]*b[0] - a[0]*b[2],
        a[0]*b[1] - a[1]*b[0]
    ]
```

### Edge Cases and Pitfalls
- **Gimbal Lock**: Pitch must be clamped to $(-\pi/2, \pi/2)$ to prevent the forward vector from aligning with the up vector, which causes loss of a degree of freedom [S3, G, unofficial].
- **Precision**: Using `float` for position and rotation is standard, but `prev_position` should be updated carefully to avoid jitter in temporal accumulation [S1, unofficial].
- **Boundary Conditions**: If the camera moves outside the volume bounds, ray generation may produce invalid intersections. Clamping or bounding box checks should be handled in the ray marching step, not necessarily here [G].

## Operating characteristics
- **Time Complexity**: $O(1)$ per frame for input processing and state update, as it involves a fixed number of vector operations and trigonometric functions [S1, S3, unofficial].
- **Memory Complexity**: $O(1)$ for CPU-side state and $O(1)$ for GPU-side data (fixed-size struct) [S1, unofficial].
- **Strengths**: Intuitive control for navigation; low computational overhead; decouples viewing direction from position [S3, unofficial].
- **Limitations**: Not suitable for orbital inspection or automated path-based visualization without additional logic [S3, unofficial].
- **When to use**: Interactive exploration of volumetric datasets where the user needs to "walk through" or look around a scene [S3, unofficial].
- **When not to use**: When a fixed viewpoint, orbital rotation, or scripted animation is required [S3, unofficial].

## Background
First-person camera control is a standard technique in 3D computer graphics, originating from first-person shooter games and virtual reality applications [S3, unofficial]. In the context of volume rendering, it allows users to navigate large volumetric datasets (e.g., medical images, scientific simulations) with intuitive mouse and keyboard inputs [S2, S3, unofficial]. The specific implementation details, such as the GPU data packing structure, are derived from modern real-time rendering engines using APIs like WebGPU and Vulkan [S1, unofficial].
