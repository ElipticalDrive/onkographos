# Basic GPU Ray Generation via Fragment Shader

Also called: Fragment shader ray tracing, Fragment Shader Ray Generation, Ray Tracing Fragment Shader

## Overview
This method generates camera rays for ray tracing by rendering a single quad (two triangles) to the screen, allowing the fragment shader to compute the ray origin and direction for each pixel using interpolated vertex coordinates [S4, S5, unofficial]. It differs from [Camera Matrix Ray Generation](2172-camera-matrix-ray-generation.md) by avoiding explicit matrix multiplications in favor of geometric basis vectors (side, up, forward) derived from camera parameters, and from [Orthographic (Parallel) Camera Ray Generation](1319-orthographic-parallel-camera-ray-generation.md) by supporting perspective projection through a viewing plane distance [S4, unofficial]. It builds on [Ray Origin and Direction Setup](1793-ray-origin-and-direction-setup.md) by providing a concrete GPU implementation pattern.

## How it works
**Inputs and Outputs:**
*   **Inputs:** Window resolution (`iResolution`), camera position (`iRayOrigin`), camera facing direction (`iRayDir`), camera up direction (`iRayUp`), distance to viewing plane (`iPlaneDist`), and interpolated texture coordinates (`texCoord`) ranging from (0,0) to (1,1) across the quad [S4, S5, unofficial].
*   **Outputs:** A ray (origin and direction) for each pixel, which is then used for intersection testing (e.g., against spheres or BVHs) and shading [S4, unofficial].

**Data Structures:**
*   **Uniforms:**
    *   `iResolution`: `vec2` (width, height) [S4, S5, unofficial].
    *   `iRayOrigin`: `vec3` (camera position) [S4, S5, unofficial].
    *   `iRayDir`: `vec3` (camera forward vector) [S4, unofficial].
    *   `iRayUp`: `vec3` (camera up vector) [S4, unofficial].
    *   `iPlaneDist`: `float` (distance from camera to the projection plane) [S4, S5, unofficial].
*   **Varying/Input:**
    *   `texCoord`: `vec2` interpolated from vertex attributes (0,0) to (1,1) [S4, S5, unofficial].

**Steps:**
1.  **Setup Geometry:** Render a single quad (two triangles covering the screen) using a minimal vertex shader that performs no transformations. Bind vertex attributes such that `texCoord` interpolates linearly from (0,0) at the bottom-left to (1,1) at the top-right (or equivalent screen mapping) [S4, S5, unofficial].
2.  **Compute Normalized Coordinates:** In the fragment shader, convert the interpolated `texCoord` (range [0,1]) to a normalized device coordinate `p` (range [-1,1]) [S4, S5, unofficial]:
    $$ p = 2.0 \cdot \text{texCoord} - 1.0 $$
3.  **Apply Aspect Ratio:** Scale the x-component of `p` by the aspect ratio to prevent distortion [S4, S5, unofficial]:
    $$ p.x = p.x \cdot \frac{\text{iResolution}.x}{\text{iResolution}.y} $$
4.  **Compute Camera Basis Vectors:** Calculate the camera's right vector (`camSide`) using the cross product of the forward (`iRayDir`) and up (`iRayUp`) vectors [S4, S5, unofficial]:
    $$ \text{camSide} = \text{normalize}(\text{cross}(\text{iRayDir}, \text{iRayUp})) $$
    *Note: Sources assume `iRayDir` and `iRayUp` are orthogonal or nearly so. If `iRayUp` is not orthogonal to `iRayDir`, `camSide` may need to be recomputed as `cross(iRayUp, iRayDir)` or `iRayUp` should be orthogonalized first [G].*
5.  **Calculate Ray Direction:** Compute the ray direction by combining the basis vectors scaled by `p` and the viewing plane distance [S4, S5, unofficial]:
    $$ \text{raydir} = \text{normalize}(p.x \cdot \text{camSide} + p.y \cdot \text{iRayUp} + \text{iPlaneDist} \cdot \text{iRayDir}) $$
    *Note: Source [S4, unofficial] uses `iRayUp` in the final sum, while the code snippet in [S5, unofficial] uses `camUp`. Assuming `camUp` is the input `iRayUp`.*
6.  **Set Ray Origin:** The ray origin is the camera position [S4, S5, unofficial]:
    $$ \text{rayorig} = \text{iRayOrigin} $$
7.  **Trace and Shade:** Use the generated ray to perform intersection tests (e.g., sphere tracing, BVH traversal) and compute the final color [S4, unofficial].

**Pseudocode:**
```python
# Fragment Shader Entry Point
# Inputs:
#   iResolution: vec2 (window width, height)
#   iRayOrigin: vec3 (camera position)
#   iRayDir: vec3 (camera forward direction)
#   iRayUp: vec3 (camera up direction)
#   iPlaneDist: float (distance to viewing plane)
#   texCoord: vec2 (interpolated from 0,0 to 1,1)

# Output:
#   fragColor: vec4

vec3 compute_ray_direction(vec2 texCoord, vec2 resolution, vec3 ray_dir, vec3 ray_up, float plane_dist) {
    # Step 2: Normalize coordinates to [-1, 1]
    vec2 p = 2.0 * texCoord - 1.0;
    
    # Step 3: Apply aspect ratio correction
    p.x *= resolution.x / resolution.y;
    
    # Step 4: Compute camera side vector (right vector)
    # Note: Assumes ray_dir and ray_up are roughly orthogonal.
    # If ray_up is not orthogonal to ray_dir, cross product order matters for handedness.
    vec3 cam_side = normalize(cross(ray_dir, ray_up));
    
    # Step 5: Compute ray direction
    # p.x * side + p.y * up + plane_dist * forward
    vec3 raydir = normalize(p.x * cam_side + p.y * ray_up + plane_dist * ray_dir);
    
    return raydir;
}

void main() {
    # Step 1: Ray generation (implicit via fragment shader execution per pixel)
    vec3 rayorig = iRayOrigin;
    vec3 raydir = compute_ray_direction(texCoord, iResolution, iRayDir, iRayUp, iPlaneDist);
    
    # Step 7: Trace ray against scene (example: sphere intersection)
    # This part depends on the specific scene representation (BVH, SDF, etc.)
    # See [S4, unofficial] for sphere intersection example.
    Hit hit = trace_scene(rayorig, raydir);
    
    # Compute color based on hit result
    vec3 color = vec3(0.0);
    if (hit.hit) {
        color = shade(hit.point, hit.normal, raydir);
    } else {
        color = background_color;
    }
    
    fragColor = vec4(color, 1.0);
}

# Example Sphere Intersection (from [S4, unofficial])
struct Hit {
    vec3 point;
    vec3 normal;
    float t;
    bool hit;
};

Hit trace_sphere(vec3 rayorig, vec3 raydir, vec3 pos, float radius) {
    float OdotD = dot(rayorig - pos, raydir);
    float OdotO = dot(rayorig - pos, rayorig - pos);
    float base = OdotD * OdotD - OdotO + radius * radius;
    
    if (base >= 0.0) {
        float root = sqrt(base);
        float t1 = -OdotD + root;
        float t2 = -OdotD - root;
        
        # Select the closest positive t
        float t = -1.0;
        if (t1 >= 0.0 && t2 >= 0.0) {
            t = min(t1, t2);
        } else if (t1 >= 0.0) {
            t = t1;
        } else if (t2 >= 0.0) {
            t = t2;
        }
        
        if (t >= 0.0) {
            vec3 pt = rayorig + raydir * t;
            vec3 normal = normalize(pt - pos);
            return Hit(pt, normal, t, true);
        }
    }
    return Hit(vec3(0), vec3(0), -1.0, false);
}
```

**Parameters:**
*   `iPlaneDist`: Controls the field of view. A smaller value results in a wider FOV. Typical values depend on the scene scale and desired FOV [S4, S5, unofficial].
*   `iResolution`: Window dimensions in pixels [S4, S5, unofficial].

**Edge Cases and Pitfalls:**
*   **Aspect Ratio Distortion:** Failing to scale the x-coordinate by the aspect ratio (`width/height`) will distort the field of view, making circles appear as ellipses [S5, unofficial].
*   **Camera Basis Orthogonality:** The `camSide` vector is computed via `cross(iRayDir, iRayUp)`. If `iRayUp` is not orthogonal to `iRayDir`, the resulting basis is not orthonormal, leading to skewed rays. It is recommended to orthogonalize `iRayUp` against `iRayDir` before use or ensure the camera setup maintains orthogonality [G].
*   **Winding Order:** The quad's vertex winding order determines the interpolation direction of `texCoord`. Ensure the quad covers the screen correctly (e.g., vertices at (0,0), (1,0), (1,1), (0,1)) and that the interpolation maps to screen space correctly (bottom-left to top-right) [S4, S5, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per pixel for ray generation. The total time is proportional to the number of pixels ($W \times H$) plus the cost of the ray tracing algorithm (intersection, shading) [S4, unofficial].
*   **Memory Complexity:** $O(1)$ for uniforms and varyings. The geometry is minimal (a single quad) [S4, S5, unofficial].
*   **Performance:** Very efficient for ray generation due to GPU interpolation. The bottleneck is typically the ray tracing and shading steps [S4, unofficial].
*   **Strengths:** Simple to implement, leverages GPU interpolation, minimal geometry overhead [S4, S5, unofficial].
*   **Limitations:** Limited to perspective or simple orthographic projections. Not suitable for complex camera models without additional computation [S4, unofficial].
*   **When to Use:** Simple ray tracing demos, educational purposes, or when a quick perspective camera setup is needed [S4, S5, unofficial].
*   **When Not to Use:** Complex camera models, non-perspective projections, or when high performance is critical and the ray tracing algorithm is the bottleneck [S4, unofficial].

## Background
This technique is a fundamental approach to GPU ray tracing, popularized by educational resources and demos [S4, S5, unofficial]. It allows developers to implement ray tracing in the fragment shader without complex vertex transformations, making it accessible for learning and simple applications [S4, unofficial]. The method is often introduced in the context of "Ray Marching" and "Signed Distance Fields" [S4, S5, unofficial].
