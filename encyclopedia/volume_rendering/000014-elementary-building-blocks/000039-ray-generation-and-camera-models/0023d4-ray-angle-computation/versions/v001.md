# Ray Angle Computation

Also called: Angular Difference Computation, Ray-to-Ray Angle Calculation

## Overview
Ray Angle Computation calculates the angular relationship between rays originating from different camera viewpoints and intersecting a common 3D point. It is primarily used in multi-view stereo and neural radiance field (NeRF) training to provide geometric context by comparing the viewing direction of a query camera against those of reference (training) cameras for the same spatial location [S1, S2, unofficial]. Unlike standard ray generation which defines the ray's path, this method computes a feature derived from the relative orientation of multiple rays, serving as an input to neural networks that model view-dependent appearance or geometry [S1, S2, unofficial].

## How it works
**Inputs:**
- `xyz`: A tensor of 3D points with shape $(N, 3)$, where $N$ is the number of points.
- `query_camera`: A tensor representing the query camera's pose, typically a $4 \times 4$ transformation matrix (or flattened 16 values) with shape $(1, 4, 4)$ or $(1, 16)$.
- `train_cameras`: A tensor of training camera poses with shape $(M, 4, 4)$ or $(M, 16)$, where $M$ is the number of training views.

**Outputs:**
- `angle_features`: A tensor representing the angular difference or dot product between the query ray and training rays, with shape $(N, M)$ or similar, depending on the specific variant.

**Data Structures:**
- Poses are stored as $4 \times 4$ matrices. The translation component is located at indices $[0:3, 3]$ (or flattened indices $12:16$).
- Directions are 3D vectors.

**Steps:**
1.  **Extract Poses:** Reshape `train_cameras` into a tensor of shape $(M, 4, 4)$ and `query_camera` into $(1, 4, 4)$. Expand `query_camera` to match the batch dimension of training cameras if necessary, resulting in `query_pose` of shape $(M, 4, 4)$ [S1, unofficial].
2.  **Compute Query Ray Direction:** Calculate the vector from the query camera center to the 3D point.
    -   Get camera center: $\mathbf{c}_{query} = \text{query\_pose}[:, :3, 3]$ [S1, unofficial].
    -   Compute direction: $\mathbf{d}_{query} = \mathbf{xyz} - \mathbf{c}_{query}$ [S1, unofficial]. *Note: Source [S1, unofficial] uses `query_pose[:, :3, 3] - xyz`, which implies $\mathbf{d} = \mathbf{c} - \mathbf{p}$. This vector points from the point to the camera. For ray direction (camera to point), it should be $\mathbf{p} - \mathbf{c}$. However, since the angle between $\mathbf{v}$ and $-\mathbf{v}$ is $\pi$, and dot products are sensitive to sign, we must follow the source's convention if it computes "difference" via vector subtraction norms. Let's look closer at S1: `ray2tar_pose = query_pose[:, :3, 3] - xyz`. This is Vector from Point to Camera. Then `ray2train_pose = train_poses[:, :3, 3] - xyz`. Also Point to Camera. Then `ray_diff = ray2tar - ray2train`. This computes the difference between two "Point-to-Camera" vectors. This is a valid geometric feature.*
    -   Normalize: $\mathbf{v}_{query} = \frac{\mathbf{d}_{query}}{\|\mathbf{d}_{query}\| + \epsilon}$, where $\epsilon = 10^{-6}$ [S1, unofficial].
3.  **Compute Training Ray Direction:** Calculate the vector from each training camera center to the 3D point.
    -   Get camera centers: $\mathbf{c}_{train} = \text{train\_poses}[:, :3, 3]$ [S1, unofficial].
    -   Compute direction: $\mathbf{d}_{train} = \mathbf{c}_{train} - \mathbf{xyz}$ [S1, unofficial].
    -   Normalize: $\mathbf{v}_{train} = \frac{\mathbf{d}_{train}}{\|\mathbf{d}_{train}\| + \epsilon}$ [S1, unofficial].
4.  **Compute Angular Difference (Variant 1):**
    -   Compute difference vector: $\mathbf{diff} = \mathbf{v}_{query} - \mathbf{v}_{train}$ [S1, unofficial].
    -   Compute norm: $n_{diff} = \|\mathbf{diff}\|$ [S1, unofficial].
    -   Compute dot product: $dot = \sum (\mathbf{v}_{query} \cdot \mathbf{v}_{train})$ [S1, unofficial].
    -   The features may be $n_{diff}$ and $dot$ [S1, unofficial].
5.  **Compute Angle Features (Variant 2):**
    -   Compute dot product between the normalized directions: $f = \mathbf{v}_{query} \cdot \mathbf{v}_{train}$ [S2, unofficial].

**Pseudocode:**

```python
import torch
import math

def compute_ray_angles(xyz, query_pose, train_poses, epsilon=1e-6):
    """
    Computes angular features between a query ray and multiple training rays.
    
    Args:
        xyz: Tensor of shape (N, 3) representing 3D points.
        query_pose: Tensor of shape (1, 4, 4) or (4, 4) representing the query camera pose.
        train_poses: Tensor of shape (M, 4, 4) representing training camera poses.
        
    Returns:
        dot_products: Tensor of shape (N, M) with dot products of normalized directions.
        diff_norms: Tensor of shape (N, M) with norms of the difference vectors.
    """
    # Ensure query_pose is (1, 4, 4)
    if query_pose.dim() == 2:
        query_pose = query_pose.unsqueeze(0)
    
    # Extract camera centers (translation components)
    # Poses are 4x4 matrices. Centers are at [:3, 3]
    query_centers = query_pose[:, :3, 3].unsqueeze(1) # Shape: (1, 1, 3)
    train_centers = train_poses[:, :3, 3]             # Shape: (M, 3)
    
    # Expand query_centers to match train_poses batch size for broadcasting
    # We want to compare each of N points against M training cameras
    # xyz: (N, 3)
    # query_centers: (1, 1, 3) -> expand to (N, M, 3)
    # train_centers: (M, 3) -> expand to (N, M, 3)
    
    query_centers_exp = query_centers.expand(xyz.shape[0], train_poses.shape[0], 3)
    train_centers_exp = train_centers.expand(xyz.shape[0], train_poses.shape[0], 3)
    
    # Compute vectors from Point to Camera (following S1 convention)
    # v_query = c_query - p
    vec_query = query_centers_exp - xyz.unsqueeze(1) # Shape: (N, M, 3)
    
    # v_train = c_train - p
    vec_train = train_centers_exp - xyz.unsqueeze(1) # Shape: (N, M, 3)
    
    # Normalize vectors
    norm_query = torch.norm(vec_query, dim=2, keepdim=True) + epsilon
    norm_train = torch.norm(vec_train, dim=2, keepdim=True) + epsilon
    
    v_query = vec_query / norm_query
    v_train = vec_train / norm_train
    
    # Compute dot product: sum(v_query * v_train) over dim 2
    dot_products = torch.sum(v_query * v_train, dim=2) # Shape: (N, M)
    
    # Compute difference vector norm: ||v_query - v_train||
    diff_vec = v_query - v_train
    diff_norms = torch.norm(diff_vec, dim=2) # Shape: (N, M)
    
    return dot_products, diff_norms
```

**Parameters:**
- `epsilon`: A small constant to prevent division by zero during normalization. Typical value: $10^{-6}$ [S1, unofficial].

**Edge Cases:**
- **Zero-length vectors:** If a point coincides with a camera center, the direction vector is zero. The epsilon addition prevents NaNs [S1, unofficial].
- **Degenerate Geometry:** If points are collinear with camera centers, the angle is 0 or $\pi$. The dot product will be $\pm 1$.

## Subtopics

### Angle Feature Generation
Generates features based on the angle between rays and camera positions for multi-view stereo rendering. It computes directions from camera centers to ray points and then calculates the dot product between these directions and ray directions to derive angle features [S2, unofficial]. This variant focuses on the dot product as the primary angular feature [S2, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N \cdot M)$, where $N$ is the number of points and $M$ is the number of training views. The operations are vectorizable and parallelizable across points and views.
- **Memory Complexity:** $O(N \cdot M)$ to store the intermediate direction tensors and final features.
- **Performance:** Highly efficient on GPUs due to tensor operations. The computation is lightweight compared to ray marching or neural network inference.
- **Strengths:** Provides explicit geometric context regarding viewing angles, which helps in disambiguating surface normals and handling view-dependent effects.
- **Limitations:** Requires access to multiple camera poses. Computation scales linearly with the number of training views.

## Background
This method is used in neural rendering pipelines, specifically in variants of NeRF that incorporate multi-view information. It appears in implementations such as VF-NeRF and PointNeRF, where angular relationships between views are used to enhance feature representation [S1, S2, unofficial].
