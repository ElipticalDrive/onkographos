# Ray Angle Computation

Also called: Angular Difference Computation, Ray-to-Ray Angle Calculation

## Overview
Ray Angle Computation determines the geometric relationship between a query ray and reference rays by calculating the angular difference between their directions at a shared 3D point [S1, unofficial]. It solves the problem of encoding multi-view consistency by quantifying how much the viewing direction changes between a target camera and training cameras for a specific spatial location [S1, unofficial]. Unlike sibling methods that generate features via coordinate transformation or uniform sampling, this method explicitly computes the dot product and difference vector between normalized ray directions to capture angular similarity [S1, unofficial].

## How it works
**Inputs:**
- `xyz`: A tensor of shape $(N, 3)$ representing $N$ 3D points in world coordinates [S1, unofficial].
- `train_poses`: A tensor of shape $(M, 4, 4)$ representing the $4 \times 4$ transformation matrices for $M$ training cameras [S1, unofficial].
- `query_pose`: A tensor of shape $(1, 4, 4)$ representing the $4 \times 4$ transformation matrix for the query camera [S1, unofficial].

**Outputs:**
- `ray_diff_dot`: A tensor of shape $(N, M)$ containing the dot product between the query ray direction and each training ray direction at the points [S1, unofficial].
- `ray_diff_norm`: A tensor of shape $(N, M)$ containing the Euclidean norm of the difference vector between the query and training ray directions [S1, unofficial].

**Data Structures:**
- Points are stored as floating-point vectors $(x, y, z)$.
- Poses are stored as $4 \times 4$ homogeneous transformation matrices. The camera center (origin) is extracted from the fourth column (indices `[:, :3, 3]`) [S1, unofficial].

**Steps:**
1.  **Extract Camera Centers:**
    Extract the camera origins from the pose matrices.
    -   $C_{train} = \text{train\_poses}[:, :3, 3]$ with shape $(M, 3)$ [S1, unofficial].
    -   $C_{query} = \text{query\_pose}[:, :3, 3]$ with shape $(1, 3)$ [S1, unofficial].

2.  **Compute Ray Directions:**
    Calculate the vector from the camera center to the point for both query and training cameras.
    -   Vector to query: $\mathbf{v}_{query} = C_{query} - \mathbf{xyz}$ [S1, unofficial].
    -   Vector to train: $\mathbf{v}_{train} = C_{train} - \mathbf{xyz}$ [S1, unofficial].
    *Note: The source code subtracts the point from the camera center, resulting in vectors pointing from the point to the camera. This is the reverse of the standard ray direction (camera to point), but the angular relationship remains consistent for dot product and difference calculations.*

3.  **Normalize Directions:**
    Normalize the vectors to unit length to obtain directions $\mathbf{d}_{query}$ and $\mathbf{d}_{train}$.
    -   $\|\mathbf{v}_{query}\| = \sqrt{\sum \mathbf{v}_{query}^2}$ [S1, unofficial].
    -   $\mathbf{d}_{query} = \mathbf{v}_{query} / (\|\mathbf{v}_{query}\| + \epsilon)$ [S1, unofficial].
    -   $\|\mathbf{v}_{train}\| = \sqrt{\sum \mathbf{v}_{train}^2}$ [S1, unofficial].
    -   $\mathbf{d}_{train} = \mathbf{v}_{train} / (\|\mathbf{v}_{train}\| + \epsilon)$ [S1, unofficial].
    -   $\epsilon = 10^{-6}$ is added to prevent division by zero [S1, unofficial].

4.  **Compute Difference Vector:**
    Calculate the element-wise difference between the normalized directions.
    -   $\mathbf{d}_{diff} = \mathbf{d}_{query} - \mathbf{d}_{train}$ [S1, unofficial].

5.  **Compute Metrics:**
    -   **Difference Norm:** Compute the Euclidean norm of the difference vector.
        -   $\text{ray\_diff\_norm} = \|\mathbf{d}_{diff}\|$ [S1, unofficial].
    -   **Dot Product:** Compute the dot product of the two direction vectors.
        -   $\text{ray\_diff\_dot} = \sum (\mathbf{d}_{query} \cdot \mathbf{d}_{train})$ [S1, unofficial].

**Pseudocode:**
```python
import torch
import torch.nn.functional as F

def compute_ray_angles(xyz, train_poses, query_pose, epsilon=1e-6):
    """
    Computes angular difference metrics between a query ray and training rays.
    
    Args:
        xyz: Tensor of shape (N, 3) containing 3D points.
        train_poses: Tensor of shape (M, 4, 4) containing training camera poses.
        query_pose: Tensor of shape (1, 4, 4) containing the query camera pose.
        epsilon: Small constant for numerical stability.
        
    Returns:
        ray_diff_dot: Tensor of shape (N, M) with dot products.
        ray_diff_norm: Tensor of shape (N, M) with difference norms.
    """
    # 1. Extract camera centers (origins) from the 4th column of the pose matrices
    # Shape: (M, 3) and (1, 3)
    train_centers = train_poses[:, :3, 3]
    query_center = query_pose[:, :3, 3]
    
    # 2. Compute vectors from camera center to point
    # Note: Source code uses (center - point), pointing from point to camera.
    # Shape: (N, 3) and (N, M, 3) after broadcasting
    # Expand query_center to match N points
    query_center_expanded = query_center.expand(xyz.shape[0], -1)
    
    vec_query = query_center_expanded - xyz  # Shape: (N, 3)
    vec_train = train_centers - xyz          # Shape: (N, M, 3) via broadcasting
    
    # 3. Normalize directions
    # Compute norms
    norm_query = torch.norm(vec_query, dim=1, keepdim=True)  # Shape: (N, 1)
    norm_train = torch.norm(vec_train, dim=2, keepdim=True)  # Shape: (N, M, 1)
    
    # Add epsilon and divide
    d_query = vec_query / (norm_query + epsilon)             # Shape: (N, 3)
    d_train = vec_train / (norm_train + epsilon)             # Shape: (N, M, 3)
    
    # 4. Compute difference vector
    # Broadcast d_query to (N, M, 3)
    d_query_expanded = d_query.unsqueeze(1).expand(-1, train_centers.shape[0], -1)
    d_diff = d_query_expanded - d_train                      # Shape: (N, M, 3)
    
    # 5. Compute metrics
    # Difference norm
    ray_diff_norm = torch.norm(d_diff, dim=2)                # Shape: (N, M)
    
    # Dot product
    ray_diff_dot = torch.sum(d_query_expanded * d_train, dim=2) # Shape: (N, M)
    
    return ray_diff_dot, ray_diff_norm
```

**Parameters:**
-   `epsilon`: $10^{-6}$, used to prevent division by zero during normalization [S1, unofficial].

**Edge Cases:**
-   **Zero Vector:** If a point coincides with a camera center, the vector norm is zero. The addition of $\epsilon$ prevents NaN values [S1, unofficial].
-   **Degenerate Input:** If `xyz` or poses are not properly aligned in the same coordinate system, the computed angles will be meaningless.

## Operating characteristics
-   **Time Complexity:** $O(N \cdot M)$, where $N$ is the number of points and $M$ is the number of training views. The operations are vectorizable and parallelizable on GPUs [S1, unofficial].
-   **Memory Complexity:** $O(N \cdot M)$ to store the intermediate difference vectors and final metrics [S1, unofficial].
-   **Strengths:** Provides a direct measure of angular consistency between views. Efficiently computed using batched tensor operations [S1, unofficial].
-   **Limitations:** Sensitive to the precision of the camera poses and point coordinates. Does not account for occlusion or visibility [S1, unofficial].
-   **When to use:** In multi-view stereo or NeRF-based methods where angular consistency between training and query views is a key feature for rendering or reconstruction [S1, unofficial].

## Background
This method originates from the VF-NeRF project, which utilizes angular differences to enhance view synthesis by leveraging multi-view geometric constraints [S1, unofficial]. It is part of a broader trend in neural rendering to explicitly encode geometric relationships between rays and cameras.
