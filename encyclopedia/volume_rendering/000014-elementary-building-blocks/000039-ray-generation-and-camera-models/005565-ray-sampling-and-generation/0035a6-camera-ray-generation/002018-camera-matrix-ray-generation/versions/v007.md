# Camera Matrix Ray Generation

Also called: Ray Generation from Camera Matrix, Ray Generation from Camera Pose, Ray to World Coordinates, Ray Generation from Camera Parameters

## Overview
Camera Matrix Ray Generation computes the 3D world-space origin and direction vectors for viewing rays corresponding to each pixel in a raster image, given explicit camera intrinsic and extrinsic parameters [S9, S12, S20, unofficial]. It solves the problem of mapping 2D screen coordinates to 3D world-space rays for volume rendering or ray tracing [S5, S9, unofficial]. Unlike [Pinhole Camera Ray Generation](5058-pinhole-camera-ray-generation.md), which often derives rays directly from geometric primitives such as field of view (FOV) and camera basis vectors, this method relies on explicit intrinsic ($K$) and extrinsic ($c2w$) matrices to define the projection geometry [S1, S2, S9, unofficial].

## How it works
**Inputs:**
*   Image dimensions: Height $H$, Width $W$ (in pixels) [S12, S21, unofficial].
*   Camera Intrinsic Matrix $K$: A $3 \times 3$ matrix containing focal lengths $f_x, f_y$ and principal point $(c_x, c_y)$ [S12, unofficial].
*   Camera-to-World Matrix $c2w$: A $4 \times 4$ (or $3 \times 4$) transformation matrix mapping camera coordinates to world coordinates [S12, S21, unofficial]. The upper-left $3 \times 3$ block is the rotation $\mathbf{R}_{c2w}$, and the rightmost column (or row 3) is the translation $\mathbf{t}_{c2w}$ (camera origin) [S12, S21, unofficial].

**Outputs:**
*   `rays_o`: Tensor of shape $(H, W, 3)$ containing ray origins in world space [S11, S12, unofficial].
*   `rays_d`: Tensor of shape $(H, W, 3)$ containing ray directions in world space [S11, S12, unofficial].

**Data Structures:**
*   Pixel coordinate grids: 2D arrays of shape $(H, W)$ representing pixel indices $i$ (rows, $0 \dots H-1$) and $j$ (columns, $0 \dots W-1$) [S12, S19, unofficial].

**Steps:**

1.  **Generate Pixel Grids:** Create 2D meshgrids for pixel coordinates $i$ and $j$. The indexing convention must match the coordinate system (e.g., 'xy' for $j$ varying along width, $i$ along height) [S12, S19, S25, unofficial].
2.  **Center Pixel Coordinates:** Add $0.5$ to $i$ and $j$ to target the center of each pixel [S6, S8, S25, unofficial]. *Note: Some implementations omit this if calibration accuracy does not justify it [S10, unofficial].*
3.  **Compute Camera-Space Directions:** Calculate unnormalized ray directions in the camera coordinate system. The camera typically looks along the negative Z-axis (OpenGL convention) or positive Z-axis (OpenCV convention). For the standard OpenGL convention (looking down $-Z$), the direction components are:
    $$
    d_{cam, x} = \frac{j - c_x}{f_x}, \quad d_{cam, y} = -\frac{i - c_y}{f_y}, \quad d_{cam, z} = -1
    $$
    The negative sign on $d_{cam, y}$ accounts for the screen Y-axis pointing downward while the camera Y-axis points upward [S6, S12, S33, unofficial]. If using OpenCV convention (looking down $+Z$), $d_{cam, z} = 1$ and the Y sign may vary based on axis alignment [S11, S35, unofficial].
4.  **Transform to World Space:** Rotate the camera-space directions to world space using the rotation part of the $c2w$ matrix. For a direction vector $\mathbf{d}_{cam}$, the world direction is:
    $$
    \mathbf{d}_{world} = \mathbf{R}_{c2w} \mathbf{d}_{cam}
    $$
    In code, this is often a matrix multiplication: `rays_d = directions @ c2w[:3, :3].T` [S9, S31, S34, unofficial].
5.  **Normalize Directions:** Normalize $\mathbf{d}_{world}$ to unit length [S6, S9, unofficial].
6.  **Set Ray Origins:** The ray origin is the camera position in world space, extracted from the translation component of $c2w$:
    $$
    \mathbf{o}_{world} = \mathbf{t}_{c2w}
    $$
    Broadcast this origin to match the shape of `rays_d` (i.e., $(H, W, 3)$) [S20, S31, unofficial].

**Pseudocode:**

```python
import numpy as np

def generate_rays_from_matrix(H, W, K, c2w):
    """
    Generate ray origins and directions for each pixel given intrinsic K and extrinsic c2w.
    
    Args:
        H (int): Image height.
        W (int): Image width.
        K (np.ndarray): 3x3 intrinsic matrix [[fx, 0, cx], [0, fy, cy], [0, 0, 1]].
        c2w (np.ndarray): 4x4 camera-to-world transformation matrix.
        
    Returns:
        rays_o (np.ndarray): Shape (H, W, 3), ray origins in world space.
        rays_d (np.ndarray): Shape (H, W, 3), normalized ray directions in world space.
    """
    # 1. Extract parameters
    fx = K[0, 0]
    fy = K[1, 1]
    cx = K[0, 2]
    cy = K[1, 2]
    
    # Rotation and translation from c2w
    R_c2w = c2w[:3, :3]
    t_c2w = c2w[:3, 3]
    
    # 2. Create pixel coordinate grids
    # j corresponds to columns (width), i corresponds to rows (height)
    j, i = np.meshgrid(np.arange(W), np.arange(H), indexing='xy')
    
    # 3. Center pixel coordinates (add 0.5)
    j = j.astype(np.float32) + 0.5
    i = i.astype(np.float32) + 0.5
    
    # 4. Compute camera-space directions
    # Standard OpenGL convention: camera looks down -Z, Y is up, X is right.
    # Screen Y is down, so we negate the Y component relative to camera Y.
    # d_cam = [ (j - cx)/fx, -(i - cy)/fy, -1 ]
    d_cam_x = (j - cx) / fx
    d_cam_y = -(i - cy) / fy
    d_cam_z = -1.0
    
    # Stack into (H, W, 3)
    directions_cam = np.stack([d_cam_x, d_cam_y, np.full_like(d_cam_x, d_cam_z)], axis=-1)
    
    # 5. Transform directions to world space
    # directions_world = directions_cam @ R_c2w.T
    # Note: R_c2w transforms vectors from camera to world.
    # If directions_cam is (H, W, 3), and R_c2w is (3, 3):
    # d_world_k = sum_j d_cam_j * R_c2w[j, k]
    # In numpy: (H, W, 3) @ (3, 3).T -> (H, W, 3)
    directions_world = np.einsum('ij,kl->ijkl', directions_cam, R_c2w.T).reshape(H, W, 3) # Efficient batch matmul alternative
    # Or simply:
    # directions_world = directions_cam @ R_c2w.T
    
    # 6. Normalize directions
    norms = np.linalg.norm(directions_world, axis=-1, keepdims=True)
    # Avoid division by zero
    norms = np.where(norms == 0, 1.0, norms)
    directions_world = directions_world / norms
    
    # 7. Set origins
    # Broadcast t_c2w (3,) to (H, W, 3)
    rays_o = np.broadcast_to(t_c2w, (H, W, 3)).copy()
    
    return rays_o, directions_world
```

**Edge Cases and Pitfalls:**
*   **Coordinate System Convention:** The sign of the Z component and the Y component depends on whether the camera looks along $+Z$ (OpenCV) or $-Z$ (OpenGL) and whether the image Y-axis is top-down or bottom-up. Mismatched conventions result in inverted or rotated images [S6, S11, S12, unofficial].
*   **Division by Zero:** If a ray direction component is zero (e.g., ray parallel to an axis), AABB intersection tests may produce infinities. IEEE 754 handles this, but explicit checks are safer for robustness [S16, unofficial].
*   **Pixel Centering:** Omitting the $+0.5$ offset is a common simplification but can introduce aliasing or misalignment in high-precision rendering [S10, S25, unofficial].

## Subtopics

### [Camera Intrinsic Matrix Construction](3112-camera-intrinsic-matrix-construction.md)
Constructs the $3 \times 3$ intrinsic matrix $K$ from focal length and image dimensions. It assumes zero skew and an aspect ratio of 1 (or incorporates aspect ratio into the focal length scaling).
*   **Formula:** $K = \begin{bmatrix} f_{\text{camera}} & 0 & W/2 \\ 0 & f_{\text{camera}} & H/2 \\ 0 & 0 & 1 \end{bmatrix}$.
*   **Parameters:** $f_{\text{camera}}$ is the focal length in pixels, $W$ is image width, $H$ is image height.
*   **When to choose:** Use when the camera is calibrated with a single focal length parameter or when simplifying the intrinsic model for synthetic data generation.

### [Pinhole Camera Ray Generation](5058-pinhole-camera-ray-generation.md)
Computes ray origins and directions assuming an ideal pinhole model where all rays pass through a single center point. Unlike Camera Matrix Ray Generation, which uses explicit $K$ and $c2w$ matrices, this method often derives rays directly from geometric primitives such as field of view (FOV), aspect ratio, and camera basis vectors (look-at formulation). It provides no depth of field.
*   **When to choose:** Use for simple synthetic scenes or when camera parameters are defined by FOV and position rather than calibration matrices.

## Operating characteristics
*   **Time Complexity:** $O(H \times W)$ for generating rays for all pixels. The operations are vectorizable and highly parallelizable on GPU [S12, S20, unofficial].
*   **Memory Complexity:** $O(H \times W)$ to store the origin and direction tensors [S11, S12, unofficial].
*   **Performance:** Highly efficient on modern GPUs due to regular memory access patterns and simple arithmetic operations [S12, S20, unofficial].
*   **Strengths:** Explicitly handles arbitrary camera poses and intrinsics; robust to complex camera setups (e.g., non-square pixels, principal point offset) [S12, S21, unofficial].
*   **Limitations:** Requires pre-computed or calibrated intrinsic and extrinsic matrices; less intuitive for artists defining cameras by FOV and look-at vectors compared to geometric methods [S1, S9, unofficial].
*   **When to use:** When working with real-world camera data (e.g., COLMAP, NeRF datasets) where intrinsics and poses are known [S11, S12, unofficial].
*   **When not to use:** For simple synthetic scenes where a basic FOV-based setup is sufficient and calibration data is unavailable [S9, unofficial].

## Background
The method originates from standard computer vision and graphics literature on camera models, specifically the pinhole camera model defined by intrinsic and extrinsic parameters [S12, S32, unofficial]. It is widely used in NeRF (Neural Radiance Fields) implementations and volume rendering pipelines that ingest real-world camera poses [S9, S11, S12, unofficial]. The use of explicit matrices allows for seamless integration with photogrammetry pipelines (e.g., COLMAP) [S11, S19, unofficial].
