# Spherical Light Grid for Shadows

Also called: Light Grid, Perspective Grid Traversal, Perspective grids, Shadow Ray Reordering, Spherical Grid

## Overview
The Spherical Light Grid for Shadows is a ray generation and reordering technique that treats shadow rays with the same coherence as primary rays by mapping the light source’s environment into a perspective grid [S1]. It solves the problem of poor spatial locality in shadow ray tracing, where rays originating from scattered primary intersections lack the tile-based coherence found in primary ray generation [S1]. Unlike sibling methods that handle frustums separately or use cumbersome cubemap clamping, this method uses a unified spherical mapping in azimuthal-elevation space to enable efficient parallel sorting and load balancing on the GPU [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** Primary ray intersection points (recorded at the end of the primary ray tracing step), light source position, camera view frustum, and scene geometry [S1].
*   **Output:** A reordered list of shadow rays grouped by light grid tiles, ready for parallel traversal [S1].

**Data Structures:**
*   **Light Grid:** A perspective grid built with the light source as the camera [S1]. It consists of voxels defined by tiles on a rectangle in $\phi$-$\theta$ space and constant depth planes (near/far bounds) [S1].
*   **Ray Arrays:** Parallel arrays storing ray properties, specifically `tileIDArr` (tile identifier) and `rayIDArr` (ray identifier) [S1].
*   **Auxiliary Arrays:** `pseudoArr`, `scratchArr`, and `oArr` used during the GPU parallel scan process [S1].

**Coordinate System:**
The spherical mapping uses azimuthal ($\phi$) and elevation ($\theta$) angles relative to a "forward" direction [S1]:
*   $\phi$: Measured from the forward direction in the forward-right plane [S1].
*   $\theta$: Measured from the forward direction in the forward-up plane [S1].

**Algorithm Steps:**

1.  **Define Forward Direction:** Choose a forward direction to mitigate pole singularity. A robust choice is the vector joining the light position to the centroid of the model [S1].
2.  **Limit Angular Extents:** Restrict the light’s frustum in $\phi$-$\theta$ space to the bounding box of the projection of the camera’s view frustum [S1]. This ensures only geometry visible to the camera participates in the grid, reducing triangle count and increasing tile granularity [S1].
3.  **Construct Grid:** Define tiles on the rectangle in $\phi$-$\theta$ space [S1]. Use constant depth planes to define the near and far bounds of the light frustum [S1].
4.  **Record Intersections:** At the end of the primary ray tracing step, record the intersection points for each primary ray [S1].
5.  **Map to Spherical Space:** For each shadow ray (originating from a primary intersection point), compute its spherical coordinates relative to the light source and determine the corresponding tile ID [S1].
6.  **Sort by Tile ID:** Sort the list of shadow rays using the tile ID as the key [S1]. This groups rays belonging to the same light tile together, restoring spatial coherence [S1].
7.  **Load Balancing (Scan):** Perform a parallel scan on the GPU to determine the boundaries of each tile’s ray count [S1]. This allows dynamic assignment of thread blocks to tiles, handling cases where ray counts per tile vary widely [S1].

**Pseudocode:**
The following pseudocode illustrates the parallel initialization and mapping step for reordering load balancing, as described in Algorithm 1 of [S1].

    for ray in range(totalrays):

        phi = atan2(dot(dir_vec, right_dir), dot(dir_vec, forward_dir))
        theta = atan2(dot(dir_vec, up_dir), dot(dir_vec, forward_dir))
        # Clamp to camera frustum bounding box in phi-theta space
        phi = max(frustum_bbox.min_phi, min(frustum_bbox.max_phi, phi))
        theta = max(frustum_bbox.min_theta, min(frustum_bbox.max_theta, theta))

        rayIDArr[ray] = ray

    # Sort rays by tile ID to group coherent rays [S1]
    indices = sorted(range(totalrays), key=lambda i: tileIDArr[i])
    sorted_tileIDArr = [tileIDArr[i] for i in indices]
    sorted_rayIDArr = [rayIDArr[i] for i in indices]

    # Load balancing: parallel scan and stream compaction [S1]

**Parameters:**
*   **Forward Direction:** Critical for performance. The line joining the light position to the model centroid is recommended [S1].
*   **Frustum Bounds:** Limited to the bounding box of the projection of the camera’s view frustum in $\phi$-$\theta$ space [S1].
*   **Spotlight Clamping:** Implemented by marking a bounding rectangle in the $\phi$-$\theta$ space to clamp the region [S1].

**Edge Cases and Pitfalls:**
*   **Pole Singularity:** Triangles lying in the right-forward plane ($\theta = \pi/2$) are duplicated along all tiles near the pole, causing performance loss [S1]. Mitigation requires choosing a "good" forward direction [S1].
*   **Variable Ray Counts:** Unlike primary rays, shadow rays per tile vary widely, requiring load balancing via scan primitives rather than static thread mapping [S1].

## Operating characteristics
*   **Time Complexity:** Dominated by the parallel sort and scan operations on the GPU [S1]. The sorting brings coherence to secondary rays, making subsequent traversal efficient [S1].
*   **Memory Complexity:** Requires storage for the light grid structure and auxiliary arrays for ray reordering (`tileIDArr`, `rayIDArr`, etc.) [S1].
*   **Performance:** The method is cheap to build on the GPU, allowing the light grid to be rebuilt dynamically for moving scenes [S1]. It improves performance by reducing the number of triangles participating in grid building and ray-triangle checks through frustum culling [S1]. Perspective grids are three to five times faster than the uniform grid method by Kalojanov and Slusallek for primary and shadow rays on a GTX480 [S1]. Grid building is about ten times cheaper than building an HLBVH with SAH [S1].
*   **Strengths:** Unified framework for shadow ray generation; handles spotlights naturally via rectangular clamping in spherical space; exploits GPU parallelism for reordering [S1].
*   **Limitations:** Suffers from pole singularity if the forward direction is poorly chosen; requires careful load balancing due to uneven ray distribution per tile [S1].
*   **When to use:** When tracing shadows from point lights in dynamic scenes on the GPU, especially when primary ray coherence is high but shadow ray coherence is low [S1].
*   **When not to use:** If the light source is directional or the scene geometry is static and simple, the overhead of grid construction and reordering may not be justified [S1].

## Background
The Spherical Light Grid for Shadows was introduced by Guntry and Narayanan in their work on raytracing dynamic scenes on the GPU using grids [S1]. It builds upon earlier cubemap-style ray mapping techniques, which handled each frustum separately and resulted in extra traversal work and tedious clamping [S1]. The spherical mapping approach provides a more unified framework for computing shadows by treating the light source as a camera with a perspective grid [S1].
