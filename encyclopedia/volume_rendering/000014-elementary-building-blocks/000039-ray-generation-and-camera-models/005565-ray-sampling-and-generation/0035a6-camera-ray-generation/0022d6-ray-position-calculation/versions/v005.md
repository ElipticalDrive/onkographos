# Ray Position Calculation

Also called: Query Point Sampling

## Overview
Ray Position Calculation computes the 3D spatial coordinates of sampling points (query points) along camera rays within specified near and far depth bounds. It solves the problem of discretizing a continuous ray into a finite set of 3D locations for volume rendering or neural radiance field (NeRF) evaluation. It differs from its siblings, such as [Camera Matrix Ray Generation](7456-camera-ray-generation.md) which produces the ray vectors themselves, by taking those rays and sampling specific positions along them. It differs from [World Space Position Reconstruction](10694-world-space-position-reconstruction.md) by generating positions along a parametric ray direction rather than reconstructing a single point from depth buffers.

## How it works
**Inputs:**
- `ray_origins`: Tensor of shape $(W, H, 3)$, where $W$ is width and $H$ is height. Contains the 3D origin for each pixel's ray.
- `ray_directions`: Tensor of shape $(W, H, 3)$. Contains the normalized direction vector for each pixel's ray.
- `near_thresh`: Float. The minimum distance along the ray to sample.
- `far_thresh`: Float. The maximum distance along the ray to sample.
- `num_samples`: Integer. The number of discrete points to generate along each ray.
- `randomize`: Boolean. If true, adds uniform noise to the depth values to reduce aliasing (jittering). Default is True.

**Outputs:**
- `query_points`: Tensor of shape $(W, H, num\_samples, 3)$. The 3D coordinates of the sampling points.

**Data Structures:**
- `depth_values`: A 1D tensor of shape $(num\_samples)$ containing the sampled distances along the ray.

**Steps:**
1. Generate a linearly spaced array of distances between `near_thresh` and `far_thresh` with `num_samples` elements. Let this be $d$.
   $$ d_i = \text{linspace}(near\_thresh, far\_thresh, num\_samples)_i $$
2. If `randomize` is true, add uniform noise $\epsilon \sim U(0, \frac{far\_thresh - near\_thresh}{num\_samples})$ to each $d_i$ to jitter the samples.
3. Compute the query points using the ray equation:
   $$ Q_{w,h,s} = O_{w,h} + d_s \cdot D_{w,h} $$
   Where:
   - $Q_{w,h,s}$ is the query point at pixel $(w,h)$ and sample index $s$.
   - $O_{w,h}$ is the ray origin at pixel $(w,h)$.
   - $D_{w,h}$ is the ray direction at pixel $(w,h)$.
   - $d_s$ is the distance value for sample $s$.

**Pseudocode:**
```python
import torch
import numpy as np

def ray_position_calculation(ray_origins, ray_directions, near_thresh, far_thresh, num_samples, randomize=True):
    """
    Computes 3D query points along rays.
    
    Args:
        ray_origins: torch.Tensor, shape (width, height, 3)
        ray_directions: torch.Tensor, shape (width, height, 3)
        near_thresh: float, nearest depth coordinate
        far_thresh: float, farthest depth coordinate
        num_samples: int, number of samples per ray
        randomize: bool, whether to add jitter noise
        
    Returns:
        query_points: torch.Tensor, shape (width, height, num_samples, 3)
    """
    # Step 1: Create linearly spaced depth values
    # torch.linspace(start, end, steps)
    depth_values = torch.linspace(near_thresh, far_thresh, num_samples, device=ray_origins.device)
    
    # Step 2: Optional jittering
    if randomize:
        # Add uniform noise in range [0, step_size)
        step_size = (far_thresh - near_thresh) / num_samples
        noise = torch.rand_like(depth_values) * step_size
        depth_values = depth_values + noise
        
    # Step 3: Expand dimensions for broadcasting
    # ray_origins: (W, H, 1, 3)
    # ray_directions: (W, H, 1, 3)
    # depth_values: (1, 1, num_samples, 1)
    ray_origins_exp = ray_origins.unsqueeze(2)
    ray_directions_exp = ray_directions.unsqueeze(2)
    depth_values_exp = depth_values.unsqueeze(0).unsqueeze(0).unsqueeze(3)
    
    # Step 4: Compute query points
    # Q = O + d * D
    query_points = ray_origins_exp + ray_directions_exp * depth_values_exp
    
    return query_points
```

**Edge Cases and Pitfalls:**
- **Precision:** When `num_samples` is very large, `depth_values` may suffer from floating-point precision issues if `near_thresh` and `far_thresh` are large. [G] Ensure `near_thresh` and `far_thresh` are consistent with the coordinate system scale.
- **Zero Direction:** If `ray_directions` contains zero vectors, the result will be invalid. [G] Ray directions should be normalized before this step.
- **Near/Far Order:** If `near_thresh > far_thresh`, `torch.linspace` will produce decreasing values, which is mathematically valid but semantically incorrect for ray marching. [G] Validate `near_thresh < far_thresh`.

## Subtopics

### [World Space Position Reconstruction](10694-world-space-position-reconstruction.md)
Reconstructs 3D world-space positions from 2D screen-space UV coordinates and depth values. Choose this when working with post-processing raymarching or deferred rendering pipelines where depth buffers are available, rather than parametric camera rays.

## Operating characteristics
- **Time Complexity:** $O(W \cdot H \cdot N)$, where $W$ is width, $H$ is height, and $N$ is `num_samples`. The operation is highly parallelizable on GPUs.
- **Memory Complexity:** $O(W \cdot H \cdot N \cdot 3)$ for the output `query_points` tensor. Intermediate tensors are minimal.
- **Performance:** On modern GPUs, this is a memory-bound operation dominated by tensor allocation and broadcasting. It is extremely fast compared to the subsequent volume rendering steps (e.g., density/color evaluation).
- **Strengths:** Simple, differentiable, and easily vectorized. Supports jittering for anti-aliasing.
- **Limitations:** Does not handle ray-object intersections or adaptive sampling. It assumes a uniform or linear spacing along the ray unless modified.
- **When to use:** Standard volume rendering, NeRF training, and any method requiring fixed-step ray marching.
- **When not to use:** When adaptive sampling based on scene complexity is required, or when ray-object intersection is needed before sampling.

## Background
This method is a fundamental building block in neural radiance fields (NeRF) and volume rendering. It was popularized by the original NeRF paper [Mildenhall et al., 2020] and is implemented in many open-source NeRF repositories. The specific implementation details, including the use of `torch.linspace` and jittering, are commonly found in PyTorch-based NeRF implementations [S1, unofficial]. The concept of sampling along rays is central to classical volume rendering [Levoy, 1988], but the explicit tensor-based calculation for differentiable rendering is a hallmark of modern neural rendering pipelines.
