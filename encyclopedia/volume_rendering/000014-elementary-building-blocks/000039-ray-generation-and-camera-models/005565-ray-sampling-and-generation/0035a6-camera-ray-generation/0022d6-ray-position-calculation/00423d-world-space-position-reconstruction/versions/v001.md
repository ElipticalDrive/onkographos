# World Space Position Reconstruction

Also called: Screen-space to World-space Position Reconstruction, NDC to World Space Conversion

## Overview
World Space Position Reconstruction is a method to reconstruct 3D world-space positions from 2D screen-space UV coordinates and depth values, enabling raymarching in post-processing by converting screen space to world space [S1, S2, unofficial]. It solves the problem of determining the exact 3D location corresponding to a pixel in a post-processing pass, which is necessary for volumetric effects like light shafts or fog that require sampling in 3D space [S1, unofficial]. It differs from [Ray Position Calculation](2895-ray-position-calculation.md) by deriving the ray origin and direction from scene depth and camera matrices rather than assuming a generic ray parameterization, allowing for occlusion-aware reconstruction [S1, S2, unofficial].

## How it works
**Inputs:**
- `uv`: The UV coordinate of the current fragment in the post-processing pass (range [0, 1]).
- `depth`: The depth value from the scene's depth texture sampled at `uv`.
- `projectionMatrixInverse`: The inverse of the camera's projection matrix.
- `viewMatrixInverse`: The inverse of the view matrix (often equivalent to `camera.matrixWorld`), transforming view space to world space [S1, unofficial].
- `CameraPosition`: The 3D position of the camera in world space [S2, unofficial].

**Outputs:**
- `worldSpace`: A 3D vector representing the reconstructed position in world space.

**Data Structures:**
- The depth texture is accessed using integer coordinates to avoid hardware filtering artifacts. An integer 3-vector `texCoordInt` is constructed from the pixel's screen-space x and y coordinates and a z of 0 [S2, unofficial].
- Intermediate vectors are 4D homogeneous coordinates (`vec4` or `float4`) for matrix multiplication, and 3D vectors (`vec3` or `float3`) for final positions.

**Steps:**
1.  **Convert UV to NDC:** Transform the screen-space UV coordinates to Normalized Device Coordinates (NDC) range [-1, 1].
    $$x_{NDC} = uv.x \times 2.0 - 1.0$$
    $$y_{NDC} = uv.y \times 2.0 - 1.0$$
    [S1, unofficial]

2.  **Convert Depth to NDC Z:** Transform the linear depth value (typically in range [0, 1] or [near, far] depending on the depth buffer format) to NDC Z range [-1, 1].
    $$z_{NDC} = depth \times 2.0 - 1.0$$
    [S1, unofficial]

3.  **Construct Clip-Space Vector:** Assemble the NDC coordinates into a homogeneous clip-space vector.
    $$clipSpace = \{ x_{NDC}, y_{NDC}, z_{NDC}, 1.0 \}$$
    [S1, unofficial]

4.  **Transform to View Space:** Multiply the clip-space vector by the inverse projection matrix.
    $$view = projectionMatrixInverse \times clipSpace$$
    [S1, unofficial]

5.  **Transform to World Space:** Multiply the view-space vector by the inverse view matrix.
    $$world = viewMatrixInverse \times view$$
    [S1, unofficial]

6.  **Perspective Divide:** Perform the perspective divide to obtain the final 3D world position.
    $$worldSpace = world.xyz / world.w$$
    [S1, unofficial]

**Alternative Linear Depth Method:**
If linear depth is available directly from the depth buffer, the position can be calculated as:
$$Position_{WS} = Depth_{linear} \times ViewDir + CameraPosition$$
where `ViewDir` is the view direction vector for the current pixel [S2, unofficial]. This requires loading the depth using point filtering [S2, unofficial].

**Pseudocode:**
```python
def get_world_position(uv: vec2, depth: float, projection_matrix_inverse: mat4, view_matrix_inverse: mat4) -> vec3:
    # Step 1: Convert UV to NDC
    ndc = uv * 2.0 - 1.0
    
    # Step 2: Convert depth to NDC Z
    clip_z = depth * 2.0 - 1.0
    
    # Step 3: Construct clip-space vector
    clip = vec4(ndc.x, ndc.y, clip_z, 1.0)
    
    # Step 4: Transform to view space
    view = projection_matrix_inverse * clip
    
    # Step 5: Transform to world space
    world = view_matrix_inverse * view
    
    # Step 6: Perspective divide
    return world.xyz / world.w
```
[S1, unofficial]

**Parameters:**
- `cameraFar`: The depth limit beyond which nothing will be visible or rendered. Used to clamp or interpret depth values [S1, unofficial].
- `lightDirection`: A normalized vector representing the direction the light points toward. Used in subsequent raymarching steps [S1, unofficial].
- `lightPosition`: A vector representing the position of the light [S1, unofficial].
- `coneAngle`: Represents how wide the spotlight aperture is [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Texture Filtering:** Using hardware texture filtering is incorrect for this reconstruction because it interpolates across edges of different blocks or depth discontinuities. Point filtering (e.g., `Texture.Load` in HLSL or `texelFetch` in GLSL) must be used instead to ensure accurate depth sampling [S2, unofficial].
- **Depth Buffer Format:** The conversion $z_{NDC} = depth \times 2.0 - 1.0$ assumes the depth buffer stores values in the range [0, 1]. If the depth buffer uses a different range (e.g., [0, far]), the formula must be adjusted accordingly. Not given in the sources.
- **W-component:** The perspective divide by `world.w` is critical. If `world.w` is zero or near-zero, the position is undefined or at infinity. This typically happens if the pixel is outside the view frustum or if the depth value is invalid. Not given in the sources.

## Operating characteristics
- **Time Complexity:** $O(1)$ per pixel. The calculation involves a fixed number of arithmetic operations and matrix-vector multiplications.
- **Memory Complexity:** $O(1)$ auxiliary memory. Requires storage for the inverse matrices and the depth texture.
- **Measured Performance:** Not given in the sources.
- **Scaling:** Scales linearly with the number of pixels in the post-processing pass.
- **Strengths:** Enables post-processing volumetric effects without requiring geometry reconstruction or additional render passes for depth. Simple to implement given access to standard camera matrices and depth buffers.
- **Limitations:** Relies on the accuracy of the depth buffer. Depth precision issues (z-fighting) can lead to inaccurate world positions, especially at far distances. Requires the depth texture to be available in the post-processing pass.
- **When to use:** When implementing volumetric lighting, fog, or other effects that require 3D sampling in post-processing.
- **When not to use:** When the depth buffer is not available or when higher precision is required than the depth buffer can provide.

## Background
The method originates from techniques used in real-time volumetric lighting with post-processing and raymarching. It was described by Maxime Heckel in "On Shaping Light: Real-Time Volumetric Lighting with Post-Processing and Raymarching" [S1, unofficial] and by kosmonaut in "Signed Distance Field Rendering Journey pt.1" [S2, unofficial]. These sources highlight the transition from screen-space coordinates to world-space for raymarching light shafts and SDF rendering.
