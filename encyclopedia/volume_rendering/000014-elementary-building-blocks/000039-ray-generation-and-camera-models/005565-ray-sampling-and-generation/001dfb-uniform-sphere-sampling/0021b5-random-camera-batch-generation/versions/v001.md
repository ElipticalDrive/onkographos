# Random Camera Batch Generation

Also called: Camera on Sphere

## Overview
Random Camera Batch Generation (COS) is a method for generating training data for neural radiance fields (NeRF) by uniformly sampling random camera views directed at the scene center from a user-controlled sphere [S1, unofficial]. It differs from methods that use specific, user-selected train and test cameras (such as TTC) by providing a dense, randomized set of viewpoints for training, while testing data is typically extracted from a selected camera [S1, unofficial]. It builds on [Uniform Sphere Sampling](1669-uniform-sphere-sampling.md) to determine camera positions.

## How it works
**Inputs and Outputs:**
*   **Inputs:** Scene configuration including `scene.seed`, `scene.frame_current`, `scene.sphere_radius`, `scene.sphere_scale`, `scene.sphere_rotation`, `scene.sphere_location`, and `scene.upper_views`. Batch parameters including `batch_size`, `cam_radius`, `fovy`, `iter_res`, and `cam_near_far`.
*   **Outputs:** A batch of camera poses (location, rotation, intrinsics) ready for rendering.

**Data Structures:**
*   **Random Number Generator (RNG):** A seeded pseudo-random number generator (e.g., `random.Random` in Python or `torch.Generator`).
*   **Camera Pose:** Defined by position (Cartesian coordinates), look-at direction, up vector, field of view, and clipping planes.

**Steps:**

1.  **Seed Initialization:**
    Generate a deterministic seed based on the scene and frame to ensure reproducibility and variation over time [S1, unofficial].
    $$ \text{seed} = (2654435761 \times (\text{scene.seed} + 1)) \oplus (805459861 \times (\text{scene.frame\_current} + 1)) $$
    Initialize the RNG with this seed [S1, unofficial].

2.  **Sample Spherical Coordinates:**
    For each of the `batch_size` cameras, sample azimuth ($\theta$) and elevation/colatitude ($\phi$) to ensure uniform distribution on the sphere [S1, S2, unofficial].
    *   Sample azimuth $\theta$ uniformly in $[0, 2\pi)$:
        $$ \theta = \text{rng.random()} \times 2\pi $$
    *   Sample $\phi$ using inverse transform sampling for uniform sphere distribution:
        $$ \phi = \arccos(1 - 2 \times \text{rng.random()}) $$
        *Note: Some implementations may use elevation ranges $[-\pi/2, \pi/2]$ but the formula $\arccos(1-2u)$ maps to $[0, \pi]$, representing the polar angle from the z-axis [S1, S2, unofficial].*

3.  **Compute Unit Vector:**
    Convert spherical coordinates to Cartesian unit vector components [S1, unofficial]:
    $$ u_x = \cos(\theta) \sin(\phi) $$
    $$ u_y = \sin(\theta) \sin(\phi) $$
    $$ u_z = \begin{cases} |\cos(\phi)| & \text{if } \text{scene.upper\_views} \text{ is true} \\ \cos(\phi) & \text{otherwise} \end{cases} $$
    Form the unit vector $\mathbf{u} = (u_x, u_y, u_z)$ [S1, unofficial].

4.  **Scale and Transform Position:**
    Scale the unit vector by the sphere radius and scale factors, then apply rotation and translation [S1, unofficial]:
    $$ \mathbf{p}_{\text{local}} = \text{scene.sphere\_radius} \times (\mathbf{u} \odot \text{scene.sphere\_scale}) $$
    $$ \mathbf{R} = \text{EulerToMatrix}(\text{scene.sphere\_rotation}) $$
    $$ \mathbf{p}_{\text{final}} = \mathbf{R} \mathbf{p}_{\text{local}} + \text{scene.sphere\_location} $$
    *Note: Source [S2, unofficial] mentions adding a random offset to camera positions: `eye = camera_pos + torch.rand((batch_size, 1), device=device) * 0.5 - 0.25`. This appears to be a specific implementation detail for jittering, not part of the core uniform sampling definition [S2, unofficial].*

5.  **Define Camera Orientation:**
    *   **Look-at:** Set the look-at direction to the origin (scene center): $\mathbf{at} = (0, 0, 0)$ [S2, unofficial].
    *   **Up Vector:** Set the up vector to the Y-axis: $\mathbf{up} = (0, 1, 0)$ [S2, unofficial].
    *   Compute the rotation matrix from the camera position to the look-at point using the up vector.

6.  **Set Intrinsics and Clipping:**
    *   **Field of View:** Set `fovy` (default $45^\circ$ or $\pi/4$ radians) [S2, unofficial].
    *   **Resolution:** Set `iter_res` (default $[2048, 2048]$) [S2, unofficial].
    *   **Clipping Planes:** Set `cam_near_far` (default $[0.1, 1000.0]$) [S2, unofficial].
    *   **Radius:** The effective sampling radius is `cam_radius` (default 3.0) [S2, unofficial]. If `scene.sphere_radius` is used, it overrides or defines this radius.

**Pseudocode:**

```python
import math
import random
import numpy as np

def generate_random_camera_batch(scene, batch_size, device='cpu'):
    """
    Generates a batch of random camera poses on a sphere.
    
    Args:
        scene: Object containing scene parameters (seed, frame_current, sphere_radius, etc.)
        batch_size: Number of cameras to generate.
        device: Device for tensor operations.
        
    Returns:
        cameras: List of camera dictionaries with 'location', 'rotation', 'fovy', 'near', 'far'.
    """
    # 1. Seed Initialization
    seed_val = (2654435761 * (scene.seed + 1)) ^ (805459861 * (scene.frame_current + 1))
    rng = random.Random(seed_val)
    
    cameras = []
    
    # Parameters
    radius = scene.sphere_radius
    scale = scene.sphere_scale
    rotation_euler = scene.sphere_rotation
    location = scene.sphere_location
    upper_views = scene.upper_views
    fovy = np.deg2rad(45) # Default 45 degrees
    near = 0.1
    far = 1000.0
    
    for _ in range(batch_size):
        # 2. Sample Spherical Coordinates
        theta = rng.random() * 2 * math.pi
        phi = math.acos(1 - 2 * rng.random())
        
        # 3. Compute Unit Vector
        sin_phi = math.sin(phi)
        cos_phi = math.cos(phi)
        
        ux = math.cos(theta) * sin_phi
        uy = math.sin(theta) * sin_phi
        
        if upper_views:
            uz = abs(cos_phi)
        else:
            uz = cos_phi
            
        unit_vec = np.array([ux, uy, uz])
        
        # 4. Scale and Transform Position
        # Apply scale factors element-wise
        scaled_vec = unit_vec * scale
        # Scale by radius
        local_pos = scaled_vec * radius
        
        # Apply rotation (Euler to Matrix)
        # Note: Standard Euler rotation application. Assuming Z-Y-X or similar order as per Blender mathutils.
        # For simplicity, we assume a generic rotation matrix R.
        R = euler_to_rotation_matrix(rotation_euler)
        rotated_pos = R @ local_pos
        
        final_pos = rotated_pos + location
        
        # Optional: Add random offset jitter if specified in implementation [S2, unofficial]
        # offset = (np.random.rand(3) * 0.5) - 0.25
        # final_pos += offset
        
        # 5. Define Camera Orientation
        # Look at origin
        at = np.array([0.0, 0.0, 0.0])
        up = np.array([0.0, 1.0, 0.0])
        
        # Compute camera rotation matrix
        # Forward vector
        forward = at - final_pos
        forward = forward / np.linalg.norm(forward)
        
        # Right vector
        right = np.cross(forward, up)
        right = right / np.linalg.norm(right)
        
        # True Up vector
        true_up = np.cross(right, forward)
        
        # Construct rotation matrix (columns are right, up, -forward for OpenGL-style or similar)
        # Assuming standard camera orientation where Z is forward or -Z is forward.
        # Here we construct a matrix that transforms world to camera.
        cam_rot = np.eye(3)
        cam_rot[:, 0] = right
        cam_rot[:, 1] = true_up
        cam_rot[:, 2] = -forward # Assuming camera looks down -Z
        
        # 6. Store Camera Data
        cameras.append({
            'location': final_pos,
            'rotation': cam_rot,
            'fovy': fovy,
            'near': near,
            'far': far
        })
        
    return cameras
```

**Edge Cases and Pitfalls:**
*   **Precision:** Using `rng.random()` ensures uniformity, but floating-point errors in `acos` near boundaries ($1$ or $-1$) should be handled by clamping the input to $[-1, 1]$ [G].
*   **Upper Views:** If `scene.upper_views` is true, the z-component is absolute, restricting cameras to the upper hemisphere. This reduces coverage but may be desired for specific scene orientations [S1, unofficial].
*   **Scale Factors:** If `scene.sphere_scale` contains zeros, the resulting positions will collapse to the origin or a line, breaking the spherical distribution [G].

## Subtopics

### [Random List Geometry Generator](19584-random-list-geometry-generator.md)
Generates a batch of $k$ random rays for a $D$-dimensional scanning volume, where origins are placed on the volume boundary and directions are adjusted to point inward. It differs from [Random Camera Batch Generation](2595-random-camera-batch-generation.md) by constraining ray origins to the volume boundary rather than sampling camera positions on a sphere, ensuring all rays intersect the interior.

## Operating characteristics
*   **Time Complexity:** $O(N)$ where $N$ is the batch size, as each camera pose is generated independently using constant-time random number generation and arithmetic operations.
*   **Memory Complexity:** $O(N)$ to store the batch of camera poses.
*   **Performance:** The generation is extremely fast, dominated by RNG and basic vector math. Rendering time depends on the downstream volume rendering method.
*   **Strengths:** Provides dense, uniform coverage of viewpoints around the scene, which is beneficial for training NeRF models to generalize across angles. Deterministic via seed.
*   **Limitations:** Does not guarantee intersection with specific scene features (unlike boundary-constrained methods). Cameras may be placed in empty space if the scene is small relative to the sphere radius.
*   **When to use:** When training data requires diverse viewpoints and the scene is centrally located. When specific camera poses are not known or available.
*   **When not to use:** When the scene is sparse or has specific structures that require rays to pass through the interior (use [Random List Geometry Generator](19584-random-list-geometry-generator.md)). When testing requires specific, controlled viewpoints.

## Background
Random Camera Batch Generation, often referred to as COS (Camera on Sphere), was popularized in the context of BlenderNeRF, an unofficial implementation of NeRF for Blender [S1, unofficial]. It was introduced as an alternative to TTC (Train/Test Cameras) which relies on user-selected specific cameras. The method leverages the mathematical property of uniform sphere sampling to ensure that training views are evenly distributed around the scene center, aiding in the reconstruction of 3D geometry from multiple angles [S1, unofficial].
