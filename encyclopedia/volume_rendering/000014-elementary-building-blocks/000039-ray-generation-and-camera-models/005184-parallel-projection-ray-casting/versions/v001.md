# Parallel Projection Ray Casting

Also called: Volume Rendering with Parallel Projection, Orthographic Ray Casting

## Overview
Parallel projection ray casting is a volume rendering technique where all cast rays are parallel to each other and aligned with a single viewing direction [S1, S4]. It is preferred for scientific visualization because it preserves accurate sizes and relative positions of structures without perspective distortion [S1]. Unlike perspective projection, which requires storing different ray parameters for each pixel, parallel projection assumes a uniform ray direction, simplifying the geometric setup [S4].

## How it works
**Inputs and Outputs**
*   **Input:** A 3D volume dataset (voxels), image resolution $(W, H)$, and viewing angles $(\alpha, \beta, \gamma)$ representing rotations around the Z, Y, and X axes respectively [S1].
*   **Output:** A 2D image where each pixel $(i, j)$ corresponds to a ray traversing the volume [S1].

**Data Structures**
*   **Rotation Matrices:** Three $3 \times 3$ matrices are used to define the viewing direction [S1]:
    $$M_x(\gamma) = \begin{pmatrix} 1 & 0 & 0 \\ 0 & \cos \gamma & -\sin \gamma \\ 0 & \sin \gamma & \cos \gamma \end{pmatrix}$$
    $$M_y(\beta) = \begin{pmatrix} \cos \beta & 0 & \sin \beta \\ 0 & 1 & 0 \\ -\sin \beta & 0 & \cos \beta \end{pmatrix}$$
    $$M_z(\alpha) = \begin{pmatrix} \cos \alpha & -\sin \alpha & 0 \\ \sin \alpha & \cos \alpha & 0 \\ 0 & 0 & 1 \end{pmatrix}$$
    where $\alpha, \beta, \gamma$ are the rotation angles [S1].
*   **Base Plane:** A rectangular plane initially aligned with one of the coordinate planes (XOY, YOZ, or XOZ) passing through the origin [S1]. Points are placed on this plane corresponding to image pixels, scaled by a coefficient determining the distance between rays [S1].

**Steps**
1.  **Initialize Base Plane:** Select a coordinate plane (e.g., XOY) and place sample points on it corresponding to the image resolution $(W, H)$, centered at the origin [S1].
2.  **Compute Viewing Direction:** Apply rotation matrices to the normal vector of the base plane to achieve the desired viewing angle. The combined rotation matrix $M$ is typically $M = M_z(\alpha) M_y(\beta) M_x(\gamma)$ (order may vary based on convention, but sources specify these three matrices define the orientation) [S1].
3.  **Generate Rays:** For each pixel $(i, j)$, define a ray origin $\mathbf{o}_{i,j}$ on the rotated base plane and a direction $\mathbf{d}$ equal to the rotated normal vector of the base plane [S1]. All rays share the same direction $\mathbf{d}$ [S4].
4.  **Ray Marching:** For each ray, iterate through the volume. Sample voxel values along the ray path [S5, unofficial].
5.  **Compositing:** Accumulate color and opacity along the ray using a compositing function (e.g., front-to-back or back-to-front) until the ray exits the volume or opacity reaches 1.0 [S5, unofficial].
6.  **Render:** Draw the final accumulated color to the pixel $(i, j)$ [S5, unofficial].

**Pseudocode**
```python
# Define rotation matrices
def M_x(gamma):
    return [[1, 0, 0],
            [0, cos(gamma), -sin(gamma)],
            [0, sin(gamma), cos(gamma)]]

def M_y(beta):
    return [[cos(beta), 0, sin(beta)],
            [0, 1, 0],
            [-sin(beta), 0, cos(beta)]]

def M_z(alpha):
    return [[cos(alpha), -sin(alpha), 0],
            [sin(alpha), cos(alpha), 0],
            [0, 0, 1]]

# Main rendering loop
def parallel_projection_ray_cast(volume, width, height, alpha, beta, gamma):
    # 1. Compute combined rotation matrix for viewing direction
    # Note: Source [S1] lists matrices but does not explicitly specify multiplication order.
    # Standard convention is often applied, but exact order is "Not given in the sources."
    M = multiply_matrices(M_z(alpha), M_y(beta), M_x(gamma)) 
    
    # 2. Determine viewing direction vector (normal of the rotated base plane)
    # Assuming initial base plane is XOY, normal is (0,0,1)
    initial_normal = [0, 0, 1]
    view_direction = matrix_vector_multiply(M, initial_normal)
    view_direction = normalize(view_direction)

    # 3. Initialize output image
    image = zeros((height, width, 3))

    # 4. Iterate over pixels
    for j in range(height):
        for i in range(width):
            # Define ray origin on the base plane
            # Source [S1] mentions placing points on the plane aligned with coordinate axes
            # and scaling by a coefficient. Exact mapping from pixel (i,j) to 3D point
            # depends on the specific base plane selection and scaling factor.
            # [G] Assuming a standard orthographic projection setup where the base plane
            # is the image plane itself in world coordinates, or mapped via the inverse rotation.
            # For simplicity, we assume the ray origin is computed based on the camera setup.
            ray_origin = compute_ray_origin(i, j, width, height, M)
            
            # Initialize compositing state
            color = [0, 0, 0]
            opacity = 0.0
            
            # Ray marching
            t = 0.0
            step_size = get_step_size() # Depends on volume resolution and scale
            while t < volume_extent:
                current_pos = ray_origin + t * view_direction
                
                if not inside_volume(current_pos):
                    break
                
                # Sample volume
                voxel_value = sample_volume(volume, current_pos)
                voxel_color, voxel_opacity = transfer_function(voxel_value)
                
                # Compositing (Front-to-Back)
                # Source [S5, unofficial] mentions "Compositing(cur-prop, vox-prop, Normal)"
                # Standard front-to-back alpha blending:
                alpha_term = voxel_opacity * exp(-opacity)
                color += voxel_color * alpha_term
                opacity += alpha_term
                
                if opacity >= 1.0:
                    break
                
                t += step_size
            
            image[j, i] = color

    return image
```

**Parameters**
*   **Rotation Angles:** $\alpha$ (Z-axis), $\beta$ (Y-axis), $\gamma$ (X-axis). Typical values depend on the desired view [S1].
*   **Step Size:** Determines the distance between samples along the ray. Scaling is achieved by changing this step size [S1].

**Edge Cases and Pitfalls**
*   **Perspective Projection:** This method does not support perspective projection. Implementing it would require modifying the system to store different ray parameters for each pixel, increasing memory requirements [S4].
*   **Rounding Errors:** In integer-based ray casting, rounding errors can cause adjacent rays to have different forms despite having the same slope [S5, unofficial].

## Subtopics

### Template-Based Ray Casting with Space-Leaping
A variant that uses integer-based rays and templates to exploit coherence among parallel rays, speeding up rendering of binary voxel models for interactive decision making [S5, S5, unofficial].
*   **Definition:** Uses discrete line algorithms to generate integer rays. The form of the rays is calculated once and stored in a template to avoid re-performing the line algorithm for each pixel due to rounding errors [S5, unofficial].
*   **Base Plane Selection:** Rays are cast from a base plane, which is one of the six volume faces with the largest projection area on the screen and closer to the viewer [S5, unofficial].
*   **Ray Type:** Integer-based rays are used because the volume is binary, voxel values are constant/uniform, and speed is crucial. Interpolation does not improve quality for such volumes, and integer rays are faster than floating-point rays [S5, unofficial].
*   **Template Choice:** A 26-ray template is chosen over a 6-ray template because it contains fewer voxels and samples the voxel space uniformly, ensuring adjacent voxels are joined by a vertex rather than just a face [S5, unofficial].
*   **Comparison:** Integer rays use discrete line algorithms and sample nearest voxels. Floating point rays use continuous generation and higher-order interpolation. Integer rays are chosen for speed and sufficient quality in binary/uniform contexts [S5, unofficial].

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of pixels and the number of samples per ray. Template-based variants reduce overhead by caching ray paths [S5, unofficial].
*   **Memory Complexity:** Lower than perspective ray casting because a single direction vector is shared among all rays, rather than storing unique origins and directions for each pixel [S4]. However, template-based methods require additional memory to store ray templates [S5, unofficial].
*   **Strengths:** Preserves accurate sizes and relative positions of structures; no perspective distortion; efficient for scientific visualization where metric accuracy is required [S1].
*   **Limitations:** Cannot represent perspective effects; requires re-traversal of the dataset if the view changes significantly in some implementations (e.g., combined slices) [S4].
*   **When to Use:** Scientific visualization, medical imaging (CT/MRI) where measurements are critical, and interactive design evaluation of binary models [S1][S5, unofficial].
*   **When Not to Use:** Artistic visualization requiring realistic depth cues or perspective distortion [S1].

## Background
Parallel projection has been a standard technique in volume rendering for scientific visualization since the early days of the field. It is widely supported in visualization toolkits such as ParaView, where it can be enabled via a "Camera Parallel Projection" checkbox [S2, S3]. The technique is particularly prevalent in X-ray computed tomography (CT) visualization, where accurate representation of internal structures is paramount [S1]. Variations like template-based ray casting were developed in the 1990s to address performance issues in interactive design environments, specifically for die casting part evaluation [S5, unofficial].
