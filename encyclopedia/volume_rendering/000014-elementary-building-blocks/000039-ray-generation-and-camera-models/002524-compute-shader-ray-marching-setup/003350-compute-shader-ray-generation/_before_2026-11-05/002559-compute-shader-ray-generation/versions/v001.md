# Compute Shader Ray Generation

Also called: Basic GPU Ray Generation via Compute Shader, Kamera-Strahl-Erzeugung im Compute-Shader, Ray Generation Program

## Overview
This method generates initial camera rays for volume rendering by launching a compute shader where each thread corresponds to one pixel. It converts thread indices into normalized UV coordinates and computes a normalized direction vector based on the focal length. It differs from sibling methods by explicitly defining the dispatch grid structure (8x8 blocks) and the specific coordinate transformation from integer pixel indices to the $[-1, 1]$ UV space used for ray direction calculation [S1, unofficial][S2].

## How it works
**Inputs:**
- Window width $W$ and height $H$ [S1, unofficial][S2].
- Field of view angle $\alpha$ (in radians) [S1, unofficial].
- Camera orientation angles $\phi, \theta$ (optional, for final orientation) [S2].

**Outputs:**
- Ray origin $\vec{o}$ [S1, unofficial][S2].
- Ray direction $\vec{d}$ (normalized) [S1, unofficial][S2].

**Data Structures:**
- Thread ID: Provided by the hardware register `DispatchThreadID` (or equivalent). It is a 3D vector $(tx, ty, tz)$ [S1, unofficial][S2].
- Block ID: Provided by the hardware register `GroupID` (or equivalent). It is a 3D vector $(bx, by, bz)$ [S1, unofficial][S2].
- Block Dimensions: Fixed at $8 \times 8$ threads per block in the X and Y dimensions [S1, unofficial][S2].

**Parameters:**
- Focal length $f$: Calculated as $f = \frac{1}{\tan(\alpha/2)}$ [S1, unofficial][S2].
- Thread group size: 64 threads (8x8) [S1, unofficial].
- Dispatch arguments: $(\lceil W/8 \rceil, \lceil H/8 \rceil, 1)$ [S1, unofficial].

**Steps:**
1. **Thread Identification:** Determine the global thread ID $(tx, ty, tz)$ from the `DispatchThreadID` register [S1, unofficial][S2].
2. **Pixel Coordinate Calculation:** Calculate the integer pixel coordinates $(px, py)$ from the thread ID and block ID [S2]:
   $$ px = tx + bx \times 8 $$
   $$ py = ty + by \times 8 $$
   [S1, unofficial][S2]
3. **Normalization:** Scale the pixel coordinates to the range $[0, 1]$ [S1, unofficial]:
   $$ u_{scaled} = \frac{px}{W} $$
   $$ v_{scaled} = \frac{py}{H} $$
   [S1, unofficial]
4. **Centering:** Center the coordinates around the origin to obtain UV coordinates in the range $[-1, 1]$, where the top-left pixel is $[-1, 1]$ and the bottom-right is $[1, -1]$ [S1, unofficial][S2]:
   $$ u = u_{scaled} \times 2 - 1 $$
   $$ v = v_{scaled} \times 2 - 1 $$
   [S1, unofficial][S2]
5. **Direction Vector Calculation:** Compute the unoriented ray direction vector $\vec{rd}^0$ using the UV coordinates and focal length $f$ [S2]:
   $$ \vec{rd}^0 = \begin{bmatrix} u \\ v \\ f \end{bmatrix} $$
   [S2]
6. **Normalization:** Normalize $\vec{rd}^0$ to get the initial direction $\vec{d}_{local}$ [S2]:
   $$ \vec{d}_{local} = \frac{\vec{rd}^0}{\|\vec{rd}^0\|} = \frac{[u, v, f]^T}{\sqrt{u^2 + v^2 + f^2}} $$
   [S2]
7. **Origin Calculation:** Set the ray origin $\vec{o}$ at the camera position. In the local coordinate system defined by [S1, unofficial], the origin is:
   $$ \vec{o} = \begin{bmatrix} 0 \\ 0 \\ -f \end{bmatrix} $$
   [S1, unofficial]

8. **Orientation (Optional):** If the camera has orientation angles $\phi, \theta$, apply rotation matrices to $\vec{d}_{local}$ to get the final world-space direction $\vec{d}$ [S2].

**Pseudocode:**
```python
# Inputs: W, H, alpha, phi, theta (optional)
# Outputs: ray_origin, ray_direction

# Pre-calculate focal length
f = 1.0 / tan(alpha / 2.0)

# Get thread and block IDs from hardware registers
tx, ty, tz = DispatchThreadID
bx, by, bz = GroupID

# Calculate integer pixel coordinates
px = tx + bx * 8
py = ty + by * 8

# Normalize to [0, 1]
u_scaled = px / W
v_scaled = py / H

# Center to [-1, 1]
u = u_scaled * 2.0 - 1.0
v = v_scaled * 2.0 - 1.0

# Calculate unoriented direction vector
rd_x = u
rd_y = v
rd_z = f

# Normalize direction
length = sqrt(rd_x**2 + rd_y**2 + rd_z**2)
d_local_x = rd_x / length
d_local_y = rd_y / length
d_local_z = rd_z / length

# Set origin (Local space: Camera at origin, looking down +Z)
o_x = 0.0
o_y = 0.0
o_z = 0.0

# Apply rotation if needed (Placeholder for rotation matrix application)
# If phi, theta are provided, rotate d_local to get final ray_direction
# If not, ray_direction = d_local
ray_origin = (o_x, o_y, o_z)
ray_direction = (d_local_x, d_local_y, d_local_z)
```

**Edge Cases and Pitfalls:**
- **Division by Zero:** If $W$ or $H$ is 0, the shader should not be dispatched.
- **Precision:** Using single-precision floats is standard for GPU ray generation. Ensure $f$ is not too small to avoid numerical instability in normalization.
- **Boundary Conditions:** The UV coordinates range from $-1$ to $1$. Pixels at the very edge of the window will have coordinates close to $\pm 1$.

## Operating characteristics
- **Time Complexity:** $O(1)$ per pixel. The computation is constant time relative to the scene, depending only on the number of pixels $W \times H$.
- **Memory Complexity:** $O(1)$ per thread. No significant memory allocation is required for ray generation itself.
- **Performance:** Highly parallelizable. The 8x8 block size aligns with GPU warp/wavefront sizes (32 threads), ensuring efficient SIMD execution [S2].
- **Strengths:** Simple, fast, and hardware-friendly. Direct mapping from thread ID to pixel.
- **Limitations:** Assumes a simple pinhole camera model. Does not handle complex camera movements or non-pinhole models without additional transformation steps [S2].

## Background
This method is a fundamental building block for GPU-based ray marching and ray casting. It is described in the context of voxel rendering implementations, specifically in the work of Enes Hergül [S1, unofficial] and in CUDA-based raymarching tutorials [S2]. The 8x8 thread block size is a common optimization for NVIDIA GPUs to align with warp boundaries.
