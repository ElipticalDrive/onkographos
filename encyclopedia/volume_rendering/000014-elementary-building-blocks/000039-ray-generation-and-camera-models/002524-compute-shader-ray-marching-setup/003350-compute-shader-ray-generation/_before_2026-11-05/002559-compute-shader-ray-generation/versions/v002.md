# Compute Shader Ray Generation

Also called: Basic GPU Ray Generation via Compute Shader, Kamera-Strahl-Erzeugung im Compute-Shader, Ray Generation Program

## Overview
This method generates initial camera rays for a frame by launching a compute shader with one thread per pixel. It converts thread indices into normalized UV coordinates and computes ray directions using a pinhole camera model defined by a focal length. It differs from standard perspective projection implementations by explicitly detailing the normalization to $[-1, 1]$ and the specific focal length derivation from the field of view, while deferring camera orientation (rotation) to subsequent transformation steps [S1, unofficial][S2].

## How it works
**Inputs:**
*   Window width $W$ and height $H$ (integers).
*   Field of view angle $\alpha$ (radians).
*   Camera orientation angles $\phi$ (yaw) and $\theta$ (pitch) [S2].

**Outputs:**
*   Ray origin $\vec{o}$ (world space).
*   Ray direction $\vec{rd}$ (world space, normalized).

**Data Structures:**
*   No persistent data structures are required for ray generation itself. The compute shader state relies on the hardware-provided `DispatchThreadID` (global thread ID) and `GroupThreadID`/`GroupID` for coordinate mapping [S1, unofficial][S2].

**Parameters:**
*   Thread block size: $8 \times 8$ threads (64 threads per group) [S1, unofficial][S2].
*   Focal length $f$: Derived from $\alpha$.
*   Near plane width $v_{nearPlaneWidth}$: Set to $1$ [S1, unofficial].

**Steps:**

1.  **Thread Identification:**
    Determine the pixel coordinates $(x, y)$ from the thread ID.
    *   $x = \text{GroupID}_x \times 8 + \text{GroupThreadID}_x$
    *   $y = \text{GroupID}_y \times 8 + \text{GroupThreadID}_y$
    *   [S2]

2.  **Normalization to [0, 1]:**
    Scale the integer pixel coordinates to the range $[0, 1]$.
    $$ \vec{v}_{scaledPixelCoord} = \left( \frac{x}{W}, \frac{y}{H} \right) $$
    *   [S1, unofficial]

3.  **Centering to [-1, 1]:**
    Shift the coordinates so the center of the screen is $(0,0)$. The top-left pixel maps to $[-1, 1]$ and the bottom-right to $[1, -1]$.
    $$ \vec{uv} = \vec{v}_{scaledPixelCoord} \cdot 2 - \vec{1} $$
    Let $u = \vec{uv}_x$ and $v = \vec{uv}_y$.
    *   [S1, unofficial][S2]

4.  **Focal Length Calculation:**
    Calculate the focal length $f$ based on the field of view $\alpha$.
    $$ f = \frac{1}{\tan(\alpha / 2)} $$
    *   [S1, unofficial]

5.  **Ray Direction Calculation (Local Space):**
    Compute the initial unoriented ray direction $\vec{rd}^0$ in a local coordinate system where the camera looks along the positive Z-axis.
    $$ \vec{rd}^0 = \frac{[u, v, f]^T}{\sqrt{u^2 + v^2 + f^2}} $$
    *   [S2]
    
    *Note: Source [S1, unofficial] describes an equivalent vector subtraction method where the origin is $\vec{o}_{origin} = [0, 0, -f]^T$ and the direction is $\vec{p}_{direction} = [u, v, 0]^T - [0, 0, -f]^T = [u, v, f]^T$, which yields the same direction vector before normalization.*

6.  **Ray Origin Calculation:**
    The ray origin is fixed at the camera center in the local coordinate system.
    $$ \vec{o}_{origin} = [0, 0, -f]^T $$
    *   [S1, unofficial]

7.  **Orientation (Rotation):**
    Transform $\vec{rd}^0$ and $\vec{o}_{origin}$ into world space using rotation matrices defined by camera angles $\phi$ and $\theta$.
    $$ \vec{rd} = R(\phi, \theta) \cdot \vec{rd}^0 $$
    $$ \vec{o} = R(\phi, \theta) \cdot \vec{o}_{origin} $$
    *   [S2]
    *   [G] The specific rotation matrix $R(\phi, \theta)$ is not provided in the sources. Typically, this involves composing yaw and pitch rotations. The implementer must define the rotation convention (e.g., intrinsic vs. extrinsic axes).

**Pseudocode:**

```python
# Compute Shader Entry Point
# Inputs: DispatchThreadID (uint3), GroupID (uint3), GroupThreadID (uint3)
# Constants: W (int), H (int), alpha (float), phi (float), theta (float)

struct Ray {
    float3 origin;
    float3 direction;
};

Ray generate_ray(uint3 thread_id, uint3 group_id, uint3 group_thread_id) {
    // 1. Determine pixel coordinates
    uint x = group_id.x * 8 + group_thread_id.x;
    uint y = group_id.y * 8 + group_thread_id.y;

    // 2. Normalize to [0, 1]
    float u_scaled = (float)x / (float)W;
    float v_scaled = (float)y / (float)H;

    // 3. Center to [-1, 1]
    // Top-left: [-1, 1], Bottom-right: [1, -1]
    float u = u_scaled * 2.0 - 1.0;
    float v = v_scaled * 2.0 - 1.0;

    // 4. Calculate focal length
    float f = 1.0 / tan(alpha / 2.0);

    // 5. Calculate local direction vector [u, v, f]
    float3 rd_local_unnormalized = float3(u, v, f);
    
    // 6. Normalize direction
    float3 rd_local = normalize(rd_local_unnormalized);

    // 7. Set local origin
    float3 origin_local = float3(0.0, 0.0, -f);

    // 8. Apply rotation matrices for camera orientation
    // Note: Rotation matrix construction depends on specific convention (e.g., Z-Y-X Euler)
    // This step is marked [G] as the exact matrix composition is not in sources
    float3 rd_world = rotate(rd_local, phi, theta);
    float3 origin_world = rotate(origin_local, phi, theta);

    return Ray(origin_world, rd_world);
}
```

**Edge Cases and Pitfalls:**
*   **Division by Zero:** If $W$ or $H$ is zero, normalization fails. [G] Ensure $W, H > 0$.
*   **Precision:** Using integer arithmetic for thread ID calculation is safe. Floating point precision for $u, v$ depends on the window size. For very large resolutions, $u^2 + v^2 + f^2$ may suffer from precision loss if $f$ is very small or very large.
*   **Boundary Pixels:** The mapping ensures all pixels from $(0,0)$ to $(W-1, H-1)$ are covered. The $8 \times 8$ block size must divide $W$ and $H$ evenly, or the dispatch arguments must be calculated as $\lceil W/8 \rceil$ and $\lceil H/8 \rceil$, with threads checking bounds against $W, H$ to avoid out-of-bounds memory access in subsequent steps [S1, unofficial][S2].

## Subtopics

### [Compute Shader Voxel Raycasting with Corner Ray Interpolation](4215-compute-shader-voxel-raycasting-with-corner-ray-interpolatio.md)
Generates view rays by bilinearly interpolating four pre-computed world-space corner rays of the camera's view frustum. It avoids per-pixel matrix-vector multiplication for ray direction generation, relying instead on spatial interpolation of boundary vectors. Choose this when minimizing arithmetic intensity per pixel is critical and the camera is static or moves slowly.

## Operating characteristics
*   **Time Complexity:** $O(1)$ per pixel. The computation involves a constant number of arithmetic operations (normalization, trigonometry, normalization).
*   **Memory Complexity:** $O(1)$ per thread. No additional memory is allocated for ray generation.
*   **Performance:** Highly parallelizable. The $8 \times 8$ thread block size aligns with typical GPU warp/wavefront sizes (32 or 64 threads), ensuring efficient SIMD execution [S2].
*   **Strengths:** Simple, deterministic, and low overhead. Suitable for real-time applications where ray generation is a small fraction of the total rendering cost.
*   **Limitations:** Assumes a pinhole camera model. Does not account for lens effects (bokeh, distortion) without extension. Requires explicit rotation handling for non-axis-aligned cameras [S2].

## Background
This method originates from implementations of GPU-based raycasting and raymarching, specifically those utilizing compute shaders for general-purpose rendering tasks. It is detailed in works on CUDA-based distance field raymarching [S2] and voxel raycasting implementations [S1, unofficial][S2]. The approach of mapping thread IDs to pixel coordinates and generating rays via a pinhole model is a standard technique in GPU ray tracing pipelines.
