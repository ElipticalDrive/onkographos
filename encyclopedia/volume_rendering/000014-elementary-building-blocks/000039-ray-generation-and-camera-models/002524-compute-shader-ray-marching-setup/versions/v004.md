# Compute Shader Ray Marching Setup

Also called: Ray Marching Setup

## Overview
This method establishes the computational pipeline for rendering volumetric smoke by launching a compute shader that marches rays through a voxel grid, accumulating density which is then composited over a camera feed [S1, unofficial]. It differs from standard ray generation by explicitly handling the resolution scaling (downsampling) and the two-stage marching logic (empty-space skipping vs. density accumulation) within the setup phase, deferring the actual ray direction calculation to the generation kernel [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** Screen resolution (`Screen.width`, `Screen.height`), camera transform (`cam.transform.position`), inverse projection matrix (`_invProjectionMatrix`), camera-to-world matrix (`_CamToWorldMatrix`), maximum ray length (`_RayMaxLength`, default 50.0), density smoothing factor (`smoothing`), density multiplier (`densityMUlt`), and a pre-generated Worley noise texture [S1, unofficial].
*   **Outputs:** A `RenderTexture` (`smokeTexture`) with format `ARGB64`, linear color space, and random write access, containing the accumulated smoke density [S1, unofficial].

**Data Structures:**
*   **Voxel Grid:** Stored in a `ComputeBuffer`. 3D coordinates $(x, y, z)$ are flattened to linear indices using $index = z \cdot (X \cdot Y) + y \cdot X + x$, where $X, Y$ are grid dimensions. Out-of-bounds access returns $-1$ [S1, unofficial].
*   **Noise Texture:** A `RWTexture2D` storing Worley noise values, sampled per pixel [S1, unofficial].
*   **Result Texture:** `RWTexture2D<float4> _ResultTexture` with `ARGB64` format [S1, unofficial].

**Steps:**
1.  **Calculate Render Resolution:** Compute the target width and height for the compute shader dispatch by dividing the screen dimensions by 8 and rounding up:
    $$
    width = \lceil \frac{Screen.width}{8} \rceil, \quad height = \lceil \frac{Screen.height}{8} \rceil
    $$
    [S1, unofficial]
2.  **Initialize Output Texture:** Create a `RenderTexture` with the calculated dimensions, format `ARGB64`, and linear color space [S1, unofficial].
3.  **Configure Shader Matrices:** Pass `_CamToWorldMatrix` and `_invProjectionMatrix` to the compute shader [S1, unofficial].
4.  **Set Camera Position:** Pass the camera's world-space position (`camPosWS`) to the shader [S1, unofficial].
5.  **Dispatch Compute Shader:** Launch the ray marching kernel with thread groups sized according to the calculated resolution:
    $$
    dispatch(kernelIndex, \frac{width}{8}, \frac{height}{8}, 1)
    $$
    [S1, unofficial]

**Pseudocode (Setup Phase):**
```python
# 1. Calculate Resolution
width = ceil(Screen.width / 8)
height = ceil(Screen.height / 8)

# 2. Create Output Texture
smokeTexture = RenderTexture(width, height, 0, RenderTextureFormat.ARGB64, RenderTextureReadWrite.Linear)

# 3. Set Shader Parameters
shader.SetMatrix("_CamToWorldMatrix", cam.transform.worldToLocalMatrix.inverse)
shader.SetMatrix("_invProjectionMatrix", camera.projectionMatrix.inverse)
shader.SetVector("_CamPosWS", cam.transform.position)
shader.SetFloat("_RayMaxLength", 50.0)
shader.SetFloat("smoothing", smoothing_factor)
shader.SetFloat("densityMUlt", density_multiplier)

# 4. Dispatch Kernel
# Assuming kernel index 0 and thread group size 8x8x1
shader.Dispatch(0, width // 8, height // 8, 1)
```

**Edge Cases and Pitfalls:**
*   **Noise Sampling Bug:** The reference implementation samples the noise texture using screen-space UV coordinates (`uv`) rather than world-space positions. This causes the noise pattern to remain fixed to the screen rather than the volume, creating a "swimming" artifact as the camera moves [S1, unofficial]. The correct approach is to sample noise using the 3D world position of the ray sample point [S1, unofficial].
*   **Volume Bounds:** The accumulation loop (Stage Two) runs for a fixed number of steps (e.g., 40) regardless of whether the ray has exited the voxel grid, potentially causing smoke to bleed outside the intended volume bounds [S1, unofficial].
*   **Color Reassignment:** In the debug visualization fragment shader, the color variable `col` is reassigned every iteration, which is inefficient and incorrect for accumulation logic [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The setup phase is $O(1)$ relative to resolution, but the dispatch scales with $\frac{W \cdot H}{64}$ thread groups. The marching cost depends on the density of the volume; empty-space skipping reduces cost for rays outside the volume [S1, unofficial].
*   **Memory Complexity:** Requires storage for the voxel grid (`ComputeBuffer`), the noise texture (`RWTexture2D`), and the output render texture (`ARGB64`, 32 bits per pixel) [S1, unofficial].
*   **Strengths:** Efficiently handles large volumes by skipping empty space; uses procedural noise to avoid texture memory overhead for the density field [S1, unofficial].
*   **Limitations:** The reference implementation has a significant bug where noise is sampled in screen space, breaking spatial coherence; fixed-step accumulation ignores volume boundaries [S1, unofficial].
*   **When to use:** Suitable for real-time volumetric effects where performance is critical and the volume is sparse or well-contained.
*   **When not to use:** Not suitable for high-fidelity volumetrics requiring accurate 3D noise sampling or precise boundary adherence without modification [S1, unofficial].

## Background
This method is derived from a GitHub repository by Schokolasbotter, which demonstrates a real-time volumetric smoke raymarching implementation in Unity using compute shaders [S1, unofficial]. It combines voxelization, procedural Worley noise generation, and a two-stage ray marcher to achieve real-time performance.
