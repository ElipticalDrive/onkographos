# Compute Shader Ray Marching Setup

Also called: Ray Marching Setup

## Overview
This method initializes the compute shader environment for volumetric ray marching by generating camera rays per pixel and configuring the necessary data structures for density accumulation. It differs from standard ray generation by explicitly handling the dispatch dimensions relative to screen resolution (often downsampled) and managing the specific render texture formats required for high-precision density storage. It serves as the foundational setup for the ray marching kernel, bridging the gap between camera parameters and the voxel grid traversal logic.

## How it works
**Inputs:**
- Screen resolution ($W_{screen}, H_{screen}$).
- Camera matrices: World-to-View inverse (or View-to-World) and Projection inverse ($\mathbf{M}_{invProj}$).
- Camera position in world space ($\mathbf{p}_{cam}$).
- Voxel grid occupancy data (ComputeBuffer).
- Noise texture (RWTexture2D or Texture2D).

**Outputs:**
- A render texture (e.g., `smokeTexture`) storing accumulated density or color.
- Dispatch parameters for the compute shader.

**Data Structures:**
1. **Render Texture (`smokeTexture`)**:
   - Dimensions: $W_{tex} = \lceil W_{screen} / 8 \rceil$, $H_{tex} = \lceil H_{screen} / 8 \rceil$ [S1, unofficial].
   - Format: `ARGB64` (32-bit float per channel) to support high dynamic range density values [S1, unofficial].
   - Usage: Random write (`RWTexture2D<float4>`).
2. **Shader Constants**:
   - `_RayMaxLength`: Maximum distance to march. Default: $50.0$ [S1, unofficial].
   - `smoothing`: Density smoothing factor [S1, unofficial].
   - `densityMult`: Density multiplier [S1, unofficial].

**Steps:**
1. **Calculate Dispatch Dimensions**:
   Compute the number of thread groups based on the screen resolution divided by a downscale factor (typically 8).
   $$ W_{dispatch} = \lceil W_{screen} / 8 \rceil $$
   $$ H_{dispatch} = \lceil H_{screen} / 8 \rceil $$
   [S1, unofficial].

2. **Configure Render Texture**:
   Allocate a `RenderTexture` with width $W_{tex}$, height $H_{tex}$, 0 depth buffer, `ARGB64` format, and linear color space [S1, unofficial].

3. **Set Shader Matrices**:
   Pass the inverse projection matrix ($\mathbf{M}_{invProj}$) and the camera-to-world matrix ($\mathbf{M}_{camToWorld}$) to the compute shader [S1, unofficial].

4. **Set Camera Position**:
   Pass the camera's world-space position ($\mathbf{p}_{cam}$) to the shader [S1, unofficial].

5. **Dispatch Compute Shader**:
   Launch the ray marching kernel with dimensions $(W_{dispatch}, H_{dispatch}, 1)$ [S1, unofficial].

**Pseudocode (C# Setup Logic):**
```python
# Calculate dimensions
width = ceil(screen_width / 8)
height = ceil(screen_height / 8)

# Create render texture
smoke_texture = RenderTexture(width, height, 0, RenderTextureFormat.ARGB64, RenderTextureReadWrite.Linear)

# Set shader properties
shader.set_matrix("_invProjectionMatrix", camera.inverse_projection_matrix)
shader.set_matrix("_CamToWorldMatrix", camera.world_to_world_matrix) # Identity or actual transform
shader.set_float("_RayMaxLength", 50.0)
shader.set_float("smoothing", 0.5) # Example default
shader.set_float("densityMult", 1.0) # Example default

# Dispatch
shader.dispatch(kernel_index, width, height, 1)
```

**Ray Reconstruction (Inside Compute Shader):**
Each thread corresponds to a pixel. It reconstructs the world-space ray:
1. **UV to NDC**:
   $$ u = \frac{thread\_id.x}{W_{tex}} $$
   $$ v = \frac{thread\_id.y}{H_{tex}} $$
   $$ \mathbf{ndc} = (2u - 1, 2v - 1, 0, 1) $$
   [S1, unofficial].

2. **View Space Direction**:
   $$ \mathbf{view\_dir} = \mathbf{M}_{invProj} \times \mathbf{ndc} $$
   $$ \mathbf{view\_dir} = \text{normalize}(\mathbf{view\_dir}.xyz) $$
   [S1, unofficial].

3. **World Space Direction**:
   $$ \mathbf{ray\_vec} = \text{normalize}(\mathbf{M}_{camToWorld} \times (0, \mathbf{view\_dir}.xyz, 0).xyz) $$
   [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Noise Sampling Bug**: If the noise texture is sampled using screen-space UV coordinates (`uv`) instead of world-space positions, the noise pattern will appear pinned to the screen and "swim" as the camera moves, rather than being attached to the volume [S1, unofficial]. The fix is to sample noise using the 3D world position of the ray sample [S1, unofficial].
- **Volume Bounds**: The accumulation loop may ignore volume bounds, running a fixed number of steps (e.g., 40) even after the ray exits the voxel grid, causing smoke to bleed [S1, unofficial].
- **Precision**: Using `ARGB64` is critical for density accumulation to prevent banding and overflow during integration [S1, unofficial].

## Subtopics

## Operating characteristics
- **Time Complexity**: $O(W \times H \times N)$, where $W, H$ are the dispatch dimensions and $N$ is the number of march steps. The two-stage march (empty-space skipping) reduces $N$ for rays that do not intersect the volume, but worst-case remains linear with resolution and depth.
- **Memory Complexity**: $O(W \times H)$ for the output texture, plus $O(V)$ for the voxel grid and noise texture, where $V$ is the voxel count.
- **Performance**: The downscale factor (8x) significantly reduces pixel shader/compute load, making real-time rendering feasible on consumer hardware. The `ARGB64` format increases memory bandwidth usage compared to 8-bit formats.
- **Strengths**: Flexible camera setup, efficient empty-space skipping, high-precision output.
- **Limitations**: Screen-space noise sampling bug if not implemented correctly; fixed-step accumulation can waste cycles outside the volume.

## Background
This setup is derived from practical implementations of GPU-based volumetric rendering, specifically those using Unity's Compute Shader infrastructure. The specific pipeline (Voxeliser → CS_Noise → CSRaytrace → Combiner) and the associated bugs/fixes are documented in the unofficial repository by Schokolasbotter [S1, unofficial].
