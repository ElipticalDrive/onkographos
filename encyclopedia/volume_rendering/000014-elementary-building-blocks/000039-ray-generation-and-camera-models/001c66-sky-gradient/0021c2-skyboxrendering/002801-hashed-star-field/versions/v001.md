# Hashed Star Field

Also called: Procedural Stars

## Overview
A procedural star field generated by hashing sky directions into cells, with a sparse probability of holding a star, jittered position within the cell, and twinkle animation [S1, unofficial]. It provides a deterministic, low-memory background for raymarched scenes without requiring external texture assets [S1, unofficial].

## How it works
**Inputs and Outputs:**
- Input: Ray direction `rd` (normalized), time uniform `uTime` (seconds).
- Output: Star brightness `vec3` (typically white or tinted).

**Data Structures:**
- No persistent data structures. The method is stateless and computes star presence/position on-the-fly using integer hashing.

**Steps:**
1. **Horizon Culling:** If the ray's vertical component `rd.y` is less than 0.04, return black (no stars below the horizon) [S1, unofficial].
2. **Projection:** Calculate a 2D screen-space-like coordinate `sp` from the ray direction to map the sphere to a plane for hashing:
   $$ sp = \left( \frac{rd.xz}{rd.y + 0.35} \right) \times 42.0 $$
   Here, `rd.xz` is the vector `(rd.x, rd.z)` [S1, unofficial].
3. **Cell Identification:** Determine the integer grid cell containing the ray:
   $$ cell = \lfloor sp \rfloor $$
4. **Hashing:** Hash the cell coordinates to produce a unique integer `hs`. The specific hash function is not detailed in the source, but it must be deterministic and produce a high-entropy integer [S1, unofficial].
5. **Star Presence Check:** Extract the first byte of the hash, `hByte(hs, 0)`. If this value (normalized to 0.0–1.0 range, i.e., `hByte(hs, 0) / 255.0`) is greater than or equal to 0.985, return black. This results in approximately 1.5% of cells containing a star [S1, unofficial].
6. **Star Position:** Calculate the jittered position of the star within the cell using subsequent bytes of the hash:
   $$ starPos = \left( \frac{hByte(hs, 8)}{255.0}, \frac{hByte(hs, 16)}{255.0} \right) $$
   This maps the star to a point in the unit square `[0, 1]` within the cell [S1, unofficial].
7. **Distance Calculation:** Calculate the distance from the ray's projected position to the star's jittered position. Use `fract(sp)` to get the fractional part of the projected coordinate within the cell. Apply `smoothstep` to create a soft falloff:
   $$ dot = \text{smoothstep}(0.14, 0.0, \| \text{fract}(sp) - starPos \|) $$
   This creates a star with a radius of approximately 0.14 units in the projected space [S1, unofficial].
8. **Twinkle:** Calculate a time-varying brightness factor using the hash to ensure each star twinkles independently:
   $$ twinkle = 0.7 + 0.3 \times \sin(uTime \times 2.0 + (hs \ \& \ 63)) $$
   The bitwise AND with 63 extracts the lower 6 bits of the hash, providing a unique phase offset [S1, unofficial].
9. **Final Compositing:** Combine the distance falloff, twinkle, and a horizon fade-out:
   $$ \text{result} = vec3(dot) \times twinkle \times 0.7 \times \text{smoothstep}(0.0, 0.25, rd.y) $$
   The final brightness is scaled by 0.7 and fades out smoothly as `rd.y` approaches 0 [S1, unofficial].

**Pseudocode:**
```python
def hashed_star_field(rd: vec3, uTime: float) -> vec3:
    # 1. Horizon culling
    if rd.y < 0.04:
        return vec3(0.0)

    # 2. Projection
    sp = vec2(rd.x, rd.z) / (rd.y + 0.35) * 42.0

    # 3. Cell identification
    cell = floor(sp)

    # 4. Hashing
    # Note: The specific hash function is not defined in the source.
    # A common choice for integer hashing is a multiplicative hash or
    # a bit-mixing function. We assume a deterministic hash function
    # that takes a vec2 and returns an integer.
    hs = hash_integer(cell)

    # 5. Star presence check
    # hByte(hs, 0) extracts the most significant byte or a specific byte.
    # Assuming standard byte extraction where value is 0-255.
    # The source uses hByte(hs, 0) >= 0.985, implying normalization.
    byte0 = (hs >> 24) & 0xFF  # Example extraction, adjust based on actual hash implementation
    if byte0 / 255.0 >= 0.985:
        return vec3(0.0)

    # 6. Star position
    byte8 = (hs >> 16) & 0xFF
    byte16 = (hs >> 8) & 0xFF
    starPos = vec2(byte8 / 255.0, byte16 / 255.0)

    # 7. Distance calculation
    frac_sp = fract(sp)
    dist = length(frac_sp - starPos)
    dot = smoothstep(0.14, 0.0, dist)

    # 8. Twinkle
    # hs & 63 extracts lower 6 bits
    phase = hs & 63
    twinkle = 0.7 + 0.3 * sin(uTime * 2.0 + float(phase))

    # 9. Final compositing
    horizon_fade = smoothstep(0.0, 0.25, rd.y)
    return vec3(dot) * twinkle * 0.7 * horizon_fade

# Helper hash function (example implementation, not from source)
def hash_integer(v: vec2) -> int:
    # Simple integer hash for demonstration
    p = vec2(239.0, 113.0)
    h = int(dot(v, p))
    h = (h ^ (h >> 16)) * 0x85ebca6b
    h = (h ^ (h >> 13)) * 0xc2b2ae35
    h = h ^ (h >> 16)
    return h
```

**Parameters:**
- **Star Density:** ~1.5% of cells hold a star (threshold 0.985 on normalized byte) [S1, unofficial].
- **Star Size:** Soft radius of 0.14 in projected space [S1, unofficial].
- **Twinkle Frequency:** `uTime * 2.0` [S1, unofficial].
- **Horizon Cutoff:** `rd.y < 0.04` [S1, unofficial].
- **Horizon Fade:** `smoothstep(0.0, 0.25, rd.y)` [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Precision:** The hash function must be deterministic and consistent across platforms. [G] Standard integer hashing may vary; use a fixed, portable hash implementation.
- **Boundaries:** The projection formula `rd.xz / (rd.y + 0.35)` avoids division by zero since `rd.y` is clamped or checked. The constant `0.35` prevents singularity at the zenith.
- **Degenerate Input:** Rays with `rd.y <= 0` are handled by the horizon culling step.

## Subtopics

### Star/Point Layer & Transform Stack
An additive high-frequency point layer for stars, supporting procedural hash-fields or catalog buffers, with a non-destructive transform stack and an aggregate-to-ambient lighting operator [S2, unofficial]. It rasterizes as sharp points for appearance but integrates to smooth ambient for lighting, demonstrating the 'same data, two operators' principle [S2, unofficial].

**Definition:**
Supports two source types: procedural hash-field (default, cheap, no assets) or a catalog buffer containing `{dir(RA/Dec), magnitude, B–V color, parallax, proper-motion}` [S2, unofficial].

**Steps:**
1. **Source Generation:** Use a procedural hash-field or catalog buffer [S2, unofficial].
2. **Transform Stack:** Apply an ordered set of nodes over `(dir, mag, color)` in a compute pre-pass on the immutable source buffer. Nodes include: Rotate, Precess, SwirlWarp(noise), Lens(center, strength), MagnitudeCurve (= limiting-magnitude / light-pollution), ColorLUT, Cull(class/distance), ProperMotionScrub(t) [S2, unofficial].
3. **Optional 3D Reprojection:** Support observer relocation using parallax-to-distance conversion [S2, unofficial].
4. **Aggregate-to-Ambient:** Reduce the point layer to feed the diffuse channel of the lighting system (Seam B) [S2, unofficial].
5. **Masked Distortion:** Support regional distortion by reusing importance-painting [S2, unofficial].

**Parameters:**
- **Noise:** Use deterministic seeded noise only [S2, unofficial].

**Comparison:**
The star buffer rasterizes as sharp points for appearance but integrates to smooth ambient for lighting, demonstrating the 'same data, two operators' principle [S2, unofficial].

## Operating characteristics
- **Time Complexity:** O(1) per ray, as it involves a constant number of arithmetic operations and a hash lookup.
- **Memory Complexity:** O(1), no persistent data structures are required for the basic procedural version.
- **Performance:** Extremely fast, suitable for real-time raymarching. The source is part of a sphere-traced raymarcher, implying it is executed per pixel per ray [S1, unofficial].
- **Strengths:** Deterministic, low memory footprint, no external assets required, supports twinkle animation.
- **Limitations:** Limited to a simple point distribution; cannot represent complex star catalogs or realistic spectral variations without the extended transform stack variant [S2, unofficial].
- **When to Use:** When a simple, procedural, animated starfield is needed for a raymarched scene without the overhead of texture lookups or large data structures.
- **When Not to Use:** When high-fidelity astronomical accuracy, catalog-based stars, or complex lighting integration is required.

## Background
The method originates from the "neon-raymarcher" project by PIGJET, which implements a procedural synthwave neon city using sphere-tracing [S1, unofficial]. It is used as a background element in this raymarched scene. The extended variant with transform stacks is part of a broader Spherical-Gaussian sky and authorable environment lighting system [S2, unofficial].
