# Camera Pose Transformation

Also called: Camera Offset and Rotation, Camera Pose Representation, Pose Transformation, RotateX

## Overview
Camera Pose Transformation applies geometric operations—specifically translation and rotation—to align camera coordinates with world space or to normalize a set of poses. It solves the problem of mapping points from a local camera frame to a global scene frame, or adjusting a scene's coordinate system to match a specific camera configuration. It differs from [View Matrix Construction](1644-view-matrix-construction.md) by focusing on the explicit application of offset and rotational primitives rather than constructing a full 4x4 view matrix from basis vectors, and from [Average Pose Calculation](1645-average-pose-calculation.md) by operating on individual poses rather than computing statistical averages.

## How it works
**Inputs and Outputs:**
- Input: A point $p \in \mathbb{R}^3$ or a pose $P \in \mathbb{R}^{3 \times 4}$; parameters for transformation (offset vector $t$, rotation angle $\theta$, axis).
- Output: Transformed point $p'$ or pose $P'$.

**Data Structures:**
- Point $p$: A 3-element vector $[x, y, z]^T$.
- Pose $P$: A $3 \times 4$ matrix representing the camera-to-world transformation, defined as $P = [R_p \ t_p]$ where $R_p \in SO(3)$ and $t_p \in \mathbb{R}^3$ [S1].

**Steps:**
1. **Translation (Offset):** Apply a linear offset to the point or translation vector. For a point $p$, the offset is $p_{offset} = p + t_{offset}$ [S3, unofficial]. In the context of LLFF conversion, the translation vector $t$ from world-to-camera format is converted to camera-to-world format $t'$ using the rotation matrix $R$: $t' = -R^T \cdot t$ [S5].
2. **Rotation:** Apply a rotation around a specified axis. For a rotation around the Y-axis by angle $\theta$, the $y$ and $z$ components are transformed using the 2D rotation matrix:
   $$
   \begin{bmatrix} y' \\ z' \end{bmatrix} = \begin{bmatrix} \cos \theta & \sin \theta \\ -\sin \theta & \cos \theta \end{bmatrix} \begin{bmatrix} y \\ z \end{bmatrix}
   $$
   Specifically, $y' = \cos(\theta)y + \sin(\theta)z$ and $z' = -\sin(\theta)y + \cos(\theta)z$ [S3, unofficial].
   For general SE(3) poses, the rotation $R$ is an element of $SO(3)$ [S1].

**Formulas:**
- SE(3) Pose Representation: $SE(3) = \left\{ \begin{bmatrix} R & t \\ 0^T & 1 \end{bmatrix} \in \mathbb{R}^{4 \times 4} \mid R \in SO(3), t \in \mathbb{R}^3 \right\}$ [S1].
- Reduced Pose: $P = [R_p \ t_p] \in \mathbb{R}^{3 \times 4}$ [S1].
- LLFF Translation Conversion: $t' = -R^T \cdot t$ [S5].

**Parameters:**
- `angle`: Float representing the rotation angle in radians [S2, unofficial].
- `offset`: Vector $[0, -1, -2.2]$ used in specific scene centering examples [S3, unofficial].

**Edge Cases and Pitfalls:**
- Coordinate System Consistency: Ensure the rotation direction (sign of sine terms) matches the coordinate system handedness (left-handed vs. right-handed) [S3, unofficial][S5].
- Numerical Stability: When converting between world-to-camera and camera-to-world, ensure $R$ is orthogonal so $R^{-1} = R^T$ holds [S5].

**Pseudocode:**
```python
import math

def rotate_y(p: list[float], angle: float) -> list[float]:
    """
    Rotates a 3D point p around the Y-axis by the given angle.
    Based on [S3, unofficial].
    """
    x, y, z = p
    cos_a = math.cos(angle)
    sin_a = math.sin(angle)
    # y' = cos(a)*y + sin(a)*z
    # z' = -sin(a)*y + cos(a)*z
    y_new = cos_a * y + sin_a * z
    z_new = -sin_a * y + cos_a * z
    return [x, y_new, z_new]

def transform_pose_llff(r: list[list[float]], t: list[float]) -> list[list[float]]:
    """
    Converts a COLMAP world-to-camera pose (R, t) to LLFF camera-to-world format.
    Returns the 3x4 matrix [R' | t'].
    Based on [S5].
    """
    # R is 3x3, t is 3x1
    # t' = -R^T * t
    # R' = R^T
    
    # Compute R_transpose
    r_t = [[r[j][i] for j in range(3)] for i in range(3)]
    
    # Compute t_prime = -R^T * t
    t_prime = [0.0, 0.0, 0.0]
    for i in range(3):
        sum_val = 0.0
        for j in range(3):
            sum_val += r_t[i][j] * t[j]
        t_prime[i] = -sum_val
        
    # Construct 3x4 matrix
    pose = []
    for i in range(3):
        row = r_t[i] + [t_prime[i]]
        pose.append(row)
        
    return pose

def apply_offset(p: list[float], offset: list[float]) -> list[float]:
    """
    Applies a translation offset to a point.
    Based on [S3, unofficial].
    """
    return [p[i] + offset[i] for i in range(3)]
```

## Subtopics

### [Pose Recentering](1786-pose-recentering.md)
Pose Recentering transforms a set of camera-to-world (c2w) poses so that their average pose becomes the identity transformation, effectively centering the scene at the origin and aligning the principal axes. This normalization is essential for Neural Radiance Fields (NeRF) and other volume rendering techniques that assume the scene occupies a bounded region (typically $[-1, 1]^3$) and for ensuring numerical stability during optimization. It differs from [Rotation Transformation](2279-rotation-transformation.md) and [Translation Transformation](2281-translation-transformation.md) by simultaneously handling both positional centering and rotational alignment in a single coherent step, whereas those siblings handle only one aspect. [Pose Recentering](1786-pose-recentering.md)

### [Rotation Transformation](2279-rotation-transformation.md)
Rotation Transformation is a geometric primitive that rotates a point, vector, or shape around a specified coordinate axis (X, Y, or Z) by a given angle. In the context of volume rendering and camera modeling, it constructs the rotational component of the view or model matrix, enabling the alignment of the camera or volume data with the world space. It sets itself apart from [Translation Transformation](2281-translation-transformation.md) by altering orientation rather than position, and from [Rigid Body Transformation (SE3)](11475-rigid-body-transformation-se3.md) by isolating the rotational degrees of freedom [G]. Unlike [Quaternion Rotation](2302-quaternion-rotation.md), it operates directly on Cartesian coordinates using trigonometric functions, which is computationally simpler for single-axis rotations but lacks the singularity-free interpolation properties of quaternions for complex orientations [G]. [Rotation Transformation](2279-rotation-transformation.md)

### [Translation Transformation](2281-translation-transformation.md)
A geometric transformation that moves a shape or point by a given vector. It solves the problem of shifting spatial coordinates without altering orientation or scale. It differs from [Rotation Transformation](2279-rotation-transformation.md) by applying no angular change, and from [Rigid Body Transformation (SE3)](11475-rigid-body-transformation-se3.md) by excluding rotational components. [Translation Transformation](2281-translation-transformation.md)

### [C-Arm to Camera Parameters Conversion](2589-c-arm-to-camera-parameters-conversion.md)
This method converts C-arm geometric parameters (Source-to-Image Distance, AP angle, lateral angle, center point, and table translation) into a camera pose defined by position, look-at point, and up vector in RAS coordinates. [C-Arm to Camera Parameters Conversion](2589-c-arm-to-camera-parameters-conversion.md)

### [Camera Matrix Decomposition](3164-camera-matrix-decomposition.md)
Decomposes a 3×4 projection matrix into an intrinsic matrix $K$, a rotation matrix $R$, and a translation vector $t$. It separates the camera's internal optical properties from its external physical pose. [Camera Matrix Decomposition](3164-camera-matrix-decomposition.md)

### [CameraMover](8734-cameramover.md)
CameraMover is a utility class for constructing and incrementally updating a 4x4 extrinsic camera transformation matrix ($M_{ext}$) using sequential translations and rotations. It solves the problem of maintaining a consistent camera pose in world space by applying incremental changes to position and orientation, which are then used to generate world-space ray directions for volume rendering. It differs from sibling methods like [RotateY](1720-rotatey.md) or [Translation Transformation](2281-translation-transformation.md) by encapsulating the entire state management and matrix composition logic into a single class that supports both axis-aligned incremental moves and aiming at specific world positions. [CameraMover](8734-cameramover.md)

### [Rigid Body Transformation (SE3)](11475-rigid-body-transformation-se3.md)
Rigid Body Transformation (SE3) maps 3D points and vectors between coordinate systems (e.g., camera to world) without altering their intrinsic geometry, preserving distances and angles. It is distinguished from its siblings by its foundational role as the mathematical group $SE(3)$ underlying all pose adjustments; while [Rotation Transformation](2279-rotation-transformation.md) and [Translation Transformation](2281-translation-transformation.md) handle specific components, SE3 combines them into a single invertible operation, and [Pose Recentering](1786-pose-recentering.md) uses it to shift the origin. [Rigid Body Transformation (SE3)](11475-rigid-body-transformation-se3.md)

### [Camera-to-Object Space Transformation & MVP Computation](12391-camera-to-object-space-transformation-mvp-computation.md)
This method precomputes the Model-View-Projection (MVP) matrix and transforms camera parameters into object space to support shader-based rendering, specifically enabling box or mesh overlays in volume visualization. It distinguishes itself by explicitly handling the synchronization of projection types (perspective vs. orthographic) via shader defines and providing the inverse-transformed camera direction and position for local-space calculations. It builds on [Camera Pose Transformation](1672-camera-pose-transformation.md) by consuming the pose data to construct the final transformation chain. [Camera-to-Object Space Transformation & MVP Computation](12391-camera-to-object-space-transformation-mvp-computation.md)

### Continuous Camera Motion Modeling
Continuous Camera Motion Modeling is a method to model camera motion as continuous time-dependent angular velocity $\omega(t)$ and linear velocity $v(t)$ instead of discrete camera-to-world poses, enabling the handling of large motions by integrating relative motions over time [S4]. It predicts $\omega(t)$ and $v(t)$ at time $t$ using an MLP $\phi_v$: $\omega(t), v(t) = \phi_v(t)$ [S4]. The camera transformation $P$ between any two frames is obtained by integrating these velocities. The relationship is defined by the differential equations: $dR/dt = [\omega(t)]_\times R$ and $dt/dt = v(t)$, where $[\omega(t)]_\times$ is the skew-symmetric matrix of $\omega(t)$ [S4]. Parameters $\omega(t), v(t) \in \mathbb{R}^3$ are the angular and linear velocity vectors [S4]. [Continuous Camera Motion Modeling](1672-camera-pose-transformation.md#continuous-camera-motion-modeling)

### LLFF Camera Pose Conversion
LLFF Camera Pose Conversion is a procedure to convert COLMAP's world-to-camera pose parameters into the camera-to-world transformation matrix required by the LLFF dataset format [S5]. The translation vector $t$ in world-to-camera format is converted to camera-to-world format $t'$ using the transpose of the rotation matrix $R$: $t' = -R^T \cdot t$ [S5]. The LLFF dataset components include image sequences, camera intrinsic parameters, and camera extrinsic parameters (rotation matrix $R^T$ and translation vector $t'$) [S5]. [LLFF Camera Pose Conversion](1672-camera-pose-transformation.md#llff-camera-pose-conversion)

## Operating characteristics
- **Time Complexity:** $O(1)$ for single point/pose transformation. $O(N)$ for processing $N$ poses.
- **Memory Complexity:** $O(1)$ auxiliary space for single transformation. $O(N)$ to store $N$ poses.
- **Strengths:** Simple, computationally inexpensive, numerically stable for small transformations.
- **Limitations:** Accumulated error in sequential transformations; not suitable for large continuous motion without integration (see Continuous Camera Motion Modeling).
- **When to use:** Standard coordinate frame alignment, dataset format conversion (LLFF), initial scene centering.
- **When not to use:** Large continuous motion modeling (use Continuous Camera Motion Modeling), complex interpolation (use Quaternions).

## Background
Camera Pose Transformation is a fundamental operation in computer graphics and computer vision, rooted in the mathematical representation of rigid body motions via the Special Euclidean group $SE(3)$ [S1]. The representation of poses as $3 \times 4$ matrices or $4 \times 4$ homogeneous matrices is standard in NeRF literature [S1, S5]. The specific application of offset and rotation primitives for scene centering and coordinate alignment is widely used in raymarching and SDF rendering tutorials [S3, S2, unofficial]. The conversion between COLMAP and LLFF formats is a standard preprocessing step for NeRF training on real-world datasets [S5].
