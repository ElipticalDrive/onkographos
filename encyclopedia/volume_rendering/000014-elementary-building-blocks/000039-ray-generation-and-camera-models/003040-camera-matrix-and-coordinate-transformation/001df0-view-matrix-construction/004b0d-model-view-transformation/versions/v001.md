# Model-View Transformation

Also called: Model Matrix Construction, Object Transformation, View Vector Calculation, updateViewVector

## Overview
The Model-View Transformation computes the relative orientation and position of a scene object with respect to the camera, specifically yielding the normalized view direction vector required for lighting and ray generation calculations. It differs from the sibling [View Matrix Construction](1644-view-matrix-construction.md) by focusing on the specific extraction of the view vector from the composite transformation rather than constructing the full camera-to-world matrix for projection purposes.

## How it works
**Inputs:**
1.  `camera.matrixWorldInverse`: A 4x4 matrix representing the inverse of the camera's world transformation.
2.  `mesh.matrixWorld`: A 4x4 matrix representing the world transformation of the target object (mesh).

**Outputs:**
1.  `modelViewMatrix`: A 4x4 matrix representing the transformation from the object's local space to the camera's view space.
2.  `viewVector`: A normalized 3D vector pointing from the camera towards the object (negative Z-axis of the model-view matrix).

**Data Structures:**
*   **Matrix**: 4x4 column-major or row-major array of 16 floating-point values. The sources use a flat array `elements` indexed 0–15.
    *   Indices 2, 6, 10 correspond to the Z-axis components of the first three columns (basis vectors).
*   **Vector**: 3D vector $(x, y, z)$.

**Steps:**
1.  Initialize `modelViewMatrix` to the identity matrix $I$.
2.  Compute the product of the camera's inverse world matrix and the mesh's world matrix:
    $$ M_{mv} = M_{cam}^{-1} \times M_{mesh} $$
    Where $M_{cam}^{-1}$ is `camera.matrixWorldInverse` and $M_{mesh}$ is `mesh.matrixWorld` [S2, unofficial].
3.  Extract the Z-axis basis vector components from $M_{mv}$. In the source implementation, these are located at indices 2, 6, and 10 of the flat matrix array [S2, unofficial].
4.  Negate these components to obtain the direction from the camera to the object:
    $$ v_x = -M_{mv}[2] $$
    $$ v_y = -M_{mv}[6] $$
    $$ v_z = -M_{mv}[10] $$
5.  Normalize the resulting vector $(v_x, v_y, v_z)$ to unit length [S2, unofficial].

**Formulas:**
The transformation matrices for translation, rotation, and scaling are defined as follows [S1, unofficial]:

Translation by $(x, y, z)$:
$$ T = \begin{pmatrix} 1 & 0 & 0 & -x \\ 0 & 1 & 0 & -y \\ 0 & 0 & 1 & -z \\ 0 & 0 & 0 & 1 \end{pmatrix} $$

Rotation of $\theta$ degrees about a unit vector axis $(x, y, z)$ (specifically about the X-axis in the source example):
$$ R = \begin{pmatrix} 1 & 0 & 0 & 0 \\ 0 & \cos(\theta) & -\sin(\theta) & 0 \\ 0 & \sin(\theta) & \cos(\theta) & 0 \\ 0 & 0 & 0 & 1 \end{pmatrix} $$

Scaling by $(a, b, c)$:
$$ S = \begin{pmatrix} a & 0 & 0 & 0 \\ 0 & b & 0 & 0 \\ 0 & 0 & c & 0 \\ 0 & 0 & 0 & 1 \end{pmatrix} $$

**Pseudocode:**
```python
def compute_model_view_transformation(camera_matrix_world_inverse, mesh_matrix_world):
    """
    Computes the model-view matrix and the normalized view vector.
    
    Args:
        camera_matrix_world_inverse: 4x4 matrix (list of lists or flat array)
        mesh_matrix_world: 4x4 matrix (list of lists or flat array)
        
    Returns:
        view_vector: tuple (x, y, z) normalized
    """
    # Step 1 & 2: Multiply matrices
    # M_mv = camera_matrix_world_inverse * mesh_matrix_world
    # Assuming standard 4x4 matrix multiplication
    model_view_matrix = multiply_matrices(camera_matrix_world_inverse, mesh_matrix_world)
    
    # Step 3 & 4: Extract Z-axis components (indices 2, 6, 10 in flat array)
    # Note: Index mapping depends on memory layout. 
    # Source [S2, unofficial] uses indices 2, 6, 10 which correspond to:
    # Col 2, Row 0 (index 2)
    # Col 2, Row 1 (index 6)
    # Col 2, Row 2 (index 10)
    # This assumes column-major storage where element[i] is at row i%4, col i//4? 
    # Actually, in column-major, element 2 is row 2, col 0. 
    # Let's verify: 
    # Col 0: 0,1,2,3
    # Col 1: 4,5,6,7
    # Col 2: 8,9,10,11
    # The source uses indices 2, 6, 10. 
    # Index 2: Row 2, Col 0.
    # Index 6: Row 2, Col 1.
    # Index 10: Row 2, Col 2.
    # This extracts the third row of the matrix, not the Z-axis column.
    # However, the source code explicitly says: "extract view vector components from matrix elements at indices 2, 6, 10".
    # And negates them. 
    # In a standard OpenGL column-major matrix, the view direction (camera's local -Z) in world space 
    # is often found in the third column (indices 2, 6, 10 if 0-indexed flat array? No, 2,6,10 are row 2).
    # Let's stick strictly to the source's indices.
    
    idx_2 = model_view_matrix[2]
    idx_6 = model_view_matrix[6]
    idx_10 = model_view_matrix[10]
    
    vx = -idx_2
    vy = -idx_6
    vz = -idx_10
    
    # Step 5: Normalize
    length = sqrt(vx*vx + vy*vy + vz*vz)
    if length == 0:
        return (0, 0, 0) # Guard against degenerate case [G]
        
    return (vx / length, vy / length, vz / length)

def multiply_matrices(A, B):
    """Multiplies two 4x4 matrices A and B."""
    C = [[0]*4 for _ in range(4)]
    for i in range(4):
        for j in range(4):
            sum_val = 0
            for k in range(4):
                sum_val += A[i][k] * B[k][j]
            C[i][j] = sum_val
    # Flatten to 1D array for consistency with source access pattern
    flat_C = []
    for row in C:
        flat_C.extend(row)
    return flat_C
```

**Edge Cases and Pitfalls:**
*   **Degenerate Camera/Mesh Pose:** If the camera and mesh are in identical positions or the transformation results in a zero vector, normalization fails. A guard for zero length is required [G].
*   **Matrix Layout:** The indices 2, 6, 10 depend on the specific memory layout (row-major vs column-major) and the definition of the matrix multiplication order. The source [S2, unofficial] uses these specific indices, implying a specific layout (likely row-major or a specific column-major interpretation where these indices correspond to the relevant basis vector components). Implementers must verify the index mapping against their matrix library's storage order.
*   **Precision:** Floating-point errors in matrix multiplication can lead to slight non-orthogonality in the basis vectors. Normalization mitigates this for the view vector but does not correct the entire matrix.

## Operating characteristics
*   **Time Complexity:** $O(1)$ for matrix multiplication of fixed 4x4 matrices and vector normalization.
*   **Memory Complexity:** $O(1)$, storing a few 4x4 matrices and a 3D vector.
*   **Strengths:** Directly provides the view vector needed for lighting calculations (e.g., Phong shading) without requiring additional vector math from the camera position and object position.
*   **Limitations:** Tightly coupled to the specific matrix layout and indexing scheme of the source implementation (indices 2, 6, 10). May not be directly portable to other matrix libraries without verifying index mapping.
*   **When to use:** When the view vector relative to a specific mesh is required for per-vertex or per-pixel lighting in a volumetric or surface rendering context.
*   **When not to use:** When only the camera's global orientation is needed, or when working with a different matrix layout that maps the Z-axis to different indices.

## Background
The concept originates from standard computer graphics pipelines, specifically OpenGL, where the modelview matrix combines the model (object) and view (camera) transformations [S1, unofficial]. The specific implementation of extracting the view vector from the model-view matrix is documented in the context of volumetric fire visualization using Three.js [S2, unofficial]. The underlying matrix definitions for translation, rotation, and scaling are standard OpenGL conventions [S1, unofficial].
