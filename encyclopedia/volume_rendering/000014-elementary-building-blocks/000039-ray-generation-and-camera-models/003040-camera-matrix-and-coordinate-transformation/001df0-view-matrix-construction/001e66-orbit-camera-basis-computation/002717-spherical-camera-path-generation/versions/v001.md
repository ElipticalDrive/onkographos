# Spherical Camera Path Generation
Also called: 360° Orbit Path, Circular Orbit Camera

## Overview
Generates a smooth circular camera path looking at the origin for 360° orbit video rendering [S1, unofficial]. It differs from [Arcball Camera View & Projection Matrix Computation](2210-arcball-camera-view-projection-matrix-computation.md) by producing a continuous temporal sequence of poses rather than a single interactive view, and from [Orbit Camera Controls](3262-orbit-camera-controls.md) by automating the trajectory generation for offline video export rather than providing user input handling.

## How it works
**Inputs:**
- `n_frames`: Integer number of frames in the path (default 120) [S1, unofficial].
- `radius`: Float distance from the origin (default 4.0) [S1, unofficial].
- `origin`: 3D vector defining the look-at target (typically `[0, 0, 0]`) [S1, unofficial].

**Outputs:**
- `poses`: `torch.Tensor` of shape `[n_frames, 4, 4]` containing camera-to-world (C2W) matrices [S1, unofficial].

**Data Structures:**
- The output is a contiguous tensor where each `4x4` slice represents a homogeneous transformation matrix.
- Matrix layout follows OpenGL convention: `+z` is backward [S1, unofficial].
- Columns 0, 1, 2 are the Right, Up, and -Forward vectors respectively. Column 3 is the translation (camera position).

**Steps:**
1. Initialize an empty list or tensor to store the resulting matrices.
2. For each frame index $i$ from $0$ to $n\_frames - 1$:
   a. Compute the orbital angle:
      $$ \theta_i = \frac{2\pi i}{n\_frames} $$
   b. Compute the camera position $(x, y, z)$:
      $$ x = \text{radius} \cdot \cos(\theta_i) $$
      $$ y = \text{radius} \cdot 0.3 $$
      $$ z = \text{radius} \cdot \sin(\theta_i) $$
      The fixed $y$ offset creates a slightly elevated orbit rather than a perfect equatorial circle [S1, unofficial].
   c. Compute the forward vector $\mathbf{f}$ pointing from the camera to the origin:
      $$ \mathbf{f} = -\frac{\text{origin}}{\|\text{origin}\|} $$
      If the origin is the zero vector, this step is undefined; in practice, the origin is usually `[0,0,0]`, making the forward vector simply the normalized negative position vector $-\mathbf{p}/\|\mathbf{p}\|$ [S1, unofficial].
   d. Compute the right vector $\mathbf{r}$:
      $$ \mathbf{r} = \text{normalize}(\mathbf{f} \times [0, 1, 0]) $$
      This assumes the camera's "up" direction in world space is generally aligned with the Y-axis. If $\mathbf{f}$ is parallel to $[0,1,0]$ (camera looking straight up or down), this cross product becomes zero, causing a singularity [S1, unofficial].
   e. Compute the up vector $\mathbf{u}$:
      $$ \mathbf{u} = \mathbf{r} \times \mathbf{f} $$
   f. Construct the $4 \times 4$ camera-to-world matrix $C$:
      $$ C = \begin{bmatrix} r_x & u_x & -f_x & x \\ r_y & u_y & -f_y & y \\ r_z & u_z & -f_z & z \\ 0 & 0 & 0 & 1 \end{bmatrix} $$
      Note the third column is $-\mathbf{f}$ because the OpenGL convention places the camera looking down $-Z$ in view space, so the view space $-Z$ axis maps to world space $\mathbf{f}$ [S1, unofficial].

**Pseudocode:**
```python
import torch
import math

def generate_spherical_camera_path(n_frames=120, radius=4.0, origin=None):
    """
    Generate a spherical camera path looking at the origin.
    
    Args:
        n_frames (int): Number of frames.
        radius (float): Distance from origin.
        origin (torch.Tensor): Look-at target, shape (3,). Default [0,0,0].
        
    Returns:
        torch.Tensor: Camera-to-world matrices, shape (n_frames, 4, 4).
    """
    if origin is None:
        origin = torch.tensor([0.0, 0.0, 0.0])
    
    poses = []
    
    for i in range(n_frames):
        # 1. Compute angle
        angle = 2.0 * math.pi * i / n_frames
        
        # 2. Compute position
        cam_x = radius * math.cos(angle)
        cam_y = radius * 0.3
        cam_z = radius * math.sin(angle)
        position = torch.tensor([cam_x, cam_y, cam_z])
        
        # 3. Compute forward vector
        # Forward points from camera to origin
        to_origin = origin - position
        forward = to_origin / torch.norm(to_origin)
        
        # 4. Compute right vector
        # Cross forward with world up [0,1,0]
        world_up = torch.tensor([0.0, 1.0, 0.0])
        right = torch.cross(forward, world_up)
        right_norm = torch.norm(right)
        
        # Handle singularity if forward is parallel to world_up
        if right_norm < 1e-6:
            # Fallback: if looking straight up/down, use a different reference
            # For simplicity in this basic generator, we might just use a fixed right
            # or clamp. Standard fallback is cross with [1,0,0]
            right = torch.cross(forward, torch.tensor([1.0, 0.0, 0.0]))
            right_norm = torch.norm(right)
            
        right = right / right_norm
        
        # 5. Compute up vector
        up = torch.cross(right, forward)
        
        # 6. Construct 4x4 matrix (OpenGL convention: +z backward)
        # Columns: Right, Up, -Forward, Position
        mat = torch.eye(4)
        mat[0, :3] = right
        mat[1, :3] = up
        mat[2, :3] = -forward
        mat[0, 3] = position[0]
        mat[1, 3] = position[1]
        mat[2, 3] = position[2]
        
        poses.append(mat)
        
    return torch.stack(poses)
```

## Subtopics

### Circular Sensor Array Initialization
Programmatically generates a set of perspective camera sensors arranged uniformly in a circle around a central point, configured for Mitsuba 3 rendering [S2, unofficial]. It differs from the main method by instantiating specific renderer sensor objects with film properties rather than returning raw pose matrices, and by supporting arbitrary numbers of discrete sensors rather than a continuous video frame sequence. It is chosen when rendering a static multi-view dataset or a light field using a specific path tracer. Parameters include `num_sensors` (count), `render_res` (film resolution, default 256), `fov` (field of view in degrees, default 45.0), `center` (circle center, default `[0,0,0]`), and `radius` (distance, default 1.3) [S2, unofficial]. The transform for each sensor $i$ is constructed by translating to `center`, rotating around the Y-axis by $\theta_i = \frac{360.0}{num\_sensors} \cdot i$, and looking at the target `[0,0,0]` from `[0,0,radius]` with up `[0,1,0]` [S2, unofficial].

## Operating characteristics
- **Time Complexity:** $O(n\_frames)$ to generate the poses, as each frame requires constant-time trigonometric and vector operations.
- **Memory Complexity:** $O(n\_frames \times 16)$ for the output tensor storage.
- **Performance:** Generation is instantaneous on modern hardware. Rendering time depends on the downstream ray tracer and scene complexity, not the path generation itself.
- **Strengths:** Simple, deterministic, and produces smooth 360° orbits suitable for visualizing 3D reconstructions or NeRFs.
- **Limitations:** The fixed Y-offset (`radius * 0.3`) may not be suitable for all scenes (e.g., if the object is tall or flat). The singularity at the poles (when looking straight up/down) requires handling, though the fixed Y-offset avoids the exact pole if the radius is large enough relative to the offset.
- **When to use:** When a smooth, automated 360-degree fly-around is needed for visualization or dataset creation.
- **When not to use:** When interactive control is required (use [Orbit Camera Controls](3262-orbit-camera-controls.md)) or when a single specific view is needed (use [Camera Look-at Computation via Rotation](2696-camera-look-at-computation-via-rotation.md)).

## Background
Originated in the context of NeRF (Neural Radiance Field) visualization pipelines, specifically in the `nerf-3d-vision` repository [S1, unofficial]. It is commonly used to generate turntable videos for evaluating or showcasing 3D neural rendering results.
