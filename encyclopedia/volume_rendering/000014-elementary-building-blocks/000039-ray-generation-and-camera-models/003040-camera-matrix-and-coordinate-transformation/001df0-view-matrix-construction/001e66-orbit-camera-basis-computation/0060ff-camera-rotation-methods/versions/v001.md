# Camera Rotation Methods
Also called: rotate

## Overview
Camera rotation methods manipulate the orientation of a camera in a right-handed coordinate system centered on the camera [S1, S2]. They solve the problem of updating the view matrix or camera basis by applying specific angular transformations (pitch, yaw, roll) or arbitrary axis rotations, while optionally pivoting around a specified center [S1, S2]. What sets them apart from sibling methods like [Arcball Camera View & Projection Matrix Computation](2210-arcball-camera-view-projection-matrix-computation.md) is their direct exposure of elementary rotation primitives (pitch/yaw/roll) rather than high-level quaternion or matrix composition APIs [S1, S2].

## How it works
**Inputs and Outputs:**
*   **Inputs:**
    *   `angle`: The rotation angle in radians or degrees (implementation dependent).
    *   `axis`: For `rotate()` and `iter_rotate()`, the arbitrary axis vector. For `pitch()`, `yaw()`, and `roll()`, the axis is implicit.
    *   `rot_center`: The pivot point for the rotation. Default is the camera position [S1, S2].
*   **Outputs:**
    *   Updated camera orientation (view matrix or basis vectors).
    *   Updated camera position if `rot_center` differs from the camera position [S1, S2].

**Data Structures:**
The camera maintains an internal state including:
*   `position`: 3D vector.
*   `orientation`: Represented as a basis (right, up, forward) or a rotation matrix/quaternion.
*   `rot_center`: 3D vector, defaulting to `position` [S1, S2].

**Numbered Steps:**
1.  **Determine Pivot:** Identify the pivot point `P`. If `rot_center` is not explicitly provided, `P` is set to the current camera `position` [S1, S2].
2.  **Select Axis:**
    *   For `pitch()`: The axis is the **lateral axis** (typically the camera's right vector) [S1, S2].
    *   For `yaw()`: The axis is the **vertical axis** (referred to as `north_vector` in the source, typically the world up or camera's up vector depending on implementation context) [S1, S2].
    *   For `roll()`: The axis is the **longitudinal axis** (referred to as `normal_vector` in the source, typically the camera's forward vector) [S1, S2].
    *   For `rotate()` and `iter_rotate()`: The axis is the user-provided arbitrary vector `axis` [S1, S2].
3.  **Apply Rotation:**
    *   Compute the rotation matrix $R$ for the given `angle` and `axis` [S1, S2].
    *   If `rot_center` equals `position`, only the orientation is updated by applying $R$ to the current basis vectors [S1, S2].
    *   If `rot_center` differs from `position`, the camera position is rotated around `P` by $R$, and the orientation is updated by $R$ [S1, S2].
4.  **Iterative Update (for `iter_rotate`):** If `iter_rotate()` is used, the rotation is applied in small increments over time or frames, rather than as a single instantaneous jump [S1, S2].
5.  **Trigger Update:** Any change triggers an update of all other camera properties (e.g., view matrix, frustum planes) [S1, S2].

**Formulas:**
Let $v$ be a vector relative to the pivot $P$. The rotated vector $v'$ is:
$$ v' = R \cdot v $$
Where $R$ is the rotation matrix derived from the axis-angle representation.
The new position $p_{new}$ is:
$$ p_{new} = P + R \cdot (p_{old} - P) $$
The new basis vectors $B_{new}$ are:
$$ B_{new} = R \cdot B_{old} $$
[G] Standard Rodrigues' rotation formula or quaternion multiplication is used to compute $R$ from the axis and angle.

**Parameters:**
*   `rot_center`: Default is the camera position [S1, S2].

**Edge Cases and Pitfalls:**
*   **Gimbal Lock:** Using sequential `pitch()` and `yaw()` calls can lead to gimbal lock if the pitch angle reaches $\pm 90^\circ$, causing the lateral and vertical axes to align. The source notes the camera exists in a right-handed system but does not explicitly detail gimbal lock prevention mechanisms [S1, S2].
*   **Pivot Displacement:** If `rot_center` is not the camera position, the camera position changes. This may be counterintuitive for users expecting pure orientation changes [S1, S2].
*   **Coordinate System:** The camera exists in a right-handed coordinate system centered on the camera. Rotations must respect this handedness [S1, S2].

**Pseudocode:**
```python
def pitch(camera, angle, rot_center=None):
    """Rotate camera about its lateral (right) axis."""
    if rot_center is None:
        rot_center = camera.position
    axis = camera.right_vector
    apply_rotation(camera, angle, axis, rot_center)

def yaw(camera, angle, rot_center=None):
    """Rotate camera about its vertical (north/up) axis."""
    if rot_center is None:
        rot_center = camera.position
    axis = camera.up_vector # Source calls this north_vector
    apply_rotation(camera, angle, axis, rot_center)

def roll(camera, angle, rot_center=None):
    """Rotate camera about its longitudinal (forward) axis."""
    if rot_center is None:
        rot_center = camera.position
    axis = camera.forward_vector # Source calls this normal_vector
    apply_rotation(camera, angle, axis, rot_center)

def rotate(camera, angle, axis, rot_center=None):
    """Rotate camera about an arbitrary axis."""
    if rot_center is None:
        rot_center = camera.position
    apply_rotation(camera, angle, axis, rot_center)

def iter_rotate(camera, total_angle, axis, steps, rot_center=None):
    """Iteratively rotate camera about an arbitrary axis."""
    if rot_center is None:
        rot_center = camera.position
    step_angle = total_angle / steps
    for _ in range(steps):
        apply_rotation(camera, step_angle, axis, rot_center)

def apply_rotation(camera, angle, axis, rot_center):
    """Apply rotation to camera position and orientation around rot_center."""
    # Compute rotation matrix R from angle and axis
    R = rotation_matrix(axis, angle)
    
    # Update position if pivot is not the camera itself
    if rot_center != camera.position:
        relative_pos = camera.position - rot_center
        new_relative_pos = R @ relative_pos
        camera.position = rot_center + new_relative_pos
    
    # Update orientation (basis vectors)
    camera.right_vector = R @ camera.right_vector
    camera.up_vector = R @ camera.up_vector
    camera.forward_vector = R @ camera.forward_vector
    
    # Normalize vectors to prevent drift [G]
    camera.right_vector = normalize(camera.right_vector)
    camera.up_vector = normalize(camera.up_vector)
    camera.forward_vector = normalize(camera.forward_vector)
    
    # Re-orthonormalize basis if necessary [G]
    # camera.forward_vector = normalize(camera.forward_vector)
    # camera.right_vector = normalize(cross(camera.up_vector, camera.forward_vector))
    # camera.up_vector = cross(camera.forward_vector, camera.right_vector)
    
    # Trigger update of view matrix and other properties [S1, S2]
    camera.update_view_matrix()
```

## Operating characteristics
*   **Time Complexity:** $O(1)$ per rotation call, assuming fixed-size vector/matrix operations.
*   **Memory Complexity:** $O(1)$ additional memory.
*   **Strengths:** Simple, intuitive API for basic orientation changes. Direct mapping to common camera control concepts (pitch/yaw/roll).
*   **Limitations:** Sequential pitch/yaw can suffer from gimbal lock. `iter_rotate` requires manual step management.
*   **When to use:** When implementing basic camera controls or simple orientation adjustments.
*   **When not to use:** When complex, smooth, or gimbal-lock-free rotation is required (use quaternions or arcball methods).

## Background
These methods are part of the `yt` project's volume rendering visualization tools, specifically the `Camera` helper class [S1, S2]. They provide a high-level interface for manipulating camera orientation in 3D visualizations [S1, S2].
