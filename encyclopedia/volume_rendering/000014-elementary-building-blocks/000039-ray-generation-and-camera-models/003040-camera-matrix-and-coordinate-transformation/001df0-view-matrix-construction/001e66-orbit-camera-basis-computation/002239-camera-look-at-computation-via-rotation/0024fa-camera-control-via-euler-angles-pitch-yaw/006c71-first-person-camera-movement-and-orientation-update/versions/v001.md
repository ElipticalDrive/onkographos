# First-Person Camera Movement and Orientation Update

Also called: 3D Camera & View Vector Calculation, Camera Movement and Orientation Update, FPS Camera Update, FPS camera setup, View frustum vector math

## Overview
This method updates a first-person camera's position and orientation in a 3D scene based on discrete input events (keyboard movement, mouse rotation). It calculates the view direction and projection plane vectors using spherical coordinate logic for rotation and vector addition for translation [S1, S2, unofficial]. It differs from the parent [Camera Control via Euler Angles (Pitch/Yaw)](3431-camera-control-via-euler-angles-pitch-yaw.md) by explicitly handling frame-time dependent movement and mouse delta accumulation to drive the Euler angles, rather than assuming the angles are already provided. It addresses the problem of synchronizing user input with the camera's world-space transformation for ray generation.

## How it works
The method maintains a camera state consisting of a position vector, a forward (view) vector, a right vector, and an up vector. It processes two types of input: continuous movement keys and discrete mouse deltas. The orientation is derived from yaw and pitch angles, which are updated by mouse input. The position is updated by moving along the basis vectors derived from the current orientation.

### Inputs and Outputs
**Inputs:**
*   `Position`: Current camera position vector $(x, y, z)$.
*   `Yaw`: Horizontal rotation angle in radians.
*   `Pitch`: Vertical rotation angle in radians.
*   `MouseDeltaX`, `MouseDeltaY`: Change in mouse position since the last frame.
*   `KeyboardInput`: Boolean flags for `Forward`, `Backward`, `Left`, `Right`, `Up`, `Down`.
*   `DeltaTime`: Time elapsed since the last frame update (seconds).
*   `Sensitivity`: Mouse sensitivity multiplier.
*   `Speed`: Movement speed multiplier.

**Outputs:**
*   Updated `Position`.
*   Updated `Yaw`, `Pitch`.
*   Updated `Front` (view direction), `Right`, and `Up` vectors.

### Data Structures
The camera state is typically stored in a struct or class with the following fields:
*   `Position`: `Vector3` (float x, y, z).
*   `Front`: `Vector3` (normalized direction vector).
*   `Right`: `Vector3` (normalized direction vector, orthogonal to Front and Up).
*   `Up`: `Vector3` (normalized direction vector, orthogonal to Front and Right).
*   `Yaw`: `float` (radians).
*   `Pitch`: `float` (radians).

### Parameters and Typical Values
*   `Sensitivity`: Not explicitly given in sources, but derived from frame time in [S2, unofficial] as `0.5f / e.Time` or treated as a constant multiplier. [S1, unofficial] uses specific speed divisors for mouse input.
*   `Speed`: `10.0` [S2, unofficial]. [S1, unofficial] uses `0.50` for movement speed.
*   `Pitch Clamp`: $[-89^\circ, 89^\circ]$ or $[-0.999, 0.999]$ radians [S1, S2, unofficial].
*   `HorzLookSpeed`: `900` [S1, unofficial].
*   `VertLookSpeed`: `2200` [S1, unofficial].

### Steps
1.  **Process Mouse Input (Orientation Update):**
    *   Calculate sensitivity factor. If using frame-time normalization [S2, unofficial], `sensitivity = 0.5 / DeltaTime`. Otherwise, use a constant.
    *   Update `Yaw`: `Yaw += MouseDeltaX * Sensitivity * DeltaTime`.
    *   Update `Pitch`: `Pitch -= MouseDeltaY * Sensitivity * DeltaTime`. Note the negative sign for Y to match standard screen coordinates where Y increases downwards [S2, unofficial].
    *   Clamp `Pitch` to the range $[-\pi/2 + \epsilon, \pi/2 - \epsilon]$ to prevent gimbal lock and inversion. Sources specify $[-89^\circ, 89^\circ]$ [S2, unofficial] or clamping the vertical look component to $[-0.999, 0.999]$ [S1, unofficial].

2.  **Recompute Orientation Vectors:**
    *   Calculate the `Front` vector from `Yaw` and `Pitch`:
        $$
        \begin{aligned}
        Front.x &= \cos(Pitch) \cdot \cos(Yaw) \\
        Front.y &= \sin(Pitch) \\
        Front.z &= \cos(Pitch) \cdot \sin(Yaw)
        \end{aligned}
        $$
    *   Normalize `Front`. (Note: The formula above produces a unit vector if Pitch and Yaw are handled correctly, but explicit normalization is recommended for numerical stability [S2, unofficial]).
    *   Calculate the `Right` vector. The sources use the world Up vector $(0, 1, 0)$ for this cross product [S2, unofficial]:
        $$
        Right = \text{normalize}(\text{cross}(Front, (0, 1, 0)))
        $$
        *Pitfall:* If `Front` is parallel to the world Up vector (looking straight up or down), the cross product is zero. A guard clause or alternative basis calculation is required [G].
    *   Calculate the `Up` vector:
        $$
        Up = \text{cross}(Right, Front)
        $$
        *Note:* [S1, unofficial] computes a horizontal vector using `cross(viewVector, (0,0,1))`. This assumes a different world orientation (Z-up). The method described here assumes Y-up, consistent with [S2, unofficial] and standard graphics APIs. If Z-up is required, swap Y and Z axes in the vector definitions.

3.  **Process Keyboard Input (Position Update):**
    *   Initialize `Movement` vector to $(0, 0, 0)$.
    *   If `Forward` is pressed: `Movement += Front`.
    *   If `Backward` is pressed: `Movement -= Front`.
    *   If `Right` is pressed: `Movement += Right`.
    *   If `Left` is pressed: `Movement -= Right`.
    *   If `Up` is pressed: `Movement += Up`.
    *   If `Down` is pressed: `Movement -= Up`.
    *   Scale `Movement` by `Speed * DeltaTime`.
    *   Update `Position`: `Position += Movement`.

### Pseudocode

```python
import math
from typing import Tuple

def update_first_person_camera(
    position: Tuple[float, float, float],
    yaw: float,
    pitch: float,
    mouse_delta_x: float,
    mouse_delta_y: float,
    delta_time: float,
    keys: dict,
    sensitivity: float = 1.0,
    speed: float = 10.0
) -> Tuple[Tuple[float, float, float], float, float, Tuple[float, float, float], Tuple[float, float, float], Tuple[float, float, float]]:
    """
    Updates camera position and orientation.
    
    Returns:
        (new_position, new_yaw, new_pitch, front_vector, right_vector, up_vector)
    """
    
    # 1. Update Orientation Angles
    # [S2, unofficial] Sensitivity can be frame-time dependent. Using constant sensitivity here for clarity,
    # but multiplying by delta_time for frame-rate independence.
    yaw += mouse_delta_x * sensitivity * delta_time
    pitch -= mouse_delta_y * sensitivity * delta_time
    
    # Clamp pitch to prevent gimbal lock and inversion
    # [S2, unofficial] Clamps to [-89, 89] degrees. Convert to radians.
    max_pitch = math.radians(89)
    pitch = max(-max_pitch, min(max_pitch, pitch))
    
    # 2. Recompute Basis Vectors
    # [S2, unofficial] Front vector calculation
    front_x = math.cos(pitch) * math.cos(yaw)
    front_y = math.sin(pitch)
    front_z = math.cos(pitch) * math.sin(yaw)
    
    # Normalize front vector
    length = math.sqrt(front_x**2 + front_y**2 + front_z**2)
    if length > 1e-6:
        front_x /= length
        front_y /= length
        front_z /= length
    
    front = (front_x, front_y, front_z)
    
    # [S2, unofficial] Right vector: Cross(Front, WorldUp)
    # World Up is (0, 1, 0)
    # Cross product of (fx, fy, fz) and (0, 1, 0)
    # i: fy*0 - fz*1 = -fz
    # j: fz*0 - fx*0 = 0
    # k: fx*1 - fy*0 = fx
    right_x = -front_z
    right_y = 0.0
    right_z = front_x
    
    # Normalize right vector
    length = math.sqrt(right_x**2 + right_y**2 + right_z**2)
    if length > 1e-6:
        right_x /= length
        right_y /= length
        right_z /= length
    else:
        # Fallback if front is parallel to world up (looking straight up/down)
        # [G] Standard fallback: use a fixed right vector or recalculate using a different reference
        right = (1.0, 0.0, 0.0)
        right_x, right_y, right_z = right
    
    right = (right_x, right_y, right_z)
    
    # [S2, unofficial] Up vector: Cross(Right, Front)
    # Cross product of (rx, ry, rz) and (fx, fy, fz)
    up_x = right_y * front_z - right_z * front_y
    up_y = right_z * front_x - right_x * front_z
    up_z = right_x * front_y - right_y * front_x
    
    # Normalize up vector
    length = math.sqrt(up_x**2 + up_y**2 + up_z**2)
    if length > 1e-6:
        up_x /= length
        up_y /= length
        up_z /= length
    
    up = (up_x, up_y, up_z)
    
    # 3. Update Position
    movement = [0.0, 0.0, 0.0]
    
    if keys.get('forward', False):
        movement[0] += front_x
        movement[1] += front_y
        movement[2] += front_z
        
    if keys.get('backward', False):
        movement[0] -= front_x
        movement[1] -= front_y
        movement[2] -= front_z
        
    if keys.get('right', False):
        movement[0] += right_x
        movement[1] += right_y
        movement[2] += right_z
        
    if keys.get('left', False):
        movement[0] -= right_x
        movement[1] -= right_y
        movement[2] -= right_z
        
    if keys.get('up', False):
        movement[0] += up_x
        movement[1] += up_y
        movement[2] += up_z
        
    if keys.get('down', False):
        movement[0] -= up_x
        movement[1] -= up_y
        movement[2] -= up_z
        
    # Scale by speed and delta time
    scale = speed * delta_time
    movement[0] *= scale
    movement[1] *= scale
    movement[2] *= scale
    
    # Add to position
    new_position = (
        position[0] + movement[0],
        position[1] + movement[1],
        position[2] + movement[2]
    )
    
    return new_position, yaw, pitch, front, right, up
```

### Edge Cases and Pitfalls
*   **Gimbal Lock / Parallel Vectors:** When the camera looks straight up or down, the `Front` vector is parallel to the World Up vector $(0,1,0)$. The cross product `Cross(Front, Up)` becomes zero, resulting in a zero-length `Right` vector. The pseudocode includes a fallback [G], but in practice, clamping pitch to $\pm 89^\circ$ [S2, unofficial] usually prevents this.
*   **Coordinate System Mismatch:** [S1, unofficial] uses `cross(viewVector, (0,0,1))` to get the horizontal vector, implying a Z-up coordinate system. [S2, unofficial] uses `cross(front, UnitY)` implying a Y-up system. The implementer must ensure the basis vector calculations match the scene's coordinate system.
*   **Frame Rate Dependency:** Movement and rotation must be scaled by `DeltaTime` to ensure consistent behavior across different frame rates. [S2, unofficial] explicitly uses `e.Time`.
*   **Mouse Delta Accumulation:** Mouse input should be processed as deltas (change in position) rather than absolute positions to allow for continuous rotation regardless of screen boundaries.

## Operating characteristics
*   **Time Complexity:** $O(1)$. The method performs a fixed number of arithmetic operations and vector calculations per frame.
*   **Memory Complexity:** $O(1)$. Only a few temporary vectors and scalars are required.
*   **Strengths:** Simple to implement; provides intuitive first-person controls; decouples input from transformation logic.
*   **Limitations:** Susceptible to gimbal lock if pitch is not clamped; relies on a fixed world up vector which can cause issues in extreme orientations; does not handle roll.
*   **When to use:** First-person games, VR applications, and any scenario requiring direct mouse-driven camera orientation.
*   **When not to use:** Third-person cameras (require offset calculation), orbit cameras (require spherical coordinate updates relative to a target point), or when roll is required.

## Background
This method is a standard technique in 3D graphics programming for implementing first-person controllers. It is widely used in voxel engines and FPS games. The specific implementation details vary between libraries, but the core logic of updating yaw/pitch from mouse deltas and moving along basis vectors from keyboard input is consistent. [S1, unofficial] presents an implementation in a Java-based voxel engine, while [S2, unofficial] provides a C#/OpenGL implementation. The approach builds on the mathematical foundations of Euler angles and vector algebra.
