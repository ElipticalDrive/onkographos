# Grid Ray Sampler

Also called: Camera Ray Generation

## Overview
The Grid Ray Sampler generates 3D camera rays from 2D screen coordinates based on the current camera view and projection matrices, providing the foundational ray data for volume rendering and neural radiance field (NeRF) training [S1, S2, unofficial]. It differs from its siblings by explicitly handling the transformation from pixel indices to world-space origins and directions, supporting both uniform full-grid sampling and random sparse sampling via a `full_grid` flag [S2, unofficial]. Unlike [Sample Streaming Payload Ray Computation](1509-sample-streaming-payload-ray-computation.md) which focuses on payload management, or [OptiX Ray Generation & Traversal Setup](1552-optix-ray-generation-traversal-setup.md) which integrates with specific ray tracing APIs, the Grid Ray Sampler provides the generic geometric ray construction logic [S1, S2, unofficial].

## How it works
**Inputs:**
- `camera`: Camera state containing intrinsic parameters (focal length, principal point) and extrinsic pose (world-to-object or world-to-camera transform) [S1, S2, unofficial].
- `world_to_object`: 4x4 transformation matrix mapping world coordinates to the object/camera local space [S1, unofficial].
- `resolution`: Integer defining image dimensions (width $W$, height $H$) and ray buffer size [S1, unofficial]. Typical value: 512 [S1, unofficial].
- `framerate.count()`: `uint32_t` representing accumulated samples per pixel, used for coherence handling [S1, unofficial].
- `full_grid`: Boolean flag. If `true`, generates rays for all $H \times W$ pixels; if `false`, generates $N_{rays}$ random rays [S2, unofficial].
- `N_rays`: Number of rays to generate when `full_grid` is `false` [S2, unofficial].

**Outputs:**
- `rays_o`: Tensor of ray origins, shape $[B, N, 3]$ where $B$ is batch size and $N$ is number of rays [S2, unofficial].
- `rays_d`: Tensor of normalized ray directions, shape $[B, N, 3]$ [S2, unofficial].

**Data Structures:**
- Ray buffer: A contiguous memory block storing origin and direction vectors. In GPU implementations, this is often a flat array or structured buffer accessible via pointers [S1, unofficial].
- Pixel coordinates: 2D grids generated via `torch.meshgrid` with `indexing="ij"` [S2, unofficial].

**Steps:**
1. **Determine Ray Count:**
   If `full_grid` is true, set $N = H \times W$. Otherwise, set $N = N_{rays}$ [S2, unofficial].

2. **Generate Pixel Indices:**
   Create 2D grids of pixel coordinates $i$ (row) and $j$ (column) using `torch.meshgrid` with `indexing="ij"` [S2, unofficial].
   Reshape and expand $i$ and $j$ to match batch dimensions:
   $$ i = i.t().reshape([*[1] * len(prefix), H \times W]).expand([*prefix, H \times W]) $$
   $$ j = j.t().reshape([*[1] * len(prefix), H \times W]).expand([*prefix, H \times W]) $$
   where `prefix` represents batch dimensions [S2, unofficial].

3. **Select Indices (if not full grid):**
   If `full_grid` is false, select random indices:
   $$ \text{select\_inds} = \text{torch.randint}(0, H \times W, \text{size}=[N], \text{device}=\text{device}) $$
   Gather selected $i$ and $j$ coordinates using `select_inds` [S2, unofficial].

4. **Lift to Camera Space:**
   Convert pixel coordinates to 3D points in camera space using intrinsic parameters:
   $$ \text{pixel\_points\_cam} = \text{lift}(i, j, \mathbf{1}, \text{intrinsic}) $$
   where $\mathbf{1}$ is a tensor of ones matching the shape of $i$ and $j$ [S2, unofficial]. The `lift` function typically performs:
   $$ x_{cam} = \frac{j - c_x}{f_x}, \quad y_{cam} = \frac{i - c_y}{f_y}, \quad z_{cam} = 1 $$
   resulting in points $[x_{cam}, y_{cam}, 1, 1]^T$ [S2, G, unofficial].

5. **Transform to World Coordinates:**
   Apply the camera pose matrix $P$ (4x4) to transform points to world space:
   $$ \text{world\_coords} = (P \times \text{pixel\_points\_cam})^T[..., :3] $$
   This extracts the first three components of the transformed homogeneous coordinates [S2, unofficial].

6. **Compute Ray Directions:**
   Extract ray origins from the pose matrix:
   $$ \text{rays\_o} = P[..., :3, 3] $$
   Compute raw directions:
   $$ \text{rays\_d}_{raw} = \text{world\_coords} - \text{rays\_o}[..., \text{None}, :] $$
   Normalize directions:
   $$ \text{rays\_d} = \frac{\text{rays\_d}_{raw}}{\|\text{rays\_d}_{raw}\|_2} $$
   Expand ray origins to match the shape of ray directions:
   $$ \text{rays\_o} = \text{rays\_o}[..., \text{None}, :].\text{expand\_as}(\text{rays\_d}) $$
   [S2, unofficial].

7. **GPU Dispatch (Optional Implementation Detail):**
   On GPU, rays are generated using a kernel call:
   ```cpp
   cuda_camera_generate_rays(camera, world_to_object, rays->data(), resolution, resolution, static_cast<uint32_t>(framerate.count()));
   ```
   [S1, unofficial].

**Parameters:**
- `resolution`: Image dimensions. Typical value: 512 [S1, unofficial].
- `framerate.count()`: Accumulated samples per pixel. Type: `uint32_t` [S1, unofficial].
- `N_rays`: Number of random rays. Value: Not given in the sources.

**Edge Cases and Pitfalls:**
- **Precision:** Normalization of ray directions must handle near-zero vectors to avoid NaNs [G].
- **Boundaries:** Pixel coordinates should be handled carefully to avoid off-by-one errors at image edges [G].
- **Degenerate Input:** If the camera pose is singular or identity is not handled, transformations may fail [G].

**Pseudocode:**
```python
import torch
import torch.nn.functional as F

def generate_grid_rays(camera, world_to_object, resolution, full_grid, N_rays, batch_size=1):
    """
    Generate camera rays for volume rendering.
    
    Args:
        camera: Object containing 'intrinsic' (3x3) and 'pose' (4x4) matrices.
        world_to_object: 4x4 transformation matrix.
        resolution: Tuple (H, W).
        full_grid: Boolean. If True, generate H*W rays. Else, generate N_rays random rays.
        N_rays: Integer. Number of rays if full_grid is False.
        batch_size: Integer. Batch size for output tensors.
        
    Returns:
        rays_o: Tensor of shape (batch_size, N, 3) for origins.
        rays_d: Tensor of shape (batch_size, N, 3) for normalized directions.
    """
    H, W = resolution
    intrinsic = camera.intrinsic
    pose = camera.pose
    
    # Step 1: Determine number of rays
    if full_grid:
        N = H * W
    else:
        N = N_rays
        
    # Step 2: Generate pixel indices
    # Create meshgrid with 'ij' indexing
    i_grid, j_grid = torch.meshgrid(torch.arange(H), torch.arange(W), indexing='ij')
    
    # Reshape to (H*W,) and expand to batch dimensions
    # Note: In practice, i and j are often flattened and then expanded
    i_flat = i_grid.flatten().float()
    j_flat = j_grid.flatten().float()
    
    # Expand to match batch size and N
    # Assuming prefix is empty or handled by batch dim
    i_batch = i_flat.unsqueeze(0).expand(batch_size, -1)
    j_batch = j_flat.unsqueeze(0).expand(batch_size, -1)
    
    if not full_grid:
        # Step 3: Select random indices
        # Flatten indices for random selection
        total_pixels = H * W
        select_inds = torch.randint(0, total_pixels, size=(batch_size, N), device=i_flat.device)
        
        # Gather selected i and j
        # Using advanced indexing or gather
        # i_batch shape: (batch_size, H*W)
        i_selected = torch.gather(i_batch, 1, select_inds)
        j_selected = torch.gather(j_batch, 1, select_inds)
        
        i_final = i_selected
        j_final = j_selected
    else:
        i_final = i_batch[:, :N] # N is H*W
        j_final = j_batch[:, :N]
        
    # Step 4: Lift to camera space
    # Intrinsic matrix K:
    # [fx, 0, cx]
    # [0, fy, cy]
    # [0,  0,  1]
    fx = intrinsic[0, 0]
    fy = intrinsic[1, 1]
    cx = intrinsic[0, 2]
    cy = intrinsic[1, 2]
    
    # Normalize pixel coordinates to camera space
    x_cam = (j_final - cx) / fx
    y_cam = (i_final - cy) / fy
    z_cam = torch.ones_like(x_cam)
    
    # Stack to form 3D points in camera space [x, y, z]
    # Add homogeneous coordinate 1 for matrix multiplication
    pixel_points_cam = torch.stack([x_cam, y_cam, z_cam], dim=-1) # (batch_size, N, 3)
    pixel_points_cam_hom = torch.cat([pixel_points_cam, torch.ones_like(z_cam).unsqueeze(-1)], dim=-1) # (batch_size, N, 4)
    
    # Step 5: Transform to world coordinates
    # Pose is 4x4. We need to apply it to each point.
    # world_coords = pose @ pixel_points_cam_hom^T
    # Since pixel_points_cam_hom is (batch_size, N, 4), we transpose last two dims
    # world_coords_hom = torch.bmm(pose.unsqueeze(0).expand(batch_size, -1, -1), pixel_points_cam_hom.transpose(1, 2))
    # world_coords = world_coords_hom[..., :3].transpose(1, 2)
    
    # More efficient:
    # pose is (4,4). pixel_points_cam_hom is (batch_size, N, 4)
    # We want to compute pose @ p for each p
    # This is equivalent to (p @ pose^T)
    world_coords_hom = torch.bmm(pixel_points_cam_hom, pose.transpose(0, 1).unsqueeze(0).expand(batch_size, -1, -1))
    world_coords = world_coords_hom[..., :3] # (batch_size, N, 3)
    
    # Step 6: Compute Ray Directions
    # Extract ray origins from pose (camera position in world space)
    # pose[..., :3, 3] gives the translation part
    rays_o = pose[:3, 3].unsqueeze(0).unsqueeze(0).expand(batch_size, N, -1)
    
    # Raw directions
    rays_d_raw = world_coords - rays_o
    
    # Normalize
    rays_d = F.normalize(rays_d_raw, dim=-1)
    
    return rays_o, rays_d
```

## Subtopics

### [Ray Sampling and Neural Rendering Pipeline](4255-ray-sampling-and-neural-rendering-pipeline.md)
Generates camera rays from pixel coordinates, passes them through an implicit neural renderer, and extracts rendered features. It differs from the Grid Ray Sampler by handling the complete inference pipeline—transforming pixel grids into ray bundles, executing the neural network forward pass, and reshaping the output—rather than just sampling ray origins and directions.

### [Near-Middle-Far Ray Generation](6817-near-middle-far-ray-generation.md)
Divides the ray into two distinct segments: a linear segment from the near plane to a middle point, and a disparity (inverse-linear) segment from the middle point to the far plane. This approach addresses uneven depth resolution in volume rendering. It sets itself apart from Near-Far Linear Ray Generation by introducing a non-linear, inverse-depth interpolation for the far segment, and from Refined Ray Generation via PDF Sampling by using a deterministic geometric split rather than probability density function-based adaptive sampling.

### [Refined Ray Generation via PDF Sampling](6837-refined-ray-generation-via-pdf-sampling.md)
Generates higher-fidelity ray samples for volume rendering by resampling depth positions based on the probability distribution defined by previous iteration's weights. It improves upon the coarse sampling provided by the Grid Ray Sampler by concentrating samples in regions of high opacity or color change, thereby reducing noise and aliasing in the final render.

### [Near-Far Linear Ray Generation](6841-near-far-linear-ray-generation.md)
Samples points along camera rays using linear spacing from near to far, optionally applying random jitter within segments to reduce banding artifacts. It differs from its sibling Near-Middle-Far Ray Generation by using a single linear interpolation between near and far planes rather than splitting the depth range into distinct near, middle, and far regions. It is distinct from Refined Ray Generation via PDF Sampling as it does not use importance sampling or probability density functions, relying instead on deterministic or jittered uniform spacing.

### Ray Unification
**Definition:** A technique to map every ray starting location onto a sphere circumscribed around the view cell, ensuring that identical rays have identical depth values regardless of the camera position, easing the task for the oracle network [S3].

**Steps:**
1. For arbitrary views looking outside the view cell, map the ray origin to the circumscribed sphere [S3].
2. For 360-degree object captures, apply the scheme inversely by placing the circumscribed sphere around the object [S3].

**Parameters:**
- Ray unification adds about 0.6 dB in PSNR compared to no unification [S3].

**Pitfalls:**
- Without ray unification, the same ray is encoded differently depending on the starting location, requiring different depth values [S3].

## Operating characteristics
- **Time Complexity:** $O(N)$ where $N$ is the number of rays (either $H \times W$ or $N_{rays}$) [S2, unofficial].
- **Memory Complexity:** $O(N)$ for storing ray origins and directions [S2, unofficial].
- **Measured Performance:** Not given in the sources.
- **Scaling:** Scales linearly with the number of rays and batch size [S2, unofficial].
- **Strengths:** Provides a flexible way to sample rays either uniformly across the entire image or randomly for sparse sampling, which is useful for training efficiency [S2, unofficial].
- **Limitations:** Random sampling may miss important regions if not stratified, and full-grid sampling can be memory-intensive for high resolutions [G].
- **When to use:** Use for standard volume rendering or NeRF training where ray generation is a separate step from neural network inference. Use random sampling for memory-constrained environments or when focusing on specific regions.
- **When not:** Use [Ray Sampling and Neural Rendering Pipeline](4255-ray-sampling-and-neural-rendering-pipeline.md) if the ray generation is tightly coupled with neural network inference and feature extraction. Use [Near-Middle-Far Ray Generation](6817-near-middle-far-ray-generation.md) if depth resolution is a critical concern for distant objects.

## Background
The Grid Ray Sampler is a fundamental component in GPU-based ray generation for volume rendering and neural radiance fields. It is implemented in projects such as SolidVoxelization [S1, unofficial] and various NeRF training pipelines [S2, unofficial]. The method leverages GPU parallelism to generate rays efficiently, often using CUDA kernels or PyTorch operations [S1, S2, unofficial]. Ray unification, a related technique, was introduced in DONeRF to improve the performance of depth oracle networks by standardizing ray origins [S3].
