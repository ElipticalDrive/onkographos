# Multicam Ray Generation

Also called: Ray Generation (Multicam)

## Overview
Multicam Ray Generation constructs ray origins and directions for a multi-camera dataset by applying per-image metadata (intrinsic and extrinsic matrices) stored in a JSON file [S1, unofficial]. It differs from single-camera models by iterating over a collection of distinct camera poses, allowing the synthesis of views from multiple physical or virtual sensors [S1, unofficial].

## How it works
**Inputs and Outputs**
- **Inputs**: A list of camera metadata dictionaries (loaded from `metadata.json`), each containing `pix2cam` (3x3 intrinsic matrix), `cam2world` (4x4 extrinsic matrix), `width`, `height`, `lossmult`, `near`, and `far` [S1, unofficial].
- **Outputs**: Two tensors of shape `(H, W, 3)` for `origins` and `viewdirs`, and scalar attributes broadcasted to `(H, W)` for `lossmult`, `near`, and `far` [S1, unofficial].

**Data Structures**
- `pix2cam`: 3x3 matrix mapping pixel coordinates to camera frame directions [S1, unofficial].
- `cam2world`: 4x4 matrix mapping camera frame to world frame [S1, unofficial].
- `res2grid(w, h)`: Generates a meshgrid of pixel centers. Using `indexing='xy'`, it returns coordinates $(x+0.5, y+0.5)$ for $x \in [0, W-1]$ and $y \in [0, H-1]$ [S1, unofficial].

**Steps**
1. **Load Metadata**: Parse `metadata.json` to extract `pix2cam`, `cam2world`, `width`, `height`, `lossmult`, `near`, and `far` for the current image [S1, unofficial].
2. **Create Pixel Grid**: Generate pixel coordinates using `res2grid(width, height)` [S1, unofficial].
3. **Compute Camera Directions**:
   - Construct pixel direction vectors: $\mathbf{p} = [x, y, 1]$ [S1, unofficial].
   - Transform to camera frame: $\mathbf{d}_{cam} = \mathbf{p} \cdot \mathbf{K}^T$, where $\mathbf{K} = \text{pix2cam}[:3, :3]$ [S1, unofficial].
4. **Transform to World Space**:
   - Rotate directions: $\mathbf{d}_{world} = \mathbf{d}_{cam} \cdot \mathbf{R}^T$, where $\mathbf{R} = \text{cam2world}[:3, :3]$ [S1, unofficial].
   - Set origins: $\mathbf{o} = \text{broadcast}(\text{cam2world}[:3, -1])$ to match the shape of $\mathbf{d}_{world}$ [S1, unofficial].
5. **Normalize Directions**: Compute $\mathbf{v} = \frac{\mathbf{d}_{world}}{\|\mathbf{d}_{world}\|}$ to obtain `viewdirs` [S1, unofficial].
6. **Calculate Radii**:
   - Compute $\Delta x$, the distance between adjacent direction vectors, for each image [S1, unofficial].
   - Pad the last element of $\Delta x$ to match the spatial dimensions [S1, unofficial].
   - Calculate radii: $r = \frac{\Delta x \cdot 2}{\sqrt{12}}$ [S1, unofficial].
7. **Broadcast Attributes**: Expand `lossmult`, `near`, and `far` from scalars to tensors of shape `(H, W)` [S1, unofficial].

**Pseudocode**
```python
import torch
import numpy as np

def res2grid(w, h):
    """Returns meshgrid of (x+0.5, y+0.5) with indexing='xy'."""
    x = torch.arange(w, dtype=torch.float32) + 0.5
    y = torch.arange(h, dtype=torch.float32) + 0.5
    return torch.meshgrid(x, y, indexing='xy')

def generate_rays(metadata):
    """
    Generate rays for a single camera from metadata.
    metadata: dict with keys 'pix2cam', 'cam2world', 'width', 'height', 
              'lossmult', 'near', 'far'.
    """
    # 1. Load metadata
    K = metadata['pix2cam'][:3, :3]  # 3x3
    R = metadata['cam2world'][:3, :3]  # 3x3
    T = metadata['cam2world'][:3, 3]  # 3x1
    H, W = metadata['height'], metadata['width']
    
    # 2. Create pixel grid
    x, y = res2grid(W, H)  # Shape (H, W)
    
    # 3. Compute camera directions
    # pixel_dirs shape: (H, W, 3) -> [x, y, 1]
    pixel_dirs = torch.stack([x, y, torch.ones_like(x)], dim=-1)
    
    # camera_dirs = pixel_dirs @ K.T
    camera_dirs = torch.matmul(pixel_dirs, K.T)
    
    # 4. Transform to world space
    # directions = camera_dirs @ R.T
    directions = torch.matmul(camera_dirs, R.T)
    
    # origins = broadcast(T)
    origins = torch.broadcast_to(T, directions.shape)
    
    # 5. Normalize directions
    viewdirs = directions / torch.norm(directions, dim=-1, keepdim=True)
    
    # 6. Calculate radii
    # dx: distance between adjacent direction vectors
    # Approximation: compute norm of difference between adjacent viewdirs
    # Note: The source mentions calculating dx for each image and padding.
    # A robust implementation computes the angular separation.
    # For simplicity, assuming dx is derived from the grid spacing in direction space.
    # The source formula: radii = dx * 2 / sqrt(12)
    
    # Compute dx as the norm of the difference between adjacent normalized directions
    # along the x-axis (or average of x and y)
    # This step requires careful handling of boundaries.
    # Source says: "Calculate dx ... and pad the last element"
    
    # Example implementation for dx (x-direction):
    dx_x = torch.norm(viewdirs[:, 1:, :] - viewdirs[:, :-1, :], dim=-1)
    dx_x = torch.cat([dx_x, dx_x[:, -1:]], dim=1)  # Pad last element
    
    # Example implementation for dx (y-direction):
    dx_y = torch.norm(viewdirs[1:, :, :] - viewdirs[:-1, :, :], dim=-1)
    dx_y = torch.cat([dx_y, dx_y[-1:, :]], dim=0)  # Pad last element
    
    # Average dx
    dx = (dx_x + dx_y) / 2.0
    
    radii = dx * 2.0 / torch.sqrt(torch.tensor(12.0))
    
    # 7. Broadcast attributes
    loss_mult = torch.full((H, W), metadata['lossmult'])
    near = torch.full((H, W), metadata['near'])
    far = torch.full((H, W), metadata['far'])
    
    return origins, viewdirs, radii, loss_mult, near, far
```

**Edge Cases and Pitfalls**
- **Precision**: Normalization of directions must be performed after rotation to ensure unit length [S1, unofficial].
- **Boundaries**: Padding is required for `dx` calculation to maintain spatial dimensions [S1, unofficial].
- **Degenerate Input**: If `pix2cam` or `cam2world` are singular, ray generation will fail [G].

## Subtopics

### Panorama Projection
A variant where the image width must be exactly twice the height ($W = 2H$) to support correct equirectangular projection [S2]. This constraint ensures proper mapping of spherical coordinates to the 2D image plane [S2].

## Operating characteristics
- **Time Complexity**: $O(N)$ where $N = H \times W$, as each pixel is processed independently [G].
- **Memory Complexity**: $O(N)$ to store origins, directions, and attributes [G].
- **Strengths**: Efficiently handles multiple cameras by reusing the same ray generation logic with different metadata [S1, unofficial].
- **Limitations**: Requires pre-computed metadata for each camera [S1, unofficial].
- **When to Use**: Multi-view reconstruction, NeRF training with multiple cameras [S1, unofficial].
- **When Not to Use**: Single-camera scenarios where simpler ray generation suffices [G].

## Background
Originating from the CaSE-NeRF project, this method adapts standard NeRF ray generation for multi-camera datasets [S1, unofficial]. It relies on JSON-stored metadata for flexibility across different camera setups [S1, unofficial].
