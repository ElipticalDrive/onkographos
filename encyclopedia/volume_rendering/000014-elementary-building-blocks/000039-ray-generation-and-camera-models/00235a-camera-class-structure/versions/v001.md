# Camera Class Structure
Also called: Camera Layout, Camera Struct, Camera fields layout

## Overview
The Camera Class Structure defines the data layout and initialization protocol for storing camera state in ray marching and volume rendering applications. It serves as the primary interface for translating high-level camera parameters (position, orientation, clipping) into the geometric primitives required for ray generation. It differs from sibling methods like [Ray Origin and Direction Setup](1793-ray-origin-and-direction-setup.md) by encapsulating the state rather than just the computation, and from [Camera Matrix and Coordinate Transformation](6231-camera-matrix-and-coordinate-transformation.md) by often exposing raw vectors or quaternions instead of a pre-computed view matrix.

## How it works
### Inputs and Outputs
**Inputs**: Field of view (FOV), eye position, orientation (quaternion or basis vectors), near and far clipping planes.
**Outputs**: A contiguous memory block (struct) containing the camera parameters, accessible by shaders or CPU-side ray generation code.

### Data Structures
Two distinct layouts are observed in the source literature. Implementers must choose based on the rendering API and mathematical preferences.

**Layout A (WGPU/Rust Style)**
Defined in [S1, unofficial], this layout uses a fixed-size struct with explicit alignment.
*   `position`: `Vec3<f32>` (12 bytes)
*   `fov`: `f32` (4 bytes)
*   `orientation`: `Quat<f32>` (16 bytes)
*   `clip_near`: `f32` (4 bytes)
*   `clip_far`: `f32` (4 bytes)
*   **Total Size**: 40 bytes.
*   **Alignment**: 16 bytes (`#[repr(C, align(16))]`).

**Layout B (WebGPU/TypeScript Style)**
Defined in [S2, unofficial], this layout includes additional metadata for volume rendering and lighting.
*   `_forward`: `vec3`
*   `_up`: `vec3`
*   `_position`: `vec3`
*   `_zoom`: `vec3`
*   `_view`: `mat4`
*   `_lightDir`: `vec3`
*   `volumeCentre`: `vec3`
*   `volumeScale`: `vec3`

### Initialization
The camera is initialized via a constructor that validates and stores these parameters.

**Pseudocode (based on [S1, unofficial])**
```python
struct Camera:
    position: Vec3
    fov: f32
    orientation: Quat
    clip_near: f32
    clip_far: f32

    def new(fov: f32, position: Vec3, orientation: Quat, clip_near: f32, clip_far: f32) -> Camera:
        # Validate clipping planes
        if clip_near >= clip_far:
            raise Error("Near plane must be less than far plane")
        
        # Normalize orientation if not already normalized
        orientation = normalize(orientation)
        
        return Camera(
            position=position,
            fov=fov,
            orientation=orientation,
            clip_near=clip_near,
            clip_far=clip_far
        )
```

### Ray Generation Integration
While the struct stores state, it feeds into the ray generation process described in [Ray generation and camera models](770-ray-generation-and-camera-models.md). The `orientation` (quat) or `_view` matrix is used to transform pixel coordinates into world-space ray directions. The `clip_near` and `clip_far` define the valid range for depth sampling along the ray.

### Edge Cases and Pitfalls
1.  **Orientation Normalization**: Quaternions must be normalized to prevent scaling artifacts in rotation [S1, unofficial].
2.  **Clipping Plane Order**: `clip_near` must be strictly less than `clip_far` to avoid division by zero or invalid depth ranges [S1, unofficial].
3.  **Alignment Padding**: In Layout A, the 16-byte alignment ensures efficient GPU memory access, but requires careful packing if combined with other uniform buffers [S1, unofficial].
4.  **Zoom Vector Interpretation**: In Layout B, `_zoom` is a `vec3`, suggesting anisotropic scaling or aspect ratio handling, which is non-standard for simple pinhole cameras [S2, unofficial].

## Operating characteristics
*   **Memory**: Layout A is compact (40 bytes), suitable for per-camera uniform buffers. Layout B is larger and includes redundant data (e.g., storing both basis vectors and a view matrix).
*   **Performance**: Initialization is $O(1)$. Ray generation cost is independent of the camera struct size, depending only on the subsequent matrix/vector operations.
*   **Strengths**: Explicit control over camera parameters; easy serialization.
*   **Limitations**: Layout B mixes camera state with volume metadata (`volumeCentre`, `volumeScale`), coupling the camera to specific rendering contexts [S2, unofficial].

## Background
The concept of a camera struct is fundamental to computer graphics, originating from early ray tracers that required explicit eye position and direction vectors. The specific layouts cited here are from modern, unofficial implementations targeting WebGPU and Rust-based ray marching frameworks.
