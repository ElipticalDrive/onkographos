# Atomic Fragment List Insertion

Also called: Atomic Counter Voxelization, Linked List Voxel Output, LinkedListGather, PPLL Gather, ST-7

## Overview
Atomic Fragment List Insertion is a GPU-side algorithm for building a per-pixel linked list of fragments using atomic operations to handle concurrent writes from multiple fragments without locks [S1, unofficial]. It solves the problem of accumulating geometry fragments into a dynamic acceleration structure (A-buffer) for subsequent compositing or ray processing [S1, unofficial]. It differs from brute-force ray marching by avoiding empty space evaluation and from [Tiled Parallel Compositing](1192-tiled-parallel-compositing.md) by using a global atomic counter for list construction rather than tiled accumulation buffers [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Fragment color (vec4), fragment depth/distance (float), viewport dimensions (int), fragment buffer width (int).
*   **Output:** Updated `uStartOffsetTex` (texture storing head pointers per pixel), updated `uFragmentBufferTex` (texture storing fragment nodes), updated `uFragCounter` (global atomic counter).

**Data Structures:**
1.  **`uStartOffsetTex`**: A 2D texture (or image buffer) of size `ViewportW x ViewportH`. Each texel is a `uvec4`. The `r` component stores the linear index of the head of the linked list for that pixel. Initialized to `0xFFFFFFFF` (sentinel for empty list) by the [PPLL Clear Pass](2803-ppll-resolve-pass.md).
2.  **`uFragmentBufferTex`**: A 2D texture of size `FRAG_BUFFER_W x ceil(TotalFragments / FRAG_BUFFER_W)`. Each texel is a `uvec4` representing a fragment node.
    *   `r`: Packed color (rgba 10/10/10/10 bit format).
    *   `g`: Depth (float bits converted to uint).
    *   `b`: Next pointer (linear index of the next fragment in the list).
    *   `a`: Unused (0u).
3.  **`uFragCounter`**: A global atomic counter initialized to 0.

**Parameters:**
*   `FRAG_BUFFER_W`: Width of the fragment buffer image. Typical value: 2048 [S1, unofficial].

**Steps:**
1.  **Early Depth Cull:** If fragment depth `a < 1e-4`, return immediately [S1, unofficial].
2.  **Pixel Coordinates:** Calculate `x = int(gl_FragCoord.x)` and `y = int(gl_FragCoord.y)` [S1, unofficial].
3.  **Atomic Index Allocation:** Atomically increment `uFragCounter` to get a unique linear index: `insertIndex = atomicCounterIncrement(uFragCounter)` [S1, unofficial].
4.  **Buffer Full Check:** If `insertIndex >= uLinkedListSize` (total capacity), silently drop the fragment [S1, unofficial].
5.  **Head Pointer Swap:** Atomically exchange the head pointer for the pixel in `uStartOffsetTex` at `(x, y)` with `insertIndex`. The return value `oldHead` is the previous head [S1, unofficial].
    *   `oldHead = imageAtomicExchange(uStartOffsetTex, ivec2(x, y), insertIndex)` [S1, unofficial].
    *   This `oldHead` becomes the `next` pointer for the new fragment, effectively prepending it to the list [S1, unofficial].
6.  **Buffer Address Calculation:** Calculate the 2D coordinates in the fragment buffer:
    *   `fragAddr = ivec2(int(insertIndex) % FRAG_BUFFER_W, int(insertIndex) / FRAG_BUFFER_W)` [S1, unofficial].
7.  **Node Construction:** Build the fragment node:
    *   `frag.r = packColor(color)` (packed rgba 10/10/10/10) [S1, unofficial].
    *   `frag.g = floatBitsToUint(depth)` [S1, unofficial].
    *   `frag.b = oldHead` [S1, unofficial].
    *   `frag.a = 0u` [S1, unofficial].
8.  **Store Node:** Store the fragment node into `uFragmentBufferTex` at `fragAddr` [S1, unofficial].

**Pseudocode:**
```python
# Fragment Shader Entry Point
# Uniforms: uFragCounter (atomic counter), uStartOffsetTex (image2D), uFragmentBufferTex (image2D), uLinkedListSize (int), FRAG_BUFFER_W (int)
# Inputs: color (vec4), fragmentDistance (float)

def atomic_fragment_list_insertion(color, fragmentDistance):
    # 1. Early Depth Cull
    if color.a < 1e-4:
        return

    # 2. Pixel Coordinates
    x = int(gl_FragCoord.x)
    y = int(gl_FragCoord.y)

    # 3. Atomic Index Allocation
    insertIndex = atomicCounterIncrement(uFragCounter)

    # 4. Buffer Full Check
    if insertIndex >= uLinkedListSize:
        return

    # 5. Head Pointer Swap
    # imageAtomicExchange returns the old value at the location
    oldHead = imageAtomicExchange(uStartOffsetTex, ivec2(x, y), insertIndex)

    # 6. Buffer Address Calculation
    fragAddr = ivec2(insertIndex % FRAG_BUFFER_W, insertIndex / FRAG_BUFFER_W)

    # 7. Node Construction
    # Pack color into 10/10/10/10 format
    packedColor = packColor10101010(color)
    
    # Convert depth float to uint bits
    depthUint = floatBitsToUint(fragmentDistance)
    
    # Construct node: r=packedColor, g=depth, b=nextPtr, a=unused
    node = uvec4(packedColor, depthUint, oldHead, 0u)

    # 8. Store Node
    imageStore(uFragmentBufferTex, fragAddr, node)
```

**Edge Cases and Pitfalls:**
*   **Race Condition:** Using `imageAtomicExchange` ensures that two concurrent inserts do not read the same old head and overwrite each other, which would orphan the first fragment [S1, unofficial].
*   **Buffer Overflow:** If the fragment count exceeds `uLinkedListSize`, fragments are silently dropped. The application must ensure sufficient buffer size or handle the drop gracefully [S1, unofficial].
*   **Sentinel Value:** The initial value `0xFFFFFFFF` (-1u) must be used as the sentinel for empty lists. The resolve pass must recognize this value to terminate list traversal [S1, unofficial].

## Subtopics

### [PPLL Resolve Pass](2803-ppll-resolve-pass.md)
The PPLL Resolve Pass is a fragment shader pass that resolves a linked list of fragments per pixel into a final color by sorting and front-to-back blending. It takes the raw fragment data collected by the [Atomic Fragment List Insertion](2465-atomic-fragment-list-insertion.md) method and produces the final image, distinguishing itself from sibling methods like [A-buffer linked-list creation and ray processing](3878-a-buffer-linked-list-creation-and-ray-processing.md) by relying on a global atomic counter for list construction and a subsequent CPU/GPU synchronization to resolve the lists via sorting and blending.

### [A-buffer linked-list creation and ray processing](3878-a-buffer-linked-list-creation-and-ray-processing.md)
This method constructs a dynamic acceleration structure (A-buffer) on the GPU to efficiently identify which segment primitives overlap a given ray, avoiding the evaluation of empty space in expensive field computations. It differs from brute-force ray marching by using a geometry shader to generate quads covering primitive supports and a fragment shader to compute ray-support intersections, storing entry/exit points in a linked list. Unlike [Bru19], which requires explicit cutoff of primitive influences, this approach leverages compact support kernels (specifically clipped sphere-cones for Cauchy kernels) to naturally limit the interaction domain.

### PPLL Clear Pass
A fullscreen quad render pass that initializes the per-pixel linked list start offset texture. It writes the sentinel value `0xFFFFFFFF` (-1u) to indicate an empty list [S1, unofficial].
**Steps:**
1.  Calculate pixel coordinates `x = int(gl_FragCoord.x)`, `y = int(gl_FragCoord.y)`. If `x >= uViewportW` or `y >= uViewportH`, return [S1, unofficial].
2.  Write sentinel to start offset texture: `imageStore(uStartOffsetTex, ivec2(x, y), uvec4(0xFFFFFFFFu, 0u, 0u, 0u))` [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** O(1) per fragment for insertion. The global atomic counter increment is the primary contention point.
*   **Memory Complexity:** O(N) where N is the maximum number of fragments. The fragment buffer size is determined by `FRAG_BUFFER_W` and the total fragment count.
*   **Strengths:** Lock-free, simple to implement, handles arbitrary fragment counts (up to buffer limit), works well with geometry shaders or fragment shaders outputting multiple fragments.
*   **Limitations:** Atomic counter contention can become a bottleneck with very high fragment counts. Buffer overflow requires careful sizing. List resolution requires additional passes (sorting/compositing).
*   **When to use:** When fragment count is moderate, and simplicity of implementation is prioritized over maximum throughput for extremely high-density scenes. Suitable for pre-passes in volume rendering pipelines.
*   **When not to use:** When fragment count exceeds available buffer memory, or when extremely high throughput is required and atomic contention is a proven bottleneck (consider [Tiled Parallel Compositing](1192-tiled-parallel-compositing.md) or [Parallel Direct Compositing](3201-parallel-direct-compositing.md)).

## Background
Originated in the context of GPU-based volume rendering and A-buffer techniques.
