# A-buffer linked-list creation and ray processing

Also called: A-buffer linked-list creation, Ray processing with A-buffer linked-list

## Overview
This method constructs a dynamic acceleration structure (A-buffer) on the GPU to efficiently identify which segment primitives overlap a given ray, avoiding the evaluation of empty space in expensive field computations [S1]. It differs from brute-force ray marching by using a geometry shader to generate quads covering primitive supports and a fragment shader to compute ray-support intersections, storing entry/exit points in a linked list [S1]. Unlike [Bru19], which requires explicit cutoff of primitive influences, this approach leverages compact support kernels (specifically clipped sphere-cones for Cauchy kernels) to naturally limit the interaction domain [S1].

## How it works
The method consists of two main phases: A-buffer construction (creation of the linked list) and Ray processing (traversal of the linked list to find the isosurface).

### Inputs and Outputs
*   **Inputs**:
    *   Skeleton data: A set of segment primitives, each defined by endpoints, radius, and potentially varying radius profiles.
    *   Kernel parameters: Scale parameter $\sigma$, clipping parameters ($\sigma_{clipping}, \epsilon_{clipping}$ for Cauchy kernels).
    *   Camera parameters: Ray origin and direction for each pixel $(i, j)$.
    *   Occlusion data: An occluding depth buffer (optional, for output sensitivity).
*   **Outputs**:
    *   For each pixel, a linked list of fragments (intervals) sorted by entry depth.
    *   The final isosurface intersection point or color.

### Data Structures
1.  **A-Buffer Linked List**: Per pixel, a linked list of fragments. Each fragment stores:
    *   `zIn`: Entry depth into the primitive support.
    *   `zOut`: Exit depth from the primitive support.
    *   `segId`: Identifier of the segment primitive.
    *   The list is sorted by `zIn` [S1].
2.  **Processing Heaps (Per Ray)**:
    *   `primitives`: A min-heap (priority queue) storing `{zOut, segId}` pairs, ordered by `zOut`. Represents primitives currently active in the ray traversal.
    *   `argmins`: A min-heap storing `{t_prim, ...}` pairs, ordered by `t_prim` (the parameter minimizing the field derivative or similar metric). Represents the next candidate for field evaluation [S1].

### Step 1: A-Buffer Construction
1.  **Occluding Depth Buffer Initialization (Optional)**:
    *   Render an occluding depth buffer to achieve output sensitivity and limit primitives registered in linked lists [S1].
    *   Initialize the depth buffer with depth values corresponding to positions guaranteed to be in the volume [S1].
    *   Compute these depth values in a first render path on a per-primitive basis [S1].
    *   Due to the integral formulation of the field, the minimal radius around primitives does not necessarily correspond to the prescribed radius (e.g., for bent skeletons) [S1]. To overcome this, rely on two assumptions: usage of skeleton end-point correctors and bounded radius variations (none of the two spheres at a primitive end-point completely encompasses the other) [S1].
    *   Do not render occluders for primitives corresponding to end-point correctors [S1].
    *   Derive a scaling factor for the sphere cones' radii such that the implicit surface is guaranteed to enclose the modified primitives, based on the worst skeleton configuration and the scale-invariant property of the SCALIS representation [S1]. The quality of the minimal volume is related to the kernel scale parameter; larger scale means smaller guaranteed volume [S1].
    *   For typical Compact polynomial kernel scale $\sigma$ ranging from 1.5 to 2, the scaling factor ranges from $\approx 0.62$ to $\approx 0.35$ [S1]. For more constrained radius variations (constant radius), better bounds can be computed [S1].
    *   Ignore primitives whose support entries are beyond the occluding depth [S1].

2.  **Primitive Support Generation**:
    *   Generate segment-aligned quads to limit the number of generated fragments for which ray/sphere-cone intersections are computed, particularly for primitives whose maximal radii are comparatively small to the segment length [S1].
    *   Use a compact support kernel to avoid the need to cut-off primitive influences in this first step [S1].

3.  **Ray-Support Intersection and List Insertion**:
    *   Compute ray-support intersections for primitives in a fragment shader [S1].
    *   Insert entry and exit points in sphere-cones and the associated primitive ID into an A-buffer linked-list [S1].
    *   Sort the linked list on the fly according to the depth of the entry [LHL14].

### Step 2: Ray Processing
The fragment shader generates and processes intervals on-the-fly using Algorithm 1 until an intersection with the isosurface is found [S1]. The resulting linked-list processing loop is given in Algorithm 2 [S1].

**Algorithm 2: Processing Linked List**

```python
def GenerateRay(i, j):
    # Initialize heaps and fragment list
    primitives = emptyHeap()  # Min-heap of {zOut, segId}
    argmins = emptyHeap()     # Min-heap of {t_prim, ...}
    frags = InitFragList(i, j) # Get sorted linked list of fragments for pixel (i,j)
    
    targmin = infinity
    tentry = frags.currZIn()
    
    # Loop until both heaps and fragment list are empty
    while not (frags.empty() and primitives.empty()):
        tb, hb = te, he  # Current interval bounds and field data
        
        # Get the exit of the last active primitive
        if not primitives.empty():
            texit = primitives.back().val
        else:
            texit = infinity
            
        # Determine if we need to pull more fragments or if the current interval is valid
        if primitives.empty() or targmin < texit or tentry < texit:
            # If no primitives are active, the field is null
            if primitives.empty():
                tb, hb = tentry, (g(0), ...) # Field is zero
                # See text for management of entry/exit of non-null field area
            
            # Pull fragments from the A-buffer linked list into the heaps
            while targmin > tentry and not frags.empty():
                # Find the primitive that minimizes the field derivative/parameter
                tprim = Argmin(sigma, frags.currSegId())
                
                # Add the current fragment's exit to the active primitives heap
                tout = frags.currZOut()
                primitives.insert({tout, frags.currSegId()})
                
                # Add the candidate parameter to the argmins heap
                argmins.insert(tprim)
                
                # Update the target minimum
                targmin = argmins.front()
                
                # Move to the next fragment
                frags.next()
                
                # Update the next entry point
                if not frags.empty():
                    tentry = frags.currZIn()
                else:
                    tentry = infinity
                    
        # Determine the next interval [te, he]
        if tb < te:
            # Process the interval [tb, hb] to [te, he]
            f, t = processInterval(tb, hb, te, he)
            if f:
                GenerateIsoSurface(t)
                return
        else:
            # If tb >= te, the interval is invalid or null
            # See text for management of entry/exit of non-null field area
            pass
            
        # Remove primitives that have exited before the current interval end
        primitives.popElements(lambda x: x <= te)
        argmins.popElements(lambda x: x <= te)
        
        # Update the target minimum
        if not argmins.empty():
            targmin = argmins.front()
        else:
            targmin = infinity
```

**Details on `processInterval` and Numerical Stability**:
*   Due to possible numerical instability in the normalized field derivative computation (the latter being non-continuous when the field switches from null to non-null), apply one step of sphere tracing to avoid those areas [S1]. Note that this requires no field evaluation as the field is null at the support limit [S1].
*   The `processInterval` function evaluates the field and its derivative within the interval $[tb, te]$ using the Hermite data $(te, he)$ and $(tb, hb)$ [S1].
*   If an intersection with the isosurface is found, return the point $t$ [S1].

**Subdivision Strategy**:
*   Combine the second subdivision strategy (switching between overlapped/non-overlapped areas) with the contribution from section 3 to limit the number of segment primitives stored at once while generating long enough intervals to limit compulsory field evaluations [S1].
*   This presents a trade-off: it limits the number of segment primitives to be stored at once while generating long enough intervals, hence limiting the number of compulsory field evaluations [S1].

**Blending**:
*   It is possible to blend different skeletons with a blending sharper than summation blending, e.g., using Ricci's blending [Ric73]. This keeps the correlation of the field with the homothetic squared distance to individual primitives by defining a blending behavior parametrized between a summation blend and a maximum blend [S1].

### Parameters
*   **Kernel Scale ($\sigma$)**: For typical Compact polynomial kernel scale $\sigma$ ranging from 1.5 to 2, the scaling factor ranges from $\approx 0.62$ to $\approx 0.35$ [S1].
*   **Cauchy Kernel Parameters**: For Cauchy kernel tests, $\sigma_{clipping} = 4$ for $\sigma = 0.3$ and $\epsilon_{clipping} = 0.005$ [S1].
*   **Sphere-Tracing Steps**: On each subinterval, the number of sphere-tracing steps is bounded (typically 256) [S1].
*   **Subdivisions per Primitive**: In the implementation of Sherstyuk's method, use four subdivisions per primitive, which is the coarsest subdivision allowing visually acceptable results on primitives with constant radius [S1].

### Edge Cases and Pitfalls
*   **Numerical Instability**: Occurs in the normalized field derivative computation because it is non-continuous when the field switches from null to non-null. Apply one step of sphere tracing to avoid these areas [S1].
*   **Minimal Radius Discrepancy**: Due to the integral formulation of the field, the minimal radius around primitives does not necessarily correspond to the prescribed radius (e.g., for bent skeletons). Overcome this by relying on skeleton end-point correctors and bounded radius variations [S1].
*   **Visual Artifacts**: Sphere-tracing and Sherstyuk's fast ray tracing can present visual artifacts. In the presence of a large amount of blending (e.g., many segments connecting at one vertex), sphere-tracing algorithms require under-relaxation to properly find the surface [S1].
*   **A-Buffer Overflow**: For kernels with larger footprints (e.g., Cauchy), ensure the A-buffer size is sufficient to avoid overflow, as this leads to an increase in computational time [S1].

## Operating characteristics
*   **Time Complexity**: The method reduces rendering time compared to sphere tracing. For compact polynomial kernel at 2048x2048 resolution: Intel UHD Graphics 630 reduction from -34.2% to -48.7%; nVidia Quadro P1000 reduction from -51.5% to -78.0%; nVidia GeForce 2080 RTX reduction from -35.3% to -72.1% compared to the most competitive alternative method [S1]. For Cauchy kernel tests on nVidia RTX at 1536x1536 resolution: Timings range from 7 to 54 milliseconds (excluding Fig.12 Middle). Rendering time reduction compared to sphere tracing ranges from -46.2% to -81.3% [S1].
*   **Memory Complexity**: The method limits the number of segment primitives stored at once by combining subdivision strategies, thus limiting memory usage per thread [S1]. Usage of occluders can have a large impact in terms of rendering time (as well as memory consumption) depending on the nature of the skeleton [S1].
*   **Measured Performance**: Stress test on nVidia RTX: rendered a foam structure consisting of 526k segments using the compact polynomial kernel at 15 frames per second [S1]. Similar improvements observed on other GPUs at 1024x1024 resolution [S1].
*   **Strengths**: Avoids evaluation of empty space; output sensitivity via occluding depth buffer; handles varying radii and complex skeletons; real-time rendering capabilities [S1].
*   **Limitations**: Numerical instability at field boundaries; potential visual artifacts with high blending; requires careful tuning of kernel parameters and subdivision strategies [S1].
*   **When to Use**: Suitable for real-time rendering of skeleton-based implicit surfaces, especially when primitives have compact support and varying radii [S1].
*   **When Not to Use**: Not suitable for kernels with very large footprints without sufficient A-buffer size; may require under-relaxation for high blending scenarios [S1].

## Background
*   **Origin**: The method is based on the work presented in "Fast Ray Tracing of Scale-Invariant Integral Surfaces" [S1].
*   **History**: The approach builds upon previous work on A-buffers [LHL14] and sphere-tracing optimizations [Bru19]. It incorporates insights from Sherstyuk's fast ray-tracing [She99] and segment-tracing [GGPP20].
*   **Usage**: Implemented in C++ using OpenGL, with shaders in GLSL. Tested on Intel UHD Graphics 630, nVidia Quadro P1000, and nVidia GeForce 2080 RTX. Tested on artistic shapes, truss structures, branching structures, procedural foam structures, and random skeletons [S1].
