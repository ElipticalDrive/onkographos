# Double Buffer Shuffling

Also called: DBShuffle

## Overview
Double Buffer Shuffling (DBShuffle) is a warp-level reduction technique that allocates two `float4` buffers from the register space of each thread to perform parallel reductions [S1]. It splits the reduction workload across two halves of the warp, mitigating the active thread reduction issue found in single-buffer approaches [S1]. It builds on [Warp Shuffling](4949-warp-shuffling.md) by introducing a dual-buffer mechanism to handle divergent shuffling sources [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** Values to be reduced, stored in thread registers [S1].
*   **Output:** The reduced result (e.g., sum, max) available in the registers of all threads in the warp [S1].

**Data Structures:**
*   Each thread allocates two `float4` buffers from its local register space, denoted as $B_1$ and $B_2$ [S1].
*   The warp size is denoted as $W$ [S1].

**Algorithm Steps:**
The reduction proceeds in cycles. Each cycle consists of two distinct phases to handle the divergent shuffling sources [S1]:

1.  **Buffer 1 Reduction:** All threads in the warp shuffle their $B_1$ values to the first half of the warp [S1]. Only the threads in the first half ($0 \le \text{threadID} < W/2$) are active [S1]. These active threads perform one step of reduction on the received values [S1]. The result is stored back into $B_1$ of the active threads [S1].
2.  **Buffer 2 Reduction:** All threads in the warp shuffle their $B_2$ values to the second half of the warp [S1]. Only the threads in the second half ($W/2 \le \text{threadID} < W$) are active [S1]. These active threads perform one step of reduction on the received values [S1]. The result is stored back into $B_2$ of the active threads [S1].

**Pseudocode:**
```python
# Simulated warp register file for shuffle operations
warp_regs = [None] * warp_size

def double_buffer_shuffle_reduce(b1, b2, thread_id, warp_size=32):
    half = warp_size // 2
    
    # Phase 1: Buffer 1 reduction in the first half of the warp
    # All threads shuffle their B1 values to the first half warp
    if thread_id < half:
        partner = thread_id ^ 1
        if partner < half:
            b1 = reduce_op(b1, shfl(b1, partner))
    else:
        # Threads in the second half shuffle B1 to the first half
        shfl_store(thread_id - half, b1)

    # Phase 2: Buffer 2 reduction in the second half of the warp
    # All threads shuffle their B2 values to the second half warp
    if thread_id >= half:
        local_id = thread_id - half
        partner = local_id ^ 1
        if partner < half:
            b2 = reduce_op(b2, shfl(b2, partner + half))
    else:
        # Threads in the first half shuffle B2 to the second half
        shfl_store(thread_id + half, b2)

    return b1, b2

def shfl(value, src_thread_id):
    # Simulates hardware warp shuffle: returns value from src_thread_id
    return warp_regs[src_thread_id]

def shfl_store(dst_thread_id, value):
    # Simulates hardware warp shuffle store: writes value to dst_thread_id
    warp_regs[dst_thread_id] = value

def reduce_op(a, b):
    # Standard reduction operation (e.g., addition)
    return a + b
```

**Parameters:**
*   **Warp Size:** Default is 32 [S1].
*   **Buffer Type:** `float4` [S1].

**Edge Cases and Pitfalls:**
*   **Divergent Branching:** The method requires divergent branching because the shuffling sources and reduction targets differ for Buffer 1 and Buffer 2 [S1].
*   **Active Threads:** Only half a warp is active in each step, which can lead to underutilization if not managed correctly [S1].
*   **Precision:** Not given in the sources.

## Subtopics

### [Double Buffer Shared Warp Marching](8113-double-buffer-shared-warp-marching.md)
A pipeline manner reduction approach (double buffer color blending) to mitigate the active thread reduction issue in SBShared. The warp delays blending until all threads have received enough data.

## Operating characteristics
*   **Time Complexity:** Not given in the sources [S1].
*   **Memory Complexity:** Uses two `float4` buffers per thread from register space [S1].
*   **Performance:** The source mentions performance improvements from optimizations including DBShuffle in the context of 1D Warp Marching, but specific speedup numbers are not provided in the excerpt [S1].
*   **Strengths:** Mitigates the active thread reduction issue by splitting the workload [S1].
*   **Limitations:** Introduces divergent branching, requiring the step to be divided into two separate steps with only half a warp active in each [S1].

## Background
Double Buffer Shuffling is described in the context of cache-friendly sampling strategies for texture-based volume rendering on GPU [S1]. It is presented as an optimization for the 1D Warp Marching algorithm [S1].
