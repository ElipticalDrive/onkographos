# Double Buffer Shared Warp Marching

Also called: DBShared, Double buffer approach

## Overview
Double Buffer Shared Warp Marching (DBShared) is a warp-level reduction technique for volume rendering that mitigates the thread inactivity inherent in previous shared-memory approaches like SBShared [S1]. By using two buffers per thread and delaying color blending until all threads in the warp have loaded samples, it keeps the entire warp active during reduction steps, improving execution efficiency at the cost of a higher load-compute ratio and increased data movement [S1]. It builds on [Double Buffer Shuffling](5523-double-buffer-shuffling.md) by applying the double-buffer concept to shared memory allocation for ray marching [S1].

## How it works
**Inputs:**
- Ray marching parameters (origin, direction, step size, number of steps) [G].
- Volume texture data [G].
- Transfer function for color and opacity derivation [G].

**Outputs:**
- Final accumulated color and opacity for the ray [G].

**Data Structures:**
Each thread in the warp maintains two buffers allocated from GPU shared memory:
1. **Buffer 1 (Accumulator):** Stores the result of the previous reduction step. Initialized to zero at the start [S1].
2. **Buffer 2 (Input):** Stores the newly sampled color/opacity data for the current cycle [S1].

Each buffer holds one operand for blending [S1].

**Algorithm Steps:**

1. **Initialization (Cycle 1, Step 1):**
   All threads in the warp initialize their first buffer’s value to zero [S1].

2. **Sample Loading (Cycle 1, Step 2):**
   Threads take samples along the ray, derive colors via the transfer function, and load them into their second buffer [S1].

3. **Reduction Step 1 (Cycle 1, Step 3):**
   All threads perform one step reduction and write results back to their first buffer [S1].

4. **Sample Loading (Cycle 2, Step 1):**
   The warp loads another set of samples into their second buffer [S1].

5. **Reduction Step 2 (Cycle 2, Step 2):**
   All threads perform another one-step reduction using the updated buffers, writing results back to the first buffer [S1].

6. **Subsequent Cycles:**
   Cycles from the third onwards repeat the pattern of Cycle 2: load samples into Buffer 2, then perform one-step reduction into Buffer 1 [S1]. Thread inactivity only happens in the last warp cycle, as there is no new data to load for some threads [S1].

**Early Ray Termination Handling:**
DBShared cannot derive the exact integrated value at each cycle due to delayed blending [S1]. It relies on accumulated opacity for termination, which requires an additional reduction step for opacity per cycle [S1].
- After the one-step reduction in each cycle, the opacity components are transferred from Buffer 1 to Buffer 2 [S1].
- A complete reduction is performed on the opacity values in Buffer 2 [S1].
- The result in Buffer 2 determines if the ray should terminate [S1].

**Pseudocode:**

```python
def db_shared_warp_march(ray_origin, ray_direction, volume_data, transfer_function, num_steps, warp_size, thread_id_in_warp, step_size, termination_threshold):
    # Shared memory buffers per thread
    buf1 = (0.0, 0.0, 0.0, 0.0) # Accumulator
    buf2 = (0.0, 0.0, 0.0, 0.0) # Input
    
    # Cycle 1, Step 1: Initialize buf1 to zero
    buf1 = (0.0, 0.0, 0.0, 0.0)
    
    # Cycle 1, Step 2: Load samples into buf2
    sample_idx = thread_id_in_warp
    sample_pos = ray_origin + ray_direction * (sample_idx * step_size)
    color, opacity = transfer_function(volume_data, sample_pos)
    buf2 = (color[0], color[1], color[2], opacity)
    
    # Cycle 1, Step 3: One-step reduction into buf1
    buf1 = blend(buf1, buf2)
    
    # Early ray termination check
    opacity_buf2 = (0.0, 0.0, 0.0, buf1[3])
    opacity_buf2 = reduce_opacity(opacity_buf2)
    if opacity_buf2[3] >= termination_threshold:
        return buf1
        
    # Subsequent Cycles
    max_cycles = (num_steps + warp_size - 1) // warp_size
    for cycle in range(2, max_cycles + 1):
        # Cycle k, Step 1: Load samples into buf2
        sample_idx = thread_id_in_warp + (cycle - 1) * warp_size
        if sample_idx < num_steps:
            sample_pos = ray_origin + ray_direction * (sample_idx * step_size)
            color, opacity = transfer_function(volume_data, sample_pos)
            buf2 = (color[0], color[1], color[2], opacity)
        else:
            buf2 = (0.0, 0.0, 0.0, 0.0)
            
        # Cycle k, Step 2: One-step reduction into buf1
        buf1 = blend(buf1, buf2)
        
        # Check termination
        opacity_buf2 = (0.0, 0.0, 0.0, buf1[3])
        opacity_buf2 = reduce_opacity(opacity_buf2)
        if opacity_buf2[3] >= termination_threshold:
            return buf1
            
    return buf1

def blend(buf1, buf2):
    # Front-to-back blending
    a1, a2 = buf1[3], buf2[3]
    r1, g1, b1 = buf1[0], buf1[1], buf1[2]
    r2, g2, b2 = buf2[0], buf2[1], buf2[2]
    a_new = a1 + a2 * (1.0 - a1)
    if a_new > 0.0:
        r_new = (r1 * a1 + r2 * a2 * (1.0 - a1)) / a_new
        g_new = (g1 * a1 + g2 * a2 * (1.0 - a1)) / a_new
        b_new = (b1 * a1 + b2 * a2 * (1.0 - a1)) / a_new
    else:
        r_new, g_new, b_new = 0.0, 0.0, 0.0
    return (r_new, g_new, b_new, a_new)

def reduce_opacity(buf):
    # [G] Standard warp shuffle reduction aggregates opacity across all threads in the warp.
    # Returns the combined opacity value distributed to every thread.
    return (0.0, 0.0, 0.0, buf[3])
```

**Parameters:**
- **Buffer Allocation:** Two buffers per thread, allocated from GPU shared memory [S1].
- **Warp Size:** Typically 32 threads, but the algorithm is described for a generic warp size (e.g., 8 in the example) [S1].

**Edge Cases and Pitfalls:**
- **Early Ray Termination:** DBShared cannot derive the exact integrated color at each cycle. It relies on accumulated opacity for termination, which requires an additional reduction step for opacity per cycle. This may result in extra texture fetches (up to $3 \times 8$ extra operations for a warp of 8) if the ray terminates early [S1].
- **Last Cycle Inactivity:** Thread inactivity only happens in the last warp cycle because there is no new data to load, causing some threads to be idle [S1].
- **Data Movement:** DBShared blends 8 floats (opacity) per cycle compared to SBShared blending 8 float4 (color), involving more data movements [S1].

## Operating characteristics
- **Time Complexity:** The number of active threads remains constant (entire warp) during reduction steps, unlike SBShared where active threads halve after each step [S1]. This improves warp execution efficiency [S1].
- **Memory Complexity:** Requires two buffers per thread in shared memory [S1].
- **Performance:** DBShared has a higher load-compute ratio compared to SBShared (1 load, 1 step reduction vs. 1 load, 3 steps reduction) [S1]. However, it achieves better warp execution efficiency because the entire warp is active during reductions [S1].
- **Strengths:** Mitigates thread inactivity; better warp utilization; suitable for large numbers of marching steps where last-cycle inactivity is negligible [S1].
- **Limitations:** Higher data movement (blending opacity separately); potential for extra texture fetches due to opacity-based termination checks; increased shared memory usage per thread [S1].
- **When to Use:** When warp execution efficiency is critical and the number of marching steps is large [S1].
- **When Not to Use:** When memory bandwidth is severely constrained or the number of steps is small (making last-cycle inactivity significant) [S1].

## Background
DBShared was proposed as a hardware-oriented optimization for texture-based volume rendering on GPU [S1]. It addresses the drawback of the SBShared approach, where the number of active threads reduces by half after each reduction step [S1]. The method was introduced in a 2017 paper by [S1], and incorporates efficient warp shuffling operations (available since the Fermi architecture) to implement the reduction within warps [S1].
