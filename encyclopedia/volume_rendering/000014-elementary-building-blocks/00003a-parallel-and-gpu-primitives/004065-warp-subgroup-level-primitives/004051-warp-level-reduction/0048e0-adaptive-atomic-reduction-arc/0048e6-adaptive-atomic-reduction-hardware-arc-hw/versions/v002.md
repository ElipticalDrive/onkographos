# Adaptive Atomic ReduCtion Hardware (ARC-HW)

Also called: ARC-HW, atomred

## Overview
ARC-HW is a hardware-software cooperative primitive that accelerates commutative atomic additions in differentiable rendering by performing warp-level reduction within the Streaming Multiprocessor (SM) and dynamically distributing the remaining atomic computation between the SM and L2 ROP units [S1]. It addresses the bottleneck of irregular atomic updates where only a subset of threads in a warp generate atomic updates, and the high throughput requirements that overwhelm standard hardware queues [S1]. Unlike its software counterpart [Adaptive Atomic ReduCtion Software (ARC-SW)](12373-adaptive-atomic-reduction-software-arc-sw.md), ARC-HW eliminates instruction overheads, redundant computation, and control flow divergence by implementing the reduction logic directly in hardware, requiring no programmer intervention or tuning of balancing thresholds [S1].

## How it works
### Inputs and Outputs
*   **Input:** A memory address `%addr` and a floating-point value `%f` to be added atomically [S1].
*   **Output:** The memory location `%addr` is updated with the sum of all `%f` values from active threads in the warp [S1]. The instruction has no return value [S1].

### Data Structures and Layout
The implementation relies on two key hardware modules within each of the 4 sub-cores of an SM [S1]:

1.  **ARC Scheduler Module:**
    *   **Inputs:** `From ARC Scheduler` (control signal), `Register File` (data), `Thread Mask` (active thread identification), `Memory Addresses` (coalesced addresses), `Atomic Ops to ROP` (dispatch signal) [S1].
    *   **Outputs:** `TM1`, `TM2` (thread masks), `Reduction Unit` (dispatch signal), `Atomic Ops to ROP` (dispatch signal) [S1].
    *   **Function:** Decides whether to schedule the atomic update to the L2 ROP units or to the SM reduction unit based on ROP utilization [S1].

2.  **ARC Reduction Unit:**
    *   **Components:** A dedicated Floating Point Unit (FPU) per sub-core, an accumulator, and logic to interface with the Load/Store Unit (LSU) [S1].
    *   **Function:** Serially sums gradients from active threads using the thread mask and memory addresses, then issues a single atomic add request to the memory interface [S1].

### Algorithm Steps
The execution of the `atomred` instruction follows this workflow [S1]:

1.  **Dispatch:** The `atomred [%addr], %f` instruction is dispatched to the ARC Scheduler unit [S1].
2.  **Scheduling Decision:** The ARC Scheduler determines the execution path based on the utilization of the L2 ROP units [S1]:
    *   If ROP units are **not stalled** (free), the instruction is sent to the address coalescing unit to generate regular atomic requests for the ROPs [S1].
    *   If ROP units are **busy** (stalled), the instruction is scheduled for warp-level reduction in the sub-core's reduction unit [S1].
    *   The scheduler uses a greedy algorithm, observing atomic stalls at the LDST units to determine ROP availability [S1].
3.  **Active Thread Identification:** To identify threads updating the same parameter, ARC-HW leverages the address coalescing module used for load operations [S1]. It generates a thread mask for each memory location being updated atomically in the warp [S1]. Only threads in this mask participate in the reduction [S1].
4.  **Warp-level Reduction:**
    *   The reduction unit fetches values from the Register File using the thread mask and memory addresses [S1].
    *   It accumulates the result using the dedicated FPU [S1].
    *   The FPU performs a floating-point addition [S1].
    *   Once additions across all threads in the warp are reduced, the aggregated update is sent to the LSU to update the memory location in global memory [S1].
5.  **Completion:** The instruction completes without returning a value [S1]. The coherence protocols must be updated to include ARC reduction units for visibility, though overhead is negligible if the same data is never read/updated across multiple SMs concurrently [S1].

### Pseudocode
The following pseudocode represents the hardware logic within a single sub-core for the `atomred` instruction. It is a self-contained simulation of the hardware flow using standard Python operations.

```python
def arc_hw_atomred(addr, f_val, warp_active_mask):
    """
    Simulates the hardware logic for the atomred instruction within a single SM sub-core.
    warp_active_mask: list of booleans (length 32) indicating which threads in the warp
                      are updating the same memory address 'addr'.
    """
    # Step 1: Dispatch to ARC Scheduler
    # Hardware: Instructions are dispatched to the ARC Scheduler unit [S1].
    
    # Step 2: Scheduling Decision (Greedy Algorithm)
    # Hardware: Scheduler checks ROP utilization via LDST stall status [S1].
    # In hardware, this is a direct read of a status register from the LSU/ROP interface [G].
    rop_stalled = False  # Hardware status flag [G]
    
    if not rop_stalled:
        # Path A: ROP units are free.
        # Hardware: Instruction sent to address coalescing unit to generate regular atomic requests for ROPs [S1].
        # Simulation: Direct atomic update to the memory interface.
        global_memory[addr] += f_val
    else:
        # Path B: ROP units are busy.
        # Hardware: Instruction scheduled for warp-level reduction in the sub-core's reduction unit [S1].
        
        # Step 3: Active Thread Identification
        # Hardware: Leverages address coalescing module to generate a thread mask for 'addr' [S1].
        # Simulation: 'warp_active_mask' is provided by the coalescing logic.
        
        # Step 4: Warp-level Reduction
        # Hardware: Reduction unit serially sums gradients using a dedicated FPU [S1].
        reduced_sum = 0.0
        for lane in range(32):
            if warp_active_mask[lane]:
                # Hardware: Fetches value from Register File using thread mask and memory addresses [S1].
                thread_val = f_val  # Each thread's register holds its specific gradient value
                # Hardware: Accumulates result using dedicated FPU (FP addition) [S1].
                reduced_sum = reduced_sum + thread_val
        
        # Step 5: Issue Atomic Op
        # Hardware: Aggregated update sent to LSU to atomically update global memory [S1].
        global_memory[addr] += reduced_sum

# Simulation memory interface
global_memory = {}
```

### Parameters
*   **Balancing Threshold:** Not used in ARC-HW [S1]. The dynamic scheduling based on ROP utilization replaces the static balancing threshold required by ARC-SW [S1].
*   **Area Overhead:** Approximately 0.047% of total transistors on an RTX 4090 (76 billion transistors), estimated at 70K transistors per FPU sub-core [S1].

### Edge Cases and Pitfalls
*   **Coherence:** ARC reduction units must be included in GPU coherence protocols to be visible to the rest of the GPU [S1]. In differentiable rendering workloads, the same data is never read and updated across multiple SMs concurrently, making the additional coherence overhead negligible [S1].
*   **Commutativity:** The `atomred` instruction assumes commutative atomic additions [S1]. It provides no ordering guarantees and should only be used for operations where the order of addition does not affect the result (e.g., gradient accumulation) [S1].
*   **Precision:** The reduction is performed using the dedicated FPU in the sub-core [S1]. Standard floating-point precision applies [S1].

## Subtopics

### Adaptive Atomic ReduCtion Software (ARC-SW)
A software-only implementation using existing warp-level primitives (e.g., `shfl`) to perform warp-level reduction [S1]. It requires a tunable balancing threshold, all threads to be active (or zero-value updates), and incurs redundant computation and control flow overhead [S1]. Choose ARC-SW when hardware modification is not possible or for GPUs lacking specific hardware support (e.g., Intel GPUs) [S1]. [Link](12373-adaptive-atomic-reduction-software-arc-sw.md)

## Operating characteristics
*   **Time Complexity:** The warp-level reduction is performed serially within the sub-core's FPU, taking time proportional to the number of active threads in the warp [S1]. However, this is amortized by the reduction in atomic memory transactions sent to L2 [S1].
*   **Memory Complexity:** No additional SRAM buffers are required [S1]. Reduction occurs directly in registers, avoiding eviction or capacity issues [S1].
*   **Measured Performance:**
    *   **RTX 4090-Sim:** Average speedup of 2.06x (up to 8.59x) for gradient computation; 2.43x average reduction in shader atomic stalls; 3.9x average reduction in energy consumption [S1].
    *   **RTX 3060-Sim:** Average speedup of 1.73x (up to 3.77x) for gradient computation; 2.28x average reduction in shader atomic stalls; 2.55x average reduction in energy consumption [S1].
*   **Strengths:** High throughput due to reduction at each of the 4 sub-cores; no buffer capacity issues; dynamic scheduling adapts to ROP contention; low area overhead [S1].
*   **Limitations:** Requires hardware modification; assumes commutative operations; coherence overhead if data is shared across SMs [S1].
*   **When to Use:** Differentiable rendering applications (e.g., 3D Gaussian Splatting, NVDiffRec, Pulsar) with high atomic update rates and irregular thread activity [S1].
*   **When Not to Use:** Applications requiring strictly ordered atomic operations, as the `atomred` instruction provides no ordering guarantees [S1].

## Background
ARC-HW was proposed by Sankeerth Durvasula et al. in the paper "ARC: Warp-level Adaptive Atomic Reduction in GPUs to Accelerate Differentiable Rendering" [S1]. It was developed to address the performance bottlenecks of atomic operations in raster-based differentiable rendering methods, which generate a large number of atomic requests that overwhelm hardware queues and compute units [S1]. The design leverages the intra-warp locality of atomic updates in these workloads, where most or all threads in a warp typically perform atomic updates to the same memory locations [S1]. The design was evaluated using the GPGPU-Sim simulator on simulated NVIDIA RTX 4090 and RTX 3060 architectures, with additional real-RTX 4090 measurements [S1].
