# Adaptive Atomic ReduCtion Software (ARC-SW)
Also called: ARC-SW, ARC-SW Serialized Reduction, SW-S, Serialized Reduction

## Overview
ARC-SW is a software-only implementation of the Adaptive Atomic Reduction (ARC) framework designed to accelerate gradient computation in raster-based differentiable rendering by reducing atomic operation bottlenecks on GPUs [S1]. It replaces standard atomic instructions with a function that dynamically chooses between baseline atomic addition, serialized warp-level reduction, or butterfly reduction based on a balancing threshold [S1]. Unlike its hardware counterpart [Adaptive Atomic ReduCtion Hardware (ARC-HW)](12371-adaptive-atomic-reduction-hardware-arc-hw.md), ARC-SW leverages existing warp-level primitives (such as `shfl`) to perform reduction at the Streaming Multiprocessor (SM) level, making it flexible for GPUs that do not support specific hardware primitives and requiring less programmer effort to integrate [S1].

## How it works
ARC-SW operates by intercepting gradient updates for 3D primitives (e.g., Gaussians). The core loop structure for gradient computation is:
1. Get thread ID corresponding to pixel.
2. Iterate through primitives associated with that thread.
3. Check conditions (`cond1`, `cond2`); if false, the thread does not participate in the update for that primitive.
4. Compute gradient contributions.
5. Perform atomic addition on parameter fields [S1].

Instead of direct `AtomicAdd`, the kernel calls `reduce_arc`. The method determines the number of active threads in the warp updating the same primitive index `idx` using `__popc(__match(idx))` [S1]. If the count of active threads is less than the balancing threshold, the function performs a baseline `atomicAdd` to global memory (ROP units) [S1]. If the count meets or exceeds the threshold, it performs warp-level reduction within the SM registers before a single thread writes the result to global memory [S1].

### Data Structures and Inputs
The function signature is:
`void reduce_arc(int idx, ATOM_T** ptr, ATOM_T *val, int num_params, int balance_thr)` [S1]
- `idx`: The primitive index being updated.
- `ptr`: Array of pointers to the primitive's parameters in global memory.
- `val`: Array of gradient values computed by the calling thread.
- `num_params`: Number of parameters to update.
- `balance_thr`: Integer threshold (0–31) determining when to switch from baseline atomic to warp-level reduction [S1].

### Algorithms
Two reduction strategies are available, selected based on the workload characteristics and programmer choice:

#### Serialized Reduction (SW-S)
This approach handles cases where threads in a warp update different parameters or when not all threads are active.
1. Identify the set of threads updating the same primitive using `__match(idx)` [S1].
2. Determine the leader thread: the active thread with the lowest lane ID updating the same primitive [S1].
3. The leader iterates through all other active lanes in the warp, fetching their gradient values using `__shfl` and accumulating them.
4. The leader performs a single `atomicAdd` for each parameter using the accumulated sum [S1].

#### Butterfly Reduction (SW-B)
This approach is more efficient but requires stricter conditions: all threads in the warp must update the same primitive, and all threads must participate in the reduction (inactive threads must generate zero-value updates) [S1].
1. Check if all threads update the same primitive: `__match(idx) == 0xffffffff` [S1].
2. If true, perform a parallel butterfly reduction tree: iterate offsets from 16 down to 1, adding `__shfl(val[i], offset)` to `val[i]` for all threads [S1].
3. Thread 0 (the leader) performs `atomicAdd` for each parameter [S1].
4. If the condition is false or the threshold is not met, fallback to baseline `atomicAdd` for each parameter [S1].

### Pseudocode
The following pseudocode combines the logic for both variants. It assumes the caller has ensured all threads participate (for SW-B) or handles the mask logic (for SW-S).

```python
def reduce_arc(idx, ptr, val, num_params, balance_thr, use_butterfly=False):
    # Determine active threads updating the same primitive
    # __match(idx) returns a mask where bit i is 1 if thread i updates idx
    prim_mask = __match(idx)
    num_active = __popc(prim_mask)

    # Decision: Baseline vs Warp-level Reduction
    if num_active < balance_thr:
        # Baseline atomic add to global memory (ROP units)
        for i in range(num_params):
            atomicAdd(ptr[i], val[i])
        return

    # Warp-level reduction at SM
    if use_butterfly:
        # SW-B: Requires all threads active and updating same primitive
        all_same = (prim_mask == 0xffffffff)
        if all_same:
            # Parallel butterfly reduction
            for offset in [16, 8, 4, 2, 1]:
                # Shuffle value from lane at offset distance
                # Note: Inactive threads must have val=0 to avoid corruption
                neighbor_val = __shfl_sync(0xffffffff, val, offset)
                for i in range(num_params):
                    val[i] += neighbor_val
            
            # Leader (lane 0) writes to global memory
            if get_lane_id() == 0:
                for i in range(num_params):
                    atomicAdd(ptr[i], val[i])
        else:
            # Fallback to baseline if condition not met
            for i in range(num_params):
                atomicAdd(ptr[i], val[i])
    else:
        # SW-S: Serialized reduction
        # Identify leader: lowest lane ID in prim_mask
        leader = __ffs(prim_mask) - 1 # __ffs returns 1-based index
        
        # Leader accumulates from other active threads
        # Iterate through all other active lanes
        for src_lane in get_active_lanes(prim_mask):
            if src_lane != leader:
                # Fetch gradient from source lane
                src_val = __shfl_sync(prim_mask, val, src_lane)
                for i in range(num_params):
                    val[i] += src_val
        
        # Leader writes accumulated result to global memory
        if get_lane_id() == leader:
            for i in range(num_params):
                atomicAdd(ptr[i], val[i])
```

### Parameters
- **Balancing Threshold**: An integer between 0 and 31. It is tuned automatically by profiling all 32 values every $N$ iterations (e.g., 2000) to select the one providing the largest speedup [S1].

### Edge Cases and Pitfalls
- **Commutativity**: ARC-SW assumes commutative atomic additions. Floating-point addition order independence is assumed; workloads are resilient to small errors from reordering [S1].
- **Shuffle Mask Limitation**: Existing shuffle primitives (e.g., `shfl_sync`) do not take predicate registers or logic masks for filtering active threads. The mask argument is a synchronization mask, not a thread activity mask. Using an "if" condition does not solve divergence because threads have already diverged. The implementation must explicitly handle inactive threads (e.g., by setting their values to zero for SW-B) [S1].
- **Redundant Computation**: SW-B forces inactive threads to perform zero-value updates, causing redundant computation and inefficiency for warps with many inactive threads [S1].
- **Control Flow Overhead**: SW-S incurs overhead from serial reduction and control flow instructions, with execution time proportional to the number of active threads per primitive [S1].

## Subtopics

### ARC-SW Butterfly Reduction (SW-B)
A variant of ARC-SW that uses a parallel butterfly reduction tree to sum gradients. It is chosen when all threads in a warp update the same primitive and all threads can be made to participate (by generating zero-value updates for originally inactive threads) [S1]. It is more efficient than SW-S when most threads are active but requires programmer intervention to ensure no control flow divergence and zero-value assignment for inactive threads [S1]. It is inefficient for warps with many inactive threads due to redundant zero-value computations [S1].

## Operating characteristics
- **Time Complexity**: For SW-S, execution time is proportional to the number of active threads per primitive due to serial reduction [S1]. For SW-B, it is logarithmic with respect to warp size (5 shuffle steps) but requires all threads to be active [S1].
- **Memory Complexity**: O(1) per thread for registers; no additional global memory buffers are allocated [S1].
- **Performance**: On a simulator (GPGPU-Sim), ARC-SW demonstrated an average speedup of 1.8× (up to 7.2×) for gradient computation in differentiable rendering applications like 3D Gaussian Splatting [S1]. On real hardware (NVIDIA RTX 4090), it provides significant speedups, though less than ARC-HW (2.1× average) [S1].
- **Strengths**: Software-only, no hardware modifications required, flexible for various GPUs (including those lacking specific hardware primitives), open-source [S1].
- **Limitations**: Overhead from redundant computations (SW-B), control flow instructions (SW-S), requires hyperparameter tuning (balancing threshold), and requires programmer intervention to integrate (modifying kernel code to ensure all threads participate for SW-B) [S1].

## Background
ARC-SW was introduced by Durvasula et al. in the paper "ARC: Warp-level Adaptive Atomic Reduction in GPUs to Accelerate Differentiable Rendering" presented at ASPLOS ’25 [S1]. The work identifies atomic updates as a key bottleneck in raster-based differentiable rendering (e.g., 3D Gaussian Splatting, NVDiffRec, Pulsar) [S1]. The authors observed that while many warps have all threads updating the same memory location, only a fraction of threads within a warp typically perform atomic updates due to dynamic conditions in gradient computation [S1]. ARC-SW was developed as a software-only counterpart to the hardware-optimized ARC-HW to provide a portable solution for existing GPUs [S1].
