# Y-Bucket Parallelization

Also called: Y-bucket grouping

## Overview
Y-Bucket Parallelization is a two-pass parallel algorithm for direct volume rendering that groups polygons representing isosurfaces or volume slices into scanline-based "y-buckets" to maximize coherence and avoid the difficulties of ray-casting intersecting cells [S1]. It solves the problem of rendering irregular and multiple grids efficiently in software by parallelizing on a scanline basis to limit duplication compared to tile-based methods that break scanlines and lose coherence [S1].

## How it works
The method processes polygons representing volume data (stored in counter-clockwise order when viewed from outside the grid to recognize boundaries and visibility order) [S1].

**Inputs:**
- A set of polygons representing volume slices or isosurfaces [S1].
- A set of processing units (processors) [G].

**Outputs:**
- A rendered image where pixels are filled based on front-to-back visibility [G].

**Data Structures:**
1. **Y-Bucket Array:** An array where each entry corresponds to a specific scanline (y-coordinate) [S1]. It stores the count of polygons belonging to that scanline [S1].
2. **Output Array:** A common array partitioned to store the final pixel data [S1].
3. **X-Bucket Structures:** Linked lists associated with the leftmost pixel of a polygon's horizontal span [S1]. These lists maintain polygons in front-to-back visibility order [S1].

**Steps:**

1. **First Pass (Polygon Distribution):**
    - Each processor distributes polygons into y-buckets based on their vertical extent [S1].
    - Polygons are assigned to the y-buckets corresponding to the scanlines they cover [S1].
    - Invalidated polygons are marked or excluded [S1].

2. **Second Pass (Bucket Allocation and Structure Creation):**
    - The number of polygons belonging to each y-bucket is determined by accessing the Y-Bucket Array [S1].
    - Space for each y-bucket is allocated by partitioning the common Output Array [S1].
    - The space for one y-bucket is further partitioned into space for each processor to fill within that y-bucket [S1].
    - Each processor creates appropriate y-bucket structures for all polygons it processed in the first pass, excluding those invalidated [S1].
    - This step is transitional; its work per processor is proportional to the number of scanlines, not the number of polygons [S1].

3. **Third Parallelizable Component (Scanline Processing):**
    - Scanlines are processed in order from bottom to top [S1].
    - For each active polygon, information is transferred to an x-bucket data structure associated with the leftmost pixel in which the polygon appears [S1].
    - A linked list of these x-bucket structures is maintained in front-to-back visibility order [S1].
    - This component involves the bulk of the computation [S1].

        y_min, y_max = polygon.vertical_extent()
        for y in range(y_min, y_max + 1):
            y_bucket_counts[y] += 1

    # Step 2: Second Pass - Allocate space and create structures
    # Partition common output array based on y_bucket_counts
    output_offsets = [0] * (num_scanlines + 1)
    current_offset = 0
    for y in range(num_scanlines):
        output_offsets[y] = current_offset
        current_offset += y_bucket_counts[y]
    output_offsets[num_scanlines] = current_offset

    # Partition space for each processor within each y-bucket
    # This is a transitional step; work is proportional to scanlines [S1]
    processor_offsets = [[0] * num_processors for _ in range(num_scanlines)]
    for y in range(num_scanlines):
        count = y_bucket_counts[y]
        per_proc = count // num_processors
        remainder = count % num_processors
        offset = output_offsets[y]

**Parameters:**
- Number of processors: Determines the partitioning of space within y-buckets [S1].
- Number of scanlines: Determines the size of the y-bucket array and the work in the second pass [S1].

**Edge Cases and Pitfalls:**
- The second pass is a transitional step and can be parallelized by standard techniques, but its workload is small relative to the third pass [S1].
- Polygons must be stored in counter-clockwise order to correctly identify boundaries and visibility order [S1].

## Subtopics

### [Parallel Direct Volume Rendering with Y-Buckets and X-Buckets](2123-parallel-direct-volume-rendering-with-y-buckets-and-x-bucket.md)
This method extends Y-Bucket Parallelization by introducing "x-buckets" and "x-actives" lists to maintain front-to-back visibility order within a scanline. It is chosen when rendering irregular and multiple grids in software to maximize coherence and avoid ray-casting intersecting cells. Unlike tile-based parallelization methods that break scanlines and lose coherence, this method parallelizes on a scanline basis to limit duplication.

## Operating characteristics
- **Time Complexity:** The second pass work is proportional to the number of scanlines, not the number of polygons [S1]. The third parallelizable component involves the bulk of the computation, processing each scanline and managing linked lists of active polygons [S1].
- **Memory Complexity:** Requires storage for y-bucket counts, the partitioned output array, and x-bucket linked lists [S1].
- **Strengths:** Maximizes coherence by processing scanlines; avoids the difficulties of ray-casting intersecting cells; limits duplication compared to tile-based methods [S1].
- **Limitations:** The second pass is a transitional step with limited parallelism benefit; relies on software processing of polygons [S1].

## Background
The method was introduced in the 1996 paper "Hierarchical and parallelizable direct volume rendering for irregular and multiple grids" [S1]. It addresses the challenges of rendering complex volume data by leveraging scanline-based parallelization [S1].
