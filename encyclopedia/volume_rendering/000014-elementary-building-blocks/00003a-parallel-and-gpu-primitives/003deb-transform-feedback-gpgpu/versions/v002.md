# Transform Feedback GPGPU

Also called: GPGPU paradigm using transform feedback, Stream-out GPGPU

## Overview
Transform Feedback GPGPU is a general-purpose computing on graphics processing units (GPGPU) paradigm that maps algorithm inputs, processing, and outputs to the graphics pipeline by utilizing vertex and geometry shaders while completely discarding fragment shaders [S1]. It differs from common render-to-texture approaches by using transform feedback (stream-out) to record processed data directly into buffer objects, offering greater flexibility for multiple outputs compared to Multiple Render Targets (MRT) [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A one-dimensional Texture Buffer Object (TBO) containing the data to be processed, and a proxy geometry stored in a Vertex Buffer Object (VBO) [S1].
*   **Output:** One or more Buffer Objects populated with processed data via transform feedback [S1].

**Data Structures:**
1.  **Input TBO:** A 1D texture buffer representing the input data in an array-like form [S1].
2.  **Proxy VBO:** A CPU-created vertex buffer containing vertices whose positions encode indices into the Input TBO [S1].
3.  **Output Buffer Object(s):** GPU memory buffers where transform feedback records vertex attributes [S1].

**Numbered Steps:**
1.  **Proxy Geometry Creation:** Create a proxy geometry on the CPU side and store it in a VBO [S1]. The position of each vertex $v_i$ in the VBO encodes the index $i$ for the corresponding element in the input TBO [S1].
2.  **Data Fetching:** Bind the Input TBO [S1]. In the vertex shader, for each vertex of the proxy geometry, perform a texel fetch using the vertex position (index) to retrieve the data value from the TBO [S1].
3.  **Processing:** Render the vertices of the proxy geometry [S1]. This triggers active vertex or geometry shader threads, which serve as computation kernels [S1]. The GPU applies an identical set of operations to each input value in parallel (Single Program, Multiple Data) [S1].
    *   *Single Output:* If a single output value is produced per input, the vertex shader processes the point primitive representing the input [S1].
    *   *Multiple Outputs:* If multiple output values are required, a geometry shader is employed as the processing kernel [S1]. The geometry shader operates on geometry primitives, allowing the creation and destruction of vertices [S1]. A point primitive from the proxy geometry (encoding a single input) is transformed into a line-strip primitive, where the vertices of the line-strip encode the array of output values [S1].
4.  **Output Recording (Transform Feedback):** Enable transform feedback (stream-out) [S1]. The graphics hardware records vertex attributes for each processed primitive into the specified Output Buffer Object(s) [S1]. This effectively scatters data from the vertex or geometry shading stage back to memory [S1].
5.  **Iteration:** For iterative algorithms, the Output Buffer Object containing the results of one stage is bound as the Input TBO for the subsequent stage [S1]. The CPU must manage the switching of the correct input buffer for each computation step [S1].

**Pseudocode:**
```python
# Initialization
input_data = [...]  # Array of values to process
num_outputs = 1     # Number of output values per input element
num_stages = 1      # Number of iterative computation stages

# 1. Proxy Geometry Creation: CPU creates a VBO where vertex positions encode indices [S1].
proxy_vbo_indices = list(range(len(input_data)))

# 2. Data Fetching & Processing: Vertex/geometry shaders execute per vertex [S1].
# Vertex shader: fetches input_data[index] using vertex position as index [S1].
# Geometry shader (if num_outputs > 1): emits a line-strip of output values [S1].
def process_vertex(index):
    value = input_data[index]
    # Apply algorithm operations here
    return [value]  # Single output per input

# 3. Output Recording: Transform feedback records vertex attributes to buffers [S1].
output_buffers = [[] for _ in range(num_outputs)]
for stage in range(num_stages):
    # Enable transform feedback to record vertex attributes to output_buffers[stage] [S1]
    # Bind current_input_tbo to vertex shader
    # Bind proxy_vbo to vertex array
    # Render POINTS primitive for each vertex in proxy_vbo_indices
    # Vertex shader fetches data from current_input_tbo using vertex position as index [S1]
    # Geometry shader (if num_outputs > 1) transforms point to line-strip of outputs [S1]
    # Transform feedback captures processed vertex attributes into output_buffers[stage] [S1]
    # Disable transform feedback
    # CPU determines correct input buffer for next stage [S1]
    for idx in proxy_vbo_indices:
        results = process_vertex(idx)
        for out_idx, val in enumerate(results):
            output_buffers[out_idx].append(val)
    # CPU determines correct input buffer for next stage [S1]
    input_data = output_buffers[0]  # Simplified for single output case
```

**Parameters and Typical Values:**
*   **Proxy Geometry Type:** Points (for single output) or Lines (for multiple outputs via geometry shader) [S1].
*   **Buffer Interleaving:** Output values can be recorded to separate buffers or interleaved into a single buffer [S1].

**Edge Cases and Pitfalls:**
*   **Hardware Performance Variance:** The performance of recording output values to separate buffers versus interleaving them into a single buffer varies across different hardware architectures [S1].
*   **Shader Unification:** This approach is only efficient when shader processing is unified (e.g., Unified Shader Model or Shader Model 4.0+), as it relies heavily on vertex and geometry shaders [S1].
*   **CPU-Side Management:** The correct input buffer for each computation stage in an iterative approach must be determined and managed by the CPU [S1].

## Operating characteristics
*   **Complexity:** Not given in the sources.
*   **Performance:** Performance varies based on hardware architecture, specifically regarding the choice between separate and interleaved output buffers [S1]. Efficiency depends on unified shader processing capabilities [S1].
*   **Strengths:** Intuitive mapping of algorithm steps (Input/Processing/Output) to GPU pipeline stages; flexible output handling (separate or interleaved buffers) compared to MRT; supports iterative approaches easily [S1].
*   **Limitations:** Discards fragment shaders, which may be inefficient on older or non-unified hardware architectures; requires careful CPU-side management for iterative buffer switching [S1].
*   **When to use:** When implementing general computations on the GPU that require flexible output structures (multiple outputs) and benefit from the simplicity of vertex/geometry shader processing, particularly in frameworks like VolFliesGPU for illustrative volume rendering [S1].
*   **When not to use:** On hardware without unified shader models where vertex/geometry shader performance is significantly lower than fragment shader performance; when fragment-based processing is inherently more suitable for the algorithm [S1].

## Background
The Transform Feedback GPGPU paradigm was proposed by R.F.P. van Pelt, A. Vilanova, and H.M.M. van Wijk in 2008 as part of the VolFliesGPU framework for interactive illustrative volume rendering [S1]. It was introduced to provide a more intuitive and flexible alternative to common render-to-texture approaches, leveraging new extensions in the shader model (transform feedback/stream-out) to map general algorithms to the stream processing pipeline [S1].
