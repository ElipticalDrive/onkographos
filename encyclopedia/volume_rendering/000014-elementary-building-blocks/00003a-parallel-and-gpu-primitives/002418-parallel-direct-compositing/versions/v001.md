# Parallel Direct Compositing

Also called: Direct compositing method

## Overview
Parallel Direct Compositing is a distributed memory volume rendering technique where image compositing is performed directly across processors following the subdivision of the data domain [S1, unofficial]. It solves the scalability bottleneck of parallel volume rendering by minimizing inter-processor communication overhead during the final image assembly phase [S1, unofficial]. Unlike tiled approaches that require complex synchronization or reduction trees, this method relies on a host processor to collect and combine subimages, accepting a serial bottleneck in display rates in exchange for simplified communication logic and decreasing relative communication costs as processor count increases [S1, unofficial].

## How it works
**Inputs:**
- A 3D volume dataset.
- A distributed memory environment with $p$ processors.
- A bidirectional torus network topology [S1, unofficial].

**Outputs:**
- A final 2D composite image of resolution $n$ pixels [S1, unofficial].

**Data Structures:**
- **Subimages:** Each processor $i$ maintains a local buffer containing the rendered portion of the final image corresponding to its assigned data block. The layout is a standard 2D pixel array.
- **Global State:** Not explicitly maintained during compositing; the host processor manages the aggregation logic [S1, unofficial].

**Steps:**
1. **Domain Subdivision:** The 3D data domain is subdivided into blocks. Each block is assigned to a specific processor in the distributed system [S1, unofficial].
2. **Local Rendering:** Each processor independently renders its assigned data block into a local subimage. This phase requires no inter-processor communication [S1, unofficial].
3. **Subimage Transmission:** Processors transmit their local subimages to a designated host processor. The transmission occurs over the network (e.g., bidirectional torus) [S1, unofficial].
4. **Aggregation:** The host processor invokes a library function to collect all incoming subimages and combine them into the final image [S1, unofficial].
5. **Display:** The final image is displayed on a remote workstation or stored [S1, unofficial].

**Formulas:**
The communication cost $C_{comm}$ for the compositing phase on a bidirectional torus is modeled as [S1, unofficial]:

$$ C_{comm} = C_1 \cdot p \cdot n \cdot t_{trans} + C_2 \cdot t_{overhead} $$

Where:
- $p$: Number of processors.
- $n$: Number of pixels in the image.
- $t_{trans}$: Per-pixel transfer cost.
- $t_{overhead}$: Per-message overhead.
- $C_1, C_2$: Positive constants smaller than 1, representing efficiency factors of the network and protocol [S1, unofficial].

**Parameters:**
- Typical values for $C_1$ and $C_2$ are not specified, only that they are positive constants $< 1$ [S1, unofficial].
- Network topology: Bidirectional torus [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Serial Bottleneck:** The display rate is limited by the serial data stream resulting from the host processor collecting subimages [S1, unofficial].
- **Network Latency:** Performance is further degraded by network latency, particularly as the number of processors increases if the per-message overhead $t_{overhead}$ dominates [S1, unofficial].
- **Mitigation:** Image compression techniques can be applied to alleviate bandwidth and latency issues, though direct transfer is often used for large-scale scientific simulations where frame rates are not critical [S1, unofficial].

**Pseudocode:**
```python
# Distributed Parallel Direct Compositing
# Assumed: MPI-like environment with a designated root/host process

def parallel_direct_compositing(volume_data, image_width, image_height, my_rank, num_ranks, is_host):
    """
    Renders a volume and composites the result using direct compositing.
    """
    # Step 1: Subdivide data domain
    # The global volume is partitioned. Each rank holds a local chunk.
    local_volume_chunk = get_local_volume_chunk(volume_data, my_rank, num_ranks)
    
    # Step 2: Render subimage
    # Each processor renders its chunk into a local subimage buffer.
    # This step is independent and requires no communication.
    local_subimage = render_volume(local_volume_chunk, image_width, image_height)
    
    # Step 3 & 4: Communication and Aggregation
    if is_host:
        # Host collects subimages from all other ranks
        final_image = create_empty_image(image_width, image_height)
        
        # Receive from all workers and combine
        # Note: The specific combination logic (e.g., alpha blending order) 
        # depends on the spatial arrangement of the subimages.
        # Here we assume a simple copy/assembly based on pre-defined layout.
        for rank in range(num_ranks):
            if rank == my_rank:
                continue
            
            # Receive subimage from rank 'rank'
            received_subimage = receive_message(rank)
            
            # Combine received_subimage into final_image
            # The exact mapping of received_subimage pixels to final_image coordinates
            # depends on how the domain was subdivided (e.g., spatial partitioning).
            final_image = combine_subimages(final_image, received_subimage)
            
        # Step 5: Display
        display_image(final_image)
        
    else:
        # Worker ranks send their subimage to the host
        send_message(host_rank, local_subimage)
```

## Subtopics

### [Tiled Parallel Compositing](1192-tiled-parallel-compositing.md)
Uses spatial tiling to reduce communication volume by only exchanging boundary data or using hierarchical reduction, differing from direct compositing's full subimage transfer.

### [Y-Bucket Parallelization](2108-y-bucket-parallelization.md)
Parallelizes along the view vector (Y-axis) rather than spatial domain blocks, avoiding the need for inter-processor compositing of disjoint spatial regions.

### [Atomic Fragment List Insertion](2465-atomic-fragment-list-insertion.md)
A GPU-centric approach using atomic operations for fragment ordering, contrasting with the CPU/distributed memory message-passing model of direct compositing.

## Operating characteristics
**Time and Memory Complexity:**
- The rendering phase is scalable with no communication required [S1, unofficial].
- The compositing communication cost is given by $C_1 \cdot p \cdot n \cdot t_{trans} + C_2 \cdot t_{overhead}$ [S1, unofficial].
- Analysis shows that communication cost decreases as the number of processors $p$ increases, making the method acceptable for large $p$ [S1, unofficial].

**Measured Performance:**
Tests on an Intel Paragon XP/S (NASA Langley Research Center) with a $256 \times 256$ image and $60^3$ data points [S1, unofficial]:

| Nodes | Raw Compositing (s) | Communication Compositing (s) |
| :--- | :--- | :--- |
| 125 | 0.0455 | 0.0612 |
| 216 | 0.0310 | 0.0583 |

Scaling analysis for simulation and resampling on the same hardware (8 to 216 nodes) [S1, unofficial]:
- Simulation compute time: 10.665s (8 nodes) $\rightarrow$ 0.4109s (216 nodes).
- Resampling time: 13.01s (8 nodes) $\rightarrow$ 0.681s (216 nodes).

**Strengths and Limitations:**
- **Strengths:** Simple communication pattern; communication overhead decreases relative to compute as processors increase; no synchronization barriers during rendering [S1, unofficial].
- **Limitations:** Display rates are limited by the serial collection of subimages on the host; performance degrades with high network latency [S1, unofficial].

**When to Use:**
- Suitable for large-scale scientific simulations on massively parallel computers where interactive frame rates are not the primary constraint, and the simulation does not run multiple time steps per second [S1, unofficial].
- Best used when the network topology supports efficient bulk data transfer (e.g., torus) and a dedicated host processor is available for aggregation [S1, unofficial].

## Background
Parallel Direct Compositing was developed and analyzed in the context of runtime volume visualization for parallel Computational Fluid Dynamics (CFD) [S1, unofficial]. The library was implemented in C/C++ using Intel's native communication library NX on a 72-node Intel Paragon XP/S operated at the NASA Langley Research Center [S1, unofficial]. The analysis was consistent with Neumann's results regarding communication costs [S1, unofficial]. The approach was designed for distributed memory message-passing environments, with suggestions for future portability using MPI or PVM [S1, unofficial].
