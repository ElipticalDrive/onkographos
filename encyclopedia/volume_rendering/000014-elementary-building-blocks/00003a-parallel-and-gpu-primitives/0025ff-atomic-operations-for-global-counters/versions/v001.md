# Atomic Operations for Global Counters

Also called: atomic operations, atomicAdd

## Overview
Atomic operations for global counters provide a thread-safe mechanism to write to global memory from multiple GPU threads simultaneously, preventing race conditions (collisions) [S1, unofficial]. This method solves the problem of concurrent access to shared state by ensuring that read-modify-write sequences are executed indivisibly. It is distinguished from sibling methods like [Tiled Parallel Compositing](1192-tiled-parallel-compositing.md) and [Parallel Prefix Sum (Scan) Orchestration](2593-parallel-prefix-sum-scan-orchestration.md) by its simplicity and lack of synchronization barriers or complex reduction trees; it relies directly on hardware-supported atomic instructions for immediate consistency, albeit at the cost of potential serialization contention under high concurrency.

## How it works
**Inputs and Outputs:**
*   **Input:** A global memory buffer (e.g., a counter variable) and a thread identifier.
*   **Output:** The updated global memory state and, optionally, the pre-increment value returned to the thread for indexing.

**Data Structures:**
*   **Count Buffer:** A storage buffer (e.g., `std430` layout in GLSL) bound to a specific binding point (e.g., binding 0). It contains a single scalar variable, typically `uint` or `int`, representing the counter [S1, unofficial].
*   **Array Buffer:** A dynamic storage buffer (e.g., `std430` layout) bound to a secondary binding point (e.g., binding 1). It acts as a destination array where threads store data at indices derived from the atomic counter [S1, unofficial].

**Steps:**
1.  **Initialization:** Initialize the global counter buffer to zero on the host or via a clear operation before kernel launch [S1, unofficial].
2.  **Invocation:** Each thread executes the atomic operation. For a counter, `atomicAdd(count, 1)` is called [S1, unofficial].
3.  **Index Retrieval:** The atomic operation returns the value of the counter *before* the increment. This return value serves as a unique, thread-safe index for the calling thread [S1, unofficial].
4.  **Storage:** The thread uses the returned index to write its computed data into the global array buffer (e.g., `array[index] = data`) [S1, unofficial].
5.  **Conditional Packing (Optional):** If data is sparse, threads check a condition (e.g., `value % 100 == 0`). Only threads meeting the condition call `atomicAdd` to secure an index and store the value, leaving unused slots in the array buffer uninitialized or zeroed [S1, unofficial].

**Pseudocode:**
The following GLSL-like pseudocode demonstrates the basic pattern for retrieving unique indices and storing data.

```glsl
// Assumed bindings:
// binding 0: buffer Count { uint count; };
// binding 1: buffer Array { uint array[]; };

void main() {
    // 1. Get global thread ID
    uint gid = gl_GlobalInvocationID.x;
    
    // 2. Compute local data (example: square of ID)
    uint value = gid * gid;
    
    // 3. Conditional check (optional)
    // Only proceed if condition is met
    if (value % 100 == 0) {
        // 4. Atomic increment and index retrieval
        // Returns the pre-increment value of 'count'
        uint index = atomicAdd(count, 1);
        
        // 5. Store data at the unique index
        // Note: array must be large enough to hold max possible indices
        array[index] = value;
    }
}
```

**Parameters:**
*   **Local Size:** The number of threads per workgroup. In examples, this is set to 64 (`layout(local_size_x = 64) in;`) [S1, unofficial].
*   **Counter Type:** Typically `uint` or `int` [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Race Conditions:** Using non-atomic increments (e.g., `count++`) on global memory results in incorrect counts due to lost updates from concurrent reads/writes [S1, unofficial].
*   **Ordering:** The order of indices returned by `atomicAdd` is **not guaranteed** to be sorted, even if small-scale examples (single workgroup) appear sorted [S1, unofficial]. Implementations must not rely on sequential ordering of indices.
*   **Buffer Size:** The destination array must be pre-allocated to a size sufficient to hold the maximum possible number of valid entries to avoid out-of-bounds writes [S1, unofficial].

## Subtopics

### [Atomic Operation Variants](5912-atomic-operation-variants.md)
`atomicAdd(inout int mem, int data)`: Performs addition. This is the most common variant for counters and index generation.

### Atomic Compare-and-Swap
Uses `atomicCompareExchange` (or similar) to handle concurrent writes to the same memory location, such as updating voxel data. It takes a pointer, an expected value, and a new value. The write occurs only if the actual data matches the expected value. The return value indicates the actual data found, allowing the thread to verify if the write was successful. This is useful for brick occupancy recomputation or voxel simulation where multiple threads might attempt to update the same voxel [S2, unofficial].

### [Thread-Safe Circular Buffer for Brick Allocation](4567-thread-safe-circular-buffer-for-brick-allocation.md)
A mechanism for allocating and recycling brick indices on the CPU side, using a circular buffer with atomic head/tail pointers and prime-stepped recycling to prevent cache false sharing. This variant extends atomic principles to buffer management for dynamic data structures [4567-thread-safe-circular-buffer-for-brick-allocation.md].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per atomic operation, but contention can increase effective latency under high concurrency.
*   **Memory Complexity:** $O(1)$ for the counter buffer; $O(N)$ for the destination array, where $N$ is the maximum number of potential entries.
*   **Performance:** Atomic operations can reduce performance due to serialization and cache coherency traffic when many threads contend for the same counter [S2, unofficial]. However, for simple counting or sparse packing, they are often efficient enough and significantly simpler to implement than tree-based reductions.
*   **Strengths:** Simple to implement; no need for complex synchronization primitives or multi-pass algorithms; handles sparse data packing naturally.
*   **Limitations:** Contention bottlenecks if many threads increment the same counter simultaneously; indices are not guaranteed to be sorted; requires pre-allocated buffer space for worst-case scenarios.
*   **When to Use:** When thread-safe indexing is required for sparse data packing, or when simple counting is needed without the overhead of parallel prefix sums.
*   **When Not to Use:** When strict ordering of indices is required (use scan instead); when high contention on a single counter is expected and performance is critical (consider tiling or hierarchical counters).

## Background
Atomic operations are a fundamental primitive in parallel programming, supported by hardware on modern GPUs (CUDA, OpenCL, Vulkan). In the context of volume rendering and voxel simulation, they are used for tasks such as counting occupied voxels, packing sparse data structures, and managing dynamic brick allocation. The specific examples provided are drawn from practical implementations in compute shaders for voxel simulation and volume rendering pipelines [S1, unofficial][S2, unofficial].
