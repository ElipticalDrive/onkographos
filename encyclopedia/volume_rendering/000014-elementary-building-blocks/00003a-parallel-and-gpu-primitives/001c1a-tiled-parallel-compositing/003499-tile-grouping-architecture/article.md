# Tile-Grouping Architecture
Also called: GS-TG
## Overview
Tile-Grouping Architecture (GS-TG) is a GPU-optimized rasterization strategy for 3D Gaussian Splatting that merges adjacent tiles into larger work units to reduce redundant sorting overhead and improve data reuse within streaming multiprocessors [S1, unofficial]. It distinguishes itself from standard tiled compositing by sharing the visibility sorting order across neighboring tiles while rasterizing each tile independently, thereby bypassing the need for per-tile CUDA radix sorts [S1, unofficial][S2, unofficial].
## How it works
### Inputs and outputs
- **Inputs**: A set of 3D Gaussians defined by center $\mathbf{c}$, covariance matrix $\Sigma$, opacity $\alpha$, and color attributes; a camera projection matrix; and a framebuffer divided into a grid of tiles.
- **Outputs**: A rasterized image where each pixel contains the final blended color and depth.

### Data structures
1. **Gaussian-Tile Association List**: A list of tuples $(g, t)$ where $g$ is a Gaussian index and $t$ is a tile index. This list is generated by intersecting Gaussian bounding spheres with tile bounding boxes.
2. **Shared Sort Order**: A single sorted list of Gaussians for a group of adjacent tiles, ordered by depth relative to the camera plane. This order is reused for all tiles within the group.
3. **Tile State**: Per-tile accumulators for color and depth, initialized to transparent/background values.

### Steps
1. **Tile Grouping**: Divide the framebuffer into groups of adjacent tiles (e.g., $2 \times 2$ or $4 \times 4$ blocks). The group size is chosen to fit within the shared memory or cache hierarchy of a Streaming Multiprocessor (SM) [S1, unofficial].
2. **Association**: For each Gaussian, determine which tiles it overlaps. Add entries to the Gaussian-Tile Association List [S2, unofficial].
3. **Group Sorting**: For each tile group, collect all Gaussians associated with any tile in the group. Sort these Gaussians by depth (front-to-back) once for the entire group [S2, unofficial]. This replaces the per-tile sort.
4. **Independent Rasterization**: For each tile in the group:
   a. Initialize tile accumulators.
   b. Iterate through the shared sorted Gaussian list.
   c. For each Gaussian, check if it overlaps the current tile.
   d. If it overlaps, project the Gaussian to screen space and compute its contribution to the tile's pixels using alpha compositing.
   e. Skip Gaussians that are fully occluded or outside the tile bounds [S2, unofficial].
5. **Assembly**: Combine the results from all tiles to form the final image.

### Formulas
- **Depth Sorting Key**: For a Gaussian $i$, the depth key $d_i$ is the distance from the camera center to the Gaussian center projected onto the view direction:
  $$ d_i = \mathbf{v} \cdot (\mathbf{c}_i - \mathbf{p}_{cam}) $$
  where $\mathbf{v}$ is the view direction, $\mathbf{c}_i$ is the Gaussian center, and $\mathbf{p}_{cam}$ is the camera position [S1, unofficial].
- **Alpha Compositing**: For a pixel $p$ in tile $t$, the final color $C_t$ is computed as:
  $$ C_t = \sum_{i \in \text{sorted}} \alpha_i \cdot c_i \cdot \prod_{j < i} (1 - \alpha_j) $$
  where $\alpha_i$ is the opacity of Gaussian $i$ at pixel $p$, and $c_i$ is its color [S2, unofficial].

### Parameters
- **Group Size**: Typically $2 \times 2$ to $4 \times 4$ tiles. Not given in the sources.
- **Sort Algorithm**: Hardware-accelerated depth test or radix sort for the group. Not given in the sources.

### Edge cases and pitfalls
- **Precision**: Depth sorting precision may vary across tiles in a group if the depth range is large. Use high-precision depth values for sorting [S1, unofficial].
- **Boundary Conditions**: Gaussians on tile boundaries must be correctly assigned to avoid double-counting or gaps. The association step must handle boundary pixels consistently [S2, unofficial].
- **Degenerate Input**: If a tile group has no overlapping Gaussians, skip sorting and rasterization for that group [S1, unofficial].

### Pseudocode
> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
def tile_grouping_rasterize(gaussians, camera, tiles, group_size):
    # Step 1: Group tiles
    tile_groups = create_tile_groups(tiles, group_size)
    
    # Step 2: Create Gaussian-Tile associations
    associations = []
    for g in gaussians:
        for t in tiles:
            if intersects(g.bounding_sphere, t.bounding_box):
                associations.append((g, t))
    
    # Step 3 & 4: Process each group
    for group in tile_groups:
        # Collect Gaussians for this group
        group_gaussians = [g for g, t in associations if t in group]
        
        # Sort Gaussians by depth for the group
        sorted_gaussians = sort_by_depth(group_gaussians, camera)
        
        # Rasterize each tile independently using the shared order
        for tile in group:
            tile_color = init_tile_accumulator(tile)
            for g in sorted_gaussians:
                if g.overlaps(tile):
                    tile_color = composite(tile_color, g, camera)
            write_tile_to_framebuffer(tile, tile_color)
    
    return framebuffer
```

## Subtopics

### [Tiled Parallel Compositing](1192-tiled-parallel-compositing.md)
The parent method that divides the framebuffer into disjoint tiles for parallel processing. GS-TG builds on this by grouping tiles to share sorting work.

### [Tile-Based Alpha Compositing](1215-tile-based-alpha-compositing.md)
A sibling method that performs alpha compositing per tile. GS-TG differs by sharing the sort order across multiple tiles.

### [Dynamic Load Balancing via Tile Queue](1763-dynamic-load-balancing-via-tile-queue.md)
A sibling method that uses a queue to balance load. GS-TG uses static grouping, which may lead to load imbalance if tile complexity varies significantly.

### [Adaptive Tile Sizing](1805-adaptive-tile-sizing.md)
A sibling method that adjusts tile size based on scene complexity. GS-TG uses fixed-size groups, which may not adapt to varying Gaussian density.

### [Tile Boundary Computation Setup](2678-tile-boundary-computation-setup.md)
A sibling method that computes tile boundaries. GS-TG assumes pre-computed tile boundaries for grouping.

### [Parallel Image Assembly](3271-parallel-image-assembly.md)
A sibling method that assembles the final image from tiles. GS-TG includes this as the final step.

### [Multi-Threaded Tile-Based Rendering](3784-multi-threaded-tile-based-rendering.md)
A sibling method that uses multiple threads per tile. GS-TG uses multiple tiles per thread group.

### [Tile-Based Wave Synchronization](5069-tile-based-wave-synchronization.md)
A sibling method that synchronizes waves of tiles. GS-TG avoids synchronization by sharing sort order.

### [Parallel Binary-Swap Compositing](10844-parallel-binary-swap-compositing.md)
A sibling method that uses binary-swap for compositing. GS-TG uses standard alpha compositing with shared sorting.

## Operating characteristics
- **Time Complexity**: Sorting is performed once per tile group instead of per tile, reducing sorting complexity from $O(N \log N \cdot T)$ to $O(N \log N \cdot \frac{T}{G})$, where $N$ is the number of Gaussians, $T$ is the number of tiles, and $G$ is the group size [S1, unofficial][S2, unofficial].
- **Memory Complexity**: Requires storage for the shared sort order and tile accumulators. Memory usage is proportional to the number of Gaussians and tiles [S2, unofficial].
- **Measured Performance**: Achieves significant speedup by reducing redundant sorting work. Specific benchmarks are not given in the sources.
- **Scaling**: Scales well with the number of tiles if the group size is optimized for the hardware cache hierarchy [S1, unofficial].
- **Strengths**: Reduces sorting overhead, improves data reuse, and leverages GPU hardware acceleration for depth testing [S1, unofficial].
- **Limitations**: May suffer from load imbalance if tile complexity varies. Fixed group size may not be optimal for all scenes [S2, unofficial].
- **When to use**: When sorting overhead is a bottleneck and tile complexity is relatively uniform.
- **When not to use**: When tile complexity varies significantly, leading to load imbalance.

## Background
GS-TG was proposed in the context of 3D Gaussian Splatting rasterization to address the high cost of per-tile sorting on GPUs [S1, unofficial][S2, unofficial]. It is part of a broader trend of hardware-algorithm co-design for Gaussian rendering, alongside methods like GauRast, GSAcc, and GEMM-GS [S1, unofficial].
