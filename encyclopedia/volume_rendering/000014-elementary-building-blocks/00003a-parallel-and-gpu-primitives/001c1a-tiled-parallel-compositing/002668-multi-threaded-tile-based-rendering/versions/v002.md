# Multi-Threaded Tile-Based Rendering
Also called: threaded rasterization

## Overview
Multi-Threaded Tile-Based Rendering is a parallelization strategy that divides the screen height into horizontal tiles and processes each tile in a separate thread to parallelize the rasterization workload [S1, unofficial]. It builds on [Tiled Parallel Compositing](1192-tiled-parallel-compositing.md) by decomposing the screen into disjoint regions for independent thread execution.

## How it works
**Inputs and Outputs:**
- Input: Screen height ($H$), screen width ($W$), number of available hardware threads ($N_{hw}$).
- Output: A fully rendered image (framebuffer) where each tile has been rasterized by its assigned thread.

**Data Structures:**
The core data structure is a `Tile` struct, which defines the rectangular region of the screen to be rendered by a specific thread [S1, unofficial]. It contains four integer fields representing the boundaries:
- `x_min`: Left boundary.
- `x_max`: Right boundary.
- `y_min`: Top boundary.
- `y_max`: Bottom boundary.

**Algorithm Steps:**
1. Determine the number of threads to use. If `std::thread::hardware_concurrency()` returns 0 or is unavailable, default to 1 thread to prevent division by zero or empty thread vectors [S1, unofficial].
   $$ THREADS = \max(1, \text{std::thread::hardware\_concurrency}()) $$
2. Calculate the height of each tile. The screen height $H$ is divided by the number of threads [S1, unofficial].
   $$ tileH = \lfloor H / THREADS \rfloor $$
3. Create and launch worker threads. For each thread index $i$ from $0$ to $THREADS - 1$:
   - Define the y-range for the tile.
     $$ y_{min} = i \times tileH $$
     $$ y_{max} = \begin{cases} H - 1 & \text{if } i == THREADS - 1 \\ (i + 1) \times tileH - 1 & \text{otherwise} \end{cases} $$
   - Define the x-range. The tile spans the full screen width, so $x_{min} = 0$ and $x_{max} = W - 1$ [G].
   - Instantiate a `Tile` struct with these coordinates.
   - Launch a new thread executing the `renderTile` function, passing the `Tile` struct as an argument [S1, unofficial].
4. Join all worker threads to ensure completion before proceeding [S1, unofficial].

**Pseudocode:**
```python
import os
import threading

class Tile:
    def __init__(self, x_min, x_max, y_min, y_max):
        self.x_min = x_min
        self.x_max = x_max
        self.y_min = y_min
        self.y_max = y_max

def render_tile(tile, framebuffer, scene):
    # Per-pixel rasterization/compositing step.
    # The exact shading or raymarching logic depends on the volume rendering method [G].
    for y in range(tile.y_min, tile.y_max + 1):
        for x in range(tile.x_min, tile.x_max + 1):
            framebuffer[y][x] = [0.0, 0.0, 0.0]  # Placeholder for pixel computation [G]

def multi_threaded_tile_rendering(width, height, scene):
    hardware_concurrency = os.cpu_count() or 1
    threads = max(1, hardware_concurrency)
    tile_h = height // threads

    thread_list = []
    framebuffer = [[None] * width for _ in range(height)]

    for i in range(threads):
        y_min = i * tile_h
        y_max = height - 1 if i == threads - 1 else (i + 1) * tile_h - 1
        x_min = 0
        x_max = width - 1
        tile = Tile(x_min, x_max, y_min, y_max)
        t = threading.Thread(target=render_tile, args=(tile, framebuffer, scene))
        thread_list.append(t)
        t.start()

    for t in thread_list:
        t.join()

    return framebuffer
```

**Parameters:**
- `THREADS`: Number of parallel workers. Typical value is `std::thread::hardware_concurrency()` [S1, unofficial].
- `tileH`: Height of each tile. Determined by $H / THREADS$ [S1, unofficial].

**Edge Cases and Pitfalls:**
- If `hardware_concurrency()` returns 0, the thread count must be clamped to 1 to avoid division by zero errors when calculating `tileH` or creating an empty thread vector [S1, unofficial].
- The last tile explicitly handles the remainder of the height division using the ternary condition for $y_{max}$ to ensure the entire screen is covered without gaps or overlaps [S1, unofficial].

## Subtopics

### Screen Parallel Rendering
A parallel scheme that divides the screen into $p$ subscreens for $p$ processors, where each processor takes responsibility for the entire ray for its subscreen [S2, unofficial]. Tasks are assigned in a cyclic manner to statically balance workloads [S2, unofficial]. It is suitable for small datasets that do not require data decomposition but requires large main memory because every processor must load the entire volume into memory [S2, unofficial].

### Tile-Based Rasterization
A GPU-oriented variant that rasterizes tile fragments by launching one CUDA thread-block per tile, blending splats in front-to-back order [S3]. The iteration process ping-pongs between utilizing 128 threads to load 128 splats into shared memory and then having each of the 256 threads iterate through the 128 loaded splats to blend them together [S3].

## Background
The concept of dividing the screen into subscreens for parallel processing was introduced in early parallel volume rendering schemes [S2, unofficial]. The specific CPU threading implementation using `std::thread::hardware_concurrency()` is documented in the `CPU-Rasterizer` repository [S1, unofficial].
