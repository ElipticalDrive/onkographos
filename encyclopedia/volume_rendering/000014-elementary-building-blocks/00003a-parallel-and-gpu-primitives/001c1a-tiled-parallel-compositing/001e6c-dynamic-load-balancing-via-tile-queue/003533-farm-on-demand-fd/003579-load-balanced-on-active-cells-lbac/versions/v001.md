# Load Balanced on Active Cells (LBAC)

Also called: LBAC Algorithm, LBC Algorithm, Load Balanced on Cells

## Overview
LBAC is a parallel isosurface extraction algorithm that partitions a 3D volume into contiguous regions along the Z-axis and dynamically balances the computational workload by equalizing the number of **active cells** (cells containing isosurface intersections) among worker processes [S1]. Unlike its sibling [Load Balanced on Cells (LBC)](52-load-balanced-on-cells-lbc.md), which distributes the total number of cells evenly but suffers from unpredictable active cell distribution, LBAC ensures near-perfect load balancing for the triangulation phase by performing a preliminary analysis of active slice weights [S1]. It builds on [Farm on Demand (FD)](7455-farm-on-demand-fd.md) by using a static, contiguous Z-axis partitioning strategy rather than FD's random task assignment, which minimizes shared vertex overhead but requires a two-phase approach to achieve balance [S1].

## How it works
**Inputs:** A 3D volumetric dataset, an isovalue, and the number of parallel processes `numP`.
**Outputs:** A partitioned isosurface mesh (Vertex table, Triangle table, and Index table for shared vertices).

**Data Structures:**
*   `weight[w]`: An array of size `numW` (workers), storing the number of intersections (active cells) found in the slices assigned to worker `w` during the Analysis phase.
*   `start[w]`, `stop[w]`: Arrays of size `numW`, defining the Z-axis slice interval boundaries assigned to each worker for the Isoextraction phase.
*   `numW`: The number of worker processes, calculated as `numP - 1` (where one process is the coordinator) [S1].

**Algorithm Steps:**
The algorithm logically subdivides `numP` processes into one coordinator and `numW` workers. It executes three distinct phases:

1.  **Analysis Phase (Data Parallel):**
    *   The volume is partitioned into `numP` intervals of approximately `Zmax / numP` slices, identical to the LBC partitioning strategy [S1].
    *   Each worker independently processes its assigned interval.
    *   Workers perform a lightweight "Cell Classification" equivalent to identify **active slices** (slices containing at least one intersection). This is faster than full classification because it does not explicitly compute the bit vector [S1].
    *   Each worker counts the number of intersections (active cells) in its interval and sends this count as `weight[w]` to the coordinator [S1].
    *   If the coordinator receives zero active slices from all workers, the algorithm terminates early, as no isosurface exists [S1].

2.  **Balancing Phase (Coordinator):**
    *   The coordinator receives the `weight` array from all workers.
    *   It performs `ActiveSliceBalancing(weight, &start, &stop)` to redistribute the slices. The goal is to assign contiguous slice intervals to each worker such that the sum of active cells in each worker's interval is approximately equal [S1].
    *   The granularity of this balancing is the **single slice**, allowing for fine-grained load distribution [S1].
    *   The coordinator communicates the new interval boundaries (`start[w]`, `stop[w]`) to each worker [S1].

3.  **Isoextraction Phase (Data Parallel):**
    *   Each worker executes the standard isosurface extraction algorithm (based on WWMC, modified for shared vertices) on its newly assigned slice interval [S1].
    *   Workers produce a Vertex table, a Triangle table, and an Index table containing indices of shared vertices on the boundaries of their intervals [S1].
    *   Shared vertices are communicated to neighboring processes to ensure topological consistency [S1].

**Pseudocode:**

```python
# Global variables
numP = number of parallel processes
numW = numP - 1
coordinator_id = 0
isovalue = target isovalue
volume = input_3d_data

# Coordinator Process
if current_process_id == coordinator_id:
    weights = [0] * numW
    
    # Phase 1: Analysis - Collect active cell counts
    for w in range(numW):
        # Receive weight from worker w
        # The weight is the number of intersections in worker w's initial interval
        weights[w] = receive_analysis_result(w)
        
    # Check for empty isosurface
    if sum(weights) == 0:
        terminate()
        
    # Phase 2: Balancing - Compute new intervals
    # ActiveSliceBalancing distributes slices to balance 'weights'
    # It returns start and stop indices for each worker
    starts = [0] * numW
    stops = [0] * numW
    active_slice_balancing(weights, starts, stops)
    
    # Send new intervals to workers
    for w in range(numW):
        send_iso_extraction_interval(w, starts[w], stops[w])

# Worker Processes
else:
    worker_id = current_process_id - 1
    
    # Phase 1: Analysis - Count active cells in initial interval
    # Initial interval is roughly worker_id * (Zmax/numW) to (worker_id+1) * (Zmax/numW)
    initial_start = worker_id * (volume.z_max // numP)
    initial_stop = (worker_id + 1) * (volume.z_max // numP)
    
    active_count = 0
    for z in range(initial_start, initial_stop):
        # Lightweight classification: check if slice z has intersections
        if slice_has_intersections(volume, z, isovalue):
            active_count += count_intersections_in_slice(volume, z, isovalue)
            
    # Send weight to coordinator
    send_analysis_result(worker_id, active_count)
    
    # Wait for new interval from coordinator
    new_start, new_stop = receive_iso_extraction_interval()
    
    # Phase 3: Isoextraction - Extract isosurface on new interval
    vertex_table = []
    triangle_table = []
    index_table = []
    
    for z in range(new_start, new_stop):
        # Extract triangles for slice z using modified WWMC
        # Handle shared vertices on slice boundaries
        triangles = extract_slice_triangles(volume, z, isovalue)
        triangle_table.extend(triangles)
        
    # Generate index table for shared vertices at new_start and new_stop
    # to communicate with neighbors
    index_table = generate_shared_vertex_indices(vertex_table, new_start, new_stop)
    
    # Output results
    output_mesh(vertex_table, triangle_table, index_table)
```

**Parameters:**
*   `numP`: Number of parallel processes. Determines the initial slice interval size [S1].
*   `numW`: Number of worker processes (`numP - 1`) [S1].

**Edge Cases and Pitfalls:**
*   **Double Execution Overhead:** The Cell Classification operation (or its lightweight equivalent) is performed twice: once in the Analysis phase and again in the Isoextraction phase. This overhead is significant for small-to-medium isosurfaces, where the rebalancing cost exceeds the active cell processing cost [S1].
*   **Empty Isosurfaces:** If the Analysis phase finds no active slices, the algorithm terminates early. This can lead to superlinear speedup compared to other algorithms that continue processing, but this is a rare edge case [S1].
*   **I/O Contiguity:** The algorithm assumes contiguous slice access. If the underlying dataset is stored in scattered blocks (e.g., 128x128x256 blocks), I/O time increases by more than 5x due to non-contiguous memory access patterns during the Analysis and Isoextraction phases [S1].
*   **Shared Vertices:** While LBAC balances triangles well, it produces more shared vertices than LBC because the rebalancing may split contiguous regions differently, though fewer than FD [S1].

## Subtopics

### Load Balanced on Cells (LBC)
Partitions volume by total cell count. Simpler but suffers from uneven active cell distribution. Choose when isosurfaces are homogeneous or when avoiding the Analysis phase overhead is critical. [LBC](52-load-balanced-on-cells-lbc.md)

### Farm on Demand (FD)
Uses random task assignment for fine-grained balancing. Produces more shared vertices and higher I/O overhead for contiguous data. Choose when data is already partitioned into scattered blocks or when extreme heterogeneity requires dynamic task stealing. [FD](7455-farm-on-demand-fd.md)

## Operating characteristics
**Time and Memory Complexity:**
*   The speedup depends heavily on the percentage of active cells. For large isosurfaces, the Active Cell Triangulation dominates, and LBAC achieves near-linear speedup due to perfect load balancing [S1].
*   For small-to-medium isosurfaces, the overhead of the Analysis phase and the double execution of input acquisition/Cell Classification degrade performance, making LBAC less efficient than LBC [S1].
*   Achievable speedup is inversely related to the size of the resulting isosurface relative to the dataset; smaller isosurfaces mean the fixed overhead of the two-phase approach is more prominent [S1].

**Measured Performance:**
*   On dataset **1NKW-3018** (large, homogeneous) with 16 processes: LBAC spends 0.30s on I/O and 0.66s on CPU computation. LBC outperforms LBAC here due to lower I/O overhead from single contiguous acquisition [S1].
*   On dataset **XT-25** (medium, large isosurface) with 16 processes: LBAC spends 9.1s on I/O and 10.2s on CPU. On **XT-180**, LBAC spends 6.0s on CPU [S1].
*   On dataset **FC-1000** (non-homogeneous): LBC was severely unbalanced (process 5 had 7x the load of others). LBAC achieved nearly perfect balance (5.5% to 6.4% load per worker) but produced 318,472 shared vertices (vs. 195,804 for LBC) [S1].

**Strengths and Limitations:**
*   **Strengths:** Near-perfect load balancing for the computationally expensive triangulation phase; handles non-homogeneous isosurfaces effectively; lower shared vertex count than FD [S1].
*   **Limitations:** Higher overhead for small/medium isosurfaces; sensitive to I/O patterns (requires contiguous slice storage); requires a coordinator process [S1].
*   **When to use:** Large datasets with large, non-homogeneous isosurfaces where perfect load balancing is required.
*   **When not to use:** Small-to-medium isosurfaces (overhead dominates); datasets stored in scattered blocks (I/O penalty) [S1].

## Background
LBAC was introduced by D. D’Agostino, A. Clematis, and V. Gianuzzi in their 2000 paper "Parallel Isosurface Extraction for 3D Data Analysis Workflows in Distributed Environments" [S1]. It represents the third class of parallel algorithms in their classification, improving upon the LBC algorithm (first class) by adding a dynamic load balancing strategy based on active cell counts. It is distinct from the Farm on Demand (FD) algorithm (fourth class) by using a static, contiguous Z-axis partitioning rather than dynamic task distribution [S1].
