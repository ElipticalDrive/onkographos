# Dynamic Task Scheduling

Also called: Dynamic Ray-Task Scheduling

## Overview
Dynamic Task Scheduling is a load-balancing method for distributed volume rendering that dynamically schedules subvolumes (flex-bricks) or ray tasks within each render node. It solves the problem of uneven computational load caused by variable ray traversal depths and data density, which static distribution cannot address efficiently. Unlike static partitioning, it uses ray queues and neighbor communication to adaptively assign work, ensuring that nodes process data in an order that minimizes cache misses and balances the workload across the cluster [S1, unofficial].

## How it works
The method operates in two distinct contexts: distributed ray tracing (using flex-bricks) and GPU-based Kernel-Reflection Sequence (KRS) rendering.

### Distributed Ray Tracing with Flex-Bricks
**Inputs:** A massive volume dataset partitioned into render nodes; a flex-block dependency graph representing the spatial hierarchy of subvolumes.
**Outputs:** Rendered image contributions from each node.
**Data Structures:**
*   **Ray Queue:** A per-cell queue holding pending rays that have entered a specific cell (flex-brick) but not yet exited it.
*   **Flex-Block Dependency Graph:** A directed graph where nodes are flex-bricks (cells containing tightly cropped subvolumes) and edges represent spatial adjacency and traversal order.

**Steps:**
1.  **Initialization:** Each render node calculates the initial ray contributions for the portion of data statically assigned to it.
2.  **Ray Queue Population:** For each cell in the local partition, initialize a ray queue to hold pending rays.
3.  **Ray Tracing Loop:**
    a.  Select the next cell to process based on the flex-block dependency graph and the direction of the ray segments.
    b.  If the cell is not in main memory, fetch it.
    c.  Trace all rays currently in the cell's ray queue through the cell's data.
    d.  For each ray:
        i.  If the ray exits the current cell, determine the next intersecting cell using the dependency graph.
        ii. Place the ray on the ray queue of the next cell.
        iii. If the ray converges (hits an object or exits the volume), store the intersection point.
4.  **Neighbor Communication:** Each node communicates ray information (newly spawned rays or rays exiting the local partition) to neighboring nodes to update their respective ray queues.
5.  **Completion:** Repeat until all rays have converged or exited the volume.

**Pseudocode:**
```python
# Pseudocode for Distributed Ray Tracing with Dynamic Task Scheduling
# Assumes a distributed system with local memory and network communication

def dynamic_task_scheduling_ray_tracing(node_id, volume_data, dependency_graph):
    # Initialize local ray queues for each cell in the node's partition
    ray_queues = {cell_id: [] for cell_id in node_id.local_cells}
    
    # Initial rays for the node's assigned data
    initial_rays = generate_initial_rays(node_id)
    for ray in initial_rays:
        start_cell = dependency_graph.get_start_cell(ray)
        ray_queues[start_cell].append(ray)
        
    while not all_rays_converged(ray_queues):
        # Determine next cell to process based on dependency graph and ray directions
        next_cell = select_next_cell(ray_queues, dependency_graph)
        
        # Fetch cell data if not in memory
        cell_data = fetch_or_load_cell(next_cell)
        
        # Process all rays in the current cell's queue
        next_queue_updates = {}
        for ray in ray_queues[next_cell]:
            # Trace ray through cell
            hit, exit_point, remaining_ray = trace_ray_through_cell(ray, cell_data)
            
            if hit:
                store_intersection(ray, hit)
            elif remaining_ray is not None:
                # Determine next cell
                next_cell_id = dependency_graph.get_next_cell(ray, exit_point)
                
                # If next cell is in another node, communicate
                if next_cell_id not in node_id.local_cells:
                    send_ray_to_neighbor(next_cell_id, remaining_ray)
                else:
                    # Add to local queue of next cell
                    if next_cell_id not in next_queue_updates:
                        next_queue_updates[next_cell_id] = []
                    next_queue_updates[next_cell_id].append(remaining_ray)
        
        # Clear current cell's queue and update with new rays
        ray_queues[next_cell] = []
        for cell_id, rays in next_queue_updates.items():
            ray_queues[cell_id].extend(rays)
            
    # Final shading pass
    shade_all_intersections()
```

### GPU Scheduling for KRS
**Inputs:** Compound KRS models with varying distance evaluation code; primary rays.
**Outputs:** Intersection points for shading.
**Data Structures:**
*   **Task Buffer:** A buffer holding tasks, where each task represents a few sphere tracing iterations.
*   **Per-Component Free Distances:** An array storing the remaining distance to travel for each ray component.
*   **Sorted Index:** A small sorted index for faster minimum selection among components.

**Steps:**
1.  **Task Breakdown:** Break ray evaluation into tasks, each evaluating a few sphere tracing iterations.
2.  **Task Buffer Management:**
    a.  For each ray, determine the component with the minimal free distance.
    b.  Insert a task into the respective buffer for that component.
    c.  If the ray has converged, store the intersection point.
3.  **Processing:** Process all task buffers one after another.
4.  **Update:** When a task is finished, update the free distance and the sorted index.
5.  **Coherence Exploitation:** For primary rays, perform the first few steps of sphere tracing at a lower resolution. Advance the current point on the ray only as far as the frustum of the low-res pixel is entirely covered by the unbounding sphere.
6.  **Deferred Shading:** Once all rays are converged, perform shading for all intersection points in a deferred manner.

**Pseudocode:**
```python
# Pseudocode for GPU Scheduling for KRS

def gpu_krs_scheduling(rays, krs_models):
    # Initialize task buffers for each component type
    task_buffers = {comp_type: [] for comp_type in krs_models}
    
    # Initialize per-component free distances and sorted index
    free_distances = {ray_id: {comp: ray.length for comp in krs_models} for ray_id in rays}
    sorted_index = build_sorted_index(free_distances)
    
    # Initial task creation
    for ray in rays:
        # Exploit coherence for primary rays
        if ray.is_primary:
            low_res_step = perform_low_res_sphere_tracing(ray)
            ray.current_point = low_res_step.point
            ray.remaining_length = low_res_step.remaining_length
            
        # Determine component with minimal free distance
        min_comp = sorted_index.get_min_component(ray.id)
        
        # Create task for a few iterations
        task = create_task(ray, min_comp, iterations=5)
        task_buffers[min_comp].append(task)
        
    # Process task buffers
    while any(task_buffers):
        for comp_type, buffer in task_buffers.items():
            if not buffer:
                continue
                
            new_tasks = []
            converged_rays = []
            
            for task in buffer:
                # Execute task (few sphere tracing iterations)
                result = execute_task(task)
                
                if result.converged:
                    converged_rays.append(result.intersection_point)
                else:
                    # Update free distance and index
                    update_free_distance(task.ray_id, comp_type, result.remaining_length)
                    update_sorted_index(task.ray_id, comp_type)
                    
                    # Determine next component
                    next_comp = sorted_index.get_min_component(task.ray_id)
                    
                    # Create new task
                    new_task = create_task(task.ray, next_comp, iterations=5)
                    new_tasks.append(new_task)
            
            # Update buffers
            task_buffers[comp_type] = new_tasks
            
    # Deferred shading
    for ray_id, points in converged_rays.items():
        shade_ray(ray_id, points)
```

## Subtopics

### GPU Scheduling for KRS
A task-based GPU scheduling scheme to handle variable sphere tracing convergence times and compound KRS models with different distance evaluation code. It breaks ray evaluation into small tasks, uses task buffers per component, and exploits coherence for primary rays by using low-resolution sphere tracing. It is chosen when rendering complex procedural models with varying convergence rates on GPU hardware [S2].

## Operating characteristics
*   **Time Complexity:** Depends on the number of rays and the depth of traversal. Dynamic scheduling reduces idle time but adds overhead for queue management and communication.
*   **Memory Complexity:** Requires storage for ray queues (distributed) or task buffers (GPU). The size depends on the number of active rays and the number of components in KRS models.
*   **Performance:** Improves load balance in distributed systems by adapting to data density and ray behavior. In GPU KRS, it prevents thread divergence by breaking long rays into smaller tasks.
*   **Strengths:** Handles variable workloads effectively; reduces cache misses in distributed systems by following data locality; improves GPU utilization for complex models.
*   **Limitations:** Adds complexity to implementation; requires communication overhead in distributed settings; task management overhead on GPU.
*   **When to Use:** When static load balancing is insufficient due to uneven data distribution or variable ray convergence times.
*   **When Not to Use:** For simple, uniform volumes where static partitioning is sufficient and overhead is not justified.

## Background
Dynamic Task Scheduling originated in the context of massive data management for distributed volume visualization. It was proposed to address the NP-Complete problem of optimal cell caching order by using dynamic scheduling of flex-bricks [S1, unofficial]. The method has been extended to GPU-based rendering for Kernel-Reflection Sequences (KRS) to handle the variability in sphere tracing convergence [S2].
