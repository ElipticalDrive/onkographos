# Tiled Parallel Compositing

Also called: Tile-based parallel compositing, Disjoint tile compositing

## Overview
Tiled parallel compositing is a rendering strategy where the framebuffer is divided into disjoint spatial tiles, allowing multiple threads or processes to composite fragments (such as splats or volume samples) into their respective regions simultaneously with zero synchronization, no atomics, and no locks [S1, unofficial]. It is distinguished from [Parallel Direct Compositing](3201-parallel-direct-compositing.md) by its explicit spatial partitioning of the output buffer, which eliminates race conditions on pixel writes, and from [Y-Bucket Parallelization](2108-y-bucket-parallelization.md) by relying on static spatial locality rather than depth-based bucketing for parallelism.

## How it works
**Inputs:**
- `N`: Total number of fragments (e.g., splats, volume samples) to composite.
- `W`, `H`: Framebuffer width and height in pixels.
- `TILE_W`, `TILE_H`: Tile dimensions in pixels.
- `fragments`: Array of fragment data, each containing projected position, bounding box, and color/opacity attributes.
- `bins`: A data structure mapping tile indices to ranges of fragment indices (typically generated by a prior sorting or binning step).

**Outputs:**
- `framebuffer`: An array of size `W * H`, where each element is a color/opacity tuple (e.g., `Vec3` color and `f32` alpha).

**Data Structures:**
- `ScratchBuffers`: A structure for reusable temporary memory to avoid allocation overhead in parallel loops.
  ```rust
  pub struct ScratchBuffers {
      pub sort_aux: Vec<Projected>, // Temporary storage for sorting if needed
      pub tiles: TileBins,          // Structure holding tile-to-fragment mappings
  }
  ```
- `TileBins`: Contains an `offsets` array of size `num_tiles + 1`, where `offsets[i]` and `offsets[i+1]` define the inclusive-exclusive range of fragment indices assigned to tile `i`.

**Steps:**
1. **Calculate Tile Grid:** Determine the number of tiles in x and y directions:
   $$ T_x = \lceil W / TILE_W \rceil $$
   $$ T_y = \lceil H / TILE_H \rceil $$
   $$ TotalTiles = T_x \times T_y $$

2. **Parallel Iteration:** Iterate over all tile indices `t_idx` from `0` to `TotalTiles - 1` in parallel. Each thread/process handles one `t_idx`.

3. **Compute Tile Bounds:**
   Calculate the pixel coordinates of the tile:
   $$ tile\_x = t\_idx \pmod{T_x} $$
   $$ tile\_y = \lfloor t\_idx / T_x \rfloor $$
   $$ px0 = tile\_x \times TILE\_W $$
   $$ py0 = tile\_y \times TILE\_H $$
   $$ px1 = \min(px0 + TILE\_W - 1, W - 1) $$
   $$ py1 = \min(py0 + TILE\_H - 1, H - 1) $$

4. **Validate Tile Bounds:**
   If `px0 > px1` or `py0 > py1`, the tile is invalid (e.g., due to rounding errors or empty space); return immediately.

5. **Retrieve Fragment Range:**
   Get the range of fragment indices for this tile from the pre-computed bins:
   $$ start = bins.offsets[t\_idx] $$
   $$ end = bins.offsets[t\_idx + 1] $$

6. **Check Empty Tile:**
   If `start == end`, the tile has no fragments; return immediately.

7. **Process Fragments:**
   For each fragment ID `sid` in the range `[start, end)`:
   a. Retrieve the projected fragment `p` from the global projected data array.
   b. Get the fragment's axis-aligned bounding box `[bx0, by0, bx1, by1]`.
   c. Compute the intersection of the fragment's bounding box with the tile's pixel bounds `[px0, py0, px1, py1]`:
      $$ ix0 = \max(bx0, px0) $$
      $$ iy0 = \max(by0, py0) $$
      $$ ix1 = \min(bx1, px1) $$
      $$ iy1 = \min(by1, py1) $$
   d. If `ix0 > ix1` or `iy0 > iy1`, the fragment does not overlap the tile; continue to the next fragment.
   e. Call `composite_splat_region(p, framebuffer, W, ix0, iy0, ix1, iy1)` to blend the fragment into the framebuffer pixels within the intersection bounds.

**Pseudocode:**
```python
def tiled_parallel_compositing(fragments, bins, framebuffer, width, height, tile_w, tile_h):
    """
    Composites fragments into disjoint tiles in parallel.
    Note: The outer loop is conceptually parallelized by the runtime (e.g., rayon, OpenMP).
    """
    tile_x_count = (width + tile_w - 1) // tile_w
    tile_y_count = (height + tile_h - 1) // tile_h
    total_tiles = tile_x_count * tile_y_count

    # Parallel loop over tiles
    for t_idx in range(total_tiles):
        # 1. Calculate tile coordinates
        tx = t_idx % tile_x_count
        ty = t_idx // tile_x_count

        # 2. Calculate pixel bounds
        px0 = tx * tile_w
        py0 = ty * tile_h
        px1 = min(px0 + tile_w - 1, width - 1)
        py1 = min(py0 + tile_h - 1, height - 1)

        # 3. Validate tile bounds
        if px0 > px1 or py0 > py1:
            continue

        # 4. Retrieve fragment range
        start = bins.offsets[t_idx]
        end = bins.offsets[t_idx + 1]

        # 5. Check empty tile
        if start == end:
            continue

        # 6. Process fragments in this tile
        for sid in range(start, end):
            p = fragments[sid]
            
            # Get fragment bounding box
            bx0, by0, bx1, by1 = p.bounding_box
            
            # 7. Compute intersection
            ix0 = max(bx0, px0)
            iy0 = max(by0, py0)
            ix1 = min(bx1, px1)
            iy1 = min(by1, py1)
            
            # 8. Validate intersection
            if ix0 > ix1 or iy0 > iy1:
                continue
            
            # 9. Composite
            composite_region(framebuffer, width, p, ix0, iy0, ix1, iy1)

def composite_region(framebuffer, width, fragment, x0, y0, x1, y1):
    """
    Blends a single fragment into the framebuffer pixels within the given bounds.
    Assumes front-to-back or appropriate compositing order is handled by the caller
    or the fragment data structure.
    """
    for y in range(y0, y1 + 1):
        for x in range(x0, x1 + 1):
            # Calculate pixel index
            idx = y * width + x
            
            # Get current pixel color/alpha
            current_color, current_alpha = framebuffer[idx]
            
            # Get fragment color/alpha at this pixel (interpolated if necessary)
            frag_color, frag_alpha = fragment.sample(x, y)
            
            # Alpha compositing: C_out = C_frag + C_curr * (1 - A_frag)
            # Or standard over operator: C_out = C_frag + C_curr * A_frag * (1 - A_frag)? 
            # Standard over: C_out = C_frag + C_curr * (1 - A_frag)
            # But usually we track accumulated alpha. 
            # Let's use standard over: C_new = C_frag + C_curr * (1 - A_frag)
            # And A_new = A_frag + A_curr * (1 - A_frag)
            
            new_alpha = frag_alpha + current_alpha * (1.0 - frag_alpha)
            new_color = frag_color + current_color * (1.0 - frag_alpha)
            
            framebuffer[idx] = (new_color, new_alpha)
```

**Parameters:**
- `TILE_W`, `TILE_H`: Typical values are 16x16 or 16x32 pixels [S2].
- `bins.offsets`: Must be pre-computed to ensure each fragment is assigned to exactly one tile (or handled via overlap logic if fragments span multiple tiles, though disjoint compositing usually implies one tile per write or careful overlap handling) [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Borrow Checker/Concurrency:** In languages like Rust, multiple threads cannot hold mutable references to the same buffer. This is handled by wrapping the raw framebuffer pointer in a `Send + Sync` newtype (e.g., `FbPtr(*mut (Vec3, f32))`) and relying on the geometric guarantee that tile `(tx, ty)` only writes to pixels `[tx*TILE_W..(tx+1)*TILE_W, ty*TILE_H..(ty+1)*TILE_H]` [S1, unofficial].
- **Precision:** Floating-point precision in bounding box calculations should be sufficient to avoid gaps or overlaps between adjacent tiles.
- **Degenerate Input:** Empty tiles (no fragments) must be skipped efficiently to avoid overhead [S1, unofficial].

## Subtopics

### Adaptive Tile Sizing
A strategy to select between two tile dimensions (16x16 and 16x32) based on the number of pixels to render to optimize performance [S2]. It is distinguished from fixed-size tiling by its dynamic adjustment based on resolution. Choose it when rendering at varying resolutions where performance characteristics change significantly. The threshold is 1.5 million pixels: if pixel count < 1.5M, use 16x32 tiles; otherwise, use 16x16 tiles [S2]. A pitfall is that tile orientation performance depends on memory indexing: with column-major indexing, 16x32 outperforms 32x16, while with row-major indexing, the reverse is true [S2]. On the low-resolution Bicycle scene, using 16x32 tiles increased the average render time to 9.77 ms, demonstrating that larger tiles are not always faster [S2]. Increasing tile size reduces duplicated Gaussians but increases sequential processing load per tile and complicates thread-block size optimization [S2].

### Tile-Based Wave Synchronization
Manages tile assignment and synchronization across worker threads using wave indices and tokens [S3, unofficial]. It is distinguished from lock-free compositing by its use of synchronization primitives for coordinated progress tracking. Choose it when global progress reporting or coordinated stopping is required. A `token` holds a tile index, wave index, and job ID, created by `TileProvider::next()` [S3, unofficial]. When a token is destroyed, it updates the provider's tile wave map and notifies all waiting threads: `m_tp.m_tile_wave[m_idx] = m_wave_idx; m_tp.m_tile_wave[m_idx].notify_all();` [S3, unofficial]. Workers can call `stop_at_next_wave()` to finish their current wave before stopping [S3, unofficial]. The ETA calculation is: `avg_progress_rate = progress / elapsed_time`, `eta = (1 - progress) / avg_progress_rate` [S3, unofficial].

### [Tile Boundary Computation Setup](2678-tile-boundary-computation-setup.md)
This method initializes the data structures required for tiled parallel compositing by computing which geometry overlaps each tile in the output framebuffer [1192-tiled-parallel-compositing.md]. It differs from [Tile-Based Alpha Compositing](1215-tile-based-alpha-compositing.md) and [Dynamic Load Balancing via Tile Queue](1763-dynamic-load-balancing-via-tile-queue.md) by relying on a global radix-sort to organize tile relationships rather than per-tile queues or expensive coverage tests during setup.

### [Parallel Image Assembly](3271-parallel-image-assembly.md)
Parallel Image Assembly is the final stage of tiled parallel volume rendering where per-process or per-rank RGBA sub-images are collected and blended into a single final image. It solves the problem of reconstructing a coherent global view from disjoint spatial tiles processed independently. Unlike its siblings which handle tile distribution or boundary computation, this method focuses on the global accumulation of color and opacity, typically using front-to-back alpha compositing.

### [Multi-Threaded Tile-Based Rendering](3784-multi-threaded-tile-based-rendering.md)
Multi-Threaded Tile-Based Rendering is a CPU-based parallelization strategy that divides the screen height into horizontal tiles, assigning each tile to a separate thread to parallelize the rasterization workload. It differs from its sibling [Tile-Based Alpha Compositing](1215-tile-based-alpha-compositing.md) by focusing on the rasterization phase itself rather than just the compositing of pre-rasterized fragments, and from [Screen Parallel Rendering](5725-screen-parallel-rendering.md) by dividing the screen into tiles processed by threads on a single machine rather than subscreens distributed across multiple processors.

### Tile-Grouping Architecture
A tile-grouping architecture that merges adjacent tiles into larger work units, reducing redundant sorting and improving data reuse within GPU streaming multiprocessors [S4, unofficial]. It is distinguished from standard tiling by its hierarchical aggregation of tiles. Choose it for GPU rendering where memory bandwidth and sorting overhead are bottlenecks. It is part of a hardware-algorithm co-design approach, as seen in GS-TG [S4, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N + T \times K)$, where $N$ is the number of fragments, $T$ is the number of tiles, and $K$ is the average number of fragments per tile. The parallelization reduces the effective time per tile to $O(K/P)$ where $P$ is the number of parallel workers, assuming balanced load.
- **Memory Complexity:** $O(W \times H + N)$ for the framebuffer and fragment data. Additional $O(T)$ for tile bins [S1, unofficial].
- **Measured Performance:** On the Bicycle scene, adaptive tile sizing showed that 16x32 tiles increased render time to 9.77 ms at low resolution, while 16x16 tiles were faster [S2].
- **Scaling:** Scales well with the number of tiles and fragments, provided the load is balanced. Imbalanced fragment distribution can lead to idle threads [S1, unofficial].
- **Strengths:** Zero synchronization overhead, no atomics, no locks, making it highly effective on CPU and simple GPU implementations [S1, unofficial].
- **Limitations:** Requires pre-computation of tile-fragment mappings (binning/sorting). Load imbalance can occur if fragments are not evenly distributed across tiles.
- **When to use:** When rendering semi-transparent fragments (splats, volumes) with high overlap, and when synchronization overhead is a bottleneck.
- **When not to use:** When fragments are sparse and tile overhead dominates, or when dynamic load balancing is critical without queue mechanisms.

## Background
Tiled parallel compositing originated as a method to parallelize alpha compositing without the need for complex synchronization primitives. It is widely used in modern Gaussian Splatting renderers (e.g., 3DGS) and volume rendering pipelines to leverage multi-core CPUs and GPUs efficiently [S1, unofficial][S2]. The technique has been refined with adaptive tile sizing and tile-grouping architectures to optimize performance across different hardware and resolutions [S2][S4, unofficial].
