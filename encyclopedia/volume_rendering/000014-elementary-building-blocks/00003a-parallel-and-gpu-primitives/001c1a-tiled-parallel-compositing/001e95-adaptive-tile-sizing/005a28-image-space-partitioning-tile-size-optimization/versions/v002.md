# Image-Space Partitioning (Tile Size Optimization)

Also called: Image Tile Sizing and Work Assignment Strategy, Image Tile Tuning, Work Block Sizing

## Overview
Image-Space Partitioning divides the output image into rectangular tiles to distribute ray-casting work among parallel threads, balancing the trade-off between mutex contention (small tiles) and load imbalance (large tiles) [S1]. It differs from sibling methods by explicitly treating tile dimensions as tunable parameters subject to empirical sweep, rather than fixed constants, to identify performance "sweet spots" on specific hardware [S1]. The method builds on [Adaptive Tile Sizing](1805-adaptive-tile-sizing.md).

## How it works
**Inputs:**
*   Image dimensions ($W \times H$) [S1].
*   Hardware constraints (e.g., maximum threads per block and register memory limits) [S1].
*   Memory layout (e.g., row-major ordering) [S1].

**Outputs:**
*   Optimal tile width ($T_w$) and height ($T_h$) [S1].
*   Work assignment strategy (static or dynamic) [S1].

**Data Structures:**
*   **Work List:** A queue of tiles to be processed, protected by a mutex for dynamic thread access [S1].
*   **Tile Grid:** The image decomposed into a grid of tiles, where boundary tiles are handled by clamping coordinates or processing partial tiles [G].

**Steps:**
1.  **Define Search Space:** Select ranges for tile width and height, typically using powers of two: $\{1, 2, 4, \dots, 256, 512\}$ [S1].
2.  **Filter Invalid Configurations:** Exclude combinations that result in fewer than 2 total work blocks, as they prevent effective parallelization [S1].
3.  **Benchmark:** For each valid $(T_w, T_h)$ pair, render multiple views (e.g., 30 views) using the chosen work assignment strategy and measure the Frame Rendering Time (FRT) [S1].
4.  **Normalize Performance:** Calculate normalized FRT for each configuration:
    $$ \text{Normalized FRT} = \frac{\text{FRT}_{config}}{\min(\text{FRT}_{all})} $$
    Values range from $1.0$ (optimal) to $\infty$ [S1].
5.  **Identify Sweet Spot:** Select the configuration with the lowest normalized FRT [S1].
6.  **Select Work Assignment:** Use static assignment for the smallest block sizes, but prefer dynamic assignment for medium and large block sizes (e.g., $32 \times 32$) due to better load balance [S1].

**Parameters:**
*   **Optimal Tile Size (CPU):** $32 \times 32$ pixels [S1].
*   **Optimal Thread Block Size (GPU, FX5800):** $4 \times 2$ threads [S1].
*   **GPU Constraints:** Maximum 512 threads per block and 16KB register memory per block [S1].

**Pitfalls:**
*   **Small Tiles:** Cause serialized access to the work list via mutex, degrading performance [S1].
*   **Large Tiles:** Result in insufficient tiles for good load balance [S1].
*   **Cache Misses:** Block widths of 1, 2, and 4 exhibit poor performance due to high L1, L2, and TLB cache miss rates caused by degraded spatial/temporal locality in row-major memory layouts [S1].
*   **Invalid Decompositions:** Configurations yielding 1 or 2 total blocks are invalid for parallelization [S1].

    """
    Sweeps tile dimensions to find the configuration with the minimum normalized FRT.
    Returns (optimal_w, optimal_h, strategy).
    """
    # Define search space: powers of two up to image dimensions
    widths = [1, 2, 4, 8, 16, 32, 64, 128, 256, 512]
    heights = [1, 2, 4, 8, 16, 32, 64, 128, 256, 512]
    
    # Filter dimensions to not exceed image size
    widths = [w for w in widths if w <= image_width]
    heights = [h for h in heights if h <= image_height]
    
    min_frt = float('inf')
    best_config = None
    
    for w in widths:
        for h in heights:
            # Calculate total number of tiles using ceiling division
            num_tiles_w = (image_width + w - 1) // w
            num_tiles_h = (image_height + h - 1) // h
            total_tiles = num_tiles_w * num_tiles_h
            
            # Filter invalid configurations (< 2 blocks)
            if total_tiles < 2:
                continue
                
            # Filter GPU hardware constraints
            if w * h > max_threads_per_block:
                continue
                
            frts = []
            for _ in range(30): # Sweep over 30 views [S1]
                # Initialize work list with tile coordinates
                work_list = [(x, y) for x in range(num_tiles_w) for y in range(num_tiles_h)]
                
                # Threads pop from work_list protected by a mutex for dynamic assignment [S1]
                render_time = measure_frame_rendering_time(work_list)
                frts.append(render_time)
                
            current_frt = min(frts) # Minimum times represent optimal, contention-free conditions [S1]
            
            if current_frt < min_frt:
                min_frt = current_frt
                best_config = (w, h)
                
    # Determine work assignment strategy
    # Dynamic is preferred for medium/large tiles for better load balance [S1]
    strategy = "dynamic" if best_config[0] * best_config[1] >= 32*32 else "static"

## Subtopics

### Thread Block Configuration
Tests block sizes ranging from 4 to 128 threads per block [S2]. Best overall results are obtained by combining compute shaders with ray/box intersection tests [S2]. Squared block configurations yield superior results compared to rectangular blocks because they enable more coalesced accesses to the volume texture [S2].

### Image-Space Partitioning
A parallelization subdivision where different parts of the image are computed on different machines [S3]. Achieves good scalability with the size of the output image but does not allow processing larger data sets [S3].

## Operating characteristics
*   **Performance Variation:** The worst-performing tile size can be up to 3.0 times slower than the best configuration, with a maximum normalized FRT of approximately 3.0 [S1].
*   **Complexity:** The optimization phase requires $O(N \cdot V \cdot T)$ operations, where $N$ is the number of tile configurations, $V$ is the number of views, and $T$ is the render time per view [S1].
*   **Strengths:** Identifies hardware-specific optimal parameters and handles load imbalance effectively for medium and large tiles using dynamic assignment [S1].
*   **Limitations:** Requires empirical tuning, suffers from mutex overhead on small tiles, suffers from load imbalance on large tiles, and experiences high cache miss rates for specific tile shapes due to row-major memory layouts [S1].
*   **When to Use:** Deploy to specific hardware architectures where tile size significantly impacts cache behavior and synchronization overhead [S1].

## Background
The method originates from studies on hybrid parallelism for volume rendering on multi-core systems, specifically analyzing shared-memory raycasting on AMD Opteron CPUs and CUDA GPUs (FX5800) [S1]. It addresses the need to balance parallel efficiency with memory access patterns in image-space partitioning [S1].
