# DP Algorithm (Configuration Selection)
Also called: Dynamic Programming

## Overview
The DP Algorithm is a configuration selection method that determines the globally optimal pair of parameters for segmented objects within a multi-NeRF framework, subject to a total memory budget constraint [S1]. It differs from baseline strategies like Fairness by intelligently reallocating resources from low-complexity objects to high-complexity ones, rather than distributing the budget equally [S1]. This approach addresses the problem of rendering failures and low quality on resource-constrained devices by ensuring the total size of all segmented NeRF representations does not exceed the available capacity [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of segmented objects, each with a set of candidate configuration pairs (parameters defining the NeRF representation size and quality), and a global total memory budget limit [S1].
*   **Output:** A selected configuration pair for each segmented object that maximizes rendering quality while satisfying the total memory constraint [S1].

**Data Structures:**
The algorithm relies on a dynamic programming solver. The specific internal data structure layout (e.g., DP table dimensions, bit packing) is not given in the sources [S1]. The solver takes inputs from a performance profiler module, which includes sample points generation and curve fitting data [S1].

**Steps:**
1.  **Profiling:** For each segmented object, generate performance data (sample points and curve fitting) to characterize the relationship between configuration parameters and memory usage/quality [S1]. This step takes approximately 0.277 seconds [S1].
2.  **DP Solver Execution:** Solve the optimization problem defined in the source paper (Eq. 2 in [S1]) using dynamic programming to find the optimal configuration pairs for all objects under the total size limit constraint [S1]. The solver accounts for the principle of optimality to ensure a globally optimal schedule [S1]. This step takes approximately 1.87 seconds [S1].
3.  **Allocation:** Assign the computed optimal configuration pair to each segmented object [S1].

**Formulas and Parameters:**
The specific mathematical formulation (Eq. 2) is not provided in the text, but the objective is to maximize rendering quality subject to $\sum_{i} \text{size}(config_i) \leq \text{Total Budget}$ [S1].

## Subtopics

### Fairness (Configuration Selection)
A baseline configuration selection strategy that distributes the total memory budget equally among all segmented objects [S1]. It divides the total size limit equally across all objects and then uses performance profilers to select the optimal configuration pair for each object within its fixed memory budget [S1]. It is chosen as a simple baseline but underperforms DP on scenes with high object diversity [S1].

## Operating characteristics
**Time and Memory Complexity:**
The DP solver overhead is 1.87 seconds for 20 training images, accounting for 31% of the total 5.9-second preprocessing overhead [S1]. The performance profiler module requires 0.277 seconds (4.7% of processing time) [S1]. The specific computational complexity (Big-O) is not given in the sources [S1].

**Measured Performance:**
On mobile devices (iPhone), the DP algorithm achieves nearly 0.92 SSIM for random scenes, compared to around 0.91 for Fairness and SLSQP [S1]. For Scene 4 (high object diversity), it attains 0.94 SSIM on both tested devices, while other methods struggle to reach this level [S1].

**Strengths and Limitations:**
*   **Strengths:** Consistently outperforms Fairness and SLSQP, especially on scenes with high object diversity [S1]. It intelligently reallocates resources from low-complexity objects to high-complexity ones (e.g., +14MB to Lego, +27MB to ship) [S1].
*   **Limitations:** Requires preprocessing overhead (5.9s total, excluding training) [S1]. The specific scalability to very large numbers of objects is not quantified beyond the 20-image test case [S1].

**When to Use:**
Use when rendering complex multi-object scenes on resource-constrained devices (e.g., mobile) where total memory is limited and object complexity varies significantly [S1].

## Background
The algorithm was proposed in the NeRFlex framework, designed for resource-aware real-time high-quality rendering of complex scenes on mobile devices [S1]. It addresses challenges of low rendering quality and high resource demands by employing a multi-NeRF framework [S1]. The method was evaluated on iPhone devices and compared against Fairness and SLSQP baselines [S1].
