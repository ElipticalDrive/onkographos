# DP Algorithm (Configuration Selection)
Also called: Dynamic Programming
## Overview
The DP Algorithm (Configuration Selection) is a method for finding optimal configuration pairs for segmented objects within a multi-NeRF framework, subject to a strict total memory budget constraint [S1]. It solves the resource allocation problem by intelligently redistributing memory from low-complexity objects to high-complexity ones, thereby maximizing overall rendering quality [S1]. It is compared against Fairness and SLSQP baselines [S1].
## How it works
The algorithm operates as a preprocessing step to generate a multi-modal NeRF representation [S1].

**Inputs and Outputs:**
- **Input:** A set of segmented objects, a discrete set of available configurations for each object (where each configuration has a specific memory footprint and expected rendering quality), and a global total memory budget $B_{total}$ [S1].
- **Output:** A selected configuration pair for each segmented object such that the sum of their memory footprints does not exceed $B_{total}$ and the aggregate rendering quality is maximized [S1].

**Data Structures:**
The implementation relies on a dynamic programming table to store optimal sub-solutions [G]. The table maps object indices and cumulative memory budgets to maximum achievable quality scores [G].

**Steps:**
1. **Initialization:** Define the objective function to maximize rendering quality (e.g., SSIM) subject to the memory constraint [S1].
2. **DP Solver Execution:** Apply the dynamic programming algorithm to find the optimal configuration pairs for all segmented objects [S1]. The solver evaluates combinations of configurations across objects to find the global optimum [S1].
3. **Selection:** Assign the optimal configuration to each object based on the DP table results [S1].

**Parameters:**
- **DP Solver Overhead:** The computational cost of the DP solver is approximately 1.87 seconds for 20 training images [S1].
- **Total Preprocessing Overhead:** Excluding neural network training, the total overhead for generating the multi-modal NeRF representation data is about 5.9 seconds [S1].

**Edge Cases and Pitfalls:**
- **Memory Budget Violation:** If the sum of the minimum required memory for all objects exceeds $B_{total}$, rendering failures may occur [S1].
- **Object Diversity:** Scenes with high diversity in object complexity benefit most from this method, as it reallocates resources effectively [S1].

**Pseudocode:**
```python
def dp_configuration_selection(objects, configs, total_budget):
    """
    Find optimal configuration for each object under total memory budget.
    
    Args:
        objects: List of segmented objects.
        configs: Dict mapping object_id to list of available configurations.
                 Each config is a tuple (memory_cost, quality_score).
        total_budget: Integer, total memory limit.
        
    Returns:
        selected_configs: Dict mapping object_id to selected config index.
    """
    num_objects = len(objects)
    # dp[i][b] stores the maximum quality achievable using the first i objects with budget b [G]
    dp = [[-float('inf')] * (total_budget + 1) for _ in range(num_objects + 1)]
    dp[0][0] = 0.0
    
    # Fill DP table
    for i in range(1, num_objects + 1):
        obj_id = objects[i-1]
        obj_configs = configs[obj_id]
        for b in range(total_budget + 1):
            # Carry over previous best if no config fits or for initialization
            dp[i][b] = dp[i-1][b]
            # Try each configuration for the current object
            for config_idx, (mem_cost, qual_score) in enumerate(obj_configs):
                if b >= mem_cost and dp[i-1][b - mem_cost] > -float('inf'):
                    new_quality = dp[i-1][b - mem_cost] + qual_score
                    if new_quality > dp[i][b]:
                        dp[i][b] = new_quality
                        # Not given in the sources: Explicit backtracking pointer storage; 
                        # reconstruction is performed by re-evaluating the DP table [G]
    
    # Backtrack to find selected configurations
    selected_configs = {}
    current_budget = total_budget
    for i in range(num_objects, 0, -1):
        obj_id = objects[i-1]
        obj_configs = configs[obj_id]
        chosen_config_idx = -1
        for config_idx, (mem_cost, qual_score) in enumerate(obj_configs):
            if current_budget >= mem_cost and dp[i-1][current_budget - mem_cost] > -float('inf'):
                if abs(dp[i][current_budget] - (dp[i-1][current_budget - mem_cost] + qual_score)) < 1e-6:
                    chosen_config_idx = config_idx
                    current_budget -= mem_cost
                    break
        selected_configs[obj_id] = chosen_config_idx
        
    return selected_configs
```
## Subtopics

### Fairness (Configuration Selection)
A baseline configuration selection strategy that distributes the total memory budget equally among all segmented objects [S1]. It divides the total size limit equally across all segmented objects and then uses performance profilers to select the optimal configuration pair for each object within its fixed memory budget [S1]. It serves as a comparison point for the DP algorithm, particularly in scenes with high object diversity where it underperforms [S1].

## Operating characteristics
- **Time Complexity:** The DP solver overhead is 1.87 seconds for 20 training images, accounting for 31% of the total 5.9-second preprocessing overhead [S1].
- **Memory Complexity:** Not given in the sources.
- **Performance:** On mobile devices (iPhone), the DP method achieves nearly 0.92 SSIM for random scenes, compared to ~0.91 for baselines [S1]. For Scene 4 (high object diversity), it attains 0.94 SSIM on both tested devices, while other methods struggle to reach this level [S1].
- **Strengths:** Outperforms Fairness and SLSQP on scenes with high object diversity by intelligently reallocating resources from low-complexity objects to high-complexity ones (e.g., allocating +14MB to Lego and +27MB to ship) [S1].
- **Limitations:** Requires preprocessing overhead; not suitable for dynamic scenes requiring real-time reconfiguration without caching [G].
- **When to use:** When rendering complex multi-object scenes on resource-constrained devices (e.g., mobile) where memory budget is strict and object complexity varies significantly [S1].
## Background
The algorithm was proposed in the NeRFlex framework, a NeRF-based rendering system designed for complex multi-object scenes on mobile devices [S1]. It addresses the challenges of low rendering quality and high resource demands by employing a multi-NeRF framework [S1]. The method was introduced in 2025 [S1].
