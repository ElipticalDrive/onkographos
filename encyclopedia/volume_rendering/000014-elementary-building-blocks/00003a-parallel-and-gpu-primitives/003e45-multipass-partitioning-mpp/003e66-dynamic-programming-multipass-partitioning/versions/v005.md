# Dynamic Programming Multipass Partitioning

## Overview
Dynamic Programming Multipass Partitioning (DPMPP) is a method for solving the resource-constrained GPU shader execution problem by partitioning a shader program's dependency graph (DAG) into multiple passes [S1, unofficial]. It determines a globally optimal schedule of passes that minimizes total runtime while respecting hardware resource limits and precedence constraints [S1, unofficial]. Unlike greedy approximations such as the MIO algorithm, which yields locally optimal but potentially suboptimal global solutions [S1, unofficial], DPMPP guarantees optimality by observing the principle of optimality [S1, unofficial]. It builds on the general Multipass Partitioning (MPP) framework [9704-multipass-partitioning-mpp.md] [S1, unofficial].

## How it works
**Inputs:** A DAG representing the computation or shader program's dependency graph, where nodes are operations and edges are data dependencies [S1, unofficial]. A set of available hardware configurations defining resource constraints such as memory or register limits [S1, unofficial].

**Outputs:** A sequence of passes (partitions) assigning each operation to a specific pass index, such that no pass exceeds resource constraints and all dependencies are respected, minimizing the total cost (runtime) [S1, unofficial].

**Data Structures:**
The algorithm operates on a set of transitions $T$ [S1, unofficial]. Each transition $t$ is a tuple with four fields [S1, unofficial]:
1. $t.\text{precondition}$: The machine state before the operation.
2. $t.\text{postcondition}$: The machine state after the operation, defined as the state resulting from applying $t.\text{operation}$ to $t.\text{precondition}$ [S1, unofficial].
3. $t.\text{operation}$: The specific shader operation or node from the DAG.
4. $t.\text{cost}$: The computational cost (e.g., time) associated with the operation.

**Algorithm Steps:**
The algorithm proceeds backwards from the last stage to the first stage [S1, unofficial].

1. **Initialization:** For the final stage, initialize the set of transitions $T_{\text{final}}$ with all possible terminal states of the computation [S1, unofficial].
2. **Backward Iteration:** For each stage $i$ from $N-1$ down to $0$:
   a. Initialize the set of candidate transitions $T_i$ for the current stage [S1, unofficial].
   b. For each transition $t \in T_i$, evaluate its validity against resource constraints [S1, unofficial].
   c. Apply the **principle of optimal substructure**: Determine which transitions in $T_i$ can lead to an optimal solution for the subsequent (earlier) stage $i-1$ [S1, unofficial].
   d. The determined optimal transitions from stage $i$ become the input (preconditions) for the transitions in stage $i-1$ [S1, unofficial].
3. **Termination:** When the first stage is reached, the remaining transition(s) in $T_0$ constitute the globally optimal schedule [S1, unofficial].

**Pseudocode:**
```python
def DPMPP(stages, resource_limits):
    # stages: list of lists of operations, ordered from first to last stage
    # resource_limits: dict with keys 'memory' and 'registers'
    num_stages = len(stages)
    T = [set() for _ in range(num_stages)]

    # Base case: Last stage
    # Initialize T with transitions representing valid terminal states [G]
    initial_machine_state = {'memory': 0, 'registers': 0}
    for op in stages[-1]:
        post_state = op.apply(initial_machine_state)
        if post_state['memory'] <= resource_limits['memory'] and post_state['registers'] <= resource_limits['registers']:
            T[-1].add({
                'precondition': initial_machine_state,
                'postcondition': post_state,
                'operation': op,
                'cost': op.cost
            })

    # Backward iteration from second-to-last stage to first
    for k in range(num_stages - 2, -1, -1):
        current_ops = stages[k]
        next_stage_transitions = T[k + 1]

        for op in current_ops:
            for next_t in next_stage_transitions:
                # Check if op can precede the operation in the next stage transition
                if op.has_edge_to(next_t['operation']):
                    # Compute postcondition for current operation
                    current_post = op.apply(next_t['precondition'])
                    current_cost = op.cost + next_t['cost']
                    if current_post['memory'] <= resource_limits['memory'] and current_post['registers'] <= resource_limits['registers']:
                        T[k].add({
                            'precondition': next_t['precondition'],
                            'postcondition': current_post,
                            'operation': op,
                            'cost': current_cost
                        })

    return T[0]
```

**Parameters:**
- **Resource Constraints:** Memory, register file size, or shared memory limits per pass [S1, unofficial].
- **Cost Function:** Typically total runtime or compute time [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Intractability:** The theoretical time complexity is intractable for large graphs [S1, unofficial].
- **Precision:** Not given in the sources.
- **Boundaries:** The algorithm assumes a well-defined DAG with clear stages [S1, unofficial].

## Subtopics

### [DP Algorithm (Configuration Selection)](15956-dp-algorithm-configuration-selection.md)
A method for determining the globally optimal set of rendering configurations for segmented objects within a multi-NeRF framework, subject to a strict total memory budget constraint. It solves the resource allocation problem by intelligently redistributing memory from low-complexity objects to high-complexity ones, thereby maximizing overall rendering quality. Unlike baseline strategies that distribute resources equally or rely on gradient approximation, this method guarantees a globally optimal solution for the discrete configuration selection problem.

### Brick grouping DP
A dynamic programming solution to the Load-Balanced Network Distribution (LBND) problem [S1, unofficial]. It starts with a directed acyclic graph (DAG) of segmented and cropped bricks, based on the MPP solution by Heirich [S1, unofficial]. It outputs a render-node assignment that minimizes total runtime cost, respects physical resource constraints, and observes precedence order for image composition [S1, unofficial]. The depth of the search tree is limited to prevent intractability, which limits the size of data bricks relative to the whole dataset [S1, unofficial]. The partition is optimized with respect to a single viewpoint [S1, unofficial]. Inputs include the scene with volumetric data and distributed system configuration (number of render-nodes, rendering/local composition costs, network transfer costs, memory capacity) [S1, unofficial].

### Moving walls DP
A dynamic programming solution to a relaxed version of the LBND problem [S1, unofficial]. It applies dynamic programming to slab-projection slices [S1, unofficial]. The output is a flex-block partition, which is a view-independent partition of cells containing a combination of empty space and cropped subvolumes [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Theoretically intractable, but experimentally achieves an average time complexity of $O(n^{1.14966})$ [S1, unofficial].
- **Memory Complexity:** Not given in the sources.
- **Measured Performance:** Achieves globally optimal solutions, outperforming greedy algorithms like MIO which have $O(n \log n)$ complexity but may be suboptimal globally [S1, unofficial].
- **Strengths:** Guarantees global optimality; respects resource constraints and precedence.
- **Limitations:** Theoretical intractability; limited search tree depth in variants like Brick grouping DP restricts brick size [S1, unofficial].
- **When to use:** When global optimality is critical and the problem size is manageable or can be segmented (e.g., distributed volume visualization) [S1, unofficial].
- **When not:** When the input cannot be segmented into a DAG of bricks or when multi-viewpoint optimization is required [S1, unofficial].

## Background
DPMPP was introduced as a dynamic programming solution to the Multipass Partitioning (MPP) problem [S1, unofficial]. MPP arises when a computation targeted for the GPU exceeds resource constraints, requiring division into multiple passes to minimize total compute time [S1, unofficial]. The MPP problem was introduced by Heirich [S1, unofficial]. DPMPP is applied in the context of distributed volume visualization and ray tracing, specifically for load-balanced network distribution (LBND) of volumetric data [S1, unofficial]. It is used to optimize rendering schedules on clusters, considering network transfer costs and node memory capacities [S1, unofficial].
