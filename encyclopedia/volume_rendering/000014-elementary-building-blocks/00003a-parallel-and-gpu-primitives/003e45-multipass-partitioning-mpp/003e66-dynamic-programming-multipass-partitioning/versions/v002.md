# Dynamic Programming Multipass Partitioning

## Overview
Dynamic Programming Multipass Partitioning (DPMPP) is a dynamic programming solution to the Multipass Partitioning (MPP) problem that determines a globally optimal schedule by observing the principle of optimality [S1, unofficial]. MPP arises when a computation targeted for the GPU exceeds resource constraints, requiring the computation to be divided into multiple passes that do not violate those constraints to minimize total compute time [S1, unofficial]. DPMPP differs from greedy alternatives like the MIO algorithm, which provides an approximate locally optimal solution with average time $O(n \log n)$ but may be suboptimal globally [S1, unofficial].

## How it works
**Inputs:** A dependency graph (DAG) of operations, hardware resource constraints, and operation costs [S1, unofficial].
**Outputs:** A partitioned schedule of multiple passes that minimizes total runtime while respecting precedence and resource limits [S1, unofficial].

**Data Structures:**
The algorithm operates on a set of transitions $T$. Each transition $t$ is a structure with four fields:
1. `t.precondition`: The machine state before the operation.
2. `t.postcondition`: The machine state in `t.precondition` following the application of `t.operation` [S1, unofficial].
3. `t.operation`: The specific operation or group of operations.
4. `t.cost`: The computational cost of the operation [S1, unofficial].

**Algorithm Steps:**
1. **Initialization:** Initialize the set $T$ of transitions for the last stage of the dependency graph [S1, unofficial].
2. **Backward Iteration:** Proceed backwards from the last stage to the first stage [S1, unofficial].
3. **Optimal Substructure Evaluation:** For each stage, use the principle of optimal substructure to determine which transitions in $T$ may be optimal [S1, unofficial].
4. **Pruning and Propagation:** Filter $T$ to keep only the determined optimal transitions and use this pruned set as the input for the next subsequent (earlier) stage [S1, unofficial].
5. **Termination:** When the first stage is reached, the remaining transition(s) in $T$ constitute the globally optimal schedule [S1, unofficial].

**Pseudocode:**
```python
def DPMPP(stages):
    # stages: list of stages, where each stage is a list of operation objects
    # Each operation object has .cost and .apply(pre_state) -> post_state
    # Proceed backwards from the last stage to the first
    # Initialize T with transitions from the last stage
    T = {}
    for op in stages[-1]:
        pre_state = 0  # Canonical initial state for the final stage [G]
        post_state = op.apply(pre_state)
        T[post_state] = {
            'precondition': pre_state,
            'postcondition': post_state,
            'operation': op,
            'cost': op.cost
        }

    # Backward iteration through remaining stages
    for stage_idx in range(len(stages) - 2, -1, -1):
        current_stage = stages[stage_idx]
        next_stage_T = T
        new_T = {}

        for op in current_stage:
            for prev_state, prev_trans in next_stage_T.items():
                # Derive predecessor state for current operation [G]
                pre_state = prev_state
                post_state = op.apply(pre_state)
                total_cost = op.cost + prev_trans['cost']

                # Principle of optimal substructure: filter to keep only optimal transitions
                # Keep the transition with the minimum cost for each resulting state
                if post_state not in new_T or total_cost < new_T[post_state]['cost']:
                    new_T[post_state] = {
                        'precondition': pre_state,
                        'postcondition': post_state,
                        'operation': op,
                        'cost': total_cost
                    }
        T = new_T

    # Termination: remaining transition(s) in T constitute the globally optimal schedule
    return T
```

**Parameters:**
*   **Stage Count:** Determined by the depth of the dependency graph. Not given in the sources.
*   **Resource Constraints:** Memory and compute limits per pass. Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Intractability:** The theoretical time complexity can be intractable for large graphs [S1, unofficial].
*   **Precision:** Floating-point precision in cost accumulation may affect optimality if costs are very small or very large. Not given in the sources.

## Subtopics

### Brick grouping DP
A dynamic programming solution to the Load-Balanced Network Distribution (LBND) problem that starts with a directed acyclic graph of segmented and cropped bricks [S1, unofficial]. It is based on the DPMPP algorithm introduced by Heirich [S1, unofficial]. It attempts to minimize a cost function that reflects the end-to-end rendering cost on a cluster without violating image composition priority constraints [S1, unofficial]. The output is a render-node assignment that minimizes total runtime cost, does not violate physical resource constraints, and observes precedence order for image composition [S1, unofficial]. The depth of the search tree is limited to prevent the recursion from becoming intractable, which limits the size of the data bricks with respect to the whole data set [S1, unofficial]. The partition is optimized with respect to a single viewpoint [S1, unofficial]. Inputs include a scene with volumetric data and a distributed system configuration (number of render-nodes, rendering and local composition costs, network transfer costs, memory capacity of each render-node) [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Theoretically intractable in the worst case, but experimentally achieves an average time complexity of $O(n^{1.14966})$ [S1, unofficial].
*   **Memory Complexity:** Not given in the sources.
*   **Strengths:** Provides a globally optimal schedule, unlike greedy algorithms such as MIO which are only locally optimal [S1, unofficial].
*   **Limitations:** Potential intractability for very large dependency graphs; requires careful pruning or depth limiting to remain feasible [S1, unofficial].
*   **When to Use:** When global optimality is required and the dependency graph size is manageable or can be effectively pruned. Not given in the sources.
*   **When Not to Use:** When real-time performance is critical and the graph is too large for the DP approach, or when approximate solutions are acceptable. Not given in the sources.

## Background
DPMPP was introduced by Heirich [S1, unofficial] as a solution to the Multipass Partitioning (MPP) problem, which arises when a computation targeted for the GPU exceeds resource constraints [S1, unofficial]. It is based on the principle of optimality, which states that the optimal solution for the current stage is optimal regardless of what policies or conditions led to this stage [S1, unofficial]. It has been adapted for load balancing in distributed rendering systems, such as in the Brick grouping DP algorithm for LBND [S1, unofficial].
