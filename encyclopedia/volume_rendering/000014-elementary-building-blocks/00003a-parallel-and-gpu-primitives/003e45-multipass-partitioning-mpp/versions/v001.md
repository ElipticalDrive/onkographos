# Multipass Partitioning (MPP)

Also called: DPMPP (Dynamic Programming Multipass Partitioning)

## Overview
Multipass Partitioning (MPP) is a technique for solving resource-constrained GPU shader execution by partitioning a shader program's dependency graph (Directed Acyclic Graph, DAG) into multiple passes, minimizing total runtime while respecting precedence and hardware limits [S1, unofficial]. It is distinct from sibling methods like [Tiled Parallel Compositing](1192-tiled-parallel-compositing.md) which partition spatial data, whereas MPP partitions the computational dependency graph itself. It addresses the problem where complex applications, such as texture-mapped volume rendering, exceed the resource capacity (registers, local memory) of even the most up-to-date GPU hardware [S1, unofficial].

## How it works
**Inputs:**
1. A valid shader program represented as a DAG, where nodes are operations and edges are dependencies [S1, unofficial].
2. Costs associated with each operation and the physical resource constraints of the target GPU (e.g., maximum register count, local memory size) [S1, unofficial].

**Outputs:**
A schedule of DAG operations partitioned into passes that minimizes the total runtime cost, where the schedule observes the precedence relations of the DAG, and no pass exceeds the physical resource constraints of the GPU [S1, unofficial].

**Data Structures:**
*   **DAG:** Nodes represent operations. Each node $n$ has an associated cost $c(n)$ and a set of predecessors $P(n)$ and successors $S(n)$.
*   **Transition:** A transition $t$ consists of:
    *   $t.precondition$: The machine state before applying the operation.
    *   $t.postcondition$: The machine state after applying the operation.
    *   $t.operation$: The specific GPU operation.
    *   $t.cost$: The computational or resource cost of the operation.
*   **State Set $T$:** A set of transitions for a given stage.

**Algorithm (Dynamic Programming Approach - DPMPP):**
The Dynamic Programming Multipass Partitioning (DPMPP) solution proceeds backwards from the last stage to the first [S1, unofficial].

1.  **Initialization:** For the final stage, initialize the set of transitions $T$ with all possible terminal operations.
2.  **Backward Induction:** For each stage $k$ from $N-1$ down to $0$:
    a.  Identify all valid transitions $t$ that can lead to the states in $T$ from stage $k+1$.
    b.  For each transition $t$, determine $t.precondition$ and $t.postcondition$. Note that $t.postcondition$ is the machine state in $t.precondition$ following the application of $t.operation$.
    c.  Apply the **principle of optimal substructure**: Determine which transitions $u$ at stage $k$ are optimal. A transition is optimal if it leads to a state in $T$ with the minimum cumulative cost, while satisfying the resource constraints for the current pass.
    d.  Update $T$ to contain only the optimal transitions for stage $k$.
3.  **Schedule Construction:** Trace forward from the initial state using the stored optimal transitions to construct the final partition schedule.

**Parameters:**
*   $n$: Number of nodes in the DAG.
*   Resource Limits: Defined by the target GPU architecture (e.g., 255 registers per thread for older architectures, variable for newer) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Multiply-Referenced Nodes:** Algorithms like Recursive Dominator Split (RDS) and MIO allow multiply-referenced nodes to be either recomputed or saved. The choice impacts the total cost and must be evaluated during partitioning [S1, unofficial].
*   **Connected Regions:** RDS considers only a single connected region of the input DAG at any time, which may limit global optimization [S1, unofficial].
*   **Precision:** Not given in the sources.

## Subtopics

### [Dynamic Programming Multipass Partitioning](9735-dynamic-programming-multipass-partitioning.md)
A dynamic programming solution to the MPP problem that determines a globally optimal schedule by observing the principle of optimality. It is chosen when global optimality is required despite higher computational complexity.

## Operating characteristics
*   **Time Complexity:** Depends on the specific algorithm used.
    *   **RDS (Recursive Dominator Split):** $O(n^3)$ [S1, unofficial].
    *   **RDS*h* (Heuristic RDS):** $O(n^2)$ [S1, unofficial].
    *   **MIO (Greedy List Scheduling):** Average $O(n \log n)$ [S1, unofficial].
    *   **DPMPP (Dynamic Programming):** Complexity is not explicitly given in the sources, but generally exponential in the worst case for general DAGs, though optimized by the DP structure and resource constraints [S1, unofficial].
*   **Memory Complexity:** Not given in the sources.
*   **Strengths:** Can handle complex dependency graphs; minimizes total runtime cost; respects hardware constraints.
*   **Limitations:** RDS is slow ($O(n^3)$); MIO may be suboptimal globally; DPMPP may have high memory/time overhead for large DAGs.
*   **When to use:** When shader programs exceed GPU resource limits and the dependency graph is complex.
*   **When not to use:** When real-time performance is critical and approximate solutions (MIO) are insufficient, but exact solutions (DPMPP/RDS) are too slow.

## Background
The concept of Multipass Partitioning was introduced to address the limitations of GPU hardware in handling complex applications like texture-mapped volume rendering [S1, unofficial]. Key algorithms include:
*   **RDS:** Introduced by Chan et al. [14], uses a minimum-cut approach to minimize the total number of passes [S1, unofficial].
*   **MIO:** Introduced by Riffel et al. [100], treats MPP as a job-shop scheduling problem using a greedy list-scheduling algorithm [S1, unofficial].
*   **DPMPP:** Described in the context of brick grouping for load balancing in distributed volume visualization [S1, unofficial].
