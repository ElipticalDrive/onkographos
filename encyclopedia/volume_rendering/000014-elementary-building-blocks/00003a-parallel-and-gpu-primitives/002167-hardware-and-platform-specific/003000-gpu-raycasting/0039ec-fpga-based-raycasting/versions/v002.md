# FPGA-based Raycasting
Also called: Raycasting Hardware (UVIZARD)

## Overview
FPGA-based raycasting refers to specialized hardware architectures, specifically the UVIZARD and VIZARD II systems developed at the University of Tübingen, designed to accelerate perspective volume raycasting on custom PCI boards [S1, unofficial][S2, book]. Unlike later general-purpose GPU solutions, these systems require long pre-processing times to configure the hardware [S1, unofficial]. The architecture is distinguished by its implementation of early ray-termination and a table-based gradient vector lookup scheme on field-programmable gate arrays (FPGAs) [S2, book].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D volume dataset (e.g., $256^3$ voxels), camera parameters for perspective view, and transfer function parameters [S1, unofficial][S2, book].
*   **Output:** A 2D rendered image [S2, book].

**Data Structures:**
*   **Volume Data:** Stored in off-chip SDRAM/SRAM memory [S2, book].
*   **Gradient Lookup Table:** A pre-computed table mapping sample values to gradient vectors, used to avoid on-the-fly finite difference calculations [S2, book].

**Numbered Steps:**
1.  **Pre-processing:** Configure the FPGAs and load necessary lookup tables, requiring significant setup time before rendering begins [S1, unofficial].
2.  **Ray Generation:** Cast rays for each pixel based on perspective camera parameters [S2, book].
3.  **Sampling and Gradient Lookup:** Traverse the volume, retrieving gradients from the pre-computed table at sample positions [S2, book].
4.  **Early Ray Termination:** Halt ray traversal when accumulated opacity exceeds a threshold to save computation [S2, book].
5.  **Image Output:** Write the final accumulated color to the frame buffer [S2, book].

**Formulas:**
The rendering equation is approximated by discrete front-to-back compositing [G]:
$$ C = \sum_{i=0}^{N-1} c_i \alpha_i \prod_{j=0}^{i-1} (1 - \alpha_j) $$
Where $c_i$ is sample color, $\alpha_i$ is sample opacity, and $N$ is the number of samples. The sources note that pre-integration can be used to tabulate the integral of the transfer function, but UVIZARD specifically emphasizes the gradient lookup for shading [S1, unofficial][S2, book].

**Parameters:**
*   **Volume Size:** Tested on $256^3$ datasets [S1, unofficial][S2, book].
*   **Hardware:** PCI board with four FPGAs, a DSP, and SDRAM/SRAM [S2, book].

**Edge Cases and Pitfalls:**
*   **Pre-processing Latency:** The system requires long pre-processing times, making it less suitable for dynamic scenes requiring rapid reconfiguration [S1, unofficial].
*   **Precision:** Fixed-point arithmetic is implied by the hardware nature, but specific bit-widths are not given in the sources [S2, book].

**Pseudocode:**
```python
def fpga_ray_cast(volume_data, volume_dims, ray_origin, ray_direction, step_size, gradient_table, transfer_func, max_opacity):
    # volume_data: 3D list of voxel values
    # volume_dims: tuple (Dx, Dy, Dz)
    # ray_origin, ray_direction: 3D tuples/lists
    # step_size: physical step length along ray
    # gradient_table: dict mapping sample value -> gradient tuple
    # transfer_func: function(value, gradient) -> (color, opacity)
    # max_opacity: threshold for early termination

    # Compute ray length to exit volume (handles negative direction and zero components)
    t_min, t_max = 0.0, float('inf')
    for i in range(3):
        if abs(ray_direction[i]) > 1e-9:
            t1 = (0.0 - ray_origin[i]) / ray_direction[i]
            t2 = (volume_dims[i] - 1.0 - ray_origin[i]) / ray_direction[i]
            t_enter = min(t1, t2)
            t_exit = max(t1, t2)
            t_min = max(t_min, t_enter)
            t_max = min(t_max, t_exit)
        else:
            if ray_origin[i] < 0.0 or ray_origin[i] >= volume_dims[i]:
                return [0.0, 0.0, 0.0]

    if t_min > t_max:
        return [0.0, 0.0, 0.0]

    accumulated_color = [0.0, 0.0, 0.0]
    accumulated_opacity = 0.0
    t = t_min

    while t < t_max and accumulated_opacity < max_opacity:
        x = ray_origin[0] + ray_direction[0] * t
        y = ray_origin[1] + ray_direction[1] * t
        z = ray_origin[2] + ray_direction[2] * t

        ix, iy, iz = int(x), int(y), int(z)
        if not (0 <= ix < volume_dims[0] and 0 <= iy < volume_dims[1] and 0 <= iz < volume_dims[2]):
            break

        sample_value = volume_data[ix][iy][iz]
        gradient = gradient_table.get(sample_value, (0.0, 0.0, 0.0))
        color, opacity = transfer_func(sample_value, gradient)

        weight = opacity * (1.0 - accumulated_opacity)
        accumulated_color[0] += color[0] * weight
        accumulated_color[1] += color[1] * weight
        accumulated_color[2] += color[2] * weight
        accumulated_opacity += weight

        t += step_size

    return accumulated_color
```

## Subtopics

### GPU Ray Casting with Fast Intersection
A software-based sibling that accelerates ray-triangle intersections on GPUs using optimized bounding volume hierarchies and parallel reduction, chosen when dynamic geometry requires programmable flexibility over fixed-function speed [7032-gpu-ray-casting-with-fast-intersection.md].

### GPU-based Ray Casting
A general-purpose sibling leveraging CUDA/OpenCL pipelines for volume rendering, chosen when hardware portability and developer productivity outweigh the raw throughput of custom ASIC/FPGA designs [7131-gpu-based-ray-casting.md].

### GPU Ray Casting with Depth Peeling and Tile-Based Subdivision
A sibling that combines depth peeling for correct transparency sorting with tile-based subdivision to reduce overdraw, chosen for complex multi-layered scenes where order-independent transparency is critical [7813-gpu-ray-casting-with-depth-peeling-and-tile-based-subdivisio.md].

### Recursive Ray-casting for Global Illumination
A sibling that extends basic raycasting to compute indirect lighting and reflections via recursive ray spawning, chosen when physically accurate global illumination is required at the cost of exponential sample counts [8544-recursive-ray-casting-for-global-illumination.md].

### Single Scattering Illumination
A sibling that approximates light transport using only the first scattering event, chosen for real-time performance in participating media where multiple scattering effects are negligible [9628-single-scattering-illumination.md].

### Distributed Volume Raycasting with Bricks
A sibling that partitions large volumes into spatial bricks for networked or multi-GPU rendering, chosen when dataset size exceeds single-node memory bandwidth or capacity [9869-distributed-volume-raycasting-with-bricks.md].

## Operating characteristics
*   **Performance:** The UVIZARD system achieved 10 Hz for a $256^3$ volume with perspective view [S1, unofficial]. The VIZARD II was anticipated to render $256^3$ datasets at interactive framerates [S2, book].
*   **Memory:** Relies on off-chip SDRAM/SRAM for volume storage [S2, book].
*   **Strengths:** Supports perspective rendering and early ray termination, features not present in earlier brute-force hardware like VolumePRO [S2, book].
*   **Limitations:** Requires long pre-processing times, reducing flexibility for rapidly changing data [S1, unofficial].

## Background
The UVIZARD and VIZARD II systems were developed at the University of Tübingen in 1997 [S1, unofficial][S2, book]. They represent an early implementation of reconfigurable hardware for volume rendering [G].
