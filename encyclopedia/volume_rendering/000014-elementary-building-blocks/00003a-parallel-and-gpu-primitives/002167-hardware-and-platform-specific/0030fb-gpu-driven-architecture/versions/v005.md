# GPU-Driven Architecture

Also called: GPU-Driven Rendering

## Overview
GPU-Driven Architecture is a rendering paradigm where the residency octree and the mixed-resolution multi-volume renderer are fully implemented on the GPU, while the CPU handles only high-level orchestration [S1, unofficial]. It minimizes CPU-to-GPU data transfer bottlenecks by keeping buffer copies small and limiting cache misses per frame [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** High-level rendering commands from the CPU, brick data streamed from a server, and the current camera/view state [G].
*   **Output:** The final rendered image frame [G].

**Data Structures:**
*   **Residency Octree:** Stored entirely in GPU memory [S1, unofficial]. Exact layout, fields, sizes, and bit packing are not given in the sources [S1, unofficial].
*   **Brick Cache:** A GPU-side buffer holding active volume bricks [G]. Exact layout, fields, sizes, and bit packing are not given in the sources [G].

**Numbered Steps:**
1.  **CPU Orchestration:** The CPU initializes the rendering context and dispatches rendering and memory management commands to the GPU [S1, unofficial].
2.  **Ray-Guided Traversal:** The GPU executes the renderer; during ray traversal through the residency octree, if a node is missing from the GPU cache, it generates a request for the missing data to be streamed in from the server [S1, unofficial]. This makes the method ray-guided [S1, unofficial].
3.  **CPU Request Handling:** The CPU receives brick requests generated by the GPU traversal and forwards them to the server [S1, unofficial].
4.  **Data Upload:** The CPU uploads the bricks received from the server to the GPU [S1, unofficial].
5.  **Rendering:** The GPU continues rendering using the newly uploaded bricks [S1, unofficial].

**Parameters:**
*   **Global Cache Miss Limit:** A global limit on the number of recorded cache misses per frame is specified to keep buffer copies from the GPU to the CPU small [S1, unofficial]. Typical values are not given in the sources [S1, unofficial].

**Edge Cases and Pitfalls:**
*   Precision and boundary conditions are not detailed in the sources [S1, unofficial].
*   Excessive cache misses can cause performance degradation due to increased CPU-GPU communication [S1, unofficial].

**Pseudocode:**
```python
def cpu_orchestrate():
    while rendering_active:
        # 1. CPU dispatches rendering and memory management commands to GPU
        gpu.execute_commands()
        # 2. CPU forwards brick requests to server and uploads received bricks
        requests = gpu.collect_brick_requests()
        for req in requests:
            data = fetch_from_server(req)  # Not detailed in sources
            gpu.upload(data)

def gpu_renderer():
    for ray in rays:
        # 3. Ray-guided traversal through residency octree
        node = traverse_octree(ray)  # Not detailed in sources
        if node is None:
            # 4. Missing node generates a request for missing data streamed from server
            gpu.submit_brick_request(node_id)  # Not detailed in sources
        else:
```

## Subtopics

### [CUDA Raymarching Pipeline](6713-cuda-raymarching-pipeline.md)
The CUDA Raymarching Pipeline is a rendering architecture where the majority of processing, including computational kernels and rendering contexts, resides on the GPU device. This design eliminates data transfer and API call bottlenecks between the host CPU and the device GPU, which are common in traditional raster engines where the host controls data assembly via draw calls. It builds on [GPU-Driven Architecture](6408-gpu-driven-architecture.md) by fully implementing the residency octree and renderer on the GPU, while the CPU handles only high-level orchestration such as loading data and switching contexts.

### [Custom GPU Architecture for Sphere Tracing](7147-custom-gpu-architecture-for-sphere-tracing.md)
A GPU architecture designed for Sphere Tracing that uses independent cores rather than multi-ALU SIMD with lockstepping, handling threading natively via a storage manager. It differs from sibling architectures like the CUDA Raymarching Pipeline by replacing warp-based scheduling with a global double-ended queue managed by a storage manager, allowing arbitrary thread spawning and termination.

## Operating characteristics
*   **Time Complexity:** Not given in the sources [S1, unofficial].
*   **Memory Complexity:** Not given in the sources [S1, unofficial].
*   **Performance:** Minimizes CPU-to-GPU data transfer bottlenecks by limiting cache misses per frame [S1, unofficial].
*   **Strengths:** Reduced CPU overhead and efficient handling of large datasets via ray-guided streaming [G].
*   **Limitations:** Requires careful management of cache misses to avoid excessive CPU-GPU communication [S1, unofficial].
*   **When to use:** Suitable for large-scale volume rendering where data cannot fit entirely in GPU memory and streaming is necessary [G].
*   **When not to use:** Not suitable for small datasets where the overhead of orchestration outweighs the benefits [G].

## Background
The GPU-Driven Architecture is part of a multi-channel page-table hierarchy system for volume rendering [S1, unofficial]. It moves rendering logic entirely to the GPU to improve performance and scalability [S1, unofficial].
