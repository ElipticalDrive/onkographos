# Multi-core BONO Tree Traversal and Ray Casting with Dynamic Tile Grouping

Also called: Phase I/Phase II Multi-core Scheme, Z-ordered Dynamic Tile Allocation

## Overview
This method is a multi-core parallel rendering technique for isosurface visualization that decouples data structure traversal from ray casting to optimize cache performance and load balancing. It solves the problem of uneven computational load and poor spatial locality in parallel volume rendering by dividing the screen into contiguous regions for initial block list generation (Phase I) and then dynamically assigning Z-ordered, weight-balanced groups of image tiles to threads for ray casting (Phase II/III). It differs from standard static tiling approaches by using a space-filling curve (Z-order) to group tiles based on their estimated complexity (weight), ensuring that threads with heavier workloads are processed in spatially coherent batches, thereby reducing synchronization overhead and improving cache hit rates [S1, unofficial].

## How it works
The method operates in three distinct phases: Phase I (Block List Generation), Phase II (Tile Grouping), and Phase III (Dynamic Ray Casting).

### Inputs and Outputs
**Inputs:**
*   $p$: Number of available processor cores/threads.
*   $k$: Maximum size of the block list for a pixel group (memory limit).
*   $T$: The BONO tree data structure representing the volume.
*   $R$: The set of rays corresponding to the screen pixels.
*   $S$: Screen resolution (e.g., $1024 \times 1024$).
*   $TileSize$: Dimensions of small image tiles (e.g., $8 \times 8$ or $16 \times 16$).

**Outputs:**
*   Rendered image.
*   List $LI$: A sequence of groups, where each group is a pair of indices $(first, last)$ defining a contiguous range of Z-ordered tiles.

### Data Structures
1.  **Block List ($L_i$):** For each pixel (or small group of pixels), a list of 3D data blocks from the BONO tree that the ray intersects.
    *   Constraint: $|L_i| \le k$.
2.  **Tile Grid:** The screen is partitioned into $N$ tiles of size $TileSize \times TileSize$.
3.  **Z-Order Map:** An array mapping tile index $i$ to its Z-order position.
4.  **Weight Array ($W_{tile}$):** An integer array where $W_{tile}[j]$ is the number of non-empty block lists within tile $j$.
5.  **Group List ($LI$):** A list of tuples $((first\_tile\_idx, last\_tile\_idx), group\_id)$.

### Numbered Steps

#### Phase I: Block List Generation
1.  Divide the screen into $p$ almost equal contiguous horizontal (or vertical) regions, one per thread.
2.  For each thread $t$ responsible for region $R_t$:
    a.  Initialize empty block lists for all pixels in $R_t$.
    b.  Traverse the BONO tree $T$.
    c.  **Traversal Rule:** For a node $N$, traverse its children in front-to-back order **only if**:
        i.  The projection of $N$'s minimum bounding box intersects $R_t$.
        ii. At least one pixel in $R_t$ has a block list size $< k$.
    d.  If the node is a leaf (data block), add the block to the lists of all intersecting pixels in $R_t$, provided the list size $< k$.
    e.  **Note:** Due to the limit $k$, only a fraction (no more than 10%) of total BONO tree nodes are accessed [S1, unofficial].

#### Phase II: Dynamic Tile Grouping
1.  **Partitioning:** Partition the entire screen into small tiles of size $TileSize \times TileSize$.
2.  **Z-Ordering:** Order these tiles using a Z-order (Morton code) space-filling curve. This ensures spatial locality [S1, unofficial].
3.  **Weighting:**
    a.  For each tile $j$, compute weight $w_j = \sum_{p \in Tile_j} (1 \text{ if } L_p \neq \emptyset \text{ else } 0)$.
    b.  Compute total weight $W = \sum_{all \ tiles} w_j$.
4.  **Grouping Algorithm:**
    a.  Initialize an empty list $LI$.
    b.  Let $remaining\_weight = W$.
    c.  Let $current\_tile\_index = 0$ (in Z-order).
    d.  While $remaining\_weight > 0$:
        i.  Target weight for this iteration: $Target = remaining\_weight / 2$.
        ii. Divide $Target$ into $p$ equal sub-targets: $SubTarget = Target / p$.
        iii. For each group $g$ from $0$ to $p-1$:
            1.  Start with $start\_tile = current\_tile\_index$.
            2.  Accumulate weights from Z-ordered tiles starting at $start\_tile$ until the sum reaches or exceeds $SubTarget$.
            3.  Let $end\_tile$ be the index of the last tile included.
            4.  Append $(start\_tile, end\_tile)$ to $LI$.
            5.  Update $current\_tile\_index = end\_tile + 1$.
        iv. Update $remaining\_weight = remaining\_weight / 2$.
    e.  **Termination:** The process repeats logarithmically relative to screen size. The first iterations create large groups (coarse-grained), and subsequent iterations create smaller groups (fine-grained) [S1, unofficial].

#### Phase III: Dynamic Ray Casting
1.  Initialize a shared queue/pointer to the list $LI$.
2.  For each thread $t$:
    a.  **Loop:**
        i.  Atomically fetch the next available group $(first, last)$ from $LI$. If none remain, terminate.
        ii. For each tile index $j$ from $first$ to $last$:
            1.  For each pixel $p$ in tile $j$:
                1.  Retrieve block list $L_p$.
                2.  If $L_p$ is empty, skip.
                3.  Shoot ray through blocks in $L_p$ (front-to-back).
                4.  **Shading:**
                    *   If ray intersects isosurface:
                        *   Calculate intersection position by solving the trilinear interpolation equation [S1, unofficial].
                        *   Compute normal using forward difference gradient.
                        *   Apply diffuse shade model.
                    *   Else if ray exits volume without intersection:
                        *   Mark pixel as background.
        iii. If any pixels in the processed tiles have block lists of size $k$ but no intersection was found (unfinished pixels), handle them in a separate pass (Step iv of the source description) [S1, unofficial].

                current_idx += 1
            
            end_idx = current_idx - 1

                    group = li_queue.pop(0)
            
            if group is None:
                break
            
            start_idx, end_idx = group
            
            for idx in range(start_idx, end_idx + 1):
                tile = z_ordered_tiles[idx]
                tx, ty = tile
                
                for dy in range(tile_size):
                    for dx in range(tile_size):
                        px, py = tx + dx, ty + dy
                        if (px, py) not in block_lists:

    for _ in range(p):

        t.start()

### Parameters
*   $p$: Number of cores/threads. Typical values tested: 1, 2, 4, 8 [S1, unofficial].
*   $k$: Upper bound on block list size. Limits memory usage and traversal depth. Exact value not specified, but it is critical for limiting BONO node access to <10% [S1, unofficial].
*   $TileSize$: Small image tile dimensions. Typical values: $8 \times 8$ or $16 \times 16$ [S1, unofficial].

### Edge Cases and Pitfalls
*   **Unfinished Pixels:** Pixels whose block lists reach size $k$ but contain no intersecting voxels must be handled separately. These pixels will not be processed in the main ray casting loop if the logic assumes intersection or empty lists. A post-processing step or specific flag is required [S1, unofficial].
*   **Precision:** Intersection position is calculated by solving a trilinear interpolation equation. Numerical stability of this solver is critical for accurate shading [S1, unofficial].
*   **Boundary Conditions:** The screen division in Phase I must handle non-divisible screen heights (e.g., $1024 / 8 = 128$, but if $p=3$, regions must be "almost equal") [S1, unofficial].

## Operating characteristics
*   **Time Complexity:**
    *   Phase I: Proportional to the number of pixels in the region and the number of BONO nodes accessed. Node access is limited to <10% of total due to $k$ [S1, unofficial].
    *   Phase II: Grouping overhead is small, approximately 2-3 milliseconds [S1, unofficial]. The grouping process requires at most a logarithmic number of iterations relative to screen size [S1, unofficial].
    *   Phase III: Proportional to the total number of pixels and the average length of block lists.
*   **Memory Complexity:**
    *   Dominated by the storage of block lists. Each pixel stores up to $k$ block references.
    *   BONO tree overhead varies by dataset (e.g., 10.53% to 25.05% of data size for tested datasets) [S1, unofficial].
*   **Measured Performance:**
    *   Hardware: Clovertown platform (2 Quad-Core Intel Xeon 5320, 1.86 GHz), 8GB RAM, 8MB L2 cache [S1, unofficial].
    *   Resolution: $1024 \times 1024$ [S1, unofficial].
    *   View Angles: Zenith $\phi \in \{15^\circ, 45^\circ, 75^\circ\}$, Azimuth $\theta \in \{22.5^\circ, 45^\circ\}$ [S1, unofficial].
    *   Scalability: Tested on 1, 2, 4, 8 cores [S1, unofficial].
*   **Strengths:**
    *   Better load balancing than static tiling due to weight-based grouping.
    *   High cache performance due to Z-order spatial locality.
    *   Minimal synchronization overhead due to coarse-to-fine grain task allocation [S1, unofficial].
*   **Limitations:**
    *   Requires preprocessing (Phase II) which adds latency.
    *   Complexity of implementation compared to simple static tiling.

## Background
The method was developed for interactive high-resolution isosurface ray tracing on multi-core processors. It was presented in a paper from the University of Maryland (UMD) [S1, unofficial]. The work addresses the limitations of standard octree ray casting with static tile allocation, which suffers from load imbalance and poor cache utilization. The BONO tree is used as the underlying data structure for efficient spatial indexing [S1, unofficial].
