# Hybrid MPI + OpenMP Parallelization
Also called: Hybrid Parallelization, MPI+OpenMP Volume Rendering, yt hybrid parallel volume rendering

## Overview
Hybrid MPI + OpenMP parallelization combines message-passing across distributed nodes with shared-memory threading on SMP nodes to leverage large supercomputing resources for volume rendering [S1, S2]. It is distinguished from pure MPI approaches by its ability to reduce inter-node communication overhead for data-intensive tasks, and from pure OpenMP by its scalability to clusters with millions of cores [S1, S2]. The method is primarily implemented in the `yt` framework, where it balances computational load against memory constraints inherent to the rendering pipeline [S1, S2].

## How it works
**Inputs and Outputs:**
- **Inputs:** Simulation dataset (e.g., AMRKDTree bricks), rendering parameters (image plane resolution, camera position), and hardware topology ($N_{node}$, $cores\_per\_node$).
- **Outputs:** Rendered image plane stored in memory.

**Data Structures:**
- **Image Plane:** A 2D array of pixel values. In this specific implementation, each MPI task stores the *entire* image plane in its local memory [S1, S2]. This is a critical constraint for memory management.
- **Task Configuration:** Defined by the tuple $(N_{mpi}, N_{mp})$, where $N_{mpi}$ is the number of MPI processes and $N_{mp}$ is the number of OpenMP threads per process.

**Parameters:**
- $N_{mpi}$: Number of MPI tasks.
- $N_{mp}$: Number of OpenMP threads per MPI task.
- $P$: Total number of available CPU cores.
- $N_{node}$: Number of SMP nodes.
- $cores\_per\_node$: Number of cores per node.
- $OMP\_NUM\_THREADS$: Environment variable controlling default OpenMP thread count [S1, S2].
- `num_threads`: Keyword argument in the `snapshot()` function to override `OMP_NUM_THREADS` [S1, S2].

**Numbered Steps:**
1. **Topology Analysis:** Determine the total number of cores $P$ and the node structure ($N_{node}$, $cores\_per\_node$) of the target hardware [S1, S2].
2. **Configuration Selection:** Choose $N_{mpi}$ and $N_{mp}$ such that $N_{mpi} \times N_{mp} = P$ [S1, S2].
   - If the simulation contains many grids or AMRKDTree bricks, increase $N_{mpi}$ to distribute the spatial data partitioning [S1, S2].
   - If the image plane resolution is large (specifically $> 2048^2$), decrease $N_{mpi}$ and increase $N_{mp}$ to prevent memory exhaustion, as each MPI task holds the full image plane [S1, S2].
3. **Environment Setup:** Set the environment variable `OMP_NUM_THREADS` to $N_{mp}$ or pass `num_threads=N_{mp}` to the rendering function [S1, S2].
4. **MPI Initialization:** Launch $N_{mpi}$ MPI processes across the available nodes [S1, S2].
5. **Thread Launch:** Within each MPI process, spawn $N_{mp}$ OpenMP threads to execute the volume rendering kernel [S1, S2].
6. **Execution:** The threads collaboratively render the volume. Since each MPI task stores the entire image plane, no inter-process synchronization is required for image assembly, but memory usage scales linearly with $N_{mpi}$ [S1, S2].

**Edge Cases and Pitfalls:**
- **Memory Limits:** If $N_{mpi}$ is too high for large image planes ($>2048^2$), the system may run out of memory because every MPI task duplicates the entire image plane [S1, S2].
- **Desktop/Laptop Use:** On single-node machines with limited cores, pure OpenMP is often preferable to MPI due to lower overhead [S1, S2].
- **Topology Awareness:** Incorrect mapping of MPI tasks to sockets/nodes can degrade performance. Users must understand the hardware topology [S1, S2].

## Operating characteristics
- **Time Complexity:** Linear with respect to the number of voxels and rays, parallelized by $P$ cores. Speedup is limited by Amdahl's law and communication overhead between MPI tasks.
- **Memory Complexity:** $O(N_{mpi} \times W \times H)$ for the image plane storage, where $W, H$ are image dimensions. This is a significant limitation compared to tiled approaches where memory scales with $N_{mpi}$ only for the tile [S1, S2].
- **Scaling:** Scales well on supercomputers with many nodes if the dataset is partitioned effectively (many grids) [S1, S2]. Scaling is constrained by memory bandwidth and capacity when image planes are large [S1, S2].
- **Strengths:** Leverages existing MPI infrastructure for distributed data; reduces inter-node traffic for image assembly by keeping images local to nodes [S1, S2].
- **Limitations:** High memory footprint for high-resolution images; not suitable for resource-constrained environments [S1, S2].

## Background
This method is documented in the `yt` project's visualization documentation, specifically regarding volume rendering on supercomputing resources [S1, S2]. It addresses the need to scale volume rendering to large datasets that exceed the memory of a single node while avoiding the communication bottlenecks of pure MPI image compositing.
