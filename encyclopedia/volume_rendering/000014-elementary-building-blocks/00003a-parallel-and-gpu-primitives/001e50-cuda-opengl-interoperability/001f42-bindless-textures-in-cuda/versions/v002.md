# Bindless Textures in CUDA

Also called: Bindless Textures, BindlessTexture objects

## Overview
Bindless Textures in CUDA is a method for managing and accessing texture data directly from CUDA kernels without the per-frame binding and mapping overhead of OpenGL-CUDA interoperability [S1, S2]. It solves the performance bottlenecks and resource limits of traditional OpenGL-CUDA texture sharing, where textures must be bound, mapped to CUDA resources, and unmapped every frame [S1, S2]. Unlike [CUDA-OpenGL Interop Surface Write](2228-cuda-opengl-interop-surface-write.md), which focuses on surface buffers, this method addresses texture sampling by allowing a dynamic number of textures to be exposed simultaneously to the kernel at runtime [S1, S2].

## How it works
**Inputs:** Raw texture data and format specifications (channel type, internal format) [S1, S2].
**Outputs:** `BindlessTexture` objects stored in device-accessible memory, enabling simultaneous texture exposure to the kernel [S1, S2].

**Data Structures:**
1. **BindlessTexture Object:** A C++ templated class wrapping the CUDA texture object descriptor, supporting formats like `unsigned char`, `unsigned short`, and internal formats like `float1`, `float4`, `uchar4` [S1, S2].
2. **Texture Registry:** A linked list tracking all loaded `BindlessTexture` objects and their mipmap arrays for cleanup on program closure [S1, S2].

**Steps:**
1. Create mipmapped texture objects in VRAM using the CUDA API [S1, S2].
2. Launch a simple CUDA kernel asynchronously to compute mipmaps for each texture during loading [S1, S2].
3. Wrap the created texture objects in `BindlessTexture` instances using C++ templates to match the data format [S1, S2].
4. Append each `BindlessTexture` to a linked list to track objects and mipmap arrays for later deallocation [S1, S2].
5. Sample textures in device code using only the `tex` variable descriptor associated with the `BindlessTexture` object [S1, S2].

**Parameters:**
* `tex`: The variable name used to read a texture from device code; only this descriptor value needs to be known by the kernel [S1, S2].

**Edge Cases and Pitfalls:**
* **Overhead:** Traditional OpenGL-CUDA mapping requires binding every frame, mapping to a CUDA resource prior to kernel launch, and unbinding/unmapping after, which adds significant overhead [S2].
* **Resource Limits:** The traditional method limits the number of textures that can be simultaneously loaded [S2].
* **Hardcoding:** The traditional method requires all CUDA resources to be declared in global scope, meaning the number of textures used must be hardcoded [S1, S2].
* **Cleanup:** Textures and their mipmap arrays must be explicitly freed on program closure or when no longer needed to prevent memory leaks [S1, S2].

## Operating characteristics
**Time and Memory Complexity:**
* **Loading:** Not given in the sources.
* **Sampling:** Not given in the sources.
* **Memory:** VRAM usage scales with the total size of loaded textures and their mipmap arrays [S1, S2].

**Measured Performance:**
* Eliminates the per-frame binding and mapping overhead associated with OpenGL-CUDA interoperability [S1, S2].
* Allows a dynamic number of textures to be specified at runtime [S1, S2].
* Allows all textures to be exposed to the kernel simultaneously [S1, S2].

**Strengths and Limitations:**
* **Strengths:** High performance due to elimination of binding overhead; flexibility in the number of textures; no need to hardcode texture counts in global scope [S1, S2].
* **Limitations:** Requires careful memory management via a linked list for cleanup; relies on the CUDA API for texture creation rather than OpenGL [S1, S2].

**When to Use:**
* Use when rendering scenes with a dynamic or large number of textures that need to be accessed from CUDA kernels [S1, S2].
* Use when performance is critical and the overhead of OpenGL-CUDA binding is unacceptable [S1, S2].

**When Not to Use:**
* Use [CUDA-OpenGL Interop Surface Write](2228-cuda-opengl-interop-surface-write.md) if the primary goal is to write surface buffers directly to OpenGL for immediate display without complex texture sampling [S1, S2].
* Use traditional OpenGL-CUDA interoperability if the number of textures is small, fixed, and known at compile time, and if the simplicity of OpenGL texture management is preferred over the performance gains [S1, S2].

## Background
Bindless Textures in CUDA were introduced as a more performant design to replace the drawbacks of using OpenGL to manage textures for CUDA kernels [S1, S2]. The traditional method, similar to typical raster-based renderers, was found unsuitable for advanced raymarching renderers due to binding overhead, limited simultaneous texture counts, and the need to hardcode texture numbers in global scope [S1, S2]. The bindless approach utilizes an object-oriented design with C++ templating to support various formats and internal formats, enabling dynamic runtime specification and simultaneous exposure of all textures to the kernel [S1, S2].
