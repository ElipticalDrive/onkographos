# CUDA-OpenGL Interoperability

Also called: CUDA-GL Interop, CUDA-OpenGL Interoperability for 3D Textures, CUDA-OpenGL Interoperability for Raymarching, CUDA-OpenGL Interoperability for Volume Rendering, CUDA-OpenGL Interoperation via CUDA Array, OpenGL-CUDA Interoperability for Shared VBOs, Zero-Copy Volume Rendering, cudaGraphicsGLRegisterImage

## Overview
CUDA-OpenGL Interoperability is a mechanism that allows CUDA kernels to read from and write to OpenGL resources (textures, buffers) directly in GPU memory, eliminating the need for CPU-mediated data transfers [S1, unofficial][S2][S3, S4, S5, unofficial]. It solves the bottleneck of copying rendered volume data or simulation results from CUDA device memory back to system memory for display [S2]. It sets itself apart from standard interop methods by supporting both read-only access (via mapped arrays/texture objects) and write access (via surface objects or direct buffer pointers), enabling zero-copy rendering pipelines [S1, unofficial][S2][S3, S4, S5, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:** OpenGL resource IDs (Texture ID, Buffer ID), resource dimensions (width, height, depth), and CUDA graphics resource flags.
*   **Outputs:** CUDA graphics resource handle (`cudaGraphicsResource_t`), mapped CUDA array (`cudaArray_t`), or device pointer (`void*`).

**Data Structures:**
*   `cudaGraphicsResource_t`: Opaque handle returned by registration functions.
*   `cudaArray_t`: Device memory structure representing the mapped OpenGL texture.
*   `cudaResourceDesc`: Structure describing the resource type (Array, Buffer) and its properties.
*   `cudaSurfaceObject_t`: Object allowing atomic writes to a mapped array.

**Numbered Steps:**

1.  **Resource Registration:**
    *   For Textures: Call `cudaGraphicsGLRegisterImage` with the OpenGL texture ID, target (`GL_TEXTURE_2D` or `GL_TEXTURE_3D`), and flags. Use `cudaGraphicsRegisterFlagsSurfaceLoadStore` if write access is required [S1, S3, S4, unofficial].
    *   For Buffers (VBO/PBO): Call `cudaGraphicsGLRegisterBuffer` with the VBO ID and flags (typically `cudaGraphicsMapFlagsNone` for read/write) [S5, unofficial].
    *   *Pitfall:* Ensure the OpenGL context is current before registration [S2].

2.  **Resource Mapping (Per Frame/Per Kernel Launch):**
    *   Call `cudaGraphicsMapResources` with the resource handle count and array of handles to gain CUDA access [S1, S3, S4, S5, unofficial].
    *   *Pitfall:* Accessing the mapped resource with OpenGL before unmapping causes program failure [S5, unofficial].

3.  **Resource Acquisition:**
    *   For Textures: Call `cudaGraphicsSubResourceGetMappedArray` to retrieve the `cudaArray_t` [S1, S3, S4, unofficial].
    *   For Buffers: Call `cudaGraphicsResourceGetMappedPointer` to retrieve the device pointer (`void**`) [S5, unofficial].

4.  **Binding (Optional but Recommended for Textures):**
    *   For Read Access: Bind the `cudaArray_t` to a CUDA texture object using `cudaBindTextureToArray` [S3, unofficial].
    *   For Write Access: Initialize `cudaResourceDesc` with `resType=cudaResourceTypeArray` and `res.array.array=array`, then call `cudaCreateSurfaceObject` to create a `cudaSurfaceObject_t` [S1, unofficial]. Alternatively, bind the array to a surface using `cudaBindSurfaceToArray` [S3, unofficial].

5.  **Kernel Execution:**
    *   Launch the CUDA kernel.
    *   If using Surface: Pass the `cudaSurfaceObject_t` to the kernel. Use `surfaceStore` or atomic functions for writes [S1, S3, unofficial].
    *   If using Pointer (VBO): Pass the device pointer obtained in Step 3. The kernel writes directly to the VBO memory [S5, unofficial].
    *   If using Texture Array (Read-only): Use standard texture fetch functions (`tex3D`, `tex2D`) [S3, unofficial].

6.  **Unmapping:**
    *   Call `cudaGraphicsUnmapResources` to release CUDA access, allowing OpenGL to use the resource again [S1, S3, S4, S5, unofficial].

7.  **Cleanup (Optional):**
    *   Destroy surface objects if created: `cudaDestroySurfaceObject` [S1, unofficial].
    *   Unregister resources on shutdown: `cudaGraphicsUnregisterResource` [S1, unofficial].

**Pseudocode:**

```python
# Initialization (One-time)
def init_opengl_texture_interop(gl_texture_id, width, height, depth, is_writable=False):
    # Step 1: Register
    flags = cudaGraphicsRegisterFlagsSurfaceLoadStore if is_writable else cudaGraphicsRegisterFlagsReadOnly
    resource_handle = cudaGraphicsGLRegisterImage(gl_texture_id, GL_TEXTURE_3D, flags)
    
    # Create surface object handle (initialized to 0)
    surface_handle = 0
    return resource_handle, surface_handle

def init_opengl_buffer_interop(gl_vbo_id, size_bytes):
    # Step 1: Register Buffer
    resource_handle = cudaGraphicsGLRegisterBuffer(gl_vbo_id, cudaGraphicsMapFlagsNone)
    return resource_handle

# Per-Frame Execution

    # Step 2: Map Resources
    cudaGraphicsMapResources(1, resource_handle)
    
    cuda_array = None
    device_ptr = None
    
    if gl_vbo_handle is None:
        # Texture Path
        # Step 3: Get Mapped Array
        cuda_array = cudaGraphicsSubResourceGetMappedArray(resource_handle, 0, 0)
        
        if surface_handle == 0:
            # Step 4: Create Surface for Writing
            res_desc = cudaResourceDesc()
            res_desc.resType = cudaResourceTypeArray
            res_desc.res.array.array = cuda_array
            surface_handle = cudaCreateSurfaceObject(res_desc)
        
        # Step 5: Launch Kernel with Surface
        # launch_kernel<<<blocks, threads>>>(surface_handle, width, height)
        # Note: Kernel uses surf2Dwrite or atomicAdd on surface
    else:
        # Buffer Path
        # Step 3: Get Mapped Pointer
        device_ptr, bytes_count = cudaGraphicsResourceGetMappedPointer(resource_handle)
        
        # Step 5: Launch Kernel with Pointer
        # launch_kernel<<<blocks, threads>>>(device_ptr, width, height)
        # Note: Kernel writes directly to device_ptr
    
    # Step 6: Unmap
    cudaGraphicsUnmapResources(1, resource_handle)
    
    return surface_handle

# Cleanup
def cleanup(resource_handle, surface_handle):
    if surface_handle != 0:
        cudaDestroySurfaceObject(surface_handle)
    cudaGraphicsUnregisterResource(resource_handle)
```

**Parameters:**
*   `block_dim`: Typically `dim3(16, 16, 1)` for 2D image writing [S3, unofficial].
*   `grid_dim`: Calculated as `(Width + block_dim.x) / block_dim.x` for x, `(Height + block_dim.y) / block_dim.y` for y, and 1 for z [S3, unofficial].
*   `constantWidth`, `constantHeight`: CUDA constants storing viewport dimensions, updated via `cudaMemcpyToSymbol` [S3, unofficial].

**Edge Cases and Pitfalls:**
*   **Context Current:** OpenGL context must be current when registering or mapping resources [S2].
*   **Surface Creation Failure:** If `cudaGraphicsSubResourceGetMappedArray` fails, the surface object is not created, preventing kernel launch. Check `cudaSuccess` before creating the surface [S1, unofficial].
*   **Typo in Constants:** Ensure variable names match exactly when using `cudaMemcpyToSymbol` (e.g., `constantNCP` vs `cosntantNCP`) [S3, unofficial].
*   **Ray-Box Intersection:** If `NOT_RAY_BOX` is defined, front/back hit positions are computed via OpenGL geometry shaders and stored in textures; otherwise, the inverse view matrix is passed to CUDA for GPU-side intersection [S3, unofficial].

## Subtopics

### [CUDA-OpenGL Interop Surface Write](2228-cuda-opengl-interop-surface-write.md)
CUDA-OpenGL Interop Surface Write is a technique to render volume data by computing ray casting on the GPU (CUDA) and writing the final image directly into a texture that is registered with OpenGL, avoiding CPU-GPU data transfer for the final image [Parent]. It sets itself apart from standard interop methods by using CUDA surface objects (`cudaSurfaceObject_t`) for write access, which allows for atomic operations and potentially better performance for concurrent writes compared to standard texture memory writes or copies.

### Bindless Textures in CUDA
Bindless Textures in CUDA is an object-oriented approach using the CUDA API to upload textures into VRAM and expose them via texture object descriptors, eliminating the need for per-frame binding and mapping required by OpenGL-CUDA interoperability for textures [S2]. It sets itself apart by allowing a dynamic number of textures specified at runtime and simultaneous exposure to the kernel, unlike the OpenGL mapping method which requires hardcoded global scope declarations and per-frame binding/unbinding [S2]. It is chosen when the number of textures is large or dynamic, and when the overhead of mapping/unmapping becomes a bottleneck [S2].

## Operating characteristics
*   **Time Complexity:** O(1) for registration/unregistration (one-time). O(1) for map/unmap per frame. Kernel execution time depends on the rendering algorithm (e.g., raymarching).
*   **Memory Complexity:** Zero-copy; no additional CPU memory allocation for the rendered image or texture data.
*   **Measured Performance:** Eliminates four serial copies and four redundant texture objects compared to SFML-based approaches [S2]. Reduces frame latency from >20 ms (under 60 fps for 1080p) to significantly lower values, enabling real-time performance [S2].
*   **Strengths:** Eliminates CPU-GPU data transfer overhead; allows direct GPU-side rendering; supports atomic writes via surfaces.
*   **Limitations:** Requires OpenGL context management; binding/unmapping overhead for textures (mitigated by Bindless Textures); limited simultaneous texture count in standard OpenGL interop (mitigated by Bindless Textures) [S2].
*   **When to Use:** Real-time volume rendering, GPU-based simulations requiring visual feedback, avoiding CPU bottlenecks.
*   **When Not to Use:** When CPU-side post-processing is required, or when using libraries that abstract away OpenGL/CUDA interop (e.g., SFML) where performance is not critical.

## Background
CUDA-OpenGL Interoperability was introduced with CUDA 2.0 [S2]. It has been widely used in volume rendering engines (e.g., VRCUDA, cuVRender) and fluid simulation visualizations (e.g., HZL-fluidEffectsStudio) to achieve real-time performance by bypassing the CPU [S1, S3, S4, S5, unofficial]. The technique evolved to include Bindless Textures to address the limitations of per-frame binding and mapping [S2].
