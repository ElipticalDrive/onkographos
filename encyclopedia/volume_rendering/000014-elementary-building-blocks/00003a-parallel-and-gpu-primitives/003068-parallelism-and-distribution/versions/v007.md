# Parallelism and Distribution
## Overview
Parallelism and Distribution refers to the family of techniques that map volume rendering computations across multiple processing units (CPUs, GPUs, or networked nodes) to handle datasets or frame rates that exceed single-device capabilities [G]. It solves the scalability bottleneck of rendering large, high-resolution, or time-varying volumes by partitioning the workload spatially, temporally, or algorithmically [G]. It builds on [Parallel and GPU primitives](771-parallel-and-gpu-primitives.md) and sets itself apart from sibling methods like [Tiled Parallel Compositing](1192-tiled-parallel-compositing.md) (which focuses on intra-node tile management) and [Compute Shader Kernel](1202-compute-shader-kernel.md) (which focuses on single-device kernel structure) by addressing inter-node communication, load balancing across heterogeneous clusters, and distributed memory management [G].
## Shared principles
This family inherits its core mechanism, thread mapping, memory hierarchy utilization, synchronization strategies, and data parallelism principles from [Parallel and GPU primitives](771-parallel-and-gpu-primitives.md).
## Subtopics

### [Parallel Image Compositing with Overlapping](3554-parallel-image-compositing-with-overlapping.md)
A distributed rendering strategy where ray segments are transmitted to responsible processors immediately upon generation, rather than waiting for local ray-tracing to complete. It sets itself apart from non-overlapping methods by overlapping communication with computation, reducing network congestion and improving compositing performance by up to 40%. Choose this when network bandwidth can handle frequent, smaller messages and when load balancing across processors is critical.

### [Ray Compaction](4039-ray-compaction.md)
A parallel primitive that filters a list of active rays by removing terminated ones and compacting the survivors into a dense, contiguous buffer. It sets itself apart from [Ray Buffer Reordering](4073-ray-buffer-reordering.md) by serving as a foundational atomic-indexing step, whereas [In-Kernel Stream Compaction (InK-Compact)](6991-in-kernel-stream-compaction-ink-compact.md) avoids separate prefix-sum launches. Choose this when ray termination rates are high and memory locality for active rays is required.

### [Manager/Workers Parallel Implementation](6359-manager-workers-parallel-implementation.md)
A distributed task-scheduling architecture designed for load-balanced execution on clusters where processor availability varies over time. It sets itself apart from sibling methods that rely on static partitioning by using a dynamic task queue where workers request work and the manager assigns tasks based on global knowledge of data boundaries and worker status. Choose this for heterogeneous clusters or when tasks have highly variable computational costs.

### [Sort-last Parallel Rendering](6889-sort-last-parallel-rendering.md)
A distributed strategy that partitions the volume dataset into sub-volumes, distributes them across independent processors, and composites the resulting partial images in a final step. It sets itself apart from sort-first methods by keeping the data distribution fixed regardless of the view angle, making it a natural choice for distributed-memory systems where data redistribution is costly. Choose this for very large volumes where network bandwidth can handle full-resolution image transfers.

### [Sort-middle Parallel Rendering](6893-sort-middle-parallel-rendering.md)
A distributed rendering strategy that partitions the workload between the geometry preprocessing (transformation and lighting) stage and the rasterization stage. It sets itself apart from sort-first by allowing geometry processors to transform and light primitives before sending the resulting screen-space primitives to specific rasterizers based on their screen coverage. This approach was notably implemented in the Chromium system to overcome sort-first network latency, achieving approximately twice the frame rate by reducing the volume of data sent over the network. Choose this when geometry processing is a bottleneck and screen-space distribution is efficient.

### [Temporal Division of Uniform Resolution Data](7094-temporal-division-of-uniform-resolution-data.md)
A parallelism strategy for time-varying volume rendering where computational tasks are distributed across processors based on time steps rather than spatial regions. It sets itself apart from spatial decomposition methods by not requiring a single data file to be broken up between processors, which reduces preprocessing overhead and allows different time steps to reside on different processors. Choose this for time-series data where spatial load imbalance is severe but temporal uniformity exists.

### [Breakable Integrals](10328-breakable-integrals.md)
A family of integral functions defined over a domain $[t_1, t_{N+1}]$ that can be decomposed into a sum of products of integrals over individual segments $[t_k, t_{k+1}]$. It sets itself apart from standard parallel primitives that distribute data elements by distributing the mathematical structure of the integral itself, making it suitable for multi-GPU implementations where segments are processed independently and aggregated. Choose this for volume integrals (e.g., density, light transport) that can be mathematically split.

### [Hybrid Distributed-Memory Parallel Volume Rendering](11442-hybrid-distributed-memory-parallel-volume-rendering.md)
A distributed-memory parallel volume rendering algorithm that combines object-order and image-order techniques to mitigate load imbalance on unstructured grids. It sets itself apart from pure object-order methods (which suffer from uneven sample distribution) and pure image-order methods (which struggle when tile boundaries cut through dense cell regions) by bounding the work per processor in each phase. Choose this for unstructured grids with high heterogeneity in cell size or density.

### [SMT Parallelization with Logical Ray Lists](13634-smt-parallelization-with-logical-ray-lists.md)
A parallelization strategy for Simultaneous Multithreading (SMT) architectures designed to maximize CPU utilization by allowing multiple threads to operate within the same processing block while sharing cache resources. It sets itself apart from methods relying on global synchronization by using a hierarchical distribution of ray lists—one per logical CPU per block—to eliminate the need for expensive synchronization primitives like mutexes. Choose this for SMT CPUs where logical processors share physical resources.

### Coalescing Launch Mode
**Definition:** A launch mode that coalesces input records into batches to reduce workload, providing expansion (many threads spawned for a single input record) but not thread coalescing for SIMD groups [S1, unofficial].
**Step:** Opportunistically merge input records to reduce workload [S1, unofficial].
**Parameter:** Merge targets include rectangles before drawing, draw call parameters into draw instance call parameters, or draw leaf records to pass a list of leaves to draw to a mesh node [S1, unofficial].
**Layout:** Spawns one workgroup for a variable number of input records [S1, unofficial].

### Distributed Data Parallel Training
**Definition:** Multi-GPU training using PyTorch DDP with NCCL backend [S2, unofficial].
**Step:** Initialize distributed process group with NCCL backend [S2, unofficial]. Wrap model in DDP [S2, unofficial]. Use `DistributedSampler` for data loading to ensure each GPU processes unique data [S2, unofficial]. Synchronize epoch for sampler [S2, unofficial].
**Parameter:** Master address is `localhost` and port is `12355` [S2, unofficial]. World size equals number of available CUDA devices [S2, unofficial].
**Code:**
```python
def setup_ddp(rank: int, world_size: int, batch_size: int, dataset):
    import torch
    import torch.distributed as dist
    import torch.nn as nn
    from torch.utils.data import DistributedSampler, DataLoader

    # 1. Initialize Process Group
    dist.init_process_group("nccl", rank=rank, world_size=world_size)

    # 2. Wrap Model
    model = nn.Linear(10, 4)  # Placeholder model definition
    model = nn.parallel.DistributedDataParallel(model.to(rank), device_ids=[rank])

    # 3. Data Loading
    sampler = DistributedSampler(dataset)
    loader = DataLoader(dataset, batch_size=batch_size, sampler=sampler)
    return model, loader
```

### Rayon Multicore Parallelism
**Definition:** Automatic parallelization of CPU rendering tasks using the rayon library, requiring no explicit API calls from the user [S3].
**Step:** World-voxel lighting baking fans out per column batch [S3]. Sprite passes batch per sprite [S3].
**Parameter:** `RAYON_NUM_THREADS` environment variable bounds the thread pool size [S3].
**Usage:** In the browser, parallelism runs on Web Workers via `wasm-bindgen-rayon` [S3].
