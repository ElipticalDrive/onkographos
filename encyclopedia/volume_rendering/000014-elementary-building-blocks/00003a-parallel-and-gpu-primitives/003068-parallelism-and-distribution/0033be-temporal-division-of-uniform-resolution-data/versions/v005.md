# Temporal Division of Uniform Resolution Data

Also called: Data streaming, Frame multiplexing, Temporal Decomposition, Time-step Parallelism

## Overview
Temporal division of uniform resolution data is a parallelism strategy for time-varying volume rendering where computational tasks are distributed across processors based on time steps rather than spatial regions [S1, unofficial]. It solves the problem of rendering large, multi-frame datasets by assigning unique groups of time steps to each processor, ensuring all processors remain busy and the frame generation rate matches the display rate [S1, unofficial]. Unlike spatial decomposition methods such as [Parallel Image Compositing with Overlapping](3554-parallel-image-compositing-with-overlapping.md), temporal division does not require breaking up a single data file between processors, which reduces preprocessing overhead and allows different time steps to reside on different processors [S1, unofficial]. The approach encompasses two variants: frame multiplexing, where each processor is assigned a unique group of time steps, and data streaming, where all processors work jointly on each time step [S1, unofficial].

## How it works
### Inputs and Outputs
- **Inputs:** A sequence of $N$ time steps of volume data, each of uniform resolution. A set of $P$ processors [S1, unofficial].
- **Outputs:** A sequence of rendered frames displayed in temporal order ($1, 2, \dots, N$) [S1, unofficial].

### Data Structures
- **Frame Pool:** A buffer that stores completed frames from processors, indexed by their time step ID [S1, unofficial].
- **Assignment Map:** A mapping of processor IDs to their assigned time step indices [S1, unofficial]. For uniform interleaving, Processor $p$ (where $1 \le p \le P$) is assigned time steps $t$ such that $p = ((t - 1) \pmod P) + 1$ [S1, unofficial].

### Steps
1. **Assignment:** Assign time steps to processors in a round-robin or interleaved fashion [S1, unofficial]. For example, with 3 processors and 9 time steps: Processor 1 gets steps 1, 4, 7; Processor 2 gets steps 2, 5, 8; Processor 3 gets steps 3, 6, 9 [S1, unofficial].
2. **Rendering:** Each processor renders its assigned time steps sequentially [S1, unofficial]. Upon completion, it adds the resulting image to the Frame Pool [S1, unofficial].
3. **Sequencing:** A display system or sequencer picks frames from the pool in increasing time order [S1, unofficial]. It displays frame $t$, then increments the target time to $t+1$ and waits for that frame if it is not yet available [S1, unofficial].
4. **Loop:** Processors continue rendering their next assigned time step immediately after finishing the previous one [S1, unofficial]. The pipeline aims to ensure a frame is ready before it is needed, eliminating lag after an initial startup delay [S1, unofficial].

### Formulas
- **Interleaving Assignment:** For Processor $p$ (1-indexed) and Time Step $t$ (1-indexed):
  $$ p = ((t - 1) \pmod P) + 1 $$
- **Pipeline Timing:** Ideally, the system ensures a frame is ready before it is needed, eliminating lag after an initial startup delay [S1, unofficial].

### Parameters
- **$P$ (Number of Processors):** Determines the stride of the interleaving [S1, unofficial].
- **$N$ (Total Time Steps):** The total number of frames in the sequence [S1, unofficial].

### Edge Cases and Pitfalls
- **Late Frames:** If a processor slows down, its assigned frame may arrive late [S1, unofficial]. This causes the sequencer to wait, resulting in fluctuating frame rates or animation pauses [S1, unofficial].
- **Initial Lag:** There is an initial startup delay while the first set of frames is generated [S1, unofficial].
- **Variable Rendering Time:** If time steps have varying computational costs (e.g., due to adaptive resolution), simple interleaving leads to load imbalance [S1, unofficial].

### Pseudocode
```python
# Configuration
P = 3  # Number of processors
N = 9  # Total time steps
frame_pool = {}  # Dictionary mapping time_step_id -> image_data

def render_loop(processor_id):
    """Each processor runs this loop. processor_id is 1-indexed (1 to P)."""
    for t in range(processor_id, N + 1, P):
        # Load volume data for time step t (standard I/O)
        # Render volume step (standard ray-casting/compositing)
        image = render_volume_step(t)
        frame_pool[t] = image
        # Loop continues to next assigned step immediately

def display_loop():
    """The sequencer runs this loop."""
    current_display_time = 1
    while current_display_time <= N:
        # Wait for the frame to be available
        while current_display_time not in frame_pool:
            pass  # Synchronization wait
        # Display frame from pool
        display_image(frame_pool[current_display_time])
        current_display_time += 1
```

## Subtopics

### [1D Input Processors (1DIP)](10828-1d-input-processors-1dip.md)
1D Input Processors (1DIP) is a parallel I/O strategy that uses multiple input processors to fetch and preprocess a single complete time step of volume data, maximizing parallel file system bandwidth. It differs from its sibling [2D Input Processors (2DIP)](10833-2d-input-processors-2dip.md) by focusing on parallelizing the read of one time step rather than concurrently reading multiple time steps, making it suitable when sending time per time step is the bottleneck.

### [2D Input Processors (2DIP)](10833-2d-input-processors-2dip.md)
2D Input Processors (2DIP) is a parallel I/O strategy for rendering large time-varying volume data that addresses the bottleneck where the data sending time ($T_s$) exceeds the rendering time ($T_r$). Unlike [1D Input Processors (1DIP)](10828-1d-input-processors-1dip.md), which distributes a single time step across multiple input processors to reduce send time, 2DIP concurrently reads and distributes multiple time steps using a two-dimensional configuration of input processors. This ensures that rendering processors remain busy by overlapping I/O and preprocessing of future time steps with the rendering of the current one.

### Decoupled Display Phase
A technique to hide latency by decoupling the display phase from the rendering and I/O phases, showing only approximate images while no reliable image information is available [S2, unofficial]. The system displays and warps approximate images based on 2.5D data while no newly rendered image data is available from the remote servers [S2, unofficial]. This approach achieves interactive frame rates of approximately 30 Hz, necessary for virtual reality applications [S2, unofficial].

### Temporal Distribution of Adaptive-Resolution Data
A load-balancing strategy for temporal division where time steps are assigned to processors based on their resolution (computational cost) rather than simple interleaving [S1, unofficial]. The system calculates the relative cost/resolution of each time step and assigns fewer high-resolution time steps to processors and more low-resolution time steps to balance the total workload [S1, unofficial]. In a specific example, Processor 1 was assigned 3 high-resolution frames and Processor 2 was assigned 6 low-resolution frames to achieve equal work distribution [S1, unofficial].

### Temporal Sequencing
A post-processing step for temporal division where completed frames from a pool are displayed in increasing time order [S1, unofficial]. The sequencer maintains a pool of frames; when a processor finishes a time step, it adds the image to the pool [S1, unofficial]. The sequencer picks the frame for the current time step from the pool and displays it, then increments the time and repeats [S1, unofficial]. To mitigate late frames, a time lag can be introduced at the start to ensure enough frames are in the pool, or a fixed display time for each frame can be set equal to the max rendering time of any resolution [S1, unofficial]. A pitfall is that if a processor slows down, frames arrive late, causing the animation to wait and resulting in fluctuating frame rates [S1, unofficial].

## Operating characteristics
- **Time Complexity:** Each processor renders its assigned time steps sequentially, dividing the workload equally among processors [S1, unofficial].
- **Memory Complexity:** Each processor stores only the time steps assigned to it, allowing very large datasets that do not fit in one processor's memory to be rendered by placing only a few time steps on each computer [S1, unofficial].
- **Performance:** STARVolume uses this method to render huge datasets at high speeds, allowing equal workload division among processors [S1, unofficial].
- **Strengths:** Reduces preprocessing work by avoiding file splitting; allows large datasets that do not fit in one processor's memory to be rendered by distributing time steps across nodes [S1, unofficial].
- **Limitations:** Requires synchronization for display sequencing; susceptible to frame rate fluctuations if rendering times vary significantly between time steps [S1, unofficial].

## Background
Temporal division techniques were described by Bhaniramka et al. [S1, unofficial]. Two primary techniques were identified: frame multiplexing (where each processor is assigned a group of unique time steps) and data streaming (where all processors work jointly on each time step) [S1, unofficial]. STARVolume uses the frame multiplexing approach for temporal parallel rendering [S1, unofficial]. This method is distinct from spatial decomposition approaches like sort-last rendering, which require complex compositing algorithms [S1, unofficial].
