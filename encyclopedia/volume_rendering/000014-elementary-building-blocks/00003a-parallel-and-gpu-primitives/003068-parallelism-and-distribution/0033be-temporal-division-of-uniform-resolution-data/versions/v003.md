# Temporal Division of Uniform Resolution Data

Also called: Data streaming, Frame multiplexing, Temporal Decomposition, Time-step Parallelism

## Overview
Temporal division of uniform resolution data is a parallelism strategy for time-varying volume rendering where computational tasks are distributed across processors based on time steps rather than spatial regions [S1, unofficial]. It solves the problem of rendering large, multi-frame datasets by assigning unique groups of time steps to each processor, ensuring all processors remain busy and the frame generation rate matches the display rate [S1, unofficial]. Unlike spatial decomposition methods such as [Parallel Image Compositing with Overlapping](3554-parallel-image-compositing-with-overlapping.md), temporal division does not require breaking up a single data file between processors, which reduces preprocessing overhead and allows different time steps to reside on different processors [S1, unofficial].

## How it works
### Inputs and Outputs
- **Inputs:** A sequence of $N$ time steps (frames) of volume data, each of uniform resolution. A set of $P$ processors.
- **Outputs:** A sequence of rendered frames displayed in temporal order ($1, 2, \dots, N$).

### Data Structures
- **Frame Pool:** A data structure (e.g., a queue or buffer) that stores completed frames from processors, indexed by their time step ID [S1, unofficial].
- **Assignment Map:** A mapping of processor IDs to their assigned time step indices. For uniform interleaving, Processor $i$ (where $0 \le i < P$) is assigned time steps $t$ such that $t \equiv i \pmod P$ [S1, unofficial].

### Steps
1. **Assignment:** Assign time steps to processors. In the standard uniform case, time steps are distributed in a round-robin or interleaved fashion. For example, with 3 processors and 9 time steps:
   - Processor 1: Steps 1, 4, 7
   - Processor 2: Steps 2, 5, 8
   - Processor 3: Steps 3, 6, 9 [S1, unofficial].
2. **Rendering:** Each processor renders its assigned time steps sequentially. Upon completion of a time step, the processor adds the resulting image to the Frame Pool [S1, unofficial].
3. **Sequencing:** A display system or sequencer picks frames from the pool in increasing time order. It displays frame $t$, then increments the target time to $t+1$ and waits for that frame if it is not yet available [S1, unofficial].
4. **Loop:** Processors continue rendering their next assigned time step immediately after finishing the previous one. The pipeline aims to ensure a frame is ready before it is needed, eliminating lag after an initial startup delay [S1, unofficial].

### Formulas
- **Interleaving Assignment:** For Processor $p$ (0-indexed) and Time Step $t$ (1-indexed):
  $$ \text{Assigned if } (t - 1) \pmod P = p $$
- **Ideal Pipeline Condition:** The time to render one frame ($T_r$) should be less than or equal to the time between required frames ($T_{display}$). If $T_r \le T_{display}$, the system can sustain real-time playback after the initial warm-up [S1, unofficial].

### Parameters
- **$P$ (Number of Processors):** Determines the stride of the interleaving.
- **$N$ (Total Time Steps):** Must be divisible by $P$ for perfect uniform distribution, or handled with remainder logic.

### Edge Cases and Pitfalls
- **Late Frames:** If a processor slows down, its assigned frame may arrive late. This causes the sequencer to wait, resulting in fluctuating frame rates or animation pauses [S1, unofficial].
- **Initial Lag:** There is an initial startup delay while the first set of frames is generated. The pipeline must be primed to avoid gaps [S1, unofficial].
- **Variable Rendering Time:** If time steps have varying computational costs (e.g., due to adaptive resolution), simple interleaving leads to load imbalance [S1, unofficial].

### Pseudocode
```python
# Configuration
P = number_of_processors
N = total_time_steps
frame_pool = {} # Dictionary mapping time_step_id -> image_data

def render_loop(processor_id):
    """
    Each processor runs this loop.
    """
    # Determine assigned time steps
    # Using 1-based indexing for time steps as per source
    start_step = processor_id + 1
    steps = range(start_step, N + 1, P)
    
    for t in steps:
        # 1. Render the current time step
        # Assumes a function render_volume(time_step_data) exists
        image = render_volume(get_data(t))
        
        # 2. Add to pool
        frame_pool[t] = image
        
        # 3. Move to next step (loop continues)

def display_loop():
    """
    The sequencer runs this loop.
    """
    current_display_time = 1
    
    while current_display_time <= N:
        # Wait for the frame to be available
        while current_display_time not in frame_pool:
            pass # Busy wait or sleep with yield
            
        # Display the frame
        display_image(frame_pool[current_display_time])
        
        # Increment time
        current_display_time += 1
```

## Subtopics

### [1D Input Processors (1DIP)](10828-1d-input-processors-1dip.md)
1D Input Processors (1DIP) is a parallel I/O strategy that uses multiple input processors to fetch and preprocess a single complete time step of volume data, maximizing parallel file system bandwidth. It differs from its sibling [2D Input Processors (2DIP)](10833-2d-input-processors-2dip.md) by focusing on parallelizing the read of one time step rather than concurrently reading multiple time steps, making it suitable when sending time per time step is the bottleneck.

### [2D Input Processors (2DIP)](10833-2d-input-processors-2dip.md)
2D Input Processors (2DIP) is a parallel I/O strategy for rendering large time-varying volume data that addresses the bottleneck where the data sending time ($T_s$) exceeds the rendering time ($T_r$). Unlike [1D Input Processors (1DIP)](10828-1d-input-processors-1dip.md), which distributes a single time step across multiple input processors to reduce send time, 2DIP concurrently reads and distributes multiple time steps using a two-dimensional configuration of input processors. This ensures that rendering processors remain busy by overlapping I/O and preprocessing of future time steps with the rendering of the current one.

### Decoupled Display Phase
A technique to hide latency by decoupling the display phase from the rendering and I/O phases, showing only approximate images while no reliable image information is available [S2, unofficial]. The system displays and warps approximate images based on 2.5D data while no newly rendered image data is available from the remote servers [S2, unofficial]. This approach achieves interactive frame rates of approximately 30 Hz, necessary for virtual reality applications [S2, unofficial].

### Temporal Distribution of Adaptive-Resolution Data
A load-balancing strategy for temporal division where time steps are assigned to processors based on their resolution (computational cost) rather than simple interleaving [S1, unofficial]. The system calculates the relative cost/resolution of each time step and assigns fewer high-resolution time steps to processors and more low-resolution time steps to balance the total workload [S1, unofficial]. In a specific example, Processor 1 was assigned 3 high-resolution frames and Processor 2 was assigned 6 low-resolution frames to achieve equal work distribution [S1, unofficial].

### Temporal Sequencing
A post-processing step for temporal division where completed frames from a pool are displayed in increasing time order [S1, unofficial]. The sequencer maintains a pool of frames; when a processor finishes a time step, it adds the image to the pool. The sequencer picks the frame for the current time step from the pool and displays it, then increments the time and repeats [S1, unofficial]. To mitigate late frames, a time lag can be introduced at the start to ensure enough frames are in the pool, or a fixed display time for each frame can be set equal to the max rendering time of any resolution [S1, unofficial]. A pitfall is that if a processor slows down, frames arrive late, causing the animation to wait and resulting in fluctuating frame rates [S1, unofficial].

## Operating characteristics
- **Time Complexity:** The rendering time per frame is $O(V)$ where $V$ is the volume size, but parallelized across $P$ processors, the effective time per frame is $O(V/P)$ assuming perfect load balancing [S1, unofficial].
- **Memory Complexity:** Each processor needs to store only the time steps assigned to it, reducing per-node memory requirements compared to spatial decomposition which might require access to large portions of a single large file [S1, unofficial].
- **Performance:** STARVolume uses this method to render huge datasets at high speeds, allowing equal workload division among processors [S1, unofficial].
- **Strengths:** Reduces preprocessing work by avoiding file splitting; allows large datasets that do not fit in one processor's memory to be rendered by distributing time steps across nodes [S1, unofficial].
- **Limitations:** Requires synchronization for display sequencing; susceptible to frame rate fluctuations if rendering times vary significantly between time steps [S1, unofficial].

## Background
Temporal division techniques were described by Bhaniramka et al. [S1, unofficial]. Two primary techniques were identified: frame multiplexing (where each processor is assigned a group of unique time steps) and data streaming (where all processors work jointly on each time step) [S1, unofficial]. STARVolume uses the frame multiplexing approach for temporal parallel rendering [S1, unofficial]. This method is distinct from spatial decomposition approaches like sort-last rendering, which require complex compositing algorithms [S1, unofficial].
