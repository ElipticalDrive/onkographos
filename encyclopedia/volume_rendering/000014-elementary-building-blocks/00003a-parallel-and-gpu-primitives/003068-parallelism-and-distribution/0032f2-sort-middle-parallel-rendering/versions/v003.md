# Sort-middle Parallel Rendering

## Overview
Sort-middle parallel rendering is a distributed rendering strategy that partitions the workload between the geometry preprocessing (transformation and lighting) stage and the rasterization stage [S1, S2, unofficial]. Unlike sort-first, which distributes primitives before transformation, sort-middle allows geometry processors to transform and light an arbitrary subset of primitives before sending the resulting screen-space primitives to specific rasterizers based on their screen coverage [S2, unofficial]. This approach was notably implemented in the Chromium system to overcome the network latency issues of sort-first, achieving approximately twice the frame rate of sort-first by reducing the volume of data sent over the network [S1, unofficial].

## How it works
The method operates in a distributed environment where geometry processors and rasterizers are distinct entities [S2, unofficial].

**Inputs and Outputs:**
*   **Input:** A set of 3D primitives and a scene graph [G].
*   **Output:** A composite image formed by merging the rasterized outputs from all rasterizers [S1, S2, unofficial].

**Data Structures:**
*   **Primitive List:** A list of 3D primitives with attributes (vertices, normals, colors) [G].
*   **Transformed Primitive List:** A list of 2D screen-space primitives (clipped and projected) generated by geometry processors [S2, unofficial].
*   **Screen Partition Map:** A mapping that defines which rasterizer is responsible for which region of the screen [S2, unofficial].
*   Exact layouts and bit packing are Not given in the sources.

**Steps:**
1.  **Distribution to Geometry Processors:** The original 3D primitives are distributed among available geometry processors as an arbitrary subset [S2, unofficial].
2.  **Transformation and Lighting:** Each geometry processor transforms its assigned 3D primitives into screen space and performs lighting calculations [S2, unofficial].
3.  **Screen-Space Sorting/Distribution:** The transformed 2D primitives are analyzed to determine their screen coverage, and each primitive is sent to the rasterizer(s) responsible for the screen region(s) it overlaps [S2, unofficial].
4.  **Rasterization:** Each rasterizer rasterizes the subset of primitives assigned to its screen region [S2, unofficial].
5.  **Compositing:** The resulting sub-images (or pixel buffers) from all rasterizers are combined to form the final image [S1, S2, unofficial].

**Formulas:**
*   Let $P$ be the set of all primitives.
*   Let $G_i$ be the set of primitives assigned to geometry processor $i$.
*   Let $R_j$ be the rasterizer responsible for screen region $S_j$.
*   For a primitive $p \in G_i$, let $proj(p)$ be its screen-space projection.
*   The primitive $p$ is sent to rasterizer $R_j$ if $proj(p) \cap S_j \neq \emptyset$ [S2, unofficial].

**Parameters:**
*   **Screen Partitioning:** The geometry of screen regions assigned to each rasterizer [S2, unofficial].
*   **Primitive Distribution Strategy:** The method for assigning an arbitrary subset of primitives to each geometry processor [S2, unofficial].
*   Typical values are Not given in the sources.

**Edge Cases and Pitfalls:**
*   **Load Imbalance:** Primitives may be distributed unevenly over the screen, causing load imbalance between rasterizers [S2, unofficial].
*   **High Bandwidth Requirement:** The approach requires high bandwidth for the transfer of data between the geometry processing and rasterization stages [S2, unofficial].
*   **Primitive Overlap:** A single primitive may overlap multiple screen regions, requiring it to be sent to multiple rasterizers, which increases network traffic and potential redundancy [S2, unofficial].

## Subtopics

### Parallel Rendering (Hybrid Systems)
Hybrid systems combine shared and distributed memory features, such as clusters of multicore processors [S3, unofficial]. They often use image space partitioning schemes to distribute data across nodes [S3, unofficial]. Both data and image space may be partitioned to maintain a coherent distribution of work [S3, unofficial]. A key challenge is maintaining cache coherence; failure to do so progressively deteriorates overall system performance [S3, unofficial].

## Operating characteristics
*   **Performance:** Achieves approximately twice the frame rate of sort-first parallel rendering by reducing network delays associated with sending primitives before transformation [S1, unofficial].
*   **Strengths:** Reduces network delays compared to sort-first by avoiding pre-transformation distribution; leverages parallelism in both geometry processing and rasterization [S1, S2, unofficial].
*   **Limitations:** Requires high bandwidth for data transfer between geometry and rasterization stages; susceptible to load imbalance if primitives cluster unevenly on the screen [S2, unofficial].
*   **Suitability:** It is suitable for clusters of high-end graphics machines where network bandwidth is sufficient [S2, unofficial].

## Background
Sort-middle rendering was developed as an improvement over sort-first rendering, which suffered from network latency issues when distributing primitives before transformation [S1, unofficial]. Williams and Hiromoto modified the Chromium system to implement sort-middle, allowing it to achieve better performance [S1, unofficial]. It became a popular approach due to the availability of high-end graphics machines [S2, unofficial].
