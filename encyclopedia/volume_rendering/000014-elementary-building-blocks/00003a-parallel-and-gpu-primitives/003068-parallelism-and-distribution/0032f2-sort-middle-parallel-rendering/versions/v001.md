# Sort-middle Parallel Rendering


## Overview
Sort-middle parallel rendering is a parallelization strategy that distributes screen-space primitives between the geometry preprocessing (transformation and lighting) stage and the rasterization stage [S2, unofficial]. It assigns an arbitrary subset of primitives to each geometry processor and a portion of the screen to each rasterizer [S2, unofficial]. This approach is distinct from sort-first, which distributes primitives before transformation, and sort-last, which distributes pixels after rasterization [S1, unofficial]. Sort-middle was developed to mitigate the network delays associated with sort-first by allowing geometry processing to occur in parallel, achieving approximately twice the frame rate of sort-first in systems like Chromium [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A set of 3D primitives (e.g., triangles, quads) and a screen partitioning scheme.
*   **Output:** A composited final image.

**Data Structures:**
*   **Primitive List:** A collection of primitives, each containing vertex data and metadata (e.g., bounding box, ID).
*   **Screen Partition Map:** A data structure defining which rasterizer is responsible for which region of the screen (e.g., a grid or arbitrary partition).
*   **Primitive Queue:** A buffer holding primitives assigned to a specific rasterizer for rasterization.

**Steps:**
1.  **Geometry Processing:** Each geometry processor receives an arbitrary subset of the total primitives [S2, unofficial]. It performs transformation (model-view-projection) and lighting calculations on these primitives [S2, unofficial].
2.  **Distribution/Sorting:** The transformed primitives are sorted or distributed based on their screen-space position. Each primitive is sent to the rasterizer responsible for the screen region it overlaps [S2, unofficial].
3.  **Rasterization:** Each rasterizer processes its assigned subset of primitives, generating color and depth values for the pixels in its assigned screen region [S2, unofficial].
4.  **Compositing:** The results from all rasterizers are combined to form the final image. If primitives overlap across rasterizer boundaries, depth buffering or alpha compositing is used to resolve visibility [S1, unofficial].

**Pseudocode:**
```python
# Global configuration
screen_regions = define_screen_partitions(num_rasterizers)
primitive_list = get_all_primitives()

# Step 1: Geometry Processing (Parallel)
# Each geometry processor handles a subset of primitives
geometry_results = []
for proc_id in range(num_geometry_processors):
    # Assign arbitrary subset of primitives
    local_primitives = primitive_list[proc_id * chunk_size : (proc_id + 1) * chunk_size]
    
    # Transform and light primitives
    transformed_primitives = []
    for prim in local_primitives:
        transformed_prim = transform_and_light(prim)
        transformed_primitives.append(transformed_prim)
    
    geometry_results.append(transformed_primitives)

# Step 2: Distribution to Rasterizers
# Collect all transformed primitives and distribute based on screen region
rasterizer_queues = [[] for _ in range(num_rasterizers)]

for transformed_prim in geometry_results:
    for prim in transformed_prim:
        # Determine which screen region(s) the primitive overlaps
        overlapping_regions = get_overlapping_regions(prim.bounding_box, screen_regions)
        
        # Send primitive to the appropriate rasterizer(s)
        for region_id in overlapping_regions:
            rasterizer_queues[region_id].append(prim)

# Step 3: Rasterization (Parallel)
final_images = []
for rasterizer_id in range(num_rasterizers):
    # Rasterize the assigned primitives
    image = rasterize_primitives(rasterizer_queues[rasterizer_id], screen_regions[rasterizer_id])
    final_images.append(image)

# Step 4: Compositing
# Combine images from all rasterizers
final_image = composite_images(final_images, screen_regions)
return final_image
```

**Edge Cases and Pitfalls:**
*   **Load Imbalance:** Primitives may be distributed unevenly over the screen, causing some rasterizers to have significantly more work than others [S2, unofficial].
*   **High Bandwidth Requirement:** Significant data transfer is required between the geometry processing stage and the rasterization stage, necessitating high bandwidth networks [S2, unofficial].
*   **Primitive Overlap:** A single primitive may overlap multiple screen regions, requiring it to be sent to multiple rasterizers, which can increase communication overhead [S2, unofficial].

## Subtopics

### Parallel Rendering (Hybrid Systems)
Hybrid systems mix shared and distributed memory features, such as clusters of multicore processors [S3, unofficial]. They distribute data across nodes using an image space partitioning scheme and may partition both data and image space to keep a coherent distribution of work [S3, unofficial]. A key challenge is maintaining cache coherence throughout execution; failure to do so progressively deteriorates overall system performance [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** The geometry processing stage scales with the number of primitives and processors. The distribution and compositing stages add overhead.
*   **Memory Complexity:** Requires memory for storing transformed primitives and intermediate rasterization buffers.
*   **Performance:** Achieves approximately twice the frame rate of sort-first parallel rendering by reducing network delays associated with sending primitives before transformation [S1, unofficial].
*   **Strengths:** Allows parallel geometry processing, which can be a bottleneck in sort-first approaches.
*   **Limitations:** Suffers from load imbalance if primitives cluster in certain screen regions. Requires high bandwidth for data transfer between geometry and rasterization stages [S2, unofficial].
*   **When to Use:** Suitable for systems with high-end graphics machines where geometry processing is a significant portion of the rendering pipeline and network bandwidth is sufficient [S2, unofficial].
*   **When Not to Use:** Not ideal for systems with limited network bandwidth or where primitives are highly clustered, leading to severe load imbalance.

## Background
Sort-middle parallel rendering was developed as an improvement over sort-first parallel rendering. The Chromium system initially used sort-first, but network delays made it inefficient [S1, unofficial]. Williams and Hiromoto modified Chromium to use the sort-middle approach, which distributes primitives between the transformation/lighting stage and the rasterization stage [S1, unofficial]. This approach became popular due to the availability of high-end graphics machines [S2, unofficial]. It is often compared with sort-last approaches, which distribute pixels during rasterization and scale well with the number of primitives but require high bandwidth for pixel transfers [S2, unofficial].
