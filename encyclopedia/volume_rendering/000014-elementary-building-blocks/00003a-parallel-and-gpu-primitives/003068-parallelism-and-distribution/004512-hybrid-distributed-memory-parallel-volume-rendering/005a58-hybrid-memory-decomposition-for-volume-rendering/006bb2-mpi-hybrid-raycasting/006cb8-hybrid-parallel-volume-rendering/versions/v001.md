# Hybrid Parallel Volume Rendering

Also called: Hybrid Memory Decomposition for Volume Rendering, Hybrid-parallel implementation, MPI+OpenMP, MPI+pthreads, MPI-hybrid Raycasting, hybrid parallelism for volume rendering, hybrid-memory implementation

## Overview
Hybrid Parallel Volume Rendering is a parallel programming model that combines distributed-memory parallelism (MPI) for inter-node communication with shared-memory parallelism (threads/GPU) for intra-node computation [S1, S2]. It solves the problem of diminishing returns and high communication costs associated with extreme concurrency in pure MPI implementations by reducing the number of MPI participants [S1, S2]. Unlike pure MPI approaches where raycasting runs serially on each task, this method multi-threads the raycasting step within each task using image-parallel decomposition, significantly improving performance, reducing memory footprint, and lowering communication bandwidth requirements [S1, S2].

## How it works
The method partitions the source data volume $S$ among $n$ parallel tasks (MPI PEs), where each PE reads $1/n$ of $S$ [S1, S2]. The process consists of three main phases: Raycasting, Compositing, and Gathering [S1, S2].

### Inputs and Outputs
*   **Input:** Source data volume $S$ (structured rectilinear grid), camera parameters, transfer function.
*   **Output:** Final composited image gathered at PE 0 [S1, S2].

### Data Structures
**Image Fragment:**
Each fragment generated during raycasting contains the following fields [S2]:
*   `x`: Pixel x-coordinate.
*   `y`: Pixel y-coordinate.
*   `R, G, B`: Color components.
*   $\alpha$: Opacity.
*   `z`: Eye-coordinate depth where the ray penetrates the data block [S2].

**Ghost Data:**
Two layers of ghost data are required around each data subdomain [S2]:
1.  First layer: For trilinear interpolation of sampled values.
2.  Second layer: For computing the gradient field using central differences [S2].

### Parameters
*   $n$: Total number of MPI ranks [S1].
*   $T$: Number of threads per MPI PE. In the reference implementation on six-core AMD Opteron processors, $T=6$ [S2].
*   Image Tile Size: $32 \times 32$ pixels. This size was found to produce consistently better performance than other tile sizes [S2].
*   Interpolation: Trilinear interpolation [S2].
*   Shading: Phong-style shader [S2].

### Steps

1.  **Data Partitioning:** Distribute source data volume $S$ across $n$ MPI PEs. Each PE loads a disjoint block of data [S1, S2]. In the hybrid case, a data block is shared among $T$ threads, using $1/T$ as many MPI PEs as the MPI-only case [S2].
2.  **Raycasting (Multi-threaded):**
    *   Each MPI PE launches $T$ threads [S2].
    *   The image is divided into small tiles (e.g., $32 \times 32$ pixels) distributed among the $T$ threads [S2].
    *   Tiles are assigned dynamically to threads to minimize load imbalance [S2].
    *   Each thread performs raycasting on its assigned tiles:
        *   Test for ray-triangle intersections along the data block's bounding box [S2].
        *   If a hit occurs, integrate the ray by sampling data values at a fixed interval [S2].
        *   Apply the transfer function to sampled values [S2].
        *   Aggregate color and opacity into a fragment using the "over" operator (see Formula) [S2].
        *   Store the fragment with the fragment's $z$-coordinate (entry point into the block) [S2].
    *   *Note:* Early ray termination adds a 5% overhead due to conditional checks; it may be disabled if the dataset/transfer function ensures at least one block has no early terminations [S2].
3.  **Compositing (Hybrid):**
    *   Partition the pixels of the final image amongst the PEs [S2].
    *   **Intra-node Gathering:** Only one thread per socket participates in compositing. This thread gathers fragments from all other threads in the same socket, packs them into a single buffer [S2].
    *   **Inter-node Exchange:** Execute an all-to-all communication step using `MPI_Alltoallv` to exchange each packed fragment from the generating PE to the PE owning the region of the image where the fragment lies [S2].
    *   **Final Composition:** Each PE performs final compositing for each pixel in its region using the "over" operator [S2].
4.  **Gathering:** Gather the completed image to PE 0 for display or I/O to storage [S1, S2].

### Formula
The integration uses the "over" operator [S2]:
$$
C_o = C_s + (1 - \alpha_s) C_b
$$
$$
\alpha_o = \alpha_s + (1 - \alpha_s) \alpha_b
$$
Where:
*   $C_o, \alpha_o$: Output color and opacity.
*   $C_s, \alpha_s$: Source (sampled) color and opacity.
*   $C_b, \alpha_b$: Background (accumulated) color and opacity [S2].

# Hybrid Parallel Volume Rendering Implementation
# Assumes MPI is initialized, and each rank has a disjoint block of data 'data_block'
# and access to ghost layers.

def hybrid_volume_rendering(rank, num_ranks, data_block, image_width, image_height, transfer_function):
    # 1. Thread Configuration
    # On a 6-core node, T=6. One thread per socket handles compositing.
    T = 6 
    threads = []
    fragments = [] # Local list to store fragments generated by this PE's threads

    # 2. Raycasting Phase (Shared Memory)
    # Divide image into 32x32 tiles
    tile_size = 32
    tiles = generate_tiles(image_width, image_height, tile_size)
    
    # Dynamic work assignment: distribute tiles among T threads
    # Using a simple queue-based approach for pseudocode clarity
    tile_queue = list(tiles)
    
    def raycast_thread(thread_id):
        local_fragments = []
        while tile_queue:
            try:
                tile = tile_queue.pop(0)
            except IndexError:
                break
            
            # Raycast for each pixel in the tile
            for y in range(tile.y_start, tile.y_end):
                for x in range(tile.x_start, tile.x_end):
                    # Compute ray origin and direction for pixel (x, y)
                    ray_origin, ray_direction = compute_ray(x, y, camera_params)
                    
                    # Test intersection with data block bounding box
                    if not intersect_box(ray_origin, ray_direction, data_block.bounds):
                        continue
                    
                    # Initialize compositing variables
                    alpha_acc = 0.0
                    color_acc = (0.0, 0.0, 0.0)
                    
                    # Integrate along ray
                    # Fixed step size sampling
                    t = ray_entry_t
                    while t < ray_exit_t and alpha_acc < 1.0:
                        # Sample data value using trilinear interpolation
                        # Requires ghost layers for boundary conditions
                        value = sample_data(data_block, ray_origin + t * ray_direction)
                        
                        # Apply transfer function
                        color_s, alpha_s = transfer_function(value)
                        
                        # Composite using "over" operator
                        # C_o = C_s + (1 - alpha_s) * C_b
                        # alpha_o = alpha_s + (1 - alpha_s) * alpha_b
                        color_acc = color_s + (1.0 - alpha_s) * color_acc
                        alpha_acc = alpha_s + (1.0 - alpha_s) * alpha_acc
                        
                        # Advance ray (fixed step)
                        t += step_size
                    
                    # Create fragment
                    # z-coordinate is the entry point into the block
                    z_coord = dot_product(ray_origin, ray_direction) + step_size * (t - step_size) # Approximation for pseudocode
                    fragment = Fragment(x=x, y=y, r=color_acc[0], g=color_acc[1], b=color_acc[2], alpha=alpha_acc, z=z_coord)
                    local_fragments.append(fragment)
        
        return local_fragments

    # Launch threads
    for i in range(T):
        t = Thread(target=raycast_thread, args=(i,))
        threads.append(t)
        t.start()
    
    # Wait for all threads to finish and collect fragments
    for t in threads:
        t.join()
        fragments.extend(t.result) # Assuming result is stored in thread object

    # 3. Compositing Phase
    # Partition final image pixels among PEs
    my_pixel_region = partition_image_pixels(rank, num_ranks, image_width, image_height)
    
    # Intra-node gathering: One thread per socket gathers fragments
    # For pseudocode, assume rank 0 of the socket group handles this
    if rank % (num_cores_per_socket) == 0:
        # Gather fragments from all threads in this socket
        packed_buffer = pack_fragments(fragments)
        
        # Determine which PEs own the regions for these fragments
        # This requires knowing the pixel-to-PE mapping
        dest_ranks = get_dest_ranks_for_fragments(fragments, my_pixel_region)
        
        # All-to-all exchange using MPI_Alltoallv
        # Send packed_buffer to dest_ranks, receive from all ranks
        received_buffers = mpi_alltoallv(packed_buffer, dest_ranks)
        
        # Final compositing for pixels in my region
        final_image = create_empty_image(image_width, image_height)
        for buffer in received_buffers:
            for frag in unpack_fragments(buffer):
                if frag.x in my_pixel_region and frag.y in my_pixel_region:
                    # Composite fragment into final_image at (frag.x, frag.y)
                    # Note: Fragments must be sorted by z-depth for correct over-operator application
                    pass 
        # Note: The actual sorting and compositing logic for the final image 
        # is distributed. Each PE composites only its assigned pixels.
        # The 'received_buffers' contain fragments destined for this PE's region.
        # These fragments must be sorted by z before compositing.
        sort_fragments_by_z(received_buffers)
        for frag in received_buffers:

### Edge Cases and Pitfalls
*   **NUMA Penalties:** Sharing data across sockets results in non-uniform memory access (NUMA) penalties (estimated 5-10% of raycasting time). To avoid this, threads should run on cores of a single processor/socket [S2].
*   **Early Ray Termination:** Adds a 5% overhead due to conditional statements. It may be disabled if the dataset guarantees no early terminations for at least one block [S2].
*   **Communication Dominance:** At high concurrency, compositing becomes the dominant cost. Reducing MPI participants via hybrid parallelism mitigates message latency and overhead [S1, S2].

## Operating characteristics
*   **Time Complexity:** Raycasting scales nearly linearly as it involves no inter-processor communication [S2]. Compositing involves `MPI_Alltoallv` communication, which is reduced in hybrid mode by aggregating messages per socket [S2].
*   **Memory Complexity:** MPI-hybrid uses significantly less memory than MPI-only. At 216,000 cores, MPI-only used 37,023MB aggregate memory, while MPI-hybrid used 2,892MB (nearly 12x less) [S2]. Per-PE runtime overhead was 82MB for hybrid vs 176MB for MPI-only [S2].
*   **Communication:** Ghost data storage and exchange are reduced by roughly 40% in hybrid implementations due to fewer, larger blocks [S2].
*   **Strengths:** Improved performance at high concurrency, reduced memory footprint, lower communication bandwidth usage [S2].
*   **Limitations:** Complexity of implementation (managing both MPI and threads); load imbalance in raycasting if tiles are not distributed dynamically [S2].
*   **When to use:** Large-scale volume rendering on multi-core clusters where communication overhead in pure MPI becomes a bottleneck [S1, S2].
*   **When not to use:** Small-scale problems where the overhead of thread management and hybrid logic outweighs the benefits [S2].

## Background
Hybrid Parallel Volume Rendering was developed to address the challenges of scaling volume rendering on multi- and many-core systems. Traditional MPI-only implementations faced diminishing returns and high communication costs as core counts increased [S1]. The method was demonstrated on the JaguarPF supercomputer at Oak Ridge National Laboratory, achieving weak and strong scaling studies up to 216,000 cores and datasets as large as 12.2 trillion cells [S1, S2]. It builds on Levoy's raycasting method [S1, S2] and previous distributed-memory implementations [S1].
