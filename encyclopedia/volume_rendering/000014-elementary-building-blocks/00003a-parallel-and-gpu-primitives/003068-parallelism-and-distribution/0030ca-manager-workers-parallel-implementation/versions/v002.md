# Manager/Workers Parallel Implementation

Also called: LSF-HPC Cluster Implementation, LSF-HPC worker model, Master/Slave Worker Architecture, Task-based parallelism

## Overview
The Manager/Workers Parallel Implementation is a distributed task-scheduling architecture designed for load-balanced execution on clusters where processor availability varies over time [S1, S2]. It solves the problem of coordinating independent computational tasks (such as isosurface extraction or volume rendering) across distant workers by centralizing state management in a single manager process [S1, S2]. Unlike sibling methods that rely on static partitioning or hardware-specific synchronization primitives, this approach uses a dynamic task queue where workers request work and the manager assigns tasks based on global knowledge of data boundaries and worker status [S1, S2].

## How it works
**Inputs and Outputs:**
*   **Input:** A volumetric dataset (e.g., a grid of voxels or AMR blocks) and a set of available worker processes [S1, S2].
*   **Output:** A final aggregated surface mesh or rendered image [S1, S2].

**Data Structures:**
*   **Task:** A message object containing:
    *   `type`: Enum {EXTRACT, SEND, MERGE, FINISHED} [S1, S2].
    *   `worker_id`: Unique identifier for the target worker [S1, S2].
    *   `target_id`: (Optional) Identifier for the destination worker in SEND tasks [S1].
    *   `block_id`: (Optional) Identifier for the data sub-block in EXTRACT tasks [S1].
*   **Worker State:** Each worker maintains a local surface mesh (initially empty) [S1, S2].
*   **Manager State:** The manager maintains a global view of:
    *   Extracted blocks [S1].
    *   Worker surface availability [S1].
    *   Topological neighbors of workers/blocks [S1].

**Parameters:**
*   **Task Scheduler:** Typically Platform LSF-HPC or similar HPC job schedulers to dispatch tasks on the distant grid [S1, S2].
*   **Worker Count:** Can range from 1 (sequential fallback) to $N$ (cluster size) [S2].

**Algorithm Steps:**

1.  **Initialization:** The manager identifies all available workers and the full set of data blocks [S1, S2]. Workers start in an infinite loop waiting for tasks [S1, S2].

2.  **Worker Loop:** Each worker executes the following logic [S1, S2]:
    *   Request a task from the manager.
    *   Execute the task based on its type:
        *   **EXTRACT:** Perform the core computation (e.g., `tandem(E0)`) on the assigned sub-block. Append the resulting local surface to the worker's current mesh. Note: For block borders, a "time lag" method may be used to prevent edge collapse by preserving vertices on boundaries before simplification [S1].
        *   **SEND:** Send the current accumulated surface mesh to the specified `target_id`. Clear the local surface memory after sending [S1].
        *   **MERGE:** Receive a surface mesh from another worker (or the manager) and merge it with the current local surface. Simplify the combined surface and dump finished components if applicable [S1].
        *   **FINISHED:** Set a local `finished` flag to true and terminate the loop [S1].

3.  **Manager Loop:** The manager iterates until all data is processed and all workers are finished [S1, S2]:
    *   Wait for a task request from a worker with ID `id`.
    *   Check conditions in priority order [S1]:
        1.  **Has Surface:** If the worker `id` currently holds a surface mesh that needs aggregation, send a `MERGE` task. This task likely includes the ID of the worker to merge with (determined by the manager's knowledge of topology) [S1].
        2.  **Has Neighbor:** If the worker has no surface but has topological neighbors that might hold relevant data, send a `SEND` task with a `target_id` to forward its current (empty or partial) state or request data [S1]. *Note: Sources indicate SEND is used to send current mesh to target; the logic implies routing intermediate results.*
        3.  **Has Block:** If there are un-extracted data blocks, send an `EXTRACT` task assigning a specific block to the worker [S1].
        4.  **Else:** Send a `FINISHED` task to terminate the worker [S1].

**Pseudocode:**

```python
# Worker Process
def worker_process(worker_id, task_queue):
    finished = False
    local_surface = EmptyMesh()
    
    while not finished:
        # Block until a task is received from the manager
        task = task_queue.receive()
        
        if task.type == "EXTRACT":
            # Extract surface from the assigned sub-block
            # E0 is the extraction algorithm (e.g., extended tandem)
            new_mesh = extract_surface(task.block_id, algorithm=E0)
            local_surface.append(new_mesh)
            
        elif task.type == "SEND":
            # Send current surface to target worker
            # The manager determines the target_id based on topology
            task_queue.send(task.target_id, local_surface)
            local_surface = EmptyMesh() # Clear memory
            
        elif task.type == "MERGE":
            # Receive mesh from another worker and merge
            incoming_mesh = task_queue.receive_mesh()
            local_surface.merge(incoming_mesh)
            # Simplify and dump finished components if needed
            local_surface.simplify()
            
        elif task.type == "FINISHED":
            finished = True

# Manager Process
def manager_process(worker_ids, data_blocks, task_queues):
    # Global state maintained by manager
    extracted_blocks = set()
    worker_surfaces = {wid: None for wid in worker_ids}
    # Topology map: which workers/blocks are neighbors
    topology = build_topology(data_blocks) 
    
    finished_workers = set()
    
    while len(finished_workers) < len(worker_ids):
        # Wait for any worker to request a task
        requesting_worker_id = task_queue.wait_for_request()
        
        # Priority 1: Merge if worker has surface
        if worker_surfaces[requesting_worker_id] is not None:
            # Find a target to merge with (e.g., a neighbor or the manager)
            target_id = find_merge_target(requesting_worker_id, topology)
            task = Task(type="MERGE", target_id=target_id)
            task_queues[requesting_worker_id].send(task)
            
        # Priority 2: Send if worker has neighbor but no surface to merge?
        # Note: Source logic says "If has neighbor(id) then send SEND".
        # This implies routing or handoff even if surface is empty or being prepared.
        elif has_neighbor(requesting_worker_id, topology):
            target_id = find_neighbor(requesting_worker_id, topology)
            task = Task(type="SEND", target_id=target_id)
            task_queues[requesting_worker_id].send(task)
            
        # Priority 3: Extract if blocks remain
        elif len(extracted_blocks) < len(data_blocks):
            block_id = get_next_unextracted_block(data_blocks, extracted_blocks)
            task = Task(type="EXTRACT", block_id=block_id)
            task_queues[requesting_worker_id].send(task)
            
        # Priority 4: Finish
        else:
            task = Task(type="FINISHED")
            task_queues[requesting_worker_id].send(task)
            finished_workers.add(requesting_worker_id)
```

**Edge Cases and Pitfalls:**
*   **Precision/Boundaries:** When extracting from sub-blocks, borders must be handled carefully. The "time lag" method is used to preserve vertices on block boundaries to ensure mesh continuity and quality after simplification [S1].
*   **Statelessness:** Workers are stateless regarding global progress; they do not know which blocks are processed or who holds which data. All state is in the manager [S2].
*   **Single Worker Mode:** The algorithm degrades gracefully to a single worker, which processes blocks sequentially [S2].

## Subtopics

### Python Multiprocessing with Dynamic Load Balancing
A variant implementation using Python's `multiprocessing` module for dynamic load balancing [S3, unofficial]. It employs a master process that dynamically sends work to available worker processes until rendering is complete [S3, unofficial]. To optimize CPU usage, it starts more processes than available processors, relying on the OS task scheduler to map processes to idle cores [S3, unofficial]. Data distribution uses a "sort last" strategy [S3, unofficial]. Pitfalls include: OS-defined process limits (e.g., on 64-core machines), lack of shared memory for NumPy arrays (requiring separate arrays per process, complicating load balancing), and limitation to a single HPC node unless MPI is used, which restricts total RAM and caching capabilities compared to distributed clusters [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** Depends on the task scheduler's efficiency and network latency. The manager's decision loop is $O(1)$ per request, but global state updates are required.
*   **Memory Complexity:** Distributed across workers. Each worker stores only its local surface mesh, reducing peak memory usage compared to brute-force approaches [S1]. The manager stores global metadata, which is minimal.
*   **Performance:** Critical bottleneck is often I/O (reading large datasets) rather than computation [S3, unofficial]. The architecture allows for efficient load balancing on clusters with varying processor availability [S1, S2].
*   **Strengths:** Adaptable to dynamic cluster resources; simple worker implementation; no shared memory requirements between workers [S1, S2][S3, unofficial].
*   **Limitations:** Manager becomes a bottleneck if task requests are frequent; network overhead for sending meshes; OS scheduler limitations in Python variant [S3, unofficial].

## Background
The architecture was proposed for parallel isosurface extraction on very large geophysical datasets [S1]. It was designed to work with Platform LSF-HPC, a task scheduler for high-performance computing clusters, to handle time-varying processor allocations [S1, S2]. The approach extends the "tandem algorithm" for isosurface extraction, incorporating simplification and merging steps [S1, S2]. It has also been adapted for volume rendering of AMR (Adaptive Mesh Refinement) simulations, where dynamic load balancing is crucial due to irregular data distribution [S3, unofficial].
