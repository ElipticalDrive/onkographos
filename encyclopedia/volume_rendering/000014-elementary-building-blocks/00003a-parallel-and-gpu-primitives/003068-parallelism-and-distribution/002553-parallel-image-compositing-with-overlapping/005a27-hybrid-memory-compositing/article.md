# Hybrid-memory Compositing

Also called: Compositing Phase, Fragment exchange, Image assembly

## Overview
Hybrid-memory compositing is a parallel image assembly strategy that reduces communication overhead by aggregating ray-casting fragments in shared memory before exchanging them across the network [S1]. It solves the bottleneck of high message counts in distributed-memory compositing by allowing threads within a node to merge data locally, thereby sending fewer, larger blocks to the compositing tasks [S1]. It differs from pure distributed-memory approaches by leveraging intra-node shared memory to reduce the number of MPI messages by approximately 6x [S1].

## How it works
**Inputs:**
*   Ray-casting fragments generated by rendering tasks [S1].
*   A subset of tasks designated as compositors [S1].
*   Image space partitioning scheme defining which compositor owns which region [G].

**Outputs:**
*   Final composited image components on the root task [S1].

**Data Structures:**
*   **Fragment Buffer:** Stores ray-casting results aggregated in memory shared by six threads [S1].
*   **MPI Buffers:** Temporary structures for `MPI_Alltoallv` and `MPI_Reduce`. Overallocation occurs if the compositing subset is too small relative to the image size [S1].

**Steps:**
1.  **Local Aggregation:** Threads within a node (specifically, a group of six threads as observed in the reference implementation) aggregate fragments in shared memory [S1]. This reduces the volume of data sent over the network by performing partial compositing or merging before exchange [S1].
2.  **Fragment Exchange:** Use `MPI_Alltoallv` to move fragments from the task where they originated during raycasting to the compositing task that owns their region of image space [S1]. The hybrid-memory implementation exchanges less fragment data because its larger data blocks allow for more compositing to take place during ray integration [S1].
3.  **Image Reduction:** Reduce the final image components to the root task using `MPI_Reduce` for assembly and output to a file or display [S1]. One-sixth as many hybrid-memory tasks participate in this reduction compared to distributed-memory tasks, improving performance [S1].
4.  **Compositor Selection:** Use a subset of tasks for compositing rather than all tasks [S1]. The ratio of compositors to renderers is tuned based on scaling behavior [S1].

**Parameters:**
*   **Compositor Subset Size:**
    *   For strong and weak-dataset scaling: Optimal range is 2,000 to 8,000 tasks [S1].
    *   For weak scaling: Optimal range is 2,000 to 30,000 tasks [S1].
*   **Thread Grouping:** Aggregation occurs in memory shared by six threads [S1].

**Edge Cases and Pitfalls:**
*   **Weak Scaling Overallocation:** In weak scaling, setting the compositing subset too small leads to overallocation from temporary data structures and MPI buffers because additional data is concentrated in fewer compositors [S1].
*   **Inflection Points:** Performance inflection points exist due to interconnect fabric characteristics. For hybrid memory, the inflection point is at 13,824-way concurrency (strong/weak-dataset) and higher for weak scaling [S1].

## Subtopics

### [MPI-hybrid Compositing](20911-mpi-hybrid-compositing.md)
MPI-hybrid compositing is a parallel image compositing optimization that reduces communication overhead by aggregating fragments in memory shared by six threads before exchanging them between processing elements (PEs). It sets itself apart from pure MPI-only compositing by leveraging hybrid parallelism to perform more compositing during ray integration, thereby sending fewer and smaller messages.

## Operating characteristics
**Time and Memory Complexity:**
*   **Message Count:** Hybrid-memory uses on average about 6x fewer messages than distributed-memory during fragment exchange [S1].
*   **Data Volume:** Exchanges less fragment data due to larger data blocks allowing more compositing during ray integration [S1].

**Measured Performance:**
*   **Strong Scaling (216,000-way concurrency):**
    *   Best compositing time: 0.35s (4,500 compositors) [S1].
    *   Distributed memory compositing time: 1.06s (6,750 compositors) [S1].
    *   Hybrid memory is 3x faster in compositing [S1].
    *   Total render time: 0.56s (hybrid) vs 1.25s (distributed), a 2.2x speedup [S1].
    *   Rendering time was ~0.2s for both; compositing dominated total time [S1].
*   **Weak Scaling:**
    *   Optimal subset range: 2,000 to 30,000 compositing tasks [S1].
    *   Inflection point arises at higher concurrency than in strong scaling [S1].
*   **Small Scale (448-way concurrency, 4608^3 dataset):**
    *   Minimum compositing time: 0.15s (median 0.19s) [S1].
    *   Raycasting time: 1.18s [S1].

**Strengths and Limitations:**
*   **Strengths:** Significantly reduced message count and data volume; superior compositing performance at high concurrency (216,000+ cores) [S1].
*   **Limitations:** Requires careful tuning of the compositor subset size; small subsets in weak scaling cause memory overallocation [S1]. Gains are less pronounced when raycasting dominates (e.g., weak scaling with large datasets) [S1].

**When to Use:**
*   High-concurrency environments (e.g., >13,824 cores) where communication overhead dominates [S1].
*   Systems with hybrid memory architectures (multi-core nodes with shared memory) [G].

**When Not to Use:**
*   Low-concurrency scenarios where raycasting dominates and compositing overhead is negligible [S1].
*   Environments where the interconnect fabric does not benefit from fewer, larger messages [S1].

## Background
Hybrid-memory compositing was analyzed in the context of large-scale volume rendering on multi-core and many-core systems [S1]. The approach builds on observations by Peterka et al. that reducing the number of compositors at higher concurrencies increases overall performance [S1]. The specific implementation details and performance metrics (6x fewer messages, 2.2x total speedup at 216,000 cores) are derived from studies on systems like JaguarPF and Longhorn [S1].
