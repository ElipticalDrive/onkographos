# Parallel Image Compositing with Overlapping

Also called: Distributed Image Compositing, Ray Segment Delivery

## Overview
Parallel Image Compositing with Overlapping is a distributed rendering strategy where ray segments are transmitted to their responsible processors immediately upon generation, rather than waiting for local ray-casting to complete [S1, unofficial]. This approach solves the network congestion problem inherent in non-overlapping methods, where all processors send large batches of data simultaneously at the end of the frame [S1, unofficial].

## How it works
**Inputs:**
- Local volume data partition assigned to the processor [S1, unofficial].
- Ray generation parameters (camera position, orientation, step size) [G].
- Image decomposition scheme (typically horizontal strips) [S1, unofficial].

**Outputs:**
- Final subimage corresponding to the processor's assigned pixel region [S1, unofficial].

**Data Structures:**
- **Ray Buffer:** A two-dimensional array of linked lists. The dimensions correspond to the processor's assigned portion of the image plane. Each entry points to a linked list of ray segments [S1, unofficial].
- **Ray Segment:** Contains color, opacity, and depth/position information required for compositing [G].

**Steps:**
1. **Initialization:** Each processor allocates an empty Ray Buffer according to the image decomposition scheme. The buffer size is dynamic; it grows as ray segments arrive [S1, unofficial].
2. **Ray Casting and Immediate Delivery:** The processor generates ray segments as it traverses its local volume data. As soon as a ray segment is generated, it is grouped with other segments destined for the same pixel. These groups are sent immediately to the responsible processor via point-to-point communication. This overlaps communication with computation [S1, unofficial].
3. **Sorting:** Upon receipt, each processor sorts incoming ray segments into the local Ray Buffer. Segments are inserted into the linked list pointed to by the corresponding pixel address. Sorting ensures segments are ordered by visibility (depth) for correct compositing [S1, unofficial].
4. **Final Compositing:** After all local ray-casting is complete and all segments have been received and sorted, the processor composites the segments in order for each pixel. Standard front-to-back compositing is applied using the sorted lists [G].
5. **Result Submission:** The final subimage generated by the processor is sent back to the host computer [S1, unofficial].

**Pseudocode:**

```python
class RaySegment:
    def __init__(self, color, opacity, depth):
        self.color = color      # List of 3 floats [R, G, B]
        self.opacity = opacity  # Float alpha
        self.depth = depth      # Float distance from camera

class LinkedListNode:
    def __init__(self, segment):
        self.segment = segment
        self.next = None

class RayBuffer:
    def __init__(self, width, height):
        self.width = width
        self.height = height
        # 2D array of linked list heads
        self.buckets = [[None for _ in range(width)] for _ in range(height)]

    def add_segment(self, pixel_x, pixel_y, segment):
        # Insert segment into the linked list for the specific pixel
        # Maintains sorted order by depth (visibility)
        node = LinkedListNode(segment)
        head = self.buckets[pixel_y][pixel_x]
        
        # Insertion sort for linked list
        if head is None or head.segment.depth >= segment.depth:
            node.next = head
            self.buckets[pixel_y][pixel_x] = node
        else:
            current = head
            while current.next is not None and current.next.segment.depth < segment.depth:
                current = current.next
            node.next = current.next
            current.next = node

def compositing_overlapping(image_width, image_height, rows_per_proc, segments_by_pixel):
    # 1. Initialize Local Ray Buffer
    local_buffer = RayBuffer(image_width, rows_per_proc)
    
    # 2. Populate Buffer (Simulates receiving and sorting segments)
    for y_local in range(rows_per_proc):
        for x in range(image_width):
            pixel_y_global = y_local
            for seg in segments_by_pixel.get((x, pixel_y_global), []):
                local_buffer.add_segment(x, y_local, seg)
                
    # 3. Final Compositing
    final_subimage = [[[0.0, 0.0, 0.0] for _ in range(image_width)] for _ in range(rows_per_proc)]
    
    for y_local in range(rows_per_proc):
        for x in range(image_width):
            head = local_buffer.buckets[y_local][x]
            r, g, b, a = 0.0, 0.0, 0.0, 0.0
            
            # Front-to-back compositing
            while head is not None:
                seg = head.segment
                contrib = seg.opacity * (1.0 - a)
                r += contrib * seg.color[0]
                g += contrib * seg.color[1]
                b += contrib * seg.color[2]
                a += contrib
                head = head.next
            
            final_subimage[y_local][x] = [r, g, b]
            
    return final_subimage
```

**Parameters:**
- **Image Partitioning:** Image space is partitioned evenly into horizontal strips for simplicity [S1, unofficial].
- **Performance Gain:** Overlapping ray casting and compositing improves overall image compositing performance by as much as 40% compared to non-overlapping approaches [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Variable Buffer Sizes:** Irregular shapes and data partitioning cause rays to enter/exit multiple faces, creating varying numbers of local ray segments. This leads to variable ray buffer sizes and linked list lengths, making memory management complex [S1, unofficial].
- **Network Congestion:** While overlapping reduces peak congestion, improper grouping of segments (sending one-by-one) can increase message overhead. Groups of ray segments should be sent immediately following the rendering of one locally visible face to balance message count and size [S1, unofficial].

## Subtopics

### Ray-segment Migration (RSM)
A variant where ray segments are migrated based on mesh-cell to processor assignment. Each processor traverses its local RayBuffer to packetize and gather ray-segment lists belonging to mesh-cells assigned to other processors into send-buffers. These are sent via point-to-point communication. Each processor then gathers all ray-segments belonging to pixels of mesh-cells assigned to itself. The task-to-task cut-edge component of the cutsize of the current partition of the remapping graph constitutes an upper bound on the total number of ray-segments communicated in this step for all pixel-assignment schemes [S2, unofficial].

### Hierarchical MPI Image Reduction
A method that combines per-process rendered sub-images into a single image using a binary tree reduction over MPI ranks. It computes tree depth $d = \lfloor \log_2(\text{size}) \rfloor$. Odd-ranked processes send their `rgba_image`, `max_time`, and `early_ray_terminations` to rank-1. In each tree level $i$, processes send their accumulated `image_list` to `destination_rank = rank - \lceil 2^d / (2^i) \rceil`. This repeats until $i=0$, where rank 0 holds the final composite image. The total number of MPI processes (`size`) determines the tree height [S3, unofficial].

## Operating characteristics
- **Time Complexity:** The compositing cost is relatively low compared to ray-tracing cost, assuming efficient preprocessing [S1, unofficial]. The sorting step adds overhead proportional to the number of segments per pixel.
- **Memory Complexity:** Memory usage is dominated by the Ray Buffer, which grows dynamically. The final size depends on the viewing position, the shape of the data volume, and the data partitioning scheme [S1, unofficial].
- **Performance:** Overlapping improves performance by up to 40% by reducing network congestion [S1, unofficial].
- **Strengths:** Reduces peak network load; hides communication latency behind computation.
- **Limitations:** Complex memory management due to variable buffer sizes; sorting overhead increases with irregular data [S1, unofficial].
- **When to Use:** Suitable for distributed-memory architectures with unstructured grid data where network congestion is a bottleneck.
- **When Not to Use:** Not ideal for regular data where image compositing order can be determined a priori and simpler batched approaches may suffice [S1, unofficial].

## Background
This method was developed to address the challenges of parallel volume ray-casting for unstructured-grid data on distributed-memory architectures. Traditional approaches separated local rendering from global compositing, leading to large message bursts. The overlapping approach was proposed to mitigate this by sending smaller messages throughout the rendering process. It builds on earlier efficient parallel image compositing algorithms for regular data but adapts them for irregular, unstructured domains where ray segments cannot be combined until all are received and sorted [S1, unofficial].
