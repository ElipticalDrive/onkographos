# Ray Compaction
## Overview
Ray Compaction is a parallel primitive that filters a list of active rays by removing terminated ones and compacting the survivors into a dense, contiguous buffer [S1, unofficial]. It solves the problem of sparse ray lists, ensuring subsequent processing stages operate only on valid rays [G]. It sets itself apart from siblings like [Ray Buffer Reordering](4073-ray-buffer-reordering.md) by serving as a foundational atomic-indexing step, whereas [In-Kernel Stream Compaction (InK-Compact)](6991-in-kernel-stream-compaction-ink-compact.md) avoids separate prefix-sum launches [G].

## How it works
**Inputs and Outputs:**
- Input: `rays_alive_old` (array of ray state/position data), `rays_t_old` (array of ray termination flags or distances), `N` (number of input rays) [S1, unofficial].
- Output: `rays_alive` (compacted ray data), `rays_t` (compacted flags), `alive_count` (total number of surviving rays) [S1, unofficial].

**Data Structures:**
- `rays_alive_old`: Array of size $N$ [S1, unofficial].
- `rays_t_old`: Array of size $N$. Rays are considered terminated if `rays_t_old[n] < 0` [S1, unofficial].
- `rays_alive`: Array of size $N$ (worst case) [S1, unofficial].
- `rays_t`: Array of size $N$ [S1, unofficial].
- `alive_counter`: Global atomic integer, initialized to 0 [S1, unofficial].

**Steps:**
1. Initialize `alive_counter` to 0 [S1, unofficial].
2. Launch a GPU kernel with one thread per input ray $n$ ($0 \le n < N$) [S1, unofficial].
3. Each thread $n$ checks if its ray is alive: `if rays_t_old[n] >= 0` [S1, unofficial].
4. If alive:
   a. Atomically increment `alive_counter` to obtain a unique new index: `index = atomicAdd(&alive_counter, 1)` [S1, unofficial].
   b. Copy the ray data: `rays_alive[index] = rays_alive_old[n]` [S1, unofficial].
   c. Copy the termination flag: `rays_t[index] = rays_t_old[n]` [S1, unofficial].
5. After kernel completion, read `alive_counter` to determine the number of valid rays in the output buffers [S1, unofficial].

**Pseudocode:**
```python
def atomic_add(counter, value):
    counter[0] += value
    return counter[0] - value

def ray_compaction_kernel(rays_alive_old, rays_t_old, rays_alive, rays_t, alive_counter, thread_id):
    if thread_id < len(rays_t_old):
        if rays_t_old[thread_id] >= 0:
            index = atomic_add(alive_counter, 1)
            rays_alive[index] = rays_alive_old[thread_id]
            rays_t[index] = rays_t_old[thread_id]

def compact_rays(rays_alive_old, rays_t_old, N):
    rays_alive = [0] * N
    rays_t = [0] * N
    alive_counter = [0]
    alive_count = 0

    for tid in range(N):
        ray_compaction_kernel(rays_alive_old, rays_t_old, rays_alive, rays_t, alive_counter, tid)

    alive_count = alive_counter[0]
    return rays_alive, rays_t, alive_count
```

**Parameters:**
- `N`: Number of input rays. Typical values depend on resolution (e.g., $W \times H$ for primary rays) [G].
- Termination Threshold: Defined by application logic; rays terminate when `rays_t_old[n] < 0` [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Precision:** Atomic operations on integers are precise. If `rays_t` stores floating-point termination distances, ensure the comparison logic (`>= 0`) aligns with the termination definition [G].
- **Boundaries:** Output buffers must be sized to $N$ to handle the case where all rays survive [G].
- **Degenerate Input:** If all rays terminate, `alive_count` is 0, and subsequent steps must handle empty buffers [G].

## Subtopics

### [Ray Buffer Reordering](4073-ray-buffer-reordering.md)
Uses double-buffering and atomic counters to reorder rays without prior sorting. Choose when maintaining strict input-output order is required without global reductions [G].

### [In-Kernel Stream Compaction (InK-Compact)](6991-in-kernel-stream-compaction-ink-compact.md)
Computes output indices entirely within a single kernel using bit-decomposition scans. Choose when minimizing kernel launch overhead and synchronization is critical [G].

## Operating characteristics
- **Time Complexity:** $O(N)$ work, where $N$ is the number of input rays [S1, unofficial]. The atomic add operation is the bottleneck, potentially causing contention [G].
- **Memory Complexity:** $O(N)$ for input and output buffers [S1, unofficial].
- **Performance:** Performance depends heavily on the ratio of alive rays. High contention on `alive_counter` can reduce throughput [G].
- **Strengths:** Simple to implement; low memory overhead compared to sorting-based methods [G].
- **Limitations:** Atomic contention can limit scalability on high-core-count GPUs [G].
- **When to Use:** When ray lists are moderately sparse and simplicity is preferred [G].
- **When Not to Use:** When strict input order preservation is required without additional sorting steps, or when extreme sparsity makes sorting-based approaches more efficient [G].

## Background
Originating from parallel volume rendering implementations on GPUs, Ray Compaction is a standard technique for managing active ray lists [G]. It is commonly found in CUDA-based volume renderers where efficient memory usage and processing of only active rays are critical [G]. The method leverages atomic operations, a fundamental GPU primitive, to achieve thread-safe compaction [S1, unofficial].
