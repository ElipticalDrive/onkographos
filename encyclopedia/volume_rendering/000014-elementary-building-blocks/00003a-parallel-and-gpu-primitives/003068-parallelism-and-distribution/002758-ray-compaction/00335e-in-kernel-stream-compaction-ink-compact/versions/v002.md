# In-Kernel Stream Compaction (InK-Compact)
Also called: In-Kernel compaction, InK-Compact

## Overview
In-Kernel Stream Compaction (InK-Compact) is a parallel primitive that compacts a list of active items (such as alive rays) by removing terminated ones, performed as a device function within the same GPU kernel that generated the data [S1, unofficial]. It solves the performance bottleneck and overhead associated with launching separate kernels or calling host-side libraries for stream compaction between pipeline stages [S1, unofficial]. Unlike [Ray Buffer Reordering](4073-ray-buffer-reordering.md) which focuses on spatial locality, InK-Compact prioritizes execution latency by avoiding kernel synchronization and additional kernel launches, making it suitable for multi-kernel rendering pipelines where compacting outputs between lightweight kernels is required [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** An array of items (e.g., ray indices) where valid items are marked (e.g., index $\ge 0$) and terminated items are marked (e.g., index $< 0$) [Parent].
*   **Output:** A compacted array containing only valid items, preserving their relative order [S1, unofficial].

**Data Structures:**
*   **Global Counter:** A single integer in global device memory used to track the total number of compacted items across all blocks [S1, unofficial].
*   **Intermediate Buffer:** A temporary buffer used to store block-level outputs. This allows blocks to exit early without locking GPU resources, though it increases memory usage for large data types [S1, unofficial].
*   **Shared Memory:** Used to store block-specific offsets and synchronization variables [S1, unofficial].

**Algorithm Steps:**
1.  **Predication:** Each thread checks if its assigned item is valid. If invalid, the thread exits immediately [Parent].
2.  **Local Prefix Sum:** Valid threads within a warp/block compute a local prefix sum to determine their rank within the block [S1, unofficial]. *Note: The specific local scan algorithm (e.g., Blelloch, Hillis-Steele) is not detailed in the sources, but standard parallel prefix sum techniques are implied [G].*
3.  **Block Offset Calculation:** Thread 0 of each block performs an atomic addition on the global counter to obtain the block's starting offset in the output array.
    $$ k(u) = \text{atomicAdd}(\text{global\_counter}, \text{block\_valid\_count}) $$
    where $k(u)$ is the block offset stored in shared memory [S1, unofficial].
4.  **Synchronization:** A memory fence and block synchronization are executed to ensure all threads see the updated shared memory variables ($s(u)$ and $k(u)$) [S1, unofficial].
5.  **Final Index Calculation:** Each thread calculates its final output index $t_f$ by combining the block offset $k(u)$, the warp offset $s(u)$, and the thread's offset within the warp $t(u)$:
    $$ t_f = k(u) + s(u) + t(u) $$
    where $s(u)$ is the warp offset and $t(u)$ is the thread offset within the warp [S1, unofficial].
6.  **Scatter:** Each thread writes its valid item to the final buffer at index $t_f$ [S1, unofficial].

**Pseudocode:**
```python
def ink_compact_kernel(input_array, output_array, num_items):
    # Assume grid/block configuration is set by caller
    tid = threadIdx.x + blockIdx.x * blockDim.x
    bid = blockIdx.x
    local_tid = threadIdx.x
    
    # 1. Predication
    if tid >= num_items:
        return
    
    item = input_array[tid]
    is_valid = (item >= 0) # Predicate defined by parent context
    
    if not is_valid:
        return

    # 2. Local Prefix Sum (Simplified for demonstration)
    # In practice, this involves warp-level primitives or shared memory scans
    # to count valid items before this thread and determine local rank.
    # Let local_rank be the number of valid items in this block before this thread.
    local_rank = compute_local_prefix_sum(is_valid) 
    
    # 3. Block Offset Calculation
    # Only thread 0 in the block updates the global counter
    if local_tid == 0:
        # Calculate how many valid items are in this block
        block_valid_count = compute_block_sum(is_valid)
        # Atomically add to global counter to get block start offset
        block_offset = atomic_add(global_counter, block_valid_count)
        # Store in shared memory for synchronization
        shared_block_offset[0] = block_offset
    sync_threads() # Block synchronization
    
    # 4. Retrieve Block Offset
    block_offset = shared_block_offset[0]
    
    # 5. Final Index Calculation
    # s(u) and t(u) are derived from local_rank depending on warp/block hierarchy
    # For simplicity, assuming local_rank accounts for warp/block structure
    final_index = block_offset + local_rank
    
    # 6. Scatter
    output_array[final_index] = item
```

**Parameters:**
*   **Global Counter:** Initialized to 0 before kernel launch [S1, unofficial].
*   **Intermediate Buffer Size:** Must be at least equal to the input size to accommodate worst-case scenarios where no items are discarded [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Register Burden:** InK-Compact runs as a device function, increasing register pressure. On older architectures (e.g., Fermi), registers used in the main kernel work are reallocated for compaction once the main work is complete, mitigating this cost [S1, unofficial].
*   **Memory Usage:** Requires an intermediate buffer, which can be significant for large data types [S1, unofficial].
*   **Ordering:** Preserves relative order of valid items but does not guarantee global ordering of blocks unless specifically designed (see InK-Collate) [S1, unofficial].

## Subtopics

### In-Kernel Collation (InK-Collate)
In-Kernel Collation (InK-Collate) is a variant that preserves local ordering within a thread block but not global ordering across kernel blocks [S1, unofficial]. It avoids inter-block dependencies by having each block immediately determine its output location using a kernel offset $k(u)$ computed via `atomicAdd` on a global counter by thread 0 [S1, unofficial]. After synchronization, each thread computes its final output location $t_f = k(u) + s(u) + t(u)$ and stores the output, exiting immediately [S1, unofficial]. This approach ensures that blocks do not wait for prior blocks to complete, improving cache hit rates through natural spatial clustering of blocks while maintaining local order [S1, unofficial]. It is chosen when local ordering is beneficial for cache performance but global ordering is not required, and it shows little performance difference from InK-Compact in ray-tracing applications [S1, unofficial].

### Out-of-Kernel Compaction (OfK-Compact)
Out-of-Kernel Compaction (OfK-Compact) is a method where the InK-Compact logic is wrapped in a global kernel and called explicitly when data needs to be compacted, mimicking the usage pattern of Thrust and Chag::PP [S1, unofficial]. When used in this out-of-kernel fashion, InK-Compact runs on par with Chag::PP [S1, unofficial]. This variant is used to test the baseline performance of the compaction algorithm itself, separate from the overhead benefits of in-kernel execution [S1, unofficial].

### Chag::PP Compaction
Chag::PP Compaction refers to the use of the Chag::PP library for stream compaction. In this method, kernels output ray indices to an output array in the same location as the input, setting non-valid elements to zero/null [S1, unofficial]. After kernel completion, the `Chag::PP.compact` method is called on the host to compact the items [S1, unofficial]. This method is slower than InK-Compact because it requires kernel synchronization before calling the host-side compaction routine [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ for $N$ items, with parallel prefix sum operations [S1, unofficial].
*   **Memory Complexity:** $O(N)$ for the output buffer and $O(N)$ for the intermediate buffer if used [S1, unofficial].
*   **Measured Performance:** On an NVIDIA 480 GTX, InK-Compact is 99% faster than Thrust and 28% faster than Chag::PP in a multi-kernel isosurface ray-tracing pipeline [S1, unofficial].
*   **Scaling:** Performance gains are most significant in multi-kernel pipelines where avoiding kernel launch overhead and synchronization is critical [S1, unofficial].
*   **Strengths:** Eliminates kernel synchronization overhead; reduces bottlenecks by keeping compaction within the execution context; encourages more frequent use of compaction in pipelines [S1, unofficial].
*   **Limitations:** Increases register pressure (mitigated on modern architectures like Fermi); requires intermediate buffer memory; not feasible to implement directly with libraries like Thrust which require host-side calls [S1, unofficial].
*   **When to Use:** Multi-kernel rendering pipelines (e.g., Generation-Traversal, Traversal-Intersection, Intersection-Traversal, Intersection-Shade) where compacting outputs between lightweight kernels is necessary [S1, unofficial].
*   **When Not to Use:** Single-kernel pipelines where compaction can be integrated into the main logic without intermediate steps, or when memory bandwidth is severely constrained by large intermediate buffers [S1, unofficial].

## Background
InK-Compact was introduced by D. M. Hughes et al. in 2013 as part of research on optimizing GPU-based isosurface ray-casting pipelines [S1, unofficial]. The method was developed to address the inefficiencies of conventional stream compaction libraries (Thrust, Chag::PP) which require leaving the kernel context, preparing temporary arrays, and launching multiple additional kernels [S1, unofficial]. The authors demonstrated its effectiveness in a multi-kernel rendering pipeline, showing significant performance improvements over existing methods [S1, unofficial].
