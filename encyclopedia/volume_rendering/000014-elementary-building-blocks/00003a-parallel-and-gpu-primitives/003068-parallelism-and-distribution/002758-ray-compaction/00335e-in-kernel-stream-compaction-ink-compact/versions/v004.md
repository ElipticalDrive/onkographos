# In-Kernel Stream Compaction (InK-Compact)

Also called: In-Kernel compaction, InK-Compact

## Overview
In-Kernel Stream Compaction (InK-Compact) is a parallel primitive that compacts a stream of valid elements into a contiguous output array while preserving input order, executed entirely within a single GPU kernel as a device function [S1, unofficial]. It solves the performance bottleneck of conventional stream compaction methods (like Thrust or Chag::PP) which require leaving the kernel to launch separate prefix-sum and scatter kernels [S1, unofficial]. Unlike its sibling [Ray Buffer Reordering](4073-ray-buffer-reordering.md), which focuses on spatial locality, InK-Compact focuses on minimizing synchronization overhead and kernel launch latency by avoiding global memory writes for invalid elements and eliminating inter-kernel dependencies [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   Input: An array of $N$ elements $X[0 \dots N-1]$ with an associated predicate $P[0 \dots N-1]$ (valid/invalid).
*   Output: An array $Y[0 \dots M-1]$ containing only elements where $P[i]$ is true, preserving their relative order from $X$.
*   Auxiliary: An intermediate buffer $Y'$ of size $N$ (or sufficient to hold block-local outputs) and global section management structures.

**Data Structures:**
*   **Section Management:** For a kernel divided into $S$ sections, each section $S_i$ has:
    *   `flag` $S_i(f)$: Boolean, initially false. Becomes true when section $i$ is ready to write to final output.
    *   `offset` $S_i(u)$: Integer, the starting index in the final output array $Y$ for section $i$.
    *   `counter` $S_i(c)$: Integer, atomic counter for the number of blocks in section $i$ that have completed local compaction.
*   **Block Counts:** A buffer $B(c)$ to store the total write count $k(c)$ for each block in the current section.
*   **Shared Memory:**
    *   `ww(c)[w(n)]`: Stores the total number of valid elements written by each warp in the block.
    *   `s(u)[w(n)]`: Stores the warp offset for each warp.

**Parameters:**
*   $w(s)$: Warp size (e.g., 32 for CUDA 4.0) [S1, unofficial].
*   $w(n)$: Number of warps per block.
*   $S(N)$: Section size, number of blocks per section. Typically 32, chosen so that the bit-decomposition scan for block offsets fits within a single warp [S1, unofficial].

**Algorithm Steps:**

1.  **Thread Offset Computation ($t(u)$):**
    Each thread $t(i)$ computes its local offset within its warp.
    *   Compute warp index: $w(i) = \lfloor t(i) / w(s) \rfloor$.
    *   Compute warp lane: $w(l) = t(i) \pmod{w(s)}$.
    *   Compute thread mask: $t(m) = \text{MAXINT} \gg (w(s) - w(l))$. This mask has bits $0$ to $w(l)-1$ set to 1.
    *   Compute ballot: $b = \text{ballot}(P[t(i)]) \ \& \ t(m)$.
    *   Compute thread offset: $t(u) = \text{popc}(b)$.
    *   Compute warp total: The last thread in the warp ($w(l) = w(s)-1$) computes $w(c) = t(u) + P[t(i)]$.
    *   Store $w(c)$ into shared memory `ww(c)[w(i)]`.
    *   Synchronize: `_syncthreads()` to ensure visibility.

2.  **Warp Offset Computation ($w_i(u)$):**
    Compute the offset of the current warp relative to the start of the block.
    *   Synchronize: `_syncthreads_count()` with each thread's predicate to gather total block writes (optional for some implementations, but cited for gathering total writes) [S1, unofficial].
    *   Perform bit-decomposition scan over $\log_2(w(s))$ bits. For each bit $j$ from $0$ to $\log_2(w(s))-1$:
        *   $b(j) = \text{ballot}(w_i(c) \ \& \ 2^j)$. Note: $w_i(c)$ here refers to the warp count stored in shared memory, accessed by the first $w(n)$ threads of a warp.
        *   Accumulate: $w_i(u) += \text{popc}(b(j) \ \& \ t(m)) \gg i$.
    *   Synchronize: `_syncthreads()` to ensure all warps have computed their offsets.

3.  **Stage 1: Local Block Compaction:**
    *   Each block computes its local write count $k(c) = \sum w(c)$.
    *   Each thread stores its valid element into the intermediate buffer $Y'$ at index:
        $$ \text{index} = (\text{block\_id} \times \text{threads\_per\_block}) + (w(i) \times w(s)) + t(u) $$
        *(Note: The source describes offsetting by block-id * threads-per-block + thread/warp offsets. Since $t(u)$ is within-warp offset and warp offset is implicit in the block layout, the exact linear index in $Y'$ depends on the specific buffer layout. The source implies $Y'$ is large enough to hold all potential outputs without collision within the block's allocated space.)* [S1, unofficial].
    *   A single thread (e.g., thread 0) atomically increments the section counter: `atomicAdd(&S_i(c), 1)`.
    *   If the block is **not** the section controller (i.e., $S_i(c)$ did not reach $S(N)$), it exits the compaction function.
    *   If the block **is** the section controller (the last block in the section, identified by $S_i(c) == S(N)$), it proceeds to Stage 2.

4.  **Stage 2: Block Offset Computation:**
    *   The section controller loads the block counts $k(c)$ for all blocks in the section into shared memory.
    *   It performs a bit-wise prefix sum scan on these block counts to determine the starting offset for each block within the section.
    *   The scan is performed using bit-decomposition over $\log_2(w(s) \times w(n))$ bits, fitting into a single warp if $S(N)=32$ [S1, unofficial].
    *   The total number of valid elements in the section, $t$, is computed.
    *   The section offset is calculated: $S_i(u) = S_{i-1}(u) + t$ (for $i>0$). For $S_0$, $S_0(u) = 0$.
    *   The section controller sets the flag $S_i(f) = \text{true}$ after a memory fence.

5.  **Stage 3: Section Synchronization:**
    *   Blocks in section $S_i$ (where $i>0$) wait for the flag $S_{i-1}(f)$ to become true.
    *   Section $S_0$ proceeds immediately.
    *   Once the flag is true, the section controller moves the compacted data from the intermediate buffer $Y'$ to the final output array $Y$ at the computed offset $S_i(u)$.
    *   All blocks in the section then use the block-specific offsets computed in Stage 2 to write their local outputs to the final array $Y$.

**Pseudocode:**

```python
def ink_compact_kernel(input_data, predicates, output_buffer, section_flags, section_offsets, section_counters, intermediate_buffer, block_counts_shared):
    # 1. Thread Offset
    tid = get_thread_id()
    warp_id = tid // warp_size
    lane_id = tid % warp_size
    
    # Mask for threads before current lane
    mask = MAXINT >> (warp_size - lane_id)
    
    # Ballot for valid threads before current thread
    valid_mask = ballot(predicates[tid]) & mask
    thread_offset = popc(valid_mask)
    
    # Warp total
    if lane_id == warp_size - 1:
        warp_total = thread_offset + predicates[tid]
        shared_warp_totals[warp_id] = warp_total
    sync_threads()
    
    # 2. Warp Offset (Bit-decomposition scan)
    warp_offset = 0
    for j in range(log2(warp_size)):
        # Check if the j-th bit of the warp total is set
        # Note: This logic assumes the first warp in the block performs the scan
        # or that all warps participate correctly. The source specifies using
        # ballot on the warp count bits.
        bit_val = shared_warp_totals[warp_id] & (1 << j)
        ballot_result = ballot(bit_val != 0) & mask
        warp_offset += popc(ballot_result) >> j
        
    sync_threads()
    
    # 3. Stage 1: Local Compaction
    # Calculate index in intermediate buffer
    # Assuming intermediate buffer is sized to hold all elements without overlap per block
    # Index = block_id * max_elements_per_block + warp_id * warp_size + thread_offset
    # However, source says "offset by block-id * threads-per-block + thread/warp offsets"
    # This implies a flat layout in intermediate buffer.
    local_idx = (get_block_id() * threads_per_block) + (warp_id * warp_size) + thread_offset
    
    if predicates[tid]:
        intermediate_buffer[local_idx] = input_data[tid]
        
    # Atomic section counter increment
    my_section_id = get_block_id() // section_size
    old_count = atomic_add(section_counters[my_section_id], 1)
    
    # Check if this block is the last in the section
    is_controller = (old_count == section_size - 1)
    
    if not is_controller:
        return # Exit early to free resources
        
    # 4. Stage 2: Block Offsets (Controller only)
    # Load block counts into shared memory
    # Assume block_counts_shared is pre-filled or filled by threads 0 of each block
    # This part requires coordination. Source says "block-counts within the section are loaded into shared memory"
    # We assume a mechanism to gather k(c) from all blocks in the section.
    # For simplicity, assuming block_counts_shared is populated by the time controller runs.
    
    # Perform prefix sum on block counts to get block offsets
    # This is done in shared memory by the controller's warp
    block_offset = prefix_sum_block_counts(block_counts_shared, section_size)
    
    # Calculate total valid elements in section
    total_valid = block_offset[section_size - 1] + block_counts_shared[section_size - 1]
    
    # Calculate section offset
    if my_section_id == 0:
        section_offsets[my_section_id] = 0
    else:
        # Wait for previous section to finish? No, Stage 3 handles dependency.
        # But we need S_{i-1}(u).
        # Source: "Si(u) = Si-1(u) + t"
        # We must ensure S_{i-1}(u) is ready.
        while not section_flags[my_section_id - 1]:
            pass # Spin wait
        
        section_offsets[my_section_id] = section_offsets[my_section_id - 1] + total_valid
        
    # Set flag for next section
    memory_fence()
    section_flags[my_section_id] = True
    
    # 5. Stage 3: Write to Final Output
    # Wait for this section's flag to be set (it is set by controller, but other blocks need to wait)
    # Actually, other blocks exited. Only controller writes?
    # Source: "Finally, the last block in section Si moves the already block-compacted data... to the final output array Y"
    # And "All blocks... exit" in Stage 2 except controller.
    # So only the controller writes the data from intermediate to final?
    # Or do all blocks write?
    # Source: "The last block in section Si moves the already block-compacted data from the intermediate output array Si to the final output array Y."
    # This implies the controller performs the bulk copy or scatter.
    
    # Calculate final offset for this block
    final_block_offset = section_offsets[my_section_id] + block_offset[get_block_id() % section_size]
    
    # Copy valid elements from intermediate to final
    # This loop runs on the controller thread(s)
    for i in range(threads_per_block):
        # Check if thread i was valid in this block
        # We need to know which threads were valid. 
        # We can re-evaluate predicate or store validity.
        # Assuming we can iterate through the intermediate buffer range for this block
        start_idx = (get_block_id() * threads_per_block)
        end_idx = start_idx + threads_per_block
        
        # This part is tricky without storing validity map.
        # Alternative: The controller knows the offsets.
        # It can copy the valid chunks.
        pass 
        
    # Note: The source description of Stage 4 is slightly ambiguous about whether
    # all blocks write or just the controller. "The last block... moves... data".
    # This suggests the controller handles the final scatter from Y' to Y.
```

*Note: The pseudocode above simplifies the gathering of block counts and the final scatter, as the source describes these as multi-step shared memory operations. The key constraint is that only the section controller performs the global synchronization and offset calculation, while other blocks exit early.*

## Subtopics

### [Out-of-Kernel Compaction (OfK-Compact)](7270-out-of-kernel-compaction-ofk-compact.md)
Out-of-Kernel Compaction (OfK-Compact) is a variant where the compaction logic is executed outside the primary rendering kernel, typically by invoking a host-side library function (like Thrust) after the kernel completes. Unlike InK-Compact, which performs compaction immediately within the operating kernel to avoid synchronization overhead, OfK-Compact relies on separate kernel launches or library calls, introducing potential bottlenecks but offering a simpler implementation pattern. When implemented as an out-of-kernel wrapper, InK-Compact runs on par with Chag::PP but loses the primary advantage of avoiding kernel synchronization.

### In-Kernel Collation (InK-Collate)
In-Kernel Collation (InK-Collate) is a compromise compaction method that preserves local ordering within a block but not global ordering of kernel blocks, avoiding inter-block dependencies [S1, unofficial]. It computes a kernel offset $k(u)$ using an atomic add on a global counter by thread 0 in the block, then stores output at $t_f = k(u) + s(u)_{w(i)} + t(u)$ [S1, unofficial]. It shows little performance difference from InK-Compact in ray-tracing applications where global order is not strictly required, but avoids the complex section management and synchronization of InK-Compact [S1, unofficial].

### Chag::PP Compaction
Chag::PP Compaction is a conventional out-of-kernel method where kernels output ray indices to an output array in the same location as read, setting non-valid elements to zero/null. After kernel completion, a host-side `Chag::PP.compact` method is called to compact the array [S1, unofficial]. It is slower than InK-Compact and requires kernel synchronization before calling the host-side compaction [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The method performs $O(\log w(s))$ operations per thread for warp offset and $O(\log (w(s) w(n)))$ for block offset, making it efficient for typical warp/block sizes. The overall complexity is dominated by the synchronization and atomic operations, which are minimized by the section-based approach.
*   **Memory Complexity:** Requires an intermediate buffer $Y'$ of size $N$ (or sufficient for block-local outputs) and small shared memory for warp/block counts. The source notes that the intermediate buffer can cause higher memory usage if the data type is large [S1, unofficial].
*   **Performance:** On an NVIDIA 480 GTX, InK-Compact is on average 99% faster than Thrust and 28% faster than Chag::PP in a ray-tracing pipeline [S1, unofficial]. When used out-of-kernel, it runs on par with Chag::PP [S1, unofficial].
*   **Strengths:** Eliminates kernel launch overhead, avoids writing invalid elements to global memory, and maintains high thread coherency in multi-kernel pipelines.
*   **Limitations:** Register burden due to running as a device function, though mitigated by register reallocation on architectures like Fermi [S1, unofficial]. Requires careful management of section synchronization.

## Background
In-Kernel Stream Compaction was introduced by D. M. Hughes et al. in 2013 [S1, unofficial]. It was developed to address the inefficiencies of multi-kernel pipelines in GPU ray-tracing, where conventional compaction methods (Thrust, Chag::PP) required leaving the kernel to perform prefix-sum and scatter operations, causing synchronization bottlenecks. The method builds on previous work in warp-level primitives (Billeter, Harris) but introduces bit-decomposition and balloting for inter-warp scans and a novel section-based approach for block-level ordering [S1, unofficial]. It is used in multi-kernel isosurface ray-tracing pipelines for stages such as Generation-Traversal, Traversal-Intersection, Intersection-Traversal, and Intersection-Shade [S1, unofficial].
