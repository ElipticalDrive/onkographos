# In-Kernel Stream Compaction (InK-Compact)

Also called: In-Kernel compaction, InK-Compact

## Overview
InK-Compact is a stream compaction method that completes the compaction process within the same GPU kernel execution context, rather than requiring the kernel to exit and launch separate prefix-sum and scatter kernels [S1, unofficial]. It generates a smaller output stream $Y[0...M-1]$ from an input stream $X[0...N-1]$ by filtering elements based on a predicate, while strictly preserving the relative input-output data ordering [S1, unofficial]. Unlike conventional methods such as Thrust or Chag::PP, which require leaving the kernel to compute global offsets and scatter data, InK-Compact computes thread, warp, and block offsets internally using bit-decomposition and balloting, thereby eliminating kernel synchronization overhead and temporary array management for invalid elements [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** An array of valid predicates $P[0...N-1]$ (boolean) and corresponding data elements $X[0...N-1]$.
*   **Output:** A compacted array $Y[0...M-1]$ containing only elements where $P[i]$ is true, preserving order.
*   **Global State:** An array of section structures $S$ managing inter-block dependencies.

**Data Structures:**
1.  **Section Structure $S_i$:** Represents a group of blocks (a "section").
    *   $S_i(f)$: Boolean flag indicating if the section's total output count is finalized.
    *   $S_i(u)$: The starting offset in the global output buffer $Y$ for this section.
    *   $S_i(c)$: Atomic counter tracking the number of blocks in the section that have completed local compaction.
2.  **Intermediate Buffer $\tilde{Y}$:** Temporary storage for block-local compacted data before final placement into $Y$.
3.  **Block Count Buffer $B(c)$:** Stores the number of valid elements produced by each block in the current section.

**Parameters:**
*   $w(s)$: Warp size (typically 32 in CUDA 4.0) [S1, unofficial].
*   $w(n)$: Number of warps per block.
*   $S(N)$: Section size, defined as the number of blocks per section. Chosen as 32 to fit the final bit-decomposition scan into a single warp [S1, unofficial].

**Algorithm Steps:**
The method computes offsets in three hierarchical levels: thread within warp, warp within block, and block within kernel.

1.  **Thread Offset Calculation ($t(u)$):**
    *   Compute warp index: $w(i) = \lfloor t(i) / w(s) \rfloor$.
    *   Compute warp lane: $w(l) = t(i) \pmod{w(s)}$.
    *   Compute thread mask: $t(m) = \text{MAXINT} \gg (w(s) - w(l))$. This mask has bits $0$ to $w(l)-1$ set to 1.
    *   Compute ballot: $b = \text{ballot}(P[t]) \ \& \ t(m)$.
    *   Compute thread offset: $t(u) = \text{popc}(b)$.
    *   Compute warp write count: The last thread in the warp ($w(l) = w(s)-1$) calculates $w(c) = t(u) + P[t]$.
    *   Store $w(c)$ in shared memory array $ww(c)[w(i)]$.
    *   Perform memory fence and `__syncthreads()` to ensure visibility.

2.  **Warp Offset Calculation ($w_i(u)$):**
    *   Use bit-decomposition scan over $\log_2(w(s))$ bits to compute the prefix sum of warp counts.
    *   For each bit $j$ from $0$ to $\log_2(w(s))-1$:
        *   $b(j) = \text{ballot}(w_i(c) \ \& \ 2^j)$.
        *   Accumulate: $w_i(u) += \text{popc}(b(j) \ \& \ t(m)) \gg i$.
    *   Perform `__syncthreads_count()` with each thread's predicate to gather the total block write count and ensure visibility.

3.  **Block Offset Calculation (Order-Preserving Compaction):**
    *   **Stage 1 (Local Compaction):** Each block computes its local output in $\tilde{Y}$ using the formula: $\text{index} = \text{block\_id} \times \text{threads\_per\_block} + t(u) + w_i(u)$. The block computes its total write count $k(c)$.
    *   **Stage 2 (Section Controller):** A single thread (e.g., thread 0) atomically increments the section counter $S_i(c)$. All blocks except the "section controller" (the last block in the section, identified when $S_i(c)$ reaches $S(N)$) exit the compaction function. The section controller loads block counts into shared memory and performs a bit-wise prefix sum scan to determine the offset $S_i(u)$ for the section.
    *   **Stage 3 (Dependency Wait):** The last block in section $S_i$ waits for the flag $S_{i-1}(f)$ from the previous section to become true. Section $S_0$ proceeds immediately.
    *   **Stage 4 (Final Placement):** Once $S_i(u)$ is set (using $S_i(u) = S_{i-1}(u) + \text{total\_writes}$), the memory is fenced, and $S_i(f)$ is set to true. The last block in $S_i$ moves the data from $\tilde{Y}$ to the final output buffer $Y$ using the computed offsets.

    WARP_SIZE = 32
    SECTION_SIZE = 32
    
    tid = threadIdx.x
    warp_id = tid // WARP_SIZE

    block_id = blockIdx.x

    block_in_section = block_id % SECTION_SIZE
    
    # Shared memory for warp counts
    shared_warp_counts = [0] * (blockDim.x // WARP_SIZE)
    
    # --- Stage 1: Thread and Warp Offsets ---
    
    # 1. Thread offset within warp
    # Mask for threads before current thread
    thread_mask = (2**WARP_SIZE - 1) >> (WARP_SIZE - lane_id)

    ballot_result = __ballot(predicates[tid]) & thread_mask

    thread_offset = __popc(ballot_result)
    
    # Warp write count (computed by last thread in warp)
    warp_write_count = 0
    if lane_id == WARP_SIZE - 1:
        warp_write_count = thread_offset + predicates[tid]
        shared_warp_counts[warp_id] = warp_write_count
        
    __syncthreads()
    
    # 2. Warp offset within block (Bit-decomposition scan)
    warp_offset = 0

            bit_mask = 1 << j

**Edge Cases and Pitfalls:**
*   **Register Burden:** InK-Compact runs as a device function, increasing register usage. On architectures like Fermi, registers used for main kernel work are reallocated for compaction once the main work is complete, mitigating this cost [S1, unofficial].
*   **Intermediate Buffer:** Requires additional memory for $\tilde{Y}$. If the data type is large, this increases memory footprint compared to methods that do not use an intermediate buffer [S1, unofficial].
*   **Section Size:** $S(N)$ must be chosen such that the final bit-decomposition fits into a warp (typically 32). If $S(N) > 32$, the scan must be spread across multiple warps, complicating the implementation [S1, unofficial].

## Subtopics

### In-Kernel Collation (InK-Collate)
A compromise compaction method that preserves local ordering within a block but not global ordering of kernel blocks, thereby avoiding inter-block dependencies [S1, unofficial]. It computes a kernel offset $k(u)$ using `atomicAdd` on a global counter by thread 0 of each block, then stores output at $t(f) = k(u) + s(u)_{w(i)} + t(u)$ [S1, unofficial]. It shows little performance difference from InK-Compact in ray-tracing applications but does not guarantee global order [S1, unofficial].

### Out-of-Kernel Compaction (OfK-Compact)
A variant where InK-Compact is wrapped in a global kernel and called externally, mimicking the usage pattern of Thrust and Chag::PP [S1, unofficial]. Kernels output ray indices to an output array (setting non-valid elements to zero/null), and then a host-side method (like Thrust's `copy-if`) is called to compact the data [S1, unofficial]. When used this way, it runs on par with Chag::PP, losing the primary advantage of in-kernel execution [S1, unofficial].

### Chag::PP Compaction
A comparison baseline method where kernels output ray indices to an output array (setting non-valid elements to zero/null), followed by a call to `Chag::PP.compact` [S1, unofficial]. It is slower than InK-Compact and requires kernel synchronization before calling the host-side compaction routine [S1, unofficial].

## Operating characteristics
*   **Performance:** On average, InK-Compact is 99% faster than Thrust and 28% faster than Chag::PP in ray-tracing pipeline tests on an NVIDIA 480 GTX [S1, unofficial].
*   **Scaling:** The method scales with the number of blocks and warps, limited by the section size $S(N)$ and register usage [S1, unofficial].
*   **Strengths:** Eliminates kernel synchronization overhead; avoids writing/clearing memory for invalid elements; maintains input-output data ordering [S1, unofficial].
*   **Limitations:** Requires an intermediate buffer $\tilde{Y}$, increasing memory usage for large data types; causes a register burden (mitigated on Fermi+ architectures) [S1, unofficial].
*   **When to use:** Multi-kernel isosurface ray-tracing pipelines (Generation-Traversal, Traversal-Intersection, Intersection-Traversal, Intersection-Shade) where thread coherency and low overhead are critical [S1, unofficial].
*   **When not to use:** When global ordering is not required and simpler local compaction (InK-Collate) suffices, or when memory bandwidth is extremely constrained and intermediate buffers are prohibitive.

## Background
In-Kernel Stream Compaction was introduced by D. M. Hughes et al. in 2013 [S1, unofficial]. It was motivated by the need for efficient parallel compaction in multi-kernel GPGPU pipelines, specifically for ray-tracing-based visualization of volumetric data. The work contrasts with conventional methods like Thrust [HB10] and Chag::PP, which require leaving the kernel to perform prefix-sum and scatter operations. The method builds on previous work by Billeter [BOA09] and Harris [Hwu11] for per-warp prefix sums, introducing bit-decomposition and balloting for inter-warp scans and a novel block-section management scheme for order-preserving compaction without leaving the kernel [S1, unofficial].
