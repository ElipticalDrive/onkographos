# Out-of-Kernel Compaction (OfK-Compact)

Also called: OfK-Compact, Thrust, Thrust Compaction, copy-if, out-of-kernel implementation

## Overview
Out-of-Kernel Compaction (OfK-Compact) is a stream compaction technique where the compaction logic is executed outside the primary rendering kernel, typically by invoking a host-side library function after the kernel completes. It solves the problem of removing invalid or empty rays from an output array generated by a parallel GPU kernel. Unlike its sibling [In-Kernel Stream Compaction (InK-Compact)](6991-in-kernel-stream-compaction-ink-compact.md), which performs compaction immediately within the operating kernel to avoid synchronization overhead, OfK-Compact relies on separate kernel launches or library calls, introducing potential bottcks but offering a simpler implementation pattern.

## How it works
**Inputs and Outputs:**
- Input: An output array generated by a preceding kernel (e.g., ray generation or traversal) containing valid ray indices and invalid elements marked as zero/null.
- Output: A compacted array containing only valid ray indices, with no gaps.

**Data Structures:**
- The input array is a flat array of integers (ray indices).
- Invalid elements are explicitly set to zero or a null value by the preceding kernel.

**Steps:**
1. The preceding GPU kernel (e.g., for ray generation or traversal) executes. For each ray, if the ray is valid, it writes its index to the output array at the same location it was read from the input array. If the ray is invalid, it writes zero or null to that location [S1, unofficial].
2. The kernel completes execution.
3. The host code invokes a compaction library function (such as Thrust's `copy-if` or `remove_if`) on the output array [S1, unofficial].
4. The library function iterates through the array, removing elements that satisfy a predicate (e.g., being zero/null) and compacting the remaining valid elements into a contiguous block [S2].

**Pseudocode:**
```python
# Step 1: Execute the rendering kernel
# The kernel writes valid ray indices to out_array[i] if ray i is valid,
# otherwise it writes 0 to out_array[i].
launch_rendering_kernel(out_array, num_rays)

# Step 2: Call out-of-kernel compaction
# Thrust's remove_if removes elements where predicate returns true.
# Here, we remove zeros.
valid_count = thrust::remove_if(
    out_array.begin(),
    out_array.end(),
    out_array.begin(),
    is_zero # Predicate: returns true if element is 0
)

# The valid rays are now in out_array[0...valid_count-1]
```

**Parameters and Edge Cases:**
- Predicate: The condition for removal is typically equality to zero or null [S2].
- Precision: No specific precision issues noted, but standard floating-point or integer comparison applies.
- Pitfalls: Requires synchronization between the GPU kernel and the host call to the library. If not managed correctly, the library may operate on stale data.

## Subtopics

### Thrust Stream Compaction
Uses the Thrust library function `thrust::remove_if` to remove elements satisfying a predicate (zeros) from an array [S2]. It is a standard, high-level API approach for out-of-kernel compaction, relying on Thrust's optimized implementations.

## Operating characteristics
- **Time Complexity:** Depends on the underlying library implementation (e.g., Thrust). Generally efficient but incurs host-device synchronization overhead.
- **Memory Complexity:** Requires the output array to be pre-allocated with the same size as the input array to hold potential worst-case scenarios (all valid) [S1, unofficial].
- **Performance:** When InK-Compact is used in an out-of-kernel fashion (wrapped in a global kernel and called similarly to Thrust), it runs on par with Chag::PP [S1, unofficial]. However, the main advantage of InK-Compact is avoiding the need to leave the kernel, which reduces bottlenecks associated with kernel synchronization and additional launches [S1, unofficial].
- **Strengths:** Simpler to implement using existing libraries; no need to write custom compaction kernels.
- **Limitations:** Higher overhead due to kernel launches and synchronization compared to in-kernel methods; register cost is minimal but present if wrapped in a kernel [S1, unofficial].
- **When to use:** When simplicity is prioritized over maximum performance, or when integrating with existing library-based pipelines.
- **When not to use:** When minimizing kernel launch overhead and synchronization is critical, favoring InK-Compact instead.

## Background
Originated from the need to handle sparse data in volume rendering pipelines, specifically in stages like Generation, Traversal, and Shading [S1, unofficial]. The method mimics the usage pattern of libraries like Thrust and Chag::PP [S1, unofficial]. It was evaluated in the context of comparing in-kernel vs. out-of-kernel compaction strategies, highlighting the trade-offs between implementation complexity and performance [S1, unofficial].
