# Distributed Volume Rendering Pipeline

Also called: Distributed Volume Rendering Architecture, Distributed software architecture for volume rendering, Virvo Architecture, Virvo system

## Overview
The Distributed Volume Rendering Pipeline is a software architecture for direct volume rendering on heterogeneous High-Performance Computing (HPC) systems, structured as a pipeline of loosely coupled stages [S1, unofficial]. It solves the problem of managing interactive rendering across distributed, multi-user environments by decoupling elementary renderers from parallelism and resource management logic [S1, unofficial]. Unlike traditional batch-style resource managers, it uses Zero Configuration Networking (ZCN) for dynamic node allocation and exposes domain-specific hardware metrics for node selection [S1, unofficial]. It builds on [Sort-last Parallel Rendering](6889-sort-last-parallel-rendering.md) by enforcing a strict four-stage pipeline where data distribution and display are sequential, while rendering and compositing are parallelized [S1, unofficial].

## How it works
The architecture implements a four-stage pipeline: **Data Distribution**, **Rendering**, **Compositing**, and **Display** [S1, unofficial].

### Inputs and Outputs
*   **Input**: A volume dataset (scalar field), transfer functions, viewing parameters, and a list of available computing resources (nodes/GPUs) registered via ZCN [S1, unofficial].
*   **Output**: A final composited image displayed on the client interface [S1, unofficial].

### Data Structures
The system relies on a **Resource Manager** and **Resources** (workers).
*   **Resource**: An entity capable of rendering. It exposes hardware metrics such as available/used video memory and CUDA compute capability [S1, unofficial].
*   **Renderer**:
    *   *Elementary Renderer*: Handles the core volume rendering task for a single resource [S1, unofficial].
    *   *Parallel Brick Renderer*: Instantiated when a request requires multiple resources. It is configured for sort-last parallel Multi-GPU or distributed memory rendering [S1, unofficial].
*   **Visibility Sorting Structure**: A k-d tree search structure superimposed on top of elementary renderers to handle threading and parallelism [S1, unofficial]. The implementation chooses not to expose this structure for replacement to avoid performance degradation compared to ray tracing [S1, unofficial].

### Steps
1.  **Resource Registration**: Resources dynamically register with the Resource Manager using Zero Configuration Networking (ZCN) [S1, unofficial].
2.  **Request Reception**: The client sends a rendering request. The Resource Manager selects a suitable node based on hardware-specific metrics (e.g., video memory, CUDA capability) [S1, unofficial].
3.  **Data Distribution**: Assigned to a single processor. The dataset is distributed to the selected rendering resources [S1, unofficial].
4.  **Rendering**:
    *   If one resource is assigned, an *Elementary Renderer* is created [S1, unofficial].
    *   If multiple resources are assigned, a *Parallel Brick Renderer* is created, configured for sort-last parallel rendering [S1, unofficial].
    *   The renderer uses the k-d tree structure for parallelism [S1, unofficial].
5.  **Compositing**:
    *   If multiple resources rendered the job, their sub-images are composited [S1, unofficial].
    *   If a single resource handled the job, this stage is omitted, and execution proceeds directly to Display [S1, unofficial].
6.  **Display**: A dedicated stage determines how the final image is displayed on the remote client, accommodating varying interactive requirements (e.g., high-frame-rate VR vs. low-frame-rate monitoring) [S1, unofficial].
7.  **Re-registration**: After completing a request, resources re-register with the Resource Manager via ZCN [S1, unofficial].

```python
class Resource:
    def __init__(self, node_id, video_memory, cuda_capability):
        self.node_id = node_id
        self.video_memory = video_memory
        self.cuda_capability = cuda_capability
        self.is_available = True

class ResourceManager:
    def __init__(self):
        self.resources = []
        # ZCN protocol handles dynamic addition/removal
        pass

    def select_node(self, request):
        # Select based on hardware metrics, not batch scheduling
        # [G] Simple greedy selection for illustration
        for r in self.resources:
            if r.is_available and r.video_memory >= request.memory_requirement:
                return r
        return None

class Pipeline:
    def __init__(self, resource_manager):
        self.rm = resource_manager

    def execute(self, volume_data, transfer_function, view_params):
        # 1. Data Distribution (Sequential, Single Processor)
        # [G] Distribute volume data to selected nodes
        selected_nodes = self.rm.select_nodes_for_job(volume_data)
        
        # 2. Rendering (Parallel)
        if len(selected_nodes) == 1:
            renderer = ElementaryRenderer(selected_nodes[0])
        else:
            renderer = ParallelBrickRenderer(selected_nodes)
        
        # [G] Execute rendering using k-d tree for parallelism
        sub_images = renderer.render(volume_data, transfer_function, view_params)
        
        # 3. Compositing (Parallel or Omitted)
        if len(selected_nodes) > 1:
            final_image = Composite(sub_images)
        else:
            final_image = sub_images[0]
            
        # 4. Display (Sequential, Single Processor)
        DisplayStage.show(final_image)
        
        # 5. Re-registration
        for node in selected_nodes:
            node.re_register_via_zcn()

class ElementaryRenderer:
    def __init__(self, resource):
        self.resource = resource
        # [G] Initialize k-d tree for this resource
        self.kd_tree = build_kd_tree(resource.data_partition)

    def render(self, volume, tf, view):
        # [G] Ray casting or similar DVR method using k-d tree
        return render_slice(self.kd_tree, volume, tf, view)

class ParallelBrickRenderer:
    def __init__(self, resources):
        self.resources = resources
        # [G] Configure for sort-last parallel Multi-GPU/Distributed Memory
        pass

    def render(self, volume, tf, view):
        # [G] Distribute bricks, render in parallel, return sub-images
        return [r.render(volume, tf, view) for r in self.resources]
```

### Parameters and Edge Cases
*   **Parallelism Model**: Restricted to sort-last parallel volume rendering to achieve data parallelism [S1, unofficial]. Sort-first is noted as easily accommodable but would generalize the compositing stage [S1, unofficial].
*   **Single Resource**: If one resource handles the job, the compositing stage is omitted [S1, unofficial].
*   **Failure Handling**:
    *   If a socket connection breaks during a job, the client is notified of the resource's unavailability [S1, unofficial].
    *   The resource management subsystem remains unaffected due to loose coupling [S1, unofficial].
    *   If an idle resource becomes unavailable, its status is broadcast via ZCN, and it is removed from the active list [S1, unofficial].
*   **Limitations**: The handcrafted resource management system lacks generality and is restricted to direct volume rendering; supporting alternative visualization methods requires explicit adaptation [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: Not given in the sources.
*   **Memory Complexity**: Not given in the sources.
*   **Performance**: The architecture is designed to scale to heterogeneous HPC systems, ranging from high-end graphics workstations to dedicated render clusters with Multi-GPU nodes and large distributed memory systems without graphics accelerators [S1, unofficial].
*   **Strengths**:
    *   Dynamic resource allocation via ZCN reduces system downtime and allows runtime load balancing without restarts [S1, unofficial].
    *   Loose coupling allows generic replacement of pipeline stages with custom logic via subclassing [S1, unofficial].
    *   Dedicated display stage accommodates varying interactive requirements (VR vs. monitoring) [S1, unofficial].
*   **Limitations**:
    *   Restricted to direct volume rendering; not generalizable to other visualization methods without adaptation [S1, unofficial].
    *   Network latency and bandwidth constraints are primary bottlenecks in remote scenarios [S2, unofficial].
    *   The handcrafted resource management system lacks the generality of traditional batch-style systems [S1, unofficial].

## Background
The Distributed Volume Rendering Pipeline, also known as the Virvo Architecture, was introduced in a paper titled "A SOFTWARE ARCHITECTURE FOR DISTRIBUTED VOLUME RENDERING ON HPC SYSTEMS" [S1, unofficial]. It addresses the need for interactive, multi-user volume rendering on heterogeneous clusters by extending existing pipeline approaches with multi-user support and a dedicated display phase [S1, unofficial]. It differs from traditional resource management by being handcrafted for visualization, exposing domain-specific metrics like CUDA capability and video memory [S1, unofficial].
