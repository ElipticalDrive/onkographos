# Remote Rendering Client/Server Architecture

Also called: Client/Server Volume Rendering, I/O subsystem, Network Rendering, Remote Rendering, Remote client, Remote server, Thin Client Remote Rendering

## Overview
Remote Rendering Client/Server Architecture separates the volume rendering engine into a server and a client connected via a network, allowing rendering computation to be performed on a remote machine while the user interacts locally [S1][S2, S3, unofficial]. It solves the problem of limited local hardware performance or data accessibility by centralizing data storage and rendering power on a server, while the client handles user interface and display [S1][S2, unofficial]. It distinguishes itself from client-side compositing approaches (like Visapult) by performing all rendering and compositing remotely, resulting in a "thin client" that only receives final composited RGB images [S2, unofficial].

## How it works
The architecture relies on a transparent API where the client exposes the same interface as a local renderer, encoding function calls into network messages and deserializing results as if they were computed locally [S1].

**Inputs and Outputs:**
*   **Input:** User interaction events (viewpoint changes, parameter adjustments) from the client; volume data and scene definition stored on the server.
*   **Output:** Final composited RGB images (optionally compressed) sent from server to client for display [S2, unofficial].

**Data Structures:**
*   **Command Stream:** A sequence of serialized function calls (e.g., `setViewpoint`, `setTransferFunction`, `render`) sent from client to server [S1].
*   **Result Buffer:** Binary image data (RGB pixels) generated by the server's renderer, serialized and transmitted back to the client [S1].
*   **Communication Protocol:** Configurable to support TCP/IP, InfiniBand, or shared memory (if client and server are on the same physical machine) [S3, unofficial].

**Steps:**
1.  **Client Initialization:** The client establishes a network connection to the remote server [S3, unofficial].
2.  **Command Encoding:** The client encodes user commands (scene modifications or rendering requests) into a binary format [S1].
3.  **Transmission:** The client sends the serialized commands over the network to the server [S1].
4.  **Server Interpretation:** The server receives the commands, interprets them, and executes corresponding local calls (e.g., modifying scene elements, assigning data files, or triggering the renderer) [S1].
5.  **Rendering:** The server executes the volume rendering algorithm (e.g., ray casting, 3D texture mapping) using the local data and scene parameters [S1][S3, unofficial].
6.  **Result Serialization:** The server serializes the resulting image buffer (binary pixel data) [S1].
7.  **Result Transmission:** The server sends the serialized image data back to the client [S1].
8.  **Client Display:** The client deserializes the image data and renders it to an OpenGL context or provides it directly to the user interface [S1].

**Parameters:**
*   **Network Bandwidth:** The architecture assumes network overhead is acceptable for use cases involving low-performance workstations or very large data volumes [S1].
*   **Compression:** On-the-fly JPEG compression can be applied to transient images to mitigate bandwidth constraints [S2, unofficial].

**Edge Cases and Pitfalls:**
*   **Latency:** The thin client approach requires a full round-trip for each update during interactive rendering, which can introduce latency if the network is slow [S2, unofficial].
*   **Synchronization:** In standard implementations, the client waits for the result of each command before sending the next, unlike asynchronous variants that ignore intermediate updates [S1][S2, unofficial].
*   **Data Locality:** Data is stored centrally on the server; clients do not hold copies of the volume data, ensuring consistency but requiring sufficient server storage and I/O bandwidth [S1][S2, unofficial].

## Subtopics

### [Asynchronous UDP Client-Server Volume Rendering](8490-asynchronous-udp-client-server-volume-rendering.md)
This variant decouples user navigation from rendering by using UDP/IP to transfer rendered images. It solves interaction latency by ignoring intermediate update requests during active rendering, processing only the youngest message upon completion, which yields lower latency than synchronous TCP cycles.

### GPU Cluster Sort-last Rendering with MPI
In this variant, a thin client communicates via TCP/IP as an image viewer, while server nodes synchronize using MPI [S4, unofficial]. Partial images are sent to the client either gathered and composited or directly without compositing, with optional compression of the final image [S4, unofficial].

## Operating characteristics
*   **Time Complexity:** Rendering time depends on the server's hardware and the volume size. For a 128x256x256 volume rendered to a 512x512 image using a 3D texture GPU renderer, the remote configuration over a 100Mbit/s network took 557.12 ms [S1].
*   **Memory Complexity:** The server must hold the entire volume dataset in memory or accessible storage; clients hold only the UI state and the current frame buffer [S1][S2, unofficial].
*   **Performance:** Interactive visualization of large AMR data sets has been achieved at several frames per second under the latency and bandwidth constraints of a consumer-level DSL Internet connection, leveraging on-the-fly JPEG compression [S2, unofficial].
*   **Strengths:** Platform-independent clients (e.g., Java applets); centralized data management; ability to use high-end server hardware for rendering [S1][S2, unofficial].
*   **Limitations:** Requires a full round-trip for each update in synchronous modes, potentially limiting interactivity on high-latency networks; dependent on network stability [S2, unofficial].
*   **When to use:** When local hardware is insufficient for the data size or rendering complexity, or when data is too large to distribute to multiple clients [S1][S2, unofficial].
*   **When not to use:** When ultra-low latency is critical and network conditions are poor, or when client-side compositing is preferred for fault tolerance [S2, unofficial].

## Background
The architecture originated from the need to support remote visualization on HPC systems and heterogeneous clusters [S3, unofficial]. It was formalized in the VRE volume rendering engine, which separated user interaction, scene management, and rendering into distinct components to facilitate remote extension [S1]. It has been used in systems like Visapult (as a contrast point) and various AMR rendering frameworks to enable sort-last parallel rendering on distributed memory systems [S2, S3, unofficial].
