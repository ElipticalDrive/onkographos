# Multi-Frame Rate Volume Rendering

Also called: Asynchronous Multi-GPU Volume Rendering, Fast/Slow GPU Volume Rendering

## Overview
Multi-frame rate volume rendering is an asynchronous parallel rendering technique that distributes workload across multiple GPUs to balance high frame rates with high visual quality [S1]. A fast display GPU handles user input and low-latency feedback, while one or more backend GPUs asynchronously compute high-quality views [S1]. It distinguishes itself from earlier multi-frame rate systems by using layered image warping to preserve motion parallax and enable view-dependent lighting for transparent volumetric structures, rather than reconstructing the scene as a single surface [S1].

## How it works
The method operates on a client-server architecture where the "fast node" (client) manages display and interaction, and the "slow node" (server) performs heavy raycasting [S1].

**Inputs and Outputs**
*   **Input:** Volumetric dataset, camera parameters, and user input (mouse/keyboard) [S1].
*   **Output:** Final composited image displayed on the fast node's monitor [S1].

**Data Structures**
*   **Ring Buffer:** Process-local heap memory on the host, used as an intermediate storage for images transferred from the slow node to the fast node [S1].
*   **G-Buffers:** Stored on the fast node GPU [S1]. Each G-Buffer stores three channels: Color, Normal, and Depth [S1]. Multiple G-Buffers may exist to hold reference frames or intermediate warping results [S1].

**Pipeline Steps**
The rendering pipeline executes five main steps in order [S1]:

1.  **Raycasting (Slow Node):** The slow node GPU performs volume raycasting [S1]. It produces three buffers: Color, Depth, and Normal [S1]. The raycaster supports complex translucent objects and CSG intersections [S1].
2.  **Transfer:** The image buffers are downloaded from the slow node's GPU memory to the host memory (ring buffer) and then uploaded to the fast node's GPU memory [S1].
3.  **Latency Compensation (Warping):** The fast node warps the reference frames (stored in G-Buffers) to compensate for camera movement since the last raycast [S1]. This involves projecting the depth and normal information to estimate new pixel positions and colors [S1].
4.  **Shading:** View-dependent lighting is computed on the warped data [S1]. This step is critical for transparent objects to correctly light inner structures revealed by motion parallax [S1].
5.  **Compositing:** Fragments are sorted per pixel, blended front-to-back, and written to the frame buffer [S1].

**Pseudocode**
The following pseudocode outlines the asynchronous loop on the fast node and the raycasting loop on the slow node [S1].

```python
class GBuffer:
    def __init__(self, color, normal, depth):
        self.color = color
        self.normal = normal
        self.depth = depth

class Camera:
    def __init__(self, view_matrix, proj_matrix):
        self.view_matrix = view_matrix
        self.proj_matrix = proj_matrix

def project_point(point_3d, camera):
    """Projects a 3D world point to normalized device coordinates [-1, 1]"""
    # Standard matrix multiplication: clip = proj * view * point
    return apply_matrices(point_3d, camera.proj_matrix, camera.view_matrix)

def unproject_pixel(u, v, depth, camera):
    """Reconstructs a 3D world point from screen coordinates and depth"""
    # Standard inverse projection using camera matrices
    return inverse_projection(u, v, depth, camera.proj_matrix, camera.view_matrix)

def is_in_viewport(x, y, width, height):
    return 0 <= x < width and 0 <= y < height

def fast_node_loop(g_buffers, ring_buffer, camera, screen_width, screen_height):
    while True:
        # Step 1: Process user input (camera updated externally)
        # Step 2: Check for new frames from slow node
        if ring_buffer.has_new_frame():
            new_color, new_depth, new_normal = ring_buffer.read()
            ref_g_buffer = GBuffer(new_color, new_depth, new_normal)
            g_buffers.append(ref_g_buffer)
            if len(g_buffers) > 2:
                g_buffers.pop(0)

        # Step 3: Latency Compensation (Warping)
        if g_buffers:
            ref = g_buffers[-1]
            warped_color = [[0.0] * screen_width for _ in range(screen_height)]
            warped_normal = [[(0.0, 0.0, 0.0)] * screen_width for _ in range(screen_height)]
            warped_depth = [[float('inf')] * screen_width for _ in range(screen_height)]

            src_h, src_w = len(ref.depth), len(ref.depth[0])
            for y_src in range(src_h):
                for x_src in range(src_w):
                    depth_val = ref.depth[y_src][x_src]
                    if depth_val == float('inf'): continue

                    # Unproject reference pixel to 3D world space
                    p_world = unproject_pixel(x_src, y_src, depth_val, ref.camera)
                    # Project to current camera view
                    p_clip = project_point(p_world, camera)
                    x_dst = int(p_clip.x * screen_width / 2.0 + screen_width / 2.0)
                    y_dst = int(p_clip.y * screen_height / 2.0 + screen_height / 2.0)

                    if is_in_viewport(x_dst, y_dst, screen_width, screen_height):
                        # Depth test handles occlusion for layered warping
                        if p_clip.z < warped_depth[y_dst][x_dst]:
                            warped_depth[y_dst][x_dst] = p_clip.z
                            warped_color[y_dst][x_dst] = ref.color[y_src][x_src]
                            warped_normal[y_dst][x_dst] = ref.normal[y_src][x_src]

            warped_g_buffer = GBuffer(warped_color, warped_normal, warped_depth)

            # Step 4: Shading
            shaded_color = [[0.0] * screen_width for _ in range(screen_height)]
            for y in range(screen_height):
                for x in range(screen_width):
                    if warped_depth[y][x] == float('inf'): continue
                    normal = warped_normal[y][x]
                    view_dir = normalize(camera.view_matrix[2][:3])
                    light_intensity = max(0.0, dot(normal, view_dir))
                    shaded_color[y][x] = [c * light_intensity for c in warped_color[y][x]]

            shaded_g_buffer = GBuffer(shaded_color, warped_normal, warped_depth)

            # Step 5: Compositing
            # Front-to-back blending for multiple layers
            final_image = [[0.0] * screen_width for _ in range(screen_height)]
            alpha_accum = 0.0
            for g_buf in g_buffers:
                for y in range(screen_height):
                    for x in range(screen_width):
                        if g_buf.depth[y][x] == float('inf'): continue
                        color = g_buf.color[y][x]
                        alpha = 1.0 - alpha_accum
                        final_image[y][x] = [c * alpha for c in color]
                        alpha_accum += alpha
                        if alpha_accum >= 1.0: break

            # Display
            display_image(final_image)
        else:
            display_image(previous_frame)

def slow_node_loop(volume_data, ring_buffer, camera):
    while True:
        # Step 1: Raycasting
        color, depth, normal = raycast_volume(volume_data, camera)
        # Step 2: Transfer to Host Memory (Ring Buffer)
        ring_buffer.write(color, depth, normal)
```

**Parameters**
*   **Ring Buffer Size:** Not given in the sources [S1]. Must be large enough to hold at least one full frame of color, depth, and normal data [S1].
*   **Layer Separation:** The system uses feature peeling to separate layers for transparent objects, adapting to dataset features rather than using regular intervals [S1].

**Edge Cases and Pitfalls**
*   **Data Transfer Bottleneck:** Transfer through host memory is a major performance limitation, especially when the slow node's frame rate approaches the fast node's frame rate [S1].
*   **Economic Viability:** Due to transfer costs, the system is only economic for large rendering problems until fast inter-GPU links are available [S1].
*   **Transparent Objects:** Previous systems failed to preserve motion parallax for transparent objects by using a single surface representation [S1]. This method avoids that by warping layered G-Buffers [S1].

## Operating characteristics
*   **Time Complexity:** Not given in the sources [S1].
*   **Memory Complexity:** Not given in the sources [S1].
*   **Measured Performance:** Not given in the sources [S1].
*   **Scaling:** Scales by adding backend GPUs for higher quality or resolution, while the fast node maintains display latency [S1].
*   **Strengths:** High frame rates and low latency for user input; preserves motion parallax and view-dependent lighting for transparent volumes [S1].
*   **Limitations:** Performance limited by host memory bandwidth for inter-GPU transfer; requires large rendering problems to be economic [S1].
*   **When to use:** Medical visualization or scientific visualization of transparent volumetric data where user interaction latency is critical but high-quality rendering is also required [S1].
*   **When not to use:** Small datasets where single-GPU rendering is sufficient, or when fast inter-GPU links are not available and transfer overhead dominates [S1].

## Background
Multi-frame rate volume rendering was introduced by Stefan Hauswiesner, Denis Kalkofen, and Dieter Schmalstieg from Graz University of Technology [S1]. It was presented in the context of the Eurographics Symposium on Parallel Graphics and Visualization (EGPGV) in 2010 [S1]. The work addresses limitations in previous multi-frame rate systems that used single-surface reconstruction, which destroyed motion parallax for transparent objects [S1].
