# Sequential Image Composition with Bounding Box and Chunking

Also called: Sequential Compositing with Bounding Box and Chunking

## Overview
A communication scheme for parallel image composition where a root processor receives local images from other processors one at a time, using bounding boxes and chunking to prevent communication buffer overflow. It differs from [Direct Send Compositing](9377-direct-send-compositing.md) by strictly serializing the reception of tiles and explicitly managing buffer constraints via chunking, whereas Direct Send assumes full-tile transmission is feasible or handled differently. It avoids the complexity of [Tiling Compositing](12057-tiling-compositing.md) by not distributing the compositing load across multiple nodes.

## How it works
**Inputs and Outputs:**
- Input: Local rendered image data from each processor in the parallel system.
- Output: The final composited image on the root processor.

**Data Structures:**
- `LocalImage`: The pixel data generated by a specific processor.
- `BoundingBox`: A rectangular region defined by minimum and maximum coordinates $(x_{min}, y_{min})$ and $(x_{max}, y_{max})$ encompassing all pixels in `LocalImage` that contribute to the final view.
- `Chunk`: A sub-segment of the `BoundingBox` data, sized to fit within the fixed-size communication buffer.

**Steps:**
1. **Bounding Box Calculation:** Each non-root processor determines the portion of the total image affected by its local data. It computes the bounding box around these active pixels.
2. **Chunking:** If the data within the bounding box exceeds the size of the communication buffer, the processor divides the bounding box data into appropriately sized chunks. Each chunk must not exceed the buffer size.
3. **Sequential Transmission with Handshaking:** The root processor receives data from processors one at a time.
    - A processor sends its chunks sequentially.
    - A handshaking protocol is used to ensure the root processor is ready to receive the next chunk, preventing buffer overflow.
    - The root processor composites each received chunk into the final image.
4. **Completion:** The process repeats until all processors have sent their data and the root processor has composited the entire image.

**Formulas:**
- Let $B$ be the size of the communication buffer in bytes.
- Let $P$ be the number of pixels in the bounding box.
- Let $V$ be the number of floating-point values per pixel.
- Let $S$ be the size of one floating-point value in bytes.
- Total bytes to send $T = P \times V \times S$.
- If $T > B$, the data is split into chunks of size at most $B$.

**Parameters:**
- Communication buffer size: Fixed at compile time. Example: 500,000 bytes [S1, unofficial].
- Pixel data size: Example: 5 floating-point values per pixel [S1, unofficial].

**Edge Cases and Pitfalls:**
- **Buffer Overflow:** If a processor attempts to send a message larger than the communication buffer, the message is dropped, and the program fails [S1, unofficial]. This is critical because the buffer size is fixed at compile time and cannot be dynamically adjusted [S1, unofficial].
- **Wasted Bandwidth:** If the bounding box is small, only a portion of the communication buffer is used, leading to wasted bandwidth. Sending multiple sub-images simultaneously to avoid this is difficult because unused bandwidth varies dramatically with image size, processor count, and viewpoint [S1, unofficial].

**Pseudocode:**
```python
def sequential_composition_with_bounding_box_and_chunking(root_processor_id, my_processor_id, local_image, buffer_size):
    """
    Performs sequential image composition with bounding box and chunking.
    
    Args:
        root_processor_id: The ID of the root processor.
        my_processor_id: The ID of the current processor.
        local_image: The pixel data generated by this processor.
        buffer_size: The maximum size of the communication buffer in bytes.
    """
    if my_processor_id == root_processor_id:
        # Root processor receives and composites
        final_image = initialize_empty_image()
        for other_processor_id in all_processors_except(root_processor_id):
            # Wait for signal from other_processor_id
            wait_for_signal(other_processor_id)
            
            # Receive bounding box info
            bbox = receive_bounding_box(other_processor_id)
            
            # Receive chunks sequentially
            while has_more_chunks(other_processor_id):
                chunk = receive_chunk(other_processor_id, buffer_size)
                composite_chunk(final_image, chunk, bbox)
                
            # Signal completion to other_processor_id
            send_signal(other_processor_id)
            
        return final_image
    else:
        # Non-root processor sends data
        # 1. Determine bounding box
        bbox = compute_bounding_box(local_image)
        
        # 2. Send bounding box info to root
        send_bounding_box(root_processor_id, bbox)
        
        # 3. Chunk the data within the bounding box
        chunks = create_chunks(local_image, bbox, buffer_size)
        
        # 4. Send chunks sequentially with handshaking
        for chunk in chunks:
            # Wait for ready signal from root
            wait_for_ready_signal(root_processor_id)
            
            # Send chunk
            send_chunk(root_processor_id, chunk)
            
            # Signal that chunk is sent
            send_signal(root_processor_id)
            
        # Wait for final signal from root
        wait_for_signal(root_processor_id)
```

## Operating characteristics
- **Time Complexity:** Sequential reception means the total time is proportional to the sum of transmission times of all processors. This can be slower than parallel reception schemes if bandwidth is underutilized.
- **Memory Complexity:** Requires a fixed-size communication buffer on each node. The buffer size must be sufficient to hold the largest possible chunk, which is determined at compile time.
- **Performance:** Prevents buffer overflow and program failure, which is a critical advantage over naive direct send methods. However, it may suffer from wasted bandwidth if the bounding box is small relative to the buffer size.
- **Strengths:** Simple to implement, robust against buffer overflow, handles arbitrary viewpoints and image sizes by chunking.
- **Limitations:** Sequential nature can lead to underutilized bandwidth. Difficult to optimize for simultaneous transmission due to variable unused bandwidth.
- **When to use:** When communication buffer size is fixed and small, and buffer overflow is a critical concern. When simplicity and robustness are prioritized over maximum bandwidth utilization.
- **When not to use:** When high bandwidth utilization is critical and the bounding box size is consistently small relative to the buffer size, leading to significant wasted bandwidth.

## Background
This method was investigated as part of the parallel implementation of volume visualization techniques on the nCUBE 2 system [S1, unofficial]. It addresses the specific challenge of fixed-size communication buffers on the nCUBE 2, where buffer overflow leads to program failure [S1, unofficial]. The method was explored as an alternative to more complex schemes like binary tree-based communication [S1, unofficial].
