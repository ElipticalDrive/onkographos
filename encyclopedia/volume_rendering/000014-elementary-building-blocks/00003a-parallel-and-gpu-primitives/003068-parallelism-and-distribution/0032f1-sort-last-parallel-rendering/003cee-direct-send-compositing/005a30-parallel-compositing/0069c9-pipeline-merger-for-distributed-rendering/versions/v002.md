# Pipeline Merger for Distributed Rendering

Also called: merge histogram, merge image, respond procedure

## Overview
The Pipeline Merger is a distributed compositing module that combines partial rendering results from local sub-processors and adjacent pipeline stages, handling both obscuration (for view/layer/z-shade modes) and accumulation (for integrate/histogram modes) [S1, unofficial]. It differs from sibling methods by operating within a synchronous pipeline where it waits for inputs from two specific channels to determine obscuration priority based on slice order and view direction, rather than using a global sort-last approach [S1, unofficial].

## How it works
**Inputs and Outputs:**
The merger process receives data via two input channels (`in.0`, `in.1`) and sends the merged result to one output channel (`out`) [S1, unofficial]. The data types include tags (commands, data, messages, quit) and image slices [S1, unofficial].

**Data Structures:**
The core logic resides in two procedures: `merger` and `respond` [S1, unofficial].
- `merger`: Manages the main loop, listening on `in.0` and `in.1` using an ALT construct [S1, unofficial].
- `respond`: Processes the tag received on the first-arriving channel, handling synchronization, obscuration logic, and forwarding [S1, unofficial].

**Parameters:**
- `normal.order` (BOOL): Indicates if lower slice numbers arrive on the channel that triggered the `respond` call (i.e., `input.0` in the context of the `respond` invocation) [S1, unofficial].
- `forward.merge` (BOOL): Indicates the view direction relative to the voxel data [S1, unofficial].

**Steps:**
1. **Initialization:** The `merger` process initializes a quit counter (`nr.of.quits`) to 0 and sets `running` to TRUE [S1, unofficial].
2. **Wait for Input:** The `merger` waits on either `in.0` or `in.1` for a tag [S1, unofficial].
3. **Invoke Respond:** If `in.0` receives a tag, `respond` is called with `normal.order = TRUE` [S1, unofficial]. If `in.1` receives a tag, `respond` is called with `normal.order = FALSE` [S1, unofficial].
4. **Process Tag (in `respond`):** If the tag is `slice.data`, `message`, or `quit`, the expected packet is received and forwarded to `output` [S1, unofficial]. If `quit`, the quit counter increments; if it reaches 2, `running` becomes FALSE [S1, unofficial].
5. **Synchronize Inputs (for Command):** If the tag is `command`, the process synchronizes inputs to receive merge parameters from both channels [S1, unofficial]. It receives `render.mode` and `forward.merge` flags from the channel that already provided the tag [S1, unofficial]. It receives `render.mode` and `forward.merge` flags from the other channel [S1, unofficial]. It sends a `command` tag followed by the merge type (`merge.image` or `merge.histogram`) and the received parameters to `output` [S1, unofficial].
6. **Determine Obscuration Order (for `merge.image`):** Calculate priority based on `forward.merge` and `normal.order` [S1, unofficial]. If `(forward.merge.0 AND normal.order) OR (NOT forward.merge.0 AND NOT normal.order)`, then `result.1` obscures `result.0` [S1, unofficial]. Otherwise, `result.0` obscures `result.1` [S1, unofficial]. For view/layer/z-shade modes, use block move instructions to overwrite pixels from the higher-priority result onto the lower-priority result where the higher-priority pixels are non-zero [S1, unofficial].
7. **Accumulate (for `merge.histogram`):** For integrate/histogram modes, perform element-wise addition of partial results instead of obscuration [S1, unofficial].

**Formula:**
The obscuration priority is determined by:
$$ \text{result.1 obscures result.0} \iff (\text{forward.merge.0} \land \text{normal.order}) \lor (\neg \text{forward.merge.0} \land \neg \text{normal.order}) $$
where `forward.merge.0` is the view direction flag from the first-arriving channel, and `normal.order` is TRUE if that channel carries lower slice numbers [S1, unofficial].

**Pseudocode:**
```python
# Valid Python representation of Transputer Occam logic [S1, unofficial]
# Module state shared between processes
_state = {'nr_of_quits': 0, 'running': True}

def merger(node_nr, in_0, in_1, out):
    while _state['running']:
        # ALT construct: block until a tag arrives on either channel
        tag, channel = in_0.receive_tag() if in_0.has_tag() else in_1.receive_tag()
        if channel == in_0:
            respond(in_0, in_1, out, True, tag)
        else:
            respond(in_1, in_0, out, False, tag)
        if _state['nr_of_quits'] >= 2:
            _state['running'] = False

def respond(input_0, input_1, output, normal_order, tag):
    if tag == 'command':
        # input_0 already received the tag, receive its payload
        render_mode_0, forward_merge_0 = input_0.receive_payload()
        # input_1 needs to provide its payload (source receives dummy tags first)
        input_1.receive_tag()
        input_1.receive_tag()
        render_mode_1, forward_merge_1 = input_1.receive_payload()
        # Forward merge command with parameters from first channel
        output.send('command', 'merge.image', render_mode_0, forward_merge_0)
        # Determine obscuration order
        if (forward_merge_0 and normal_order) or (not forward_merge_0 and not normal_order):
            obscures_higher = 1  # result.1 obscures result.0
        else:
            obscures_higher = 0  # result.0 obscures result.1
        # Perform merge based on render mode
        if render_mode_0 in ('view', 'layer', 'z-shade'):
            # Hardware block move obscuration: overwrite higher-priority pixels [S1, unofficial]
            # In practice, this uses Transputer Block move instructions to copy non-zero pixels
            pass
        elif render_mode_0 in ('integrate', 'histogram'):
            # Element-wise addition per entry [S1, unofficial]
            result = [a + b for a, b in zip(input_0.get_data(), input_1.get_data())]
        output.send('data', result)
    elif tag == 'data':
        slice_data = input_0.receive_payload()
        output.send('data', slice_data)
    elif tag == 'message':
        msg = input_0.receive_payload()
        output.send('message', msg)
    elif tag == 'quit':
        _state['nr_of_quits'] += 1
        if _state['nr_of_quits'] == 2:
            _state['running'] = False
        output.send('quit')
    else:
        raise ValueError("Unknown tag")
```

**Edge Cases and Pitfalls:**
- Channel ordering must be consistent: `input.0` should receive lower slice results in normal order to ensure correct obscuration logic [S1, unofficial].
- Block move obscuration only works for modes where one result completely obscures another; integrate mode requires additive merging [S1, unofficial].

**Strengths and Limitations:**
- Strengths: Efficient obscuration using hardware-specific 'Block move' instructions on Transputers [S1, unofficial].
- Limitations: Relies on specific hardware instructions (Transputer Block move) for obscuration [S1, unofficial]. Requires consistent channel ordering [S1, unofficial].

**When to Use:**
Use for distributed rendering on Transputer networks where pipeline synchronization is feasible and obscuration or accumulation is required [S1, unofficial].

## Background
The Pipeline Merger was described in the context of voxel data processing on a Transputer network [S1, unofficial]. It is part of a graphics system that includes a voxel processor and a framegrabber [S1, unofficial].
