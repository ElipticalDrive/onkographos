# Parallel Compositing

Also called: Fragment Compositing, MPI Alltoallv Compositing

## Overview
Parallel Compositing is a distributed rendering technique that partitions the final image into spatial tiles, assigning each tile to a specific compositing task. It solves the bottleneck of global image assembly by exchanging only the ray-casting fragments relevant to each tile, performing local compositing, and gathering the result. It differs from [Direct Send Compositing](9377-direct-send-compositing.md) by using a collective `MPI_Alltoallv` communication pattern rather than explicit point-to-point sends, and from [Tiling Compositing](12057-tiling-compositing.md) by its specific reliance on the Alltoallv primitive for fragment exchange.

## How it works
**Inputs:**
- A set of $N$ tasks.
- Ray-casting fragments generated by each task, where each fragment contains color, opacity, and depth information for a ray segment.
- The final image resolution and the partitioning scheme.

**Outputs:**
- The final composited image, gathered on the root task.

**Data Structures:**
- **Fragment Buffer:** A contiguous memory block holding all fragments generated by a task. The layout is not explicitly defined in the sources, but fragments are packed into a single buffer per socket in hybrid implementations [S1].
- **Image Partition:** The image is divided into $K$ tiles. Each task owns one or more tiles.

**Parameters:**
- **Compositing Tasks Ratio:** The ratio of total tasks to active compositing tasks. Typical values are 4 or 5, depending on memory constraints [S1].
- **Max Receiving Tasks:** To mitigate scaling issues, the number of tasks receiving fragments is limited. Emulated values cap this at 2,000, though higher values were experimented with [S1].

**Steps:**
1. **Partition:** Divide the pixels of the final image across the available tasks. Each task is assigned a specific region (tile) of the image [S1].
2. **Exchange:** Perform an `MPI_Alltoallv` call to exchange fragments. Each task sends its generated fragments to the tasks that own the image regions where those fragments lie [S1].
   - In hybrid-memory implementations, only one thread per socket participates in compositing. This thread gathers fragments from all other threads in the same socket, packs them into a single buffer, and transmits it [S1].
3. **Composite:** For each pixel in its assigned region, perform the final compositing using the 'over' operator ($C_{out} = C_{in} + C_{frag}(1 - \alpha_{in})$) [S1].
4. **Gather:** Collect the final composited image tiles from all tasks onto the root task [S1].

**Pseudocode:**
```python
def parallel_compositing(task_id, num_tasks, fragments, image_width, image_height, compositing_ratio):
    # 1. Partition
    # Determine which image tiles this task owns based on task_id and compositing_ratio.
    # The sources do not specify the exact partitioning algorithm (e.g., block, cyclic).
    # [G] Assume a simple block distribution for illustration.
    tiles_per_task = num_tasks // compositing_ratio
    my_tile_start = (task_id % compositing_ratio) * tiles_per_task
    my_tile_end = my_tile_start + tiles_per_task
    
    # 2. Exchange (MPI_Alltoallv)
    # In hybrid mode, gather fragments from local threads first.
    # [G] Assuming 'gather_local_fragments' is a local operation.
    local_buffer = gather_local_fragments(fragments)
    
    # MPI_Alltoallv sends local_buffer to all compositing tasks.
    # The sendcounts and recvcounts depend on the number of fragments 
    # destined for each task.
    # [G] The exact send/recv counts are not provided in sources.
    received_fragments = mpi_alltoallv(local_buffer, sendcounts, recvcounts)
    
    # 3. Composite
    # For each pixel in my tiles, composite the received fragments.
    # [G] The 'over' operator is standard: C_out = C_in + C_frag * (1 - alpha_in)
    for tile in range(my_tile_start, my_tile_end):
        for pixel in get_pixels_in_tile(tile, image_width, image_height):
            pixel_color = composite_over(received_fragments, pixel)
            
    # 4. Gather
    # Gather the final image tiles to the root task.
    # [G] Assuming a standard MPI_Gather or MPI_Gatherv.
    final_image = mpi_gather(my_tile_results, root=0)
    
    return final_image
```

**Edge Cases and Pitfalls:**
- **Scaling Limits:** Using more than 8,000 tasks causes scaling difficulties due to communication overhead. This is mitigated by limiting the number of tasks receiving fragments to ~2,000 [S1].
- **Message Size:** The total message size in `MPI_Alltoallv` is greater than in binary swap algorithms because intermediate compositing is not performed during exchange [S1].

## Operating characteristics
- **Time Complexity:** Dominated by the `MPI_Alltoallv` communication step. The number of messages is similar to sophisticated algorithms like binary swap, but the total data volume is higher [S1].
- **Memory Complexity:** Depends on the fragment buffer size. Hybrid implementations reduce memory pressure by aggregating fragments per socket [S1].
- **Performance:** On small scales, this method performs well. However, optimized binary swap or Radix-K implementations can outperform this approach by up to 40% [S1].
- **Strengths:** Simpler implementation than binary swap; leverages MPI optimizations for collective operations; effective in hybrid-memory environments by reducing message count [S1].
- **Limitations:** Higher total message size than binary swap; scaling issues beyond 8,000 tasks without fragment receiver limiting [S1].

## Background
Parallel Compositing was analyzed in the context of hybrid parallelism for volume rendering on large multi- and many-core systems. The approach emulates techniques from Peterka et al. [S1]. The study compared this method against binary swap and direct send strategies, highlighting the trade-offs between communication volume and algorithmic complexity [S1].
