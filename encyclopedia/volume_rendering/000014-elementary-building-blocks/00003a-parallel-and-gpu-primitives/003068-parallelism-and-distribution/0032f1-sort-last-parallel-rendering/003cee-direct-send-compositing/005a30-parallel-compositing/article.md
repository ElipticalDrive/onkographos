# Parallel Compositing

Also called: Compositing Stage, Fragment Compositing, Image Fragment Compositing, MPI Alltoallv Compositing

## Overview
Parallel Compositing is a distributed rendering technique that partitions the final image pixels across tasks, exchanges fragments generated during raycasting to the task owning each fragment's image region, performs final compositing using the 'over' operator, and gathers the final image on the root task [S1]. It solves the bottleneck of global image assembly by exchanging only relevant fragments and performing local compositing [S1]. It differs from [Direct Send Compositing](9377-direct-send-compositing.md) by using a collective `MPI_Alltoallv` communication pattern rather than explicit point-to-point sends, and from [Tiling Compositing](12057-tiling-compositing.md) by its specific reliance on the Alltoallv primitive for fragment exchange [S1].

## How it works
**Inputs:**
- Ray-casting fragments generated by each task, containing color, opacity, and depth information for ray segments [S1].
- Final image resolution and partitioning scheme [S1].

**Outputs:**
- The final composited image, gathered on the root task [S1].

**Data Structures:**
- **Fragment Buffer:** A contiguous memory block holding all fragments generated by a task. The exact layout is not given in the sources [S1]. In hybrid implementations, fragments from all threads in a socket are packed into a single buffer per socket [S1].
- **Image Partition:** The image is divided into tiles, with each task owning a specific region [S1].

**Parameters:**
- **Compositing Tasks Ratio:** The ratio of total tasks to compositing tasks. Tested values were four or five, depending on memory constraints [S1].
- **Max Receiving Tasks:** To mitigate scaling issues, the number of tasks receiving fragments is limited. Emulated values cap this at 2,000, though higher values were experimented with [S1].

**Steps:**
1. **Partition:** Divide the pixels of the final image across the available tasks. Each task is assigned a specific region (tile) of the image [S1].
2. **Exchange:** Perform an `MPI_Alltoallv` call to exchange fragments. Each task sends its generated fragments to the tasks that own the image regions where those fragments lie [S1].
3. **Composite:** For each pixel in its assigned region, perform the final compositing using the 'over' operator [S1].
4. **Gather:** Collect the final composited image tiles from all tasks onto the root task [S1].

**Pseudocode:**
> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
def parallel_compositing(task_id, num_tasks, local_fragments, image_width, image_height, compositing_ratio):
    # 1. Partition: Divide image pixels across tasks
    num_compositing_tasks = num_tasks // compositing_ratio
    pixels_per_task = (image_width * image_height) // num_compositing_tasks
    my_pixel_start = (task_id % num_compositing_tasks) * pixels_per_task
    my_pixel_end = my_pixel_start + pixels_per_task

    # 2. Exchange: MPI_Alltoallv collective communication
    # Each task sends local_fragments to all compositing tasks and receives buffers from all compositing tasks.
    # In hybrid-memory mode, one thread per socket packs fragments from all local threads into a single buffer before transmission [S1].
    received_fragments = collective_exchange(local_fragments, num_compositing_tasks)

    # 3. Composite: Apply 'over' operator to pixels in assigned range [S1]
    my_tile_results = []
    for i in range(my_pixel_start, my_pixel_end):
        # Standard 'over' compositing: C_out = C_in + C_frag * (1 - alpha_in) [G]
        pixel = apply_over_operator(received_fragments, i)
        my_tile_results.append(pixel)

    # 4. Gather: Collect final image on root task [S1]
    final_image = gather_to_root(my_tile_results, root=0)
    return final_image
```

**Edge Cases and Pitfalls:**
- **Scaling Limits:** Using more than 8,000 tasks causes scaling difficulties due to communication overhead [S1]. This degradation was reproduced on JaguarPF with up to 216,000 cores [S2]. Mitigation involves limiting the number of tasks receiving fragments to approximately 2,000 [S1].
- **Message Size:** The total message size in `MPI_Alltoallv` is greater than in binary swap algorithms because intermediate compositing is not performed during exchange [S1].
- **Hybrid Memory Optimization:** In hybrid-memory implementations, only one thread per socket participates in compositing, gathering fragments from all other threads in the same socket into a single buffer to reduce message count [S1].

## Operating characteristics
- **Time Complexity:** Dominated by the `MPI_Alltoallv` communication step. The number of messages is similar to sophisticated algorithms like binary swap, but the total data volume is higher [S1].
- **Memory Complexity:** Depends on the fragment buffer size. Hybrid implementations reduce memory pressure by aggregating fragments per socket [S1].
- **Performance:** On small scales, this method performs well. Optimized binary swap or Radix-K implementations can outperform this approach by up to 40% [S1].
- **Strengths:** Simpler implementation than binary swap; leverages MPI optimizations for collective operations; effective in hybrid-memory environments by reducing message count [S1].
- **Limitations:** Higher total message size than binary swap; scaling issues beyond 8,000 tasks without fragment receiver limiting [S1, S2].

## Background
Parallel Compositing was analyzed in the context of hybrid parallelism for volume rendering on large multi- and many-core systems [S1]. The approach emulates techniques from Peterka et al. [S1, S2]. The study compared this method against binary swap and direct send strategies, highlighting the trade-offs between communication volume and algorithmic complexity [S1].
