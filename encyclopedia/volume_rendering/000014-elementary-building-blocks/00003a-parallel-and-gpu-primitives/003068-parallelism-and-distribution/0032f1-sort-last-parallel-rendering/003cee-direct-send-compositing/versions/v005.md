# Direct Send Compositing


## Overview
Direct Send Compositing is the simplest parallel image compositing technique for sort-last volume rendering, where each processor sends its partial image pixel data directly to the specific processor responsible for compositing that image partition [S3]. It avoids exchanging full-size images by dividing the final image into screen-space tiles, with each processor associated with compositing one tile [S2, unofficial]. Unlike [Binary Swap](6889-sort-last-parallel-rendering.md), which divides communication over log2(N) rounds with paired processors swapping tiles, Direct Send performs a single stage of all-to-all communication, making it easier to implement but prone to link contention [S1, S3].

## How it works
**Inputs and Outputs:**
*   **Input:** Partial image tiles rendered by $N$ processors. Each processor holds a full-size image but is responsible for compositing only a specific tile of the final image [S2, unofficial].
*   **Output:** The final composited image, assembled from the tiles processed by each processor.

**Data Structures:**
*   **Image Tile:** A 2D array of pixel values (e.g., RGBA) representing a screen-space partition of the final image [S2, unofficial]. The size of the tile depends on the number of processors $N$ and the total image resolution.
*   **Message Buffer:** A contiguous block of memory containing the pixel data for the tile that processor $p$ needs to send to processor $q$.

**Steps:**
1.  **Tile Assignment:** The final image is divided into $N$ screen-space tiles. Each processor $p$ is assigned one unique tile $T_p$ to composite [S2, unofficial].
2.  **Data Exchange:** Each processor $p$ sends its rendered partial image data for every tile $T_q$ (where $q \neq p$) to processor $q$, and simultaneously receives the partial image data for its assigned tile $T_p$ from all other $N-1$ processors [S3]. This constitutes a single stage of all-to-all communication [S3].
3.  **Local Compositing:** Once all tiles have arrived, each processor $p$ composites its assigned tile $T_p$ independently [S2, unofficial]. Compositing involves sorting volume samples by depth and blending them using the standard front-to-back alpha blending operator [G].
4.  **Final Gathering:** Composited tiles are sent to a master process for final gathering [S2, unofficial].

**Formulas:**
Let $N$ be the number of processors.
Let $P$ be the total number of pixels in the final image.
Let $P_{sendrecv}$ be the number of pixels a processor sends and receives.
Let $N_{sendrecv}$ be the number of messages a processor sends and receives.

*   Number of messages per processor:
    $$N_{sendrecv} = N - 1$$
    [S3]

*   Number of pixels sent/received per processor:
    $$P_{sendrecv} = P \times \left(1 - \frac{1}{N}\right)$$
    [S3]

*   Total compositing time for a processor ($T_{comp}$):
    $$T_{comp} = T_{exchange} + T_{blend}$$
    [S3]

    Where $T_{exchange}$ is the time for sending and receiving, and $T_{blend}$ is the time for blending. Assuming full-duplex communication and equal latency/bandwidth for send/receive:
    $$T_{exchange} = \max(L_{send} + T_{send}, L_{recv} + T_{recv})$$
    [S3]

    With:
    $$L_{send} = N_{sendrecv} \times l_{sendrecv}$$
    $$T_{send} = \frac{P_{sendrecv}}{B_{sendrecv}}$$
    [S3]

    And blending time:
    $$T_{blend} = \frac{P_{blend}}{B_{blend}}$$
    [S3]

    Where:
    *   $l_{sendrecv}$: Latency per message.
    *   $B_{sendrecv}$: Network bandwidth for sending/receiving.
    *   $B_{blend}$: Blending speed (pixels per second).
    *   $P_{blend}$: Number of pixels to blend ($P/N$).

**Pseudocode:**
```python
def direct_send_compositing(rank, num_procs, image_resolution, render_function, composite_function):
    # 1. Render volume
    my_partial_image = render_function(rank, num_procs)

    # 2. All-to-All Communication
    # Each processor sends its partial image to all processors
    # and receives partial images from all processors.
    send_buffers = [my_partial_image] * num_procs
    recv_buffers = [None] * num_procs

    for target_rank in range(num_procs):
        if target_rank == rank:
            recv_buffers[target_rank] = send_buffers[target_rank]
        else:
            # Network transmission: send send_buffers[target_rank] to target_rank
            # and receive data into recv_buffers[target_rank] from target_rank
            pass

    # 3. Local Compositing
    tile_height = image_resolution[1] // num_procs
    y_start = rank * tile_height
    y_end = y_start + tile_height

    fragments = []
    for source_rank in range(num_procs):
        # Extract the tile region from the received full partial image
        fragment = recv_buffers[source_rank][y_start:y_end, :]
        fragments.append(fragment)

    composited_tile = composite_function(fragments)

    # 4. Final Gathering
    if rank == 0:
        final_image = [composited_tile]
        for r in range(1, num_procs):
            # Receive composited tile from rank r
            pass
    else:
        # Send composited_tile to rank 0
        pass

    return composited_tile if rank == 0 else None
```

**Edge Cases and Pitfalls:**
*   **Link Contention:** Because all processors send to all other processors simultaneously, link contention is likely to occur, especially on networks with limited bandwidth or non-full-duplex capabilities [S3].
*   **Message Size Limits:** On some systems (e.g., Cray XT4 with MPICH), large data sizes and all-to-all communication can exceed MPI capabilities, causing failures beyond a certain number of processors (e.g., 1021 processors for $4096^2$ images) [S3].
*   **Protocol Switching:** Timing drops can occur when the message size exceeds the `MPICH_MAX_SHORT_MSG_SIZE` (default 128000 bytes), switching from short (eager) to long message protocols, which increases latency [S3].
*   **Power of Two:** Unlike Binary Swap, Direct Send does not require the number of processors to be a power of two [S1].

## Subtopics

### [Tiling Compositing](12057-tiling-compositing.md)
Tiling Compositing is a parallel compositing strategy for distributed volume rendering where processing elements (PEs) hold tiles of the final image and pass partial results to adjacent PEs in a staggered, linear fashion to merge them into the final image. Unlike the inverted binary tree method, which leaves a majority of PEs idle during latter cycles, tiling keeps all PEs working on the problem until the final image is completed.

### [Parallel Compositing](16580-parallel-compositing.md)
Parallel Compositing is a distributed rendering technique that partitions the final image pixels across tasks, exchanges fragments generated during raycasting to the task owning each fragment's image region, performs final compositing using the 'over' operator, and gathers the final image on the root task. It solves the bottleneck of global image assembly by exchanging only relevant fragments and performing local compositing. It differs from Direct Send Compositing by using a collective `MPI_Alltoallv` communication pattern rather than explicit point-to-point sends, and from Tiling Compositing by its specific reliance on the Alltoallv primitive for fragment exchange.

### SLIC Parallel Image Compositing
SLIC Parallel Image Compositing is an optimized parallel image compositing algorithm for sort-last rendering that minimizes the number of messages exchanged among processors using a view-dependent precomputed compositing schedule [S4]. It solves the bottleneck of Direct Send by reducing the total amount of data sent over the network. The algorithm involves a preprocessing step (overhead < 10ms) to compute a compositing schedule for each new view, which is then used to minimize data transmission [S4]. SLIC outperforms previous algorithms, especially for high-resolution images (1024x124 pixels or larger) [S4]. On low-bandwidth networks, care must be taken to avoid many-to-one or many-to-many communication patterns inherent in direct send [S4].

## Operating characteristics
**Time and Memory Complexity:**
*   **Communication Steps:** Direct Send requires only one stage of all-to-all communication [S3].
*   **Messages:** In the worst case, $N \times (N - 1)$ messages are exchanged among $N$ compositing processors [S3].
*   **Data Volume:** Each processor sends and receives $P \times (1 - 1/N)$ pixels, where $P$ is the total number of pixels in the image [S3].
*   **Memory:** Each processor must store the full partial image it rendered and the partial images received from all other processors before compositing [S3].

**Measured Performance:**
*   On the Cray XT4 machine, Direct Send failed beyond 1021 processors for $4096^2$ images due to MPI limitations with large data sizes [S3].
*   Performance drops significantly when message sizes exceed the short message protocol threshold (e.g., 128000 bytes in MPICH) [S3].
*   Direct Send scales poorly compared to Binary Swap or 2-3 Swap as the number of processors increases, due to the $O(N^2)$ message complexity and network congestion [S3].

**Strengths and Limitations:**
*   **Strengths:** Simplest implementation; requires only one communication stage; does not require the number of processors to be a power of two; works well for small numbers of processors or high-bandwidth networks [S1, S3].
*   **Limitations:** Prone to link contention; poor scalability for large $N$; high communication overhead; sensitive to network topology and MPI implementation limits [S3].

**When to Use:**
*   Use Direct Send when implementation simplicity and low latency for small processor counts are prioritized, or when network bandwidth is sufficient to handle all-to-all traffic [S1, S3].
*   Avoid Direct Send when the number of processors is large or the network is congested, due to $O(N^2)$ message complexity and link contention [S3].

## Background
Direct Send Compositing was introduced as the simplest image compositing technique for sort-last parallel rendering [S3]. It has been used often in prior work [S1]. The method relies on each processor sending its pixel data directly to the processor responsible for the corresponding image partition in a single stage of communication [S3]. It is frequently compared with Binary Swap, which divides communication over log2(N) rounds to reduce network congestion [S1].
