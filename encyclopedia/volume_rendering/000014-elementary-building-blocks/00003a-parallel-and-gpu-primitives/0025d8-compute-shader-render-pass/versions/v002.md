# Compute Shader Render Pass

Also called: Compute Shader Pass

## Overview
A Compute Shader Render Pass is a rendering technique that bypasses the traditional fixed-function graphics pipeline by using compute shaders to write directly to image resources (such as swapchain images or storage buffers) acting as framebuffers [S1, unofficial]. It solves the problem of rendering complex data structures, such as point clouds or volumetric data, where hardware rasterization is inefficient or insufficient [S1, unofficial]. Unlike standard rasterization, this method replaces the `GL_POINTS` or `GL_TRIANGLES` primitives with custom storage buffers, allowing for custom visibility resolution (e.g., via atomic depth comparisons) and color packing in a single pass [S1, unofficial].

## How it works
The method executes a compute shader to generate pixel data, managing resource layouts and synchronization manually.

**Inputs and Outputs:**
*   **Inputs:** Image dimensions (width, height), source data (e.g., point cloud positions, colors, or volume samples), and pipeline state.
*   **Outputs:** A rendered image stored in a swapchain image or storage buffer.

**Data Structures:**
*   **Push Constants:** A `uint32_t[2]` array containing `{width, height}` [S1, unofficial].
*   **Descriptor Sets:** Bindings for storage buffers (SSBOs) containing input data and output images [S1, unofficial].
*   **Image Layouts:** The target image transitions between `eGeneral` (for compute access) and `eColorAttachmentOptimal` or `ePresentSrcKHR` (for presentation) [S1, unofficial].

**Steps:**
1.  **Pipeline Binding:** Bind the compute pipeline (`renderPipeline`) and its associated descriptor sets [S1, unofficial].
2.  **Push Constants:** Push the image width and height as `uint32_t[2]` constants to the shader [S1, unofficial].
3.  **Layout Transition (Compute):** Transition the swapchain image layout from `eUndefined` to `eGeneral` to allow compute shader access [S1, unofficial].
4.  **Dispatch:** Execute the compute shader with workgroup dimensions calculated as:
    $$
    \text{workgroups}_x = \lceil \frac{\text{width}}{16} \rceil, \quad \text{workgroups}_y = \lceil \frac{\text{height}}{16} \rceil
    $$
    This assumes a local workgroup size of $16 \times 16$ threads [S1, unofficial].
5.  **Layout Transition (Present):**
    *   If a GUI is enabled: Transition the image layout to `eColorAttachmentOptimal` [S1, unofficial].
    *   If no GUI: Transition directly to `ePresentSrcKHR` [S1, unofficial].
6.  **GUI Rendering (Optional):** If the GUI is enabled, draw the overlay (e.g., ImGui) [S1, unofficial].
7.  **Final Transition:** If a GUI was drawn, transition the image layout from `eColorAttachmentOptimal` back to `ePresentSrcKHR` for presentation [S1, unofficial].

**Pseudocode:**
```python
def compute_shader_render_pass(device, command_buffer, swapchain_image, width, height, pipeline, descriptor_sets):
    # 1. Bind pipeline and descriptor sets
    device.cmd_bind_pipeline(command_buffer, vk.PipelineType.COMPUTE, pipeline.handle)
    device.cmd_bind_descriptor_sets(command_buffer, vk.PipelineLayoutType.COMPUTE, pipeline.layout, 0, descriptor_sets, None)

    # 2. Push constants (width, height)
    push_constants = struct.pack('II', width, height)
    device.cmd_push_constants(command_buffer, pipeline.layout, vk.ShaderStageFlagBits.COMPUTE, 0, len(push_constants), push_constants)

    # 3. Transition image to General for compute access
    # Assume image_layout_transition is a helper that handles VkImageMemoryBarrier
    image_layout_transition(command_buffer, swapchain_image, vk.ImageLayout.UNDEFINED, vk.ImageLayout.GENERAL, vk.AccessFlagBits.COMPUTE_SHADER_READ_BIT | vk.AccessFlagBits.COMPUTE_SHADER_WRITE_BIT)

    # 4. Dispatch compute shader
    # Workgroup size is typically 16x16
    group_count_x = (width + 15) // 16
    group_count_y = (height + 15) // 16
    device.cmd_dispatch(command_buffer, group_count_x, group_count_y, 1)

    # 5. Transition image for presentation
    if gui_enabled:
        # Transition to ColorAttachmentOptimal for GUI drawing
        image_layout_transition(command_buffer, swapchain_image, vk.ImageLayout.GENERAL, vk.ImageLayout.COLOR_ATTACHMENT_OPTIMAL, vk.AccessFlagBits.COLOR_ATTACHMENT_WRITE_BIT)
        
        # Draw GUI (e.g., ImGui)
        draw_gui(command_buffer)
        
        # Transition back to PresentSrcKHR
        image_layout_transition(command_buffer, swapchain_image, vk.ImageLayout.COLOR_ATTACHMENT_OPTIMAL, vk.ImageLayout.PRESENT_SRC_KHR, vk.AccessFlagBits.NONE)
    else:
        # Direct transition to PresentSrcKHR
        image_layout_transition(command_buffer, swapchain_image, vk.ImageLayout.GENERAL, vk.ImageLayout.PRESENT_SRC_KHR, vk.AccessFlagBits.NONE)
```

**Edge Cases and Pitfalls:**
*   **Precision:** When using atomic operations for depth/color packing (e.g., 64-bit integers), ensure the GPU supports 64-bit atomics [S1, unofficial].
*   **Boundaries:** Ensure workgroup calculations correctly handle non-divisible image dimensions to avoid out-of-bounds memory access [S1, unofficial].
*   **Synchronization:** Properly manage memory barriers between compute writes and subsequent present operations to avoid rendering artifacts [S1, unofficial].

## Subtopics

### [Atomic Depth-Color Packing for Point Clouds](10206-atomic-depth-color-packing-for-point-clouds.md)
This variant renders point clouds by encoding depth and color into a single 64-bit integer and using `atomicMin` to resolve visibility. It replaces the hardware pipeline's `GL_POINTS` primitive with a custom storage buffer acting as a framebuffer. Unlike Günther et al. [GKLR13], which uses a busy-loop and atomic compare-and-swap to lock pixels, this method updates an interleaved depth and color buffer with a single atomic instruction, improving performance. Choose this when rendering large point clouds with custom visibility logic.

### Buffer Reset
This variant uses a compute shader to reset a buffer to a specific value [S2, unofficial]. It binds a storage buffer (SSBO) to a reset shader, sets uniform variables for `arraySize` and `value`, and executes the shader with a number of groups determined by `ComputeShader::getNumGroups(count)` and a group size of `ComputeShader::getMaxGroupSize()` [S2, unofficial]. Choose this for initializing or clearing large buffers efficiently on the GPU.

## Operating characteristics
*   **Time Complexity:** $O(W \times H)$ for the dispatch, where $W$ and $H$ are image dimensions [S1, unofficial].
*   **Memory Complexity:** Depends on the size of the input data and output buffers [S1, unofficial].
*   **Performance:** Performance is highly dependent on the efficiency of the compute shader logic and memory access patterns [S1, unofficial].
*   **Strengths:** Flexibility in rendering logic, ability to handle complex visibility resolution, and bypassing rasterization overhead [S1, unofficial].
*   **Limitations:** Requires manual management of resource layouts and synchronization, which can be error-prone [S1, unofficial].
*   **When to Use:** When rendering point clouds, volumetric data, or other structures where rasterization is inefficient or insufficient [S1, unofficial].
*   **When Not to Use:** For simple geometric primitives where hardware rasterization is faster and easier to implement.

## Background
The Compute Shader Render Pass is a technique popularized by implementations such as `3DGS.cpp`, which performs Gaussian Splatting using Vulkan compute shaders [S1, unofficial]. It leverages the flexibility of compute shaders to handle rendering tasks that are difficult to express in the traditional graphics pipeline. The method is often used in real-time rendering of large-scale point clouds and volumetric data.
