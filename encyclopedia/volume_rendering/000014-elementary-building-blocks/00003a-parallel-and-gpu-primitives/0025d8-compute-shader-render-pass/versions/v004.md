# Compute Shader Render Pass

Also called: Compute Shader Pass

## Overview
A Compute Shader Render Pass executes a compute shader to generate image data, managing pipeline binding, resource association, workgroup dispatch, and swapchain layout transitions [S1, unofficial]. It differs from [Tiled Parallel Compositing](1192-tiled-parallel-compositing.md) by processing pixels without explicit tile partitioning, and from [Compute Shader Kernel](1202-compute-shader-kernel.md) by explicitly handling presentation synchronization [G].

## How it works
The method sets up a compute pipeline, binds resources, dispatches workgroups, and manages image layout transitions for presentation [S1, unofficial].

**Inputs and Outputs:**
*   **Inputs:** Image dimensions (`width`, `height`), descriptor sets, compute pipeline, swapchain image, and a GUI enable flag [S1, unofficial].
*   **Outputs:** A rendered swapchain image [S1, unofficial].

**Data Structures:**
*   **Push Constants:** A `uint32_t[2]` array storing `{width, height}` [S1, unofficial].
*   **Storage Buffers:** Buffers bound via descriptor sets containing vertex/point data and intermediate state [S1, unofficial].
*   **Image Views:** The target swapchain image accessed for compute and presentation [S1, unofficial].

**Steps:**
1.  **Pipeline Binding:** Bind the compute pipeline and its associated descriptor sets [S1, unofficial].
2.  **Push Constants:** Push `width` and `height` as `uint32_t[2]` constants to the compute shader [S1, unofficial].
3.  **Initial Layout Transition:** Transition the swapchain image layout from `VK_IMAGE_LAYOUT_UNDEFINED` to `VK_IMAGE_LAYOUT_GENERAL` [S1, unofficial].
4.  **Dispatch:** Execute the compute shader with workgroup dimensions `(width + 15) / 16` by `(height + 15) / 16` [S1, unofficial].
5.  **Final Layout Transition:** Transition the image layout to `VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL` if a GUI is enabled, else transition directly to `VK_IMAGE_LAYOUT_PRESENT_SRC_KHR` [S1, unofficial].
6.  **GUI Rendering:** If a GUI is enabled, draw the overlay into the image while it is in `COLOR_ATTACHMENT_OPTIMAL` layout [S1, unofficial].
7.  **Present Transition:** If a GUI was drawn, transition the image layout from `VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL` back to `VK_IMAGE_LAYOUT_PRESENT_SRC_KHR` [S1, unofficial].

**Pseudocode:**
```python
def compute_shader_render_pass(pipeline, descriptor_sets, image, width, height, gui_enabled):
    # 1. Bind pipeline and descriptor sets
    bind_pipeline(pipeline)
    for i, desc_set in enumerate(descriptor_sets):
        bind_descriptor_sets(pipeline.layout, i, desc_set)

    # 2. Push constants: width and height
    push_constants(pipeline.layout, 0, [width, height])

    # 3. Transition image layout to GENERAL for compute access
    transition_image_layout(image, UNDEFINED, GENERAL)

    # 4. Dispatch compute shader
    group_count_x = (width + 15) // 16
    group_count_y = (height + 15) // 16
    dispatch(group_count_x, group_count_y, 1)

    # 5. Transition image layout based on GUI flag
    if gui_enabled:
        transition_image_layout(image, GENERAL, COLOR_ATTACHMENT_OPTIMAL)
        draw_gui(image)
        transition_image_layout(image, COLOR_ATTACHMENT_OPTIMAL, PRESENT_SRC_KHR)
    else:
        transition_image_layout(image, GENERAL, PRESENT_SRC_KHR)

# Helper definitions
def bind_pipeline(pipeline): ...
def bind_descriptor_sets(layout, index, desc_set): ...
def push_constants(layout, offset, values): ...
def transition_image_layout(image, old_layout, new_layout): ...
def dispatch(x, y, z): ...
def draw_gui(image): ...
```

**Parameters:**
*   **Workgroup Size:** Typically 16x16 threads [S1, unofficial].
*   **Image Layouts:** `GENERAL` for compute access, `COLOR_ATTACHMENT_OPTIMAL` for GUI drawing, `PRESENT_SRC_KHR` for presentation [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Boundaries:** Dispatch dimensions must cover the entire image, rounding up to the nearest workgroup size [S1, unofficial].
*   **Synchronization:** Memory barriers are critical to ensure compute writes are visible to subsequent GUI or present operations [S1, unofficial].

## Subtopics

### [Atomic Depth-Color Packing for Point Clouds](10206-atomic-depth-color-packing-for-point-clouds.md)
This variant renders point clouds by replacing the hardware pipeline's `GL_POINTS` primitive with a custom storage buffer acting as a framebuffer. It resolves visibility and color simultaneously by encoding depth and color into a single 64-bit integer and using 64-bit `atomicMin` to select the point with the lowest depth for each pixel. Unlike Günther et al. [GKLR13], which uses a busy-loop to wait for a pixel to be free and locks it with atomic compare-and-swap, this method updates an interleaved depth and color buffer with a single atomic instruction, improving performance.

### Buffer Reset
Uses a compute shader to reset a buffer to a specific value [S2, unofficial]. It binds a storage buffer object (SSBO) to a reset shader, sets uniform variables for the array size and target value, and executes the shader with a number of groups determined by the buffer size and maximum group size [S2, unofficial].

### Overlapped Compute-Render Scheduling
A double-buffering strategy to systematically overlap compute (LOD calculation, vertex assembly) and rendering passes by swapping front and back buffers between frames [S3]. In Frame N, the CPU submits a command buffer for compute passes writing to the back buffer, and a second command buffer for rendering using the front buffer (prepared in Frame N-1) [S3]. Synchronization is implicitly handled by the queue, ensuring commands execute in submission order [S3]. This introduces a one-frame latency (~16.7 ms) but improves effective frame rate by ~11% compared to serial execution [S3].

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of pixels and work items processed per pixel [G].
*   **Memory Complexity:** Depends on the size of the input data buffers and the framebuffer [G].
*   **Performance:** Highly dependent on GPU hardware and memory bandwidth [G].
*   **Strengths:** Full control over rendering logic, ability to handle custom visibility resolution, and compatibility with non-standard primitives [G].
*   **Limitations:** Requires manual management of memory barriers and layout transitions, which can be error-prone [G]. Lacks hardware rasterization optimizations unless explicitly implemented [G].
*   **When to Use:** Custom rendering algorithms where the fixed-function pipeline is insufficient [G].
*   **When Not to Use:** Simple geometric primitives where hardware rasterization is more efficient [G].

## Background
The method is implemented in modern graphics APIs such as Vulkan [S1, unofficial] and WebGPU [S3], extending general-purpose GPU computing principles to rendering pipelines.
