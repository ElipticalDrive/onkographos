# Atomic Depth-Color Packing for Point Clouds

Also called: Atomic point rendering, Basic Compute Shader Point Cloud Rendering, Basic Compute Shader Point Rendering, Compute-based point rendering, Single-pass atomicMin rendering

## Overview
This method renders point clouds using compute shaders by replacing the hardware pipeline's `GL_POINTS` primitive with a custom storage buffer acting as a framebuffer [S1]. It resolves visibility and color simultaneously by encoding depth and color into a single 64-bit integer and using 64-bit `atomicMin` to select the point with the lowest depth for each pixel [S1]. Unlike Günther et al. [GKLR13], which uses a busy-loop to wait for a pixel to be free and locks it with atomic compare-and-swap, this method updates an interleaved depth and color buffer with a single atomic instruction, improving performance [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** Point cloud data (positions in world space, colors) [S1].
*   **Input:** World-View-Projection matrix ($M_{wvp}$) [S1].
*   **Input:** Image dimensions ($W \times H$) [S1].
*   **Output:** An OpenGL texture containing the final RGB color for each pixel [S1].

**Data Structures:**
*   **Framebuffer Storage Buffer:** A 1D array of 64-bit integers, one entry per pixel [S1].
    *   **Layout:** Bits 0–23 store the RGB color (8 bits per channel) [S1]. Bits 24–55 store the linear depth value as a 32-bit integer representation of the float [S1]. Bits 56–63 are unused [S1].

**Numbered Steps:**

1.  **Render Pass:** For each point in the cloud:
    1.  Transform the point position to clip space: `pos = worldViewProj * position` [S1].
    2.  Calculate the pixel ID from the screen position: `pixelID = toPixelID(pos)` [S1].
    3.  Extract the linear depth from the $w$-component of the clip-space position and convert it to an integer: `depth = floatBitsToInt(pos.w)` [S1].
    4.  Pack the depth and RGB color into a 64-bit integer: `point = (depth << 24) | rgb` [S1].
    5.  Perform an atomic minimum update on the framebuffer storage buffer: `atomicMin(framebuffer[pixelID], point)` [S1].

2.  **Resolve Pass:** For each pixel $(x, y)$ in the image:
    1.  Calculate the linear index in the storage buffer: `pixelID = x + y * imageSize.x` [S1].
    2.  Read the packed value from the framebuffer: `packed = framebuffer[pixelID]` [S1].
    3.  Extract the RGB component: `icolor = colorAt(pixelID)` [S1].
    4.  Write the result into an OpenGL texture: `imageStore(texture, ivec2(x, y), icolor)` [S1].

**Pseudocode:**

```python
# Globals/Inputs: W (int), H (int), worldViewProj (mat4), framebuffer (array[int64]), texture (image2D)
# Standard operations: floatBitsToInt(f) -> int64 (bit-cast), atomicMin(addr, val) -> None

def render_pass(position, rgb):
    # 1. Transform to clip space
    pos = worldViewProj * position
    
    # 2. Calculate pixel ID (maps NDC [-1,1] to pixel coordinates)
    px = int((pos.x + 1.0) * 0.5 * W)
    py = int((pos.y + 1.0) * 0.5 * H)
    pixelID = px + py * W
    
    # Bounds check
    if pixelID < 0 or pixelID >= W * H:
        return

    # 3. Extract linear depth and convert to int
    depth = floatBitsToInt(pos.w)
    
    # 4. Pack depth and color (depth << 24 | rgb)
    point = (depth << 24) | rgb
    
    # 5. Atomic minimum update
    atomicMin(framebuffer[pixelID], point)

def resolve_pass(x, y):
    # Bounds check
    if x >= W or y >= H:
        return
        
    pixelID = x + y * W
    
    # Read packed value
    packed = framebuffer[pixelID]
    
    # Extract RGB (lower 24 bits)
    rgb = packed & 0xFFFFFF
    r = rgb & 0xFF
    g = (rgb >> 8) & 0xFF
    b = (rgb >> 16) & 0xFF
    
    # Write to texture
    texture[ivec2(x, y)] = uvec4(r, g, b, 1.0)
```

**Parameters:**
*   **Storage Buffer Format:** Interleaved depth and color buffer, one 64-bit integer per pixel [S1].
*   **Depth Representation:** Linear depth value (`pos.w`) is used directly, avoiding hyperbolic transformations and precision loss associated with standard hardware depth buffers [S1].

**Edge Cases and Pitfalls:**
*   **Precision:** Using linear depth (`pos.w`) avoids the precision loss associated with standard hardware depth buffers, which use hyperbolic transformations [S1].
*   **Dense Point Clouds:** The method is thread-safe and handles dense point clouds without artifacts, unlike Lukac et al. [Lpa14] which is not thread-safe [S1].
*   **Holes:** If point density is not high enough, holes may appear as the method renders at most one pixel per point [S1].
*   **Atomic Contention:** High contention on `atomicMin` can occur if many points map to the same pixel [S1].

## Subtopics

### Compute Shader with Early-Z and Local Reduction
An optimization of the basic compute shader that incorporates early-z testing and group-wide reduction of points using warp-level primitives to reduce contention in global GPU memory [S1]. The method performs early-z testing to discard fragments that are occluded before writing to memory, and uses warp-level primitives to perform group-wide reduction of points, minimizing global memory contention [S1]. This method outperforms the hardware pipeline by up to an order of magnitude and achieves significantly better frame times than previous compute-based methods [S1].

## Operating characteristics
*   **Time Complexity:** $O(N + P)$, where $N$ is the number of points and $P$ is the number of pixels [S1].
*   **Memory Complexity:** $O(P)$ for the framebuffer storage buffer [S1].
*   **Performance:** The method outperforms the hardware pipeline by up to an order of magnitude and achieves significantly better frame times than previous compute-based methods [S1]. Observed peak performance reached 796 million points (12.7GB) at rates of 62 to 64 frames per second [S1].
*   **Strengths:** Thread-safe, handles dense point clouds, avoids hardware depth buffer precision issues, and uses a single atomic instruction instead of a busy-loop [S1].
*   **Limitations:** Aliasing artifacts if points are sparse, potential atomic contention in dense regions, and requires 64-bit atomic support [S1].
*   **When to Use:** When rendering large, dense point clouds on hardware with compute shader support and 64-bit atomics [S1].
*   **When Not to Use:** When sparse point clouds are used (holes may appear) or when hardware lacks 64-bit atomic support [S1].

## Background
This method was introduced in "Rendering Point Clouds with Compute Shaders and Vertex Order Optimization" [S1]. It builds on earlier work by Günther et al. [GKLR13] and Lukac et al. [Lpa14], improving upon their approaches by using a single atomic instruction instead of a busy-loop or non-thread-safe methods [S1].
