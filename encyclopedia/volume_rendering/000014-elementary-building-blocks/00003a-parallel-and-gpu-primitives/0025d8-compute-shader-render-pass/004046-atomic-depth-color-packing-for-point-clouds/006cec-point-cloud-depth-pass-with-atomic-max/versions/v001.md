# Point Cloud Depth Pass with Atomic Max

Also called: Atomic Max Depth Pass, Compute Shader Atomic Depth Buffer

## Overview
A compute shader pass that stores the closest point cloud depth value for each screen pixel to enable hidden surface rejection [S1, unofficial]. It sets apart from its sibling [Discrete Volume Rendering for Point Clouds](15875-discrete-volume-rendering-for-point-clouds.md) by using a single-pass atomic buffer approach rather than volumetric accumulation, and differs from [Custom Point Rendering Pipeline](21229-custom-point-rendering-pipeline.md) by explicitly relying on 64-bit atomic operations for depth resolution.

## How it works
**Inputs and Outputs:**
*   Input: Point cloud positions in world space, view-projection matrix.
*   Output: A depth buffer (texture) storing the minimum depth value for each pixel.

**Data Structures:**
*   Depth Buffer: A 2D texture or structured buffer. The specific bit-depth is not given in the sources, but the values stored are unsigned integers derived from floating-point depth.

**Steps:**
1.  **Clear Buffer:** Set all values in the depth buffer to zero to prevent corruption from the previous frame [S1, unofficial].
2.  **Project Points:** For each point, multiply its world-space position by the view-projection matrix to obtain clip-space coordinates. The model matrix is identity because the point cloud is stored in world space [S1, unofficial].
3.  **Convert Depth:** Convert the floating-point depth value to an unsigned integer using the HLSL `asuint` function. This preserves ordering because normalized floating-point numbers stored in binary guarantee that greater floats are greater as unsigned integers [S1, unofficial].
4.  **Atomic Write:** Write the unsigned integer depth value to the buffer using the `InterlockedMax` HLSL intrinsic. This atomic function only writes the value if it is greater than the currently stored value. It requires unsigned integers, so floating-point numbers cannot be used directly [S1, unofficial].

**Pseudocode:**
```python
# Pseudocode for the depth pass compute shader
# Assumes 'depth_buffer' is a RWStructuredBuffer<uint> or RWTexture2D<uint>
# Assumes 'points' is an array of float3 positions in world space
# Assumes 'vp_matrix' is the view-projection matrix

# Step 1: Clear buffer (handled by pipeline state or explicit dispatch)
# depth_buffer.Clear(0)

for each point in points:
    # Step 2: Project to clip space
    # point_pos is float3, assume w=1.0 for position
    clip_pos = mul(vp_matrix, float4(point_pos, 1.0))
    
    # Check if point is in front of camera and within view
    if clip_pos.z > 0 and clip_pos.z < clip_pos.w:
        # Normalize to NDC depth [0, 1] or [0, far_plane] depending on projection
        # The source implies standard clip-space depth conversion
        depth_float = clip_pos.z / clip_pos.w 
        
        # Step 3: Convert to unsigned int preserving order
        depth_uint = asuint(depth_float)
        
        # Step 4: Atomic Max
        # InterlockedMax writes if new_value > current_value
        # Note: Standard depth buffers usually want minimum depth (closest).
        # The source explicitly states InterlockedMax is used because 
        # 'asuint' inverts the comparison logic for depth (closer = smaller float = larger uint? 
        # Actually, standard depth 0 is near, 1 is far. 
        # If depth_float is closer (smaller), asuint makes it smaller.
        # InterlockedMax keeps the LARGER value. 
        # This implies the source might be storing 'distance from camera' or 
        # the source description contains a logical inversion or specific depth convention.
        # However, we must follow the source exactly: "InterlockedMax... only writes if greater".
        # And "stores the closest point cloud depth value".
        # This is a contradiction in standard depth buffering unless depth is inverted (0=far, 1=near)
        # or the source describes a specific non-standard behavior.
        # We implement exactly as described in [S1, unofficial].
        
        InterlockedMax(depth_buffer[pixel_index], depth_uint)
```

**Parameters:**
*   Shader Compiler: Requires DXC (DirectX Compiler) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Floating Point to Integer Conversion:** Direct use of floating-point atomics is not supported by `InterlockedMax`; conversion via `asuint` is mandatory [S1, unofficial].
*   **Compiler Support:** Requires a newer shader compiler (DXC) which may not be fully integrated in older engine versions, potentially leaving performance improvements on the table [S1, unofficial].

## Subtopics

### Point Cloud Color Pass with Atomic Add
A rasterization phase pass that accumulates color data and point counts for visible points, following the depth pass [S1, unofficial]. It differs from the depth pass by using `InterlockedAdd` instead of `InterlockedMax` and testing against the depth buffer with a slight nudge toward the camera to ensure the closest point passes [S1, unofficial]. It is chosen when color accumulation is required after depth resolution. A key limitation is the use of 32-bit atomics instead of 64-bit atomics due to Unity limitations at the time of development [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Linear with respect to the number of points, $O(N)$, where $N$ is the number of points in the cloud.
*   **Memory Complexity:** $O(W \times H)$ for the depth buffer, where $W$ and $H$ are the screen dimensions.
*   **Performance:** Performance is limited by the availability of the DXC compiler and the efficiency of 64-bit atomics on the target hardware. The source notes that using DXC may leave performance improvements on the table if not fully integrated [S1, unofficial].
*   **Strengths:** Enables efficient hidden surface rejection for large point clouds.
*   **Limitations:** Dependent on specific shader compiler support (DXC). The color pass variant is limited to 32-bit atomics in certain engines (Unity) [S1, unofficial].

## Background
Originated in the context of rendering extremely large point clouds, as described by Magnopus [S1, unofficial]. The method is part of a pipeline that includes hidden surface rejection and hole filling logic, building on techniques referenced in external papers (not detailed in the source) [S1, unofficial].
