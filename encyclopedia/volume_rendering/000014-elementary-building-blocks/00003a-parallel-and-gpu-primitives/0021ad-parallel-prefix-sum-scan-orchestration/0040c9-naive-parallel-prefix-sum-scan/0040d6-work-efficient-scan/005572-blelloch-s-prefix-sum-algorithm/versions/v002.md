# Blelloch’s Prefix Sum Algorithm

Also called: Blelch's algorithm, Blelloch Scan, Blelloch's parallel prefix sum, Parallel Prefix Sum via Binary Tree, Tree Scan Algorithm, Up-sweep/Down-sweep Scan, up-sweep/down-sweep prefix sum

## Overview
Blelloch’s algorithm is an exclusive parallel in-place algorithm for computing the prefix sum of an array of size $N$ [S2]. It solves the problem by decomposing the computation into two distinct phases: an up-sweep (reduce) phase that builds a binary tree of partial sums, and a down-sweep (scan) phase that distributes these sums to compute the final exclusive prefix values [S2]. Unlike Kogge-Stone, which is an inclusive algorithm, Blelloch’s method explicitly excludes the current element from its own sum, making it suitable for operations where the current value must not influence its own prefix result [S2]. It is a work-efficient alternative to naive parallel scan, building on the principles of [Work-Efficient Scan](10349-work-efficient-scan.md) [G].

## How it works
**Inputs and Outputs:**
*   **Input:** An array `Input` of size $N$ [S2].
*   **Output:** An array `Output` of size $N$ such that $Output[i] = \sum_{t=0}^{i-1} Input[t]$ for $0 \le i < N$ [S2].
*   **Constraint:** The algorithm is in-place; `Input` and `Output` initially share the same values, and `Output` is overwritten during execution [S2].

**Data Structures:**
The algorithm operates on a single array `Output` of size $N$ [S2]. Threads are indexed by `tid` (thread ID) [S2]. The implementation assumes a block size of $N/2$ threads, where each thread handles two elements in the initial step, or generally maps to the indices defined by the `indicator` variable [S2].

**Parameters:**
*   `stride`: The distance between elements being summed. Starts at 1 in up-sweep, $N/2$ in down-sweep [S2].
*   `indicator`: The index of the element currently being processed by the thread [S2].

**Steps:**

1.  **Initialization:**
    *   Let `tid` be the thread ID [S2].
    *   Initialize `stride = 1` [S2].
    *   Initialize `indicator = 2 * tid + 1` [S2].

2.  **Phase 1: Up-sweep (Reduce):**
    *   Loop while `stride < N`:
        *   If `indicator < N` and `indicator >= stride`:
            *   Update `Output[indicator] = Output[indicator] + Output[indicator - stride]` [S2].
        *   Synchronize all threads (`__syncthreads()`) [S2].
        *   Update `indicator = 2 * indicator + 1` [S2].
        *   Update `stride = 2 * stride` [S2].
    *   Synchronize all threads (`__syncthreads()`) [S2].
    *   *Result:* The last element `Output[N-1]` holds the total sum of all input values [S2].

3.  **Phase 2: Down-sweep (Scan):**
    *   Initialize `indicator = N * tid + N - 1` [S2].
    *   Initialize `stride = N / 2` [S2].
    *   If `indicator < N`:
        *   Set `Output[indicator] = 0` [S2].
    *   Loop while `stride >= 1`:
        *   If `indicator < N` and `indicator >= stride`:
            *   Store `temporary = Output[indicator]` [S2].
            *   Update `Output[indicator] = Output[indicator] + Output[indicator - stride]` [S2].
            *   Set `Output[indicator - stride] = temporary` [S2].
        *   Synchronize all threads (`__syncthreads()`) [S2].
        *   Update `indicator = (indicator - 1) / 2` [S2].
        *   Update `stride = stride / 2` [S2].
    *   *Result:* The array `Output` contains the exclusive prefix sums [S2].

**Pseudocode:**
```python
# Thread synchronization barrier (standard primitive)
def barrier(): pass

def blelloch_scan_kernel(Output, N, thread_idx):
    indicator = 2 * thread_idx + 1
    stride = 1

    # Phase 1: Up-sweep
    while stride < N:
        if indicator < N and indicator >= stride:
            Output[indicator] = Output[indicator] + Output[indicator - stride]
        barrier()
        indicator = 2 * indicator + 1
        stride = 2 * stride

    barrier()  # Barrier between phases

    # Phase 2: Down-sweep
    indicator = N * thread_idx + N - 1
    stride = N // 2

    if indicator < N:
        Output[indicator] = 0

    while stride >= 1:
        if indicator < N and indicator >= stride:
            temporary = Output[indicator]
            Output[indicator] = Output[indicator] + Output[indicator - stride]
            Output[indicator - stride] = temporary
        barrier()
        indicator = (indicator - 1) // 2
        stride = stride // 2
```

**Edge Cases and Pitfalls:**
*   **Data Race Freedom:** The algorithm requires careful permission management [S2]. In each iteration, some threads lose write permissions because their `indicator` exceeds the array bounds $N$ [S2]. To maintain correctness, thread 0 collects these lost permissions in each iteration and redistributes them at the barrier [S2].
*   **In-place Verification:** Because the algorithm is in-place, elements change in every iteration [S2]. Verifying functional correctness requires tracking the history of values using ghost variables, as intermediate steps are non-trivial [S2].
*   **Synchronization:** Barriers are strictly required between iterations in both phases and between the up-sweep and down-sweep phases to ensure that partial sums from previous levels are available for the next level [S2].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** $O(N)$ for the input/output array. The algorithm is in-place, requiring no additional auxiliary storage proportional to $N$ beyond the input array itself [S2].
*   **Strengths:** It is work-efficient (linear total work $O(N)$) and avoids the high memory bandwidth usage of naive approaches. It is widely used in libraries such as AMD APP SDK and NVIDIA CUDA SDK [S2].
*   **Limitations:** It requires synchronization barriers at every level, which can introduce latency on hardware with poor barrier performance. The sources do not specify a power-of-2 requirement; boundary checks handle arbitrary $N$ [S2].

## Background
Blelloch’s algorithm was introduced by Guy E. Blelloch [S2]. It is frequently cited alongside Kogge-Stone as one of the two primary parallel in-place prefix sum algorithms used in practice [S2]. The algorithm is implemented in major parallel computing SDKs, including the AMD Accelerated Parallel Processing (APP) SDK and the NVIDIA CUDA SDK [S2]. Formal verification of its correctness, particularly regarding data race freedom and in-place state management, has been studied in recent literature [S2].
