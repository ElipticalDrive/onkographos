# Naive Parallel Prefix Sum (Scan)

Also called: Naive GPU Scan, Naive Parallel Inclusive Scan, Naive Parallel Scan, Naive Scan, Naïve algorithm, StreamCompaction::Naive::scan, kernNaiveScan

## Overview
The Naive Parallel Prefix Sum (Scan) is a GPU-based algorithm for computing the inclusive prefix sum of an array using global memory and multiple kernel invocations [S3]. It serves as a baseline implementation compatible with arbitrary input sizes, distinguishing itself from work-efficient variants by its iterative, level-by-level reduction approach which results in higher computational work ($O(n \log n)$) but simpler synchronization logic within each kernel launch [S2, unofficial][S3]. Unlike in-place tree-based methods, it avoids race conditions by double-buffering data between two device arrays across iterations [S3].

## How it works
**Inputs and Outputs:**
- Input: An array of $n$ integers `idata` on the host.
- Output: An array of $n$ integers `odata` on the host containing the exclusive prefix sum [S1, unofficial][S2, unofficial].

**Data Structures:**
- Two device arrays, `dev_data1` and `dev_data2`, of size $n$ to double-buffer results and prevent race conditions, as threads are not guaranteed to run simultaneously [S3].
- The algorithm processes the input in chunks fitting within a single thread block. If $n$ exceeds the block size, the array is split into multiple blocks, and intermediate kernels propagate block sums to combine results [S2, unofficial].

**Parameters:**
- `blockSize`: Number of threads per block. Typically 256 [S2, unofficial] or 512 [S1, unofficial].
- `ilog2ceil(n)`: The ceiling of the base-2 logarithm of $n$, determining the number of kernel launches [S3].

**Steps:**
1. **Allocation:** Allocate two device arrays of size $n$. Copy `idata` to the first device array [S2, unofficial].
2. **Iteration Loop:** Calculate iterations $L = \lceil \log_2(\min(n, \text{blockSize})) \rceil$ [S2, unofficial]. For each iteration $d$ from 1 to $L$:
   - Launch a kernel with `blocksPerGrid = \lceil n / blockSize \rceil` and `blockSize` threads [S1, unofficial].
   - The kernel parameter `offset` is $2^{d-1}$ [S1, unofficial].
   - Inside the kernel for each thread with global index `id`:
     - Copy `data[id]` to a local buffer `buffer[id]`.
     - Synchronize threads within the block.
     - If `threadIdx.x >= offset`, update the value: `buffer[id] = data[id - offset] + data[id]` [S2, unofficial].
     - Synchronize threads.
     - Write `buffer[id]` back to `data[id]`.
     - Synchronize threads.
   - Swap `dev_data1` and `dev_data2` pointers after each kernel launch to double-buffer results [S3].
3. **Post-Processing (Exclusive Scan):**
   - The result in `dev_data1` is an inclusive scan [S1, unofficial]. Convert to exclusive scan:
     - Set `odata[0] = 0`.
     - Copy `dev_data1[1...n-1]` to `odata[1...n-1]` [S1, unofficial].
   - If the input size $n$ was larger than the block size, additional kernels (`kernExtractLastElementPerBlock`, `kernAddOffsetPerBlock`, `kernShiftToExclusive`) are used to combine block results and shift to exclusive [S2, unofficial].

**Pitfalls:**
- The algorithm suffers from warp divergence and uncoalesced global memory accesses due to interleaved thread utilization patterns [S2, unofficial].
- Must be tested with non-power-of-two sized arrays to ensure correctness [S3].
- The original pseudocode and CUDA code in GPU Gems 3 Chapter 39 contain known errors (superscripting, missing braces, bad indentation) [S3].

**Pseudocode:**
```python
def ilog2ceil(x):
    """Ceiling of base-2 logarithm."""
    if x <= 1: return 0
    lg = 0
    while x > 1:
        x >>= 1
        lg += 1
    return lg

def kernNaiveScan(data, buffer, n, block_size):
    """Kernel logic for a single thread."""
    id = blockIdx.x * block_size + threadIdx.x
    tx = threadIdx.x
    if id < n:
        log2n = ilog2ceil(min(n, block_size))
        for d in range(1, log2n + 1):
            offset = 1 << (d - 1)
            buffer[id] = data[id]
            # __syncthreads()
            if tx >= offset:
                buffer[id] = data[id - offset] + data[id]
            # __syncthreads()
            data[id] = buffer[id]
            # __syncthreads()

def naive_scan(n, idata, block_size):
    # 1. Allocation and Initialization
    dev_data1 = list(idata)
    dev_data2 = [0] * n
    
    # 2. Iterative Kernel Launches (simulated)
    log2n = ilog2ceil(min(n, block_size))
    blocks_per_grid = (n + block_size - 1) // block_size
    
    for d in range(1, log2n + 1):
        offset = 1 << (d - 1)
        for b in range(blocks_per_grid):
            for t in range(block_size):
                id = b * block_size + t
                if id < n:
                    dev_data2[id] = dev_data1[id]
                    # __syncthreads()
                    if t >= offset:
                        dev_data2[id] = dev_data1[id - offset] + dev_data1[id]
                    # __syncthreads()
                    dev_data1[id] = dev_data2[id]
                    # __syncthreads()
        # Swap buffers for next iteration
        dev_data1, dev_data2 = dev_data2, dev_data1
        
    # 3. Convert Inclusive to Exclusive
    odata = [0] * n
    if n > 1:
        odata[1:] = dev_data1[1:]
    return odata
```

## Subtopics

### [Work-Efficient Scan](10349-work-efficient-scan.md)
A parallel algorithm that computes the inclusive prefix sum of an array in $O(n)$ total work and $O(\log n)$ parallel depth, significantly improving upon the $O(n \log n)$ work complexity of naive parallel scan. It achieves this efficiency by decomposing the computation into an upsweep (reduction) phase and a downsweep (scan) phase, operating on a binary tree structure. Unlike the Kogge-Stone algorithm, which is inherently inclusive and computes all prefix sums simultaneously via fixed-distance dependencies, the Work-Efficient Scan explicitly constructs exclusive intermediate values before converting them to inclusive results, making it suitable for operations where the current element must not influence its own prefix result during intermediate steps.

### Naive GPU Parallel Scan
A naive GPU-based parallel scan implementation, implemented in the `StreamCompaction::Naive` namespace [S2, unofficial].

### 4-way Prefix Sum
A parallel prefix sum algorithm that concurrently generates binary masks for each radix combination, computes local prefix sums, merges results, and outputs total counts per block [S4, unofficial]. It generates binary masks for each radix combination, computes the local prefix sum of the mask, merges the prefix sum results for all combinations, and sends the total number of each radix combination in each block to the output block sum array [S4, unofficial].

## Operating characteristics
- **Time Complexity:** $O(\log n)$ per block, but requires multiple kernel launches for arrays larger than block size, leading to higher overhead [S2, unofficial].
- **Memory Complexity:** $O(n)$ for double-buffering (two device arrays) [S3].
- **Performance:** On an RTX 2060 Super, the naive scan took 31.3315ms for a power-of-two array size $2^{27}$ and 24.8398ms for a non-power-of-two array size $2^{27}$ [S2, unofficial]. Performance improves as block size increases from 32 to 128, reaching optimal performance at 64 threads per block, with no further gains at higher sizes [S1, unofficial].
- **Strengths:** Simple implementation, compatible with arbitrary input sizes, no shared memory management required (if using global memory double-buffering) [S2, unofficial][S3].
- **Limitations:** Not work-efficient ($O(n \log n)$ total work), suffers from warp divergence and uncoalesced global memory accesses due to interleaved thread utilization patterns [S2, unofficial]. Requires `ilog2ceil(n)` kernel launches, which adds overhead [S3].
- **When to use:** As a baseline for comparison or when implementation simplicity is prioritized over performance [S2, unofficial].
- **When not to use:** For large arrays where performance is critical, or when work efficiency is required [S2, unofficial][S3].

## Background
The Naive Parallel Prefix Sum algorithm is described in GPU Gems 3, Chapter 39, Section 39.2.1 [S3]. It is a foundational parallel primitive used in stream compaction and other data-parallel algorithms [S2, unofficial]. The method is notable for its simplicity but is known to have errors in the pseudocode and CUDA code provided in the original GPU Gems chapter (e.g., superscripting, missing braces, bad indentation) [S3].
