# Indirect Argument Preparation

Also called: FPrepareIndirectArgsCS

## Overview
Indirect Argument Preparation is a GPU compute shader that prepares indirect dispatch and draw arguments from the visible splat count generated by the preceding Global Accumulator + Compaction pass [S1, unofficial]. It serves as the orchestration layer that translates per-proxy visibility data into the specific argument structures required by the graphics API for subsequent Phase-3 rendering and sorting kernels [S1, unofficial]. Unlike the compaction pass which gathers data, this method configures the execution parameters for the geometry generation and indexing stages [S2, unofficial].

## How it works
**Inputs and Outputs:**
The method takes the `VisibleSplatCount` buffer (a `StructuredBuffer<uint>`) as input, which contains the number of visible splats per proxy computed in the previous step [S1, unofficial]. It produces four output buffers:
1.  `IndirectDispatchArgs`: A `RWStructuredBuffer<uint>` of size 3, storing `numGroupsX`, `numGroupsY`, and `numGroupsZ` for the main rendering dispatch [S1, unofficial].
2.  `IndirectDrawArgs`: A `RWStructuredBuffer<uint>` of size 5, storing the arguments for `DrawIndexedIndirect` (index count, instance count, start index location, start vertex location, start instance location) [S1, unofficial].
3.  `SortIndirectArgs`: A `RWStructuredBuffer<uint>` of size 3, storing `NumTiles`, 1, and 1 for the sorting kernel dispatch [S1, unofficial].
4.  `SortParamsBuffer`: A `RWStructuredBuffer<uint>` of size 2, storing `SortCount` and `NumTiles` [S1, unofficial].

**Parameters:**
*   `ComputeThreadGroupSize` (`uint3`): The thread group dimensions used for the compute shaders [S1, unofficial].

**Steps:**
1.  **Reset Counters:** Reset all append buffer counters to zero to prepare for the upcoming geometry generation passes [S2, unofficial].
2.  **Map Kernel Dispatch:** Dispatch the map kernel using thread group sizes derived from the `ComputeThreadGroupSize` parameter [S2, unofficial].
3.  **Vertex Generation Dispatch:** Dispatch the vertex generation kernel [S2, unofficial].
4.  **Vertex Counting Dispatch:** Dispatch the vertex counting kernel using indirect dispatch. The indirect arguments must include an offset pointing to the vertex count in the counter buffer [S2, unofficial].
5.  **Triangle Generation Dispatch:** Dispatch the triangle generation kernel using indirect dispatch with the same offset used in the previous step [S2, unofficial].
6.  **Index Buffer Building Dispatch:** Dispatch the index buffer building kernel using indirect dispatch with an offset pointing to the triangle count [S2, unofficial].
7.  **Intermediate Vertex Indexing Dispatch:** Dispatch the intermediate vertex indexing kernel using indirect dispatch with an offset pointing to the intermediate vertex count [S2, unofficial].

**Pseudocode:**
> **Unverified code.** The code below did not pass a test run against a reference implementation, or no test fits it, so it may contain errors.

```python
# Input: VisibleSplatCount (StructuredBuffer<uint>)
# Output: IndirectDispatchArgs (RWStructuredBuffer<uint>), IndirectDrawArgs (RWStructuredBuffer<uint>),
#         SortIndirectArgs (RWStructuredBuffer<uint>), SortParamsBuffer (RWStructuredBuffer<uint>)
# Parameter: ComputeThreadGroupSize (uint3)

def PrepareIndirectArgsCS():
    # Step 1: Reset all append buffer counters to zero
    ResetAppendBufferCounters()

    # Step 2: Dispatch the map kernel
    # Thread group sizes derived from ComputeThreadGroupSize
    DispatchMapKernel(ComputeThreadGroupSize)

    # Step 3: Dispatch the vertex generation kernel
    DispatchVertexGenerationKernel()

    # Step 4: Dispatch the vertex counting kernel using indirect dispatch
    # Offset points to the vertex count in the counter buffer
    VertexCountOffset = GetVertexCountOffset()
    DispatchIndirect(
        kernel=VertexCountingKernel,
        indirect_args=GetIndirectArgsForVertexCounting(VertexCountOffset)
    )

    # Step 5: Dispatch the triangle generation kernel using indirect dispatch
    # Same offset as vertex counting
    DispatchIndirect(
        kernel=TriangleGenerationKernel,
        indirect_args=GetIndirectArgsForTriangleGeneration(VertexCountOffset)
    )

    # Step 6: Dispatch the index buffer building kernel using indirect dispatch
    # Offset points to the triangle count
    TriangleCountOffset = GetTriangleCountOffset()
    DispatchIndirect(
        kernel=IndexBufferBuildingKernel,
        indirect_args=GetIndirectArgsForIndexBufferBuilding(TriangleCountOffset)
    )

    # Step 7: Dispatch the intermediate vertex indexing kernel using indirect dispatch
    # Offset points to the intermediate vertex count
    IntermediateVertexCountOffset = GetIntermediateVertexCountOffset()
    DispatchIndirect(
        kernel=IntermediateVertexIndexingKernel,
        indirect_args=GetIndirectArgsForIntermediateVertexIndexing(IntermediateVertexCountOffset)
    )

    # Finalize Output Buffers
    # IndirectDispatchArgs is populated based on the total work units
    IndirectDispatchArgs[0] = CalculateNumGroupsX()
    IndirectDispatchArgs[1] = CalculateNumGroupsY()
    IndirectDispatchArgs[2] = CalculateNumGroupsZ()

    # IndirectDrawArgs is populated for the final draw call
    IndirectDrawArgs[0] = GetIndexCount()
    IndirectDrawArgs[1] = GetInstanceCount()
    IndirectDrawArgs[2] = GetStartIndexLocation()
    IndirectDrawArgs[3] = GetStartVertexLocation()
    IndirectDrawArgs[4] = GetStartInstanceLocation()

    # SortIndirectArgs and SortParamsBuffer are populated for the sorting phase
    SortIndirectArgs[0] = NumTiles
    SortIndirectArgs[1] = 1
    SortIndirectArgs[2] = 1

    SortParamsBuffer[0] = SortCount
    SortParamsBuffer[1] = NumTiles
```

## Subtopics

### Indirect Dispatch Orchestration
This variant refers to the specific sequence of indirect dispatches used to drive the geometry generation pipeline (map, vertex, triangle, index, and intermediate vertex kernels) [S2, unofficial]. It is distinguished by its reliance on dynamic offsets into counter buffers to determine the number of work groups for each stage, rather than static counts. Choose this approach when the geometry generation workload is highly variable per frame and depends on the output of previous compute stages. It links to the broader concept of [Global Accumulator + Compaction](10410-global-accumulator-compaction.md) as the source of the visibility data that drives these counts.

## Operating characteristics
**Time and Memory Complexity:**
The time complexity is dominated by the sequential dispatches of the geometry generation kernels, which scale with the number of visible splats and the complexity of the generated geometry (vertices, triangles, indices) [S2, unofficial]. Memory complexity is linear with respect to the number of proxies for the input `VisibleSplatCount` buffer and the size of the output argument buffers, which are fixed-size structures [S1, unofficial].

**Measured Performance:**
Specific performance metrics for Indirect Argument Preparation alone are not provided in the sources. However, related performance data from the OpenSplat4D plugin indicates that optimizing the overall pipeline, including sorting intervals, can yield significant FPS gains (e.g., ~60% increase on an RTX 4090 for a 57-million-splat scene) [S1, unofficial]. The efficiency of this method relies on the preceding compaction pass correctly identifying visible splats to minimize the workload for the subsequent indirect dispatches [S1, unofficial].

**Strengths and Limitations:**
Strengths include dynamic adaptation to scene complexity and efficient use of GPU resources by only dispatching work for visible proxies [S2, unofficial]. Limitations include the overhead of managing multiple indirect dispatches and the dependency on the correctness of the counter buffers and offsets [S2, unofficial].

**When to Use:**
Use this method when rendering dynamic scenes with variable visibility where static draw calls would be inefficient or impossible to determine in advance [S2, unofficial]. It is essential for pipelines that generate geometry on the GPU based on splat data [S2, unofficial].

## Background
Indirect Argument Preparation is part of the rendering pipeline for Gaussian Splatting, specifically within the OpenSplat4D plugin ecosystem [S1, unofficial]. The method is implemented as a compute shader (`FPrepareIndirectArgsCS`) and is used in conjunction with other compute kernels for map, vertex, triangle, and index generation [S2, unofficial]. The broader context includes the use of Nanite-like precision settings and sort intervals to optimize performance in large-scale Gaussian Splatting scenes [S1, unofficial].
