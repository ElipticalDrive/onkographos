# In-block shuffle and coalesced mapping

Also called: Coalesced Cluster-wise Mapping, In-block shuffle radix counting with coalesced cluster-wise mapping, Modified non-coalesced element-wise mapping

## Overview
This method modifies the shuffle steps of radix sorting to achieve coalesced memory access, addressing the performance penalty of random-like scattering patterns in global memory writes [S1, unofficial]. It sets itself apart from standard element-wise mapping by performing local shuffling in shared memory to cluster same-radix elements, followed by a coalesced cluster-wise mapping to global memory, ensuring that the $i$-th thread outputs data to the $i$-th position in a 128-byte aligned region [S1, unofficial].

## How it works
**Inputs:** An array of values (and optionally indices) residing in global memory, partitioned into blocks processed by a thread block [S1, unofficial].
**Outputs:** The sorted array in global memory [S1, unofficial].
**Data Structures:**
*   **Shared Memory Buffer:** A temporary buffer sized to hold one block of data [S1, unofficial].
*   **Cluster Start Positions:** An array storing the global memory offset of the first element for each unique radix combination (cluster) present in the block [S1, unofficial]. The size of this array equals the number of unique radix combinations (e.g., 16 for 4-bit radix, 256 for 8-bit) [S1, unofficial].

**Algorithm Steps:**
The procedure is executed per radix digit pass [S1, unofficial]. Let $N$ be the number of elements in the block, $B$ be the block size (number of threads), and $R$ be the radix size (number of possible digit values) [S1, unofficial].

1.  **Read to Shared Memory:** All threads in the block read their assigned elements from global memory into the shared memory buffer [S1, unofficial].
2.  **Compute Cluster Start Positions:**
    *   Each thread determines the radix digit of its element [S1, unofficial].
    *   Using a parallel prefix sum (scan) or atomic operations within the block, compute the starting global memory offset for each radix cluster [S1, unofficial].
    *   Crucially, only the start position of the *first* element in each cluster is stored [S1, unofficial]. The position of subsequent elements in the same cluster is defined implicitly based on the order of appearance in the input (due to the stability of LSD radix sort) [S1, unofficial].
3.  **Determine Thread-to-Cluster Mapping:**
    *   For each thread, identify which cluster its element belongs to [S1, unofficial].
    *   Determine the corresponding thread index that will handle the output for the specific position in the global memory output buffer [S1, unofficial]. This step ensures that consecutive threads in the warp write to consecutive memory addresses [S1, unofficial].
4.  **Coalesced Cluster-wise Mapping:**
    *   Each thread reads its element from the shared memory buffer [S1, unofficial].
    *   The thread calculates the final global memory destination address [S1, unofficial]. This address is derived from the cluster start position (computed in Step 2) plus the implicit offset of the element within its cluster [S1, unofficial].
    *   The thread writes its element to the calculated global memory address [S1, unofficial].
    *   This step is performed in parallel by all threads, once for each radix combination, ensuring that the $i$-th thread outputs data to the $i$-th position in a 128-byte aligned region [S1, unofficial].

**Pseudocode:**
```python
def in_block_shuffle_coalesced_mapping(data, global_out, shared_mem, cluster_starts, RADIX_SIZE, BLOCK_SIZE):
    tid = threadIdx.x  # [G] Standard GPU thread identifier
    # Step 1: Read data in block to shared memory
    shared_mem[tid] = data[tid]
    __syncthreads()  # [G] Standard thread block synchronization

    # Step 2: Compute the position of first elements in a cluster and corresponding thread
    r = extract_radix(shared_mem[tid])
    # Compute cluster start positions using a parallel prefix sum [G]
    cluster_starts = prefix_sum(r, RADIX_SIZE)
    # Compute implicit offset within cluster by counting preceding elements with same radix [G]
    offset = 0
    for k in range(tid):
        if extract_radix(shared_mem[k]) == r:
            offset += 1
    dest_addr = cluster_starts[r] + offset
    # Map to coalesced thread index: thread i writes to base + i
    target_tid = dest_addr % BLOCK_SIZE
    # Reorder numbers in shared memory to align with target thread indices
    temp_shared = [0] * BLOCK_SIZE
    temp_shared[target_tid] = shared_mem[tid]
    __syncthreads()

    # Step 3: Each thread outputs corresponding data to global memory output
    # Each thread writes its element to the calculated global memory address
    # Since data was reordered, thread i now holds the element for global_out[base + i]
    global_out[cluster_starts[extract_radix(temp_shared[tid])] + compute_offset(tid, temp_shared, extract_radix(temp_shared[tid]))] = temp_shared[tid]
    __syncthreads()
```

**Parameters:**
*   **Alignment Requirement:** Global memory output must be 128-byte aligned to satisfy the coalesced writing condition [S1, unofficial].
*   **Radix Size:** Typically 4-bit (16 buckets) or 8-bit (256 buckets) depending on the hardware and data type [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Memory Footprint:** By storing only the first position of each cluster, the memory footprint for tracking positions is reduced compared to storing all mapping positions [S1, unofficial].
*   **Stability Assumption:** The method relies on the stability of the LSD radix sort [S1, unofficial]. If the sort is not stable, the implicit offset calculation will be incorrect [S1, unofficial].
*   **Shared Memory Contention:** High contention on shared memory during the read and cluster start computation steps can reduce performance [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** The method adds an $O(N)$ shuffling step in shared memory but reduces the global memory write latency by ensuring coalesced accesses [S1, unofficial].
*   **Memory Complexity:** Requires $O(N)$ shared memory for the block data and $O(R)$ shared memory for cluster start positions, where $R$ is the radix size [S1, unofficial].
*   **Performance:** Provides a 50% performance improvement on graphics cards supporting CUDA 1.0 and 1.1 (e.g., G80 and GeForce Quadro FX generation) [S1, unofficial]. On newer cards (e.g., GTX 280), it provides a 10% improvement [S1, unofficial].
*   **Strengths:** Significantly reduces the penalty of non-coalesced writing, which can account for up to 36% of sorting time in standard implementations [S1, unofficial].
*   **Limitations:** Requires additional logic to compute cluster start positions and implicit offsets [S1, unofficial]. The benefit diminishes on newer hardware with better memory controllers [S1, unofficial].

## Background
This technique was proposed to address the inefficiency of random-like scattering patterns in GPU radix sorting, which lead to non-coalesced writing [S1, unofficial]. It is based on the observation that LSD radix sorting is stable, preserving the order of numbers with the same radix combination bits [S1, unofficial]. The method is implemented as an implicit four-way radix counting with an additional in-block shuffle step [S1, unofficial].
