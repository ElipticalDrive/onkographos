# 8-bit Radix Sort

Also called: Bitwise radix sort

## Overview
This method implements the 8-bit digit extraction phase of a wait-free parallel radix sort for GPU execution via Vulkan compute shaders [S1, unofficial]. It sorts 64-bit keys through eight sequential passes, one for each byte, using ping-pong buffer swapping and dynamic buffer resizing to handle variable scene sizes [S1, unofficial]. It builds on the hierarchical scan orchestration of [Wait-Free Radix Sort](1879-wait-free-radix-sort.md).

## How it works
### Inputs and Outputs
*   **Inputs**: `numInstances` (elements to sort), `numVertices` (scene vertex count for allocation), `numRadixSortBlocksPerWorkgroup`, and `sortBufferSizeMultiplier` [S1, unofficial].
*   **Buffers**: `sortKBufferEven/Odd` (64-bit keys), `sortVBufferEven/Odd` (32-bit values), and `sortHistBuffer` (histograms) [S1, unofficial].
*   **Outputs**: Sorted keys and values reside in the ping-pong buffers corresponding to the final pass parity [S1, unofficial].

### Data Structures
**RadixSortPushConstants**
A push constant structure passed to the compute shader containing four `uint32_t` fields: `g_num_elements`, `g_num_blocks_per_workgroup`, `g_shift`, and `g_num_workgroups`, with a total size of `sizeof(RadixSortPushConstants)` [S1, unofficial].

**Buffers**
*   `sortKBufferEven/Odd`: `uint64_t` arrays. Size: `numVertices * sizeof(uint64_t) * sortBufferSizeMultiplier` [S1, unofficial].
*   `sortVBufferEven/Odd`: `uint32_t` arrays. Size: `numVertices * sizeof(uint32_t) * sortBufferSizeMultiplier` [S1, unofficial].
*   `sortHistBuffer`: `uint32_t` arrays. Size: `numWorkgroups * 256 * sizeof(uint32_t)`. The dimension 256 corresponds to the 256 possible values of an 8-bit digit (0-255) per block [G].

### Algorithm Steps
1.  **Initialization**: Calculate `invocationSize = (numInstances + numRadixSortBlocksPerWorkgroup - 1) // numRadixSortBlocksPerWorkgroup`, then align to 256 threads: `alignedInvocationSize = (invocationSize + 255) // 256` [S1, unofficial].
2.  **Loop 8 times**: Execute one pass for each 8-bit chunk of the 64-bit sort keys [S1, unofficial].
3.  **Histogram Phase**: Bind histogram pipeline `sortHistPipeline`, set push constants with `g_shift = i * 8`, dispatch the histogram shader, then barrier on `sortHistBuffer` [S1, unofficial].
4.  **Scatter/Scan Phase**: Bind scatter/scan pipeline `sortPipeline`, dispatch with the same push constants and ping-pong index [S1, unofficial].
5.  **Ping-Pong Synchronization**: If `i % 2 == 0`, barrier `sortKBufferOdd` and `sortVBufferOdd`; else barrier `sortKBufferEven` and `sortVBufferEven` [S1, unofficial].

### Parameters
*   `numRadixSortBlocksPerWorkgroup`: Number of sort blocks per compute workgroup, used to calculate invocation count [S1, unofficial].
*   `sortBufferSizeMultiplier`: Dynamic scaling factor for sort buffer capacity, starts at 1 and grows as needed [S1, unofficial].

### Edge Cases and Pitfalls
*   **Buffer Overflow**: If `numInstances` exceeds the pre-allocated buffer capacity, the algorithm must detect this condition and trigger dynamic buffer resizing [S1, unofficial].

## Subtopics

### Dynamic Sort Buffer Resizing
This variant handles cases where the number of instances exceeds the pre-allocated buffer capacity [S1, unofficial]. It checks if `numInstances > numVertices * sortBufferSizeMultiplier` [S1, unofficial]. If true, it increments `sortBufferSizeMultiplier` in a while loop until the condition fails [S1, unofficial]. It then reallocates `sortKBufferEven/Odd` to `numVertices * sizeof(uint64_t) * sortBufferSizeMultiplier` and `sortVBufferEven/Odd` to `numVertices * sizeof(uint32_t) * sortBufferSizeMultiplier` [S1, unofficial]. It recalculates `globalInvocationSize` and `numWorkgroups` for the histogram buffer and reallocates `sortHistBuffer` to `numWorkgroups * 256 * sizeof(uint32_t)` [S1, unofficial]. Finally, it calls `recordPreprocessCommandBuffer()` and returns `false` to skip the current render pass, forcing a retry with the new buffers [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: $O(8 \cdot N)$, where $N$ is the number of elements, due to the fixed 8 passes for 64-bit keys [S1, unofficial].
*   **Memory Complexity**: $O(N \cdot M)$, where $M$ is the `sortBufferSizeMultiplier`, as buffers scale linearly with element count and dynamic multiplier [S1, unofficial].
*   **Performance**: Performance depends on histogram and scatter/scan kernel efficiency [S1, unofficial]. The ping-pong strategy doubles memory footprint for keys and values but enables overlapping computation and memory access [S1, unofficial].
*   **Strengths**: Handles variable input sizes dynamically and avoids inter-workgroup spin-waiting by relying on the parent's wait-free scan orchestration [S1, unofficial].
*   **Limitations**: Requires significant memory for ping-pong buffers; dynamic resizing incurs overhead and may require restarting the pass [S1, unofficial].
*   **When to use**: When sorting large, variable-sized datasets on GPU where memory allocation flexibility is required [S1, unofficial].
*   **When not to use**: When memory is constrained or the dataset size is known and fixed to a small value [S1, unofficial].
