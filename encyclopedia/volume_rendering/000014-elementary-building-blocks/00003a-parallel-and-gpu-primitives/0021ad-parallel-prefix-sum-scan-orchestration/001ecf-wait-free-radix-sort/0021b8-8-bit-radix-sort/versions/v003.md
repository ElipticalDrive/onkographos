# 8-bit Radix Sort

Also called: Bitwise radix sort

## Overview
This method performs a single pass of a radix sort on 64-bit keys by processing one 8-bit chunk per iteration, designed for GPU execution within a wait-free orchestration framework [S1, unofficial]. It differs from full radix sort implementations by serving as the core digit-processing kernel, relying on parent orchestration for global position calculation and on subgroup-based variants for optimized local partitioning [S1, unofficial][3368-subgroup-based-radix-sort-partition.md].

## How it works
**Inputs:**
- `numInstances`: Number of elements to sort [S1, unofficial].
- `numRadixSortBlocksPerWorkgroup`: Number of sort blocks allocated per compute workgroup [S1, unofficial].
- `sortBufferSizeMultiplier`: Dynamic scaling factor for buffer capacity, initialized to 1 [S1, unofficial].
- Key buffer (`sortKBufferEven/Odd`): Storage for 64-bit keys [S1, unofficial].
- Value buffer (`sortVBufferEven/Odd`): Storage for 32-bit values associated with keys [S1, unofficial].
- Histogram buffer (`sortHistBuffer`): Temporary storage for digit counts [S1, unofficial].

**Outputs:**
- Sorted keys in the alternate ping-pong buffer pair [S1, unofficial].
- Corresponding values in the alternate ping-pong buffer pair [S1, unofficial].

**Data Structures:**
- `RadixSortPushConstants`: A structure containing four `uint32_t` fields:
  - `g_num_elements`: Total number of elements [S1, unofficial].
  - `g_num_blocks_per_workgroup`: Value of `numRadixSortBlocksPerWorkgroup` [S1, unofficial].
  - `g_shift`: Current bit shift amount (0, 8, 16, ..., 56) [S1, unofficial].
  - `g_num_workgroups`: Calculated number of workgroups for the current dispatch [S1, unofficial].
  - Total size: `sizeof(RadixSortPushConstants)` [S1, unofficial].

**Algorithm Steps:**
1. **Buffer Resizing Check:** If `numInstances > scene->getNumVertices() * sortBufferSizeMultiplier`, increment `sortBufferSizeMultiplier` in a loop until the condition fails [S1, unofficial].
2. **Buffer Reallocation:**
   - Reallocate `sortKBufferEven`, `sortKBufferOdd`, `sortVBufferEven`, and `sortVBufferOdd` to size `scene->getNumVertices() * sizeof(uint64_t) * sortBufferSizeMultiplier` for keys and `scene->getNumVertices() * sizeof(uint32_t) * sortBufferSizeMultiplier` for values [S1, unofficial].
   - Recalculate `globalInvocationSize` and `numWorkgroups` based on the new multiplier [S1, unofficial].
   - Reallocate `sortHistBuffer` to size `numWorkgroups * 256 * sizeof(uint32_t)` [S1, unofficial].
   - Record the command buffer and return `false` to skip the current render pass, deferring the sort to the next frame [S1, unofficial].
3. **Loop Execution:** Iterate 8 times, once for each 8-bit chunk of the 64-bit sort keys [S1, unofficial].
4. **Invocation Calculation:** Calculate the number of invocations per pass:
   $$ \text{invocationSize} = \frac{\text{numInstances} + \text{numRadixSortBlocksPerWorkgroup} - 1}{\text{numRadixSortBlocksPerWorkgroup}} $$
   Align to 256 threads:
   $$ \text{alignedInvocations} = \frac{\text{invocationSize} + 255}{256} $$
   [S1, unofficial].
5. **Histogram Dispatch:**
   - Bind the histogram pipeline `sortHistPipeline` [S1, unofficial].
   - Determine ping-pong index: `pingPongIndex = i % 2` [S1, unofficial].
   - Dispatch the histogram shader with push constants and `pingPongIndex` [S1, unofficial].
   - Execute a barrier on `sortHistBuffer` to ensure histogram data is visible [S1, unofficial].
6. **Scatter/Scan Dispatch:**
   - Bind the scatter/scan pipeline `sortPipeline` [S1, unofficial].
   - Dispatch with the same push constants and `pingPongIndex` [S1, unofficial].
7. **Ping-Pong Barrier:**
   - If `i % 2 == 0`, execute barriers on `sortKBufferOdd` and `sortVBufferOdd` [S1, unofficial].
   - Else, execute barriers on `sortKBufferEven` and `sortVBufferEven` [S1, unofficial].

**Pseudocode:**
```python
def radix_sort_8bit_pass(num_instances, num_radix_sort_blocks_per_workgroup, 
                         sort_buffer_size_multiplier, scene_num_vertices, 
                         sort_k_buffer_even, sort_k_buffer_odd, 
                         sort_v_buffer_even, sort_v_buffer_odd, 
                         sort_hist_buffer, sort_hist_pipeline, sort_pipeline):
    # Step 1: Dynamic Buffer Resizing
    while num_instances > scene_num_vertices * sort_buffer_size_multiplier:
        sort_buffer_size_multiplier += 1
    
    # Step 2: Reallocation
    key_buffer_size = scene_num_vertices * sizeof(uint64_t) * sort_buffer_size_multiplier
    value_buffer_size = scene_num_vertices * sizeof(uint32_t) * sort_buffer_size_multiplier
    
    # Reallocate buffers (implementation detail: allocate memory)
    sort_k_buffer_even.allocate(key_buffer_size)
    sort_k_buffer_odd.allocate(key_buffer_size)
    sort_v_buffer_even.allocate(value_buffer_size)
    sort_v_buffer_odd.allocate(value_buffer_size)
    
    # Recalculate workgroups
    global_invocation_size = (num_instances + num_radix_sort_blocks_per_workgroup - 1) // num_radix_sort_blocks_per_workgroup
    aligned_invocations = (global_invocation_size + 255) // 256
    num_workgroups = aligned_invocations
    
    hist_buffer_size = num_workgroups * 256 * sizeof(uint32_t)
    sort_hist_buffer.allocate(hist_buffer_size)
    
    # Record command buffer and skip pass (as per source logic)
    record_preprocess_command_buffer()
    return False

    # Step 3-7: The 8-pass loop (executed if resizing was not triggered)
    for i in range(8):
        # Step 4: Invocation Calculation
        invocation_size = (num_instances + num_radix_sort_blocks_per_workgroup - 1) // num_radix_sort_blocks_per_workgroup
        aligned_invocations = (invocation_size + 255) // 256
        
        # Step 5: Histogram Dispatch
        ping_pong_index = i % 2
        bind_pipeline(sort_hist_pipeline)
        set_push_constants(
            g_num_elements=num_instances,
            g_num_blocks_per_workgroup=num_radix_sort_blocks_per_workgroup,
            g_shift=i * 8,
            g_num_workgroups=aligned_invocations
        )
        dispatch_compute(aligned_invocations, 1, 1)
        barrier(sort_hist_buffer)
        
        # Step 6: Scatter/Scan Dispatch
        bind_pipeline(sort_pipeline)
        set_push_constants(
            g_num_elements=num_instances,
            g_num_blocks_per_workgroup=num_radix_sort_blocks_per_workgroup,
            g_shift=i * 8,
            g_num_workgroups=aligned_invocations
        )
        dispatch_compute(aligned_invocations, 1, 1)
        
        # Step 7: Ping-Pong Barrier
        if ping_pong_index == 0:
            barrier(sort_k_buffer_odd)
            barrier(sort_v_buffer_odd)
        else:
            barrier(sort_k_buffer_even)
            barrier(sort_v_buffer_even)
```

**Parameters:**
- `numRadixSortBlocksPerWorkgroup`: Determines the number of sort blocks per compute workgroup, used to calculate invocation count [S1, unofficial].
- `sortBufferSizeMultiplier`: Starts at 1 and grows as needed to accommodate instance counts exceeding initial allocations [S1, unofficial].

**Edge Cases:**
- If the instance count exceeds the current buffer capacity, the algorithm reallocates buffers and skips the current pass, returning `false` to defer sorting [S1, unofficial].
- Precision issues are mitigated by using 64-bit keys and 32-bit values, with explicit 8-bit chunk processing [S1, unofficial].

## Subtopics

### [Subgroup-based Radix Sort Partition](3368-subgroup-based-radix-sort-partition.md)
This method performs a single pass of a radix sort for a partition of elements (typically 4096) using GPU subgroup ballot operations to compute local offsets, thereby minimizing atomic contention on shared memory. It builds on [8-bit Radix Sort](2599-8-bit-radix-sort.md) by replacing per-element atomic updates with subgroup-level exclusive scans, making it suitable for high-throughput sorting in compute shaders where subgroup size is known and fixed.

### [Radix Sort (GPU)](10404-radix-sort-gpu.md)
A GPU-based integer sorting algorithm implemented via four compute shader passes: histogram counting, prefix sum, digit prefix sum, and scatter. It sorts keys by processing digits in a specific order, using parallel prefix sum (scan) as a subroutine to determine output positions. It is distinct from subgroup-based partitioning methods by explicitly separating the counting, offset calculation, and scattering phases into dedicated shader invocations[3368-subgroup-based-radix-sort-partition.md].

### Dynamic Sort Buffer Resizing
This variant handles dynamic buffer resizing by checking if `numInstances > scene->getNumVertices() * sortBufferSizeMultiplier` [S1, unofficial]. If true, it increments `sortBufferSizeMultiplier` in a while loop until the condition fails, then reallocates key buffers `sortKBufferEven/Odd` and value buffers `sortVBufferEven/Odd` to `scene->getNumVertices() * sizeof(uint64_t) * sortBufferSizeMultiplier` [S1, unofficial]. It recalculates `globalInvocationSize` and `numWorkgroups` for the histogram buffer based on the new multiplier, reallocates `sortHistBuffer` to `numWorkgroups * 256 * sizeof(uint32_t)`, and calls `recordPreprocessCommandBuffer()` to return `false` and skip the current render pass [S1, unofficial].

## Operating characteristics
**Time Complexity:** The algorithm performs 8 passes for 64-bit keys, with each pass involving histogram computation and scatter/scan operations [S1, unofficial]. The dynamic resizing check is $O(1)$ amortized but may trigger reallocation [S1, unofficial].

**Memory Complexity:** Memory usage scales with `scene->getNumVertices() * sizeof(uint64_t) * sortBufferSizeMultiplier` for keys and `scene->getNumVertices() * sizeof(uint32_t) * sortBufferSizeMultiplier` for values, plus `numWorkgroups * 256 * sizeof(uint32_t)` for the histogram buffer [S1, unofficial].

**Performance:** Performance depends on the efficiency of the histogram and scatter/scan pipelines, which are hardware-dependent [S1, unofficial]. The ping-pong buffer strategy allows for overlapping computation and memory access [S1, unofficial].

**Strengths:** The method is designed for GPU execution and avoids inter-workgroup spin-waiting by relying on parent orchestration [S1, unofficial]. Dynamic resizing ensures robustness against varying instance counts [S1, unofficial].

**Limitations:** The algorithm requires reallocation and pass skipping if buffer capacity is exceeded, which may introduce latency [S1, unofficial]. It is a low-level kernel and does not handle global sorting logic itself [S1, unofficial].

**When to Use:** Use this method as a core digit-processing kernel within a larger radix sort implementation on GPU architectures that support the required compute pipelines [S1, unofficial].

**When Not to Use:** Do not use this method for sorting on CPU or for algorithms requiring immediate completion without deferral [S1, unofficial].
