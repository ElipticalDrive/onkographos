# 4-way Parallel Radix Sort

Also called: 2-bit-radix sort, 4-way parallel radix sorting, 4-way radix sort, Fast 4-way parallel radix sorting on GPUs, Four-way radix sorting

## Overview
A hardware-optimized parallel implementation of the radix sort algorithm for GPUs that uses a 4-way (2-bit) radix to reduce the number of passes by half compared to binary-radix sort, eliminating restrictions on key space and supporting arbitrary data types [S1, unofficial]. It lifts limitations on element count and precision compared to previous GPU sorters by processing two bits per iteration across four digits simultaneously [S1, unofficial]. Unlike [8-bit Radix Sort](2599-8-bit-radix-sort.md) which processes 8 bits per pass, this method processes 2 bits per pass, requiring more passes but reducing the complexity of the counting and mapping logic per pass, and unlike [Subgroup-based Radix Sort Partition](3368-subgroup-based-radix-sort-partition.md) which relies on hardware subgroup primitives, this method uses a block-based shared memory approach compatible with older GPU architectures [S1, unofficial].

## How it works
The algorithm is composed of four major subsystems: the order checking function, an implicit four-way radix counting, the prefix sum positioning, and the final mapping [S1, unofficial]. Floating point values are first mapped to integers as proposed by Terdiman [Ter00] before sorting [S1, unofficial]. Sorting is performed in $\lceil n/2 \rceil$ passes, each processing a 2-bit radix pair, from the least significant bit to the most significant one, where $n$ is the number of bits in the key [S1, unofficial].

### Inputs and Outputs
*   **Input:** An array of $N$ keys (32-bit integers or mapped floats) and an optional array of values/indices to be permuted in parallel.
*   **Output:** The keys and associated data sorted in ascending order.

### Data Structures
*   **Input Array:** Array of $N$ elements.
*   **Block Sum Array:** Array of size $\lceil N / \text{blockSize} \rceil \times 4$. Stores the total count of each of the 4 digits (0-3) for each block.
*   **Local Prefix Sum Array:** Array of size $N$. Stores the local prefix sum for each element based on its digit. Only one array is used instead of four separate arrays to reduce memory requirements [S1, unofficial].
*   **Shared Memory Block:** Size `blockSize` elements. Used for in-block shuffling and local counting.

### Parameters
*   **Radix width:** 2 bits (4-way) [S1, unofficial].
*   **Key type:** 32-bit keys, arbitrary $n$-bit numerical values, negative numbers, floating-point numbers, indices, pointers, and general records [S1, unofficial].
*   **blockSize:** 256 elements per block (128 threads, each handling 2 inputs) [S1, unofficial].
*   **bit:** Loop variable for radix sort stages, iterating from 0 to 30 in steps of 2 [S1, unofficial].
*   **Warp size:** 32 threads (assumed for coalesced access) [S1, unofficial].

### Steps
1.  **Initialization:** Initialize `blockSize` to 256. Allocate and initialize 4 block-sum arrays on GPU memory [S1, unofficial].
2.  **Loop:** Iterate `bit` from 0 to 30 (inclusive), incrementing by 2.
3.  **Order Check:** At the beginning of each loop iteration, check if the current input array is already sorted using an optimized reduction operation [S1, unofficial]. If all elements are in order, terminate the loop immediately [S1, unofficial].
4.  **Blocking:** Divide the input data into equal blocks of size `blockSize` [S1, unofficial].
5.  **Parallel Block Processing:** For all blocks in parallel:
    a.  **Counting:** Generate a bit mask for each of the four possible digits (0-3) corresponding to the current 2-bit radix pair extracted from the input data [S1, unofficial].
    b.  **Local Scan:** Apply shared-memory parallel optimized prefix sum computation simultaneously on the four counting bit combinations to compute local frequencies [S1, unofficial].
    c.  **Store Local Prefix:** Store the total count of every element in a block in global memory using a single 'local prefix sum' array of the same size as the input, outputting the corresponding local prefix for each digit to avoid using four separate arrays [S1, unofficial].
    d.  **In-block Shuffle:** Perform in-block shuffling in shared memory to reorder numbers so that those with the same radix combination bits are clustered together in sorted order [S1, unofficial]. This enables coalesced global writing [S1, unofficial].
    e.  **Output Block Sums:** Output the total number of each scan path (count of each digit 0-3) to the block sum array [S1, unofficial].
6.  **Global Prefix Sum:** Perform scan prefix sum on the block sum array to compute global positions [S1, unofficial].
7.  **Mapping:** Compute the new position for elements of radix sort and map the element to the right position using the derived indices [S1, unofficial].
    *   The sorted position is calculated as:
        $$ \text{Sorted Position} = P_d[n] + m $$
        Where $P_d[n]$ is the prefix block sum for digit $d$ at block $n$, and $m$ is the local prefix sum value for the element in that block [S1, unofficial].
8.  **Increment:** Increment `bit` by 2.

    keys: list of integers (or mapped floats)
    values: list of associated data
    n: number of elements
    """
    blockSize = 256
    numBlocks = (n + blockSize - 1) // blockSize
    
    # Allocate block-sum array: size numBlocks * 4
    # Each block stores counts for digits 0, 1, 2, 3

    # Local prefix sum array: size n

    # Loop for each 2-bit radix pair (bits 0-1, 2-3, ..., 30-31)
    for bit in range(0, 31, 2):
        # 1. Order Checking
        if is_sorted(keys, n):

        # 2. Process Blocks in Parallel
        for block_id in range(numBlocks):
            start_idx = block_id * blockSize
            end_idx = min(start_idx + blockSize, n)
            block_size_actual = end_idx - start_idx
            
            # Shared memory simulation for the block
            s_data_keys = keys[start_idx : end_idx]
            s_data_vals = values[start_idx : end_idx]
            
            # Counters for digits 0-3
            cnt = [0] * 4
            
            # Extract digits and count
            for i in range(block_size_actual):
                # Extract 2 bits from key
                digit = (keys[start_idx + i] >> bit) & 0x3
                cnt[digit] += 1
                
            # Store block sums
            block_sums[block_id * 4 + 0] = cnt[0]
            block_sums[block_id * 4 + 1] = cnt[1]
            block_sums[block_id * 4 + 2] = cnt[2]
            block_sums[block_id * 4 + 3] = cnt[3]
            
            # Compute local prefix sums for this block
            # We need the cumulative count of digits < current digit within the block
            # plus the offset from previous blocks (handled later)

            local_offsets = [0] * 4
            local_prefix_sums_block = [0] * block_size_actual

                local_prefix_sums_block[i] = local_offsets[digit]
                local_offsets[digit] += 1

            # so that elements with same digit are clustered

                current_pos += cnt[d]

            # We need to preserve order within the cluster (stability)
            # Use the local prefix sum to determine position within cluster
            # Actually, the local prefix sum computed above is the index within the cluster
            # So position = digit_starts[digit] + local_prefix_sums_block[i]

                digit = (keys[start_idx + i] >> bit) & 0x3
                pos_in_cluster = local_prefix_sums_block[i]
                global_pos_in_block = digit_starts[digit] + pos_in_cluster
                s_out_keys[global_pos_in_block] = keys[start_idx + i]
                s_out_vals[global_pos_in_block] = values[start_idx + i]
                
            # Copy back to global memory
            for i in range(block_size_actual):

### Edge Cases and Pitfalls
*   **Non-coalesced scattering:** Non-coalesced scattering during global shuffle reduces efficiency. This is addressed by in-block shuffling to create clusters that allow coalesced writing [S1, unofficial].
*   **General Record Sorting:** To handle general record sorting optimally, the method uses index sorting to avoid moving large data structures, exploiting hardware features like instant thread switching and fast random texture access [S1, unofficial].
*   **Memory Requirements:** Using a single local prefix sum array instead of four separate arrays reduces memory requirements [S1, unofficial].
*   **Redundancy:** Redundancy is minimized and slow global memory access is minimized by using a merging strategy that exploits fast shared-memory as the computational bridge [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(n \cdot \lceil n_{bits}/2 \rceil)$, where $n_{bits}$ is the number of bits in the key. For 32-bit keys, this is 16 passes.
*   **Memory Complexity:** $O(n)$ for input/output arrays, plus $O(n)$ for local prefix sums and $O(N/blockSize \cdot 4)$ for block sums.
*   **Performance:** The algorithm outperforms all known GPU-based sorting systems by about a factor of two at the time of publication [S1, unofficial]. It is almost twice as fast as the fastest known approaches on the GPU (Sintorn/Assarsson, Sengupta, Le Grand) [S1, unofficial].
*   **Strengths:** Eliminates restrictions on key space, supports arbitrary data types, early termination if sorted, coalesced memory access via in-block shuffling.
*   **Limitations:** Requires more passes than 8-bit radix sort, but each pass is simpler. Relies on shared memory, so block size is limited by hardware constraints (e.g., 16KB shared memory).
*   **When to use:** When sorting large datasets on GPUs, especially when data types are arbitrary or when early termination is beneficial (e.g., collision detection in evolving systems).
*   **When not to use:** When memory bandwidth is extremely constrained and the overhead of multiple passes is prohibitive compared to a single 8-bit pass, or when hardware supports more efficient subgroup-based operations.

## Background
The paper was submitted to COMPUTER GRAPHICS Forum in February 2009 by Linh Ha, Jens Krüger, and Cláudio T. Silva from the University of Utah [S1, unofficial]. It was developed to address the need for efficient sorting in physics-based simulations for virtual environments and computer games, such as collision detection for thousands of falling chairs, millions of particles, and n-body galaxy problems [S1, unofficial]. It improves upon previous GPU sorting approaches like those in the CUDPP library which used binary-radix sort, and Sintorn/Assarsson which required atomic counting [S1, unofficial].
