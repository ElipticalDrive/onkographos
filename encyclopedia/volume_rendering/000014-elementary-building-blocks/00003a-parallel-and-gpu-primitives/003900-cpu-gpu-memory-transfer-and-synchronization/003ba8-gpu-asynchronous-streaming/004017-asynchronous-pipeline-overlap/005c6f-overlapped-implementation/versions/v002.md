# Overlapped Implementation

Also called: Asynchronous Disk Access and Texture Loading, Multi-threaded overlapped rendering, asynchronous loading

## Overview
The Overlapped Implementation is a rendering technique that hides data transfer overhead by fully overlapping data loading, volume slicing, and rendering [S1]. It addresses the performance bottleneck of out-of-core volume roaming, where sequential execution of cache scanning, data fetching, and rendering drastically reduces frame rates [S1]. It sets itself apart from sequential implementations by using multi-threading and asynchronous I/O to allow rendering to proceed while data is still being fetched from storage or the network [S1].

## How it works
**Inputs and Outputs:**
Input: A request for a set of volume bricks from the volume renderer; access to a hierarchical cache system (DHCS) and storage (local disks, network) [S1].
Output: Rendered frames of volume slices; updated local memory state for inter-node communication [S1].

**Numbered Steps:**
The system uses a multi-threaded architecture with six threads [S1].
1. The volume renderer requests a series of bricks from the DHCS [S1].
2. The DHCS scans its cache hierarchy to locate the bricks [S1].
3. The DHCS launches asynchronous data loads. The Async Load HDD to RAM thread uses Linux `libaio` for disk I/O [S1]. The Async Load LAN to RAM thread uses a TCP client-server protocol for network fetching [S1].
4. While data is loading, the volume renderer computes proxy geometries for the requested bricks. In hardware-accelerated rendering, these are view-aligned back-to-front slices [S1].
5. As soon as a brick is loaded into graphics memory, the volume renderer renders it in back-to-front order. Rendering begins for the first loaded bricks before all requests are satisfied [S1].
6. Once all asynchronous loads are launched, the local memory state at the end of the current frame is known. This allows binary all-to-all communication to be launched overlapped with the rendering process [S1].

**Edge Cases and Pitfalls:**
OpenGL context restrictions prevent the GPU loader thread from loading textures directly into the main application's rendering context; a new context with resource sharing must be created [S1].

**Pseudocode:**
```python
import threading

# Standard OpenGL context creation with resource sharing [G]
def create_shared_gl_context():
    # In practice, this calls glXCreateContext or wglCreateContext with a share list.
    return {"type": "gl_context", "shared": True}

class OverlappedRenderer:
    def __init__(self):
        self.shared_context = create_shared_gl_context()
        self.dhcs_thread = threading.Thread(target=self.dhcs_worker)
        self.renderer_thread = threading.Thread(target=self.render_worker)
        self.gpu_loader_thread = threading.Thread(target=self.gpu_loader_worker, args=(self.shared_context,))
        self.hdd_async_thread = threading.Thread(target=self.hdd_async_io)
        self.lan_async_thread = threading.Thread(target=self.lan_async_io)

    def start(self):
        self.dhcs_thread.start()
        self.renderer_thread.start()
        self.gpu_loader_thread.start()
        self.hdd_async_thread.start()
        self.lan_async_thread.start()

    def request_bricks(self, brick_ids):
        # 1. Volume renderer requests bricks from DHCS [S1]
        self.dhcs_thread.queue_request(brick_ids)

    def dhcs_worker(self):
        # 2. DHCS scans cache hierarchy [S1]
        # 3. DHCS launches asynchronous data loads [S1]
        # 6. Launch all-to-all communication overlapped with rendering [S1]
        while True:
            brick_ids = self.dhcs_thread.get_request()
            locations = self.scan_cache_hierarchy(brick_ids)
            for brick_id, location in locations.items():
                if location == 'HDD':
                    self.hdd_async_thread.load(brick_id)
                elif location == 'LAN':
                    self.lan_async_thread.load(brick_id)
            self.launch_all_to_all_communication()

    def render_worker(self):
        # 4. Compute proxy geometries (view-aligned back-to-front slices) [S1]
        # 5. Render bricks in back-to-front order as soon as loaded [S1]
        while True:
            proxies = self.compute_proxy_geometries()
            for brick in self.get_loaded_bricks():
                if brick.ready:
                    self.render_slice(brick, proxies[brick.id])

    def gpu_loader_worker(self, context):
        # GPU loader thread cannot load textures directly in main context [S1]
        with context:
            while True:
                brick = self.get_bricks_ready_for_gpu()
                if brick:
                    self.upload_texture_to_gpu(brick.data)

    def hdd_async_io(self):
        # Async Load HDD to RAM uses Linux libaio [S1]
        while True:
            brick_id = self.hdd_async_thread.get_request()
            data = self.read_from_disk_async(brick_id)
            self.mark_as_loaded(brick_id, data)

    def lan_async_io(self):
        # Async Load LAN to RAM uses TCP client-server protocol [S1]
        while True:
            brick_id = self.lan_async_thread.get_request()
            data = self.fetch_from_network_async(brick_id)
            self.mark_as_loaded(brick_id, data)
```

## Operating characteristics
Sequential implementation (synchronous requests) dramatically decreases performance because data loading, cluster memory state update, volume slicing, and rendering are executed serially [S1]. The overlapped implementation optimizes volume roaming by hiding these latencies [S1]. Using two Gigabit Ethernet network interfaces per node accelerates data fetching by a factor of 4 compared to directly accessing local disks [S1]. Enables optimal volume roaming for extremely large datasets by preventing the renderer from stalling on I/O [S1]. Requires complex multi-threading and context management (specifically OpenGL resource sharing) [S1].

## Background
The Overlapped Implementation was proposed by Castanié et al. in the paper "Distributed Shared Memory for Roaming Large Volumes" [S1]. It builds upon their previous cache system [8] to add fully asynchronous loading in memory and graphics memory [S1]. The work is part of the broader field of Distributed Shared Memory (DSM) for PC clusters, aiming to handle large time-varying volumes from scientific domains like seismic captors, CT scanners, and numerical simulations (FEM, CFD) [S1].
