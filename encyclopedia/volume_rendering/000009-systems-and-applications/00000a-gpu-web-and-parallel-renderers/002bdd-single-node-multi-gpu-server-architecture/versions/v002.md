# Single Node Multi-GPU/Server Architecture

Also called: Chromium Framework Cluster Rendering, Cluster rendering with OpenGL Stream Processing Units, Remote visualization via Chromium, Sarton et al. approach, Single node server with multiple GPUs/CPUs (Sarton et al.)

## Overview
This architecture enables interactive visualization of large volumetric datasets on resource-constrained mobile clients by offloading all storage and computation to a server system [S1, S2, unofficial]. It distinguishes itself from distributed cluster approaches by utilizing a single server node equipped with multiple GPUs and CPUs, managed via the Chromium framework to virtualize OpenGL execution across local hardware [S1, S2, unofficial]. Unlike pure client-side renderers that require significant local GPU power, this method transmits compressed image data to lightweight clients [S1, unofficial].

## How it works
**Inputs:** Large volumetric dataset (exceeding local workstation capacity), client device with limited RAM and wireless connectivity, server node with multiple GPUs/CPUs.
**Outputs:** Final composited image displayed on the client device.

**Data Structures:**
*   **OpenGL Stream:** A packed representation of OpenGL commands generated by the client or server, transmitted over TCP [S1, unofficial].
*   **Image Buffer:** Rendered framebuffer content from each GPU, compressed using ZLIB or JPEG [S1, unofficial].
*   **Client State:** Minimal state management for user interactions (mapping/rendering parameters) exchanged via separate TCP sockets [S1, unofficial].

**Steps:**
1.  **Server Setup:** Configure a single server node with multiple GPUs and CPUs. Install the Chromium framework to provide a virtualized interface to the hardware via the OpenGL API [S1, S2, unofficial].
2.  **Client Initialization:** The client application initializes with minimal resources. Note: While the original proposal suggested 32 MB RAM, practical implementation requires at least 128 MB RAM and a graphics card for the client to handle decompression and display [S1, unofficial].
3.  **Stream Generation:** The client generates OpenGL streams representing the desired view and interaction parameters [S1, unofficial].
4.  **Stream Management:** The server manages incoming network connections, parsing the packed OpenGL streams [S1, unofficial].
5.  **SPU Execution:** The server utilizes OpenGL Stream Processing Units (SPUs), implemented as dynamically loadable libraries, to transform and execute the streams [S1, unofficial]. Each GPU on the server renders its assigned portion of the scene directly on local hardware [S1, unofficial].
6.  **Compositing:** Image buffers are read back from the cluster nodes (GPUs) and transmitted to a final compositing server to combine into a single final image [S1, unofficial].
7.  **Compression:** The resulting image is compressed using ZLIB or JPEG algorithms [S1, unofficial].
8.  **Transmission:** Compressed image data is streamed to the client over a TCP channel via a wireless link [S1, unofficial].
9.  **Client Decompression and Display:** The client receives the encoded information, decompresses it using integrated decoders, and renders the raw image to the screen [S1, unofficial].
10. **Interaction Loop:** User interactions are captured by the visualization interface, which supervises the render area. Parameters are exchanged over separate TCP socket connections to update the next frame [S1, unofficial].

**Parameters:**
*   **Client RAM:** 32 MB is theoretically sufficient for the client application logic, but 128 MB RAM and a graphics card are necessary for practical implementation [S1, unofficial].
*   **Compression:** ZLIB and JPEG are used for image transmission [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Network Latency:** Wireless transmission of compressed images introduces latency, potentially affecting interactivity [S1, unofficial].
*   **Client Hardware:** The original 32 MB RAM specification is insufficient for modern mobile devices; 128 MB RAM and GPU support are required [S1, unofficial].
*   **Compression Artifacts:** JPEG compression may introduce artifacts in volumetric visualizations, particularly in low-contrast regions [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Rendering time depends on the server's GPU capacity and the complexity of the volumetric dataset. Network transmission time depends on image size and compression ratio.
*   **Memory Complexity:** Server memory usage scales with dataset size and number of GPUs. Client memory usage is minimal, primarily for image buffers and decompression buffers.
*   **Strengths:** Enables visualization of large datasets on low-end mobile devices; leverages powerful server hardware; reduces client-side computational burden.
*   **Limitations:** Requires network connectivity; latency can impact interactivity; client hardware requirements are higher than originally proposed; single point of failure at the server.
*   **When to use:** Remote visualization of large scientific datasets on mobile or low-power devices.
*   **When not to use:** Offline scenarios without network access; real-time applications requiring extremely low latency; datasets that fit within local workstation memory.

## Background
The technique was proposed by Lamberti et al. [S1, unofficial] as a method for visualizing big models interactively using Personal Digital Assistants (PDAs). It utilizes the Chromium framework to unify the rendering power of a graphics accelerator cluster. Sarton et al. [S2, unofficial] presented a similar approach using a single node server with multiple GPUs and CPUs instead of a distributed cluster. This architecture is part of the broader field of remote visualization and distributed rendering systems.
