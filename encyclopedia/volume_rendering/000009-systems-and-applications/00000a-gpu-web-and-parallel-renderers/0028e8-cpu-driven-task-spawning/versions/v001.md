# CPU-Driven Task Spawning

Also called: CPU-controlled GPU execution, CPU-driven thread spawning

## Overview
CPU-driven task spawning is a rendering architecture where the CPU acts as the central governor, deciding when and how GPU tasks are launched, while the GPU executes these work requests as a coprocessor [S1, unofficial]. This model solves the problem of centralized control by leveraging the CPU's role as the system's hub for memory, storage, and peripheral management [S1, unofficial]. It is distinct from GPU-driven approaches because the GPU cannot generate new work requests on its own, creating a dependency on the CPU for every dispatch [S1, unofficial]. This contrasts with siblings like [WebSplatter](1741-websplatter.md) or [ClearView (Unified) Renderer](2460-clearview-unified-renderer.md), which may utilize more autonomous or hybrid execution models to mitigate CPU bottlenecks.

## How it works
The method relies on the CPU issuing commands to the GPU, which then executes them. Due to high communication latency, pure synchronous control is often ineffective, leading to variants like asynchronous and indirect submission.

**Inputs and Outputs:**
*   **Input:** CPU-side decision logic, task parameters (initially), and GPU memory addresses (for indirect submission).
*   **Output:** GPU execution of workloads (compute, rasterization, ray tracing).

**Data Structures:**
*   **Submission Queue:** A buffer or list where the CPU places commands before they are processed by the GPU driver/hardware.
*   **Indirect Parameter Buffer:** A GPU-accessible memory region containing the actual parameters (e.g., workgroup counts, vertex counts) for indirect submissions [S1, unofficial].

**Steps:**
1.  **Command Generation:** The CPU determines the necessary work for the current frame or pipeline stage.
2.  **Submission:** The CPU places the command into a submission queue.
    *   *Standard:* Parameters are embedded in the command.
    *   *Indirect:* The command contains a pointer to a GPU memory location [S1, unofficial].
3.  **Execution (GPU):**
    *   *Standard:* The GPU reads the embedded parameters and executes the task.
    *   *Indirect:* The GPU reads the pointer, fetches the parameters from the GPU memory buffer, and then executes the task [S1, unofficial].
4.  **Synchronization:** If dependencies exist, barriers are inserted.
    *   *Coarse:* A barrier forces all subsequent tasks to wait for all preceding tasks in the same queue [S1, unofficial].
    *   *Queue-Specific:* If multiple queues are used, barriers only enforce dependencies between tasks within the same queue [S1, unofficial].

**Formulas:**
*   **Latency:** $L_{CPU-GPU} \approx 20\text{--}30 \, \mu s$ for an empty round-trip submission (CPU $\to$ GPU $\to$ CPU) [S1, unofficial].

**Parameters:**
*   **Queue Limits:**
    *   Vulkan: 24 queues (Nvidia), 16 queues (AMD), 5 queues (Intel) [S1, unofficial].
    *   CUDA: Unlimited logical streams, mapped to 32 internal hardware queues [S1, unofficial].
*   **Task Size:** Can be set to zero to cancel a submission, though submission overhead remains [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Latency Bottleneck:** The 20–30 µs latency is significant compared to sub-nanosecond CPU/GPU clocks, making synchronous control ineffective for pipelines with fine-grain micro-dependencies [S1, unofficial].
*   **Indirect Submission Overhead:** If the number of pipeline passes is unknown, the CPU must issue indirect submissions for the maximum possible passes and cancel unnecessary ones, incurring overhead repeatedly [S1, unofficial].
*   **Barrier Granularity:** Barriers block all tasks submitted after them, not just dependent ones, leading to unnecessary stalling [S1, unofficial].
*   **Queue Limitations:** The limited number of queues (e.g., max 24 in Vulkan) is insufficient for micro-dependencies at the GPU core granularity (modern GPUs have 50–100 cores) [S1, unofficial].
*   **Hybrid Complexity:** Indirect submission is an "awkward hybrid" where the GPU controls parameters but cannot initiate submissions, making it error-prone [S1, unofficial].

## Subtopics

### [Asynchronous Submission](5531-asynchronous-submission.md)
A model where the CPU places GPU commands into a queue and the GPU executes them as resources become available, but the CPU returns immediately without waiting for completion. This mitigates the CPU-GPU latency bottleneck by allowing the CPU to continue processing other tasks while the GPU works. It is a partial solution to the latency issues inherent in synchronous CPU-driven spawning. See [Asynchronous Submission](5531-asynchronous-submission.md).

### Indirect Submission
A semi-GPU-driven variant where the CPU emits commands, but the parameters (e.g., workgroup count, vertex count) are stored in GPU memory and read by the GPU at execution time [S1, unofficial].
*   **Mechanism:** A first pass writes parameters to a GPU memory pointer; a barrier ensures completion before the second pass (the actual command) executes [S1, unofficial].
*   **Capabilities:** Advanced implementations (DirectX ExecuteIndirect, Vulkan `VK_EXT_device_generated_commands`) can indirectly select shaders, bind resources, and set rasterization states [S1, unofficial].
*   **Limitations:** The GPU cannot create *new* submissions. If pass counts are unknown, the CPU must pre-allocate maximum passes and cancel unused ones, paying overhead for each [S1, unofficial]. It is considered unintuitive and error-prone due to its hybrid nature [S1, unofficial].

### Multiple submission queues
A solution to coarse barrier granularity where commands are submitted to specific queues rather than a single global queue [S1, unofficial].
*   **Mechanism:** Barriers only enforce dependencies between tasks within the *same* queue. Tasks in different queues can run independently [S1, unofficial].
*   **Limits:** The number of queues is restricted (Vulkan: 24 Nvidia/16 AMD/5 Intel; CUDA: 32 internal) [S1, unofficial]. This is insufficient for micro-dependencies across the 50–100 cores of modern GPUs [S1, unofficial].

## Operating characteristics
*   **Latency:** High CPU-GPU round-trip latency (20–30 µs) is the primary bottleneck, regardless of whether the GPU is integrated or dedicated [S1, unofficial].
*   **Complexity:** Managing dependencies via barriers and queues is complex. Barriers cause coarse-grained stalling, and queue management is limited by hardware constraints [S1, unofficial].
*   **Flexibility:** Indirect submission offers flexibility in parameter determination but lacks the ability to dynamically spawn new tasks from the GPU [S1, unofficial].
*   **Suitability:** Best suited for coarse-grained parallelism where dependencies are minimal or can be managed via multiple queues. Unsuitable for fine-grain micro-dependencies or pipelines requiring dynamic task generation from the GPU [S1, unofficial].

## Background
The CPU-driven model stems from the traditional view of GPUs as coprocessors [S1, unofficial]. As GPUs evolved to support more complex workloads, the limitations of this model—specifically high latency and lack of GPU-initiated work—became apparent. Variants like indirect submission and multiple queues were developed to patch these issues, though they remain imperfect solutions compared to fully GPU-driven approaches [S1, unofficial].
