# Asynchronous Submission

Also called: GPU command queue submission, Non-blocking GPU submission

## Overview
Asynchronous submission is a model where GPU commands are placed into a queue and executed by the GPU as soon as required resources are available, but they return immediately from the point of view of the CPU [S1, unofficial]. It solves the problem of high CPU-GPU communication latency inherent in synchronous control, allowing the CPU and GPU to work concurrently [S1, unofficial]. Unlike synchronous submission, which blocks the CPU until the GPU completes a task, asynchronous submission removes round-trip latency and enables parallel execution of many small tasks or chaining of big tasks [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A stream of GPU commands (e.g., kernel launches, memory copies) generated by the CPU.
*   **Output:** Immediate return of the submission function to the CPU; execution of commands on the GPU hardware.

**Data Structures:**
*   **Command Queue:** A buffer managed by the driver/runtime where the CPU appends command descriptors. The exact layout is implementation-dependent (driver-specific), but logically it is a FIFO structure [S1, unofficial].
*   **Event Objects:** Optional objects used to track completion status for synchronization (e.g., for split barriers or indirect submission) [S1, unofficial].

**Steps:**
1.  The CPU constructs a command descriptor (e.g., kernel arguments, grid/block dimensions) [S1, unofficial].
2.  The CPU appends this descriptor to the GPU command queue [S1, unofficial].
3.  The submission function returns immediately to the CPU [S1, unofficial].
4.  The GPU driver/hardware dequeues commands and executes them as soon as resources (cores, memory bandwidth) are available [S1, unofficial].

**Formulas:**
*   None specified in sources.

**Parameters:**
*   Not given in the sources.

**Edge Cases and Pitfalls:**
*   **RAW/WAR Dependencies:** If Task B uses results from Task A (Read After Write) or writes to memory read by Task A (Write After Read), submissions cannot overlap safely [S1, unofficial]. Barriers must be used, but they stall the GPU [S1, unofficial].
*   **Dynamic Dispatch Parameters:** If Task A computes parameters (e.g., thread count) for Task B, the CPU must wait for Task A to complete before submitting Task B, reintroducing CPU-GPU communication delay [S1, unofficial]. This necessitates indirect submission [S1, unofficial].
*   **Barrier Granularity:** Modern GPUs have 50–100 cores (SMs/WGPs/Xe Cores). Queues cannot enforce dependencies at the core granularity; barriers enforce global dependencies, potentially creating pipeline bubbles if micro-dependencies exist [S1, unofficial].

**Pseudocode:**
```python
# Example of asynchronous submission flow
def submit_task_async(queue, kernel_args):
    """
    Appends a task to the GPU queue and returns immediately.
    """
    # 1. Construct command descriptor
    command = {
        'kernel': kernel_args.kernel,
        'grid': kernel_args.grid,
        'block': kernel_args.block,
        'args': kernel_args.data
    }
    
    # 2. Append to queue (Driver handles the actual queueing)
    queue.append(command)
    
    # 3. Return immediately
    return

def submit_with_barrier(queue, task_a, task_b):
    """
    Submits Task A, then a barrier, then Task B.
    Task B waits for Task A to complete.
    """
    # Submit Task A
    submit_task_async(queue, task_a)
    
    # Insert barrier command
    # The GPU will stall execution of subsequent commands until Task A finishes
    queue.append_barrier()
    
    # Submit Task B
    submit_task_async(queue, task_b)
```

## Subtopics

### Split Barriers
A mechanism that splits the barrier command into two distinct commands: `Set` and `Wait` [S1, unofficial]. Tasks submitted after `Wait` will wait for tasks submitted before `Set`, but tasks submitted between `Set` and `Wait` can run independently [S1, unofficial]. This adds flexibility by allowing independent work to be scheduled in the gap between the two barrier halves [S1, unofficial].
*   **Parameters:** `Set` and `Wait` commands take an event parameter to allow for multiple split barriers to run in parallel [S1, unofficial].
*   **Pitfalls:** Requires careful advance planning to schedule independent work before submitting the `Wait` command, making it difficult to reason with [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** Submission is $O(1)$ from the CPU perspective as it returns immediately [S1, unofficial].
*   **Memory Complexity:** Depends on the size of the command queue, which scales with the number of pending tasks [S1, unofficial].
*   **Performance:** Improves GPU utilization by removing round-trip latency and allowing parallel execution of small tasks or overlapping of big tasks [S1, unofficial].
*   **Strengths:** High concurrency, reduced CPU idle time, better hardware utilization [S1, unofficial].
*   **Limitations:** Dependency management is complex; barriers can stall the GPU; dynamic dispatch requires additional mechanisms like indirect submission [S1, unofficial].
*   **When to use:** Default mode for all modern GPU APIs due to performance benefits [S1, unofficial].
*   **When not to use:** When strict sequential execution is required without the overhead of dependency management, or when CPU-GPU synchronization latency is acceptable and simplicity is prioritized.

## Background
Asynchronous submission is the default model in all modern GPU APIs [S1, unofficial]. It was developed to address the high CPU-GPU communication latency caused by the many layers of drivers that commands must go through [S1, unofficial]. The concept of indirect submission was invented as a semi-GPU-driven model to solve the problem of dynamic dispatch parameters in the asynchronous model [S1, unofficial].
