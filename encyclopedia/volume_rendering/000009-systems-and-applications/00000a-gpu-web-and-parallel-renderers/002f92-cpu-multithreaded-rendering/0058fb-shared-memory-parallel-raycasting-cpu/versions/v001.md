# Shared-Memory Parallel Raycasting (CPU)

Also called: Multi-Core CPU Implementation, POSIX Threads Raycasting

## Overview
Shared-memory parallel raycasting on CPUs is a volume rendering technique that distributes the computational load of ray casting and integration across multiple threads within a single process using a shared-memory programming model [S1, unofficial]. It solves the performance bottleneck of sequential raycasting by decomposing the output image into spatially disjoint work blocks, allowing multiple cores to render pixels concurrently [S1, unofficial]. It is distinguished from GPU-based parallel raycasting by its use of explicit thread management (e.g., POSIX threads) and dynamic work queues to handle load imbalance, rather than relying on hardware-level SIMT execution [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar/vector volume dataset, camera parameters (view matrix, projection matrix), and a user-specified number of rendering threads.
*   **Output:** A 2D final image buffer containing the composited color and opacity for each pixel.

**Data Structures:**
1.  **Shared-Memory Data Structure:** A global memory region visible to all threads. It stores precomputed values common to all rendering tasks, such as the inverse of the model-view matrix [S1, unofficial].
2.  **Work Queue:** A thread-safe queue containing work assignments (blocks of pixels) to be processed by slave threads [S1, unofficial].
3.  **Final Image Buffer:** A shared memory buffer where threads write the final pixel color and opacity [S1, unofficial].

**Numbered Steps:**
1.  **Initialization:** The application launches a user-specified number of rendering threads. Each thread acts as a "slave" and enters an event loop [S1, unofficial].
2.  **Precomputation:** The master thread computes values common to all slaves (e.g., inverse model-view matrix) and stores them in the shared-memory data structure [S1, unofficial].
3.  **Work Assignment Generation:** The master thread computes a list of work assignments. Each assignment is a spatially disjoint region of the final image (a work block) [S1, unofficial].
4.  **Synchronization:** A pair of shared-memory barriers synchronizes communication between the master and slave threads in the event loop [S1, unofficial].
5.  **Execution Loop (Slave Threads):**
    a.  The master thread signals slave threads to begin rendering [S1, unofficial].
    b.  Each slave thread requests a work block from the work queue [S1, unofficial].
    c.  The thread performs raycasting over all pixels in the assigned block, performing color and opacity integration along each ray [S1, unofficial].
    d.  The thread writes the results to the final image buffer [S1, unofficial].
    e.  The thread returns to step (b) to request the next work block until the queue is empty [S1, unofficial].
6.  **Completion:** The master thread waits for all slave threads to finish their current blocks (potentially using a barrier if "block synchronization" is enabled) and then proceeds to the next frame or task [S1, unofficial].

**Formulas:**
*   **Ray Casting:** For each pixel $(u, v)$ in a work block, a ray is generated. The volume is sampled along the ray. The color $C$ and opacity $\alpha$ are integrated using standard volume rendering integration (Levoy’s formulation) [S1, unofficial]:
    $$ C = \sum_{i=0}^{n-1} c_i \alpha_i \prod_{j=0}^{i-1} (1 - \alpha_j) $$
    Where $c_i$ and $\alpha_i$ are the color and opacity at sample $i$, and $n$ is the number of samples along the ray [S1, unofficial].

**Parameters:**
*   **Work Block Tessellation:** The user specifies the size of the work blocks. Examples include $4 \times 4$, $8 \times 8$, $512 \times 1$, or $1 \times 512$ pixels [S1, unofficial].
*   **Thread Count:** User-specified number of rendering threads, typically matching the number of available CPU cores [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Load Imbalance:** Static work assignment (round-robin) can suffer from load imbalance if the volume data or camera view causes some rays to require significantly more computation (e.g., due to empty space skipping or complex transfer functions) than others [S1, unofficial].
*   **Memory Contention:** If not managed carefully, concurrent writes to the final image buffer or shared data structures can cause cache thrashing or race conditions [S1, unofficial].
*   **Precision:** Standard floating-point precision is used for ray marching and integration [S1, unofficial].

```python
import math

# Global shared state
shared_data = {}  # Stores inverse model-view matrix, etc.
work_queue = queue.Queue()
final_image_buffer = None
barrier = threading.Barrier()
stop_event = threading.Event()

def compute_shared_data():
    """Master thread computes common values."""
    # Example: Compute inverse model-view matrix
    shared_data['inv_mv_matrix'] = compute_inverse_model_view_matrix()

def generate_work_blocks(image_width, image_height, block_size):
    """Master thread generates work assignments."""
    blocks = []
    for y in range(0, image_height, block_size):
        for x in range(0, image_width, block_size):
            blocks.append((x, y, min(x + block_size, image_width), min(y + block_size, image_height)))
    return blocks

def raycast_pixel(u, v, inv_mv_matrix, volume_data):
    """Cast a single ray and integrate color/opacity."""
    # Generate ray from camera through pixel (u, v)
    ray_origin, ray_direction = generate_ray(u, v, inv_mv_matrix)
    
    color = [0.0, 0.0, 0.0]
    alpha = 0.0
    
    # March along ray

    while t < ray_length and alpha < 1.0:
        sample = trilinear_sample(volume_data, ray_origin + ray_direction * t)
        c, a = apply_transfer_function(sample)
        
        # Volume rendering integration
        weight = a * math.exp(-alpha)
        color = color + c * weight
        alpha = alpha + a * (1.0 - alpha)
        
        t += step_size
        
    return color, alpha

def slave_thread_event_loop(thread_id):
    """Slave thread event loop."""
    while not stop_event.is_set():
        try:
            # Request work block from queue
            block = work_queue.get(timeout=1.0)
        except queue.Empty:
            continue
            
        x_min, y_min, x_max, y_max = block
        
        # Process all pixels in the block
        for y in range(y_min, y_max):
            for x in range(x_min, x_max):
                color, alpha = raycast_pixel(x, y, shared_data['inv_mv_matrix'], volume_data)
                final_image_buffer[y][x] = (color, alpha)
                
        # Optional: Block synchronization barrier
        # barrier.wait()
        
        work_queue.task_done()

def master_thread_render(image_width, image_height, num_threads, block_size):
    """Master thread manages rendering."""
    global final_image_buffer
    final_image_buffer = [[None for _ in range(image_width)] for _ in range(image_height)]
    
    # 1. Precompute shared data
    compute_shared_data()
    
    # 2. Generate work blocks
    blocks = generate_work_blocks(image_width, image_height, block_size)
    
    # 3. Populate work queue
    for block in blocks:
        work_queue.put(block)
        
    # 4. Launch slave threads
    threads = []
    for i in range(num_threads):
        t = threading.Thread(target=slave_thread_event_loop, args=(i,))
        t.start()
        threads.append(t)
        
    # 5. Wait for completion
    work_queue.join()
    stop_event.set()
    for t in threads:
        t.join()
```

## Subtopics

### Hybrid Parallelism for CPU Concurrency Testing
A hybrid parallelism approach that combines image-tile decomposition with domain decomposition to distribute the data volume across groups of threads, allowing testing at varying concurrency levels while maintaining image and data volume size [S1, unofficial]. It uses multiple groups of threads at a given concurrency level, with each group allocating its own memory buffer disjoint from other groups [S1, unofficial]. Thread affinity is enforced using the `-Mconcur=numa` flag in the PGI compiler to prevent threads from migrating across cores [S1, unofficial]. Data decomposition configurations vary by platform:
*   **Intel/Nehalem:** 1 thread per buffer, 8 disjoint buffers, buffer size $256 \times 256 \times 256$ [S1, unofficial].
*   **AMD/MagnyCours:** 2 threads per buffer, 4 disjoint buffers, buffer size $256 \times 256 \times 512$ [S1, unofficial].
*   **Intel/Nehalem (4 threads/buffer):** 2 buffers, size $256 \times 512 \times 512$ [S1, unofficial].
*   **Intel/Nehalem (8 threads/buffer):** 1 buffer, size $512 \times 512 \times 512$ [S1, unofficial].
*   **AMD/MagnyCours (6 threads/buffer):** 4 buffers, size $256 \times 256 \times 512$ [S1, unofficial].
*   **AMD/MagnyCours (24 threads/buffer):** 1 buffer, size $512 \times 512 \times 512$ [S1, unofficial] [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \cdot M \cdot L)$, where $N$ is the number of pixels, $M$ is the number of rays per pixel (if multi-sampling), and $L$ is the number of samples per ray. Parallelization reduces wall-clock time by a factor approaching the number of threads, subject to overhead and load imbalance [S1, unofficial].
*   **Memory Complexity:** $O(V + I)$, where $V$ is the size of the volume data and $I$ is the size of the image buffer. In hybrid parallelism, memory usage scales with the number of disjoint buffers [S1, unofficial].
*   **Measured Performance:** Dynamic work assignment performs better than static assignment due to reduced load imbalance [S1, unofficial]. Performance scales with the number of cores but is limited by memory bandwidth and cache contention [S1, unofficial].
*   **Strengths:** Flexible work distribution, good load balancing with dynamic queues, easy to implement on standard multi-core CPUs [S1, unofficial].
*   **Limitations:** Overhead of thread management and synchronization; static assignment suffers from load imbalance [S1, unofficial].
*   **When to Use:** When rendering on multi-core CPUs where load balance is unpredictable or when GPU resources are unavailable [S1, unofficial].
*   **When Not to Use:** When extreme scalability on many-core architectures is required (use GPU raycasting) or when memory bandwidth is the primary bottleneck and static assignment with block synchronization might offer better cache locality [S1, unofficial].

## Background
The method is based on Levoy’s formulation of volume rendering [S1, unofficial]. It was implemented using POSIX threads as the shared-memory programming model [S1, unofficial]. The approach was explored in the context of multi-core and many-core shared-memory parallel raycasting volume rendering optimization and tuning [S1, unofficial]. The hybrid parallelism approach for concurrency testing was adapted from distributed-memory parallel implementations [S1, unofficial].
