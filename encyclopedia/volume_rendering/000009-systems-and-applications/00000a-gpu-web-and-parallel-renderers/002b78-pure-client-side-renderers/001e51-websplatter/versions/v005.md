# WebSplatter
## Overview
WebSplatter is a pure client-side WebGPU renderer for 3D Gaussian Splatting (3DGS) designed to achieve high-performance, cross-device compatibility in web browsers [S1, unofficial]. It solves the problem of inconsistent performance and stability in existing web-based 3DGS viewers by replacing CPU-based or spin-wait-based sorting with a fully GPU-based, wait-free radix sort [S1, unofficial]. Unlike its sibling [ClearView (Unified) Renderer](2460-clearview-unified-renderer.md), which focuses on unified rendering pipelines, WebSplatter specifically targets the constraints of the WebGPU API and heterogeneous hardware (from high-end desktops to mobile phones), ensuring that the system never becomes sort-bound and maintains visual fidelity comparable to native CUDA implementations [S1, unofficial].

## How it works
WebSplatter processes 3D Gaussian Splatting data through three main stages: pre-processing, sorting, and rendering [S1, unofficial]. The method relies on WebGPU compute shaders for data transformation and sorting, and fragment shaders for rasterization [G].

### Inputs and Outputs
*   **Input**: A 3DGS scene file containing Gaussian primitives (position, covariance/scale, rotation, opacity, spherical harmonics coefficients) and camera parameters (view and projection matrices) [G].
*   **Output**: A 2D color buffer (framebuffer) representing the rendered image [S1, unofficial].

### Data Structures
The implementation uses GPU buffers to store intermediate states [G]. While exact byte layouts are not fully specified in the source, the following structures are implied by the WebGPU context and 3DGS requirements [S1, unofficial]:
1.  **Gaussian Attributes Buffer**: Stores raw Gaussian data [G]. Fields typically include:
    *   `position`: `vec3<f32>` (3D coordinates) [G].
    *   `scale`: `vec3<f32>` (scaling factors) [G].
    *   `rotation`: `vec4<f32>` (quaternion) [G].
    *   `opacity`: `f32` [G].
    *   `sh_coeffs`: Array of `f32` (Spherical Harmonics) [G].
2.  **Splat List Buffer**: Stores the projected 2D splats [G]. Fields typically include:
    *   `center`: `vec2<f32>` (projected screen coordinates) [G].
    *   `width`/`height`: `f32` (extent of the 2D Gaussian) [G].
    *   `depth`: `f32` (for sorting) [G].
    *   `original_index`: `u32` (to retrieve attributes) [G].
3.  **Sorting Buffers**: Double-buffered arrays of indices or keys used by the radix sort algorithm [G].

### Numbered Steps
1.  **Pre-processing (Projection)**:
    *   For each Gaussian primitive, compute the 3D-to-2D projection using the camera's view and projection matrices [G].
    *   Calculate the 2D covariance matrix in screen space [G].
    *   Determine the bounding box (width and height) of the 2D Gaussian ellipse [G].
    *   Discard Gaussians that are outside the view frustum or have negligible contribution [G].
    *   Store the projected splat data (center, width, height, depth, original index) in the Splat List Buffer [G].
2.  **Sorting (Wait-Free Radix Sort)**:
    *   Sort the Splat List Buffer by depth (z-coordinate) in front-to-back order [S1, unofficial].
    *   Use a GPU-based radix sort algorithm [S1, unofficial]. The source emphasizes a "wait-free" design to avoid spin-waiting, which is critical for Apple M-series chips where workgroup execution order is not guaranteed [S1, unofficial].
    *   The sort is performed entirely on the GPU using compute shaders, avoiding CPU-GPU synchronization stalls [G].
3.  **Rendering (Rasterization)**:
    *   Iterate through the sorted splats [G].
    *   For each splat, rasterize the 2D Gaussian ellipse onto the screen [G].
    *   Perform alpha blending:
        $$ C_{out} = C_{src} \cdot \alpha_{src} + C_{dst} \cdot (1 - \alpha_{src}) $$
        Where $C_{src}$ is the color of the current splat, $\alpha_{src}$ is its opacity, and $C_{dst}$ is the current color in the framebuffer [G].
    *   Update the depth buffer if necessary (though standard 3DGS often uses depth peeling or simple alpha blending without strict depth testing for the final image) [G].

### Pseudocode
The following pseudocode outlines the core logic, focusing on the sorting and rendering pipeline. WebGPU-specific shader execution is abstracted into standard Python operations for clarity [G].

```python
import math

def render_gaussian_splats(gaussians, camera_view_proj, viewport_w, viewport_h):
    # Step 1: Pre-processing (Projection & Culling)
    splat_list = []
    for g in gaussians:
        # Project 3D center to screen space [G]
        screen_pos = project_to_screen(g.position, camera_view_proj)
        # Compute 2D covariance and bounding box [G]
        cov_2d = compute_screen_covariance(g.cov_3d, camera_view_proj)
        width, height = compute_bounding_box(cov_2d)
        # Frustum culling [G]
        if is_in_view(screen_pos, width, height, viewport_w, viewport_h):
            splat_list.append({
                'center': screen_pos,
                'width': width,
                'height': height,
                'depth': g.position.z,
                'index': g.id,
                'opacity': g.opacity,
                'color': g.color
            })

    # Step 2: Sorting (Wait-Free Radix Sort)
    # Sort by depth ascending (front-to-back) [S1, unofficial]
    # Production uses WebGPU compute shaders; standard radix sort shown [G]
    sorted_splats = radix_sort(splat_list, key=lambda s: s['depth'])

    # Step 3: Rendering (Rasterization & Blending)
    framebuffer = [[(0.0, 0.0, 0.0, 0.0) for _ in range(viewport_w)] for _ in range(viewport_h)]
    for splat in sorted_splats:
        framebuffer = rasterize_splat(framebuffer, splat)
    return framebuffer

def project_to_screen(pos_3d, view_proj_matrix):
    # Standard homogeneous projection [G]
    clip = mat_mul_4x4_vec4(view_proj_matrix, [pos_3d[0], pos_3d[1], pos_3d[2], 1.0])
    ndc = [c / clip[3] for c in clip[:3]]
    return (ndc[0], ndc[1])

def mat_mul_4x4_vec4(matrix, vec):
    # 4x4 matrix-vector multiplication [G]
    res = [0.0] * 4
    for i in range(4):
        for j in range(4):
            res[i] += matrix[i][j] * vec[j]
    return res

def compute_screen_covariance(cov_3d, view_proj_matrix):
    # Jacobian of projection applied to 3D covariance [G]
    # Simplified 2D projection covariance calculation [G]
    return [cov_3d[0][0], cov_3d[0][1], cov_3d[1][0], cov_3d[1][1]]

def compute_bounding_box(cov_2d_flat):
    # Eigenvalues of 2D covariance give semi-axes [G]
    cov_2d = [[cov_2d_flat[0], cov_2d_flat[1]], [cov_2d_flat[2], cov_2d_flat[3]]]
    trace = cov_2d[0][0] + cov_2d[1][1]
    det = cov_2d[0][0] * cov_2d[1][1] - cov_2d[0][1] * cov_2d[1][0]
    disc = math.sqrt(max(0.0, trace**2 - 4 * det))
    semi_x = math.sqrt(0.5 * (trace + disc))
    semi_y = math.sqrt(0.5 * (trace - disc))
    return 2.0 * semi_x, 2.0 * semi_y

def is_in_view(center, width, height, w, h):
    # Check if bounding box overlaps viewport [G]
    return abs(center[0]) < 1.0 and abs(center[1]) < 1.0 and width > 0 and height > 0

def radix_sort(data, key):
    # Standard radix sort implementation [G]
    # WebSplatter uses a GPU-based wait-free variant [S1, unofficial]
    return sorted(data, key=key)

def rasterize_splat(framebuffer, splat):
    # Alpha blend 2D Gaussian onto framebuffer [G]
    cx, cy = splat['center']
    w, h = splat['width'], splat['height']
    for y in range(max(0, int(cy - h)), min(len(framebuffer), int(cy + h))):
        for x in range(max(0, int(cx - w)), min(len(framebuffer[0]), int(cx + w))):
            dx, dy = x - cx, y - cy
            alpha = splat['opacity'] * math.exp(-0.5 * (dx**2/splat['width']**2 + dy**2/splat['height']**2))
            alpha = max(0.0, min(1.0, alpha))
            fb_r, fb_g, fb_b, fb_a = framebuffer[y][x]
            new_r = splat['color'][0] * alpha + fb_r * (1.0 - alpha)
            new_g = splat['color'][1] * alpha + fb_g * (1.0 - alpha)
            new_b = splat['color'][2] * alpha + fb_b * (1.0 - alpha)
            framebuffer[y][x] = (new_r, new_g, new_b, fb_a + alpha * (1.0 - fb_a))
    return framebuffer
```

### Parameters and Typical Values
*   **Radix Sort Bins**: Not specified in the source, but standard radix sort uses 8-bit or 16-bit bins [G].
*   **Splat Resolution**: Not specified, but depends on the Gaussian scale [G].
*   **Frame Time Targets**: Real-time (>30 FPS, i.e., <33.3 ms/frame) is the goal [G]. On high-end GPUs, frame times are ~9.5 ms [S1, unofficial].

### Edge Cases and Pitfalls
*   **Apple M1/M-Series Chips**: Spin-wait-based sorting performs poorly due to lack of workgroup execution order guarantees, leading to busy-waiting [S1, unofficial]. WebSplatter's wait-free design avoids this [S1, unofficial].
*   **Memory Constraints**: Low-end devices (e.g., Oppo Find X2, iPhone 15 Pro Max) may crash if memory requirements exceed hardware limits [S1, unofficial]. WebSplatter's efficient memory usage allows it to render on these devices where baselines fail [S1, unofficial].
*   **Firefox WebGPU Instability**: Firefox may block WebGPU or report unreliable timestamp queries [S1, unofficial]. WebSplatter is tested on Chrome/Edge where WebGPU is stable [S1, unofficial].
*   **Pre-processing Bottleneck**: On low-end GPUs (e.g., Nvidia MX350), pre-processing (scanning raw splats) becomes the bottleneck due to limited memory throughput [S1, unofficial].

## Operating characteristics
*   **Time Complexity**: The sorting step is $O(N \log N)$ or $O(N)$ depending on the radix sort implementation, but the key metric is that it is GPU-accelerated and never becomes the bottleneck [S1, unofficial]. Pre-processing is $O(N)$ [G]. Rendering is $O(S)$ where $S$ is the number of splats [G].
*   **Memory Complexity**: $O(N)$ for storing Gaussian data and intermediate splat lists [G]. WebSplatter is optimized to fit within the memory constraints of mobile devices [S1, unofficial].
*   **Measured Performance**:
    *   **Nvidia RTX 3070**: Median frame time of 9.497 ms on the garden scene (5.8M splats), a 1.52× speedup over the fastest competing WebGPU implementation [S1, unofficial].
    *   **MacBook Air M4**: 1.06× faster than baseline [S1, unofficial]. P99 latency of 116.851 ms with a standard deviation of 22.303 ms, indicating low jitter [S1, unofficial].
    *   **Redmi K70 Pro**: 1.18× faster than baseline [S1, unofficial]. Renders 2.5M splats in 52.7 ms without crashing [S1, unofficial].
    *   **Intel NUC iGPU**: 2.26× faster than baseline [S1, unofficial].
    *   **Scalability**: On Nvidia MX350, scaling from 0.3M to 5.8M splats increases frame time by ~143 ms, compared to >280 ms for KeKsBoTer/web-splat (2.1× speedup) [S1, unofficial].
*   **Bottleneck Analysis**:
    *   **High-end GPUs** (RTX 3070, M-series, Redmi K70 Pro): Render-bound [S1, unofficial]. Rasterization consumes 51.8% to 62.6% of frame time [S1, unofficial].
    *   **Low-end GPUs** (MX350, Intel NUC iGPU): Pre-process-bound [S1, unofficial]. Pre-processing consumes up to 47.2% of frame time due to limited memory throughput [S1, unofficial].
    *   **Sort-bound**: Never occurs across all tested hardware [S1, unofficial].
*   **Strengths**:
    *   Cross-device compatibility (works on mobile, desktop, integrated graphics) [S1, unofficial].
    *   Wait-free sorting avoids hardware-specific pitfalls (e.g., Apple M1) [S1, unofficial].
    *   Low variance in frame time, reducing micro-stuttering [S1, unofficial].
    *   Visual fidelity comparable to native CUDA implementation [S1, unofficial].
*   **Limitations**:
    *   Dependent on WebGPU support in browsers (Firefox has stability issues) [S1, unofficial].
    *   Pre-processing can be a bottleneck on very low-end hardware [S1, unofficial].

## Background
WebSplatter was introduced in the paper "WebSplatter: Enabling Cross-Device Efficient Gaussian Splatting in Web Browsers via WebGPU" [S1, unofficial]. It addresses the limitations of previous web-based 3DGS renderers, which suffered from poor performance on certain hardware (especially Apple M-series) and instability on mobile devices [S1, unofficial]. The method leverages the WebGPU API to provide a high-performance, portable solution for rendering 3DGS in web browsers [S1, unofficial].
