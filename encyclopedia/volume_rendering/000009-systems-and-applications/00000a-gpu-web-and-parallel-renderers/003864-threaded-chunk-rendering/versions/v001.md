# Threaded Chunk Rendering

Also called: RendererManager

## Overview
Threaded Chunk Rendering is a parallel execution strategy that distributes volumetric rendering tasks across a pool of worker threads to maximize hardware utilization. It solves the problem of CPU-bound rendering bottlenecks by decoupling task scheduling from execution, allowing multiple chunks of the world to be rendered concurrently. It differs from [CPU Multithreaded Rendering](6052-cpu-multithreaded-rendering.md) by explicitly managing a queue of reusable renderers and synchronization primitives to handle dynamic workloads, and from [CPU-Driven Task Spawning](4397-cpu-driven-task-spawning.md) by using a fixed-size thread pool rather than spawning new threads per task.

## How it works
**Inputs:** A 3D grid of world chunks defined by dimensions $LOADED\_WORLD\_SIZE \times LOADED\_WORLD\_SIZE \times LOADED\_WORLD\_SIZE$, where each chunk has a fixed physical size (e.g., $8 \times 8 \times 8$ blocks) [S1, unofficial].
**Outputs:** A composited image frame, where Z-buffering is used to resolve depth conflicts between concurrently rendered chunks [S1, unofficial].

**Data Structures:**
The `RendererManager` maintains the following state [S1, unofficial]:
- `freeRenderers`: A thread-safe queue (`ThreadsafeQueue<Renderer*>`) storing available renderer instances.
- `activeRenderers`: An atomic integer (`std::atomic<int>`) tracking the number of currently executing rendering threads, initialized to 0.
- `cv`: A condition variable (`std::condition_variable`) used to signal when active renderers complete or when new work is available.
- `mtx`: A mutex (`std::mutex`) protecting the condition variable and queue state.

**Parameters:**
- `MAX_RENDERERS`: The maximum number of concurrent rendering threads allowed. The source specifies a value of 20 [S1, unofficial].

**Algorithm Steps:**
1. **Iteration:** Iterate through all loaded world chunks using indices $i, j, k$ ranging from 0 to $LOADED\_WORLD\_SIZE - 1$ [S1, unofficial].
2. **Dispatch:** For each chunk, invoke the `renderChunk` function [S1, unofficial].
3. **Acquire Renderer:** Inside `renderChunk`:
    a. Lock the mutex `mtx`.
    b. Wait on `cv` while `activeRenderers >= MAX_RENDERERS` AND `freeRenderers` is empty. This prevents thread explosion when the pool is exhausted [S1, unofficial].
    c. Pop a `Renderer` pointer from `freeRenderers`. If the queue is empty (but `activeRenderers < MAX_RENDERERS`), allocate a new `Renderer` instance [G].
    d. Increment `activeRenderers`.
    e. Unlock `mtx`.
4. **Spawn Thread:** Create a detached `std::thread` that executes `Chunk::render(chunk, renderer)` [S1, unofficial].
5. **Render:** The thread calls `renderer->renderChunk(this)` on the chunk [S1, unofficial].
6. **Release:** Upon completion, `Chunk::render` calls `rendererManager.freeRenderer(renderer)` [S1, unofficial].
7. **Cleanup:** Inside `freeRenderer`:
    a. Lock `mtx`.
    b. Push the `renderer` back onto `freeRenderers`.
    c. Decrement `activeRenderers`.
    d. If `activeRenderers` reaches 0, notify `cv` to wake up any waiting dispatchers [S1, unofficial].
    e. Unlock `mtx`.

**Pseudocode:**

```python
import threading
import queue
import atomic

class RendererManager:
    def __init__(self, max_renderers=20):
        self.max_renderers = max_renderers
        self.free_renderers = queue.Queue()
        self.active_renderers = atomic.Int(0)
        self.cv = threading.Condition()
        self.mtx = threading.Lock()

    def render_chunk(self, chunk):
        with self.mtx:
            # Wait if pool is exhausted and no free renderers are available
            while self.active_renderers.get() >= self.max_renderers and self.free_renderers.empty():
                self.cv.wait()
            
            # Get a renderer
            if not self.free_renderers.empty():
                renderer = self.free_renderers.get()
            else:
                renderer = Renderer() # [G] Allocate if pool is empty
            
            self.active_renderers.increment()
        
        # Spawn detached thread
        thread = threading.Thread(target=chunk.render, args=(renderer,))
        thread.daemon = True
        thread.start()

    def free_renderer(self, renderer):
        with self.mtx:
            self.free_renderers.put(renderer)
            self.active_renderers.decrement()
            
            # Notify if all work is done (optional optimization for frame completion)
            if self.active_renderers.get() == 0:
                self.cv.notify_all()

class Chunk:
    def __init__(self, x, y, z):
        self.x = x * CHUNK_SIZE * BLOCK_SIZE
        self.y = y * CHUNK_SIZE * BLOCK_SIZE
        self.z = z * CHUNK_SIZE * BLOCK_SIZE
        self.blocks = allocate_3d_array(CHUNK_SIZE, CHUNK_SIZE, CHUNK_SIZE)

    def render(self, renderer):
        if renderer is None:
            raise ValueError("Renderer is null")
        
        renderer.render_chunk(self)
        renderer_manager.free_renderer(renderer)
```

## Subtopics

### Mutex-based Read/Write Lock for Chunks
Implements a reader-writer lock using two pthread mutexes (`mutex_read`, `mutex_write`) and a `readers` counter to allow concurrent reads but exclusive writes for chunk data [S2, unofficial]. To acquire a read lock (`chunk_open_ro`), lock `mutex_read`, increment `readers`; if `readers` becomes 1, lock `mutex_write` to block writers [S2, unofficial]. To release, decrement `readers`; if it reaches 0, unlock `mutex_write` [S2, unofficial]. Write locks (`chunk_open_rw`) directly lock `mutex_write` and are exclusive [S2, unofficial]. The `readers` counter must be initialized to 0 [S2, unofficial].

## Operating characteristics
- **Time Complexity:** $O(N)$ where $N$ is the number of chunks, with a constant factor reduced by parallelism.
- **Memory Complexity:** $O(R)$ where $R$ is `MAX_RENDERERS`, for the renderer pool.
- **Performance:** In tests on a 4x4x4 chunk configuration, Z-buffering improved performance by a factor of 1.33x compared to the painters algorithm, achieving ~600 FPS [S1, unofficial].
- **Strengths:** Prevents thread explosion via `MAX_RENDERERS`; reuses renderer objects to reduce allocation overhead.
- **Limitations:** Requires careful synchronization to avoid race conditions on shared chunk data; Z-buffering adds memory overhead per chunk.

## Background
Originated in the development of voxel-based game engines and real-time renderers, specifically cited in the context of the Voxel1993 project [S1, unofficial]. It was developed to replace the CPU-bound Painters algorithm with a multi-threaded approach utilizing Z-buffering for correct depth sorting [S1, unofficial].
