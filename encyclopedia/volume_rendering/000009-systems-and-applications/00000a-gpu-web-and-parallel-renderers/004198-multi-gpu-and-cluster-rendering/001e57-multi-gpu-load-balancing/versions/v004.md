# Multi-GPU Load Balancing

Also called: Multi-Context GPU Rendering, Multi-GPU Rendering

## Overview
This method distributes the rendering workload of a single volume dataset across multiple GPUs on a single node by interleaving data partitions and switching rendering contexts per frame. It solves the problem of memory capacity limits and throughput bottlenecks in single-GPU rendering by leveraging multiple graphics cards to process disjoint subsets of the volume data simultaneously. It differs from general multi-GPU setups by enforcing a strict sequential context switching model combined with pixel-wise result combination, rather than independent frame rendering or complex inter-GPU communication protocols.

## How it works
**Inputs and Outputs**
- Input: A large volumetric dataset represented as a multi-resolution pyramid (e.g., wavelet coefficients).
- Input: Two or more NVIDIA graphics cards connected to a single X-server.
- Output: A single composite image combining the results from all GPUs.

**Data Structures**
The volume data is organized as a sorted array of voxels with associated detail coefficients for each pyramid level.
- **Voxel Data**: Each voxel entry includes position and intensity attributes. For Streaming MIP variants, an extra attribute for the originating pyramid level is required, stored in two bits of the position attribute (4 bytes total for position) plus a short for intensity (2 bytes), totaling 6 bytes per voxel [S1].
- **Partitioning**: The sorted array of voxels is split equally among the GPUs. The split is performed by **interleaving** the detail coefficients (and the histogram) for each pyramid level across the GPUs, rather than splitting the array in the middle [S1].

**Steps**
1. **Context Creation**: Create a separate OpenGL context for each GPU, targeting distinct X-screens supported by the NVIDIA driver [S1].
2. **Data Distribution**: Distribute the interleaved voxel data and histogram to the respective GPU memory. Ensure the histogram is also split appropriately to maintain statistical accuracy for transfer functions [S1].
3. **Rendering Loop (Per Frame)**:
   a. Activate the first GPU's context.
   b. Render the volume subset assigned to the first GPU.
   c. Read the resulting image back to system memory using `glReadPixels`. The preferred pixel format for this transfer is `GL_UNSIGNED_INT_8_8_8_8` [S1].
   d. Activate the second GPU's context.
   e. Write the intermediate result from the first GPU into the second GPU's framebuffer using `glDrawPixels` [S1].
   f. Render the volume subset assigned to the second GPU, which now composites over the first GPU's result.
   g. (Repeat for additional GPUs if applicable, chaining the read/write operations).
4. **Result Combination**: The final image is obtained from the last GPU in the chain. The combination is achieved via a **pixel-wise maximum operator** (Maximum Intensity Projection) [S1].

**Pseudocode**
```python
def render_multi_gpu(voxel_data, gpu_count):
    # 1. Partition data by interleaving coefficients
    partitions = []
    for i in range(gpu_count):
        # Interleave detail coefficients and histogram for each pyramid level
        partitions.append(interleave_data(voxel_data, i, gpu_count))

    # 2. Initialize contexts and framebuffers
    contexts = [create_gl_context(screen_id=i) for i in range(gpu_count)]
    framebuffers = [create_framebuffer() for _ in range(gpu_count)]

    # 3. Render and combine sequentially
    # Load first partition
    load_data(contexts[0], partitions[0])
    bind_framebuffer(contexts[0], framebuffers[0])
    execute_render(contexts[0])

    # Chain subsequent GPUs
    for i in range(1, gpu_count):
        # Read result from previous GPU
        prev_image = gl_read_pixels(framebuffers[i-1], format=GL_UNSIGNED_INT_8_8_8_8)
        
        # Switch to current GPU context
        activate_context(contexts[i])
        bind_framebuffer(contexts[i], framebuffers[i])
        
        # Draw previous result as background
        gl_draw_pixels(prev_image)
        
        # Load and render current partition
        load_data(contexts[i], partitions[i])
        execute_render(contexts[i])

    # 4. Final readout
    final_image = gl_read_pixels(framebuffers[gpu_count-1], format=GL_UNSIGNED_INT_8_8_8_8)
    return final_image
```

**Parameters**
- **Pixel Format**: `GL_UNSIGNED_INT_8_8_8_8` is the preferred format for CPU transfers (`glReadPixels`/`glDrawPixels`) [S1].
- **Split Strategy**: Interleaving coefficients is preferred over contiguous splitting to better divide the load during progressive refinement [S1].

**Edge Cases and Pitfalls**
- **No Direct Inter-GPU Transfer**: There is no extension for direct data shuffling between cards. Intermediate results must pass through the CPU. This introduces significant latency and bandwidth overhead [S1].
- **Multi-threading Inefficiency**: Attempting to run rendering loops for multiple contexts in separate threads yields no performance gain. The algorithm is GPU-bound, and the CPU synchronization overhead outweighs the minimal CPU load of queuing commands [S1].
- **Monitor Connection**: The second (and subsequent) cards do not need to be connected to a monitor, as their output is combined internally via the CPU-mediated transfer [S1].

## Subtopics

## Operating characteristics
- **Time Complexity**: The rendering time is dominated by the GPU computation, which is roughly halved per additional GPU (linear speedup in ideal conditions). However, the CPU-mediated data transfer (`glReadPixels`/`glDrawPixels`) adds a constant overhead per frame per GPU pair [S1].
- **Memory Complexity**: Memory usage is distributed. Each GPU holds only a fraction (1/N) of the voxel data and histogram, allowing rendering of volumes larger than a single GPU's VRAM [S1].
- **Performance**: The method achieves "almost optimal speedup" for large volumes, provided the transfer overhead is acceptable [S1].
- **Strengths**: Simple implementation using standard OpenGL extensions; supports volumes exceeding single-GPU memory; effective for MIP rendering.
- **Limitations**: High CPU bandwidth usage due to intermediate result transfers; no true parallelism in the final composition step (sequential chaining); limited to NVIDIA hardware with multi-screen X-server support [S1].
- **When to use**: When rendering very large volumes on a single node with multiple NVIDIA GPUs and when the bottleneck is VRAM or single-GPU throughput, and inter-GPU latency is tolerable.
- **When not to use**: When low latency is critical, or when using hardware that supports direct peer-to-peer GPU communication (e.g., NVLink) which would bypass the CPU bottleneck.

## Background
This method originates from research on multiresolution MIP rendering of large volumetric data accelerated on graphics hardware. It was developed to support datasets that exceed the memory capacity of a single graphics card. The approach leverages the NVIDIA driver's support for multiple screens within a single X-server to manage multiple OpenGL contexts [S1].
