# Multi-GPU Load Balancing

Also called: Multi-Context GPU Rendering, Multi-GPU Rendering

## Overview
Multi-GPU Load Balancing distributes volumetric rendering workloads across multiple graphics processing units (GPUs) to handle datasets exceeding single-card memory or computational capacity [S1]. It differs from single-node architectures by explicitly managing data partitioning and result compositing across distinct hardware contexts, often requiring CPU-mediated data transfer due to the lack of direct peer-to-peer GPU communication extensions [S1]. Unlike web-based or pure client-side renderers, this method relies on low-level OpenGL context management and specific pixel format optimizations for inter-GPU data exchange [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A large volumetric dataset, typically represented as a multi-resolution pyramid of detail coefficients and a histogram [S1].
*   **Output:** A composite 2D image generated by combining results from multiple GPUs [S1].

**Data Structures:**
*   **Voxel Pyramid:** The volume is decomposed into pyramid levels. Each level consists of detail coefficients and a histogram [S1].
*   **Interleaved Coefficients:** To balance load, the sorted array of voxels is split by interleaving detail coefficients for each pyramid level across the available GPUs [S1]. This approach is preferred over simple mid-array splitting to better distribute load during progressive refinement [S1].
*   **Streaming MIP Attributes:** For Streaming Maximum Intensity Projection (MIP), each voxel requires an extra attribute storing its originating pyramid level. This level is encoded into two bits of the 4-byte position attribute, and intensity is stored in an additional short, totaling 6 bytes per voxel [S1].

**Steps:**
1.  **Context Creation:** Create an OpenGL context on each target X-screen (corresponding to a specific GPU, e.g., NVIDIA cards) [S1].
2.  **Data Partitioning:** Split the sorted voxel array equally among the GPUs by interleaving the detail coefficients (and the histogram) for each pyramid level [S1].
3.  **Rendering Loop:**
    *   Switch the active rendering context to the first GPU.
    *   Render the assigned subset of voxels.
    *   Switch the active rendering context to the second GPU.
    *   Render the assigned subset of voxels.
    *   *Note:* The second GPU does not need to be connected to a monitor; its result is combined with the first [S1].
4.  **Data Transfer (Inter-GPU):** Since no extension exists for direct data shuffling between cards, intermediate results must pass through the CPU [S1].
    *   Read the result from the first GPU's context using `glReadPixels`.
    *   Write the result to the second GPU's context using `glDrawPixels` [S1].
    *   Use the pixel format `GL_UNSIGNED_INT_8_8_8_8` for optimal transfer performance [S1].
5.  **Compositing:** Combine the resulting images from both cards using a pixel-wise maximum operator [S1].

**Pseudocode:**
```python
def multi_gpu_render(volume_pyramid, gpus):
    # 1. Partition data by interleaving coefficients for each pyramid level
    # This ensures balanced load during progressive refinement
    partitions = interleave_split(volume_pyramid, len(gpus))
    
    # 2. Create OpenGL contexts for each GPU/X-screen
    contexts = [create_gl_context(gpu) for gpu in gpus]
    
    # 3. Render to each GPU sequentially within one frame
    # Note: Threading rendering loops does not yield performance gains 
    # as the algorithm is GPU-bound and CPU synchronization overhead 
    # outweighs the tiny load of queuing commands [S1]
    
    # Render first GPU
    active_context = contexts[0]
    render_voxels(active_context, partitions[0])
    
    # Transfer result to CPU and then to next GPU
    # Preferred format: GL_UNSIGNED_INT_8_8_8_8 [S1]
    intermediate_image = gl_read_pixels(active_context, format=GL_UNSIGNED_INT_8_8_8_8)
    
    # Render second GPU
    active_context = contexts[1]
    gl_draw_pixels(active_context, intermediate_image, format=GL_UNSIGNED_INT_8_8_8_8)
    render_voxels(active_context, partitions[1])
    
    # 4. Combine results
    # The second card's result is combined with the first
    final_image = pixel_wise_maximum(intermediate_image, gl_read_pixels(active_context, format=GL_UNSIGNED_INT_8_8_8_8))
    
    return final_image
```

**Parameters:**
*   **Pixel Format:** `GL_UNSIGNED_INT_8_8_8_8` is the preferred format for CPU transfer between contexts [S1].

**Edge Cases and Pitfalls:**
*   **No Direct GPU-to-GPU Transfer:** There is no extension for direct data shuffling between cards; data must pass through the CPU [S1].
*   **Threading Overhead:** Multi-threading the rendering loops for multiple contexts does not yield performance gains because the algorithm is GPU-bound; CPU synchronization overhead outweighs the minimal load of queuing commands [S1].
*   **Partitioning Strategy:** Splitting the coefficient array in the middle is less effective than interleaving, especially for progressive refinement scenarios [S1].

## Subtopics

### Parallel streaming model with GPU-CPU matching
In this variant, each GPU is matched to a specific CPU core as part of a parallel streaming model [S2, unofficial]. This approach supports multiple GPUs per node, aiming to keep communication, CPU/GPU data transfers, disk access, and GPU kernel execution concurrent [S2, unofficial]. It addresses load imbalance by ensuring work is distributed as equally as possible to different resources, as system speed is bounded by the slowest unit [S2, unofficial].

## Operating characteristics
*   **Performance:** Achieves almost optimal speedup for large volumes [S1].
*   **Limitations:** The method is GPU-bound; CPU overhead for context switching and data transfer (`glReadPixels`/`glDrawPixels`) is a bottleneck but necessary due to driver limitations [S1].
*   **Scalability:** Limited by the lack of direct inter-GPU communication extensions; scaling requires more CPU-mediated transfers [S1].
*   **Use Cases:** Suitable for large volumetric datasets that exceed single-GPU memory or processing capacity, particularly in offline or high-end visualization scenarios [S1].

## Background
This method was developed to support large volumetric datasets on graphics hardware, specifically leveraging NVIDIA drivers that support multiple cards for one X-server with multiple screens [S1]. The approach was detailed in research on multiresolution MIP rendering [S1]. The concept of matching GPUs to CPU cores in a parallel streaming model is also discussed in the context of large-scale display systems [S2, unofficial].
