# Parallel streaming model with GPU-CPU matching

Also called: GPU-CPU matched parallel streaming

## Overview
This method defines the hardware mapping and concurrency model for multi-GPU volume rendering systems, ensuring that communication, data transfers, disk access, and kernel execution occur concurrently [S1, unofficial]. It solves the problem of resource underutilization in cluster-based rendering by explicitly binding each GPU to a dedicated CPU core, thereby preventing contention and enabling true parallel streaming [S1, unofficial]. It differs from general multi-GPU setups by enforcing a strict 1:1 CPU-GPU affinity to maximize throughput in distributed environments.

## How it works
**Inputs and Outputs:**
- Input: A cluster node configuration with $N$ GPUs and $N$ available CPU cores; a stream of volume rendering tasks.
- Output: Concurrent execution of I/O, data transfer, and rendering kernels without idle cycles.

**Data Structures:**
- Not given in the sources.

**Steps:**
1. Identify the available GPUs and CPU cores on the node.
2. Establish a static mapping where each GPU is assigned to a specific CPU core. This is the "matching" phase [S1, unofficial].
3. Initiate the parallel streaming pipeline for each matched pair:
   a. The CPU core handles disk access and data preparation.
   b. The CPU initiates data transfer to its matched GPU.
   c. The GPU executes the rendering kernel.
   d. These three operations (disk access, transfer, kernel execution) must happen concurrently across the matched pairs [S1, unofficial].

**Parameters:**
- Not given in the sources.

**Edge cases and pitfalls:**
- The system speed is bounded by the slowest unit; thus, load imbalance must be minimized [S1, unofficial].
- If the number of GPUs exceeds available cores, the matching model breaks down, leading to contention.

**Pseudocode:**
```python
# Initialize cluster node resources
gpus = get_available_gpus()
cpu_cores = get_available_cpu_cores()

# Enforce 1:1 matching
# Note: Exact binding mechanism (e.g., pthread_setaffinity_np) is implementation-specific [G]
gpu_cpu_pairs = list(zip(gpus, cpu_cores))

def parallel_streaming_task(gpu, cpu_core, task_data):
    """
    Executes the concurrent pipeline for a single GPU-CPU pair.
    """
    # 1. Disk Access (CPU side)
    # Read volume data from disk
    data = disk_read(task_data.path)
    
    # 2. Data Transfer (CPU to GPU)
    # Transfer data to the matched GPU's memory space
    gpu_memory = gpu.allocate(data.size)
    gpu.copy_to_device(gpu_memory, data)
    
    # 3. Kernel Execution (GPU side)
    # Launch rendering kernel on the GPU
    # The CPU core remains free to handle the next I/O or transfer for other pairs
    gpu.launch_kernel(task_data.kernel_config, gpu_memory)
    
    # 4. Result Retrieval (Optional, depends on sync requirements)
    # Read back results if needed
    result = gpu.copy_to_host(gpu_memory)
    return result

# Execute in parallel across all matched pairs
threads = []
for gpu, cpu_core in gpu_cpu_pairs:
    # Bind thread to specific CPU core [G]
    thread = Thread(target=parallel_streaming_task, args=(gpu, cpu_core, task))
    threads.append(thread)
    thread.start()

for thread in threads:
    thread.join()
```

## Subtopics

### [Single-User Multi-Object Scheduling](11517-single-user-multi-object-scheduling.md)
This method is a scheduling policy for distributing rendering jobs for a single user viewing multiple objects in a large scene. It solves the problem of unbalanced GPU workload and I/O bandwidth bottlenecks by separating objects into "Heavy" (larger-sized) and "Light" (smaller-sized) tasks. It distinguishes itself from uniform resource assignment by dynamically allocating dedicated GPUs to heavy tasks and shared GPUs to light tasks, thereby reducing long tail latency for large objects and preventing I/O saturation.

**Time and memory complexity:**
- Not given in the sources.

**Measured performance:**

**Scaling:**
- The model scales with the number of matched GPU-CPU pairs. Performance is limited by the slowest unit in the cluster, making load balancing critical [S1, unofficial].

**Strengths and limitations:**
- Strength: Enables concurrent I/O, transfer, and computation, maximizing hardware utilization [S1, unofficial].
- Limitation: Susceptible to load imbalance if tasks are not evenly distributed; the system speed is bounded by the slowest unit [S1, unofficial].

**When to use it and when not:**
- Use when running on cluster nodes with multiple GPUs and sufficient CPU cores to maintain 1:1 affinity.
- Not suitable for environments with severe load imbalance or insufficient CPU cores relative to GPUs.

## Background
**Origin:**
- The concept was presented by Fogal et al. [21] in a system designed for cluster-based GPU rendering [S1, unofficial].

**History and development:**
- Load imbalance has been a long-researched topic in parallel computing, and parallel rendering systems are not exempt from these issues [S1, unofficial]. Sort-first algorithms are noted as being particularly susceptible to load imbalance [S1, unofficial].

**Where it is used:**
- Large-scale display volume visualization systems [S1, unofficial].
