# Single Node Multi-GPU/Server Architecture

Also called: Chromium Framework Cluster Rendering, Cluster rendering with OpenGL Stream Processing Units, Remote visualization via Chromium, Sarton et al. approach, Single node server with multiple GPUs/CPUs (Sarton et al.)

## Overview
This architecture enables interactive visualization of large volumetric datasets on resource-constrained mobile clients by offloading all rendering computation to a server-side cluster [S1, S2, unofficial]. It differs from pure client-side renderers by requiring a dedicated rendering backend, and from distributed shared-memory schemes by utilizing a single node with multiple GPUs/CPUs or a cluster of nodes managed via the Chromium framework [S1, S2, unofficial]. It solves the problem of limited local hardware (e.g., PDAs) by transmitting compressed image buffers rather than raw volumetric data [S1, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** Large volumetric datasets (too large for client storage), user interaction parameters (viewpoint, transfer function), client device capabilities.
*   **Output:** Compressed image frames transmitted to the client for display.

**Data Structures:**
*   **OpenGL Streams:** Packed representations of OpenGL commands generated by the client and managed by the server [S1, unofficial].
*   **Image Buffers:** Rendered frames read back from cluster nodes [S1, unofficial].
*   **Compression Buffers:** Data compressed using ZLIB or JPEG [S1, unofficial].

**Steps:**
1.  **Cluster Setup:** Arrange graphics accelerators (GPUs) in a cluster or single node with multiple GPUs/CPUs. Provide a virtualized interface to the hardware through the OpenGL API [S1, S2, unofficial].
2.  **Stream Generation:** The client node generates OpenGL streams representing the desired view and interaction parameters [S1, unofficial].
3.  **Stream Management:** Server nodes manage multiple incoming network connections, interpreting them as packed representations of the OpenGL streams [S1, unofficial].
4.  **SPU Execution:** Perform stream transformations using OpenGL Stream Processing Units (SPU). SPUs are implemented as dynamically loadable libraries providing the OpenGL interface. Each cluster node renders its portion of the scene directly on its local hardware [S1, unofficial].
5.  **Compositing:** Read back image buffers from the cluster nodes. Transmit these buffers to a final compositing server to combine them into a single final image [S1, unofficial].
6.  **Compression:** Compress the resulting composite image. The sources specify the use of ZLIB and JPEG (Joint Photographic Experts Group) for this step [S1, unofficial].
7.  **Transmission:** Send the compressed image data to the client over a TCP channel established on a wireless link [S1, unofficial].
8.  **Client Decompression and Display:** The client-side image data decoder receives the encoded information. An uncompress mechanism extracts the raw image. The visualization interface supervises the render area for the framebuffer content received from the remote server [S1, unofficial].

**Parameters:**
*   **Client RAM:** A device with 32 MB of RAM is sufficient for the client application [S1, unofficial]. However, [S1, unofficial] also notes that a graphic card with 128 MB RAM is necessary for the proposal, contradicting the "mobile/PDA" focus slightly [S1, unofficial].
*   **Compression Algorithms:** ZLIB and JPEG [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Network Latency:** The reliance on TCP over wireless links for image transmission can introduce latency, affecting interactivity [S1, unofficial].
*   **Hardware Requirements:** While targeting mobile devices, the requirement for 128 MB VRAM on the client contradicts typical PDA specifications of the era [S1, unofficial].
*   **Compression Artifacts:** JPEG is a lossy compression method, which may degrade visual quality for medical or scientific data [S1, unofficial].

## Subtopics

### Chromium Framework Cluster Rendering
Uses the Chromium framework to unify rendering power of a graphics accelerator cluster via OpenGL stream processing [S1, unofficial].

### Single Node Multi-GPU/Server Architecture (Sarton et al.)
Uses a single node server with multiple GPUs and CPUs instead of a distributed cluster [S2, unofficial].

## Operating characteristics
*   **Time Complexity:** Not given in the sources.
*   **Memory Complexity:** Client memory usage is low (32 MB RAM sufficient for application logic) [S1, unofficial]. Server memory usage depends on the size of the volumetric dataset and the number of GPUs/CPUs [S1, S2, unofficial].
*   **Measured Performance:** Not given in the sources.
*   **Scaling:** Scales with the number of GPUs/CPUs in the cluster or single node [S1, S2, unofficial].
*   **Strengths:** Enables interactive visualization on low-end mobile devices; leverages powerful server-side hardware [S1, S2, unofficial].
*   **Limitations:** Requires network connectivity; dependent on server availability; potential visual quality loss due to JPEG compression [S1, unofficial].
*   **When to use:** When client hardware is insufficient for local rendering of large volumes.
*   **When not to use:** When network bandwidth is severely limited or unavailable; when lossy compression artifacts are unacceptable.

## Background
This technique was proposed by Lamberti et al. to visualize big models in an interactive mode using Personal Digital Assistants (PDAs) [S1, unofficial]. It uses the Chromium framework to unify the rendering power of a collection of graphics accelerators arranged in a cluster [S1, unofficial]. A similar approach using a single node server with multiple GPUs and CPUs was presented by Sarton et al. [S2, unofficial].
