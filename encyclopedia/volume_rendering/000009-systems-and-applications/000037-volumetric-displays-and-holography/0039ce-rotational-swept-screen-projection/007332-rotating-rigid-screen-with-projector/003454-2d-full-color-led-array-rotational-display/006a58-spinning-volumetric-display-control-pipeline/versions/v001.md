# Spinning Volumetric Display Control Pipeline

Also called: LED Volumetric Display Serial Protocol, Volumetric Pattern Encoding

## Overview
This pipeline converts text-based volumetric patterns into polar coordinates, packs them into a serial data stream, and transmits them to an Arduino to drive a spinning 3D LED volumetric display [S1, unofficial]. It bridges the gap between abstract 3D shape definitions and the hardware-specific timing requirements of a rotating rigid screen with a 2D full-color LED array [7246-2d-full-color-led-array-rotational-display]. Unlike real-time ray-casting or ray-marching methods, this is a pre-computed, static-pattern encoding scheme optimized for low-bandwidth serial transmission to embedded controllers.

## How it works

### Inputs and Outputs
**Inputs:**
1.  **Configuration File:** Text file containing `vol_slices`, `vol_layers`, `vol_radius`, `display_wipe`, `serialport`, and `baudrate`.
2.  **Pattern File:** Text file defining the 3D shape. Supports three modes:
    *   `TOPDOWN`: Cartesian grid iteration.
    *   `FRONTBACK`: Cartesian grid iteration with line-break markers.
    *   `OUTSIDEIN`: Direct polar coordinate iteration.
    *   Active voxels are marked with `'0'`. In `FRONTBACK` mode, `'E'` marks a line break.

**Outputs:**
*   A raw binary serial stream sent to the Arduino via the specified serial port.

### Data Structures

**Configuration Globals:**
*   `vol_slices`: `int`. Number of angular divisions.
*   `vol_layers`: `int`. Number of vertical layers.
*   `vol_radius`: `int`. Maximum radial extent (excluding center).
*   `display_wipe`: `uint8_t`. Initial wipe command.
*   `serialport`: `char[32]`. Port identifier (e.g., "/dev/ttyUSB0").
*   `baudrate`: `int`. Communication speed.

**Coordinate Objects:**
*   `CartPnt`: Stores `height` (int), `x` (int), `y` (int).
*   `PolPnt`: Stores `height` (int), `slice` (int), `radius` (int), `deg` (int).

**Serial Data Buffer:**
*   `serialData`: 2D array of `uint16_t` with dimensions `[360][vol_layers]`.
*   Indexed as `serialData[slice][height]`.
*   Each `uint16_t` acts as a bitmask representing active LEDs at a specific slice and height.

### Steps

1.  **Parse Configuration:** Read `config.txt` to initialize global variables `vol_slices`, `vol_layers`, `vol_radius`, `display_wipe`, `serialport`, and `baudrate`.
2.  **Parse Pattern File:**
    *   Read the mode string (`TOPDOWN`, `FRONTBACK`, or `OUTSIDEIN`).
    *   **TOPDOWN/FRONTBACK:** Iterate grid coordinates. For `FRONTBACK`, handle `'E'` markers. Read character markers; if `'0'` and within `vol_radius`, create a `CartPnt`.
    *   **OUTSIDEIN:** Iterate radius, height, and slice indices directly. If marker is `'0'`, create a `PolPnt` directly.
    *   Convert all `CartPnt` objects to `PolPnt` objects using the coordinate transformation formulas.
3.  **Pack Serial Data:**
    *   Initialize `serialData` array to zero.
    *   For each `PolPnt` in the pattern:
        *   Calculate the radius bitmask: `data = 2^(vol_radius - (radius - 1))`.
        *   Update the buffer: `serialData[polPnt.slice][polPnt.height] |= data`.
4.  **Transmit Data:**
    *   Open serial port with 8N1 settings, raw mode, no flow control.
    *   Send `display_wipe` (1 byte).
    *   Iterate through `serialData` by slice index `i` and layer index `j`.
    *   For each `serialData[i][j]` that is non-zero:
        *   Send 2 bytes of data (little-endian `uint16_t`).
        *   Send 1 byte of slice index `i`.
        *   Send 1 byte of layer index `j`.
    *   Pause for 1 second every 20 bytes transmitted to prevent buffer overflow or timing issues.
    *   Close serial port.

### Formulas

**Cartesian to Polar Slice:**
$$ \text{slice} = \left\lfloor \frac{\text{atan2}(y, x) \times 180}{\pi} \right\rfloor \times \frac{\text{vol\_slices}}{360.0} $$
If $\text{slice} < 0$, then $\text{slice} = \text{slice} + \text{vol\_slices}$.

**Cartesian to Polar Radius:**
$$ \text{radius} = \text{round}\left(\sqrt{x^2 + y^2}\right) $$

**Radius Bitmask Encoding:**
$$ \text{data} = 2^{(\text{vol\_radius} - (\text{radius} - 1))} $$
This encodes the radius as a single bit within the 16-bit word. The bit position corresponds to the radial distance from the center.

### Parameters

*   **vol_slices:** Number of angular divisions. Determines angular resolution.
*   **vol_layers:** Number of vertical layers. Determines vertical resolution.
*   **vol_radius:** Maximum radial extent. Defines the size of the display volume.
*   **baudrate:** Supported values: 4800, 9600, 14400, 19200, 28800, 38400, 57600, 115200.
*   **display_wipe:** A single byte command sent at the start to clear the display.

### Edge Cases and Pitfalls

*   **Radius Overflow:** The radius encoding uses `pow(2, ...)` cast to `int`. If `radius` exceeds `vol_radius` or is 0, the exponent becomes negative or large, potentially causing overflow or incorrect bitmasks. The code assumes `radius` is in `[1, vol_radius]` [S1, unofficial].
*   **Serial Framing:** The transmission uses raw binary writes without framing or checksums. The Arduino expects exact byte sequences: 2 bytes data, 1 byte slice, 1 byte layer per active voxel [S1, unofficial].
*   **Precision:** The slice calculation uses floating-point arithmetic for `atan2` and division. Integer truncation occurs after multiplication by `vol_slices/360.0`.

def cartesian_to_polar(x, y, height, vol_slices, vol_radius):
    slice_idx = int(math.floor((math.atan2(y, x) * 180 / math.pi) * (vol_slices / 360.0)))
    if slice_idx < 0:
        slice_idx += vol_slices
    radius = int(round(math.sqrt(x**2 + y**2)))
    return height, slice_idx, radius

def pack_serial_data(pattern_points, vol_slices, vol_layers, vol_radius):
    # Initialize 2D array [360][vol_layers] with 0
    serial_data = [[0 for _ in range(vol_layers)] for _ in range(360)]
    
    for height, slice_idx, radius in pattern_points:
        # Clamp radius to valid range [1, vol_radius]
        if radius < 1:
            radius = 1
        if radius > vol_radius:
            continue
            
        # Encode radius into bitmask
        # data = 2^(vol_radius - (radius - 1))
        exponent = vol_radius - (radius - 1)
        data = 1 << exponent
        
        # Merge into buffer using bitwise OR
        serial_data[slice_idx][height] |= data
        
    return serial_data

def transmit_serial_data(serial_data, serialport, baudrate, display_wipe):
    ser = serial.Serial(serialport, baudrate, bytesize=serial.EIGHTBITS, 
                        parity=serial.PARITY_NONE, stopbits=serial.STOPBITS_ONE, 
                        timeout=1)
    
    # Send display wipe
    ser.write(bytes([display_wipe]))
    
    byte_count = 0
    for slice_idx in range(360):
        for layer_idx in range(vol_layers):
            data_val = serial_data[slice_idx][layer_idx]
            if data_val != 0:
                # Send 2 bytes data (little-endian)
                ser.write(struct.pack('<H', data_val))
                # Send 1 byte slice index
                ser.write(bytes([slice_idx]))
                # Send 1 byte layer index
                ser.write(bytes([layer_idx]))
                
                byte_count += 4
                # Pause every 20 bytes
                if byte_count % 20 == 0:
                    time.sleep(1)
                    
    ser.close()

def main():

    # Example pattern points (height, slice, radius)
    # In reality, these are parsed from a text file
    pattern_points = [
        (0, 0, 1),
        (1, 10, 2),
        (2, 20, 3)
    ]
    
    serial_data = pack_serial_data(pattern_points, vol_slices, vol_layers, vol_radius)
    transmit_serial_data(serial_data, serialport, baudrate, display_wipe)

## Operating characteristics

*   **Time Complexity:** Parsing is $O(N)$ where $N$ is the number of active voxels. Packing is $O(N)$. Transmission is $O(N)$ but dominated by I/O latency and the 1-second pause every 20 bytes.
*   **Memory Complexity:** $O(\text{vol\_slices} \times \text{vol\_layers})$ for the `serialData` buffer. For typical values (360 slices, 10 layers), this is 7200 `uint16_t` entries, which is negligible.
*   **Performance:** The bottleneck is the serial transmission speed and the explicit pauses. At 115200 baud, transmitting 4 bytes takes ~0.35 ms. However, the 1-second pause every 20 bytes (80 bytes of data) dominates the runtime.
*   **Strengths:** Simple implementation, low hardware requirements (Arduino + shift registers), deterministic output.
*   **Limitations:** Static patterns only (no dynamic animation without re-transmission), low bandwidth due to serial protocol, no error checking, fixed resolution based on configuration.
*   **When to use:** For simple, static 3D LED displays where cost and simplicity are prioritized over dynamic content or high resolution.
*   **When not to use:** For real-time interactive applications, high-resolution displays, or scenes requiring frequent updates.

## Background

This method originates from an open-source project by YangR13, which provides code for a spinning 3D volumetric display running off an Arduino [S1, unofficial]. The project includes a computer-end interpreter (`interpreter.cpp`) that converts 3D shapes from text files into byte strings, and an Arduino-end sketch (`vol_display.ino`) that reads these values and drives the LEDs via daisy-chained shift registers. The serial communication library (`arduino-serial-lib`) is based on work by Tod E. Kurt (2006-2013) [S1, unofficial]. The method is designed for educational and hobbyist purposes, demonstrating the principles of volumetric display control with minimal hardware.
