# Inverse Tomographic Display

Also called: TomoLit

## Overview
Inverse Tomographic Display (TomoLit) is a volumetric rendering technique for mid-air graphics where multiple emitters surround a scattering medium to project rays with programmed intensity, creating images via ray intersection [S1]. It solves the problem of generating 3D content in free space without a physical screen by treating the display area as a volume where light accumulation forms the visible image [S1]. Unlike standard volume rendering which computes light transport from a source to a viewer, TomoLit inverts this process: it calculates the required emitter intensities to produce a target central image, relying on the additive nature of light in a scattering medium [S1].

## How it works
**Inputs and Outputs:**
*   **Input:** A target 2D or 3D image (intensity distribution) to be rendered in the central volume.
*   **Output:** A control signal for an array of emitters, specifying the intensity to emit at each angle.

**Data Structures:**
*   **Emitter Control Buffer:** An array of 256 positions storing ray intensity values for each projection angle [S1].
*   **Emitter Array:** A set of emitters (e.g., lasers) arranged in a geometry (circular, semi-circular, or linear) around the display area [S1].

**Method Steps:**
1.  **Geometry Setup:** Place emitters around the display area. The prototype uses a circular arrangement of 32 emitters, though simulations suggest 16 is a viable trade-off [S1].
2.  **Intensity Calculation:** Determine the required intensity for each emitter at each angle to create the target central image. This involves solving the inverse problem where the forward model is the summation of ray contributions in the scattering medium [S1].
3.  **Buffer Update:** Store the calculated ray intensities in the emitter control buffer (size 256) [S1].
4.  **Transmission:** Send the buffer data to the emitters via a microcontroller (e.g., Arduino Serial port) [S1].
5.  **Projection:** Emitters project rays with the programmed intensities into the scattering medium (e.g., ultrasonically-generated fog) [S1].
6.  **Image Formation:** The intersection of rays in the medium produces the graphics. The brightness follows a non-linear rule: $brightness = luminosity^3$ [S1].

**Parameters:**
*   **Number of Emitters:** Prototype uses 32; simulation suggests 16 [S1].
*   **Intensity Levels:** Prototype uses 60; simulation suggests 16 [S1].
*   **Angular Resolution:** Prototype uses 0.35°; simulation suggests 1° [S1].
*   **Buffer Size:** 256 positions [S1].
*   **Rotation Speed:** Prototype spins at 60 rotations per second [S1].
*   **Update Rate:** Estimated at 24 frames per second for 32 emitters using standard Arduino Serial port [S1].

**Pitfalls:**
*   **Non-linear Brightness:** The addition of laser beams is not linear; brightness follows $luminosity^3$ [S1]. This must be accounted for when calculating target intensities.
*   **Obstructions:** Hand or object insertion does not break rendering; images project around obstructions due to the circular/semi-circle geometry [S1].

## Operating characteristics
*   **Time Complexity:** Not explicitly defined in terms of algorithmic complexity. The bottleneck is the serial communication update rate, estimated at 24 frames per second for 32 emitters [S1].
*   **Memory Complexity:** Low. Requires a buffer of 256 positions per frame [S1].
*   **Strengths:**
    *   Allows direct manipulation and augmented reality capabilities by rendering around obstructions (e.g., hands) [S1].
    *   Uses low-cost off-the-shelf components (lasers, DC motors, Arduino) [S1].
    *   Circular geometry provides high image quality [S1].
*   **Limitations:**
    *   Requires a scattering medium (fog) which may not be suitable for all environments [S1].
    *   Non-linear brightness addition ($luminosity^3$) complicates intensity control [S1].
    *   Limited by the number of emitters and angular resolution; simulations suggest 16 emitters and 1° resolution are sufficient for recognizable 2D images, but higher quality requires more resources [S1].
*   **When to use:** Mid-air graphics, interactive volumetric displays, augmented reality applications where direct hand interaction is desired [S1].
*   **When not to use:** Environments where fog cannot be generated or maintained, or where high-resolution 3D content is required without a stack of displays [S1].

## Background
The concept of Inverse Tomographic Displays, also known as TomoLit, was introduced in the paper "Volumetric Reach-through Displays for Direct Manipulation of 3D Content" [S1]. The authors were inspired by a Hackio concept that proposed using lasers and spinning mirrors [S1]. The prototype was implemented using low-cost components, including an Arduino Nano, DC motors, and rotating mirrors with attached lasers [S1]. The work explores the potential for direct manipulation of 3D content and augmented reality applications [S1].
