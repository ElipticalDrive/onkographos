# Four-View Hologram Compositor

Also called: FourViewCompositor, Pepper's Ghost volumetric display rendering

## Overview
The Four-View Hologram Compositor is a rendering technique that projects four synchronized views of a 3D scene onto a four-sided acrylic pyramid to create a floating volumetric image visible from all sides [S1, unofficial]. It differs from multi-view lenticular rendering by using physical reflection parity via a pyramid rather than optical lenses, requiring independent rotation and mirroring of each view to correct for the acrylic's reflection properties [S1, unofficial].

## How it works
### Inputs and Outputs
**Inputs:**
- A 3D scene graph containing objects to be displayed.
- Camera parameters: `elevation` (default 12 degrees), `fov` (default 42 degrees) [S1, unofficial].
- Calibration data: `pyramid.scale`, `view.scale`, `view.rotation`, `view.mirrorX`, `view.mirrorY` for each of the four views [S1, unofficial].
- Global calibration rotation `globalRot` [S1, unofficial].

**Outputs:**
- A single composite image rendered to the screen (or device display), which is then projected onto the physical pyramid [S1, unofficial].

### Data Structures
The system maintains a collection of `ViewSlot` objects, one for each of the four views (front, right, back, left).

**ViewSlot Interface:**
- `name`: Enum `ViewName` ('front', 'right', 'back', 'left').
- `camera`: A `PerspectiveCamera` instance.
- `target`: A `WebGLRenderTarget` with `RGBAFormat`, `LinearFilter`, and a depth buffer.
- `quad`: A `Mesh` object using `PlaneGeometry`.
- `material`: A `MeshBasicMaterial` with `AdditiveBlending`, `transparent: true`, `depthTest: false`, and `depthWrite: false` [S1, unofficial].

**View Layout Constant (`VIEW_LAYOUT`):**
Maps each `ViewName` to its geometric configuration:
- `front`: `azimuth` = 0, `dir` = [0, -1]
- `right`: `azimuth` = $\pi/2$, `dir` = [1, 0]
- `back`: `azimuth` = $\pi$, `dir` = [0, 1]
- `left`: `azimuth` = $-\pi/2$, `dir` = [-1, 0]

All azimuth values are in radians [S1, unofficial].

### Algorithm Steps

1.  **Initialization**:
    - Create four `PerspectiveCamera` instances.
    - Create four `WebGLRenderTarget` instances with the specified format and filters.
    - Create four `Mesh` objects (quads) using `PlaneGeometry` and the specified `MeshBasicMaterial` settings.
    - Store these in a `ViewSlot` array indexed by view name [S1, unofficial].

2.  **Camera Positioning**:
    - For each view in `VIEW_LAYOUT`:
        - Let $\theta$ be the `azimuth`.
        - Let $h$ be the horizontal distance from the target: $h = \cos(\text{elevation}) \times \text{distance}$.
        - Let $v$ be the vertical height from the target: $v = \sin(\text{elevation}) \times \text{distance}$.
        - Set camera position:
          $$x = \sin(\theta) \times h$$
          $$y = v$$
          $$z = \cos(\theta) \times h$$
        - Set camera target to the scene origin (or object center).
        - Update the projection matrix [S1, unofficial].

3.  **Rendering Loop (Per Frame)**:
    - For each `slot` in the four view slots:
        - If the slot's quad is visible:
            - Set the renderer's active render target to `slot.target`.
            - Clear the renderer.
            - Render the 3D scene using `slot.camera`.
    - Set the renderer's active render target back to the screen (null).
    - Clear the renderer.
    - Render the `compositeScene` (containing the four textured quads) using an `orthographic compositeCamera` [S1, unofficial].

4.  **Calibration and Compositing**:
    - Calculate `baseSize`:
      $$\text{baseSize} = \frac{\min(\text{width}, \text{height})}{2}$$
    - For each `slot` corresponding to view $i$:
        - Let $\vec{d}$ be the `dir` vector from `VIEW_LAYOUT` for view $i$.
        - Rotate $\vec{d}$ by `globalRot` to get $\vec{d}'$.
        - Calculate quad position:
          $$\text{pos} = \vec{d}' \times (\text{baseSize} \times \text{pyramid.scale} \times \text{view.scale}) + \text{offsets}$$
        - Set quad position to `pos`.
        - Set quad scale to $(\text{size}, \text{size}, 1)$, where `size` is derived from `baseSize` and calibration factors.
        - Set quad rotation $z$ to $\text{globalRot} + \text{view.rotation}$ [S1, unofficial].
        - Apply texture mirroring:
            - If `mirrorX` is true, set `tex.repeat.x = -1` and `tex.offset.x = 1`.
            - If `mirrorY` is true, set `tex.repeat.y = -1` and `tex.offset.y = 1`.
            - Otherwise, set `tex.repeat` to $(1, 1)$ and `tex.offset` to $(0, 0)$ [S1, unofficial].

### Pseudocode

```python
# Initialization
cameras = []
targets = []
quads = []
slots = []

for view_name in ['front', 'right', 'back', 'left']:
    cam = PerspectiveCamera(fov=42, aspect=1.0) # Aspect assumed 1.0 for square pyramid base
    target = WebGLRenderTarget(width, height, format=RGBAFormat, filter=LinearFilter, depth=True)
    quad = Mesh(PlaneGeometry(size, size), MeshBasicMaterial(
        blending=AdditiveBlending,
        transparent=True,
        depthTest=False,
        depthWrite=False
    ))
    cameras.append(cam)
    targets.append(target)
    quads.append(quad)
    slots.append({
        'name': view_name,
        'camera': cam,
        'target': target,
        'quad': quad,
        'material': quad.material
    })

# Camera Setup
elevation_deg = 12
elevation_rad = radians(elevation_deg)
distance = 1.0 # Normalized distance

for i, slot in enumerate(slots):
    view_info = VIEW_LAYOUT[slot['name']]
    theta = view_info['azimuth']
    
    horiz_dist = cos(elevation_rad) * distance
    vert_height = sin(elevation_rad) * distance
    
    x = sin(theta) * horiz_dist
    y = vert_height
    z = cos(theta) * horiz_dist
    
    slot['camera'].position.set(x, y, z)
    slot['camera'].lookAt(0, 0, 0)
    slot['camera'].updateProjectionMatrix()

# Calibration Constants
global_rot = 0.0 # From calibration data
pyramid_scale = 1.0 # From calibration data

def render_frame(scene, screen_width, screen_height):
    base_size = min(screen_width, screen_height) / 2
    
    # 1. Render 4 views to targets
    for slot in slots:
        renderer.setRenderTarget(slot['target'])
        renderer.clear()
        renderer.render(scene, slot['camera'])
        
    # 2. Composite to screen
    renderer.setRenderTarget(None)
    renderer.clear()
    
    for slot in slots:
        view_info = VIEW_LAYOUT[slot['name']]
        view_cal = get_calibration(slot['name']) # Returns scale, rotation, mirrorX, mirrorY, offsets
        
        # Calculate position
        dir_vec = view_info['dir'] # [dx, dy]
        # Rotate dir_vec by global_rot
        cos_g = cos(global_rot)
        sin_g = sin(global_rot)
        rotated_x = dir_vec[0] * cos_g - dir_vec[1] * sin_g
        rotated_y = dir_vec[0] * sin_g + dir_vec[1] * cos_g
        
        scale_factor = base_size * pyramid_scale * view_cal['scale']
        pos_x = rotated_x * scale_factor + view_cal['offsets'][0]
        pos_y = rotated_y * scale_factor + view_cal['offsets'][1]
        
        slot['quad'].position.set(pos_x, pos_y, 0)
        
        # Scale quad
        slot['quad'].scale.set(scale_factor, scale_factor, 1)
        
        # Rotation
        slot['quad'].rotation.z = global_rot + view_cal['rotation']
        
        # Texture Mirroring
        tex = slot['material'].map
        if tex:
            if view_cal['mirrorX']:
                tex.repeat.x = -1
                tex.offset.x = 1
            else:
                tex.repeat.x = 1
                tex.offset.x = 0
                
            if view_cal['mirrorY']:
                tex.repeat.y = -1
                tex.offset.y = 1
            else:
                tex.repeat.y = 1
                tex.offset.y = 0
                
        renderer.render(composite_scene, ortho_camera)
```

### Edge Cases and Pitfalls
- **Opaque Quads**: Using opaque materials for the composite quads causes the last drawn view to paint black corners over adjacent views, creating visible rectangular artifacts. This is resolved by using `AdditiveBlending` on black backgrounds, where black contributes zero intensity [S1, unofficial].
- **Mirroring vs. Scaling**: Mirroring via negative scale breaks backface culling. The method uses texture coordinate mirroring (`tex.repeat` and `tex.offset`) instead of geometric scaling to handle reflection parity [S1, unofficial].
- **Scissor Passes**: Using scissored viewport passes for the four views is not viable because they cannot independently rotate or mirror views, which is necessary due to unknown reflection parity in the acrylic [S1, unofficial].

## Operating characteristics
- **Time Complexity**: The method requires four full scene render passes plus one composite pass.
- **Memory Complexity**: Requires memory for four render targets (resolution $\times$ resolution $\times$ 4 bytes per pixel for RGBA) plus the scene graph.
- **Performance**: On the reference hardware (iPhone, mobile GPU), it holds 60 fps comfortably when the scene consists of a handful of additive primitives [S1, unofficial].
- **Strengths**: No headset or glasses required; viewable from all sides; real-time interaction via hand tracking.
- **Limitations**: Limited to a single central object; requires precise physical calibration of the pyramid; performance degrades with complex scene geometry due to four render passes [S1, unofficial].

## Background
The Four-View Hologram Compositor is based on the Pepper's Ghost illusion, adapted for modern mobile devices and acrylic pyramids [S1, unofficial]. It was implemented as part of the `hologram-system` project by Ojasra Kulkarni, integrating hand-tracking gestures via MediaPipe to allow users to interact with the volumetric display physically [S1, unofficial]. The system was designed for applications in engineering review, medical education, and retail presentations [S1, unofficial].
