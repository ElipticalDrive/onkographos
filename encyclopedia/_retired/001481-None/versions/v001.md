# Dynamic Resolution Adaptation

Also called: ComputeReductionFactor, Frame Rate Maintenance via Resolution Adjustment

## Overview
Dynamic Resolution Adaptation is a runtime technique that adjusts the spatial resolution of the rendered output to maintain a target frame rate. It operates by computing a viewport reduction factor based on the previous frame's render time and an allocated time budget [S1, unofficial]. Unlike static resolution scaling, this method adapts dynamically to scene complexity and hardware load, ensuring consistent performance without manual intervention. It differs from [Level-of-detail (LOD) methods](1007-level-of-detail-lod-methods.md) by modifying the output pixel grid rather than the underlying volume data structure, and from [Dynamic Volume Resolution & Alpha Mask Update](2539-dynamic-volume-resolution-alpha-mask-update.md) by focusing on frame-time stability rather than data-level optimization.

## How it works
**Inputs and Outputs:**
*   **Inputs:** `TimeToDraw` (double, seconds, time taken to render the previous frame), `allocatedTime` (double, seconds, target time budget for the next frame), `ReductionFactor` (double, current resolution scale, range $(0.0, 1.0]$) [S1, unofficial].
*   **Outputs:** `newReductionFactor` (double, updated resolution scale) [S1, unofficial].

**Data Structures:**
No complex data structures are required. The method relies on scalar values tracking timing and resolution state.

**Steps:**
1.  **Validate State:** Ensure `ReductionFactor` is in the range $(0.0, 1.0]$ and `TimeToDraw` is $\ge 0.0$. If not, the method cannot proceed correctly [S1, unofficial].
2.  **Compute Ratio:** Calculate the ratio of the actual time taken to the allocated time budget:
    $$ \text{ratio} = \frac{\text{TimeToDraw}}{\text{allocatedTime}} $$
3.  **Adjust Factor:** Update the reduction factor. While the exact algebraic formula is not explicitly detailed in the source snippet, the logic implies scaling the factor inversely to the time ratio to maintain the budget. A common implementation ensures the new factor stays within bounds:
    $$ \text{newReductionFactor} = \text{clamp}\left( \text{ReductionFactor} \times \frac{\text{allocatedTime}}{\text{TimeToDraw}}, 0.0, 1.0 \right) $$
    *Note: The source specifies ensuring the factor stays in $(0.0, 1.0]$, implying a lower bound strictly greater than 0.0 to prevent division by zero or infinite scaling in subsequent frames.* [S1, unofficial].
4.  **Apply:** Use `newReductionFactor` to scale the render viewport dimensions for the next frame.

**Pseudocode:**
```python
def update_dynamic_resolution(TimeToDraw: float, allocatedTime: float, currentReductionFactor: float) -> float:
    # Pitfall: Requires existing ReductionFactor > 0.0 and <= 1.0, and TimeToDraw >= 0.0 [S1, unofficial]
    if currentReductionFactor <= 0.0 or currentReductionFactor > 1.0:
        raise ValueError("Invalid currentReductionFactor")
    if TimeToDraw < 0.0:
        raise ValueError("Invalid TimeToDraw")
    if allocatedTime <= 0.0:
        raise ValueError("Invalid allocatedTime")

    # Compute the new reduction factor based on time budget
    # The goal is to reduce resolution if TimeToDraw > allocatedTime
    # and increase it if TimeToDraw < allocatedTime
    if TimeToDraw == 0.0:
        # Avoid division by zero; if previous frame was instant, max out resolution
        new_factor = 1.0
    else:
        # Scale factor inversely proportional to time usage
        # If TimeToDraw is double the budget, factor should halve
        new_factor = currentReductionFactor * (allocatedTime / TimeToDraw)

    # Ensure the factor stays in the valid range (0.0, 1.0] [S1, unofficial]
    # Note: Strictly greater than 0.0 is required for stability
    if new_factor <= 0.0:
        new_factor = 1e-6 # Small epsilon to prevent zero, or clamp to min valid value
    if new_factor > 1.0:
        new_factor = 1.0

    return new_factor
```

**Parameters:**
*   `allocatedTime`: The target frame time in seconds. Typical values depend on the target frame rate (e.g., 0.016s for 60 FPS) [S1, unofficial].

**Edge Cases and Pitfalls:**
*   **Zero Time:** If `TimeToDraw` is 0.0, division by zero occurs. Handle by capping resolution at maximum [S1, unofficial].
*   **Oscillation:** Rapid fluctuations in scene complexity can cause resolution to oscillate. This is not addressed in the basic method but is a known issue in adaptive systems [G].
*   **Boundary Conditions:** The factor must remain strictly positive to avoid invalid viewport dimensions [S1, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(1)$ per frame for the adaptation logic. The rendering cost scales with the square of the reduction factor (assuming 2D pixel count).
*   **Memory Complexity:** $O(1)$ for the adaptation state. The rendered image memory scales with the square of the reduction factor.
*   **Strengths:** Maintains consistent frame rates under varying load; simple to implement.
*   **Limitations:** Visual quality fluctuates; may cause noticeable popping if adaptation is too aggressive. Not given in the sources: specific performance numbers on hardware.
*   **When to use:** Real-time applications where frame rate stability is more critical than consistent resolution.
*   **When not to use:** Applications requiring fixed resolution for consistency (e.g., medical imaging analysis where pixel size matters).

## Background
Originated in the context of VTK (Visualization Toolkit) volume rendering, specifically in the `VTKMultiVolumeRayCaster` implementation by Bozorgi [S1, unofficial]. It is part of the broader family of adaptive rendering techniques that balance fidelity and performance.
