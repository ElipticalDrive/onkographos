# Terrain Raymarching

Also called: Height Field, Heightmap Raymarching, 高度场

## Overview
Terrain Raymarching renders a 3D landscape defined by a 2D heightmap by casting rays through the image plane and stepping along them until they intersect the surface defined by the heightmap value at the ray's current horizontal position [S1, unofficial]. It differs from standard Signed Distance Field (SDF) raymarching by using a height function $h(x,z)$ rather than a global distance field $f(\mathbf{p})$, which simplifies the intersection test but requires careful handling of step sizes to avoid tunneling through steep terrain [S1, unofficial]. Unlike [Heightfield Rendering](1634-heightfield-rendering.md), which projects the heightmap onto screen-space depth planes to solve hidden surfaces, Terrain Raymarching operates in world space per pixel, allowing for easier integration with global illumination and SDF-based lighting techniques [S1, unofficial].

## How it works
**Inputs:**
*   Camera ray origin $\mathbf{o}$ and direction $\mathbf{d}$ for each pixel.
*   Heightmap function $h(x, z)$, which returns the surface height at world coordinates $(x, z)$. This can be a procedural function (e.g., fractal Brownian motion) or a texture lookup [S1, unofficial].
*   Maximum marching steps $N_{max}$ and minimum step size $\epsilon$ to prevent infinite loops or precision errors [G].

**Outputs:**
*   Color $C$ for each pixel, determined by the height and shading of the intersection point.

**Data Structures:**
*   No complex acceleration structures are required if the heightmap is evaluated directly. If the heightmap is large, a 2D texture array or procedural noise function is used.

**Steps:**
1.  Initialize current position $\mathbf{p} = \mathbf{o}$ and step count $i = 0$.
2.  While $i < N_{max}$:
    a.  Extract the horizontal coordinates of the current position: $x = \mathbf{p}.x$, $z = \mathbf{p}.z$.
    b.  Query the terrain height at these coordinates: $h_{terrain} = h(x, z)$.
    c.  Calculate the vertical distance to the surface: $dist = \mathbf{p}.y - h_{terrain}$.
    d.  If $dist < \epsilon$ (intersection found):
        i.  Set $\mathbf{p}_{hit} = \mathbf{p}$.
        ii. Break loop.
    e.  If $dist < 0$ (ray passed below surface without detection, or tunneling):
        i.  This indicates the step size was too large for the terrain slope. Reduce step size or clamp $\mathbf{p}.y$ to $h_{terrain}$ and break [G].
    f.  Advance the ray. In standard SDF raymarching, the step size is $dist$. However, for heightmaps, the Lipschitz condition of the height function $h(x,z)$ with respect to the ray direction is not guaranteed to be 1. Therefore, a fixed step size $\Delta$ or a step size proportional to the ray's vertical component is often used. A robust approach is to step by a fixed amount $\Delta$ in the ray direction, or use the SDF approach if the heightmap is treated as a distance field approximation (where $f(\mathbf{p}) = \mathbf{p}.y - h(\mathbf{p}.x, \mathbf{p}.z)$ and the gradient is normalized) [S1, unofficial].
    g.  Increment $i$.
3.  If intersection found, compute color:
    a.  Determine base color based on height $h_{terrain}$ (e.g., white for snow at high $h$, green for grass at low $h$) [S1, unofficial].
    b.  Compute surface normal $\mathbf{n}$ at $\mathbf{p}_{hit}$ using finite differences of $h(x,z)$:
        $$ \mathbf{n} = \text{normalize}(\langle -\frac{\partial h}{\partial x}, 1, -\frac{\partial h}{\partial z} \rangle) $$
    c.  Shade the point using lighting models (e.g., raymarch towards light source for shadows) [S1, unofficial].

**Pseudocode:**
```python
def raymarch_terrain(ray_origin, ray_direction, height_func, max_steps, step_size):
    p = ray_origin
    for i in range(max_steps):
        # Get terrain height at current x, z
        h_terrain = height_func(p.x, p.z)
        
        # Vertical distance to surface
        dist = p.y - h_terrain
        
        # Check for intersection
        if dist < 0.001: # epsilon
            return p, h_terrain
            
        # Step along the ray
        # Note: Using a fixed step size or adaptive step based on ray direction
        # is critical because h(x,z) is not necessarily a valid SDF with Lipschitz constant 1
        p = p + ray_direction * step_size
        
    return None, None # No intersection found
```

**Parameters:**
*   `step_size`: Depends on terrain resolution and camera distance. Too large causes tunneling; too small causes performance issues. Not given in the sources.
*   `max_steps`: Typically 64-256 for real-time applications. Not given in the sources.

**Edge Cases:**
*   **Tunneling:** If the terrain has steep slopes, a fixed step size may jump over the surface. This is a known pitfall of perspective relationships in heightfield rendering [S2, unofficial].
*   **Precision:** Floating-point precision errors can cause jittering near the surface. [G]

## Subtopics

### Horizon Mapping
Horizon Mapping is a technique to describe the self-occlusion of a heightfield by calculating visibility [S3, unofficial]. It determines the altitude or horizon angle for a set of azimuth directions for every point in the surface, storing this data in a horizon map [S3, unofficial]. This allows for efficient precomputed ambient occlusion or shadowing without raymarching towards light sources for every pixel [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N \cdot S)$, where $N$ is the number of pixels and $S$ is the average number of steps per ray.
*   **Memory Complexity:** $O(H \cdot W)$ for storing the heightmap, where $H$ and $W$ are the heightmap dimensions.
*   **Strengths:** Simple to implement; easily integrates with procedural noise for infinite terrain detail; fits well on GPU as each pixel is independent [S1, unofficial].
*   **Limitations:** Prone to tunneling on steep terrain if step sizes are not carefully managed; does not naturally handle complex geometry like caves or overhangs unless the heightmap is extended to a full SDF [S1, unofficial].
*   **When to use:** Real-time terrain visualization where performance is critical and terrain is relatively smooth.
*   **When not to use:** Scenes with complex overhangs or caves, where a full SDF is required.

## Background
Terrain Raymarching emerged as a practical application of raymarching techniques for rendering landscapes. It was popularized by blogs and tutorials discussing distance field raymarching, such as the 2013 article by 9bitscience [S1, unofficial]. The technique leverages the simplicity of heightmaps, which have been used in computer graphics since the 1970s, and applies modern GPU-based raymarching to them. It is often discussed in the context of "shadertoy" style programming and real-time terrain rendering [S1, unofficial].
