# Octree Volume Structure

Also called: Cap node octree, Octree Data Format with Caps and Child Arrays, Octree Data Layout, Octree Volume Format, Parent-based node storage, Parent-centric octree storage

## Overview
The Octree Volume Structure is a memory-efficient storage scheme for 3D scalar fields that represents an octree by storing nodes corresponding to the parents of logical octree nodes [S1, S2]. It solves the problem of high memory overhead in standard octree representations by eliminating explicit leaf nodes for the deepest level of interior nodes, instead embedding scalar values directly within parent structures [S2, S3]. This approach serves as a lossless compression format for scalar data while simultaneously providing an acceleration structure for ray traversal via a built-in min/max tree [S1, S5]. It differs from standard octrees by using "cap" nodes at the maximum depth and "scalar leaves" embedded in interior nodes, rather than distinct leaf node types [S2, S3].

## How it works
### Inputs and Outputs
**Input:** A 3D rectilinear grid of scalar values [S1, S2].
**Output:** An `OctreeData` structure containing arrays of `OctNode` pointers, an `OctCap` array, and precomputed hashing data [S1, S2].

### Data Structures
The structure consists of three main components [S1, S4]:

1. **`OctreeData`**: The root container.
   - `OctNode* nodes[max_depth]`: An array of pointers to interior nodes, indexed by depth from 0 (root) to `max_depth - 2` [S1, S2].
   - `OctCap* caps`: A pointer to an array of cap nodes [S1, S2].
   - `int child_bit_depth[max_depth]`: A precomputed array for hashing, where `child_bit_depth[d] = 1 << (max_depth - d - 1)` [S1, S3].

2. **`OctNode`**: Represents an interior node (parent of logical nodes) [S1, S2].
   - `T child_scalars[8]`: Stores scalar values for children that are scalar leaves [S1, S2].
   - `T child_mins[8]` and `T child_maxs[8]`: Stores the minimum and maximum values of the 8 children for pruning [S1, S5].
   - `unsigned int child_start`: A base index (pointer offset) for the children's location in the `caps` or subsequent node arrays [S1, S2].
   - `char child_offset[8]`: An array of 8 signed bytes. Each entry stores the offset from `child_start` to the child node. If the child is a scalar leaf, the value is `-1` [S1, S2].

3. **`OctCap`**: Represents nodes at depth `max_depth - 1` [S1, S2].
   - `T scalars[8]`: Stores the 8 scalar values of the finest-level voxels. Cap nodes always contain scalars and never have children [S1, S3].

*Note: `T` is the scalar type of the input data (e.g., `float`, `int16_t`).*

### Build Process
The structure is built bottom-up from the input 3D grid [S1, S2].

1. **Determine Dimensions:** Calculate $N$, the smallest power of 2 that encompasses the largest dimension of the input volume. Set `max_depth` = $\log_2(N)$ [S1, S2].
2. **Precompute Hashing:** Compute `child_bit_depth` for all depths $d$ from 0 to `max_depth - 1`:
   $$ \text{child\_bit\_depth}[d] = 1 \ll (\text{max\_depth} - d - 1) $$ [S1, S3].
3. **Initialize Caps:** Assign groups of 8 voxels from the original structured grid to `OctCap` nodes. These caps correspond to the finest level of the octree (depth `max_depth`) [S1, S2].
4. **Bottom-Up Consolidation:** Iterate from depth `max_depth - 2` down to 0 [S1, S2].
   - For each group of 8 children (which may be `OctNode`s or `OctCap`s), check if they are identical [S1, S2].
   - **Scalar Leaf Consolidation:** If 8 children are identical scalar values (or consolidate into identical values), store that single value in the parent's `child_scalars` array. Mark the corresponding `child_offset` entry as `-1` [S1, S2].
   - **Pointer Assignment:** If children are not identical, assign pointers. Set `child_start` to the base index of the children in the memory layout. Set `child_offset[i]` to the offset of the $i$-th child from `child_start` [S1, S2].
   - **Min/Max Computation:** Simultaneously compute the min/max tree. For each parent, calculate the minimum and maximum of the 8 children's values. Store these in `child_mins` and `child_maxs` [S1, S5]. The min/max values represent the bounds of the 8 children, allowing rejection of subtrees during traversal without accessing them [S1].
5. **Memory Management:** Remove child nodes from memory once they have been consolidated into their parent. Scalar values are retrieved from the original data only for cap nodes; parent nodes are computed solely from their children's values [S1, S2].

### Point Location Algorithm
To retrieve a scalar value at a specific 3D coordinate, use the precomputed `child_bit_depth` array to avoid costly arbitrary bit shifts [S3].

```python
def point_locate(dest: Vec3i, depth: int, index: int, data: OctreeData) -> T:
    """
    Retrieve scalar value at coordinate 'dest' starting from node at 'depth' and 'index'.
    """
    while True:
        node = data.nodes[depth][index]
        child_bit = data.child_bit_depth[depth]
        
        # Determine child index (0-7) based on coordinate bits
        child = ((dest.x & child_bit) != 0) << 2 | \
                ((dest.y & child_bit) != 0) << 1 | \
                ((dest.z & child_bit) != 0)
        
        offset = node.child_offset[child]
        
        if offset == -1:
            # Child is a scalar leaf embedded in the parent
            return node.child_scalars[child]
        
        if depth == data.max_depth - 2:
            # Reached the level above caps; child is in the caps array
            cap_index = node.child_start + offset
            # Final child index within the cap (LSB of coordinates)
            final_child = ((dest.x & 1) << 2) | \
                          ((dest.y & 1) << 1) | \
                          ((dest.z & 1))
            return data.caps[cap_index].scalars[final_child]
        
        # Move to next depth
        index = node.child_start + offset
        depth += 1
```

### Parameters
*   **`max_depth`**: Determined by the input volume dimensions. Must be a power of 2 [S1, S2].
*   **`child_bit_depth`**: Cached array to optimize point location and neighbor finding [S3].

### Edge Cases and Pitfalls
*   **Performance of Bit Arithmetic:** Early implementations used binary arithmetic masks and bit-counting to determine leaves, but left-shifting by a non-constant hampered performance. The final implementation uses explicit offset arrays (`child_offset`) to avoid this [S1, S2].
*   **Scalar Leaf Ambiguity:** Scalar leaves are not separate structures but single values embedded in the parent. A null pointer (represented by `-1` in `child_offset`) indicates a leaf [S2, S3].
*   **Min/Max Bounds:** The min/max values stored in interior nodes are derived from the 8 children. This allows for efficient rejection during ray traversal [S1, S5].

## Subtopics

### [Octree Volume Ray Tracing](1990-octree-volume-ray-tracing.md)
A technique for interactive isosurface rendering of large compressed structured volumes by using a single octree structure that serves simultaneously as a lossless compression format for scalar data and an acceleration structure for ray traversal.

## Operating characteristics
*   **Memory Efficiency:** By storing nodes as parents and embedding scalar leaves, the structure avoids explicit leaf nodes for the deepest level. Cap nodes store only 8 scalars. This reduces memory overhead compared to standard octrees where every leaf is a distinct node [S2, S3].
*   **Min/Max Tree Overhead:** The min/max tree adds approximately 22% footprint on top of the raw octree voxel data, providing a serviceable acceleration structure for ray tracing [S5].
*   **Traversal Speed:** The use of precomputed `child_bit_depth` and explicit offset arrays allows for fast point location and neighbor finding without costly bit manipulation [S3].
*   **Limitations:** The structure is optimized for structured grids. Coherent traversal optimization is noted as future work [S1].

## Background
The Octree Volume Structure was introduced in the context of interactive isosurface ray tracing of large volumes. It was developed to address the memory and performance limitations of uncompressed structured data and standard octree representations [S1, S2]. The specific optimization of using parent-based storage with cap nodes and embedded scalar leaves was detailed in the paper "Interactive Isosurface Ray Tracing of Large Octree Volumes" [S1, S2].
