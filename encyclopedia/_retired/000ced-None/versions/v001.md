# VDB Volume Rendering with OpenVDB/NanoVDB

Also called: Fixed-rate VDB compression, GPU Volume Rendering with Hierarchical Compression Using VDB, NanoVDB Compression for Volume Rendering, NanoVDB encoding, OpenVDB structure, OpenVDB/NanoVDB rendering, VDB, VDB Data Structure (5-4-3)

## Overview
This method enables GPU volume rendering of large, sparse volumetric datasets by combining offline fixed-rate lossy compression on the CPU (using OpenVDB) with fast, low-overhead on-the-fly decompression and sampling on the GPU (using NanoVDB) [S2, unofficial]. It solves the problem of rendering volumes that exceed single-GPU memory capacity by significantly reducing the memory footprint while maintaining random access patterns suitable for incoherent workloads like path tracing [S2, unofficial]. Unlike hierarchical space-skipping approaches which show diminishing returns with RGBA transfer functions, this method typically employs a uniform majorant grid for traversal acceleration to facilitate direct comparison with dense texture rendering [S1, S2, unofficial].

## How it works
The method consists of two phases: CPU-side compression/conversion and GPU-side rendering.

### Inputs and Outputs
*   **Input:** A dense volumetric dataset (e.g., structured regular grid) and a user-defined quality parameter $q \in [0, 1]$ [S2, unofficial].
*   **Output:** A NanoVDB structure in GPU memory, supporting nearest-neighbor and trilinear interpolation sampling [S2, unofficial].

### Data Structures

#### OpenVDB Structure (CPU)
The standard OpenVDB structure uses a hierarchical layout with three levels of internal nodes and leaf voxels [S3, unofficial].
*   **Index Space:** $4096^3$ ($1 \ll 12$) [S3, unofficial].
*   **Node5 (Top):** Span $32^3$ ($1 \ll 5$) [S3, unofficial].
*   **Node4 (Middle):** Span $16^3$ ($1 \ll 4$) [S3, unofficial].
*   **Node3 (Bottom):** Span $8^3$ ($1 \ll 3$) [S3, unofficial].
*   **Brick Size:** $32 \times 32 \times 32$ voxels for the standard {3,4,5} layout [S2, unofficial]. Note: Some implementations (e.g., Evolve) use $8^3$ bricks for the leaf data storage [S3, unofficial].

#### NanoVDB Structure (GPU)
NanoVDB creates a linear, pointer-free layout optimized for GPU access [S2, unofficial]. The structure on GPU memory is defined as [S3, unofficial]:

```rust
struct Volume {
    constants: Vec<VolumeConstants>, // Translation, scale, AABB (unique per animation frame)
    nodes5: Vec<Node5>,
    nodes4: Vec<Node4>,
    nodes3: Vec<Node3>,
    voxel_data: VoxelData,           // 3D texture buffer
}
```

**Node Layout:**
Each node (Node5, Node4, Node3) contains [S3, unofficial]:
*   `child_pointer: u32`: Points to the start of $N\_CHILDREN$ child nodes.
*   `tile_value: f32`: Value for homogeneous regions.
*   `min_value: f32`, `max_value: f32`, `mean_value: f32`: Statistical bounds.
*   `child_mask: [u32; N\_CHILDREN / 32]`: Bitmask indicating validity of child nodes.

**Voxel Data:**
*   Stored in a 3D texture buffer [S3, unofficial].
*   Layout: Voxels are stored in bricks of $8^3$ [S3, unofficial].
*   Packing: Each 4 values in the Z direction are stored as RGBA components of a texel [S3, unofficial].
*   Compression: BC7 block compression is applied to the 3D texture, resulting in 2 bits per voxel [S3, unofficial].

### Compression Algorithm (CPU)
The fixed-rate encoding algorithm achieves target compression ratios by encoding homogeneous blocks as nearly empty and voxelizing non-empty regions [S1, unofficial].

1.  **Background Value Identification:** Compute a histogram of the input volume's values. The most frequent value is assumed to be the background value $B$ [S2, unofficial].
2.  **Bricking:** Divide the volume conceptually into bricks sized to match the leaf node dimensions (e.g., $32 \times 32 \times 32$) [S2, unofficial].
3.  **Brick Analysis:** For each brick, compute the minimum and maximum voxel values $[lo, hi]$ [S2, unofficial].
4.  **Brick Sorting:** Sort bricks in ascending order of similarity to $B$. Three metrics are defined [S2, unofficial]:
    *   $f_1 = \min(|lo - B|, |hi - B|)$ (closest point-in-range)
    *   $f_2 = \max(|lo - B|, |hi - B|)$ (farthest point-in-range)
    *   $f_3 = |(lo + hi)/2 - B|$ (median distance)
    *   *Note:* Evaluation suggests $f_2$ and $32 \times 32 \times 32$ brick size generally yield better quality [S2, unofficial].
5.  **Voxel Activation:** Determine the target number of bricks to activate based on quality $q$. Iterate through the sorted list starting from the brick *least* similar to the background (end of list). Activate all voxels in the current brick by setting their original values. Continue until the target number of bricks is processed. Voxels in non-selected bricks remain inactive (implicitly background) [S2, unofficial].
6.  **Finalization:** Prune the resulting OpenVDB tree for memory optimization [S2, unofficial].

### GPU Rendering and Decompression
1.  **Conversion:** Convert the compressed OpenVDB structure to NanoVDB. This creates a linear, pointer-free layout [S2, unofficial]. Copy this block to GPU memory [S2, unofficial].
2.  **Traversal Acceleration:** Use a uniform majorant grid for traversal acceleration. Hierarchical traversal was found to offer diminishing returns for this representation [S1, S2, unofficial].
3.  **On-the-Fly Decompression:** During rendering, GPU threads sample the volume using NanoVDB accessor and sampler functions. These functions handle tree traversal and voxel value retrieval directly on the GPU [S2, unofficial].
    *   Supported sampling: Nearest-neighbor and trilinear interpolation [S2, unofficial].
    *   If a sample location falls into an inactive region, the background value $B$ is returned [S2, unofficial].

### Pseudocode

```python
# CPU Compression
def compress_volume(volume_data, quality):
    # 1. Background Value Identification
    histogram = compute_histogram(volume_data)
    background_value = get_most_frequent_value(histogram)
    
    # 2. Bricking
    brick_size = 32 # Standard for {3,4,5} layout
    bricks = divide_into_bricks(volume_data, brick_size)
    
    # 3. Brick Analysis & 4. Brick Sorting
    def similarity_metric(brick):
        lo, hi = min_max(brick)
        # Using f2 metric as suggested for better quality
        return max(abs(lo - background_value), abs(hi - background_value))
    
    sorted_bricks = sort(bricks, key=similarity_metric, ascending=True)
    
    # 5. Voxel Activation
    total_bricks = len(sorted_bricks)
    num_to_activate = int(total_bricks * quality)
    
    # Activate from the end (least similar to background)
    active_bricks = sorted_bricks[-num_to_activate:]
    
    # Create sparse OpenVDB structure
    openvdb_tree = create_empty_openvdb_tree()
    for brick in active_bricks:
        activate_brick(openvdb_tree, brick)
        
    # 6. Finalization
    prune_tree(openvdb_tree)
    return openvdb_tree

# GPU Rendering (Conceptual)
def render_vdb(nanovdb_gpu_ptr, ray, uniform_grid):
    # 1. Traversal Acceleration
    # Use uniform majorant grid for DDA
    cell = uniform_grid.find_cell(ray.origin)
    
    # 2. On-the-Fly Decompression
    # NanoVDB accessor handles traversal and decompression
    value = nanovdb_sample(nanovdb_gpu_ptr, ray.position)
    
    # If inactive, returns background value implicitly
    return value
```

### Parameters
*   **Compression Rates:** 1:8, 1:4, 1:2, 1:1 [S1, unofficial]. 1:1 means zero percent targeted reduction (lossless activation of non-empty voxels) [S1, unofficial].
*   **Quality:** A user-defined parameter between 0 and 1 that controls the compression rate. It determines the percentage of bricks to fully activate [S2, unofficial].
*   **NanoVDB Overhead:** Modest, approximately 10% for large datasets compared to raw data size [S2, unofficial].

### Edge Cases and Pitfalls
*   **Lossless Compression:** At 1:1 rate, the algorithm only activates voxels not considered empty, resulting in an actual size lower than the original even if target reduction is zero [S1, unofficial].
*   **High Compression:** High compression rates may lead to missing features if the transfer function highlights regions deemed 'background' and thus deactivated during compression, resulting in block artifacts [S2, unofficial].
*   **Animation:** Each animation frame has a unique Node5 vector. Switching frames changes only the starting point of structure traversal [S3, unofficial].

## Operating characteristics
*   **Time Complexity:** Rendering performance is competitive with hardware-accelerated 3D texture sampling [S2, unofficial].
*   **Memory Complexity:** Significant memory savings compared to dense textures. For the Galaxy dataset (108 GB raw), VDB achieves 14 GB at 1:8 rate [S1, unofficial]. NanoVDB overhead is ~10% for large datasets [S2, unofficial].
*   **Measured Performance:**
    *   Galaxy dataset: VDB achieves 34.8 FPS on 1 GPU vs 18.6 FPS for dense textures on 3 GPUs [S1, unofficial].
    *   Aneurism dataset: VDB achieves 55.8 FPS on 1 GPU vs 75.9 FPS for dense textures on 1 GPU [S1, unofficial].
    *   WDAS dataset: VDB achieves 24.2 FPS on 1 GPU vs 25.4 FPS for dense textures on 1 GPU [S1, unofficial].
*   **Scaling:** Enables rendering of datasets requiring multiple GPUs uncompressed on a single GPU [S2, unofficial].
*   **Strengths:** Low memory footprint, random access suitable for path tracing, competitive performance with dense textures [S2, unofficial].
*   **Limitations:** Block artifacts at high compression; hierarchical traversal offers diminishing returns [S1, S2, unofficial].

## Background
*   **Origin:** The method was proposed by Stefan Zellmann, Milan Jaros, Jefferson Amstutz, and Ingo Wald in 2025 [S2, unofficial].
*   **Development:** It integrates OpenVDB for CPU-side compression and NanoVDB for GPU-side rendering, integrated into the Barney ray tracer using the ANARI API [S2, unofficial].
*   **Usage:** Used for scientific visualization of large, sparse volumetric data [S2, unofficial].
