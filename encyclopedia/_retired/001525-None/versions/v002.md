# Photon Splatting

Also called: Capturing Direct Illumination (Photon Splatting)

## Overview
Photon Splatting is a method for capturing direct illumination by rasterizing a light-view map and projecting the resulting photons into a sparse voxel octree structure [S1]. It solves the problem of efficiently storing incoming radiance as a direction distribution and energy proportional to the subtended solid angle of the light source [S1]. It differs from [Per-Splat Relighting](3371-per-splat-relighting.md) by baking the lighting information directly into the voxel data structure during a pre-computation or capture phase, rather than computing shading dynamically per splat during rendering [S1, 3371-per-splat-relighting.md].

## How it works
**Inputs:**
*   Light-view map: A world position map rendered from the light's perspective using standard rasterization [S1].
*   Sparse Voxel Octree: A hierarchical data structure representing the scene geometry, with leaf nodes storing photon data [S1].

**Outputs:**
*   Updated Octree: Leaf nodes contain photon direction distributions and energy values [S1].

**Data Structures:**
*   **Octree Leaf:** Stores photon data. Due to hardware constraints, this is often implemented using 16-bit normalized texture formats to support atomic operations, which are otherwise limited to integer textures [S1]. The data includes direction vectors and energy values [S1].
*   **Light-View Map:** A 2D texture where each pixel corresponds to a photon ray from the light [S1].

**Steps:**
1.  **Render Light-View Map:** Render the scene from the light's view to generate a world position map. Each pixel in this map represents a photon to be bounced into the scene [S1].
2.  **Splat Photons:** Use a fragment shader with one thread per pixel of the light-view map. For each pixel, determine the corresponding leaf node in the octree [S1].
3.  **Store Photon Data:** Store the photon as a direction distribution and an energy value proportional to the subtended solid angle of the pixel as seen from the light [S1].
4.  **Handle Collisions:** Since multiple photons may map to the same voxel, use atomic addition to accumulate values [S1].
5.  **Resolve Brick Boundaries:** Because voxels are repeated in adjacent bricks for hardware filtering, direct copying causes thread collisions and bandwidth issues. Perform a value transfer to neighboring bricks to ensure coherence [S1, S2].

**Pseudocode:**
```python
def splat_photons(light_view_map, octree):
    # Step 1 & 2: Iterate over light-view map pixels
    for y, x in light_view_map.dimensions():
        photon_data = light_view_map[y, x]
        
        # Determine target leaf node in octree based on world position
        leaf_node = octree.find_leaf(photon_data.world_position)
        
        # Step 3: Calculate energy based on subtended solid angle
        # Note: Exact formula for solid angle calculation is not provided in sources [S1]
        energy = calculate_subtended_solid_angle(photon_data.pixel_size, photon_data.distance_to_light)
        
        # Step 4: Atomic add to store direction and energy
        # Using 16-bit normalized format to allow atomic operations [S1]
        leaf_node.add_photon_atomic(photon_data.direction, energy)

    # Step 5: Resolve brick boundary inconsistencies
    resolve_brick_boundaries(octree)

def resolve_brick_boundaries(octree):
    # Six passes: two for each axis (x, y, z) [S2]
    
    # X-axis passes
    # Pass 1: Add data from current node to the right neighbor
    for node in octree.leaves():
        right_neighbor = node.get_neighbor('right')
        if right_neighbor:
            right_neighbor.add_data(node.data)
            
    # Pass 2: Copy sum from right neighbor back to current node
    for node in octree.leaves():
        right_neighbor = node.get_neighbor('right')
        if right_neighbor:
            node.data = right_neighbor.data # Copy values for coherence [S2]
            
    # Repeat similar logic for Y and Z axes [S2]
    # Y-axis passes
    for node in octree.leaves():
        top_neighbor = node.get_neighbor('top')
        if top_neighbor:
            top_neighbor.add_data(node.data)
    for node in octree.leaves():
        top_neighbor = node.get_neighbor('top')
        if top_neighbor:
            node.data = top_neighbor.data
            
    # Z-axis passes
    for node in octree.leaves():
        front_neighbor = node.get_neighbor('front')
        if front_neighbor:
            front_neighbor.add_data(node.data)
    for node in octree.leaves():
        front_neighbor = node.get_neighbor('front')
        if front_neighbor:
            node.data = front_neighbor.data
```

**Parameters:**
*   **Light-View Map Resolution:** Typically higher than the lowest level of the voxel grid to avoid gaps [S1].
*   **Texture Format:** 16-bit normalized format to enable atomic additions [S1].

**Edge Cases and Pitfalls:**
*   **Atomic Operations:** Atomic add operations are only available for integer textures in many hardware APIs. Using 16-bit normalized textures requires denormalization when accessing values later [S1].
*   **Thread Collisions:** Copying photons directly to all required locations in adjacent bricks leads to significant thread collisions and bandwidth issues [S1]. The six-pass neighbor transfer scheme avoids this [S2].

## Subtopics

### Value Transfer to Neighboring Bricks
This variant addresses the inconsistency of duplicated voxels at brick boundaries. It uses six passes (two per axis) to transfer data between neighbors. First, data is added from the current node to the right (or up/forward) neighbor. Second, the sum is copied back to the current node. This ensures coherence along each axis without requiring atomic operations or causing thread collisions, making it more efficient than direct copying [S2].

## Operating characteristics
*   **Time Complexity:** The splatting phase is $O(N)$ where $N$ is the number of pixels in the light-view map. The boundary resolution phase is $O(M)$ where $M$ is the number of leaf nodes, involving a constant number of passes (6) [S1, S2].
*   **Memory Complexity:** Depends on the size of the octree and the amount of photon data stored per leaf. The use of 16-bit normalized textures helps manage memory bandwidth [S1].
*   **Performance:** The method is efficient for capturing direct illumination in real-time or interactive settings. The neighbor transfer scheme significantly reduces performance degradation caused by thread collisions and bandwidth issues associated with redundant voxel storage [S1, S2].
*   **Strengths:** Efficient handling of sparse voxel structures; avoids complex atomic operations on non-integer formats; resolves boundary inconsistencies effectively [S1, S2].
*   **Limitations:** Requires pre-computation or capture phase; static lighting information unless re-captured [S1].

## Background
Photon Splatting was introduced in the context of Interactive Indirect Illumination Using Voxel Cone Tracing by Nishita et al. (2011) [S1, S2]. It builds upon earlier work on capturing direct illumination [DS05] (cited in [S1]). The method is part of a broader framework for real-time global illumination using voxel cone tracing [S1].
