# Min/Max Tree Construction

Also called: Acceleration Structure Build, Extrema Tree, GPU Min/Max Tree Construction, GPU Pre-processing, Min/Max Cell Construction, Min/Max Octree Construction, Quasi-interpolation Prefiltering

## Overview
Min/Max Tree Construction builds a hierarchical acceleration structure embedded within an octree to accelerate ray traversal and volume classification by storing the minimum and maximum scalar values for each node [S1, S2]. It solves the problem of inefficient traversal in sparse or large-volume rendering by allowing the renderer to reject entire subtrees when the target isovalue or classification range falls outside the node's computed extrema [S1, S2]. Unlike sibling methods that may focus on structural compression or partitioning, this method specifically optimizes traversal speed by embedding scalar bounds directly into the tree topology, enabling early-out checks during ray casting [S4, unofficial].

## How it works
**Inputs and Outputs:**
*   **Input:** A 3D scalar voxel array (raw volume data) and an octree structure built via bottom-up consolidation [S1][S4, unofficial].
*   **Output:** An augmented octree where interior nodes store min/max pairs, serving as an acceleration structure for ray tracing [S1][S4, unofficial].

**Data Structures:**
The min/max tree is stored within the same octree structure used for voxel data [S1].
*   **Leaf Nodes:** Do not store min/max pairs explicitly to save space. Instead, bounds are computed on-the-fly from the 8 constituent voxels and their forward neighbors [S4, unofficial].
*   **Interior Nodes (Depth $d_{max}-1$ and above):** Store a min/max pair $(min, max)$ for each scalar field [S2][S4, unofficial].
*   **Cap Nodes:** Nodes at the maximal depth of the octree that contain 8 scalar values (voxels) [S4, unofficial].

**Algorithm Steps:**
1.  **Initialization:** Define the unclassified volume using size, voxel spacing, and raw voxel data [S2]. Initialize the octree structure [S2].
2.  **Cap Node Processing:** Retrieve scalar values from the original data only for cap nodes [S4, unofficial].
3.  **Leaf Bounds Computation:** For leaf nodes (or cap nodes acting as leaves in the logical traversal), compute the minimum and maximum of the 27 voxel values associated with the cell corner [S4, unofficial]. This includes the 8 voxels of the cell and their forward neighbors to handle boundary conditions and neighbor-finding [S4, unofficial].
    *   *Note:* If min/max pairs were stored at leaf nodes, storage would exceed three times the raw octree data size [S4, unofficial]. Therefore, they are omitted at the leaf level [S4, unofficial].
4.  **Bottom-Up Propagation:** Starting at depth $d_{max}-1$, compute the min/max pair for each parent node by taking the minimum of all children's minimums and the maximum of all children's maximums [S4, unofficial].
    *   Formula for node $P$ with children $C_0 \dots C_7$:
        $$ P.min = \min_{i=0}^{7} (C_i.min) $$
        $$ P.max = \max_{i=0}^{7} (C_i.max) $$
5.  **Recursive Consolidation:** When child voxels consolidate into a parent node during the octree build, remove the corresponding child nodes and update the parent's min/max based on the remaining children [S4, unofficial]. Repeat recursively until the root node is completed [S4, unofficial].
6.  **Parameter Configuration:**
    *   `base_node_size`: The size in voxels of one side of the smallest node in the octree. A value of 4 is a typical starting point [S2]. Smaller values provide better resolution at the expense of increased size [S2].
    *   `range` (for classification): A range of table indices considered 'small' for classification tables. Choosing a value too small or too large may reduce performance benefit [S2].

**Pseudocode:**
```python
def compute_min_max_tree(octree, raw_voxels, d_max):
    """
    Computes min/max bounds for the octree bottom-up.
    octree: The octree structure with nodes.
    raw_voxels: The original 3D scalar array.
    d_max: The maximum depth of the octree.
    """
    # Process from depth d_max - 1 up to root (depth 0)
    for depth in range(d_max - 1, -1, -1):
        nodes_at_depth = get_nodes_at_depth(octree, depth)
        for node in nodes_at_depth:
            if node.is_leaf():
                # Leaf nodes do not store min/max. 
                # Bounds are computed on-the-fly during traversal using 
                # the 8 voxels and forward neighbors [S4, unofficial].
                node.min = None
                node.max = None
            else:
                # Interior nodes compute bounds from children
                children = node.children
                if not children:
                    # Should not happen for interior nodes in a valid octree
                    continue
                
                # Initialize with extreme values
                min_val = infinity
                max_val = -infinity
                
                for child in children:
                    # If child is a leaf, its bounds are implicit.
                    # However, the parent's bound must cover the child's volume.
                    # In this implementation, children (even leaves) must have
                    # computed bounds to propagate up, OR we handle leaf 
                    # expansion here. 
                    # Based on [S4, unofficial]: "parent nodes are computed solely based 
                    # on children values". 
                    # Since leaves don't store values, we assume the 
                    # consolidation process ensures that when a parent is 
                    # formed, it aggregates the extrema of the consolidated 
                    # voxels. 
                    # For simplicity in this abstract:
                    if child.min is not None:
                        min_val = min(min_val, child.min)
                        max_val = max(max_val, child.max)
                    else:
                        # Fallback for leaf children: compute from raw data
                        # This matches the "cap node" logic in [S4, unofficial]
                        voxel_bounds = compute_leaf_bounds(child, raw_voxels)
                        min_val = min(min_val, voxel_bounds.min)
                        max_val = max(max_val, voxel_bounds.max)
                
                node.min = min_val
                node.max = max_val

def compute_leaf_bounds(node, raw_voxels):
    """
    Computes min/max for a leaf node based on 27 voxels (cell + forward neighbors) [S4, unofficial].
    """
    # Get the 8 voxels of the leaf cell
    voxels = get_cell_voxels(node, raw_voxels)
    
    # Get forward neighbors (positive X, Y, Z directions) to handle 
    # cell corner reconstruction [S4, unofficial]
    neighbors = get_forward_neighbors(node, raw_voxels)
    
    all_values = voxels + neighbors
    
    return {
        'min': min(all_values),
        'max': max(all_values)
    }
```

**Edge Cases and Pitfalls:**
*   **Storage Overhead:** Storing min/max pairs for every scalar voxel demands over three times the storage of the raw octree data [S4, unofficial]. To avoid this, min/max pairs are omitted at leaf nodes and stored starting at depth $d_{max}-1$ [S4, unofficial].
*   **Data Updates:** If the volume data changes, the min/max tree must be recomputed (e.g., via `vpCreateMinMaxOctree` in VolPack) or renderings will be incorrect [S2].
*   **Neighbor Finding:** Leaf nodes must account for forward-adjacent voxels to correctly compute cell corner extrema, requiring efficient neighbor-finding routines [S4, unofficial].

## Subtopics

### [AMR-KDTree Leaf Filtering](2732-amr-kdtree-leaf-filtering.md)
AMR-KDTree Leaf Filtering is a traversal optimization for Adaptive Mesh Refinement (AMR) volume rendering that accelerates isosurface extraction by pruning leaf nodes of an AMR-KDTree based on scalar value ranges [2732-amr-kdtree-leaf-filtering.md]. It builds on Min/Max Tree Construction but applies the filtering specifically to the leaf nodes of the AMR-KDTree structure, which represent regions of uniform brick origin [2732-amr-kdtree-leaf-filtering.md]. Unlike sibling methods that may filter at coarser levels or use complex bounding volumes, this method leverages the pre-computed min/max values of the finest-level cells within each leaf to immediately discard regions that do not contain the target isovalue, reducing redundant octant generation and vertex computation [2732-amr-kdtree-leaf-filtering.md].

### Min-Max Grid Preprocessing
Min-Max Grid Preprocessing is a preprocessing step that computes minimum and maximum data values for each block of a volume, stored as a 2-channel volume texture [S5]. This allows occupancy determination with a single texture lookup during the occlusion culling pass, where proxy geometry for occupied regions is determined [S5]. It can be recomputed on the fly for smaller volumes, such as when streaming time-varying data sets [S5].

## Operating characteristics
**Time and Memory Complexity:**
*   **Memory:** The min/max tree adds approximately 22% additional footprint on top of raw scalar octree-compressed data [S4, unofficial]. This is calculated as one min/max pair for 8 voxels plus pairs for other interior nodes [S4, unofficial]. The octree itself yields 3:1 or 4:1 lossless compression ratios [S4, unofficial].
*   **Time:** The construction is performed bottom-up during octree consolidation [S1]. GPU pre-processing (including min/max cell construction) can achieve speed-ups of up to ≈ 26-fold compared to CPU (e.g., 95.542s vs 3.555s for MRI-Head) [S3]. The gain from GPU pre-processing is roughly proportional to the size of the dataset [S3].

**Performance and Scaling:**
*   **Acceleration:** The structure allows rejecting children without traversing them, sparing cache misses [S4, unofficial]. It occupies an order of magnitude less memory footprint than a comparable kd-tree or hierarchical grid method [S4, unofficial].
*   **Strengths:** Significant reduction in traversal time for ray casting and classification [S1, S2]. Effective for large datasets where cache misses are a bottleneck [S4, unofficial].
*   **Limitations:** The 22% memory overhead is non-trivial [S4, unofficial]. Requires recomputation if data changes [S2]. Performance benefit depends on choosing an appropriate `base_node_size` and classification `range` [S2].

**When to Use:**
*   Use when rendering large sparse volumes with ray tracing or classification where isovalue ranges are known or constrained [S1, S2].
*   Use when memory bandwidth is a bottleneck and cache misses from traversal are significant [S4, unofficial].

**When Not to Use:**
*   Use when memory is extremely constrained and the 22% overhead is prohibitive [S4, unofficial].
*   Use when the volume data is static and small enough that simple traversal is sufficient [S4, unofficial].

## Background
The min/max tree was introduced as an acceleration structure for ray tracing implicit surfaces in interactive applications [S4, unofficial]. It was developed to allow efficient traversal of octree volumes by embedding scalar bounds directly into the tree structure [S4, unofficial]. The concept is also present in VolPack, where it is used to accelerate rendering unclassified volumes and computing classified volumes [S2]. GPU implementations have been developed to accelerate the pre-processing stages, such as quasi-interpolation and min/max cell construction, leveraging OpenCL for significant performance gains [S3].
