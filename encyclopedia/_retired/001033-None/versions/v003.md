# Voxel Memory Bank Allocation and Miniblock Organization

Also called: Miniblock Reordering for SDRAM, Voxel Memory Layout, Voxel Memory Organization (Miniblocks and Skewing)

## Overview
Voxel Memory Bank Allocation and Miniblock Organization is a hardware-oriented memory layout technique designed to maximize memory bandwidth and eliminate bank conflicts in SDRAM-based volume rendering systems [S1, unofficial]. It solves the problem of inefficient burst reads and simultaneous access conflicts by grouping voxels into small, linearly stored **miniblocks** and applying a two-level skewing scheme across memory modules and internal SDRAM banks [S1, unofficial]. Unlike standard interleaved layouts that may still suffer from bank collisions under arbitrary ray traversal, this method guarantees that adjacent miniblocks in any direction map to distinct memory resources, enabling conflict-free, back-to-back access [S1, unofficial]. It sets itself apart from its siblings by explicitly handling the transition from linear memory bursts to the slice-based processing requirements of rendering pipelines through de-skewing and reordering logic [S1, unofficial].

## How it works
The method maps 3D voxel coordinates $(u, v, w)$ to physical SDRAM addresses using a hierarchical structure of miniblocks, memory modules, and internal banks.

### Inputs and Outputs
*   **Input:** Volume data with arbitrary dimensions in host memory.
*   **Output:** A linear memory layout in Voxel Memory optimized for SDRAM burst access and conflict-free parallel retrieval.

### Data Structures and Layout
1.  **Miniblock:** A $2 \times 2 \times 2$ array of voxels. The 8 voxels are stored linearly in consecutive memory addresses within a single memory module [S1, unofficial].
2.  **Voxel Memory Dimensions:** The allocated volume dimensions must be multiples of 32 voxels ($2 \times 4 \times 4 = 32$) to ensure proper alignment of miniblocks and modules for optimum SDRAM performance [S1, unofficial]. Arbitrary host volumes are padded to these dimensions and automatically cropped during rendering [S1, unofficial].
3.  **Memory Modules:** The system uses four parallel memory interfaces/modules [S1, unofficial].
4.  **SDRAM Banks:** Each SDRAM chip contains four internal memory banks (based on 64-megabit SDRAMs) [S1, unofficial].

### Coordinate Mapping
Voxel coordinates $(u, v, w)$ are mapped to miniblock coordinates $(u_m, v_m, w_m)$ via integer division:
$$
u_m = \lfloor u / 2 \rfloor, \quad v_m = \lfloor v / 2 \rfloor, \quad w_m = \lfloor w / 2 \rfloor
$$
The memory location is determined by two modulo operations:
1.  **Module Index:** Distributes miniblocks across the four memory modules.
    $$
    \text{Module} \equiv (u_m + v_m + w_m) \bmod 4
    $$
2.  **Bank Index:** Distributes miniblocks within a module across the four SDRAM banks.
    $$
    \text{Bank} \equiv ((u_m \div 4) + (v_m \div 4) + (w_m \div 4)) \bmod 4
    $$
    Here, $\div$ denotes integer division and $\bmod$ denotes the modulus operator [S1, unofficial].

### Processing Steps
1.  **Storage:** Voxels are stored in Voxel Memory in $2 \times 2 \times 2$ miniblocks. Within a miniblock, voxels are stored sequentially to exploit SDRAM burst capabilities [S1, unofficial].
2.  **Distribution:** Miniblocks are distributed across memory modules such that any group of four adjacent miniblocks in any direction resides in separate modules [S1, unofficial].
3.  **Skewing:** Within each memory module, miniblocks are skewed so that adjacent miniblocks never fall into the same SDRAM bank [S1, unofficial].
4.  **Reading:** The Voxel Memory interface reads two slices of voxels at a time. Because data is organized in miniblocks, this read operation retrieves the necessary data for processing [S1, unofficial].
5.  **Reordering (Miniblock Level):** Miniblocks are rearranged based on the current view direction. This logic ensures that the positions of the voxels within the miniblock correspond to the canonical positions assumed for tri-linear interpolation [S1, unofficial].
6.  **De-skewing (Global Level):** The four miniblocks output by the Voxel Memory controllers are de-skewed and potentially re-shuffled by a global de-skewing network. This ensures spatial continuity: the left-most voxel along the x-axis flows down the leftmost pipeline, and adjacent voxels in x flow down neighboring pipelines [S1, unofficial].
7.  **Buffering:** The de-skewed miniblocks are written into the voxel slice buffers of the four rendering pipelines. The system stores three slices worth of data in these buffers to enable z-gradient computation using central differences [S1, unofficial].
8.  **Computation:** With the data in the slice buffers, interpolated samples and gradients can be computed without pipeline stalls [S1, unofficial].

### Pseudocode
```python
def map_voxel_to_memory(u, v, w):
    """
    Maps voxel coordinates (u, v, w) to a memory module and bank index.
    Assumes u, v, w are integers.
    """
    # Step 1: Convert voxel coordinates to miniblock coordinates
    # Miniblock size is 2x2x2
    u_m = u // 2
    v_m = v // 2
    w_m = w // 2
    
    # Step 2: Calculate Memory Module Index
    # Distributes miniblocks across 4 modules
    module_index = (u_m + v_m + w_m) % 4
    
    # Step 3: Calculate SDRAM Bank Index
    # Skews miniblocks within a module across 4 banks
    # Uses integer division by 4
    bank_index = ((u_m // 4) + (v_m // 4) + (w_m // 4)) % 4
    
    return module_index, bank_index

def process_voxel_memory_read(view_direction, slice_buffer_size=3):
    """
    Describes the data flow from Voxel Memory to Rendering Pipelines.
    """
    # 1. Read two slices of voxels at a time from Voxel Memory
    # Data is read in miniblock bursts (2x2x2 voxels)
    raw_miniblocks = read_miniblocks_burst()
    
    # 2. Reorder miniblocks based on view direction
    # Ensures canonical positions for tri-linear interpolation
    reordered_miniblocks = reorder_miniblocks(raw_miniblocks, view_direction)
    
    # 3. De-skew and re-shuffle via global network
    # Ensures x-axis adjacency maps to pipeline adjacency
    deskewed_miniblocks = global_deskew_network(reordered_miniblocks)
    
    # 4. Write to slice buffers
    # Buffer must hold 3 slices for z-gradient central differences
    write_to_slice_buffers(deskewed_miniblocks, slice_buffer_size)
    
    # 5. Compute samples and gradients
    samples = compute_interpolation_and_gradients()
    return samples
```

### Parameters and Edge Cases
*   **Volume Dimensions:** Must be multiples of 32 voxels. If the host volume is smaller, it is padded; if larger, it is partitioned into supervolumes (max 256 voxels per edge) with 3-voxel duplication at boundaries for correct interpolation [S1, unofficial].
*   **SDRAM Type:** Based on 64-megabit SDRAMs with 4 internal banks [S1, unofficial].
*   **Precision:** Integer arithmetic is used for all coordinate mappings.
*   **Pitfall:** Failure to pad volume dimensions to multiples of 32 will misalign miniblocks, degrading SDRAM burst performance [S1, unofficial].

## Subtopics

### [Skewed Memory Organization for Conflict-Free Ray Access](2351-skewed-memory-organization-for-conflict-free-ray-access.md)
Skewed memory organization is a hardware-oriented memory layout for Cubic Frame Buffers (CFBs) that maps 3D voxel data into $n$ memory banks such that any ray of $n$ voxels accesses exactly one voxel per bank, enabling conflict-free simultaneous retrieval in a single memory cycle. It sets itself apart from standard interleaved or tiled layouts by using linear modular arithmetic to guarantee parallel access for specific viewing directions, often combined with barrel shifting to support efficient geometric transformations.

### [Eight Logical Memories Architecture](7287-eight-logical-memories-architecture.md)
The Eight Logical Memories Architecture is a memory layout optimization for dense volume rendering that maps voxel data to physical SDRAM banks to minimize access latency. It solves the problem of bank conflicts and high switching times by grouping eight neighboring subcubes into a logical unit that spans two physical SDRAM devices, assuming four banks per SDRAM. It sets itself apart from the parent [Voxel Memory Bank Allocation and Miniblock Organization](1638-voxel-memory-bank-allocation-and-miniblock-organization.md) by introducing a hierarchical grouping of banks into logical memories, and from its sibling [Skewed Memory Organization for Conflict-Free Ray Access](2351-skewed-memory-organization-for-conflict-free-ray-access.md) by relying on coordinated precharging rather than spatial skewing to handle ray traversal.

### Cubic Addressing Scheme
A memory addressing scheme where the basic unit for address calculation is an $s^3$ sub-cube instead of a single voxel. Voxels are grouped into sub-cubes that fit into a row of an SDRAM [S2]. The sub-cube index is calculated by dividing x, y, and z coordinates by $s$, and the intra-sub-cube offset is found by taking the modulus by $s$ [S2]. Typical value for $s$ is 8 [S2]. This scheme achieves an 87.5% cache hit/miss ratio for ray casting along x, y, and z axes, as every eighth voxel requires a cache refresh [S2].

### Sixty Four Memories Architecture
An ideal solution using 64 independently accessible SDRAMs to achieve conflict-free memory access without pipeline stalls [S2]. It ensures no access penalty while crossing a page boundary by placing 2x2 neighborhoods across the boundary in four other SDRAMs not currently accessed, and precharging/activating SDRAMs 4-15 while accessing 1-4 [S2]. This architecture reaches the optimum of 10 ns access time and a 100% cache hit ratio [S2]. However, it requires the calculation and distribution of 64 independent addresses, which is expensive and exceeds PCI-Card board space budgets [S2].

## Operating characteristics
*   **Time Complexity:** Memory access is $O(1)$ per miniblock read, with constant-time arithmetic for address calculation. The de-skewing and reordering are hardware-based, adding negligible latency compared to memory access [S1, unofficial].
*   **Memory Complexity:** Requires padding volume dimensions to multiples of 32 voxels. For a volume of size $N \times N \times N$, the memory footprint is slightly larger than the raw data due to padding [S1, unofficial].
*   **Performance:** Enables burst rates of 4 interfaces $\times$ 133 MHz $\times$ 133 million voxels/second (approx. 532 million voxels/sec) when organized appropriately [S1, unofficial].
*   **Strengths:** Eliminates bank conflicts for adjacent miniblocks in any direction; maximizes SDRAM burst efficiency; supports real-time rendering of large volumes (up to 128 million 8-bit voxels) [S1, unofficial].
*   **Limitations:** Requires specific hardware support (VLI software, vg500 ASIC) for de-skewing and reordering; rigid dimension requirements (multiples of 32); limited to 256 voxels per edge per supervolume block without software partitioning [S1, unofficial].
*   **When to use:** High-performance, hardware-accelerated volume rendering systems using SDRAM with multiple banks.
*   **When not to use:** Software-only renderers without specialized memory controllers; scenes requiring frequent dynamic resizing of volume dimensions without padding overhead.

## Background
The method was developed for the VolumePro real-time ray-casting system by researchers at Mitsubishi Electric Research Laboratories (MERL) [S1, unofficial]. It was introduced in the paper "The VolumePro Real-Time Ray-Casting System" (TR99-19) to address the memory bandwidth bottlenecks of early 2000s hardware [S1, unofficial]. The design leverages the properties of 64-megabit SDRAMs, which were common at the time, and the vg500 ASIC, which integrated the memory controllers and de-skewing networks [S1, unofficial].
