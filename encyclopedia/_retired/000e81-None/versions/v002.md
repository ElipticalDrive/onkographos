# Ray-marched Shadows

Also called: Hard Shadow Casting, Hard Shadow Ray Marching, Hard Shadows, Hard Shadows via Sphere Tracing, SDF Shadow Ray Marching, SDF Shadows

## Overview
Ray-marched shadows determine if a surface point is occluded from a light source by performing sphere tracing along a ray directed from the surface point toward the light [S1, S2, S3, S8, S10, unofficial]. Unlike [Distance Color Blending](791-distance-color-blending.md) which blends colors based on depth, this method returns a binary occlusion factor (0 for shadow, 1 for light) by checking if the Signed Distance Field (SDF) drops below a threshold before the ray reaches the light [S7, S10, unofficial].

## How it works
**Inputs and Outputs:**
*   **Inputs:**
    *   `x`: The 3D surface point being shaded (obtained from the primary ray march) [S7, S9, unofficial].
    *   `lightPos`: The 3D position of the light source [S7, S10, unofficial].
    *   `f`: The scene's Signed Distance Function, where $f(p)$ returns the distance to the nearest surface at point $p$ [S7, S10, unofficial].
    *   `D`: The maximal ray traversal distance (typically the distance to the light source for point lights, or a large constant for directional lights) [S7, S10, unofficial].
    *   `t_min`: The initial traversal distance to prevent self-shadowing [S7, S10, unofficial].
    *   `epsilon`: The intersection threshold (e.g., $10^{-3}$ or $0.001$) [S7, S9, S10, unofficial].
*   **Outputs:**
    *   `shadowFactor`: A scalar value, typically 1.0 if not in shadow, and 0.0 (or a small value like 0.2) if in shadow [S7, S8, S10, unofficial].

**Data Structures:**
*   Not given in the sources.

**Numbered Steps:**
1.  **Initialize Ray:** Calculate the unit direction vector toward the light: $\mathbf{r}_{Ld} = \text{normalize}(\text{lightPos} - \mathbf{x})$ [S7, S10, unofficial].
2.  **Initialize Traversal:** Set current distance $t = t_{min}$ and distance to surface $d = 0$ [S7, S10, unofficial].
3.  **March Loop:** While $t < D$:
    a.  Evaluate the SDF at the current ray position: $\mathbf{p} = \mathbf{x} + t \cdot \mathbf{r}_{Ld}$. Compute $d = f(\mathbf{p})$ [S7, S10, unofficial].
    b.  **Check Intersection:** If $d < \epsilon$, the ray has hit a surface. Return 0 (in shadow) [S7, S10, unofficial].
    c.  **Advance:** Update $t = t + d$ [S7, S10, unofficial].
4.  **Return:** If the loop completes without hitting a surface, return 1 (not in shadow) [S7, S10, unofficial].

**Formulas:**
*   Shadow ray equation: $\mathbf{r}_S(t) = \mathbf{x} + t \mathbf{r}_{Ld}$, where $\mathbf{x}$ is the surface point, $t$ is the distance along the ray, and $\mathbf{r}_{Ld}$ is the unit vector from $\mathbf{x}$ towards the light source [S7, S10, unofficial].
*   Intersection condition: $d < \epsilon$ indicates a surface intersection [S7, S10, unofficial].

**Parameters:**
*   `epsilon`: Intersection threshold. Typical values: $0.001$ [S9, unofficial], $10^{-3}$ [S3, unofficial].
*   `t_min`: Initial step. Must be $> \epsilon$ to avoid self-intersection. Typical values: $0.1$ [S9, unofficial], or a small offset like $10^{-3}$ [S3, unofficial].
*   `D`: Max traversal distance. For directional lights, this is often an arbitrary large value or the scene bounding box diameter [S7, S10, unofficial].
*   `MAX_MARCH_STEPS`: Optional limit on iterations to prevent infinite loops. Typical value: 255 [S6, unofficial], 20 [S5, unofficial].

**Pseudocode:**
```python
def ray_marched_shadow(x, light_pos, scene_sdf, epsilon=0.001, t_min=0.1, max_dist=None):
    """
    Computes hard shadow for point x relative to light_pos using SDF sphere tracing.
    
    Args:
        x: vec3, surface point.
        light_pos: vec3, light position.
        scene_sdf: function, returns distance to nearest surface.
        epsilon: float, intersection threshold.
        t_min: float, initial step to avoid self-shadowing.
        max_dist: float, max traversal distance. If None, uses distance to light.
        
    Returns:
        float: 1.0 if lit, 0.0 if in shadow.
    """
    # 1. Initialize Ray
    light_dir = normalize(light_pos - x)
    
    # Determine max distance
    if max_dist is None:
        max_dist = length(light_pos - x)
        
    # 2. Initialize Traversal
    t = t_min
    d = 0.0
    
    # 3. March Loop
    while t < max_dist:
        # a. Evaluate SDF
        p = x + t * light_dir
        d = scene_sdf(p)
        
        # b. Check Intersection
        if d < epsilon:
            return 0.0  # In shadow
            
        # c. Advance
        t += d
        
    # 4. Return
    return 1.0  # Not in shadow
```

**Edge Cases and Pitfalls:**
*   **Self-Shadowing:** If $t_{min}$ is 0, the initial point $\mathbf{x}$ yields distance $d=0$ (since $\mathbf{x}$ is on the surface). This triggers the intersection condition $d < \epsilon$ immediately, incorrectly marking the point as in shadow [S7, S10, unofficial]. To fix this, the initial traversal distance must be set to $t_{min} > \epsilon$ [S7, S10, unofficial], or the ray origin must be offset along the surface normal: $\mathbf{x} + \mathbf{n} \cdot \text{offset}$ [S3, S8, unofficial].
*   **Precision:** Floating-point precision errors can cause jitter or incorrect occlusion near surfaces. Using a small $t_{min}$ and appropriate $\epsilon$ mitigates this [S7, S10, unofficial].

## Subtopics

### [Soft Shadow Ray Marching](1107-soft-shadow-ray-marching.md)
Soft Shadow Ray Marching computes a soft shadow factor along a ray by accumulating the ratio of the Signed Distance Field (SDF) height to the ray step distance, simulating area light penumbra. Unlike [Hard Shadow Ray Marching](1087-hard-shadow-ray-marching.md), which returns a binary occlusion result, this method attenuates illumination based on how close the ray passes to intervening geometry relative to the light's size.

### Local Light Shadow Removal
Local Light Shadow Removal addresses artifacts in depth-buffer ray tracing for local lights where pixels are wrongly shadowed [S12, unofficial]. Depth-buffer ray tracing causes phantom wedges because the depth buffer only stores the nearest surface, resulting in 16% of traceable pixels being wrongly shadowed [S12, unofficial]. Removing this pass fixes the artifacts without affecting sun or moon shadows [S12, unofficial].

## Operating characteristics
*   **Time Complexity:** $O(N)$ per light source per pixel, where $N$ is the number of sphere tracing steps. $N$ depends on the scene complexity and the distance to the light [S7, unofficial].
*   **Performance:** Hard shadows are straightforward to implement with SDFs compared to rasterization, requiring only one additional sphere trace per light source per pixel [S2, unofficial]. However, they add significant computational cost proportional to the number of lights, as each light requires a separate ray march [S2, unofficial].
*   **Strengths:** No aliasing artifacts associated with shadow maps (e.g., pixelation, peter-panning); shadows are resolution-independent and consistent with the SDF geometry [S7, S9, unofficial].
*   **Limitations:** Computationally expensive for multiple lights; hard shadows can appear aliased if the step size is too large relative to the geometry [S7, unofficial]. Soft shadows require careful tuning of the attenuation function [S9, unofficial].

## Background
Ray-marched shadows were popularized in the context of Signed Distance Field (SDF) ray marching for real-time graphics [S1, S9, unofficial]. The technique is described in "GPU Ray Marching of Distance Fields" (DTU, 2011) as Algorithm 3.2, attributed to IQ (Inigo Quilez) [S7, S10, unofficial]. It is a standard component of SDF-based renderers, often cited alongside basic sphere tracing [S1, S9, unofficial].
