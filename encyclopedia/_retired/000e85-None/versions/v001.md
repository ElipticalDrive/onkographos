# Multi-type Voxel Storage

Also called: HashMap-based Voxel Storage, VoxelKind Enum Storage

## Overview
Multi-type Voxel Storage extends the sparse grid alignment of [Voxel World Data Structure](1101-voxel-world-data-structure.md) by associating a material type with each occupied voxel, allowing distinct rendering or logic for different block kinds. It differs from sibling sparse structures by using a per-chunk hash map to store non-air voxels, where the absence of a key implicitly represents air, rather than storing a uniform block type or using dense arrays.

## How it works
**Inputs and Outputs:**
*   Input: World position (`IVec3`), optional material kind (`VoxelKind?`).
*   Output: Updated world state (chunk data).

**Data Structures:**
*   `Chunk`:
    *   `position`: `IVec3` (chunk coordinates).
    *   `voxels`: `HashMap<IVec3, VoxelKind>` mapping local 3D integer coordinates to material types.
    *   `mesh`: Reference or handle to the generated mesh geometry.
*   `VoxelKind`: An enumeration defining material types (e.g., `Dirt`, `Stone`, `Air`).
*   `World`:
    *   `chunks`: `HashMap<IVec3, Chunk>` mapping chunk positions to chunk objects.

**Constants:**
*   `CHUNK_SIZE`: 32 (integer).

**Steps:**

1.  **Chunk Addressing:** Given a world position $P$, calculate the chunk position $C$ and local position $L$ using Euclidean division and remainder:
    $$ C = \lfloor P / 32 \rfloor $$
    $$ L = P \pmod{32} $$
    Note: The sources use `div_euclid` and `rem_euclid`, ensuring correct handling of negative coordinates.

2.  **Chunk Retrieval:** Retrieve the chunk at $C$ from the world's chunk map. If it does not exist, create a new chunk at $C$ (see Generation below).

3.  **Voxel Update:**
    *   Invalidate the chunk's mesh by setting `chunk.mesh = None`.
    *   If the requested `kind` is `None` (air):
        *   Remove $L$ from `chunk.voxels`.
    *   If the requested `kind` is not `None`:
        *   Insert the pair $(L, \text{kind})$ into `chunk.voxels`.

4.  **Chunk Generation (Lazy):** When creating a new chunk at $C$:
    *   Initialize an empty `HashMap<IVec3, VoxelKind>`.
    *   Iterate $x, y, z$ from 0 to 31.
    *   Calculate world position $W = C \times 32 + (x, y, z)$.
    *   Apply generation rules:
        *   If $W.y == 0$, insert $( (x,y,z), \text{Dirt} )$.
        *   If $W.y < 0$, insert $( (x,y,z), \text{Stone} )$.
        *   Otherwise, do not insert (implicitly air).

**Pseudocode:**

```python
CHUNK_SIZE = 32

def set_voxel(world, position, kind):
    # Calculate chunk and local coordinates using Euclidean division
    chunk_pos = position // CHUNK_SIZE
    local_pos = position % CHUNK_SIZE
    
    # Ensure chunk exists
    chunk = get_or_create_chunk(world, chunk_pos)
    
    # Invalidate mesh to force regeneration
    chunk.mesh = None
    
    if kind is None:
        # Remove voxel if it exists; absence implies air
        if local_pos in chunk.voxels:
            del chunk.voxels[local_pos]
    else:
        # Insert or update voxel type
        chunk.voxels[local_pos] = kind

def get_or_create_chunk(world, chunk_pos):
    if chunk_pos not in world.chunks:
        chunk = Chunk()
        chunk.position = chunk_pos
        chunk.voxels = {}
        
        # Generate initial terrain for new chunks
        for z in range(CHUNK_SIZE):
            for y in range(CHUNK_SIZE):
                for x in range(CHUNK_SIZE):
                    offset = IVec3(x, y, z)
                    world_pos = chunk_pos * CHUNK_SIZE + offset
                    
                    if world_pos.y == 0:
                        chunk.voxels[offset] = VoxelKind.Dirt
                    elif world_pos.y < 0:
                        chunk.voxels[offset] = VoxelKind.Stone
                    # else: air (not stored)
        
        world.chunks[chunk_pos] = chunk
    
    return world.chunks[chunk_pos]
```

**Edge Cases and Pitfalls:**
*   **Negative Coordinates:** Standard integer division truncates towards zero in many languages, but `div_euclid`/`rem_euclid` is required for correct chunk addressing in negative space [S1].
*   **Mesh Invalidation:** Every voxel change requires mesh invalidation. Frequent updates can cause performance issues if mesh generation is expensive [S1].
*   **Hash Map Overhead:** Using a hash map for every chunk introduces memory overhead compared to dense arrays, though it saves space in sparse regions [S1].

## Subtopics

### [Typed Voxels](1399-typed-voxels.md)
Associates a specific type enum with each voxel to distinguish materials. Use when different materials require different rendering or physics properties.

## Operating characteristics
*   **Time Complexity:** Lookup and insertion are $O(1)$ average case for hash maps. Chunk generation is $O(CHUNK\_SIZE^3)$, but only occurs once per chunk.
*   **Memory Complexity:** $O(N)$ where $N$ is the number of non-air voxels. Overhead includes hash map entries and chunk objects.
*   **Strengths:** Efficient storage for sparse worlds; easy to add new material types via enum extension.
*   **Limitations:** Mesh regeneration on every change can be costly; hash map iteration order is undefined, which may affect deterministic rendering or physics if not handled.
*   **When to use:** Small to medium worlds with varied terrain and frequent voxel changes.
*   **When not to use:** Extremely dense worlds (use dense arrays) or worlds requiring massive concurrent chunk updates without mesh invalidation overhead.
